# Web 主链驱动交互模型

## 1. 设计目标

装得清要让企业“装得清、看得清”：使用者沿客户、房屋、合同、项目和工地理解业务，不靠记忆一级模块或寻找散落功能。Web 的价值是让同一事实被更快地看到、核对和批量推进。

## 2. 四个锚点与一条事实链

```text
客户锚点：线索、负责人、跟进、房屋、机会
房屋锚点：量房、设计、报价、合同、项目
合同锚点：报价快照、签约基线与签约价调整、变更、收款节点
项目/工地锚点：阶段、任务、动态、材料、验收、整改
账务事实链：报价快照 -> 合同基线 -> 应收/应付 -> 收付 -> 成本 -> 结算/利润
```

任何一级模块页面都应能回到锚点，任何锚点视图都应能展开完整事实链；不得让用户在不同菜单中手工拼装同一项目。

## 3. 系统的下一动作

每个对象页首屏优先回答：

1. 现在处于什么业务状态？
2. 当前由谁负责，多久未推进，是否逾期？
3. 下一步最合理的业务动作是什么？
4. 为什么不能继续，缺哪个前置事实或权限？
5. 完成后会写回哪些对象、状态、金额或通知？

“下一步”必须由后端正式状态、前置条件和权限推导；前端不得自行猜测状态机或绕过服务端校验。若需要新增“推荐动作/阻断原因/下一责任人”等业务字段，先走业务咨询和正式设计。

## 4. Web 双壳层职责

### 经营管控层（Boss）

- 首屏是决策信息：经营结果、趋势、结构、风险和待决事项。
- 每个数字必须带口径、周期、截止时间（`asOf`）和来源。
- 只承载决策与下钻，不承载普通员工的批量录入。
- 下钻到对象页后，沿用同一对象骨架和同一事实。

### 岗位执行层（StoreManager / TeamLeader / Marketer / Designer / Pm / ProjectSupport / Finance）

- 首屏是行动队列：今天必须处理什么、卡在哪里、谁负责。
- 角色工作台优先，专业列表作为深链接和批量操作入口。
- 岗位执行聚焦批量、对账、排期、审核和跨角色交接——即 App 不擅长的事。

### 共享对象层

所有角色共享统一对象骨架：

```text
对象身份
+ 状态轨道
+ 下一步
+ 事实摘要
+ 关联对象
+ 操作记录
+ 时间线
```

Boss 和员工看到同一对象，区别只在权限、字段、动作和默认排序。

## 5. 信息层级与交互规则

- 一个页面只有一个主行动；次要动作降级为描边、文字或更多菜单。
- 状态、责任人、时间、金额/风险、下一动作按任务重要性排序。
- 表单按业务阶段分组，不一次铺满大型 ERP 全字段；低频专业字段按需展开。
- 错误必须说明“发生了什么、为什么、如何恢复、谁负责”，不能只弹“操作失败”。
- 列表用于定位，详情用于推进；不要要求用户从列表跳多个菜单才能完成同一业务动作。
- 页面切换后回到原业务上下文，保留租户、项目、房屋、筛选项和操作进度。
- 高影响动作（签约、收款、付款、验收确认、删除、批量改价、权限变更）必须前置条件可见、二次确认、幂等和审计留痕。
- 关键路径必须可仅用键盘完成；焦点可见、顺序合理、弹层可 Esc 关闭并归还焦点。

## 6. 双端分工（Web 与 App）

| 场景 | 首选端 | 说明 |
| --- | --- | --- |
| 现场拍照、留证、签到、即时确认 | App | 手机在现场，Web 不复制该主路径 |
| 批量录入、对账、排期、导出、经营分析、多栏对比 | Web | 宽屏优势必须转化为更少步骤 |
| 客户沟通与业主确认 | App / 业主端 | Web 只做内部查看和代录入口 |
| 审批与纠偏 | 双端 | 同一事实、同一权限、同一结果 |
| 深度配置（模板、规则、组织、权限、报价库） | Web | 变更必须写审计且可回滚 |

同一业务动作在两端都能完成时，必须使用同一 Provider、同一状态机和同一金额口径；禁止 Web 自行计算或另存一份规则。

## 7. 多分辨率与浏览器验收

- 至少覆盖 1440×900、1280×800、1024×768；需要时补充 1920×1080 和窄屏（≤768）降级表现。
- 检查长企业名、长中文、金额、日期、空状态、加载、失败、权限不足、超长表格、横向滚动和弹层遮挡。
- 表格必须验证列宽、固定列、分页、排序、空数据、超长文本换行与表头对齐。
- 禁止：文字截断无提示、卡片互相覆盖、按钮跳出可视区、非预期横向滚动、浮层遮挡主操作、颜色是唯一状态标识。
- 浏览器至少覆盖 Chrome；如产品承诺则补充 Edge/Safari 关键路径。

视觉与交互问题必须提供分辨率、角色、页面、URL、截图和具体溢出/遮挡证据。

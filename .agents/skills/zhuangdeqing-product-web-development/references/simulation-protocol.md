# 真实 Web 应用模拟协议

## 1. 模拟目标

模拟不是“逐页点一遍”，而是让角色带着业务目标完成跨对象、跨状态、跨端、跨账务事实的任务，并记录系统在何处帮助或阻碍了人。

Web 侧额外关注：宽屏信息密度是否真的减少操作步数，而不是把同一功能摊开成更多格子；批量、对账、排期和经营分析是否比 App 更高效；同一事实是否与 App 一致。

## 2. 租户画像

全链批次至少并行运行以下三个合成企业；单项需求可取其中最相关的两个。

### T-A 单店成长型

- 10–15 人，1 家店，在施 3–8 个。
- Boss 同时看经营和关键审批；角色边界容易重叠。
- 重点验证：上手成本、角色工作台、报价到回款、现场履约、经营总览是否可用。

### T-B 2–3 店成长型

- 20–30 人，2–3 家店，多个团队并行。
- 存在员工调店、调团队、客户/项目转交和跨店协作。
- 重点验证：Company/Store/Team/Self、归属快照、跨店隔离、经营汇总和门店对比。

### T-C 小团队共创型或边界企业

- 3–8 人，角色兼任明显，数据容易不完整。
- 作为问题发现样本，不证明主流市场结论。
- 重点验证：缺失数据、历史迁移、职责兼任、异常恢复和低学习成本。

每个画像必须记录企业、门店、团队、员工、客户、房屋、项目、供应商和财务账号映射，禁止复用生产客户隐私。

## 3. 角色任务卡

| 角色 | 登录后必须先看到什么 | 核心动作 | 禁止越界 |
| --- | --- | --- | --- |
| Boss | 经营结果、风险、待决事项、资金与利润 | 审批、授权、经营纠偏、下钻 | 不代表可跳过业务前置条件 |
| StoreManager | 本店转化、项目、团队和收款风险 | 分配、审批、盯办、门店绩效 | 不得看其他门店越权数据 |
| TeamLeader | 团队客户、转化、履约和业绩 | 分派、辅导、推进 | 不得突破团队范围 |
| Marketer/家装顾问 | 今日跟进、待量房、黄金期客户 | 登记、跟进、约量房、批量录入 | 不拍板报价/施工 |
| Designer | 待设计、待报价、待客户决策、变更影响 | 设计、报价、解释、提交 | 不直接改合同/财务结果 |
| Pm | 今日开工/节点、逾期、质量、验收、材料 | 排期、留证、报事、申请验收 | 不改设计价格和财务归属 |
| ProjectSupport/材料 | 材料计划、采购、到场、异常 | 计划、采购协同、确认到场、库存 | 采购执行价与成本权限分离 |
| Finance | 应收、收款、应付、付款、结算、异常 | 记账、核对、结算、台账导出 | 不修改原始业务事实来平账 |
| 业主（只读/确认） | 本人进度、待确认、验收和整改结果 | 查看、确认、提出异议 | 不得看到其他客户或内部成本 |

每个角色任务卡必须包含 `触发事件 -> 当前动作 -> 系统下一步 -> 异常处理 -> 完成证据`。

## 4. 0-1 主链案例

使用合成客户与房屋案例，禁止将示例贴到生产账户或对外材料。

### 正常链

```text
企业入驻 -> 团队邀请/角色建立
-> 线索登记/分配 -> 客户 -> 房屋 -> 跟进/量房
-> 设计诉求/方案 -> 报价选择项目库/自定义价格标记/快照/导出
-> 客户决策（直接签约补录时生成签约基线报价）
-> 合同/签约价调整/签约生效 -> 项目立项
-> 施工计划/工地 -> 增减项 -> 动态/日报/问题
-> 验收 -> 整改 -> 复验 -> 应收/收款/应付/付款 -> 结算/利润/经营看板
```

Web 侧必须额外验证：

- 同一客户在 App 与 Web 的责任人、阶段、金额和下一步一致。
- 角色切换（登录不同员工）后菜单、路由守卫、列表范围和详情动作同时收敛，不只是菜单隐藏。
- 批量操作、导出和批量删除有范围提示、结果反馈和失败明细。
- 深链接（复制 URL、刷新、直开详情）在会话有效/失效两种情况下行为正确。

### 拒绝/返工链

至少覆盖：

- 报价被拒并形成新版本，旧版本不被覆盖。
- 签约价调整必须形成可解释快照，不能无痕改写报价。
- 合同变更影响项目金额和后续履约基线。
- 成本不完整时利润为空并显示“成本未完整”。
- 材料延期、现场质量整改、业主拒绝验收和逾期回款。

### 跨企业负向链

至少覆盖：

- 租户 A 伪造租户 B 对象 ID 查询、更新、删除和导出。
- 跨门店、跨团队、非项目参与人访问。
- 直接输入 URL / 修改路由参数 / 修改请求参数 / 历史 token / 批量导出越权。
- 两租户并发创建、变更、收款和结算不串事实。

## 5. 并行推进方式

同一批次可并行，但事实必须隔离：

```text
租户主线：T-A 正常链 | T-B 多店/转交链 | T-C 兼任/缺数据链
业务支线：报价决策 | 合同变更 | 材料/应付 | 现场/验收/整改
负向支线：跨租户 | 跨门店 | 跨团队 | 重复/并发 | 回退 | 深链接
```

每个任务是独立样本，不允许跨租户拼接角色或数据。

## 6. 证据粒度

每步至少记录：

- 租户、角色、浏览器与窗口分辨率、时间、URL 和操作入口。
- 业务对象 ID/展示编号、前置状态和操作动作。
- 页面反馈、接口/状态码、服务端状态变化和账务写入。
- 截图（含整屏与关键区域）；敏感信息必须脱敏或使用合成数据。
- 期望结果、实际结果、偏差、影响和恢复路径。
- 若涉及金额：来源、公式、快照时点、缺失值处理和跨页一致性。

## 7. 问题分级

- `P0`：越权、跨租户泄漏、资金/成本错误、主链错误、数据不可恢复。
- `P1`：关键角色无法完成任务、状态失配、重复记账、异常无恢复。
- `P2`：明显增加工作量、跨端口径不一致、交互误导、适配阻塞。
- `P3`：文案、视觉层级、低风险一致性或可访问性问题。

体验问题不得只写“排版乱”“操作繁琐”，必须对应具体角色任务和业务损失。

# 数据权限与操作权限审查

## 权威依据

1. 项目 `AGENTS.md`。
2. `rules.md` §0.2、§4.2.1、§5。
3. `docs/design/07-数据权限设计规范.md`。
4. `docs/design/16-项目权限与合同变更履约落地说明.md`。
5. `docs/design/08-财务域业务闭环设计.md`。
6. 业务知识库 `BR-003` 及当前采购、财务相关验收证据。

规则存在不代表链路已经验收。任何“已隔离”结论至少要同时有实现路径、负向测试和可观察结果。

## 三条不可混淆的边界

```text
企业隔离：任何企业数据永远不能跨 com_id。
数据范围：Company / Store / Team / Self / ProjectParticipation 决定“能查到什么”。
功能权限：角色、能力和状态决定“能执行哪个动作”。
```

`@ServiceProperties`、菜单、路由、按钮和响应字段裁剪只控制“返回什么”，不控制“查得到什么”，不能代替服务端数据权限。

## 角色基准

| 角色 | 默认数据范围 | 审查重点 |
| --- | --- | --- |
| Boss | Company | 能管理全企业；但不应绕过不可变流水、审计和已确认快照 |
| StoreManager | Store | 只处理本门店；财务域只能按正式口径只读或受限 |
| TeamLeader | Team | 只处理本团队；不能借成员详情扩到其他团队 |
| Marketer | Self + 已分配客户/房屋 | 客户跟进和推进；不能看企业成本、毛利、财务和他人客户 |
| Designer | Self + 已分配客户/项目参与 | 设计、量房、报价；标准成本、供应商历史和毛利按业务口径限制 |
| Pm | Self + 项目参与关系 | 项目履约；参与关系本身不是财务或采购历史授权 |
| ProjectSupport | Self + 已分配项目/采购执行 | 下单、催货、到货；只可看当前执行价，不默认看成本历史和综合毛利 |
| Finance | 财务域功能范围 | 按财务域设计可处理本企业财务；`EmployeeRole=Finance` 当前映射为 `Self`，必须以专用 Provider 和验收证明企业财务范围，不能靠通用 Self 规则推断 |

### 已知高影响待决点

`EmployeeRole.Finance` 在代码中是 `DataScopeType.Self`，而财务域正式设计描述为“当前企业全部项目与企业费用”。这是范围映射与领域能力的差异，不能自行选择一边。上线前必须由业务智能体裁决并明确采用以下哪一种模式：

- 财务角色维持通用 `Self`，通过财务域专用 Provider 对财务对象应用企业范围；或
- 调整角色范围模型，使财务获得受控的企业级财务范围。

在裁决和负向测试完成前，不能把“财务能看到企业全部财务”写成已验证事实。

## 权限矩阵必须包含的列

```text
角色 | 登录企业 | 数据范围 | 对象 | 操作 | 状态前置 | 敏感字段 | 允许/拒绝 | 证据 | 复验条件
```

操作至少覆盖：

```text
read / list / detail / create / update / delete / export / count
approve / reject / execute / transfer / receive / pay / settle
view_standard_cost / view_execution_price / view_supplier_history / view_gross_profit
```

敏感字段必须逐项处理，不能把“采购价”作为一个字段：

| 信息 | 业务含义 | 默认敏感级别 |
| --- | --- | --- |
| 标准采购成本 | 报价成本和估算成本基线 | 高 |
| 当前采购执行价 | 当前采购单履约事实 | 中，按采购角色和项目范围 |
| 供应商历史报价 | 比价和采购策略 | 高 |
| 项目综合成本 | 多成本项汇总 | 高 |
| 项目毛利/毛利率 | 经营结果 | 高 |
| 财务账本/应收应付 | 企业资金事实 | 高 |

## 各领域的范围规则

### 客户与房屋

- 归属为 `company/store/team/owner`，业务负责人变化必须定义归属快照更新或保留策略。
- 销售、设计师按 Self 或已分配关系访问；项目参与关系不能反向成为客户域的无限授权。
- 客户转交、员工调店、调团队后必须验证旧数据可见性和新负责人访问结果。

### 报价、合同、项目与变更

- 派生对象必须从最近父对象继承企业、门店、团队和经营负责人。
- 项目经理、设计师、履约专员通过项目参与关系取得的权限是补充可见性，不得覆盖经营归属。
- 合同和报价属于高敏感对象；PM 参与项目不等于拥有改价、签约、变更金额和毛利的写入权。
- `info/update/delete` 和跨域读取必须使用 `DataScopeContext + DataScopeSpecification`，不得 `findById` 后补判断。

### 材料、采购与供应商

- 标准采购成本、供应商报价历史、项目毛利仅向已确认角色开放。
- 当前采购执行价按采购执行角色和项目范围开放，且不能被解释为综合成本或毛利。
- 采购、到货、应付必须同时校验企业、项目和供应商归属，防止跨企业拼接。

### 财务

- BOSS/Finance 的财务写权限、店长的只读边界和其他角色的拒绝边界必须分别测试。
- 收款、付款、应收、应付、台账和结算属于同一权限域，不能只保护列表而遗漏详情、导出、核销和统计。
- 汇总报表、首页卡片和消息通知同样是数据出口，必须验证不会泄漏其他门店、团队或企业数据。

## 容易漏掉的越权出口

- `count/sum/report/dashboard` 聚合查询。
- CSV、Excel、PDF 和图片导出。
- 模糊搜索、拼音搜索、全局关键字搜索。
- 详情、附件、预签名 URL、消息通知和站内信。
- 通过父对象 ID 查询子对象，或通过子对象反向展开父对象。
- 批量更新、批量审批、批量删除和批量导出。
- 缓存、异步任务、离线包、索引和定时报表。
- 离职、调店、调团队、强制交接和临时代管后的旧会话。

## 负向测试基线

每个权限领域至少覆盖：

1. BOSS 在本企业范围内可见，跨企业不可见。
2. StoreManager 只可见本门店，跨门店不可见。
3. TeamLeader 只可见本团队，跨团队不可见。
4. Marketer/Designer/Pm/ProjectSupport 在 Self 或参与关系内可见，超出后不可见。
5. 伪造 `companyId/storeId/teamId/empId/ownerId/projectId` 不能扩权。
6. 越权 `info/update/delete` 返回“不存在或无权访问”，不能泄漏对象是否存在。
7. 列表、计数、报表、搜索、导出、附件和通知使用同一权限边界。
8. 调店、调团队、转交和离职交接后的历史数据符合既定快照规则。
9. 普通员工不能通过组合查询拼出标准成本、供应商历史或企业毛利。
10. 财务范围差异经过业务裁决并有专用 Provider 测试。

## 审查结论

权限审查输出必须包含：

- 角色 × 数据范围 × 操作矩阵。
- 敏感字段可见性矩阵。
- 越权出口清单。
- 未通过的反向用例和复现证据。
- 无法判断的范围冲突，标记为业务咨询 `BLOCKED` 或建议 `GAP-*`。

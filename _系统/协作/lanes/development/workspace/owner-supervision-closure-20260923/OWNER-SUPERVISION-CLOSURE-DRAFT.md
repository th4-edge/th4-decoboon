# 装得清 · 业主端同频监管业务闭环设计草案

> 状态：业务/产品方案已形成，P0 纵向闭环已实现，待独立验收与业务口径确认
> 日期：2026-09-23
> 范围：业主端小程序 + 员工业务端响应链路
> 依据：用户本轮反馈、`SCN-003`、`SCN-010`、`BR-008`、`CAP-001`、当前后端/App 实现

## 1. 结论

当前业主端不是“同频监管端”，而是“项目只读页 + 阶段验收确认入口”。业主能提交意见、驳回验收，但员工业务端没有把业主意见作为一线项目事实持续呈现，导致：

- 业主提交的问题只进入后台验收/整改数据；
- 员工在项目详情、阶段详情、首页和项目经理待办中看不到“客户刚才提了什么”；
- 阶段状态被改写为 `Doing`，业务端显示“进行中”，掩盖了“整改中”这一事实；
- 没有独立的意见/投诉对象、处理状态、回应时限和业主可见反馈；
- 缺少让业主持续感知项目在推进的现场、材料、人员、变更、资金和服务细节。

## 2. 现有链路审计

### 2.1 已存在的事实

业主驳回阶段验收时：

```text
Acceptance: Pending -> Rejected
Acceptance.issues = 业主问题清单
AcceptanceRound.result = Rejected
AcceptanceRound.issues = 本轮问题
AcceptanceRound.rectificationOwner = 项目经理
AcceptanceRound.rectificationDueDate = 后端按类型计算
ProjectStage.status = Doing
```

后端整改清单 `project/acceptance/rectify/page` 会返回当前 `Rejected` 验收单，并包含问题、责任人、类型、截止日期和逾期天数。

### 2.2 断链位置

1. **项目详情不展示业主意见**
   - `subpackages/project/pages/detail.vue` 只展示项目概况、阶段、合同、任务和动态。
   - 业主驳回的 `issues`、整改轮次、责任人和截止日期没有进入项目主线卡片。

2. **阶段详情不展示整改事实**
   - `subpackages/project/pages/stage/detail.vue` 展示阶段状态和验收入口，但没有把 `Acceptance.issues`、`AcceptanceRound` 和处理状态作为阶段详情的一等事实。
   - 员工看到的是“阶段进行中”，不知道这是正常的施工过程，还是验收被打回后的整改过程。

3. **整改入口藏在“我的”页**
   - `pages/mine/index.vue` 只对 `boss/storeManager/teamLeader/pm/finance` 展示“整改跟进”。
   - 员工必须先知道去“我的”里找入口，项目经理首页、项目页和阶段页没有统一的待整改提示。
   - 因此从业务操作视角，业主已经提交，但员工端感知不到“这是一条必须处理的工作”。

4. **阶段状态语义被压缩**
   - `StageStatus` 只有 `Todo / Doing / Accepting / Done`。
   - `ProjectContext.confirmAcceptance` 在业主驳回后把阶段设置为 `Doing`。
   - 前端映射 `doing -> 进行中`，于是“验收驳回、待整改”被错误表达为正常“进行中”。
   - 这既影响业主看进度，也影响项目经理、店长、老板和财务判断真实交付状态。

5. **没有意见/投诉独立对象**
   - 当前只有验收问题 `issues`，没有“业主意见”或“客户投诉”的业务对象。
   - 非验收类问题，如沟通态度、现场文明、材料迟到、设计师答复慢、收费疑问，没有可提交、分派、跟进、回复和关闭的入口。
   - 问题只能塞进验收流程，导致业务语义不一致，也容易丢失。

6. **没有业主可见的处理反馈**
   - 业主提交后看不到：企业是否已读、谁在负责、何时响应、处理到哪一步、下一步是什么。
   - 没有“处理完成待业主确认”“业主仍不满意”“升级投诉”等状态。

## 3. 业务定位

业主端不是企业内部 ERP，也不是施工方工作台。它应承担四项权利：

1. **知情**：我看到项目正在发生什么，是否有风险。
2. **确认**：我知道哪些决定需要我确认，确认后影响什么。
3. **反馈**：我可以随时提出问题、意见或投诉，并看到处理过程。
4. **评价**：我能对阶段交付和服务质量留下可追溯反馈。

边界：

- 不开放成本、利润、内部报价成本、供应商底价。
- 不允许业主修改企业业务事实；业主的动作只产生自己的反馈、确认或验收结果。
- 业主的问题必须进入企业侧责任分派和时限管理，不能只停留在聊天记录。

## 4. 业主端目标操作闭环

### 4.1 总闭环

```text
进入项目
-> 看同频总览（今天/当前阶段/下一步/风险）
-> 看施工事实（现场照片、节点、材料、人员）
-> 参与需确认事项（验收、变更、选材、款项）
-> 提交意见/整改要求/投诉
-> 看受理、责任人、处理计划、时限和过程证据
-> 复验或确认解决
-> 形成项目档案与服务评价
```

### 4.2 七段业务操作

#### A. 项目同步

- 业主看到项目名称、地址、当前阶段、整体进度、计划完工时间和项目经理。
- 首屏回答三个问题：现在做什么、下一步是什么、是否有需要我处理的事。

#### B. 现场感知

- 阶段、区域、工艺任务、节点照片/视频、隐蔽工程留证和现场动态。
- 每张证据应带时间、执行人、所属阶段/任务和简短说明。

#### C. 事项确认

- 阶段验收确认/驳回；
- 设计变更、合同变更、材料选材确认；
- 涉及金额、工期、范围变化时，在确认前明确展示影响。

#### D. 意见与整改

- 业主可在项目/阶段/当前问题进行反馈。
- 验收驳回进入整改闭环：问题清单、整改类型、责任人、系统截止日期、整改轮次、整改前后证据。
- 非验收问题进入意见/投诉闭环。

#### E. 处理跟踪

每个业主反馈必须有：

```text
已提交 -> 已受理 -> 已分派 -> 处理中 -> 待业主确认 -> 已解决/已关闭
                           \-> 升级投诉 -> 负责人介入 -> 复核关闭
```

- 业主可见：受理时间、责任人、预计完成时间、最新进展、证据、逾期状态、下一步。
- 员工可见：我的待办、全店待办、项目风险、超时升级。

#### F. 复验与结论

- 整改后在原阶段、原验收单上追加轮次，不新建第二张验收单。
- 业主看到“本轮改了什么、由谁改、改后照片、是否解决上一轮问题”。
- 业主确认通过后，阶段完结；再次驳回则继续追加轮次。

#### G. 服务评价与档案

- 阶段完成后评价：施工质量、设计落地、沟通响应、现场文明、工期履约。
- 形成业主可见的项目服务档案和问题闭环记录。
- 纠纷、售后、维保等后续事项可继续追踪。

## 5. 状态与语义修正

### 5.1 阶段状态

建议不能再用 `Doing` 统一表达“正常施工”和“被驳回待整改”。推荐二选一：

1. 新增阶段状态 `Rectifying（整改中）`；
2. 保留底层 `Doing`，但在项目/阶段投影上增加 `rectificationStatus=Rectifying`，前端优先展示“整改中”。

业务展示口径：

```text
施工中：按计划执行，没有验收驳回事实
待验收：阶段任务完成，等待业主确认
整改中：验收单 Rejected，存在未关闭整改要求
已完成：验收单 Confirmed
```

整改中不能覆盖原施工事实，但必须覆盖当前阶段状态展示。

### 5.2 业主反馈状态

建议统一领域对象 `OwnerFeedback`，用 `feedbackType` 区分意见、整改、投诉：

| feedbackType | 示例 | 默认处理方向 |
| --- | --- | --- |
| Quality | 瓷砖空鼓、收口不严 | 项目经理 |
| Design | 插座位置、柜体颜色与方案不一致 | 设计师/项目经理协同 |
| Material | 材料迟到、规格不符 | 项目经理/财务协同 |
| Schedule | 工期拖延、无人施工 | 项目经理/店长 |
| Service | 沟通慢、态度、文明施工 | 店长/企业负责人 |
| Fee | 款项疑问、变更费用 | 财务/企业负责人 |
| Safety | 现场安全、消防、公共区域风险 | 项目经理/企业负责人 |
| Other | 其他意见 | 按内容分派 |

该对象可以是验收问题的补充，也可以独立存在；验收驳回仍保留在 `AcceptanceRound`，非验收意见/投诉走 `OwnerFeedback`。

## 6. 岗位与响应规则

| 角色 | 对业主反馈的职责 |
| --- | --- |
| 项目经理 | 第一响应人和现场质量/进度负责人；不能忽略客户反馈 |
| 设计师 | 处理设计解释、方案调整、落地差异 |
| 财务 | 处理款项、变更费用、材料应付相关问题 |
| 店长 | 督办、升级、跨项目资源协调 |
| 企业负责人 | 高风险投诉、重大服务问题、最终兜底 |
| 业主 | 提交、补充证据、确认解决或继续不满意 |

业主提交后，系统必须至少产生：

1. 企业侧待办；
2. 责任人通知；
3. 项目详情上的可见标记；
4. 业主侧处理进度；
5. 到期未处理升级；
6. 解决后的业主确认或关闭结论。

## 7. 业主可见的“服务感知”内容

### 7.1 首页

- 今天工地发生了什么；
- 当前施工阶段和下一步；
- 我需要确认/评价/补资料的事项；
- 当前风险与处理中的问题。

### 7.2 项目页

- 施工计划 vs 实际时间；
- 阶段验收状态与整改轮次；
- 现场影像、隐蔽工程照片、材料到场；
- 项目服务人员：设计师、项目经理、督导/负责人。

### 7.3 问题中心

- 我的意见/整改/投诉；
- 处理中 / 待我确认 / 已解决；
- 谁在处理、多久响应、是否逾期；
- 处理过程证据；
- 争议升级入口。

### 7.4 资金与变更

- 合同金额、已收款、未收款、下期应收节点；
- 变更前金额、变更金额、变更后合同金额；
- 变更是否影响工期、材料、验收；
- 不展示企业内部成本和利润。

### 7.5 服务评价

- 阶段质量；
- 设计落地；
- 沟通响应；
- 现场文明；
- 工期履约；
- 是否愿意推荐。

## 9. 业务场景闭环（至少两个真实中小装企场景）

### 场景一：防水验收被驳回

- 使用人：业主。
- 触发：闭水试验后查看现场照片，发现楼下渗水隐患。
- 当前动作：提交整改意见并上传图片，指定整改类型。
- 系统下一步：生成验收轮次，标记阶段为整改中，生成项目经理待办和通知；项目经理整改后提交整改说明与照片；业主复验确认。
- 异常：项目经理为空或超时未处理时，升级到店长/企业负责人。

### 场景二：非验收阶段的设计插座位置问题

- 使用人：业主。
- 触发：施工现场照片显示插座位置与设计确认不一致。
- 当前动作：在项目中提交“设计意见”，上传现场照片，期望在木工前调整。
- 系统下一步：按设计类型分派设计师，项目经理知悉；设计师回复调整方案和影响，业主确认后进入现场执行。
- 异常：若业主不同意调整方案，升级为投诉并保留原决策记录。

### 场景三：材料延期影响工期

- 使用人：业主。
- 触发：业主看不到材料到场，询问进度。
- 当前动作：提交“材料/工期意见”。
- 系统下一步：财务/项目经理确认采购与到场状态，更新预计到场日期和工期影响，业主可见最新承诺。
- 异常：连续超期时升级店长督办，不能以“进行中”掩盖延误。

## 10. 验收标准

### 可见性

- 业主驳回后，项目经理、店长、企业负责人均可在项目详情和待办中看到问题。
- 员工不能通过返回上一页或重新进入项目“丢失”整改事实。
- 阶段显示为“整改中”，直至业主确认通过。

### 状态

- 整改中阶段不能显示为普通“进行中”。
- 业主提交意见后，必须能查到处理状态、责任人和下一步。

### 权限

- 其他企业、未授权项目、非参与员工不能查看业主意见。
- 业主只能查看自己的项目和自己的反馈。

### 金额边界

- 业主反馈与整改过程不改变合同、成本、应收应付、结算和利润，除非另行发起合同变更并完成确认。

## 11. 待业务裁决

1. 意见、整改、投诉是否统一为一个 `OwnerFeedback` 对象，还是投诉独立主对象。
2. 阶段是否新增 `Rectifying` 状态，还是仅在投影层增加“整改中”。
3. 各类意见/投诉的默认响应时限和升级规则。
4. 哪些投诉必须由店长/企业负责人介入。
5. 业主“已解决”的确认方式：业主确认、超时自动关闭，还是企业关闭+业主可复议。
6. 服务评价是否进入项目经理绩效和企业经营看板。

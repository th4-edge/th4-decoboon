## 2. 关键学习

### 2.1 B 端首先是效率产品

途牛商旅样本最关键的结论：

- C 端常见流量思维，B 端更强调效率思维；
- 用户目标明确时，设计应尽量不打扰；
- 三个首页原型中，视觉感更强的方案 B 没有胜出，最平实直叙的方案 A 更适合真实操作；
- 设计目的是让用户更快完成工作，不是展示设计技巧；
- B 端用户研究要理解企业层级、管理层诉求和终端层诉求。

对装得清的启发：

- 第一屏不应该像品牌首页；
- 不需要用大面积视觉语言证明“高级”；
- 最短路径、低干扰、清晰对象和动作优先；
- 设计说明和业务边界不应占据工作界面。

### 2.2 功能性 > 表现力

《B端产品设计思路&高频设计要点笔记》明确提出：

- B 端用户首先关心里实际工作带来什么便利，而不是界面多好看；
- B 端设计要理解业务流程、角色职责和用户画像；
- 设计目标是提高效率、降低业务链路操作和学习成本；
- 表单、表格和按钮要围绕可读性、易操作和稳定性；
- 数字右对齐、文本左对齐、列宽考虑极限值；
- 设计规范需要覆盖状态、异常、加载、禁用和极端内容。

对装得清的启发：

- 先证明页面减少步骤、判断或错误，再谈视觉；
- 说明性文案不属于业务工作面；
- 页面结构要能处理内容过多、空值、长文本和权限边界。

### 2.3 工作台不是仪表盘，是进入工作状态的导航

《B端工作台不会做？》把工作台定义为：

> 帮助用户快速掌握工作进展、进入工作状态的导能页面。

常见模块：

- 统计业务数据；
- 待办事项；
- 常用功能；
- 快捷入口；
- 消息通知；
- 新手引导和帮助中心；
- 个人/组织信息。

对装得清的启发：

- 工作台核心是“我现在应该做什么”，不是“我有多少张图表”；
- 数据要服务于判断，判断要连接到待办和对象；
- 快捷入口和待办队列应比大幅图表更接近工作台本质。

### 2.4 HAWK 的 UDO 模型

HAWK 用三组词描述商业工作台：

- **User Personas**：企业用户的分层画像；
- **Duty Driven**：基于工作职责和指标分解进行目标驱动设计；
- **Object Oriented**：将工作解构至最小对象。

对装得清的启发：

```text
角色 -> 职责 -> 指标 -> 业务对象 -> 动作 -> 结果
```

页面如果不清楚这个链条，只是把功能做成卡片，必然缺乏专业感。

### 2.5 复杂产品需要角色分层和多场景协作

EasyV 企业协作空间设计复盘强调：

- 从单一生产工具走向多场景协作平台；
- 目标用户不止设计师，还包括开发、产品经理、运营；
- 需要空间、团队、权限、组织概念；
- 设计流程覆盖调研、定义问题、设计目标、策略、方案和 4 次评审。

对装得清的启发：

- 老板、店长、设计师、项目经理、财务看到的是同一事实的不同工作面；
- 不能把一个角色的页面机械复制给所有角色；
- 权限和协作关系是 UI 结构的一部分，不是后端才关心的事；
- 设计评审必须覆盖产品架构、角色、权限和协作，而不只是视觉。

### 2.6 复杂流程要“清晰、易用、简洁”

智慧车站样本明确：

- B 端用户长时间操作并完成任务；
- 视觉必须克制、简洁；
- 功能为主，视觉服务于功能；
- 色彩、状态和层级要服务于快速识别与操作。

智慧工厂样本则区分：

- 管理者看宏观数据和透明化；
- 操作者看流程是否顺畅、操作是否方便；
- 从宏观模块进入微观工作台，从浅到深。

对装得清的启发：

- BOSS 驾驶舱看经营判断和风险；
- 店长看本店经营与执行；
- 设计师看方案和报价；
- 项目经理看现场和任务；
- 财务看款项、成本和口径。
- 不能用一个“万能大屏”替代所有角色工作面。

### 2.7 内容过多是专业 UI 的硬问题

《B端交互设计之内容太多怎么办》给出了大量硬规则：

- 标题截断、折行、先折后截；
- 文本最大宽度和 hover 提示；
- 弹层最大/最小宽高；
- 选项过多用分组、搜索、滚动；
- 按钮/标签过多用更多、箭头、渐进式设计；
- 表格列多时锁首列/操作列、横向滚动；
- 功能多用导航、页签、面包屑、抽屉收纳。

对装得清的启发：

- 专业 UI 不是把内容删到好看，而是对极限值给出明确交互规则；
- 长内容、选项多、按钮多、表格列多必须有规则，而不是靠“留白”掩盖；
- 渐进披露要连接真实任务，不是把所有内容都折叠起来。

## 3. AI 味从哪里来

从这些真实产品案例反推，AI 味通常来自：

1. 把每个模块做成独立卡片；
2. 每个标题都带小副标题；
3. 大量 pill、badge、英文 eyebrow；
4. 4 个通用 KPI 卡片 + 一张趋势图 + 一个风险列表的模板化组合；
5. 设计说明写成产品文案；
6. 没有真实对象和动作，只有“数据”和“洞察”；
7. 为了视觉丰富加入 2.5D/3D、装饰圆环、呼吸点；
8. 页面看起来像作品集封面或提案页，不像员工每天用的工具；
9. 每个模块都同等重要，没有角色职责和任务优先级；
10. 没有真实极限值、失败路径和恢复路径。

## 4. 2.5D/3D 的正确率反思

上一版 BOSS 驾驶舱的 2.5D 模块证明了一个问题：

- 它视觉上有空间感；
- 但它没有真实 CAD/BIM 数据；
- 它没有减少 BOSS 的判断步骤；
- 它不属于 BOSS 的主要职责工作面；
- 因此它是**负担设计**，不是加分设计。

新的结论：

- 2.5D/3D 只用于真正需要空间定位的项目、设计、材料、施工和验收页面；
- BOSS 驾驶舱优先用表格、趋势、风险队列和门店对比；
- 2.5D/3D 必须能说明比 2D 多解决了什么，否则移除；
- 不得为了“看起来不像传统后台”而强行加 3D。

## 5. 对装得清 UI 智能体的直接要求

1. 先做角色职责和任务链，再做页面。
2. 页面必须围绕对象、状态、动作、反馈和回读。
3. 产品文案只服务操作，不解释设计。
4. 删除不必要的卡片、pill、英文标题和说明性副标题。
5. 每页只有一个主行动。
6. 对长内容、量大、选项多、空值和极端值给出交互规则。
7. 2.5D/3D 必须先通过价值证明。
8. 视觉评审必须结合业务评审，不允许只看截图。
9. 页面通过后，必须用真实角色任务走一遍：进入 -> 判断 -> 操作 -> 反馈 -> 回读 -> 交接。
10. 不用“更像作品集”作为成功标准，用“更快做对事”作为成功标准。

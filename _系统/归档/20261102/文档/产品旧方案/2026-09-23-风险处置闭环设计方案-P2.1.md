## 1. 现状与为什么要做

| 项 | 现状 |
| --- | --- |
| 预警怎么来 | 每次请求由 `BusinessAlertContext` **实时计算**（逾期应收 / 停工与交付风险 / 材料超领 / 变更率异常），**不落库** |
| 预警长什么样 | `BusinessAlert`：type、level、title、message、project、owner、amount、dueDate |
| 处置建议 | `BusinessAlertType#nextAction()` 的固定文案，**只读**，与首页、项目台账同源 |
| 缺口 | ① 无法知道这条预警**谁在看、谁在做**；② 无法记录**做了什么、什么时候做完**；③ 无法回答"本周处理了几项、闭环率多少、平均多久闭环" |

**因此 P2.1 要解决的不是"再算一遍风险"，而是"把人对风险的处理过程记下来"。**

---

## 2. 核心难点：预警是算出来的，处置是记下来的

这是本设计**唯一真正的难点**，必须先定义清楚，否则会做出两套风险数据：

```text
预警（BusinessAlert）  = 由业务事实实时推导 → 会随事实变化而出现/消失
处置（RiskItem）       = 由人的动作产生     → 一旦发生就不会消失
```

两条硬规则：

1. **处置记录绝不复制预警内容**。`RiskItem` 只存 `alertKey`（稳定键）+ 处置事实。清单渲染时用 `alertKey` 把「算出来的预警」和「记下来的处置」**join** 起来。
2. **底账只有一套**。风险等级、类型、金额、责任人初始值**全部来自预警**；`RiskItem` 只允许覆盖「处置归属人」和「处置状态」两个字段。

### 2.1 稳定的 `alertKey`

```text
alertKey = alertType + ":" + businessType + ":" + businessId
例：OverdueReceivable:Receivable:10231
    ProjectSuspensionRisk:Project:88
    MaterialOverIssue:StockMovement:5512
    AbnormalChangeRate:ProjectContract:301
```

要求：**同一业务事实跨天、跨月重复出现时，`alertKey` 保持不变**（因此不含日期）。这样次月预警仍在时，能接上上个月已经记录过的处置轨迹，而不是凭空又来一条"待响应"。

### 2.2 预警条件消失 vs 已处置（必须区分）

| 情形 | 含义 | 系统行为 |
| --- | --- | --- |
| 事实消失（应收已收 / 项目复工 / 变更已审批） | **问题本身不存在了** | 预警从列表消失 → 对应 `RiskItem` 自动置 `已消解(Void)`，**不计入闭环率分子也不计入分母** |
| 事实仍在，但人已处理（已催收、已确认还款计划） | **问题存在、处置已完成** | `RiskItem` = `已关闭(Closed)`，**计入闭环率** |

> 这条不写清楚，会出现两种错误：把"问题自己好了"算成"员工处理得好"；或把"已经催过但钱还没到"永远挂在待处理里。

## 3. 对象模型

### 3.1 `RiskItem`（处置单，当前处理态）

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `riskId` | Long | `@Id + @SnowflakeId` |
| `company` | Company | **强制企业归属** |
| `store` / `team` | Store / Team | 归属快照，用于数据范围 |
| `owner` | Employee | **当前处置责任人**（可由指派覆盖预警默认责任人） |
| `alertKey` | String(160) | 稳定键，见 §2.1 |
| `alertType` | BusinessAlertType | 冗余便于筛选与索引 |
| `businessType` / `businessId` | String / Long | 关联业务事实（应收 / 项目 / 领料 / 合同） |
| `project` | Project | 可空；便于"按项目看风险" |
| `levelAtCreate` | BusinessAlertLevel | **创建时的级别快照**（用于判断后续是否升级） |
| `status` | RiskStatus | 见 §4 |
| `discoveredAt` | LocalDateTime | 首次出现时间（系统写入） |
| `assignedAt` | LocalDateTime | 最近一次指派时间 |
| `dueAt` | LocalDateTime | 按 SLA 计算的应处置截止时间（见 §7） |
| `closedAt` | LocalDateTime | 关闭时间 |
| `closedBy` | Employee | 关闭人 |
| `closeResult` | String(500) | 处置结果说明（关闭必填） |
| `roundNo` | Integer | 重开轮次，从 1 递增（对齐 `BR-008` 的追加留痕） |
| `evidenceUrls` | List&lt;String&gt; | 处置凭证（可选，见 §14 待裁决） |

唯一约束：`(com_id, alert_key)` 唯一 —— **同一企业、同一预警只有一张处置单**；重开不新建单，只加轮次。

### 3.2 `RiskDispositionLog`（处置流水，append-only）

对齐 `AcceptanceRound` 的 append-only 约定（`DEC-007` 同一精神）：

| 字段 | 说明 |
| --- | --- |
| `logId` | 主键 |
| `risk` | 所属处置单 |
| `action` | `Assign / Claim / Comment / Urge / Close / Reopen / Void` |
| `fromStatus` / `toStatus` | 状态迁移前后，便于审计 |
| `operator` | 操作人 |
| `note` | 处置说明 |
| `evidenceUrls` | 附件 |
| `createdAt` | 发生时间 |

**不可修改、不可删除**；轮次与结论按时间线保留。

## 4. 状态机

```text
                  ┌──────────────┐
   预警首次出现 → │  待响应 Pending │
                  └──────┬───────┘
                         │ 指派 / 认领
                         ▼
                  ┌──────────────┐
                  │ 处理中 Handling │◄──── 重开（条件升级或人工重开）
                  └──────┬───────┘
                         │ 关闭（必填处置结果）
                         ▼
                  ┌──────────────┐
                  │ 已关闭 Closed  │
                  └──────────────┘

   任意未关闭状态 + 预警条件消失 → 已消解 Void（终态，不计闭环率）
```

| 状态 | 含义 | 谁可以进入 | 是否计入「待处理」 | 是否计入闭环率分母 |
| --- | --- | --- | --- | --- |
| `Pending` 待响应 | 预警已出现，没人接手 | 系统自动创建 | ✅ | ✅ |
| `Handling` 处理中 | 已指派或已认领 | 有处置权的人 | ✅ | ✅ |
| `Closed` 已关闭 | 已处置并填写结果 | 有闭环权的人 | ❌ | ✅（作为分子） |
| `Void` 已消解 | 预警条件自己消失了 | 系统自动 | ❌ | ❌ |

> **不设「已处理待确认」这类中间态**：本系统里风险的确认人是负责人自己，加中间态只会制造"谁审谁"的歧义。

## 5. 动作与权限矩阵

| 动作 | Boss | StoreManager | Finance | Designer/Marketer/Pm | 说明 |
| --- | --- | --- | --- | --- | --- |
| 查看清单 | 全企业 | 本店 | 全企业 | 仅与本人相关的风险 | 服务端 `@DataPermission` 强制 |
| 指派给他人 | ✅ | ✅（本店成员） | ✅（财务类风险） | ❌ | 指派必须校验被指派人属于当前企业/门店 |
| 认领 | ✅ | ✅ | ✅ | ✅（仅本人相关） | 认领后 `owner = 当前员工` |
| 写处置记录（Comment） | ✅ | ✅ | ✅ | ✅ | append-only |
| 催办（Urge） | ✅ | ✅ | ✅ | ❌ | 写流水 + 通知受理人 |
| 关闭（Close） | ✅ | ✅ | ✅ | ✅（仅本人相关） | 必填处置结果 |
| 重开（Reopen） | ✅ | ✅ | ✅ | ❌ | 必填重开原因 |
| 批量指派 | ✅ | ✅ | ✅ | ❌ | 单次上限（建议 ≤ 50 条） |

**四条硬约束**

1. **不能关闭自己指派的单**？—— 不设此限制（10–30 人装企里老板往往既指派又处理），但**关闭必须写处置结果**，留痕替代审批。
2. **越权一律服务端阻断**：指派、认领、关闭都必须校验 `DataScopeContext + DataScopeSpecification`，禁止 `findById` 后判断。
3. **跨企业指派直接拒绝**，不做静默忽略。
4. **前端隐藏按钮不构成权限**（`AGENTS.md` 权限先行）。

`RiskItem` 实现 `ProjectOwned`（对齐 `Acceptance`/`AcceptanceRound` 的归属链），字段齐备：


| 索引 | 用途 |
| --- | --- |

## 7. SLA 与时效口径

设计稿给的分级语义（高=立即 / 中=48h / 低=本周）需要落成**可计算字段**：

| 级别 | 响应 SLA（出现 → 首次指派/认领） | 处置 SLA（出现 → 关闭） |
| --- | --- | --- |
| `High` 严重 | 4 小时 | 24 小时 |
| `Medium` 警告 | 24 小时 | 48 小时 |
| `Low` 关注 | 48 小时 | 7 天 |

- `dueAt` 在 `RiskItem` 创建时按级别计算并**落库**（便于扫描与排序），级别变化时重算。
- **SLA 数值需业务确认**（见 §14 待裁决 Q1）：上表是建议值，现行系统只有 `BR-005` 里 3 天/7 天的停留阈值，没有处置 SLA。

## 8. 重新打开规则（最容易做错的地方）

三种重开场景，行为必须区分：

| 场景 | 触发 | 行为 |
| --- | --- | --- |
| **级别升级** | 已关闭后同一 `alertKey` 再次出现，且级别 > `levelAtCreate` | 自动 `Reopen`：`roundNo++`，写流水（含"由 X 级升为 Y 级"），**保留上一次关闭记录** |
| **人工重开** | 有重开权的人主动重开 | `roundNo++`，必填原因 |
| **同级重复出现** | 已关闭后同级再次出现 | **不自动重开**，只在清单上打「复现」标记 + 累计 `recurrenceCount`，由人决定是否重开 |

> 为什么同级不自动重开：逾期应收在客户真正付款前**每天都会满足预警条件**，如果同级就自动重开，会变成"永远关不掉"，闭环率失去意义。

## 10. 闭环率与平均处置时长（口径先冻结）

风险中心设计稿里的「本周已处理 18 项 / 平均 6.2h 闭环 / 闭环率 86.4%」需要新口径：

```text
闭环率 = 统计期内 Closed 数量 ÷ (统计期内 Closed + 期末仍 Pending|Handling 的数量)
        排除 Void（条件自行消失，不算人的功劳，也不算没做完）
平均处置时长 = AVG(closedAt - discoveredAt)，仅统计 Closed
超时率 = 期内 dueAt < closedAt 的 Closed 数量 ÷ 期内 Closed 数量
```

**必须与 `MET-001` 同样的写法冻结**（分子/分母/时间归属/排除项），否则报表之间会互相打架。

## 12. 异常与边界

| # | 边界 | 期望 |
| --- | --- | --- |
| 1 | 同一预警并发创建处置单 | `(com_id, alert_key)` 唯一约束兜底，第二次为幂等命中，不报 500 |
| 2 | 预警关联对象被删除 | 处置单保留 `alertKey` 与业务 id，清单显示"对象已删除"，操作禁用 |
| 3 | 受理人离职/转岗 | 处置单 `owner` 保留历史，清单显示"责任人已离职"，允许重新指派 |
| 4 | 已关闭后事实消失 | 保持 Closed，不回退为 Void（人的处置事实不可抹掉） |
| 5 | 关闭后金额/成本变化 | 处置单**不影响任何账务**（同 `BR-008` 的"不碰账"不变量） |
| 6 | 预警从 High 降为 Medium 再关闭 | 按 `levelAtCreate` 记录创建级别，`dueAt` 按当前级别重算 |

## 1. 业务问题

店长打开「门店业绩」时，看到的是一屏数字，但存在两个硬问题：

1. **口径错误**：页面把 `已接受报价 ÷ 全部报价` 标成“报价接受率”。`MET-001`/`DEC-001` 已明确禁止该分母，正式口径为“**最终报价接受率** = 最终为 Accepted/Converted 的报价机会 ÷（Accepted + Converted + Rejected），机会按客户 + 房屋，草稿/待决策/已被替代不进分母”，并要求“**设计师、门店、团队、老板使用同一最终口径**”。
2. **无法行动**：门店经营结构 6 张卡片带右箭头却不可点击，指标看得到、下一步找不到；店长只能自己回到客户、报价、项目三个入口重新筛选。

一句话目标：**让店长在同屏内判断“门店经营结果对不对、差在哪、下一步找谁办”。**

## 2. 真实场景（编码前闭环）

### 场景 A：单店 12 人的店长（合肥，月产值约 60 万）

- 使用人：店长王店长，只在手机 App 上管理门店。
- 触发事件：周一早会前想知道本周该盯什么。
- 当前动作（优化前）：打开门店业绩，看到“报价接受率 40%”“待推进报价 5”，但 5 份里 3 份是没人提交的草稿；40% 的分母含草稿和已被替代报价，无法用来评价设计师。
- 系统下一步（优化后）：首屏显示“待决策报价 2”“最终报价接受率 66.7%（6 个已决策机会）”；点击“推动 2 份待决策报价”直达报价池的待客户确认筛选；点击“待指派 n 位客户”直达客户列表的待指派设计筛选。
- 异常处理：如果门店没有任何已决策报价，接受率显示 0 且被解释为“暂无已决策机会”，不显示为“0% 经营能力”。

### 场景 B：2 店的店长（其中 1 店仅 3 人，设计师兼顾问）

- 使用人：店长李店长，同时管两店，但 App 数据范围锁定在当前门店。
- 触发事件：想确认某位设计师的首版方案命中能力，判断是缺线索还是缺命中。
- 当前动作（优化前）：设计师排名里 11 个指标全部铺开，接受率与门店同源错误口径，无法区分“首版被拒后改版才接受”。
- 系统下一步（优化后）：设计师卡片默认只显示关键 6 项——负责客户、待量房、待决策报价、最终接受机会、首版接受率、逾期任务；需要看报价额、项目数、动态数时点“展开设计师明细”。
- 异常处理：设计师未归属门店或已离职时不产生业绩行；跨门店客户不计入本店机会（门店数据范围由后端强制，前端只展示当前门店结果）。

## 4. R1–R3 迭代结论

- **R1 因果**：门店业绩的价值不是“多展示指标”，而是判断“报价机会有没有被决策、决策结果如何、谁在拖”。因此主指标必须是机会级最终接受率，并单列待决策报价量。
- **R2 条件**：口径必须唯一实现，不能被 5 个报表各自复制；同一客户多房屋、同一房屋多改版、已被替代报价、草稿、待决策、历史缺失决策时间六类边界必须同时成立。
- **R3 体验**：门店业绩是“判断 + 分派”页面，不是报表导出页；主指标 + 待处理数量 + 一键到达处理入口构成首屏；低频明细默认收起。

## 5. 已实现改动（P0）

### 5.1 统一报价接受率口径

新增 `statistic/context/QuoteAcceptanceContext.java`，作为唯一算法，输出：

```text
submittedQuoteCount          已提交报价量（排除草稿、已被替代）
pendingDecisionQuoteCount    待决策报价量（Submitted），单独展示、不进分母
decidedOpportunityCount      已产生明确客户决策的报价机会数
acceptedOpportunityCount     最终为 Accepted/Converted 的机会数
finalAcceptanceRate          最终报价接受率（主指标）
firstAcceptanceRate          首版报价接受率（辅助指标）
```

接入范围：门店报告、门店内设计师表现、团队报告、团队成员表现、设计师报告、人员绩效（`BusinessAnalysisContext` 改为调用同一上下文，避免第二套算法）。

### 5.2 门店业绩页面

- 顶部 Hero：`报价接受率` → `最终报价接受率`，取 `finalQuoteAcceptanceRate`。
- 顶部指标卡：`待推进报价` → `待决策报价`（`pendingDecisionQuoteCount`），并支持点击“去处理”。
- 门店经营结构 6 张卡片：补齐真实跳转（成员管理 / 客户池或待指派客户 / 报价池或待决策报价 / 项目列表 / 风险项目 / 现场动态），每张卡片增加一行“下一步动作”文案，消除死箭头。
- 报价转化卡片：`待决策 N · 最终接受 X/Y 个机会`，不再展示错误百分比。
- 设计师排名：默认只显示 6 项关键指标，其余明细通过“展开设计师明细”按需查看；设计师标签改为“最终 X%”，并补充“最终接受 X/Y”“首版接受 X%”。
- 最近客户：可点击进入客户详情（与最近报价、最近项目一致）。
- 首页店长经营卡：同步为“最终报价接受率”。

### 5.4 卡片排版兼容修复

门店经营概览、门店经营结构、顾问三列卡、动作卡等栅格原实现混用 `display: grid` / flex `gap` / `calc(50% - 9rpx)`。
在部分小程序基础库下 `calc()` 内的 `rpx` 与 `gap` 组合会把两个 50% 卡片挤到换行，表现为“一行一个”。
已统一改为 `display: flex; flex-wrap: wrap; justify-content: space-between` + 百分比宽度（49% / 32%），
不再依赖 `grid`、`gap`、`calc(rpx)`，保证 750rpx 宽度下稳定两列/三列。

### 5.3 深链承载

- 报价池支持 `?status=`（待客户确认等）。
- 客户列表支持 `?filter=assign`（待指派设计）及客户阶段。
- 项目列表支持 `?status=`（施工中/待开工/待验收/停工/已完工）。

### 5.5 最近客户 / 报价 / 项目记录卡片

- 客户卡片：头像 + 姓名 + 客户阶段标签 + 负责人/小区/电话 + 右箭头，整卡可点进入客户详情。
- 报价卡片：客户 + 报价状态标签（接受/转项目成功色、待决策警示色、驳回风险色）+ 编号/面积 + 金额，整卡可点进入报价详情。
- 项目卡片：项目名 + 项目状态标签（中文，不再直出 `ongoing` 等枚举）+ 客户/设计 + 进度条 + 合同额，整卡可点进入项目详情。
- 交互：按下缩放 + 品牌浅底反馈；区块标题补「全部客户 / 报价池 / 全部项目」入口。
- 团队业绩、设计业绩、我的业绩（业务员）和项目经理履约的同类列表同步统一，避免同一 App 多套卡片语言。

### 5.6 底部留白

原页面依赖 `jz-tabbar-gap`（仅等于 TabBar 高度）留白，最后一张项目卡片仍被固定 TabBar 遮住。
现改为页面自身预留：`.perf { padding-bottom: calc(#{$jzb-tabbar-height} + 96rpx + #{$jzb-safe-bottom}) }`，
即 116rpx TabBar + 96rpx 呼吸位 + 安全区，并移除重复的占位元素。

### 5.7 顶部 Header 与主指标卡（视觉重构）

原顶部是「品牌渐变 Header + 24rpx 浅色缝 + 另一块品牌深绿渐变 Hero」，两块同色系深色相邻、中间夹一条浅缝，
既重又碎；Hero 内部又是「小标签 + 大数字 + 左右顶边同级小字」，层级不清晰。

- **只保留一层深色**：品牌渐变 Header 继续承担“我在哪”（页面名 + 范围说明），主指标改成**浅品牌底卡**
  （`linear-gradient(160deg, #F2FBFA → #FFF)` + 1rpx 品牌描边 + 品牌浅投影），两块深色不再相邻。
- **概览卡改为横向主信息**：图标与数字同一排（图标 62rpx 左置、数字 40rpx 右置、指标名在数字下方），
  取代原来「图标 → 数字 → 名称」纵向堆叠；「去处理」改为卡片底行 + 细分割线，不再绝对定位。
- **口径可见**：指标名右侧增加口径 chip（累计 / 本月 / 合同口径），回答“这个数是什么区间”。
- **数值分级**：金额拆成「数值 + 单位」两段（`moneyParts`），数字 64rpx 品牌深色、单位 30rpx 品牌色。
- **支撑指标结构化**：底部两项支撑指标改为等宽两列 + 细分割线（标签 20rpx 灰、数值 26rpx 深），
  取代原来左右顶边、字号相同的排法。
- **视觉呼应**：Header 右上白色圆形装饰，主指标卡右上品牌圆形装饰，形成同一套语言而不是重复色块。
- **板块间距**：品牌 Header 与主指标卡之间 32rpx，主指标卡与下方板块之间 40rpx（业务员页 36rpx），
  避免深底与浅底贴合过紧。
- **顺带修一个数据展示缺陷**：业务员主指标是“本月录入客户（人数）”，原模板用 `money()` 渲染人数，
  会显示成 `¥12`；现改为数值 + “位”。

## 6. 权限与数据范围

- 门店业绩 Provider 继续继承 `Security`，`@User` 注入当前员工，仅 `StoreManager` 可调用，数据按登录员工 `company + store` 限定；前端传参不参与范围判定。
- 门店接受率使用门店范围内的客户/房屋机会，跨门店客户的报价不进入本店机会。
- 设计师行按“机会最终决策报价的负责人”归属；无决策的机会按最新版本报价负责人归属，不产生跨店归属。
- 前端跳转不构成权限；目标页面（客户/报价/项目）仍由各自 Provider 与 `DataScopeRequestFilter` 服务端兜底。

## 7. 验收标准（待 acceptance 独立执行）

1. 同一客户两个房屋、同一房屋两次改版，机会数分别为 2 和 1。
2. 2 草稿 + 2 待决策 + 4 接受 + 2 拒绝，最终接受率 = 4 ÷ 6 = 66.7%，待决策报价量 = 2。
3. 已被替代报价不计入分母，也不计为拒绝。
4. 首版被拒、改版后被接受：最终接受率 100%，首版接受率 0%。
5. 门店、团队、设计师、人员绩效四处同一数据样本结果一致。
6. 店长只能看到本门店数据；跨企业/跨门店请求负向用例失败。
7. 门店业绩页 6 张结构卡与 4 张指标卡均可到达对应业务页，箭头与可点击状态一致。
8. 门店无任何已决策报价时不出现“0% 能力”误导文案。

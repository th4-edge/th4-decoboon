# 店长业务能力与企业负责人对齐设计

```text
文档状态: 已确认（用户 2026-10-17 裁决，DEC-075 + DEC-076；待研发实施与验收）
日期: 2026-10-17
目标角色: 店长 StoreManager
关联规则: BR-028、DEC-065、DEC-067、DEC-070、DEC-075、DEC-076、BR-049、MET-011
核心命题: 店长具备企业负责人的“业务能力全集”，但数据范围锁定为本人所属门店
```

## 1. 结论先行

店长不应被理解为“比企业负责人少很多功能的一个角色”，而应被理解为：

> **同一套内部业务能力 + 更小的数据范围。**

即：

```text
企业负责人 = 业务能力全集 + 企业范围 + 企业治理能力
店长       = 业务能力全集 + 本门店范围 + 少量企业治理例外
```

这里的“业务能力”指客户、设计、报价、合同、项目、材料、财务、员工管理等日常经营动作；“企业治理”指订阅、套餐、门店增删、企业主体资料、跨店口径、企业级主数据维护等会改变企业边界或全公司口径的动作。

## 2. 两类能力必须分开

### 2.1 业务能力（店长应与 BOSS 对齐）

| 能力域 | 店长在本门店内应具备的动作 |
| --- | --- |
| 客户经营 | 新建/编辑客户、分配负责人、设置休眠、标签、批量导入、转交本店员工、查看跟进记录 |
| 房屋与量房 | 新建/编辑房屋、录量房、指派设计师、查看量房结论 |
| 设计与方案 | 查看/编辑方案、空间、分项、指派设计师、推进设计节点 |
| 报价 | 新建/编辑报价、选择企业报价库、调整折扣与最终价、提交/撤回/作废报价、查看成本与毛利 |
| 合同 | 发起/复核合同、确认签约、确认生效、查看合同变更 |
| 项目与工地 | 立项后指派项目经理和成员、排期、开工、任务推进、日报、阶段验收、整改、复验、增减项 |
| 材料 | 材料计划、选材、采购、到货、入库、库存、退换货、供应商选择 |
| 财务 | 应收/应付、收款/付款、台账、结算、质保金释放、期初余额、门店财务工作台 |
| 员工与团队 | 邀请本店员工、管理本店员工、建团队、调整本店团队成员、查看本店员工绩效 |
| 经营分析 | 本店驾驶舱、本店经营分析、本店绩效、本店组织效能、本店风险队列 |
| 导出与导入 | 本店范围导出、本店范围客户/业务导入 |

### 2.2 企业治理能力（默认仅 BOSS）

| 能力 | 默认归属 | 原因 |
| --- | --- | --- |
| 订阅、套餐、席位、门店包 | BOSS | 影响企业付费与容量 |
| 新增/停用门店、默认总店设置 | BOSS | 改变组织边界 |
| 企业名称、Logo、对外资料、品牌配置 | BOSS | 全企业统一口径 |
| 企业级报价库/工艺库/模板/凭证模板/手工记账分类的维护 | BOSS + 店长（影响全企业，需提示与审计） | 改一次影响所有门店；店长写入是明确例外 |
| 全部门店合计、门店对比、公司利润 | BOSS / 总部财务 | 跨店经营口径 |
| 企业级安全日志、API/集成、数据导出与删除 | BOSS | 高风险与合规 |
| 企业负责人转让、角色治理 | BOSS | 租户治理 |

> 已确认：店长可以修改企业级主数据（`DEC-075` SM-CAP-02）。这是门店范围之外的写权限例外，不是跨店业务数据授权；保存前必须提示“此修改影响全企业所有门店”，并记录操作人、门店、字段前后值和时间。已签约合同、已生成报价和已发生单据继续使用历史快照。

## 3. 数据范围设计

### 3.1 唯一范围来源

- 店长的 `storeId` 只能来自登录员工 `employee.store`，服务端加载，禁止信任前端 `storeId/companyId/empId`。
- 所有分页、列表、详情、计数、选择器、导出、统计、看板统一走数据范围。
- 写操作必须校验对象当前是否属于本店；跨店对象一律 403/404，不泄露记录是否存在。
- 门店归属写入遵循 `DEC-070`：以客户门店为事实源，在创建时快照；换负责人、换门店不回溯历史对象。

### 3.2 聚合与看板

- 店长只能得到本店合计，不得出现“全部门店”选项、跨店合计、其他门店名称或金额。
- 门店对比矩阵、公司经营利润、全公司经营驾驶舱仅 BOSS/总部财务可用。
- 本店报表必须下推 SQL，禁止全量加载后内存过滤。
- 未归属门店的数据：BOSS 可见并标注；店长不可见；单店企业不出现该差异。

### 3.3 单店企业等价性

单店企业下，店长范围 `Store` 与企业范围 `Company` 等价，业务行为、数字、页面不得出现差异；只是不展示门店切换控件。

## 5. 关键场景

### 场景 A：店长独立经营一家门店

店长登录后看到“本店客户、本店设计、本店项目、本店财务、本店经营”，可完成从客户登记到签约、施工、验收、收款的完整闭环；所有列表和统计只显示本店。企业负责人登录后看到全部门店，并可下钻到该店。

### 场景 B：店长尝试访问其他门店

店长通过 URL、接口参数、选择器或导出尝试访问他店客户/项目/财务：
- 返回 403/404，不返回空列表伪装“没有数据”；
- 不泄露他店名称、金额、客户是否存在；
- 记录一次越权访问审计。

### 场景 C：员工从 A 店调到 B 店

员工调动后：
- 历史客户、合同、项目、单据仍归属 A 店，不回溯；
- 新创建对象归属 B 店；
- A 店店长不再看到该员工的新业务，B 店店长开始看到；
- 员工当前登录会话每次请求由服务端重新取范围，不依赖前端缓存。

### 场景 D：单店企业

店长与企业负责人看到的业务数据范围等价；页面不显示门店切换器，不出现“全部门店/本店”差异；所有单店验收用例必须通过。

### 场景 E：一人管理两家店（本期不支持）

当前 `Employee.store` 是单门店。若一人实际管理两家店，现有模型无法表达“可切换的两店范围”。建议：
- 短期：一店一店长账号；
- 中期：增加 `employee_store_scope` 管理范围关系，店长可在授权门店间切换，但仍无“全部门店”；
- 不新增“区域负责人”角色，避免角色体系膨胀。

## 5.1 不在本次裁决范围内

- 店长可查看本店经营利润（`DEC-076`）；具体公式按 `MET-011` 冻结后实现，公式未冻结前不得上线金额。
- 门店财务、总部财务的作废/更正/冲正权限不自动扩展；本设计只下放给店长。
- 企业治理动作仍仅 BOSS。

## 5.2 剩余待裁决（不自动下放）

`DEC-076` 已下放合同变更审批、门店月度目标、门店利润、在跑项目承接代确认；剩余未下放项只有薪酬动作：

- 工资单确认：现为 BOSS 专属，店长仅查看本店工资构成；
- 工资单作废/删除草稿：现为 BOSS 专属。

上述两项仍登记 `GAP-060`，未裁决前不得下放。

## 6. 现状差距

### 6.1 后端

- 多个业务入口仍使用 `requireBoss`，其中一部分是真正的企业治理，另一部分是可以用“业务能力 + 门店范围”替代的经营动作。
- 统计域部分报表只有 BOSS 入口，店长无法获得本店版本。
- 财务域已按 `DEC-065` 给店长本店记账权限；`DEC-075` 进一步把作废/更正/冲正下放店长（本店），门店财务/总部财务仍不获得。
- 部分选择器、导出、详情接口未统一走门店范围，存在“列表看不到、详情能打开”的风险。

### 6.2 Web

- 店长的静态路由是 BOSS 的子集，不是能力对齐：例如项目验收、团队/组织视图、部分设计/材料页面缺失。
- 菜单按角色硬编码，容易出现“页面建了但店长菜单没有”或“菜单有但接口 403”。
- 财务/薪酬入口有“只读”标签，与 `DEC-065` 的店长记账写权限不完全一致，需要按能力重新标注。

### 6.3 App

- 店长已覆盖客户、量房、报价、合同、项目、材料、财务等较多页面，但覆盖不完整，且部分页面按角色名判断，未按能力键判断。
- 需要与 Web 共用同一套能力矩阵和门店范围语义，避免两端行为分叉。

## 7. 设计与实现原则

1. **能力与范围分离**：`capability` 决定“能不能做”，`dataScope` 决定“对哪些数据做”；不要用角色名散落判断。
2. **服务端唯一裁决**：前端隐藏按钮不作为权限；所有入口服务端校验。
3. **一个动作一个能力键**：菜单、路由、按钮、接口、审计使用同一能力键。
4. **企业治理显式例外**：例外必须列入白名单并写清原因，不能靠 `requireBoss` 隐式形成。
5. **不新增重复角色**：继续使用现有 7 类角色；需要多店管理时扩展范围关系，不新增“区域负责人”。
6. **单店等价**：任何门店维度改造都必须通过单店企业回归。
7. **审计可追溯**：记录实际操作人、角色、能力键、门店范围、对象、前后状态、金额、时间、幂等键。

## 8. 实施批次建议

### P0：口径冻结

- 确认本文件的“企业治理例外”和“高风险例外”。
- 将“店长 = BOSS 业务能力全集 + 本店范围”写入 `BR-028` 的 StoreManager 行，并建立新的 DEC/GAP 记录。
- 产出完整能力清单：每个 Provider 路由标注 `业务能力/企业治理/外部确认` 和 `Company/Store/Team/Self`。

### P1：后端门禁改造

- 新增统一能力校验入口，替代经营动作上的硬编码 `requireBoss`。
- 对经营类 Provider 开放店长，并补齐 `DataScopeSpecification`/`DataScopeRequestFilter`。
- 保留企业治理类 `requireBoss`。
- 补跨店负向、单店等价、历史门店快照、未归属数据用例。

### P2：Web 对齐

- 以能力矩阵生成店长菜单/路由，不再维护 BOSS 子集。
- 店长菜单统一使用“本店”语义，隐藏企业治理入口。
- 门店选择器只读显示本店，不出现“全部门店”。

### P3：App 对齐

- 与 Web 共用能力键和门店范围语义。
- 补齐缺失的本店经营/项目验收/团队视图。
- 统一越权提示和空状态，不用空数组伪装无权限。

### P4：验收门禁

- 对 BOSS 的每个业务能力，至少有一条店长本店正向用例。
- 对每个业务能力，至少有一条跨店负向用例。
- 单店企业全量回归。
- 财务/薪酬/员工管理按 `DEC-065`、`DEC-046` 做权限与隐私回归。
- 统计接口做 SQL 条数与 P95 门禁。

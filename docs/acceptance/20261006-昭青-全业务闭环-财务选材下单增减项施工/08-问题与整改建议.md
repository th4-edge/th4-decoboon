# 问题与整改建议（含行业规范业务行为思考）

> 说明：以下按「观察到 / 推测 / 待验证」标注，不替代业务智能体裁决。金额、成本、利润、权限口径以
> 业务事实源与 `AGENTS.md` 为准。

## 一、行业规范业务行为对照（用户点名领域）

### 1. 选材（主材/全屋定制）

行业实际：选材不是「一次勾选」，而是**带品牌/型号/规格/数量的确认单**，涉及「设计师推荐 → 业主确认 →
锁价 → 下单 → 到场验收」。中小装企最常见的争议是「选的时候是 A 品牌，到场是 B」「数量按投影还是展开」。

- 观察：`material/selection/board` 走「草稿 → 确认」两态，`material/selection/confirm` 单独成接口。
- 建议（P2）：选材确认单应固定 **品牌/型号/规格/单价/数量/单位/是否主材** 七个要素，并在确认时做
  **快照冻结**；后续方案变更不得回改已确认项。
- 建议（P1，商务风险）：**「客户已确认」必须有客户身份证据**（业主端确认或带时间戳的客户签字/授权），
  员工端不得代替客户确认。上一轮遗留 `XA-20261004-004` 即该口径，仍未裁决，本次不代客户确认。
- 建议（P2）：选材与报价中的主材项要能**双向追溯**（报价明细 ↔ 选材项），避免两套数据。

### 2. 下单 / 材料计划

行业实际：装企下单多为「材料计划 → 汇总 → 分供应商下采购单 → 到场验收 → 入库」，且**按项目而非按人**归集成本。

- 观察：`project/material-plan` + `material-plan-workbench` + `project/purchase/{save,order,approve,batch}` +
  `project/goods-receipt` + `inventory/stock/*` 已形成链路；`material-batch-order` 提供批量下单入口。
- 建议（P1）：下单必须**校验库存/在途/已承诺量**，避免重复下单；批量下单要有幂等键与「已下单」标识。
- 建议（P1）：**实际材料成本只在到货/入库累计**（符合 AGENTS.md），领料与损耗只流转库存、不退成本；
  当前不可用 0 成本计算利润。
- 建议（P2）：供应商直送 vs 入仓要有不同到货确认路径，且都能回写项目成本。

### 3. 增减项（变更）

行业实际：增减项是家装纠纷重灾区。规范做法是「变更申请（附项+量+价）→ 客户确认 → 合同金额重算 →
生效留痕 → 施工/材料联动」。

- 观察：`project/contract-change/{save,update,customer-confirm,cancel,batch-save}` 与 `change`/`change-workbench`/
  `change-detail` 页面齐备，`db_contract_change_item` 保存明细。
- 建议（P1）：变更生效必须**双向可对账**：原合同额 + Σ确认变更 = 现合同额；且客户确认需身份证据。
- 建议（P1）：变更要有**是否影响工期/是否影响材料**的显式字段，联动施工计划与材料计划。
- 建议（P2）：未确认变更不得计入应收与利润，避免「虚增合同额」。

### 4. 项目施工

行业实际：工地推进靠「阶段-工序-任务-日报-验收」五件套，关键是**责任到人 + 异常可升级**。

- 观察：`project/stage`、`project/task/{save,update}`、`project/task-node/save`、`project/report`、`project/acceptance` 齐备。
- 建议（P1）：阶段推进应有**前置校验**（上阶段验收/整改闭环、关键材料到场），否则不允许直接推进。
- 建议（P2）：日报与任务应绑定「施工区域/工艺项」，避免一张日报糊多个项目。
- 建议（P2）：整改（`acceptance/rectify`）应有**超期提醒与责任人**，不能只留状态。

### 5. 财务

行业实际：装企财务核心是**应收计划 → 收款核销 → 应付/付款 → 项目成本 → 结算利润**，且必须能按项目对账。

- 观察：`finance/receivable|receipt|payable|payment|project|ledger|settlement|summary` 覆盖完整；含 `retention-release`（质保金）。
- 建议（P1）：收款必须**核销到应收节点**，重复/超额收款要阻止（幂等）。
- 建议（P1）：利润与毛利率在**成本不完整时必须为空并显示「成本未完整」**，禁止伪利润。
- 建议（P2）：资金台账与应收/应付三处金额应同一口径，页面/接口/库三方对账。

## 三、整改顺序建议

1. **P1 安全/口径**：dev→prod 构建门禁；选材/变更/收款的客户身份证据与金额幂等。
2. **P1 业务**：变更金额重算与成本完整性；下单去重。
3. **P2 体验/一致性**：iOS 日期统一、来源枚举、阶段推进前置校验。
4. **P3**：深链空态、废弃 API 迁移。

# 性能定位复盘（2026-10-07）

> 对应 `DEC-037`（性能问题定位与优化顺序规范）、`BR-032`；证据 `EV-108`、`EV-109`、`EV-110`。

## 1. 结论

把"容易测的内部指标（SQL 条数、循环查询）"当成了优化目标，而没有第一时间测"用户感知的时间花在哪一段"。
结果是 SQL 条数下降约 50% 而延迟几乎未动；真正的瓶颈（136KB 响应体）在后期才被看见，
而其定位成本本应只有分钟级。

## 2. 时间线（真实过程）

| 阶段 | 动作 | 当时判断 |
| --- | --- | --- |
| ① 直觉期 | 从"统计汇总里有循环内查库"出发，建 `DEC-036` + A1–A7 反模式 | 慢 = N+1 查询多 |
| ② 指标期 | 建 SQL 计数探针、51 条统计路由普查、逐接口消除循环查询 | SQL 条数降下来就快了 |
| ③ 打脸期 | 重 JOIN 把 SQL 106→67，延迟反而 **234ms→626ms**，回滚 | 指标改善但体验变差 |
| ④ 矛盾期 | `pm/report` 降到 **26 条 SQL**，仍 **463–820ms / 136,633B** | 矛盾信号出现但未转层 |
| ⑤ 破局期 | 拉一次真实响应，按字段统计字节：`materialRisks` 17 条占 **107,333B / 78.6%** | 分钟级定位 |
| ⑥ 解决期 | 白名单收窄 136,633B → **23,244B**，P95 **496ms** 达标 | 改动量 < 1 小时 |

## 3. 关键数据

| 指标 | 改前 | 改后 |
| --- | --- | --- |
| `pm/report` 响应体 | 136,633B | 23,244B（-83.0%） |
| `pm/report` P50 / P95 / P99 | — | 293ms / 496ms / 588ms |
| `pm/report` SQL 条数 | 106 → 26（治理后） | 未变（非瓶颈） |
| `materialRisks` 子项占比 | 107,333B / 78.6% | 14,734B |
| 重 JOIN 实验（已回滚） | 234ms / 106 条 | 626ms / 67 条（劣化） |

## 4. 五个错误

1. **代理指标替代目标指标**：SQL 条数是成本代理，不是用户感知；
2. **矛盾信号未触发停止**：26 条 SQL 仍 800ms，应立即判定瓶颈不在存储层；
3. **先改后测**：把验证放在改造之后，等于闭眼改；
4. **优化了可见的而非重要的**：代码里的循环很显眼，响应体里的重复下发要算字节才看得见；
5. **先建门禁后定位**：把错误指标（SQL 条数）先固化成了标准。

## 5. 思路转变

| 维度 | 走的弯路 | 应走的路 |
| --- | --- | --- |
| 起点 | 从代码反模式出发 | 从端到端时间分布出发 |
| 第一动作 | 读代码找 N+1 | 采样 TTFB / size / 分段耗时 |
| 主指标 | SQL 条数 | P95 + 响应体大小 + TTFB |
| 假设验证 | 改完再测 | 先证伪，再动手 |
| 范围 | 全仓 51 条路由齐推 | Top-1 单点突破 |
| 成功判据 | 内部指标改善 | 用户感知指标改善，否则回滚 |

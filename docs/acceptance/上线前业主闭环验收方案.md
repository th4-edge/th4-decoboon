### 0.2 已确认的测试设计前提

1. 业主不是员工角色，不能复用 `EmployeeRole` 的 `Self` 权限，也不能靠手机号、姓名或前端 `customerId/projectId/companyId` 推断授权。
2. 业主授权的真源必须是显式的“微信身份 + 项目授权关系”；邀请只负责建立该关系。
3. 所有需要登录的接口必须继承 `Security`。员工和业主都从服务端会话获取主体，前端身份字段不可信。
4. 所有响应继续使用实体、实体集合或分页；不接受 DTO/VO/包装对象作为领域响应。
5. 跨企业或跨项目对象统一按“不存在或无权访问”处理，不泄露对象是否存在。
6. 验收只判是否存在可复现证据。开发自测、页面可打开、示例截图不能单独作为通过依据。

### 0.3 本轮不包含

- 不修改 `src/main/**`、生产配置或前端实现。
- 不在本轮创建自动化测试代码；如后续创建，只能放 `src/test/**`。
- 不把 `PP-03` 订阅消息、`PP-04` 私有文件迁移、`PP-08` 支付、PC 管理端或电子签纳入功能实现范围。

### 3.2 状态码和响应契约

客户端统一使用 `token` 请求头和 `{ success, data, errorCode }` 响应包。acceptance lane 同时检查 HTTP 状态与 `errorCode.code`，不只看 HTTP 200。

| 场景 | 期望 |
| --- | --- |
| 成功 | 2xx 且 `success=true` |
| 缺少 token、token 无效或过期 | `401`，不得返回任何业务对象 |
| 已登录但无权执行动作 | `403`；涉及未知对象时优先使用 `404` 防枚举 |
| 参数缺失、格式错误或状态越级 | `400` |
| 对象不存在或跨企业/跨项目不可见 | `404`，响应不得泄露对象名称、企业或负责人 |
| 已使用 token 重放、冲突动作或并发输家 | `409` |
| 过期或已撤销邀请 | `410`；若产品接口统一使用 `404`，必须在方向冻结时明确并把矩阵同步调整 |
| 依赖系统错误 | `5xx`，不得把业务失败伪装成成功 |

## 5. E2E 场景

以下场景必须由独立账号、独立数据夹具执行，不得直接复用开发自测生成的会话状态。

### E2E-01：邀请接受成功并建立项目授权

```gherkin
Given 企业 A 的 BOSS 在项目 A1 创建一个有效业主邀请
And 微信身份 O1 授权手机号与邀请手机号一致
When O1 查询邀请并接受邀请
Then 邀请状态变为已使用
And O1 只获得 A1 的项目授权
And O1 能读取 A1 的本人住房、阶段、公开动态和待确认验收
And O1 不能读取企业 A 的客户列表、成本、供应商价或 A2
```

### E2E-02：过期、撤销和重放均无副作用

```gherkin
Given 存在过期、撤销和已使用的三个邀请
When 分别使用对应 token 尝试接受
Then 每次请求均被拒绝
And 不新增业主身份或项目授权
And 不改变邀请之外的任何项目/合同/验收数据
```

### E2E-03：并发接受只能消费一次

```gherkin
Given 同一有效邀请被两个并发客户端同时接受
When 两个请求同时到达服务端
Then 最多一个请求成功
And 授权关系和接受审计只产生一次
And 幸存请求无法再次使用该 token
```

### E2E-04：业主项目读取隔离

```gherkin
Given O1 只授权 A1，A2 属于同一企业，B1 属于企业 B
When O1 使用伪造的 A2/B1/propertyId/reportId 读取详情
Then 所有越权请求返回一致的不可见结果
And 响应中不出现 A2/B1 的名称、企业、负责人或文件地址
```

### E2E-05：业主确认验收

```gherkin
Given A1 的待确认验收 ACC-P
When O1 从本人会话确认 ACC-P
Then ACC-P、阶段和项目汇总在同一个事务边界内一致更新
And 确认主体来自会话而非请求字段
And 内部允许人员收到一次通知
```

### E2E-06：业主驳回并重新提交

```gherkin
Given A1 的待确认验收 ACC-P
When O1 驳回并提交原因
Then ACC-P 状态为已驳回，阶段回到可整改状态
When 内部人员整改并重新提交
Then 只创建新的待确认事实，不覆盖原驳回审计
```

### E2E-07：重复和竞争动作

```gherkin
Given 两个客户端并发提交确认
When 请求处理完成
Then 只存在一个终态和一套审计/通知事实
And 另一请求返回确定的幂等或冲突结果
And 阶段、项目、验收三处状态不出现分叉
```

### E2E-08：私有文件边界

```gherkin
Given 私有文件 F-A1-Contract 属于项目 A1
When 匿名用户、企业 B 员工、仅授权 A2 的业主分别请求文件
Then 三者都无法获取内容
When 合法 A1 员工或授权 A1 业主请求
Then 在授权未撤销且签名未过期时获取成功
```

## 9. 缺陷分级、阻断规则和回退

| 等级 | 定义 | 示例 | 验收动作 |
| --- | --- | --- | --- |
| `Blocker/P0` | 数据越权、跨企业泄露、token 重放产生授权、业主可写内部数据、私有文件泄露 | 跨企业项目可读、业主可修改金额、已用 token 再次绑定 | 立即阻断，不得验收通过 |
| `High/P1` | 核心正链路可用性、状态一致性、幂等或四角色回归失败 | 确认后阶段不更新、重复确认产生重复通知、店长看到其他门店 | 修复并重跑相关矩阵 |
| `Medium/P2` | 单页面提示、非核心字段、可接受的兼容性问题 | 过期提示不友好、排序不一致 | 记录风险并经产品判断后放行 |
| `Low/P3` | 文案、非阻断的样式或可观测性改进 | 日志字段冗余 | 记录到发布前清单 |

任何 `Blocker/P0` 或未解除的 `High/P1` 都不能被“开发已自测通过”或“规划文档已写”替代。

## 10. 风险、未知项和待冻结决策

| 风险 | 当前影响 | 验收前动作 |
| --- | --- | --- |
| 规划文档状态为 `draft_for_review` | 业主模型和范围仍未用户批准 | product-planning 冻结并登记到 shared 输出 |
| 业主数量/共同业主规则未决 | `INV-10/11` 的期望无法唯一确定 | 在 T01 决策中确认单业主、共同业主或多业主 |
| 同一微信身份是否可跨企业绑定未决 | `ID-07` 只能设计为两种分支 | 确认规则并禁止混数据 |
| 邀请撤销与已建立授权的语义未决 | `INV-15` 可能产生隐性残留权限 | development 交接明确级联规则并测试 |
| 验收效力未决 | 一键确认可能被误称电子签 | 产品明确“项目推进依据”或单独立项签名 |
| 开发 lane 尚无正式交接 | 路由、错误码、字段和迁移不可核验 | 完成交接清单后再开始黑盒执行 |
| `/upload/**` 仍为全局映射 | 已知高风险，可能阻断发布 | 必须作为 `FILE-01` 阻断项处理 |
| 现有 `CustomerInvite` 创建路径使用先查后判模式 | 可能在跨企业或并发下产生边界风险 | 回归检查并改由统一范围查询或等价安全路径验证 |
| 现有 `project/acceptance/update` 仅面向员工角色 | 业主动作无法验证通过 | 新业主动作必须使用会话主体和显式项目授权 |
| MySQL/H2 行为差异 | H2 通过不能证明锁和并发 | 并发、重放、事务用 `decoboon-test` MySQL 复测 |
| 历史公开 URL 迁移未完成 | 新文件鉴权通过也可能泄露旧文件 | 必须覆盖迁移/失效策略，不能只测试新文件 |
| 真实微信手机号授权依赖外部环境 | 本地无法完整伪造 | 保留真机手工用例并记录失败原始证据 |

## 11. 交接给 development lane 的验收要求

development lane 交付时必须提供：

1. `changed_files` 清单和每个 Provider 的实际 `@Service` 路由。
2. 业主身份、项目授权、邀请消费和验收状态机的实体字段、迁移和唯一约束。
3. `@Properties` 的 page/list/info/save/update 响应白名单，明确哪些字段不下发。
4. 邀请过期、撤销、已消费、并发冲突和验收冲突的错误码映射。
5. 员工四角色和项目参与关系的权限规则，以及跨企业处理的 SQL/条件。
6. 私有文件新旧访问策略、旧 URL 处理和迁移结果。
7. 可执行的自测命令、夹具重建方式、已知风险和未决项。
8. 不得只提供“已开发完成”口述，不得把自测截图当成独立验收。

在收到上述交接前，acceptance lane 的状态为“验收方案已设计，独立执行未开始”。

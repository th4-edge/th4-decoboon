# 小程序全链路回归规范（含缺陷根因反思）

> 版本：v1（2026-09-16）
> 来源：`ACC-MP-BOSS-20260916` 企业负责人小程序全链路闭环验收
> 适用：`th4-decoboon-app`（uni-app 微信小程序）× `th4-decoboon`（th4 Provider 后端）
> 维护：acceptance lane；开发 lane 据此补齐用例与门禁

---

## 一、本轮缺陷的统一根因

4 个缺陷表面分散，收敛后只有 **3 类根因**：

| 根因类别 | 具体表现 | 涉及缺陷 |
| --- | --- | --- |
| R1 角色分支不完整 | 页面按"店长 / 团队长"二分编写，企业负责人落入错误的 `else` 分支，调用了无权限的 Provider | 001 |
| R2 规则粒度粗放 | 权限/保护规则把"读"和"写"用同一条约束覆盖，导致本人详情被写保护规则拦截 | 002 |
| R3 状态分支缺失 | 页面只实现"新建"路径（build），未实现"已存在/已锁定"路径（查看），也未对失败态兜底 | 003、004 |

共同特征：**都不是"代码写错了"，而是"场景没被穷举"**。功能在开发时验证的路径是"主角色 + 主状态 + 顺利路径"，缺陷全部出现在"其他角色 / 其他状态 / 失败路径"。

## 二、为什么"之前测试通过的功能"又出现 BUG

这是本轮最重要的结论：**之前并不是同一个东西通过了测试，而是不同层次的验证被当成了同一种"通过"。**

### 2.1 既有"通过"的真实覆盖层级

| 既有验证 | 实际验证内容 | 未覆盖内容 |
| --- | --- | --- |
| 小程序构建门禁（`type-check` / `build:mp-weixin` / `check:subpackages`） | 类型、编译、分包体积 | 任何运行时行为、任何接口返回 |
| 小程序合规验收（`PP-06`，结论 `BLOCKED_EXTERNAL`） | 域名占位、HTTPS、协议、隐私、权限声明 | 明确记录"真机、弱网、邀请、文件签名尚未验证" |
| 后端单元/集成测试（H2） | Provider 逻辑、数据权限切面、路由安全扫描 | 真实 MySQL 数据状态、真实角色组合、真实前端调用参数 |
| Provider 路由安全扫描 | 路由存在、是否 `Security`、权限注解 | 该路由被哪个角色、从哪个页面、在什么状态下调用 |

### 2.2 两个导致"回归幻觉"的机制

1. **角色可迁移性假设**：店长/团队长路径验证通过后，默认"换成 Boss 也应该没问题"。实际 001 正是 Boss 落入错误分支。
2. **状态可迁移性假设**：在"草稿方案"上验证洽谈页正常，默认"任何方案都正常"。实际 003 在"已锁定方案"上必然失败。

### 2.3 一句话结论

> 缺陷不是"修好后复发"，而是**从未在"该角色 × 该页面 × 该数据状态"这个组合上验证过**；此前的绿灯证明的是其它组合，不能外推。

## 三、反思原则（后续所有验收必须遵守）

1. **绿灯必须带"主语"**：任何"通过"结论必须写清"哪个角色、哪个端、哪条数据、什么状态"。禁止无主语结论（如"设计调度已验证"）。
2. **组合优先于功能**：验收对象不是"功能"，而是"角色 × 页面 × 接口 × 数据状态"的四元组合。
3. **失败路径与成功路径等权**：缺参、越权、已锁定、重复提交、空数据、超时，必须与主流程同等对待。
4. **业务校验不是缺陷**：后端按规则拒绝（如"只有已提交报价可以接受"）是正确行为；判定缺陷的前提是"调用方在合法业务路径上被错误拒绝"。
5. **先分层归因再定级**：出现失败必须区分"后端规则错 / 前端调用错 / 测试参数错"，不得笼统记为后端 BUG。本轮 9 条异常中，真正后端规则问题只有 1 条。

## 四、小程序全链路回归规范

### 4.1 回归必测矩阵（四元组合）

**维度 A 角色**（每次回归至少覆盖 Boss + 本轮改动角色）
`Boss`、`StoreManager`、`Designer`、`Marketer`、`Pm`、`Finance`、`TeamLeader`、`Customer(业主)`

**维度 B 页面**：主包 12 页 + 各业务分包页，逐个真实打开（禁止只查路由表存在）

**维度 C 数据状态**（每个详情/操作页至少覆盖 3 态）
- 空态：无记录
- 常规态：草稿/进行中
- 终态：已完成/已锁定/已归档

**维度 D 失败路径**：缺参、伪造 ID、跨企业 ID、越权角色、重复提交、并发修改、超时

### 4.2 每次回归的最低执行集（Definition of Done）

- [ ] 以目标角色在开发者工具登录，确认工作台身份与门店/企业信息正确
- [ ] 逐页真实打开目标页面，记录页面首屏关键字段（非"能打开"）
- [ ] 对每个页面调用的写接口，至少执行 1 次成功路径 + 1 次规则拒绝路径
- [ ] 采集整段时间窗的后端 `ERROR / Exception / 处理失败`，逐条给出归类（缺陷 / 业务校验 / 测试问题）
- [ ] 输出缺陷清单（编号 / 级别 / 现象 / 日志 / 最小复现 / 根因 / 建议）
- [ ] 明确列出**未覆盖项**，不得用"全量通过"表述部分验证

### 4.3 跨端契约一致性检查

1. 建立 `页面 → Provider → 合法角色集合 → 所需入参 → 前置状态` 映射表（可作为 `src/test` 下的契约用例维护）。
2. 同一 Provider 被多个角色调用时，映射表必须列出全部角色；前端分支（`if role`）必须在表中有对应行。
3. 前端出现 `else` 兜底调用某接口时，视为高风险信号，必须逐一确认所有可能角色。

### 4.4 失败态与只读态要求（前端）

- 读接口使用"写保护规则"返回 4xx 时，页面必须展示可理解原因与返回入口，禁止空白页。
- 页面对"已锁定/已归档"数据必须提供只读渲染路径，禁止默认执行"重建/覆盖"动作。
- 页面 `onLoad` 中的异步加载必须 `try/catch`，并渲染错误态。

### 4.5 证据与留痕要求

| 证据 | 要求 |
| --- | --- |
| 登录证据 | 角色、企业、门店、账号（脱敏） |
| 页面证据 | 路由清单 + 每页关键文本/字段快照 |
| 接口证据 | Provider 名称、入参（脱敏）、响应码、响应体摘要 |
| 日志证据 | 时间戳、日志原文行、时间窗起始行号 |
| 数据证据 | 关键表的主键与关键字段变化 |
| 未覆盖项 | 显式列表 |

### 4.6 自动化资产

本轮沉淀的可复用资产（acceptance lane workspace）：

| 资产 | 用途 |
| --- | --- |
| `route-sweep.cjs` | 按路由清单巡检页面、采集文本/重定向/未处理异常 |
| `analyze-backend-log.sh` | 从指定行号起分析后端异常，自动过滤框架噪音 |
| `route-sweep-result.json` | 巡检原始结果，可作为历史基线对比 |

建议后续演进：
1. 将路由清单与角色矩阵参数化，支持 `--role`、`--route-group`。
2. 增加"关键字段断言"，把"页面打开"升级为"数据正确"。
3. 接入每次发版前的小程序冒烟流水（开发者工具 CLI + automator）。

## 五、针对本轮缺陷的整改建议

| 缺陷 | 责任 lane | 建议动作 | 验证方式 |
| --- | --- | --- | --- |
| DEF-MP-BOSS-001 | development | 补齐 Boss 分支或隐藏入口；建立角色-Provider 契约用例 | Boss 打开设计调度页，数据非 0 且无 403 日志 |
| DEF-MP-BOSS-002 | development | 读接口允许查询本人；写操作保留自我保护 | Boss 查看自身成员详情成功；对自己的交接/离职仍被拒 |
| DEF-MP-BOSS-003 | development | 洽谈页先查后建，锁定态只读 | 已锁定方案可查看历史洽谈；草稿方案仍可重建 |
| DEF-MP-BOSS-004 | development | 页面加载统一错误态处理 | 传入非法/缺失参数时展示错误态而非白屏与未处理异常 |

> 按项目规范，acceptance lane 不修改生产代码；以上缺陷需由 development lane 修复后，acceptance 使用同一矩阵复验。

## 六、规范速查（写进日后验收报告的开头）

1. 通过结论必须带角色、端、数据状态。
2. 每次回归覆盖：角色矩阵 × 页面清单 × 三态数据 × 失败路径。
3. 跨端不互证，跨角色不互推。
4. 业务规则拒绝 ≠ 缺陷；合法路径被拒才是缺陷。
5. 未覆盖项必须显式声明。

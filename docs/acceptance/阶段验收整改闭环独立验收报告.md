## 5. 缺陷

### DEF-RECTIFY-001 · P1 · 存量 Pending 验收没有第 1 轮

- 实际：存量 acceptance `227467828918222848` 的轮次查询返回空数组。
- 预期：首次提交应形成第 1 轮；迁移上线后存量 Pending/Rejected 验收也应补登历史轮次。
- 影响：历史待确认验收打开时间线为空；如果存量 Pending 后续驳回再复验，轮次会从 2 开始，造成第 1 轮缺失和审计不连续。
- 最小复现：查询存量 acceptance 的 `project/acceptance/round/page`。
- 建议责任：development / migration owner。
- 修复方向：在迁移中增加幂等 backfill，为每张存量 `db_acceptance` 建立 `round_no=1` 轮次并复制现有结论、问题和证据；执行前先做旧库样本审计。

### DEF-RECTIFY-002 · P1 · 重复/并发提交未按产品契约幂等

- 实际：
  - 顺序重复提交返回 `400 该阶段已有待确认验收单`；
  - 并发首次提交结果为一个 `success=true`，另一个 `undefinedErrorCode / 未定义错误信息:{0}`；
  - DB 最终只有一张验收单和一个 `Pending` 轮次。
- 预期：产品设计 §7.3 明确“直接返回该轮次，不新增”；并发后到请求也应返回已有事实，不得暴露未定义错误码。
- 影响：用户看到未知错误，移动端无法区分“重复点击”“并发冲突”和系统故障；接口不可作为稳定幂等契约使用。
- 最小复现：对同一 stage/acceptance 连续调用复验，或并发发起两个首次提交。
- 建议责任：development。
- 修复方向：在事务边界内锁定 stage/acceptance 后，重复 Pending 分支返回已有 Round；将数据库唯一冲突/deadlock 转换为同一幂等响应。

### DEF-RECTIFY-003 · P1 · 业主驳回未强制问题清单、整改责任人和截止日期

- 实际：`customer/acceptance/update` 在 `issues=[]` 时仍可完成驳回；接口没有整改责任人和截止日期字段。
- 预期：业务规则要求业主驳回给出问题清单；涉及整改时必须指定责任人和截止日期，缺少时阻断并提示补全。
- 影响：形成“整改中”阶段但没有明确问题或责任人，整改跟进页无法形成可执行的督办事实。
- 最小复现：`ownerRejectionMustRequireIssueListProbe` 预期 `400`，实际未抛出异常；日志见 `probe-owner-issues-required.log`。
- 建议责任：development。
- 修复方向：在后端统一校验驳回 issues 非空；明确责任人和截止日期由业主还是项目侧填写，并在接口和 UI 中落地同一口径。

### DEF-RECTIFY-004 · P2 · App 缺少业主驳回问题与整改责任交互

- 实际：`accept/edit.vue` 的业主驳回按钮直接调用 `acceptanceApi.confirm(id, false)`，没有问题清单输入；当前页面也没有整改责任人和截止日期选择控件。
- 预期：业主驳回时可填写问题清单；项目侧/对应角色能明确责任人、截止日期，并在整改跟进中看到。
- 影响：即使后端补齐校验，当前 App 路径仍无法完成合规驳回和整改登记。
- 建议责任：development / App。
- 修复方向：增加问题清单输入和校验；明确角色权限后增加责任人与截止日期选择，提交到 `customer/acceptance/update` 或项目整改更新入口。

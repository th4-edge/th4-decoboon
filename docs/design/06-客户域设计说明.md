# 客户域设计说明

> 对应代码：`com.th4.edge.decoboon.customer`  
> 对应数据表：`cust_customer`

## 1. 领域定位

客户域负责承接线索转化后的正式客户，保存客户的联系方式、意向地址、面积、负责人和生命周期状态。

客户是报价和项目的上游主体。一个客户可以拥有多个报价和多个项目，不在客户表保存单个 `projectId`，以支持老客复购、多套房和多次装修。

## 2. 核心模型

### Customer

- `custId`
- `company → Company`
- `store → Store`
- `team → Team`
- `name`
- `telNo`
- `community`
- `addr`
- `area`
- `status`
- `owner → Employee`
- `remark`
- 创建/更新时间

### CustStatus

```text
New → Following → Quoted → Signed → Serving → Finished
任意阶段 → Lost
```

## 3. Provider

| 路由 | 能力 | 说明 |
| --- | --- | --- |
| `customer/customer/save` | 保存 | 创建客户并绑定企业和负责人 |
| `customer/customer/page` | 分页 | 按企业、门店、团队、本人四级数据范围统一过滤 |
| `customer/customer/info` | 详情 | 使用同一数据范围 Specification 查询详情 |
| `customer/customer/update` | 编辑 | 按当前数据范围加载客户，编辑基础信息和负责人归属 |

四个 Provider 均继承 `Security` 并通过 `@User Employee employee` 获取登录主体，前端不能指定企业、门店、团队或绕过负责人范围。

数据权限统一组件：

- `com.th4.edge.tenant.user.access.annotation.DataPermission`
- `com.th4.edge.tenant.user.access.context.DataScopeContext`
- `com.th4.edge.tenant.user.access.filter.DataScopeRequestFilter`
- `com.th4.edge.tenant.user.access.filter.DataPermissionCrudAspect`
- `com.th4.edge.tenant.user.access.DataScopeSpecification`

## 4. 业务规则

- 客户必须归属一个 `Company`。
- 负责人使用 `Employee` 对象关联，禁止裸 `empId`。
- 数据权限：BOSS=`company`；门店店长=`company + store`；团队负责人=`company + team`；普通员工=`company + owner`。
- 保存模型由 `@ModelSaveInject` 组装，Provider 仍负责固定企业、校验负责人、复制门店/团队快照并执行落库；非 BOSS 的负责人强制为当前员工，BOSS 指定负责人时必须校验其属于当前企业。
- 编辑权限：编辑前通过 `DataScopeSpecification` 与主键组合加载客户，越权返回 404；非 BOSS 不能转交客户，BOSS 转交时必须校验负责人属于当前企业，并同步刷新 `store/team`。
- 客户编辑包含字段白名单、状态保护和负责人转交规则，因此不使用 `@ModelUpdateInject` 直接加载，避免绕过 `@DataPermission` 和编辑字段控制。
- 编辑接口只维护姓名、电话、小区、地址、面积和备注，客户状态由后续状态流转服务维护，前端不能直接覆盖 `status`。
- 当前自定义详情和编辑查询使用 `DataScopeSpecification`；切换到框架通用 `service/info|update|delete` 时由 `DataPermissionCrudAspect` 自动完成范围加载。
- 分页查询由 `DataScopeRequestFilter` 在 CriteriaQuery 上统一追加数据范围，前端伪造 `company/owner/store/team` 参数不能扩大范围。
- 数据表索引：`(com_id, cust_id)`、`(com_id, store_id, cust_id)`、`(com_id, team_id, cust_id)`、`(com_id, emp_id, cust_id)`。
- 客户姓名、电话、小区和地址设置 `@Keyword`，支持全局搜索。
- 客户删除采用状态关闭或归档，不物理删除已有报价/项目的客户。
- 客户状态变化由业务上下文和后续跟进服务维护，不允许前端任意覆盖。
- 客户面积是报价计算的重要输入，必须为正数。
- 客户转交时必须在同一事务中同步 `owner/store/team`，禁止只修改 `owner` 导致归属快照不一致。

## 5. 响应字段设计

客户响应遵循页面最小化原则，不使用一套字段配置覆盖所有接口：

| 接口 | Customer 字段 | 关联对象 | 说明 |
| --- | --- | --- | --- |
| `page` | `custId/name/telNo/community/area/status/owner` | `owner(empId,name)` | 支持列表卡片、筛选、搜索和跳转 |
| `info` | `custId/name/telNo/community/addr/area/status/owner/remark` | `owner(empId,name)` | 满足详情和编辑表单 |
| `save` | 与 `info` 相同的业务字段 | `owner(empId,name)` | 返回创建完成后的最小实体 |
| `update` | 与 `info` 相同的业务字段 | `owner(empId,name)` | 返回编辑完成后的最小实体 |

企业、门店、团队属于服务端数据权限归属，不作为客户页面展示字段，因此默认不进入客户接口 JSON。这样可以避免序列化完整的 `Company/Store/Team/Employee` 关联树，也避免因为访问无关懒加载对象产生额外 SQL。

## 6. 上下游关系

```text
Lead / 客户登记
→ Customer
→ Quote
→ Project
→ Receipt / 复购
```

本阶段实现客户登记、列表、详情和编辑；后续客户跟进、量房、标签、复杂归属变更继续在 `customer` 领域扩展，不放入通用组件层。

# 装得清数据权限设计规范

> 适用对象：所有企业内业务实体、Provider、Repository、Context 与跨域查询。  
> 强制级别：最高。与普通业务设计冲突时，以数据权限闭环为先。

## 1. 设计目标

装得清的数据权限不是前端菜单权限，也不是登录成功后的默认能力，而是每次访问业务数据时都必须在服务端重新计算的强约束。

系统统一使用四级数据范围：

```text
Company → 当前企业
Store   → 当前企业 + 当前门店
Team    → 当前企业 + 当前团队
Self    → 当前企业 + 当前员工
```

角色与数据范围显式关联：

| 角色 | 数据范围 |
| --- | --- |
| `BOSS` | `Company` |
| 门店店长 | `Store` |
| 团队负责人 | `Team` |
| 普通员工 | `Self` |

角色只决定“能看多大范围”，实体归属字段决定“这条数据属于哪个范围”，Provider 负责把两者组合成不可绕过的查询条件。

th4 的对象领域查询负责按实体构建 CriteriaQuery，但不会自动提供数据权限。权限条件必须由统一下沉组件追加。

## 2. 两个核心概念

### 2.1 数据归属

有明确个人负责关系的业务实体，使用统一归属结构：

```java
@Note("所属企业")
@ManyToOne(fetch = FetchType.LAZY)
@JoinColumn(name = "com_id", nullable = false)
private Company company;

@Note("所属门店")
@ManyToOne(fetch = FetchType.LAZY)
@JoinColumn(name = "store_id")
private Store store;

@Note("所属团队")
@ManyToOne(fetch = FetchType.LAZY)
@JoinColumn(name = "team_id")
private Team team;

@Note("负责人")
@ManyToOne(fetch = FetchType.LAZY)
@JoinColumn(name = "emp_id")
private Employee owner;
```

要求：

- 全部使用对象关联，禁止裸 `companyId/storeId/teamId/empId`。
- `company` 是强制租户边界，必须是所有权限联合索引的最左字段。
- 有独立门店/团队授权要求的实体，不能只保存 `owner` 后临时推导门店和团队。
- `store/team/owner` 是业务归属快照，必须明确员工调店、调团队、客户转交时的更新规则。
- 归属字段只能由服务端根据登录员工和已校验的负责人复制，不能信任前端传入值。

### 2.2 数据范围声明

实体使用 `@DataPermission` 声明权限查询字段：

```java
@Model
@Entity
@DataPermission
@Table(name = "cust_customer", indexes = {
        @Index(name = "idx_cust_customer_company", columnList = "com_id, cust_id"),
        @Index(name = "idx_cust_customer_company_store", columnList = "com_id, store_id, cust_id"),
        @Index(name = "idx_cust_customer_company_team", columnList = "com_id, team_id, cust_id"),
        @Index(name = "idx_cust_customer_company_owner", columnList = "com_id, emp_id, cust_id")
})
public class Customer extends AuditModel {
    // company / store / team / owner
}
```

默认字段名：

```text
company / store / team / owner
```

如果实体使用不同语义名，可以在注解中覆盖，但必须保持含义一致：

```java
@DataPermission(owner = "createdBy")
```

### 2.3 纯企业级主数据

BIM 工艺、材料、套餐模板等不属于员工个人的企业级主数据，不直接套用 `Self/Store/Team` 条件，也不应虚构 `owner` 字段。

这类数据仍必须强制追加当前企业条件，但不得把普通员工的 `Self` 范围错误转换成对主数据负责人字段的过滤。是否允许普通员工读取，属于功能权限；企业隔离属于数据权限，两者必须分开设计。

## 3. 统一运行时组件

### 3.1 DataScopeType

位置：

```text
com.th4.edge.tenant.user.configure.DataScopeType
```

```java
Company / Store / Team / Self
```

### 3.2 DataScopeContext

位置：

```text
com.th4.edge.tenant.user.access.context.DataScopeContext
```

职责：

1. 根据当前登录主体重新加载完整 `Employee`。
2. 读取当前角色绑定的 `DataScopeType`。
3. 校验当前员工是否具备门店或团队范围所需的组织归属。
4. 生成当前请求不可变的 `DataScope`。

禁止从 JWT、前端参数或 Request 实体拼装企业、角色、门店、团队。

### 3.3 DataScopeCriteria

位置：

```text
com.th4.edge.tenant.user.access.DataScopeCriteria
```

统一生成：

```text
Company -> com_id = ?
Store   -> com_id = ? AND store_id = ?
Team    -> com_id = ? AND team_id = ?
Self    -> com_id = ? AND emp_id = ?
```

企业条件必须永远存在，即使使用全局唯一 ID 也不能省略。

### 3.4 DataScopeRequestFilter

位置：

```text
com.th4.edge.tenant.user.access.filter.DataScopeRequestFilter
```

自动处理条件：

```text
Provider implements CriteriaQueryAware
Request 实体标注 @DataPermission
```

具体业务 Provider 仍必须继承 `Security`；框架通用 `service/page|list|count` 由过滤器统一完成认证。

拦截器优先级为 `155`：

```text
160 CriteriaQueryAwareRequestFilter：构建 CriteriaQuery
155 DataScopeRequestFilter：追加权限条件
150 业务 Predicate / Keyword / Group：追加业务条件
```

权限条件与业务条件使用 `AND` 组合。前端传入的条件即使包含企业和负责人，也只能缩小范围，不能扩大范围。

### 3.5 DataScopeSpecification

位置：

```text
com.th4.edge.tenant.user.access.DataScopeSpecification
```

用于不能依赖 Criteria 拦截器的详情、更新、删除和跨域读取：

```java
DataScope scope = dataScopeContext.requireScope(employee);

Specification<Customer> byId =
        (root, query, builder) -> builder.equal(root.get("custId"), customerId);

Customer customer = customerRepository.findOne(
        byId.and(DataScopeSpecification.visible(Customer.class, scope)))
        .orElseThrow(() -> new DefinedException(
                new DefaultErrorCode("404", "客户不存在或无权访问")));
```

禁止以下写法：

```java
repository.findById(id) // 先查后判断企业和数据范围
```

### 3.6 框架通用 CRUD 切面

框架通用 `service/save` 先由 `AccessDataPermissionSaveRequestFilter` 在 `@ModelSaveInject` 完成后覆盖归属字段；`service/update` 由 `DataPermissionCrudAspect` 先按范围加载旧实体，再由 `AccessDataPermissionUpdateRequestFilter` 在 `@ModelUpdateInject` 完成后保护归属字段。`service/delete|info` 继续由 `DataPermissionCrudAspect` 自动处理。切面运行在框架 ProviderAspect 外层，并在事务中执行：

```text
service/save   -> 服务端组装 company/store/team/owner
service/update -> 按当前范围加载旧实体，保留不可变归属，合并可修改字段
service/info   -> 按主键 + 当前数据范围加载实体
service/delete -> 按主键 + 当前数据范围加载实体后删除
```

实体只要标注 `@DataPermission`，使用通用 CRUD 路由时无需在每个 Provider 内重复编写范围判断。

### 3.7 与 @ServiceProperties 的边界

`@ServiceProperties` 只负责按 URI 注册 Jackson 响应字段过滤，不参与 CriteriaQuery，也不参与数据权限判断。

必须区分：

| 注解/组件 | 负责范围 |
| --- | --- |
| `@DataPermission` | 声明实体用于数据范围过滤的归属字段 |
| `DataScopeRequestFilter` | 向 CriteriaQuery 追加数据范围 |
| `AccessDataPermissionSaveRequestFilter` | 在 `@ModelSaveInject` 后覆盖框架保存实体的企业、门店、团队和负责人 |
| `AccessDataPermissionUpdateRequestFilter` | 在 `@ModelUpdateInject` 后保护框架修改实体的企业、门店、团队和负责人 |
| `DataScopeSpecification` | 详情、更新、删除和跨域查询的数据范围 |
| `DataPermissionCrudAspect` | 框架通用 save/update/delete/info 的自动权限闭环 |
| `@Properties` | 具体 Provider 的响应字段裁剪 |
| `@ServiceProperties` | 无具体 Provider 的通用 `{model}-{service}` 路由响应字段裁剪 |

响应字段裁剪同时遵循轻量化原则：`page/list` 只返回列表展示、筛选和跳转字段；`info` 返回详情页实际字段；`save/update` 返回前端更新本地状态所需的最小实体。关联对象使用白名单最小字段，不能默认序列化完整 `Company/Store/Team/Employee` 聚合，避免无意义响应体积和懒加载额外 SQL。

因此，给实体增加 `@ServiceProperties(uris = "{model}-page")` 不会使 `{model}-page` 自动具备角色数据权限。数据权限仍必须同时满足：

```text
实体标注 @DataPermission
Provider 实现 CriteriaQueryAware
```

### 3.8 模型注值注解与数据权限边界

`@ModelSaveInject` 和 `@ModelUpdateInject` 位于：

```text
com.th4.edge.framework.data.jpa.inject.annotation
```

两者都可标注 Provider 的 `call` 参数，但只负责模型装配，不负责持久化和数据权限：

| 注解 | 作用 | 是否自动落库 | 是否自动做 DataPermission |
| --- | --- | --- | --- |
| `@ModelSaveInject` | 按请求变量组装新模型及关联对象，可注入审计主体 | 否 | 否 |
| `@ModelUpdateInject` | 按实体 `@Id` 加载旧模型并合并非主键字段 | 否 | 否 |

保存写法：

```java
public Customer call(@ModelSaveInject Customer request) {
    Employee current = dataScopeContext.requireEmployee(employee);
    Employee owner = customerContext.resolveOwner(current, ownerId, current);
    customerContext.applyOwnership(request, owner);
    request.setStatus(CustStatus.New);
    return customerRepository.save(request);
}
```

更新边界：

- 框架通用 `service/update` 已内置 `@ModelUpdateInject`，由 `DataPermissionCrudAspect` 按范围加载旧实体，再由 `AccessDataPermissionUpdateRequestFilter` 完成最终归属保护。
- `@ModelUpdateInject` 自身通过 `EntityManager.find` 按主键加载模型，不会读取 `@DataPermission`。
- 自定义 Provider 若要保护状态、余额、审批结果、负责人等字段，必须继续使用 `DataScopeContext + DataScopeSpecification` 在同一个查询中按主键和数据范围加载，再显式合并字段白名单。
- `@ModelUpdateInject` 使用实体字段名读取主键，例如 `custId`；不能依赖前端别名 `customerId` 触发加载。
- 两个注解均不能替代 `repository.save`、`entityManager.persist`、企业覆盖或角色数据范围校验。

## 4. Provider 权限闭环

### 4.1 page / list / count

- 具体业务 Provider 接口继承 `Security`；框架通用 `service/page|list|count` 由统一过滤器认证。
- Provider 实现 `CriteriaQueryAware`，通常继承 `AbstractPage<Model>`。
- `Model` 标注 `@DataPermission`。
- 不得在 `call()` 中依赖请求对象设置企业或负责人作为唯一权限条件。
- 允许在 `call()` 中补充业务条件，但统一拦截器的权限条件必须仍然存在。

### 4.2 info / update / delete

- 框架通用 `service/info|update|delete`：由 `DataPermissionCrudAspect` 自动完成范围加载和归属字段保护。
- 自定义详情、更新、删除 Provider：必须先从 `@User Employee` 重新加载当前员工，并构造 `DataScope` 和 `DataScopeSpecification`。
- 主键条件与权限条件必须在同一次 Repository 查询或同一次 Criteria 查询中完成。
- 无命中统一返回 `404`，不得泄露“数据存在但无权访问”。

### 4.3 save

- `company` 固定为当前登录员工所属企业。
- 非 `BOSS` 的 `owner` 强制为当前员工。
- `BOSS` 指定负责人时，必须校验负责人员工属于当前企业。
- `store/team` 从服务端确认后的负责人归属复制。
- 前端提交的 `companyId/storeId/teamId/ownerId` 只能作为候选输入，不能直接落库。

### 4.4 跨域读取

报价读取客户、项目读取报价等跨域操作，也必须：

1. 从当前登录员工取得 `DataScope`。
2. 使用目标实体的 `DataScopeSpecification`。
3. 禁止使用裸 `findById` 绕过权限。

## 5. 组织变更规则

必须提前明确并写入领域文档：

- 员工调店后，历史客户是否随员工迁移。
- 员工调团队后，团队负责人是否仍可查看原团队客户。
- 客户转交后，`store/team/owner` 是否同步更新。
- 门店关闭后，数据查询和统计是否仍可按历史门店维度访问。

默认建议：

```text
customer.store / customer.team 是客户归属快照；
客户转交时，在同一 Provider 事务内同步更新 owner/store/team；
不使用查询时的 employee.store 临时推导客户门店。
```

## 6. 索引规范

有四级权限要求的业务表至少建立：

```text
(com_id, 业务主键)
(com_id, store_id, 业务主键)
(com_id, team_id, 业务主键)
(com_id, emp_id, 业务主键)
```

索引必须匹配实际 SQL 条件，`com_id` 始终是最左字段。若增加新的权限维度，按：

```text
(com_id, 新范围字段, 业务主键)
```

扩展，禁止只建立裸主键索引。

## 7. 测试要求

每个有数据权限的领域至少覆盖：

| 场景 | 必须验证 |
| --- | --- |
| BOSS | 只能查看当前企业全量，不返回其他企业 |
| 门店店长 | 只返回当前企业当前门店 |
| 团队负责人 | 只返回当前企业当前团队 |
| 普通员工 | 只返回当前企业本人 |
| 伪造参数 | 前端伪造 `company/store/team/owner` 不能扩大范围 |
| 详情越权 | 其他范围数据返回 404 |
| 更新/删除越权 | 不允许跨范围修改或删除 |
| 跨域读取 | 未命中当前数据范围时拒绝 |
| 组织变更 | 调店、调团队、转交后的预期范围明确且有测试 |

验收不得只验证“接口能返回”，必须验证不同身份在同一接口上的数据集差异。

## 8. 新业务对象接入清单

1. 定义企业、门店、团队、负责人归属。
2. 确定角色与 `DataScopeType` 映射，禁止隐式扩大权限。
3. 实体加入 `company/store/team/owner` 对象关联。
4. 实体添加 `@DataPermission`。
5. 建立四级权限联合索引。
6. page/list/count 使用 `AbstractPage` 或等价 `CriteriaQueryAware`。
7. 优先使用框架通用 `service/save|info|update|delete`：保存和修改分别由对应的 Access 过滤器加 `DataPermissionCrudAspect` 闭环，其余由 `DataPermissionCrudAspect` 闭环。
8. 自定义 info/update/delete Provider 使用 `DataScopeSpecification`。
9. save 服务端固定企业和负责人，复制门店、团队。
10. 跨域读取使用企业 + 数据范围条件。
11. 补齐四角色、伪造参数、跨企业、详情越权测试。
12. 更新领域设计文档和序列化属性白名单。

## 9. 代码生成模板

### 9.1 生成前判定

```text
实体是否有个人/门店/团队归属？
├─ 否：企业级主数据
│   └─ 只需 Company，不添加虚构 owner；不得错误应用 Self
└─ 是：@DataPermission 业务实体
    ├─ company/store/team/owner 对象关联
    ├─ 四级权限联合索引
    └─ 根据路由选择通用 CRUD 或自定义 Provider
```

### 9.2 实体模板

```java
@DataPermission
@Entity
@Table(name = "业务表", indexes = {
        @Index(name = "idx_xxx_company", columnList = "com_id, xxx_id"),
        @Index(name = "idx_xxx_store", columnList = "com_id, store_id, xxx_id"),
        @Index(name = "idx_xxx_team", columnList = "com_id, team_id, xxx_id"),
        @Index(name = "idx_xxx_owner", columnList = "com_id, emp_id, xxx_id")
})
public class Xxx extends AuditModel {

    @ManyToOne(fetch = FetchType.LAZY)
    @JoinColumn(name = "com_id", nullable = false)
    private Company company;

    @ManyToOne(fetch = FetchType.LAZY)
    @JoinColumn(name = "store_id")
    private Store store;

    @ManyToOne(fetch = FetchType.LAZY)
    @JoinColumn(name = "team_id")
    private Team team;

    @ManyToOne(fetch = FetchType.LAZY)
    @JoinColumn(name = "emp_id")
    private Employee owner;
}
```

### 9.3 通用 ModelService 模板

实体标注 `@DataPermission` 后，通用路由自动获得权限：

```text
xxx-page / xxx-list / xxx-count
    -> DataScopeRequestFilter

xxx-save
    -> AccessDataPermissionSaveRequestFilter
    -> DataPermissionCrudAspect + DataPermissionCrudContext

xxx-update
    -> AccessDataPermissionUpdateRequestFilter
    -> DataPermissionCrudAspect + DataPermissionCrudContext

xxx-info / xxx-delete
    -> DataPermissionCrudAspect + DataPermissionCrudContext
```

生成通用 CRUD 时禁止再新增一层手工角色判断。

### 9.4 自定义分页 Provider 模板

```java
public interface Page extends Provider<Xxx, Page<Xxx>>, Security {
}

@Service("domain/xxx/page")
@Scope(ScopeTypes.PROTOTYPE)
public class Page extends AbstractPage<Xxx> implements Page {

    public Page(EntityManager entityManager) {
        super(entityManager);
    }

    @Override
    public org.springframework.data.domain.Page<Xxx> call(Xxx request) {
        return super.call(request);
    }
}
```

### 9.5 自定义详情、更新、删除模板

```java
DataScope scope = dataScopeContext.requireScope(employee);
Specification<Xxx> byId = (root, query, builder) ->
        builder.equal(root.get("xxxId"), xxxId);

Xxx entity = repository.findOne(
        byId.and(DataScopeSpecification.visible(Xxx.class, scope)))
        .orElseThrow(() -> new DefinedException(
                new DefaultErrorCode("404", "数据不存在或无权访问")));
```

### 9.6 自定义创建模板

```java
Employee current = tenantContext.requireEmployee(employee);
Employee owner = current.getRole() == EmployeeRole.Boss
        ? validateOwner(ownerId, current.getCompany())
        : current;

xxx.setCompany(current.getCompany());
xxx.setOwner(owner);
xxx.setStore(owner.getStore());
xxx.setTeam(owner.getTeam());
```

自定义创建必须自行完成同样的归属组装，通用切面只保护框架通用 `service/save`。

### 9.7 生成测试模板

每个领域至少生成：

```text
1. BOSS 查询当前企业全量
2. 门店店长查询当前门店
3. 团队负责人查询当前团队
4. 普通员工查询本人
5. 跨企业数据不可见
6. 前端伪造 company/store/team/owner 不可扩权
7. 越权 info/update/delete 返回 404
8. 转交、调店、调团队后的归属快照符合领域规则
```

## 10. 禁止事项

- 禁止只在前端隐藏菜单或按钮。
- 禁止把登录成功等同于数据权限通过。
- 禁止信任前端 `companyId/storeId/teamId/empId/ownerId`。
- 禁止 `findById(id)` 后再判断企业或负责人。
- 禁止只写 `request.setCompany(...)` 而不向 CriteriaQuery 追加条件。
- 禁止在自定义 JPQL、原生 SQL、Specification 中遗漏企业和数据范围。
- 禁止把角色判断散落在每个 Provider；角色到范围映射必须集中维护。
- 禁止对不同业务域复制一套不一致的数据范围算法。

# 家装核心业务对象标准化设计

> 版本：v1.0 · 2026-09-13  
> 目标：统一装得清对施工、主材、软装家具、全屋定制、电器设备、综合其他的业务语义，支撑设计报价、项目施工、增减项、供应商、成本和账务闭环。  
> 结论：不把六类业务压成一张“大而全”的表，也不做六套互不相通的主数据。采用“一个项目根 + 六类业务明细 + 价格/供应/执行/账务分层”的组合模型。

## 1. 当前问题的本质

当前工程中同一个业务概念被多个模型重复表达：

```text
bim.construct.Construction            旧施工主数据
bim.material.Material                 旧主材主数据
bim.catalog.CatalogItem               六类业务统一目录
design.DesignItem                     设计分项
trade.quote.QuoteItem                 报价快照
project.ProjectTask                   施工任务
project.MaterialPlan                  材料计划
finance.Payable                       应付单
```

同一施工项可能同时出现在：

```text
Construction
CatalogItem
DesignItem
QuoteItem
ProjectTask
```

同一主材可能同时出现在：

```text
Material
CatalogItem
DesignItem
QuoteItem
MaterialPlan
Payable
```

这不是简单的“表太多”，而是**事实层级没有分开**：

- 行业和企业可售的项目定义，被当成了项目实际执行记录。
- 设计阶段的选择，被当成了报价合同快照。
- 报价快照，被当成了施工任务和采购订单。
- 采购或施工执行，又被反写到材料/施工目录。

因此模型必须按“定义 → 选择 → 报价 → 合同/变更 → 执行 → 账务”分层，而不是按类似字段来决定是否合并。

## 2. 关键结论

### 2.1 一个实体类是否可行

一个 `SellableItem` 根实体可以统一解决：

- 六类业务在选材、搜索、报价中的统一身份。
- 报价行、设计行、变更行的统一引用。
- 跨类型统计、权限、版本和状态管理。

但**不能把六类业务的差异化字段全部塞进同一张表**。施工没有品牌型号，电器需要功率、水电条件、序列号和保修，全屋定制需要参数化尺寸、板材、五金和拆单，主材需要品牌、SKU、损耗、采购和库存。强行合并会导致：

- 大量可空字段，数据库无法约束真正合法的组合。
- 页面和 Provider 需要针对类型写大量条件判断。
- 新业务类型每增加一项属性，所有历史和无关类型都被迫变更。
- 供应商、执行和账务无法建立准确的类型化约束。

### 2.2 推荐模型

推荐使用“项目根 + 类型明细”的组合模型：

```text
ItemCategory（分类）
    ↓
SellableItem（企业可售项目根）
    ├─ ConstructionItemDetail（施工明细）
    ├─ MaterialItemDetail（主材明细）
    ├─ SoftFurnitureItemDetail（软装家具明细）
    ├─ CustomFurnitureItemDetail（全屋定制明细）
    ├─ ApplianceItemDetail（电器设备明细）
    └─ GeneralItemDetail（综合其他明细）
```

根实体负责统一身份和通用报价能力，类型明细负责业务特有字段，价格、供应、执行和账务继续分层。

### 2.3 设计、报价、执行和账务不能合并

```text
设计选择（可修改）
  → 报价快照（不可回写）
  → 合同基线（客户确认）
  → 变更单（增减项）
  → 项目执行事实（施工/采购/交付/安装）
  → 成本与应付/应收事实
```

任何一层都不能直接修改上一层的历史数据，必须通过新版本、快照或变更记录表达。

## 3. 领域语言统一

| 领域术语 | 推荐实体 | 说明 | 不能和什么混淆 |
| --- | --- | --- | --- |
| 行业标准项目 | `StandardItemTemplate` | 平台沉淀的标准分类、计量方式、默认工艺和字段模板 | 不是某企业的实际商品 |
| 企业可售项目 | `SellableItem` | 企业在报价中可以选择和销售的施工、材料、家具、电器等 | 不是项目已经发生的任务或采购 |
| 项目变体 | `ItemVariant` | 同一项目的颜色、型号、规格、系列、尺寸或套餐组合 | 不是设计后的实际尺寸 |
| 价格本 | `PriceBook`、`PriceBookEntry` | 按区域、渠道、客户等级、时间生效的销售价格 | 不是成本价，也不是采购价 |
| 成本本 | `CostBook`、`CostBookEntry` | 人工、材料、辅料、机械、运费、安装、税费等成本 | 不是客户报价 |
| 供应商来源 | `PartnerItem` | 哪个供应商/工厂/班组能提供该项目，价格、交期、账期、起订量 | 不是采购订单 |
| 设计选择行 | `DesignItem` | 设计师在方案中选择的项目、数量和空间 | 不是合同报价 |
| 报价快照行 | `QuoteItem` | 客户报价中的不可变价格、成本和公式 | 不是可继续改的设计行 |
| 变更行 | `ChangeOrderItem` | 新增、取消、替换、调量、调价形成的差异 | 不覆盖原报价 |
| 履约行 | `ProjectTask`、`MaterialPlan`、`DeliveryPlan` | 项目实际施工、采购、交付和安装 | 不反写目录 |
| 财务事实 | `Payable`、`Receivable`、`Ledger` | 应付款、应收款和资金流水 | 不直接从目录实时计算 |

## 4. 六类业务的标准边界

### 4.1 施工 Construction

**业务本质：服务型履约，核心是人工、辅料、机械、工艺和工序。**

标准字段：

- 施工分类和工序阶段：拆除、水电、瓦工、木工、油漆、安装等。
- 施工工艺、施工步骤、验收标准、隐蔽工程标识。
- 计量方式：面积、长度、数量、点位、套、项、固定总价。
- 计算规则：工程量、最低计价量、扣减规则、损耗率、附加系数。
- 人工、辅料、机械、措施费、管理费、税费。
- 默认工期、前置工序、后续工序、是否允许并行。
- 施工班组/劳务供应商、班组技能、结算方式、质保期。
- 变更规则：已施工、未施工、拆改、返工、材料损耗等差异。

履约去向：

```text
QuoteItem(Construction)
  → ProjectTask / WorkOrder
  → 施工进度、验收、隐蔽资料、现场签证
  → LaborPayable / SubcontractPayable
```

### 4.2 主材 Material

**业务本质：标准化或半标准化 SKU，核心是品牌、规格、损耗、采购和库存。**

标准字段：

- 主材大类、品牌、系列、型号、规格、颜色、材质、等级。
- 销售单位、采购单位、换算关系、包装单位。
- 损耗率、起订量、最小包装量、补货周期。
- 展厅价、活动价、区域价、客户等级价、采购参考价。
- 供应商、工厂、产地、交期、账期、税率、运费规则。
- 库存方式：不入库、项目直送、仓库领用、供应商代发。
- 替代品、配套品、可选项、升级项。
- 批次、色差、质保和售后规则。

履约去向：

```text
QuoteItem(Material)
  → MaterialPlan
  → PurchaseOrderLine / DeliveryPlan / WarehouseReceipt
  → SupplierPayable
```

### 4.3 软装家具 SoftFurniture

**业务本质：设计风格强、组合性强的商品与服务，核心是搭配、交期、物流和安装。**

标准字段：

- 品类、风格、材质、颜色、尺寸、组合方式。
- 沙发、床、餐桌椅、窗帘、灯具、装饰画等搭配组。
- 单品、套餐、可选替换项、加价项。
- 供应商、品牌、渠道、交期、物流方式、安装方式。
- 空间适配、尺寸校核、入户条件、退换货规则。
- 销售价、采购价、物流费、安装费、售后成本。

履约去向：

```text
QuoteItem(SoftFurniture)
  → DeliveryPlan
  → InstallationTask
  → SupplierPayable / InstallationPayable
```

### 4.4 全屋定制 CustomFurniture

**业务本质：参数化制造和服务，核心是尺寸、结构、板材、五金、拆单和安装。**

标准字段：

- 空间类型、柜体类型、造型、板材、门板、台面、五金、收口。
- 参数化计价：投影面积、展开面积、延米、单元柜、板材面积、固定总价。
- 尺寸、结构、开孔、封边、见光面、灯带和电气预留。
- 设计图、下单图、拆单结果、生产批次、生产周期。
- 工厂、板材供应商、五金供应商、安装班组。
- 测量误差、复尺、补件、返工和损耗规则。

履约去向：

```text
QuoteItem(CustomFurniture)
  → CustomMeasure
  → ManufacturingOrder
  → DeliveryPlan
  → InstallationTask
  → FactoryPayable / InstallerPayable
```

### 4.5 电器设备 Appliance

**业务本质：带型号、序列号、安装条件和售后责任的设备商品。**

标准字段：

- 品牌、型号、能效、容量、功率、尺寸、颜色。
- 电压、插座、给排水、排烟、承重和安装环境要求。
- 标配附件、选配附件、安装材料、辅材。
- 渠道、供应商、采购价、销售价、促销赠品。
- 交期、送货、安装、调试、序列号、保修和售后。
- 退换货、上门服务、延保和安装费用。

履约去向：

```text
QuoteItem(Appliance)
  → DeliveryPlan
  → InstallationTask
  → DeviceAsset（序列号和保修）
  → SupplierPayable / ServicePayable
```

### 4.6 综合其他 General

**业务本质：费用、服务或项目级包干项，不进入库存，也不产生施工任务。**

典型项目：

- 设计费、管理费、监理费、材料搬运费、垃圾清运费。
- 成品保护、开荒保洁、检测费、措施费、税金和服务费。
- 项目级临时增项、优惠包、不可归类费用。

标准字段：

- 费用性质、计价方式、税率、发票类型。
- 是否可折扣、是否可赠送、是否计入项目总价。
- 成本归属：项目、门店、公司或营销费用。
- 发生时点：签约、开工、阶段、完工、售后。
- 审批规则和账务科目。

履约去向：

```text
QuoteItem(General)
  → Expense / ServiceOrder
  → ExpensePayable / RevenueAllocation
```

## 5. 核心实体设计

### 5.1 ItemCategory

企业级树形分类，六类业务共享分类能力，但通过 `itemType` 限定范围。

```text
ItemCategory
├─ itemType             施工/主材/软装/定制/电器/综合
├─ parent               父分类，使用对象关联
├─ code                 标准编码
├─ name                 企业显示名称
├─ standardCode         平台标准编码
├─ standardVersion      标准模板版本
├─ path                 分类路径，便于树查询
├─ level                层级
├─ sort                 排序
├─ icon                 图标
├─ active               是否启用
└─ company              所属企业
```

平台标准分类不作为可跨租户直接修改的业务实体，而作为版本化标准模板初始化到企业；企业可以改名、增删子类，但不能篡改标准编码。这样既符合 SaaS 行业标准化，也保留企业差异。

### 5.2 SellableItem

`SellableItem` 是企业报价项目根实体，承载所有业务类型的共同属性。

```text
SellableItem
├─ itemId
├─ company
├─ itemType             六类业务枚举
├─ itemClass            GOODS/SERVICE/GOODS_SERVICE/FEE/PACKAGE
├─ category             分类对象
├─ code                 企业编码
├─ standardCode         标准项目编码
├─ name                 报价名称
├─ shortName            设计师和客户沟通名称
├─ description          项目说明
├─ unitDefinition       计量单位与精度
├─ pricingMethod        单价/总价/面积/延米/参数/百分比
├─ defaultFormula       默认公式
├─ defaultSalePrice     默认销售价，可为空
├─ defaultCostPrice     默认成本价，可为空
├─ taxCategory          税率和发票分类
├─ applicableSpaces     适用空间
├─ status               Draft/Active/Deprecated
├─ version              商品版本
├─ effectiveFrom        生效时间
├─ effectiveTo          失效时间
├─ maintainer           材料员/负责人
└─ active               是否可选
```

要求：

- 根实体不承载类型特有施工、采购、制造或售后字段。
- 根实体不直接保存项目执行状态。
- 根实体的价格是默认值，正式价格由 `PriceBook` 或报价快照决定。
- 所有企业数据必须带 `company`。

### 5.3 六类业务明细

建议使用一对一明细表，而不是把所有字段继续堆到根表。

| 实体 | 核心职责 |
| --- | --- |
| `ConstructionItemDetail` | 施工工艺、工序、隐蔽工程、验收、人工和辅料规则 |
| `MaterialItemDetail` | 品牌、SKU、规格、损耗、包装、采购和库存规则 |
| `SoftFurnitureItemDetail` | 风格、搭配、尺寸、物流、安装和退换规则 |
| `CustomFurnitureItemDetail` | 板材、五金、参数化尺寸、拆单、生产和复尺规则 |
| `ApplianceItemDetail` | 型号、功率、水电条件、安装、序列号和保修规则 |
| `GeneralItemDetail` | 费用性质、审批、分摊、税率和账务规则 |

每个明细实体必须：

- 一对一关联 `SellableItem`。
- 使用业务对象关联，不保存裸主键。
- 所有约束由数据库和服务端共同保证。
- 作为类型扩展存在，但**不能成为第二套独立报价主数据**。

### 5.4 ItemVariant

用于主材、电器、软装和定制等有型号、颜色、尺寸或配置差异的场景。

```text
ItemVariant
├─ item                 所属 SellableItem
├─ skuCode              SKU 编码
├─ variantName          型号/颜色/规格名称
├─ attributes           标准化属性值
├─ barcode              条码
├─ salePrice            变体销售价
├─ costPrice            变体成本价
├─ supplierItem         默认供应来源
├─ active               是否启用
└─ company              所属企业
```

施工通常没有变体；主材、电器、软装和定制可以有一个或多个变体。设计报价引用 `SellableItem + ItemVariant`，而不是只引用名称字符串。

### 5.5 PriceBook / CostBook

价格必须和商品定义分离，支持企业差异和价格生效历史。

```text
PriceBook
├─ company
├─ name                 标准价/门店价/活动价/客户等级价
├─ channel              零售/整装/渠道/工程
├─ region               区域
├─ customerLevel        客户等级
├─ effectiveFrom
├─ effectiveTo
└─ status

PriceBookEntry
├─ priceBook
├─ item
├─ variant
├─ salePrice
├─ laborPrice
├─ materialPrice
├─ auxiliaryPrice
├─ minimumCharge
├─ taxRate
└─ formula
```

成本使用独立的 `CostBook` / `CostBookEntry`，至少覆盖：

- 材料成本、人工成本、机械成本、辅料成本、运费、安装、税费。
- 供应商、采购地区、账期、起订量和有效期。
- 成本来源单据和价格审核状态。

设计师看到销售价和公式，采购/财务看到成本价和供应商来源，两类数据通过权限分离。

### 5.6 FormulaRule

公式不能只保存一个字符串说明，必须保存可执行规则和显示说明。

```text
FormulaRule
├─ item
├─ expression           quantity * (saleMaterial + saleLabor)
├─ variables            工程量、单价、损耗率、系数、最低计费量
├─ roundingRule         金额精度、工程量精度、进位方式
├─ minimumRule          最低计费面积/长度/金额
├─ lossRule             损耗率或损耗公式
└─ displayFormula       给设计师和客户看的公式
```

公式变量必须来自受控字典，禁止直接执行用户 SQL、JavaScript 或任意 SpEL。

### 5.7 Partner / PartnerItem

统一供应商、工厂、劳务班组、安装队和服务商的父模型。

```text
Partner
├─ company
├─ type                 Supplier/Factory/LaborTeam/Installer/Logistics/Service
├─ name
├─ contact
├─ settlementTerms
├─ taxNo
├─ region
└─ status

PartnerItem
├─ partner
├─ item
├─ variant
├─ purchasePrice
├─ laborPrice
├─ minimumOrder
├─ leadTime
├─ settlementDays
├─ freightRule
├─ effectiveFrom
├─ effectiveTo
└─ priority
```

同一主材可以有多个供应商，同一施工项可以有多个劳务班组。项目执行时再选择实际供应来源，不能在设计阶段写死。

## 6. 报价到项目执行的标准流转

### 6.1 设计阶段

```text
Design
  → DesignItem
      ├─ SellableItem
      ├─ ItemVariant
      ├─ Space
      ├─ quantity
      ├─ pricing snapshot
      └─ design remark
```

`DesignItem` 是可修改的，可以反复选择、调量、换品。它不承担合同和财务事实。

### 6.2 报价阶段

```text
Quote
  → QuoteItem
      ├─ designItem
      ├─ item snapshot
      ├─ variant snapshot
      ├─ price/cost snapshot
      ├─ formula snapshot
      ├─ tax snapshot
      └─ immutable status
```

报价生成后，后续修改目录、价格、供应商或工艺都不能影响历史报价。

### 6.3 增减项阶段

建议新增：

```text
ChangeOrder
├─ project
├─ sourceQuote
├─ reason
├─ status              Draft/Pending/Approved/Rejected
├─ customerApproval
├─ amountDelta
├─ costDelta
└─ items

ChangeOrderItem
├─ changeOrder
├─ sourceQuoteItem
├─ changeType          Add/Remove/Replace/Quantity/Price
├─ oldQuantity
├─ newQuantity
├─ oldPrice
├─ newPrice
├─ amountDelta
├─ costDelta
└─ executionStatus
```

严禁直接修改已确认报价行来表达增项或减项。

### 6.4 项目执行阶段

| SellableItem 类型 | 执行对象 | 成本/应付去向 |
| --- | --- | --- |
| 施工 | `ProjectTask` / `WorkOrder` | 劳务工资、班组结算 |
| 主材 | `MaterialPlan` / `PurchaseOrderLine` | 材料款、供应商应付 |
| 软装家具 | `DeliveryPlan` / `InstallationTask` | 商品采购、物流、安装 |
| 全屋定制 | `ManufacturingOrder` / `InstallationTask` | 工厂款、五金款、安装款 |
| 电器设备 | `DeliveryPlan` / `InstallationTask` / `DeviceAsset` | 设备款、安装款、售后 |
| 综合其他 | `Expense` / `ServiceOrder` | 费用支出、项目成本分摊 |

项目端只能引用报价或变更单的快照，不允许重新读取当前目录价格计算项目成本。

### 6.5 财务阶段

```text
客户确认报价
  → ReceivablePlan
  → 回款单
  → Receipt / Ledger

项目执行
  → PurchaseOrder / WorkOrder / Expense
  → Payable
  → 付款单
  → Payment / Ledger
```

金额链路必须区分：

- 报价金额。
- 合同金额。
- 变更金额。
- 已确认产值。
- 实际成本。
- 应付余额。
- 已付款金额。

不能用同一个 `amount` 字段同时表达这些概念。

## 7. SAAS 行业标准化策略

### 7.1 平台标准和企业配置分层

```text
平台标准模板
  → 标准分类、标准编码、标准字段、默认计量方式
  → 企业初始化时复制
  → 企业调整名称、价格、工艺、供应来源和启用状态
```

企业之间不能共享可变价格和供应商数据；标准数据通过版本化模板升级，不能直接修改其他企业的数据。

### 7.2 企业差异

允许企业自定义：

- 分类名称和子分类。
- 企业项目编码。
- 价格本、成本本、活动价和客户等级价。
- 工艺、验收标准、施工步骤。
- 供应商、劳务班组、交期和账期。
- 计量方式、最低计费量、损耗率和取整规则。
- 是否允许折扣、赠送、拆项和项目级包干。

不允许企业自定义：

- `itemType` 的六类标准枚举。
- 标准编码的核心语义。
- 报价、变更、应付、回款之间的来源链。
- 数据和租户隔离规则。

## 8. 目标代码边界

建议将商业主数据从 `bim` 中拆出，`bim` 只保留三维模型、空间和图纸能力。

```text
com.th4.edge.decoboon.catalog
├─ category        分类
├─ item            SellableItem、ItemVariant
├─ detail          六类业务明细
├─ price           PriceBook、CostBook、FormulaRule
├─ partner         Partner、PartnerItem
└─ standard        模板导入和版本升级

com.th4.edge.decoboon.design
├─ design          方案
├─ item            设计选择行
└─ requirement     客户诉求

com.th4.edge.decoboon.trade.quote
├─ quote
└─ quoteitem

com.th4.edge.decoboon.project
├─ project
├─ task
├─ materialplan
├─ delivery
└─ change

com.th4.edge.decoboon.finance
├─ payable
├─ receivable
├─ payment
└─ ledger
```

你当前导入的 `com.th4.edge.design` 不应成为新的业务根包。装得清业务应统一位于 `com.th4.edge.decoboon` 下，否则会出现：

- 无法复用现有 `Security`、`DataScopeContext`、租户模型。
- `design` 与 `decoboon.design` 双实现。
- 框架扫描路径和事务边界不一致。
- 前端同一概念出现两套 Provider 路由。

## 9. 存量迁移方案

### 9.1 保留兼容，不直接删表

第一轮不删除现有表，使用映射关系迁移：

| 当前模型 | 目标模型 |
| --- | --- |
| `Construction` | `SellableItem` + `ConstructionItemDetail` |
| `Material` | `SellableItem` + `MaterialItemDetail` + `ItemVariant` |
| `CatalogItem` | `SellableItem` 的过渡兼容层 |
| `DesignItem.construction/material` | 过渡来源，迁移后只保留 `SellableItem + ItemVariant` |
| `QuoteItem.construction/material` | 过渡快照来源，迁移后保留来源映射 |
| `ProjectTask.construction` | 过渡执行来源，最终以 `QuoteItem` 为主 |
| `MaterialPlan.material` | 过渡采购来源，最终以 `QuoteItem + ItemVariant` 为主 |

### 9.2 分阶段实施

**阶段一：建立标准根模型**

- 新增 `SellableItem`、`ItemVariant`、`ItemCategory`。
- 新增六类业务明细实体，但暂不切换前端。
- 建立标准项目编码和分类初始化模板。

**阶段二：迁移旧施工和主材**

- `Construction` 迁移为 `ConstructionItemDetail`。
- `Material` 迁移为 `MaterialItemDetail` 和变体。
- 保持旧 ID 与新 ID 的映射表，确保历史设计、报价和项目可追溯。

**阶段三：切换设计报价**

- `DesignItem` 优先引用 `SellableItem + ItemVariant`。
- `QuoteItem` 生成不可变快照，并保留快照后的价格、成本、公式和税率。
- 旧 `construction/material` 字段仅作为迁移来源，不再作为新业务入口。

**阶段四：切换项目执行**

- 施工按 `QuoteItem` 生成任务和工单。
- 主材、软装、电器和定制生成采购、交付、安装或制造单。
- 综合其他生成费用或服务单。

**阶段五：接入供应商和成本本**

- 建立 `Partner`、`PartnerItem`、`PriceBook`、`CostBook`。
- 项目执行选择实际供应商和实际成本。
- 应付、付款和流水以执行单据为来源。

**阶段六：接入增减项和账务**

- 新增 `ChangeOrder`、`ChangeOrderItem`。
- 客户确认后的变更形成新合同基线。
- 应收、应付和台账均通过来源单据追踪。

**阶段七：清理旧模型**

- 在历史查询、项目、财务和报表全部迁移后。
- 停止新代码使用 `Construction`、`Material` 作为主目录。
- 最终删除或归档过渡字段。

## 10. 推荐的数据库约束

### 10.1 SellableItem

```text
(com_id, item_id)
(com_id, item_type, category_id, item_id)
(com_id, item_type, code)
(com_id, standard_code, version)
```

### 10.2 类型明细

```text
(com_id, item_id) 唯一
```

明细表不能存在脱离 `SellableItem` 的孤儿记录。

### 10.3 报价与变更

```text
(com_id, quote_id, item_id)
(com_id, change_order_id, item_id)
(com_id, source_quote_item_id)
```

### 10.4 项目执行

```text
(com_id, project_id, execution_id)
(com_id, quote_item_id, execution_id)
(com_id, supplier_id, payable_id)
```

## 11. 不允许的设计

- 不允许为六类业务继续新增六个互不相通的报价目录。
- 不允许 `DesignItem` 和 `QuoteItem` 各自保存一套独立的商品定义。
- 不允许报价、施工、采购、财务重新读取当前目录价格来反算历史金额。
- 不允许通过大量可空字段把施工、材料、电器、定制混成一张无约束表。
- 不允许用裸 `Long` 外键关联商品、供应商、项目或财务单据。
- 不允许用自由文本表达 `itemType`、`pricingMethod`、`taxType` 或变更类型。
- 不允许用 `@JsonIgnore` 解决递归序列化，应使用 `@Properties` 白名单。
- 不允许绕过 `Company`、`DataScope` 和 Provider 做跨租户主数据查询。

## 12. 最终推荐

装得清应采用以下标准模型：

```text
一个企业可售项目根：SellableItem
六类业务明细：Construction / Material / Soft / Custom / Appliance / General
一个项目变体层：ItemVariant
两个价格体系：PriceBook / CostBook
一个供应关系层：Partner / PartnerItem
一条设计到报价链路：DesignItem → QuoteItem
一条变更链路：ChangeOrder → ChangeOrderItem
一条履约链路：ProjectTask / MaterialPlan / DeliveryPlan / InstallationTask
一条财务链路：Payable / Receivable / Ledger
```

这样既能统一设计师选择、报价、项目、供应商和账务的语言，又能允许施工、主材、软装、定制、电器和综合项目各自保留合法字段和业务规则。

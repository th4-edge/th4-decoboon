# 装得清客户、报价、项目状态驱动逻辑

> 适用范围：`com.th4.edge.decoboon` 设计、报价、项目闭环  
> 对应账号：18660219919（设计师小林）  
> 核心原则：业务状态只能由领域上下文推进；实体只保存数据；Provider 负责权限、入参和响应裁剪。

## 1. 总链路

```text
客户登记
  -> 跟进 / 邀约量房
  -> 约定量房
  -> 指派设计师
  -> 记录客户诉求
  -> 设计方案 + 区域尺寸 + 设计分项
  -> 设计报价（不可变快照）
  -> 可谈单主推方案 + 有有效报价
  -> 谈单 PPT
  -> 客户接受报价
  -> 生成施工项目
  -> 阶段 / 施工任务 / 材料计划
  -> 阶段报验
  -> 客户确认验收
  -> 项目完工
```

数据边界如下：

| 对象 | 业务定位 | 是否可被后续业务直接修改 |
| --- | --- | --- |
| `CatalogItem` | 企业统一施工、主材、软装、定制、电器、综合项目库 | 由企业负责人/材料员维护，设计师只能选择 |
| `DesignItem` | 某套房、某个方案、某个区域的选品与工程量 | 可修改，代表当前设计 |
| `PackageLine` | 套餐模板中的标准行 | 只由套餐维护流程修改 |
| `QuoteLine` | 报价生成时的商业快照 | 生成后不改价、不改公式，只用于报价和后续转项目 |
| `ProjectTask` | 项目施工执行事实 | 由项目经理在施工过程中推进 |
| `MaterialPlan` | 项目材料需求与到场事实 | 由项目经理/材料角色推进 |
| `Acceptance` | 阶段验收事实 | 客户确认或驳回后不再重复处理 |

## 2. 客户状态业务流程

客户状态枚举：`New / Following / PendingMeasure / Quoted / Signed / Serving / Finished / Lost`。

```text
New
 ├─ 新增跟进 -> Following
 ├─ 约定量房 -> PendingMeasure
 │                 ├─ 指派设计师（状态不变）
 │                 └─ 生成报价 -> Quoted
 └─ 流失 -> Lost

Quoted
 └─ 客户接受报价 -> Signed

Signed
 └─ 接受报价转项目 -> Serving

Serving
 └─ 项目完成（当前预留，尚未自动落 Finished）
```

### 2.1 当前代码真实行为

| 动作 | Provider / Context | 状态变化 | 关键约束 |
| --- | --- | --- | --- |
| 新建客户 | `customer/customer/save` | 强制 `New` | 负责人、门店、团队、企业从当前登录员工解析 |
| 新增跟进 | `customer/customer-follow/save` | 仅 `New -> Following` | 已进入其他状态的客户不会被跟进动作回退 |
| 约定量房 | `customer/customer/measure` | -> `PendingMeasure` | 必须有地址；`Lost/Signed/Serving/Finished` 不可重新约定 |
| 指派设计师 | `customer/customer/handoff` | 状态不变 | 必须先约定量房；只能指派本企业且符合门店/团队范围的设计师 |
| 生成设计报价 | `QuoteContext.create(...)` | -> `Quoted` | 设计必须有至少一个 `DesignItem`；套餐面积必须有效 |
| 客户接受报价 | `quote/update = Accepted` | -> `Signed` | 仅 `Submitted -> Accepted` |
| 报价转项目 | `ProjectContext.createFromQuote(...)` | -> `Serving` | 仅 `Accepted` 报价；同一报价只能生成一个项目 |

### 2.2 状态职责边界

- `Customer.status` 是经营漏斗状态，不等同于设计、报价或项目状态。
- 客户状态变化必须通过 Provider/Context，不能在编辑客户基础资料时由前端直接提交。
- `Customer.store/team/owner` 是权限归属快照，转交客户时一起刷新。
- 当前 `Finished` 和 `Lost` 已建模，但没有完整的自动状态入口：
  - 项目全部完工后尚未自动把客户改为 `Finished`；
  - 客户流失需要后续增加明确的管理动作和原因记录；
  - 建议下一阶段在 `ProjectContext.refreshProject()` 判断项目 `Finished` 后同步客户为 `Finished`，并增加 `customer/customer/lose` 能力。

## 3. 设计方案与报价驱动逻辑

### 3.1 设计方案状态

设计方案枚举：`Draft / Ready / Presented / Selected / Archived`。

```text
Draft（创建方案）
  -> Ready（区域、尺寸、设计分项配置完整后具备谈单条件）
  -> Presented（已向客户讲解）
  -> Selected（客户选中）
  -> Archived（归档）
```

`design/scheme/build` 在进入 `Ready / Presented / Selected` 前强制校验：

1. 至少有一个 `Space`；
2. 至少有一个 `DesignItem`；
3. 方案面积由区域面积重新汇总。

### 3.2 分项选择规则

设计师新增分项只能从企业统一 `CatalogItem` 选择：

```text
新增分项
 -> 选择企业报价项目库
 -> 按类型/分类/品牌/规格分步筛选
 -> 多选 CatalogItem
 -> 为每个项目填写工程量
 -> 后端复制价格、规格、公式、工艺和成本
 -> 生成 DesignItem
```

禁止设计师直接修改目录价格。`DesignItem` 的价格、材料/人工单价、成本、计价公式和工艺均从 `CatalogItem` 快照而来。

### 3.3 报价快照公式

自定义报价：

```text
DesignItem.amount = 后端按 CatalogItem.pricingMode 计算
Quote.subtotal    = Σ DesignItem.amount
Quote.discounted  = Quote.subtotal × discount
Quote.taxAmount   = Quote.discounted × 5%
Quote.amount      = Quote.discounted + Quote.taxAmount
Quote.cost        = Σ DesignItem.cost
```

套餐报价：

```text
ratio          = 实际计价面积 ÷ 套餐标准面积
模板牌价金额   = 套餐模板牌价 × ratio
Quote.subtotal = 模板牌价金额
Quote.discounted = Quote.subtotal × discount
Quote.taxAmount  = Quote.discounted × 5%
Quote.amount     = Quote.discounted + Quote.taxAmount
```

`QuoteLine` 是报价生成时的冻结快照：

- 保存来源 `DesignItem / PackageLine / CatalogItem` 引用；
- 保存当时的材料价、人工价、成本、工程量、公式和报价角色；
- 后续修改目录或设计，不得回写历史报价；
- 项目经理看到的是 `QuoteLine` 和执行事实，不依赖可变的 `DesignItem`。

### 3.5 单房屋唯一成交不变量

量房后的一个客户记录代表一个唯一房屋。因此系统强制执行：

```text
一个客户/房屋 -> 最多 1 份客户确认报价（Accepted / Converted）
一个客户/房屋 -> 最多 1 个施工项目
一个施工项目   -> 最多 1 份合同基线
合同金额调整   -> 必须通过合同变更单
```

数据库唯一索引：

```sql
UNIQUE (com_id, customer_id)
```

应用层在客户确认报价和项目立项时对客户行加悲观锁，避免并发产生多个确认报价或项目。报价确认后，设计、区域、分项、诉求和新增报价全部锁定。

### 3.4 报价状态机

```text
Draft
  └─ submit -> Submitted
                 ├─ accept -> Accepted
                 │                └─ createProject / convert -> Converted
                 └─ reject -> Rejected

Rejected 可重新生成新版本报价，但不直接复活已驳回快照
Superseded 已被其他报价替代，只保留历史记录，不再进入待办
Converted 不可再驳回
```

当前实现细节：

- `quote/save` 生成 `Draft`，并把客户状态推进为 `Quoted`；
- `quote/update` 接收 `Draft / Submitted / Accepted / Rejected / Converted`；
- `Draft` 分支当前是幂等返回，不重开报价；
- `submit()` 只允许 `Draft`；
- `accept()` 只允许 `Submitted`；
- `reject()` 当前允许除 `Converted`、`Superseded` 外的报价驳回；
- 客户确认一份报价时，同房屋其他 `Draft / Submitted / Accepted` 报价自动转为 `Superseded`；
- `Superseded` 不进入待推进、待确认、有效报价金额和转化率统计；
- `convert()` 只允许 `Accepted`；
- 项目生成成功后，报价变为 `Converted`，客户变为 `Serving`。
- `reject()` 只允许 `Submitted -> Rejected`；
- 自定义报价版本按同一设计方案已有报价数递增；套餐报价版本按同一客户 + 同一套餐模板已有报价数递增；
- 驳回报价不可原地修改，只能通过 `quote/save + sourceQuoteId` 生成新的 Draft 版本，原报价保留为 Rejected 历史；
- 套餐报价生成 Draft 后，可在提交前执行扣减、升级、替换和增项，服务端重新计算汇总金额与成本；提交后快照不可再调整。

### 3.5 设计方案使用套餐（Hybrid）

当设计方案选择套餐时，`Quote` 同时关联 `Design` 和 `PackageTemplate`，模式为 `Hybrid`。

匹配优先级：

```text
CatalogItem 完全一致
→ 套餐分区 SpaceType 与设计空间类型一致
→ 项目类型/分类/名称一致
→ 无法确认时保留为待确认差异
```

产生的差异类型：

| 差异 | 含义 | 默认处理 |
| --- | --- | --- |
| `Matched` | 套餐行与设计分项匹配 | 自动确认 |
| `PackageOnly` | 套餐有、设计未匹配 | 待确认 |
| `DesignOnly` | 设计有、套餐没有 | 待确认 |
| `QuantityChanged` | 匹配项目数量不同 | 待确认 |
| `Deduct` | 套餐项目被扣减 | 已确认 |
| `Upgrade` | 套餐项目升级 | 已确认 |
| `Replace` | 套餐项目替换 | 已确认 |

报价行同时保存 `designItem` 和 `packageLine` 来源。只要存在 `Pending` 差异，`submit()` 就拒绝提交，必须先确认、忽略、扣减、升级或替换。

报价头保存 `costComplete`。当报价存在销售金额但所有有效报价行成本合计为 0 时，`costComplete=false`；前端显示“成本未完整”，不得据此计算有效利润或毛利率。

## 4. 谈单 PPT 的业务门槛

谈单 PPT 不是报价详情页的替代品，它承担“展现设计用心、专业和可信度”的沟通价值。

生成条件：

1. 主推设计方案的 `status` 必须是 `Ready / Presented / Selected`；
2. 主推方案必须存在非驳回状态的报价；
3. 生成内容关联客户诉求、量房信息、户型问题、施工优化、区域设计、材料、电器、投资和节省点。

因此完整链路是：

```text
客户诉求 -> 方案设计 -> 区域分项 -> 设计报价 -> 谈单 PPT -> 客户确认
```

报价金额和 PPT 内容均从后端领域数据生成，前端只负责展示和补充展示字段，不允许手填报价金额覆盖计算结果。

## 5. 项目业务流程

### 5.1 从已接受报价生成项目

`ProjectContext.createFromQuote()` 的规则：

- 报价必须是 `Accepted`；
- 一个报价只能生成一个项目；
- 项目承接报价的客户、设计、企业、门店、团队、负责人和金额；
- 施工单位报价行生成施工阶段和施工任务；
- 材料报价行生成材料计划；
- 项目初始状态为 `Preparing`，进度为 0；
- 报价转为 `Converted`，客户转为 `Serving`。

生成映射：

```text
QuoteLine(type=Construction)
  -> ProjectStage(category)
  -> ProjectTask(one line = one task)

QuoteLine(type=Material)
  -> MaterialPlan

Project
  -> 汇总合同额、成本、加权进度和状态
```

### 5.2 阶段与任务状态

阶段状态：`Todo -> Doing -> Accepting -> Done`。  
任务状态：`Todo -> Doing -> Accepting -> Done`，另有 `Cancelled`。

任务推进规则：

| 目标状态 | 进度 | 日期/校验 |
| --- | ---: | --- |
| `Doing` | ≥10% | 首次开工写 `actualStart` |
| `Accepting` | 90% | 隐蔽任务必须先完成节点留证 |
| `Done` | 100% | 写 `actualEnd` |
| `Todo` | 0% | 用于重新打开未完成任务 |

每次任务或材料变化后调用 `ProjectContext.refreshProject()`：

- 阶段进度 = 阶段内任务进度平均值；
- 项目进度 = 各阶段进度 × 阶段权重；
- 阶段有任务全部完成 -> `Done`；
- 阶段存在待验收 -> `Accepting`；
- 阶段有进度但未完成 -> `Doing`；
- 所有阶段完成 -> 项目 `Finished`；
- 有施工进度 -> 项目 `Ongoing`；
- 尚无进度 -> 项目 `Preparing`。

### 5.3 材料计划状态

```text
Planned -> Requested -> Ordered -> Arrived -> Closed
```

`Arrived / Closed` 时记录到场日期。材料计划变化会刷新项目成本，但不会自行改变施工任务状态。

### 5.4 阶段验收

提交验收：`project/acceptance/save`

- 阶段内所有任务必须为 `Done`；
- 同一阶段不能已有 `Pending` 验收单；
- 新验收单为 `Pending`；
- 阶段变为 `Accepting`；
- 项目变为 `Accepting`。

确认验收：`project/acceptance/update`

- 确认通过：验收单 `Confirmed`，阶段 `Done`，刷新项目；
- 驳回整改：验收单 `Rejected`，阶段回到 `Doing`；
- 已处理的验收单不能重复确认。

### 5.5 项目状态边界

项目枚举为 `Preparing / Ongoing / Suspended / Accepting / Finished / Settled`。

当前自动推进覆盖：

- `Preparing`：项目刚生成；
- `Ongoing`：有施工任务开始；
- `Accepting`：提交阶段验收；
- `Finished`：所有阶段完成。

`Suspended` 和 `Settled` 当前没有完整自动链路，需要后续补充：

- 停工：增加停工原因、责任方、预计恢复时间和审批记录；
- 结算：增加结算金额、增减项、应收应付结清校验；
- 客户 `Finished`：项目完工后自动同步；
- 项目关闭：结算完成后冻结施工任务和材料计划。

## 7. 响应与主键约束

所有业务 Provider 必须使用 `@Properties` 白名单：

- 列表只返回页面所需摘要；
- 详情返回当前详情页字段；
- 保存和更新只返回客户端下一步真正需要的数据；
- 关联对象必须逐个声明白名单，避免 `Company -> Store -> Company`、`Quote -> Design -> Quote` 等递归序列化；
- 具体 Provider 不得依赖全量 Entity 默认序列化。

所有 JPA 业务主键统一使用：

```java
@Id
@SnowflakeId
private Long xxxId;
```

并通过 `SnowflakeEntityListener` 在持久化前生成 Long 主键。数据库不允许自增主键。Redis 对象使用 Spring Data Redis 自身的字符串键，不属于 JPA 主键。

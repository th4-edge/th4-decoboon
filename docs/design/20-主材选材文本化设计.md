# 20 · 签约后主材选材文本化设计

> 业务依据：`SCN-006 签约后主材选材确认`、`BR-004 签约后主材选材文本化规则`、`DEC-003 签约后主材选材文本化`（业务智能体 `verified`）。
> 未冻结项：`GAP-005 主材选材单归属与版本待冻结`。本设计采用其临时建议口径，不把未冻结项升级为强制规则。

## 1. 业务问题

报价单通常只约定材料的类别、品牌与规格范围。签约后客户还需要和设计师现场确认颜色、规格、大小等具体主材选择。
若只用口头或零散聊天记录，选材版本混乱，后续材料采购与现场交付容易扯皮。

## 2. 真实场景（实现前强制推演）

### 场景 A：签约后设计师与客户现场确认（默认主路径）

| 项 | 内容 |
| --- | --- |
| 使用人 | 设计师（维护）、客户（现场确认） |
| 触发事件 | 客户已签约，进入主材选材确认 |
| 前置 | 房屋明确（多房屋必须选定 `propertyId`）、合同已建立；项目可能尚未创建 |
| 当前动作 | 设计师逐项与客户确认颜色、规格、大小，在 App 记录一段选材文本并提交 |
| 系统下一步 | 保存文本为 `PendingConfirm` 版本，记录维护设计师；设计师代录客户确认后转为 `Confirmed`，记录确认人与确认时间 |
| 异常处理 | 无合同/项目上下文时允许先存草稿并提示“待补上下文”，确认环节拒绝；已确认版本再修改时自动生成新版本 |

### 场景 B：项目经理/材料角色按项目查看并执行

| 项 | 内容 |
| --- | --- |
| 使用人 | 项目经理、财务、企业负责人/店长 |
| 触发事件 | 选材已确认或材料准备阶段需要核对 |
| 当前动作 | 按项目或房屋查看最新已确认版本与历史版本 |
| 系统下一步 | 仅返回其在数据范围或项目参与关系内的选材文本；不自动生成采购单、材料数量或成本 |
| 异常处理 | 跨企业、非参与人、跨房屋访问统一 404 |

## 3. 领域模型

新增领域包 `com.th4.edge.decoboon.material`，实体 `MaterialSelection`（表 `db_material_selection`）。

| 字段 | 语义 | 说明 |
| --- | --- | --- |
| `selectionId` | 主键 | `@SnowflakeId` |
| `company/store/team/owner` | 经营归属 | 保存时由登录员工所属企业 + 房屋归属快照复制 |
| `customer/property` | 客户与房屋 | `property` 为选材唯一归属，多房屋客户必须显式指定 |
| `contract/project` | 合同与项目 | 合同为签约后主归属；项目创建后建立引用，保存时自动带出项目的履约合同 |
| `version` | 版本号 | 同一「企业 + 房屋 + 合同」下从 1 递增 |
| `status` | `Draft / PendingConfirm / Confirmed` | 已确认版本不再原地覆盖 |
| `title/content` | 选材文本 | `content` 为 `longtext`，不拆逐材料结构化字段 |
| `attachments` | 图片/附件引用 | `@ElementCollection` |
| `designer` | 维护设计师 | 取房屋已指派设计师，未指派时记为当前维护人 |
| `confirmerName/confirmedBy/confirmedAt` | 客户确认 | 记录确认人姓名、操作员工与确认时间 |

## 4. 状态与版本规则

```text
保存草稿 -> Draft
提交 -> PendingConfirm
记录客户确认 -> Confirmed（写入确认人、确认时间）
已确认后修改 -> 生成 version+1 的新 Draft，旧版本保持 Confirmed
```

- 未确认的当前版本允许原地保存，避免每次编辑堆积版本。
- 已确认版本不可无痕覆盖，历史版本永久保留。
- 保存与确认都不写回报价、合同金额、成本、材料计划、采购或库存。

## 5. 权限

| 动作 | 规则 |
| --- | --- |
| 查看 | 房屋数据范围（BOSS=Company / 店长=Store / 团队负责人=Team / 本人=Self，含房屋负责人、业务员、设计师）或项目参与关系（设计师 / 项目经理 / 财务） |
| 维护、确认 | 房屋已指派设计师、房屋数据负责人、BOSS、店长、团队负责人、项目经理、财务 |
| 拒绝 | 业务员不允许修改选材事实；跨企业/跨范围统一 404；无维护资格但可查看时返回 403 |
| 多房屋 | 必须显式 `propertyId`，A 房屋选材不串到 B 房屋 |

服务端强制：Provider 继承 `Security`，企业归属与负责人由登录员工覆盖，前端隐藏按钮不构成权限。

## 6. Provider

| 路由 | 能力 | 说明 |
| --- | --- | --- |
| `material/selection/page` | 列表 | 按房屋（可选项目）返回全部历史版本，最新在最前 |
| `material/selection/info` | 详情 | 单条选材记录 |
| `material/selection/save` | 保存 | 保存草稿或提交待确认；未确认版本原地保存，已确认版本形成新版本 |
| `material/selection/confirm` | 客户确认 | 记录确认人姓名与时间；重复确认幂等；无合同/项目上下文拒绝 |

响应统一使用 `@Properties` 白名单裁剪 `customer/property/contract/project/designer/owner` 关联；读取使用 `@EntityGraph` 预取，保证关闭 OSIV 也能加载。

## 7. 迁移

`docs/design/migrations/46-主材选材记录.sql`：`db_material_selection` + `db_material_selection_attachments`，`content` 为 `longtext`。

## 8. 边界（明确不做）

- 不拆分每种材料的颜色/规格/大小结构化字段。
- 不生成材料计划、采购单、任务或成本数据。
- 不改动报价、合同、应收应付、成本与利润。
- 采购前是否必须存在已确认选材（`GAP-005` 第 4 条）未冻结，本设计不实现强制门禁。
- 客户线上自助确认 vs 线下代录（`GAP-005` 第 3 条）未冻结，本设计通过「客户确认人姓名 + 操作员工」同时兼容两种方式，不新增客户侧账号体系。

## 9. 验收关注点

- 正向：签约后设计师创建文本并确认，项目/材料角色可按项目查看。
- 多房屋：A 房屋选材不出现在 B 房屋。
- 权限：无关员工、其他企业用户不能查看或修改。
- 变更：修改后保留历史版本，不覆盖原确认文本。
- 金额：保存选材文本后报价、合同、成本、材料计划和采购数据不变。
- 例外：没有结构化颜色/规格/大小字段也能完成保存和查看。

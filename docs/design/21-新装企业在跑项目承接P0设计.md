# 新装企业在跑项目承接 P0 研发设计

> 文档编号：DESIGN-CARRYOVER-20260926-001  
> 状态：`ready_for_development_review`  
> 日期：2026-09-26  
> 业务依据：`DEC-011`、`SCN-011`、`BR-010`、`SOL-005`、`REQ-BIZ-20260926-002`  
> 产品依据：`docs/product/2026-09-26-新装企业在跑项目承接P0业务方案.md`  
> 实施边界：只做在跑项目引导式承接；不实现在跑项目批量导入、历史已结清流水重建和已完工历史迁移

## 0. 设计结论

新增 `carryover` 领域，承载“注册后建立承接任务、逐项目录入、校验、确认、生成业务基线、首笔业务锁定”的完整流程。

与现有产品的关系：

- 报价、合同、项目、应收、应付复用现有业务对象。
- 所有接管生成的业务对象标记 `BusinessOrigin.Carryover`。
- 现有新业务对象默认 `BusinessOrigin.New`，行为不变。
- 接管项目进入工地、项目和财务当前工作范围。
- 接管基线不进入获客、报价接受率和本月新签统计。
- 历史已结清流水不重新生成。
- 接管前成本作为独立快照进入项目成本汇总。

## 1. 已冻结的五个实现选择

| 开放项 | P0 设计结论 |
| --- | --- |
| 承接任务承载 | 新增 `carryover` 领域；后台首页引导复用 `OnboardingGuideContext`，承接状态真源在 `CarryoverBatch` / `CarryoverProject` |
| 期初余额承载 | 复用现有 `Receivable` / `Payable`，每个项目最多各一条汇总期初记录；金额等于接管日未结余额 |
| 接管前成本 | 新增 `CarryoverCostSnapshot`；与接管后实际成本合并计算，完整性任一段不成立时利润为空 |
| 来源标记 | 新增 `BusinessOrigin` 枚举，加到 `Quote`、`ProjectContract`、`Project`、`Receivable`、`Payable`，存量默认 `New` |
| 首笔业务锁定 | 在首个真实业务 Provider 的同一事务内锁定 `CarryoverProject`，记录业务类型；锁定后只走调整、更正或冲正 |

## 2. 领域模型

### 2.1 CarryoverBatch

用途：企业级承接任务，保证接管日期、范围和整体进度可追溯。

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `batchId` | Long | 主键 |
| `company` | Company | 所属企业 |
| `createdBy` | Employee | 发起人，P0 为 BOSS |
| `asOfDate` | LocalDate | 接管日 |
| `status` | CarryoverBatchStatus | Active / Completed / Cancelled |
| `scopeConfirmedAt` | LocalDateTime | 承接范围确认时间 |
| `completedAt` | LocalDateTime | 全部项目处理完成时间 |
| `version` | Integer | 整批版本，用于确认失效 |

规则：

- P0 同一企业只允许一个 Active 批次。
- 已完成批次不可重新打开。
- 新批次必须建立在旧批次已完成或取消之后。

### 2.2 CarryoverProject

用途：单项目承接草稿、确认、应用结果和锁定状态。

| 字段组 | 关键字段 |
| --- | --- |
| 归属 | company、batch、store、team、owner |
| 客户房屋 | customerName、customerPhone、community、address、area |
| 人员 | manager、designer |
| 报价合同 | contractNo、signedAmount、currentAmount、signedAt、startDate、planEndDate |
| 当前工地 | projectStatus、currentStageName、progress、remainingWork、currentIssue |
| 期初应收 | receivableOutstanding、receivableDueDate、receivableSourceNo、receivableConfirmed |
| 期初应付 | payableOutstanding、payableDueDate、payablePayeeName、payableSourceNo、payableConfirmed |
| 结果对象 | quote、contract、project、costSnapshot |
| 状态 | status、version、appliedAt、cancelledAt、cancelReason |
| 锁定 | lockedAt、firstBusinessAt、firstBusinessType、lockedBy |
| 来源 | legacyId、legacyProjectNo |

状态：

```text
Draft
-> Ready
-> Confirmed
-> Applied
-> Locked
```

异常分支：

```text
Draft / Ready / Confirmed -> Cancelled
Applied -> Locked
Locked -> 不允许撤回，只允许调整或冲正
```

说明：

- `Ready` 只表示系统校验通过，不表示业务确认完成。
- `Confirmed` 必须存在所需确认记录。
- `Applied` 表示真实业务对象已经生成。
- `Locked` 由首笔真实业务触发，不能由前端直接提交。
- 校验错误不写入独立状态，由 `CarryoverReportContext` 实时推导。

### 2.3 CarryoverConfirmation

用途：记录分角色确认和 BOSS 代确认。

| 字段 | 说明 |
| --- | --- |
| `item` | 所属承接项目 |
| `requiredRole` | Boss / Finance / Pm / Designer |
| `confirmedBy` | 实际确认员工 |
| `proxy` | 是否代确认 |
| `confirmedVersion` | 对应项目草稿版本 |
| `confirmedAt` | 确认时间 |
| `summary` | 确认内容摘要 |

规则：

- 每个必确认角色每个版本最多一条有效记录。
- 草稿修改后 `version` 增加，旧确认自动失效。
- BOSS 代确认时 `proxy=true`，`requiredRole` 保留原角色。
- BOSS 代确认不能绕过负责人缺失、金额冲突和跨企业校验。

### 2.4 CarryoverCostSnapshot

用途：保存接管前成本总额和完整性。

| 字段 | 说明 |
| --- | --- |
| `item` | 所属承接项目 |
| `project` | 应用后项目 |
| `totalCost` | 接管前已发生成本总额，允许为空 |
| `complete` | 完整性是否已确认 |
| `asOfDate` | 成本截止日期 |
| `missingNote` | 缺失或待补充说明 |
| `createdBy` | 记录人 |

规则：

- `totalCost=null` 表示总额未知。
- `complete=false` 表示利润和毛利率必须为空。
- `complete=true` 时才允许接管前成本进入利润计算。
- 不得把空值自动转换为 0。

### 2.5 CarryoverAdjustment

用途：项目锁定后的期初余额和成本调整留痕。

| 字段 | 说明 |
| --- | --- |
| `item` | 所属承接项目 |
| `type` | Receivable / Payable / Cost / Other |
| `beforeAmount` | 调整前金额 |
| `deltaAmount` | 调整差额 |
| `afterAmount` | 调整后金额 |
| `reason` | 调整原因 |
| `createdBy` | 操作人 |
| `createTime` | 调整时间 |

规则：

- 锁定前通过撤回重建修复，不写调整记录。
- 锁定后禁止直接覆盖原值。
- 期初应收应付调整同时更新现有一个汇总余额记录。
- 成本调整更新 `CarryoverCostSnapshot`，原值通过调整表追溯。

### 2.6 CarryoverAttachment

用途：保存合同、报价、现场和财务依据附件。

| 字段 | 说明 |
| --- | --- |
| `item` | 所属承接项目 |
| `category` | Contract / Quote / Site / Finance / Other |
| `fileUrl` | 私有文件地址 |
| `originalName` | 原文件名 |
| `uploadedBy` | 上传人 |

附件只用于追溯，不参与历史流水重建。

## 3. 与现有对象的映射

### 3.1 报价

- 创建接管基线 `Quote`。
- 状态为 `Converted`。
- `originalAmount=currentAmount`，不要求重建报价行。
- `businessOrigin=Carryover`。
- 不进入设计师报价工作台和报价接受率。

### 3.2 合同

- 创建 `ProjectContract`。
- 状态为 `Effective`。
- `signedAt` 使用用户提供的历史签约日期。
- `effectiveAt` 不早于接管日，避免接管后统计把历史合同当成新签。
- `businessOrigin=Carryover`。
- 不进入本月新签金额。

### 3.3 项目

- 创建真实 `Project`，绑定接管报价、合同、客户和房屋。
- `status` 映射到现有 `ProjectStatus`。
- `progress` 使用接管日确认进度。
- 仅创建一条“接管当前阶段基线”：
  - 阶段名称使用企业真实当前阶段；
  - 状态根据当前项目状态映射为 `Doing` / `Accepting` / `Done`；
  - 不重建已完成阶段、历史任务和历史验收。
- `businessOrigin=Carryover`。
- 进入项目列表、工地工作台和当前经营工作量。

### 3.4 期初应收

复用 `Receivable`：

- 每个项目最多一条汇总记录；
- `name=期初未收工程款`；
- `amount=接管日未收余额`；
- `receivedAmount=0`；
- `dueDate=用户确认到期日`；
- `businessOrigin=Carryover`。

历史已收款不创建 `Receipt`，也不进入当月收入。

### 3.5 期初应付

复用 `Payable`：

- 每个项目最多一条汇总记录；
- `name=期初未付供应商款` 或用户填写摘要；
- `amount=接管日未付余额`；
- `paidAmount=0`；
- `dueDate=用户确认到期日`；
- `businessOrigin=Carryover`。

历史已付款不创建 `Payment`。

重要：期初应付只影响当前未付余额，不进入接管后的实际成本；接管前成本由 `CarryoverCostSnapshot` 单独承载，避免重复计算。

## 4. 来源字段和查询规则

新增枚举：

```text
BusinessOrigin
- New      正常业务
- Carryover 接管基线
```

加到以下实体：

- `Quote`
- `ProjectContract`
- `Project`
- `Receivable`
- `Payable`

数据库规则：

- 字段非空，默认 `New`。
- 存量数据回填 `New`。
- 按 `(com_id, business_origin, 主键)` 建索引。

查询口径：

| 场景 | 接管数据 |
| --- | --- |
| 报价接受率/转化率 | 排除 |
| 本月新签合同 | 排除 |
| 获客和渠道分析 | 排除 |
| 在建项目数/当前工地 | 纳入 |
| 当前应收应付/账龄 | 纳入 |
| 接管后实际收款/付款 | 正常纳入 |
| 项目毛利 | 按成本完整性决定 |
| 历史已完成档案 | P0 不涉及 |

禁止在各个报表自行使用不同字符串判断，统一由 `BusinessOriginFilter` 提供谓词。

## 5. 成本汇总设计

项目总成本公式：

```text
项目总成本
= 接管前成本总额
+ 接管后实际成本

成本完整性
= 接管前成本完整性
AND 接管后成本完整性
```

规则：

- 接管前成本来自 `CarryoverCostSnapshot`。
- 接管前成本总额未知或完整性未确认时，利润和毛利率为空。
- 期初应付不算作接管后实际成本。
- 接管后成本继续使用现有采购、到货和成本口径。
- `ProjectCostContext` 检测到 Carryover 项目时，必须复用同一 `CarryoverCostContext` 读取快照，禁止各页面自行相加。
- 财务汇总、项目财务、结算和项目总览必须同源。

- `CarryoverReportContext` 统一输出项目完成状态、缺失项和批次进度。

## 7. 权限设计

- BOSS：创建批次、维护所有项目、代确认、最终提交、锁定后调整。
- 财务：查看本企业承接项目，确认期初余额和成本。
- 项目经理：查看分配给自己的承接项目，确认当前工地。
- 设计师：按需查看和确认报价合同。
- 普通员工无权限访问承接草稿。

数据范围：

- `CarryoverProject` 带 company/store/team/owner。
- 未明确 owner 的项目仅 BOSS 和财务可见；财务确认后仍不能代替 owner 补全。
- 所有 Provider 从登录员工加载企业范围，不接受前端 companyId。

## 8. 首笔业务锁定

锁定时机：项目成功提交承接后，发生第一笔真实业务事实时，在业务事务内锁定。

锁定事件：

1. 新增收款；
2. 新增付款；
3. 应收或应付调整；
4. 施工任务状态变化；
5. 阶段状态变化；
6. 提交或确认验收；
7. 合同变更；
8. 采购单创建或更新；
9. 到货确认；
10. 现场日报或节点留证。

实现要求：

- 统一通过 `CarryoverLockContext.lock(project, businessType, operator)`。
- 锁定行使用 `SELECT ... FOR UPDATE`，防止并发首次业务。
- 锁定与业务写入在同一事务；业务失败时锁定回滚。
- 重复事件幂等，不重复覆盖首次业务时间和类型。
- 锁定后 `CarryoverProject` 禁止撤回、删除和直接覆盖期初金额。
- 期初应收应付和成本调整改为写 `CarryoverAdjustment`。

## 9. 数据库迁移

新增迁移：`61-新装企业在跑项目承接P0.sql`。

步骤：

1. 新表：`carryover_batch`、`carryover_project`、`carryover_confirmation`、`carryover_cost_snapshot`、`carryover_adjustment`、`carryover_attachment`。
2. 为 `quote`、`db_project_contract`、`db_project`、`db_finance_receivable`、`db_finance_payable` 增加 `business_origin`。
3. 存量数据统一回填 `New`。
4. 建立企业 + 来源 + 主键索引。
5. 不修改现有状态枚举和唯一约束。
6. 不迁移历史财务流水和已完工项目。

回滚：

- 删除来源索引和列。
- 删除 carryover 相关表。
- 已生成业务数据不允许由回滚脚本自动删除，必须单独制定业务清理方案。

## 10. 测试矩阵

### 单元/集成

- 批次和项目状态流转；
- 系统校验和异常推导；
- 分角色确认和 BOSS 代确认；
- 草稿修改后旧确认失效；
- 正式承接对象一次性生成；
- 重复提交幂等；
- 期初应收应付只生成一次；
- 成本完整性不同组合下利润结果；
- 来源过滤不影响正常新客户业务；
- 跨企业、跨门店、越权访问失败。

### 锁定事件

每个锁定事件必须有一个测试，证明：

- 首次事件后 `firstBusinessAt` 和 `firstBusinessType` 正确；
- 重复事件不覆盖首次事实；
- 业务事务失败时锁定不生效；
- 锁定后撤回、删除和直接覆盖金额失败；
- 调整和冲正成功且保留记录。

### 页面/接口回归

- 新客户普通入驻流程不变；
- 接管项目进入工地和财务工作台；
- 接管项目不进入报价接受率和本月新签；
- 已有业主项目、员工项目、财务汇总和结算查询不回归。

## 13. 已冻结技术方案

1. **编号生成**：接管报价、合同、项目编号复用现有编号上下文；不得直接使用时间戳创建编号，不得新增第二套编号规则。
2. **阶段基线**：每个接管项目创建一条当前阶段记录，名称使用用户确认的真实阶段；项目状态映射到现有 `ProjectStatus`。不创建历史已完成阶段、任务和验收；后续施工仍沿现有阶段任务闭环。
3. **调整入口**：锁定前只通过 `carryover/project/update` 修改草稿并重新确认；锁定后只通过 `carryover/adjustment/save` 调整。现有 `finance/receivable/update` 和 `finance/payable/update` 遇到 `business_origin=Carryover` 时，锁定时必须拒绝直接覆盖并提示走调整入口。
4. **锁定实现**：使用显式 `CarryoverLockContext.lock(project, businessType, operator)`，在业务 Provider 的同一事务内同步调用；不使用异步事件或消息，避免业务成功但锁定失败。
5. **迁移发布**：迁移 61 为新增表与新增列，存量行统一回填 `New`。目标环境执行前必须做生产结构审计、备份和隔离库演练；不得自动删除已承接业务数据。
6. **来源判断**：所有报表统一依赖 `BusinessOrigin`，禁止按名称、项目编号前缀或是否为空字段猜测是否接管项目。

# 微信订阅消息触达设计

> 日期：2026-09-26
> 范围：装得清小程序的微信服务通知（一次性订阅消息）
> 目标：让"需要用户本人回来处理"的业务节点能被用户及时看到，这是当前复访率的最大缺口
> 关联：`docs/design/migrations/20-小程序发布合规基线.md`、`推广营销/装得清营销智能体/status/小程序发现入口与设置清单-20260926.md`

## 1. 为什么做这件事

小程序上线后，用户回不来的原因不是"找不到入口"，而是**没有回来的理由**。站内通知只有用户主动打开小程序才看得到，等于没有触达。

业务闭环里真正需要本人回来处理的节点：

| 节点 | 谁必须回来 | 不回来的后果 |
| --- | --- | --- |
| 阶段验收待确认 | 业主 | 项目卡在"待验收"，下一阶段无法推进 |
| 业主已确认/驳回 | 项目经理、设计师 | 不知道可以继续施工或需要整改 |
| 施工任务逾期 | 项目经理、团队负责人 | 逾期被看见得太晚 |
| 材料到场待确认 | 项目经理、采购 | 应付账款挂空 |

其中**业主阶段验收待确认**价值最高：它是业主侧唯一必须主动操作的动作，也是天然的复访理由。

## 2. 现状与缺口

已有基础（无需新建）：

- `WechatMiniProgramSdk` 已经实现 `session`（code2Session）与 `phone`，并且**已有 AccessToken 进程内缓存**，可直接复用。
- 微信身份落在 `Credentials`：`type=Wx` 时 `idKey` 即 openid。
- 业主与项目的授权关系是 `CustomerAccess`（`cre_id` + `project_id` 显式授权），**不做手机号或姓名模糊匹配**。
- 站内通知已有统一生成入口 `NoticeContext`。

缺口：没有任何订阅消息能力。前端没有 `requestSubscribeMessage`，后端没有发送通道，模板 ID 也没有申请。

## 3. 架构

```text
用户点击动作
  → 前端 requestSubscribeMessage（拿到一次性订阅额度）
  → 业务事实发生（提交验收 / 业主确认）
  → 事务提交后（afterCommit）后端调用微信 subscribe/send
  → 微信侧校验额度：有额度则下发服务通知，无额度返回 43101
  → 用户点通知回到小程序指定页面
```

三条设计约束：

1. **未配置模板 ID 的场景一律跳过**，能力可逐个场景灰度，未配置不影响任何既有业务。
2. **发送在事务提交后触发**，不在数据库事务内做外部 HTTP 调用。
3. **发送失败只记日志**，绝不抛异常回滚业务事实——通知是附赠，不是事实的一部分。

### 3.1 为什么不建"订阅额度"表

一次性订阅的额度由微信侧维护。服务端重复发送会在微信侧失败并返回 `43101`；本地再记一份额度只会与微信侧不一致，还会引入"本地有额度但微信已过期"的假状态。因此**不建表、不记账，以微信返回值为准**。

### 3.2 为什么不需要数据库迁移

本设计不新增实体和字段，因此**没有迁移脚本**，也不会影响生产环境 `ddl-auto: validate` 的启动校验。这是刻意的选择：把"发不出去"的风险留在配置层，而不是留在数据库层。

## 3.3 模板选型决策（2026-09-26 用户确认）

后台实际勘察结论（微信公众平台 2026-09-26）：

- 「我的模板」初始为 0 个；一次性订阅可选用额度 50 个。
- 该小程序服务类目为「商业服务 > 企业管理」与「工具 > 办公」。
- 公共模板库共 102 个模板，**全部属「办公」类目，且没有任何验收 / 装修 / 工地语义的标题**。

## 4. 场景与模板申请清单（需要管理员在后台操作）

模板 ID **必须由小程序管理员在微信公众平台申请**，代码侧无法代替。申请路径：
`微信公众平台 → 功能 → 订阅消息 → 选用模板 / 申请模板`，类别选择「**一次性订阅**」（工具类小程序通常不具备长期订阅资格）。

申请后需要同时配置到**两端**（见第 5 节），只配一端会出现"授权了却收不到"。

### 4.1 场景一：业主 · 阶段验收待确认（已实现）

- 场景键：`owner.acceptance-pending`
- 触发时机：施工方提交阶段验收（`ProjectContext.submitAcceptance`）
- 收件人：该项目所有 `Active` 状态的业主授权（`CustomerAccess`）
- 通知落地页：`subpackages/project/pages/owner-acceptance?projectId=<项目ID>`
- 前端请求时机：业主确认完本次验收时（`accept/edit.vue`），语义是"下次验收提醒我"

模板字段（**字段名必须与所选模板一致**，微信按字段名校验，不一致会返回 47003）：

| 代码中的字段 | 建议模板字段 | 取值 |
| --- | --- | --- |
| `thing1` | 项目名称 | 项目名（超 20 字截断） |
| `thing2` | 验收阶段 | 阶段名（如"水电验收"） |
| `time3` | 提交时间 | `yyyy-MM-dd HH:mm` |
| `thing4` | 温馨提示 | 请进入小程序确认或发起整改 |

建议模板标题：**「阶段验收待确认通知」**

### 4.2 场景二：员工 · 业主已确认或驳回验收（已实现）

- 场景键：`employee.acceptance-decision`
- 触发时机：业主确认或驳回验收（`ProjectContext.confirmAcceptance` → `NoticeContext.notifyAcceptanceDecision`）
- 收件人：项目经理、设计师、履约专员、验收提交人（与站内通知同一批人）
- 通知落地页：`subpackages/project/pages/detail?id=<项目ID>`
- 前端请求时机：**尚未接入**，需要员工侧入口（见第 8 节）

| 代码中的字段 | 建议模板字段 | 取值 |
| --- | --- | --- |
| `thing1` | 项目名称 | 项目名 |
| `phrase2` | 验收结果 | 已确认 / 已驳回（≤5 字） |
| `thing3` | 验收阶段 | 阶段名 |
| `time4` | 确认时间 | `yyyy-MM-dd HH:mm` |

建议模板标题：**「验收结果通知」**

### 4.3 场景三、四：尚未实现

`employee.task-overdue`（施工任务逾期）与 `employee.material-arrival`（材料到场待确认）场景键、配置项已预留，但**触发点未接入**，原因是这两个节点的通知生成时机需要先确认（逾期通知目前在报表查询路径生成，直接挂发送会出现"用户看了一眼报表就收到推送"的意外行为）。属于业务规则问题，需先确认口径再接入。

## 7. 关键实现细节

- **必须在点击手势内调用**：微信要求 `requestSubscribeMessage` 在用户点击手势中调用。因此放在提交动作**之前**而不是提交成功之后——提交前的 `await` 网络请求会让手势失效。
- **字段长度**：`thing` 类型上限 20 字符，超出微信会以 47003 拒收；代码内已统一截断。
- **空值兜底**：微信不接受空字段值，代码统一用 `—` 兜底。
- **openid 不落日志**：日志只记录 SHA-256 前 8 位指纹，与登录日志的既有口径一致。
- **`43101` 不是故障**：用户从未授权、已退订、一次性额度用尽都会返回它，只记 info 不记 warn。

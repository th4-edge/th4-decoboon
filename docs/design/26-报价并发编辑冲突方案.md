# 报价并发编辑冲突 · 方案（P1-B，仅方案不改契约）

> 状态：**待评审**。未经确认不改接口、不落库、不加迁移。
> 目标：阻止"最后写入静默覆盖"，让冲突可被识别、可提示、可恢复。
> 背景：Web 已支持批量保存（`quote/lines/save`，单次 ≤200 行、可分多批），
> App 仍走单行 `quote/line/save`。

## 1. 三种候选方案对比

| 维度 | A · Quote 级乐观锁（`@Version`） | B · 条件更新（`updateTime` / 行级快照哈希） | C · 仅前端冲突检测 |
| --- | --- | --- | --- |
| 实现位置 | 实体 + JPA | Provider/Context 内的条件写入 | 前端比对 |
| 能否阻止静默覆盖 | ✅ 强 | ✅ 强（条件不满足即失败） | ❌ **不能**（服务端仍会覆盖） |
| 需要迁移 | **是**（新增 version 列） | 否（复用 `updateTime`）或需行级哈希列 | 否 |
| 对 App `quote/line/save` 影响 | **有**：App 不带版本号会一律失败 → 必须改 App 或放行 | 可做成**仅批量入口启用**，App 完全不受影响 | 无 |
| 与 Web 分批保存配合 | 批间版本会变 → 需在批内保持同一版本或逐批回传 | 同 | 无 |
| 冲突判定粒度 | 整单 | 整单（updateTime）或行级（哈希） | — |
| 结论 | 语义最标准，但**动 App 契约 + 需迁移** | **推荐**：可控、可按入口灰度、无迁移 | 明确不充分，只可作为辅助提示 |

**推荐：方案 B（条件更新），以 `updateTime` 为主、必要时演进到行级哈希。**

## 2. 方案 B 细节

### 2.1 冲突基准

- 读取时（`quote/designer/info`）返回 `updateTime`（投影已包含，无需新增字段）。
- Web 保存时携带读取到的 `quoteUpdatedAt`。
- 服务端在写事务内校验：

```text
if (request.quoteUpdatedAt != null && quote.updateTime > request.quoteUpdatedAt) {
    throw 409 CONFLICT「报价已被他人修改，请重新读取后再保存」
}
```

- **不传基准**（App 的 `quote/line/save`、旧客户端）→ 保持现有行为，**不做冲突校验**，
  因此 **App 契约与行为完全不变**。

### 2.2 Web 分批保存的批间一致性

分批保存会产生多次写事务，`updateTime` 在每批后都会变化。两种处理：

| 方案 | 做法 | 取舍 |
| --- | --- | --- |
| B1（推荐） | 第 1 批成功后**重新读取** `updateTime`，后续批次用新基准 | 允许他人在批间写入 → 但每批都能发现冲突 |
| B2 | 整次批量保存视为一个事务（服务端接收全部行） | 需要突破 200 行上限或改接口语义 |

> 建议先做 **B1**：与现有分批实现天然契合；若未来要求"整次导入原子性"，再评估 B2。

### 2.3 失败提示与恢复

- 冲突返回 **409 + 明确文案**：「报价已被他人修改（更新时间 xxx）。你的改动已保留，请重新读取后重试。」
- 前端：**保留全部脏数据**、显示冲突横幅、提供「重新读取并对比」按钮
  - 重新读取后展示：服务端现值 vs 我的未保存值（复用 `QuoteDecisionPanel` 的差异区）
  - 用户选择：放弃我的改动 / 逐行采用服务端值后重试
- **禁止**：冲突后自动重试或静默丢弃本地改动。

### 2.4 App `quote/line/save` 兼容影响

| 项 | 影响 |
| --- | --- |
| 参数 | **无变化**（不传基准即跳过冲突校验） |
| 行为 | **无变化** |
| 风险 | App 仍可能覆盖 Web 的改动；如需覆盖保护，App 需另行评估（不在本次范围） |

## 3. 评分与结论

| 方案 | 阻止覆盖 | 无迁移 | App 兼容 | 批间可控 | 综合 |
| --- | --- | --- | --- | --- | --- |
| A `@Version` | ✅ | ❌ | ❌ 需改 App | 需处理 | 不推荐（现阶段） |
| **B 条件更新** | ✅ | ✅ | ✅ | ✅ B1 | **推荐** |
| C 仅前端 | ❌ | ✅ | ✅ | — | 不充分，仅作辅助 |

## 4. 并发测试方法（实施后）

1. **同一报价两页**：页 A、页 B 均读取 → A 保存成功 → B 保存 → **期望 409**，B 的改动保留
2. **App+Web 交叉**：App 单行保存 → Web 批量保存 → Web 依据新基准重读后可成功
3. **批间插入**：Web 分 2 批保存，在第 1 批与第 2 批之间由另一会话写入 → **期望第 2 批 409**
4. **无基准请求**（模拟旧客户端）：不传 `quoteUpdatedAt` → 期望按现有行为写入（兼容性验证）

## 5. 是否需要迁移

| 方案 | 迁移 |
| --- | --- |
| B（`updateTime` 基准） | **不需要**（投影已含 `updateTime`） |
| 行级哈希 | 需要新增列 → 属迁移，需另行批准 |
| A（`@Version`） | 需要新增列 → 属迁移，需另行批准 |

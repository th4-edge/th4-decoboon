# 一后端多端同源架构规范（强制）

> 适用范围：`th4-decoboon` 后端、`th4-decoboon-app` App、`th4-decoboon-web` Web、Admin 及所有未来客户端。
>
> 状态：强制生效。与页面级实现、历史代码、旧接口封装冲突时，以本规范为准。

## 1. 唯一架构结论

装得清是**一后端、多客户端**：

```text
                    ┌──────── App ────────┐
业务事实 / 数据库 ───┤                     ├── 同一 Provider / 同一权限 / 同一状态
                    └──────── Web ────────┘
```

- 只有一个业务后端。
- App、Web 只部署不同客户端，不拥有各自独立后端。
- App、Web 必须连接同一 API 网关、同一租户数据库和同一领域服务。
- 页面布局、交互密度、端侧导航可以不同；业务事实、规则、接口、权限和状态不得不同。

## 2. 同源强制定义

同一业务能力在 App/Web 同时存在时，必须同时满足：

1. **同 Provider**：调用同一后端 Provider 路由，不因客户端不同而另建同义接口。
2. **同请求语义**：业务主键、月份、状态、动作和前置条件一致。
3. **同响应语义**：字段名称、类型、枚举 key、金额精度、空值和派生字段一致。
4. **同权限与数据范围**：角色、能力键、company/store/team/self 范围一致。
5. **同状态机**：允许动作、状态迁移、幂等和错误恢复一致。
6. **同金额/成本/利润口径**：公式只由后端计算；前端不得自行得出正式金额。
7. **同错误码与可恢复路径**：同类失败在 App/Web 返回同一业务错误及下一步。
8. **同事实回读**：写动作成功后两端都必须重新读取服务端事实，不用本地状态冒充结果。

## 3. 端侧允许差异

仅允许以下差异：

- 页面结构、信息层级、密度；
- 交互形态：拖拽、批量、键盘、宽屏/移动布局；
- 客户端能力：扫码、拍照、打印、文件选择等；
- 同一 Provider 的参数选择或响应裁剪，但不得改变业务语义。

不允许把“电脑端更适合批量”或“小程序页面更简单”作为新建第二套业务接口的理由。

## 4. 禁止模式（硬阻断）

以下任一出现即阻断开发和发布：

1. App 调用 `payroll/compensation/info`，Web 却另建同义接口或前端写死结果。
2. 一端使用 Provider 事实，另一端使用默认值、Mock、本地常量或前端计算。
3. 正式业务字段硬编码，如应出勤 22、工资 5000、状态 Pending、权限角色等。
4. 客户端自行实现金额公式、成本归属、权限判断或状态机。
5. 同一业务动作在两端使用不同路由、不同字段名或不同枚举。
6. 为了适配某个页面而新建同义 Provider，且未标注统一契约关系。
7. 只验证一端接口，未核对另一端调用链。
8. 页面有按钮但服务端未校验；或服务端允许但另一角色端错误展示。
9. 接口失败时前端用 0、空数组、默认 22 等值伪装业务事实。
10. 发现跨端差异后继续扩展功能，而不先关闭现有生产问题。

## 5. 前端业务默认值禁则

- 正式业务值必须来自 Provider。
- 未加载、加载失败或无业务记录时，显示“暂不可确认/未找到方案/请联系负责人”并保留重试路径。
- 禁止使用默认值伪装真实业务事实。
- 表单默认值只能表示“未填写”，不得表示某个正式业务结果。
- 例如应出勤天数：必须按员工 + 工资月份读取；无方案时不得回退 22。

## 6. 新能力开发门禁

在定义实体、页面、接口或任务前，必须填写能力对账矩阵：

| 项 | 要求 |
| --- | --- |
| 业务能力 | 一句话描述唯一用户结果 |
| 后端 Provider | 唯一路由、请求、响应、权限、状态、金额口径 |
| App 消费 | 页面、API 方法；不适用时说明理由 |
| Web 消费 | 页面、API 方法；不适用时说明理由 |
| 权限矩阵 | 各角色、数据范围、后端拒绝结果 |
| 状态矩阵 | 前置状态、目标状态、失败恢复、幂等 |
| 金额/成本 | 服务端公式和缺失值处理 |
| 跨端测试 | 同场景两端结果一致；至少一组反例 |
| 发布门禁 | 两端代码/构建/生产冒烟证据 |

没有该矩阵，不得派发跨端能力研发。模板：`docs/design/templates/app-web-provider-parity.md`。

## 7. 已存在不一致的修复顺序

发现 App/Web 不一致时：

1. 先确认唯一业务事实和正确 Provider；
2. 将正确结果限定为生产可验证的最小修复；
3. 只修改偏离端，不复制第二套后端逻辑；
4. 先在受影响生产端闭环；
5. 再按同一矩阵修复其余差异；
6. 不得借修复扩大到整个业务域，除非用户明确授权。

## 8. 测试与发布门禁

每个跨端业务能力至少验证：

- App/Web 均引用同一 Provider；
- 正向主路径结果一致；
- 无数据、加载失败、权限拒绝时路径一致；
- 金额/状态/字段与 Provider 回读一致；
- 客户端 console error 为 0；
- 生产发布记录列出两侧调用的 Provider 路由和关键字段。

同一能力只验证一端，不得标记“跨端对齐”。

## 9. 事故案例（强制反例）

Web 月度考勤曾把应出勤硬编码为 22，而 App 已调用 `payroll/compensation/info` 读取薪酬方案，导致同一员工在 App 显示 27、Web 显示 22。

根因不是双后端，而是：

- Web 没有复用统一 Provider；
- Web 把正式业务值写死为前端默认值；
- 没有跨端 Provider 对账和契约测试；
- 发布只看页面可用，没有验证数据来源。

正确处理：Web 删除 22 默认值，按员工 + 工资月份调用同一 Provider；无方案明确提示，不回退默认值。

## 10. 责任与关闭标准

- 后端负责唯一业务事实、状态、权限、金额和错误语义。
- App/Web 负责展现和交互，不得复制业务规则。
- 架构不一致属于跨端事实缺陷，必须建立问题单并阻断相关发布。
- “两端都有页面”“按钮能点”“自测通过”都不等于跨端对齐。
- 只有同 Provider、同语义、同权限、同状态、同金额口径，且两端验证通过，才能关闭跨端对齐问题。

# 后端分页与聚合接口强制规范

> 状态：生效（2026-10-31）
> 风险级别：L1（后端接口契约与性能治理）
> 关联变更：`CHG-20261031-042`
> 适用范围：th4-decoboon 所有 App、Web、Admin、站点和内部客户端消费的列表、选择器、明细、汇总、报表、排行与导出接口
> 上位规范：`rules.md` §0.4、§0.5、`docs/design/34-后端接口查询与业务编排强制规范.md`、Web `docs/standards/WEB-列表分页与汇总数据规范.md`

## 1. 一句话规则

> **会增长的数据必须由服务端分页；业务汇总必须由服务端聚合接口返回。前端不得用固定大页接口拉取全量，也不得对接口返回列表做金额、计数、比例、分组、趋势或排行计算。**

## 2. 问题根因

当前前端页面大量出现以下模式：

```text
current: 1
size: 200

const totalAmount = list.reduce((sum, item) => sum + item.amount, 0)
const overdueCount = list.filter(item => isOverdue(item)).length
const summary = list.filter(...).reduce(...)
```

这会同时导致：

1. 数据量超过 200 后结果被静默截断，页面仍把截断结果当作全量；
2. 首屏响应体、传输时间和序列化成本随业务增长线性增加；
3. 前端重复实现金额、状态、权限和口径逻辑，App/Web 容易产生不同结果；
4. `current page` 的合计被误认为全量经营指标；
5. 选择器只搜索已加载的前 200 条，后续数据无法被发现；
6. 后端为了支持大页或二次过滤，容易出现全表加载、Java 内存分页、N+1 和全量排序。

## 3. 接口分类：先分类，再编码

每个读取接口必须先归入以下四类之一。

| 类型 | 判定 | 强制契约 |
| --- | --- | --- |
| `PAGE_LIST` | 记录数量会随业务增长，需要浏览、筛选、翻页 | 服务端 `current + size + filters + sort`，返回当前页与全量 `total` |
| `PICKER_PAGE` | 选择器、关联对象搜索、远程候选 | 服务端关键词搜索 + 分页；不得一次返回全量 |
| `BOUNDED_LIST` | 业务上有不可突破的小上限，如固定枚举、角色、状态、单张单据固定配置 | 必须声明服务端上限、排序和业务理由；返回 `List<T>` 才允许 |
| `REPORT_SUMMARY` | 金额、计数、比例、分组、趋势、Top-N、经营看板 | 不接收 `current/size`；通过聚合 SQL 返回一行或有限分组行 |

无法归入以上四类的接口不得提交。

## 4. PAGE_LIST 分页契约

### 4.1 请求

Provider 使用实体类内成员变量接收：

```text
current       页码，从 1 开始
size          每页条数
keyword       可选关键词
filters       页面全部业务筛选条件
sort          服务端允许的排序字段和方向
```

硬性要求：

- 默认 `size = 20`。
- 普通业务列表硬上限 `50`。
- 任何请求 `size > 50` 必须由服务端收敛到允许上限，并在响应中返回实际 `size`。
- 需要“全选”或“批量操作”时，调用独立 action/batch 接口传对象 ID 或筛选条件，不得把 `size` 调到 1000。
- 搜索、筛选、排序全部在数据库查询完成。
- 排序必须包含唯一键作为最后一级，例如 `create_time DESC, id DESC`，防止翻页重复或遗漏。
- 租户、企业、门店、团队、本人和项目参与关系必须由服务端强制。

### 4.2 响应

框架标准 `Page<T>` 必须包含：

```text
content          当前页记录
totalElements    当前筛选条件下的总记录数
totalPages       总页数
number           当前页
size             服务端确认的实际每页条数
```

如果客户端使用统一包装，也必须保留等价语义：

```text
list + total + current + size
```

禁止：

- 前端用 `current * size` 自行推算 `total`；
- 前端用列表长度作为全量数量；
- 接口返回 `content` 后再在前端切页；
- 响应中没有实际 `size`，导致前端误以为请求的 200 已生效。

### 4.3 后端实现

分页必须在数据库执行：

```text
Specification/Criteria/JPQL/Native SQL
→ ORDER BY 稳定排序
→ LIMIT/OFFSET 或框架 Pageable
→ COUNT 使用同一套范围与筛选
```

禁止：

- `findAll()` 后 Java 过滤、排序、`subList` 分页；
- `PageRequest.of(0, 500)` 先取固定全量再二次过滤；
- 为一次分页请求加载完整实体图；
- 在分页结果上逐行查询关联；
- 让 `@EntityGraph` 加载页面未使用的关联；
- 先查当前页再额外查相同数据算 `total` 时使用不同筛选条件。

## 5. PICKER_PAGE 选择器契约

选择器是远程数据检索，不是全量下拉框。

必须：

- 支持 `keyword` 服务端搜索；
- 支持 `current + size`；
- 默认 20，硬上限 50；
- 已选项通过 ID 批量回显，不依赖首次 200 条列表；
- 详情页的关联选择器显示“加载更多”或分页提示；
- 选择结果回显时按 ID 查询，不能在前端缓存全量对象。

禁止：

- `size: 200` 后在本页内存搜索；
- 前端 `filter()` 已加载候选；
- 只搜索当前页；
- 用 `list.length` 判断是否还有更多候选。

## 6. BOUNDED_LIST 例外契约

只有同时满足以下条件才允许直接返回 `List<T>`：

1. 有业务和技术上的不可增长上限；
2. 上限由服务端代码强制，不是“当前只有这么多”；
3. 返回行数稳定，不随租户经营数据增长；
4. 页面不承担历史检索、对账、导出或全量分析；
5. Provider 注释和接口契约明确上限。

允许示例：

- 固定枚举、状态字典、角色；
- 单张单据内业务规定最多 N 个固定节点；
- 单项目有限数量的配置项。

不允许示例：

- 客户、房屋、项目、报价、合同、收款、付款、应收、应付、工资、提成、台账、凭证、日志、待办、风险；
- 详情页内可持续增长的历史动态、附件、审批记录、跟进记录、验收轮次。

## 7. REPORT_SUMMARY 汇总契约

### 7.1 请求

汇总接口只接收：

```text
filter conditions
time range
dimension
scope
```

禁止接收 `current/size` 作为分页参数。

### 7.2 响应

汇总响应必须至少包含：

```text
asOf              数据截止时间
scope             数据范围说明
count             匹配总数量
amounts           金额指标
rates             比例指标
groups/topN       有限分组或 Top-N
```

要求：

- 标量指标一次 SQL 返回 O(1) 行；
- 分组统计 `GROUP BY` 返回有限行；
- Top-N 在 SQL `ORDER BY ... LIMIT N`；
- 缺值、无权限、成本不完整必须有明确字段表达；
- 不允许以 `0` 伪装未加载或不可确认；
- 汇总结果必须与列表共享同一租户、数据范围、筛选和截止时间。

### 7.3 允许的业务公式

成本、毛利、结算差额等需要多步业务公式时，允许批量取数后在内存计算，但：

- 循环体内零查询；
- 批量 `IN` 预取；
- 金额/成本/利润口径不变；
- 输出可以追溯到 SQL 或公式；
- 10 倍数据量下响应行数不线性增长。

## 8. 前端消费契约

### 8.1 列表页

- 列表请求必须携带 `current + size`；
- 当 `totalElements > size` 时展示分页或加载更多；
- 筛选、排序、搜索变化时重置到第 1 页；
- 翻页只替换列表，不重新计算另一套汇总；
- `page.total` 只能用于分页导航，不能当作经营统计卡片。

### 8.2 汇总卡片

- 必须调用独立 `report/summary/overview` 接口；
- 统计接口失败显示“统计暂不可确认”和重试入口；
- 不得从列表 `reduce/filter().length` 生成正式指标；
- 不得以当前页合计冒充全量合计；
- 如页面需要展示“当前页小计”，必须明确标注“当前页”，且不得进入经营结论。

### 8.3 前端允许的内存计算

只允许：

- 单位换算；
- 千分位、货币符号、百分比格式化；
- 日期格式；
- 未提交表单的输入预览，且最终金额仍由后端重新计算；
- 有限的纯 UI 行数统计，例如网格当前渲染行数，但不得进入业务汇总。

禁止：

- 对接口返回的业务列表做 `reduce` 生成金额；
- 对业务列表做 `filter().length` 生成状态数量；
- 对业务列表做 `groupBy` 生成分类统计；
- 对业务列表排序后截取 Top-N；
- 用列表数据计算回款率、完成率、毛利率或风险数。

## 9. 列表与汇总一致性

同一筛选条件下必须满足：

```text
列表 totalElements == 汇总 count
```

并验证：

- 列表与汇总使用相同权限和门店/团队范围；
- 列表翻页不改变汇总值；
- 汇总失败不清空列表；
- 列表失败不伪造汇总；
- `asOf` 一致或明确说明不同数据截止时间；
- 金额字段可由全量明细或对账脚本验证到同一口径。

## 10. 后端查询反模式

以下任一出现即阻断：

1. `findAll()` 后 `stream().filter/sum/count/groupBy` 生成业务汇总；
2. `PageRequest.of(0, 500)` 先取固定全量再分页；
3. `List<Entity> all = repository.find...; all.subList(...)` 做内存分页；
4. 先全量加载再 `sort().limit(N)`；
5. 在 `for` 循环内调用 Repository 或访问 LAZY 关联；
6. 为减少 SQL 条数堆叠完整 `JOIN FETCH`，但页面实际只使用少量字段；
7. 汇总接口返回行数随业务明细增长；
8. 列表接口使用 `size > 50` 的默认值；
9. 选择器按 200 条全量加载后本地过滤；
10. 导出接口复用列表大页查询并逐页拼接全量数据。

## 11. 性能与容量门禁

### 11.1 接口预算

核心读取 API：

```text
P95 ≤ 500ms
P99 ≤ 1000ms
max ≤ 2000ms
SQL ≤ 30 条
```

普通读取 API：

```text
P95 ≤ 800ms
P99 ≤ 1500ms
max ≤ 3000ms
```

### 11.2 数据增长验证

至少验证：

- 0 条、不足一页、恰好一页、超过一页、最后一页；
- 10 倍数据量下分页 SQL 条数不随 `size` 增长；
- 汇总接口返回行数保持 O(1) 或有限分组；
- 多租户和大租户场景下 P95/P99 达标；
- 列表与汇总在同筛选条件下可对账；
- 前端首屏请求数和响应体大小符合预算。

## 12. 现有存量基线（2026-10-31 扫描）

以下数量是静态扫描结果，不等同于全部业务缺陷；用于整改排序和防止新增债务。

| 检查 | Web | App |
| --- | ---: | ---: |
| 固定大页调用 `size >= 50` | 51 处 / 46 个文件值组合 | 38 处 / 33 个文件值组合 |
| `reduce` / `filter().length` 可疑业务计算 | 92 处 | 117 处 |
| 前端分页门禁 | 已存在 `check:pagination` | 已存在 `check:pagination` |

后端静态扫描：

| 检查 | 数量 |
| --- | ---: |
| 返回 `List<T>` 的 `/list` Provider | 15 |
| `PageRequest.of(0, >=100)` 硬编码全量页 | 5 |
| `.subList()` 内存切页 | 39 |
| `/page` Provider | 108 |
| `/report` Provider | 44 |

这些存量必须先分类：

- 固定大页是否是 `BOUNDED_LIST`；
- `reduce` 是否是纯 UI 行数或未提交表单预览；
- `subList` 是否只是内存计算后的最终切片，还是完整实体全量加载；
- `List<T>` Provider 是否有服务端不可增长上限。

未完成分类的调用不得作为新接口模板。

## 13. 整改顺序

1. 金额、成本、利润、工资、提成、应收、应付、收款、付款、台账、凭证；
2. 客户、项目、合同、报价、待办、风险、审批、日志；
3. 选择器和关联对象搜索；
4. 详情页内持续增长的历史明细；
5. 纯配置和固定枚举。

整改前置：

- 先建立指标口径和 report 接口；
- 再替换前端计算；
- 最后删除固定大页调用和前端 reduce；
- 每一批保留前后端对账、权限负向和 10 倍数据量证据。

## 14. 交付检查清单

- [ ] 接口已分类为 `PAGE_LIST / PICKER_PAGE / BOUNDED_LIST / REPORT_SUMMARY`；
- [ ] 增长列表有 `current/size/total`；
- [ ] `size` 有服务端上限，普通列表和选择器均不超过 50；
- [ ] 搜索、筛选、排序在服务端执行；
- [ ] 没有固定 `size: 200/500` 冒充全量；
- [ ] 没有全量加载后 `subList` 分页；
- [ ] 汇总接口不接收分页参数，使用聚合 SQL；
- [ ] 前端业务卡片消费 report/summary；
- [ ] 前端没有对业务列表做 reduce/filter 汇总；
- [ ] 列表 `totalElements` 与汇总 `count` 可对账；
- [ ] 汇总失败显示暂不可确认；
- [ ] 10 倍数据量下查询行数和 SQL 条数稳定；
- [ ] 跨企业、跨门店/团队和权限负向用例通过；
- [ ] 有端到端 P95、响应体大小和真实页面证据。

## 15. 机器门禁与文档边界

已有前端门禁：

```bash
# Web
npm run check:pagination

# App
npm run check:pagination
```

门禁当前采用基线棘轮策略：存量固定大页调用被登记，新增大页值会阻断。`--write` 只能在已完成服务端分页评审后使用，禁止为了让检查变绿直接扩大基线。

后端新增或修改分页、汇总接口时必须同时执行：

```bash
python3 scripts/audit-provider-response-contract.py --check
```

该脚本主要验证响应序列化；分页与聚合的实现仍需按本规范进行 SQL、对账和性能验收。后续可将本规范的静态规则扩展为独立门禁，但不得以“有脚本”替代端到端性能测量。

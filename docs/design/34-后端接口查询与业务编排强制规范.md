# 后端接口查询与业务编排强制规范

> 状态：生效（2026-10-31）
> 风险级别：L1（接口设计、查询契约与研发门禁；无运行时业务语义变更）
> 关联变更：`CHG-20261031-049`
> 适用范围：`th4-decoboon` 所有 Provider，包括 App、Web、Admin、站点和内部任务消费的读取、写入、批量、导出接口
> 上位规范：`AGENTS.md`、`rules.md` §0.1、§0.3、§0.4、§0.5、§0.6、§4.5、§5
> 配套规范：`docs/design/31-一后端多端同源架构规范.md`、`32-Provider接口响应序列化与懒加载安全规范.md`、`33-后端分页与聚合接口强制规范.md`

## 1. 一句话规则

> **一个 Provider 只服务一个真实用户目标；编码前必须先写清业务场景、接口类别、数据增长方式和查询链。读取只允许有界结果、批量装配和聚合取数；写入只允许一个原子业务动作。N+1、全量加载后内存统计、固定大页和万能接口均不得新增。**

接口的“功能正确”不等于“产品可用”。业务结果正确、权限正确、金额口径正确、查询规模有界、响应可解释、失败可恢复，必须同时成立。

## 2. 问题现象与根因

### 2.1 已出现的典型现象

| 现象 | 直接后果 | 根因 |
| --- | --- | --- |
| 先加载项目/客户/合同/工资项全量实体，再在 Java 中 `filter/count/sum/groupBy` | 数据量增长后 CPU、内存、SQL 返回行数和响应时间同步增长 | 把领域实体当作查询模型，把数据库擅长的聚合放到应用内存 |
| 当前页查询后逐行查关联，或循环项目逐个查合同、采购、动态 | 一次请求产生 `1 + N` 甚至 `1 + N × M` 条 SQL | 先按实体关系写代码，没有设计批量装配和固定查询链 |
| `PageRequest.of(0, 200/500)` 后排序、过滤、`subList` | 超过固定值后静默漏数；分页总数和金额都可能是错的 | 用“固定大页”冒充全量查询，没有数据库分页 |
| 一个接口同时承担列表、汇总、详情、权限判断、脱敏和多个角色分支 | 逻辑难懂、改动互相影响、无法准确测量和测试 | 按数据表或页面拼接口，没有按单一用户目标拆边界 |
| 汇总接口顺序调用多个重型汇总接口 | 延迟和 SQL 相加/相乘，一个子模块慢会拖垮整个页面 | 把“页面组合”误做成“接口嵌套组合” |
| 只看 SQL 条数，不看 P95、响应体和真实页面 | SQL 变少但接口更慢，优化投入没有用户体验收益 | 代理指标替代用户感知指标，违反 `DEC-037` / `BR-032` |

### 2.2 根因判断

1. **场景缺失**：没有先回答“谁在什么时点、为了完成什么动作、最晚能等多久”，直接从实体和表开始写 Provider。
2. **接口边界缺失**：把“页面需要什么”理解成“一个接口全给”，导致一个接口承担多个用户目标。
3. **数据规模缺失**：默认数据永远是几十条，没有区分 O(1)、O(一页)、O(有限分组) 和 O(全部数据)。
4. **查询链缺失**：没有在编码前列出主查询、批量补充查询、聚合查询及其随 `size`/租户数据增长的变化。
5. **JPA 使用方式错误**：把 LAZY 关联、`findAll`、流式 Java 计算当成框架默认能力，未改用投影、批量 `IN`、聚合 SQL。
6. **门禁只覆盖局部**：已有汇总类静态门禁，但分页实现、循环查库、批量写入校验和“万能接口”仍主要依赖人工评审。

## 3. 当前接口盘点（2026-10-31）

### 3.1 规模概览

| 检查 | 结果 | 说明 |
| --- | ---: | --- |
| `@Service` Provider 实现 | 543 | 全部对外/内部能力入口 |
| `/page` 能力 | 117 | 增长型列表必须逐项分类 |
| `/report` 能力 | 44 | 必须使用聚合/投影 SQL |
| `/list` 能力 | 21 | 必须证明是不可增长的有限列表 |
| `findAll(` | 64 处 / 53 文件 | 不等于全部违规，但每处必须说明边界 |
| `PageRequest.of(` | 96 处 / 86 文件 | 不等于全部违规，必须检查是否为内存分页 |
| `subList(` | 40 处 / 38 文件 | 33 个 `/page` 或 `/range` 路由命中，属重点分类对象 |
| `size` 硬上限大于 50 | 68 文件 | 与 §33 普通列表/选择器上限冲突，需分类或整改 |
| 固定 `PageRequest.of(0, >=100)` | 5 处 / 4 文件 | 明确高风险，见 3.2 |
| 循环体或流式 lambda 内仓储查询候选 | 7 文件 | 含写入前逐行校验，不能只看读接口 |

以上是静态盘点，不等同于 543 个接口都存在缺陷。固定枚举、单张单据的不可增长配置、已限制规模的批量动作可以合理返回 `List`，但必须声明上限和业务理由。

### 3.2 已确认的高风险路由

| 路由 | 当前实现风险 | 必须的方向 |
| --- | --- | --- |
| `customer/report/page` | 无项目过滤时遍历所有可访问项目，每个项目查 200 条动态，再全局排序和 `subList` | 按项目集合与筛选条件在数据库分页；排序、总数、可见性统一下推 SQL |
| `project/report/page` | 无项目过滤时先加载可见项目，再取 500 条动态到 Java 过滤，分页和筛选失真 | 用一条带权限子查询/关联条件的数据库分页查询；类型筛选下推 |
| `project/report/list` | 固定取 500 条动态，存在截断和无界增长风险 | 改为 `PAGE_LIST`；确实需要有限摘要时声明业务上限 |
| `project/acceptance/page` | 固定取 100 条，`current/size` 没有形成真实分页契约 | 改为数据库 Pageable 和稳定排序 |
| `project/purchase/page` | 可见项目全量加载，项目流中逐个查采购单，再全量装配明细；没有真实分页 | 项目/门店范围下推采购单查询；数据库分页后批量装配当前页明细 |
| `project/material-plan/page` | 可见项目全量加载，项目流中逐个查材料计划，返回全量列表 | 改用数据库分页；项目范围通过关联条件下推 |
| `payroll/workbench/report` | 原实现为考勤、工资单、应付、提成、工资条多次全量加载后 Java 计数/求和 | `PAY-OPS-01` 已改为 6 条有界聚合/投影查询，实体加载 22→2；真实页面与生产 P95 待验收 |
| `finance/summary/report` 等财务汇总 | 多类财务实体全量加载后流式汇总，已有 A1 基线 | 按指标拆聚合查询；业务公式必须批量取数、循环内零查询 |

### 3.3 老问题复盘

`statistic/pm/report` 曾从 106 条 SQL 优化到 26 条，但延迟仍是 463–820ms；真正瓶颈是 136,633B 响应体中的 `materialRisks` 占 78.6%。收窄白名单后降到 23,244B，P95 降到 496ms。这个案例说明：

- N+1 必须治理，但 SQL 条数不是唯一目标；
- 查询形状、响应体大小、序列化和真实页面必须一起看；
- 任何优化必须用同口径 P95、TTFB 和响应体变化证明收益。

## 4. 编码前强制场景卡

任何新增 Provider 或实质修改查询逻辑前，必须在 PRD、任务单或 `CHG-*` 中填写场景卡。没有场景卡不得编码。

| 字段 | 必须回答 |
| --- | --- |
| 使用人/角色 | 谁使用：BOSS、店长、团队负责人、设计师、营销、项目经理、财务、员工、业主或平台运营 |
| 触发时点 | 打开哪个页面、点击哪个动作、收到哪个事件后触发 |
| 当前线下动作 | 用户现在如何完成这件事，最关心哪 1–3 个判断 |
| 系统最短动作 | 一次操作最少需要哪些事实、状态和下一步入口 |
| 下游消费者 | 结果给谁继续做任务、确认、交接、对账或留证 |
| 数据增长 | 0、1、几十、几千、持续增长时结果规模如何变化 |
| 异常路径 | 无数据、权限不足、部分失败、超时、重复提交、历史快照缺失时如何处理 |
| 验收 | 用户完成什么动作、看到什么结果、服务端产生什么事实，才算闭环 |

### 4.1 场景卡示例：工地动态

- 使用人：项目经理发布动态；店主/设计师查看项目动态；业主查看已授权且可见的动态。
- 触发时点：项目现场录入后，或进入项目动态/业主“工地相册”。
- 最短动作：发布人选择项目、类型、内容和图片；查看人只看当前项目或本人可访问项目的最新动态。
- 下游消费者：项目详情、业主工地页、项目风险/任务跟进。
- 数据增长：单项目动态持续增长，不能返回全量。
- 默认路径：按项目数据库分页，默认 20 条，稳定倒序。
- 例外：跨项目总览只允许使用独立聚合/读模型，不能在同一个接口里逐项目查询后合并。

### 4.2 场景卡示例：薪酬工作台

- 使用人：BOSS、店长、财务。
- 触发时点：月初进入薪酬工作台，判断“是否可发、还差什么、风险金额是多少”。
- 最短动作：看到待处理考勤、当前工资单状态、待发金额和待发工资条数量，再进入具体工资单。
- 下游消费者：工资单编辑、确认、发放、财务应付。
- 数据增长：历史工资单和工资项持续增长，单次页面只需要一个期间和当前门店范围。
- 默认路径：每个指标由聚合 SQL 返回；工资单列表单独分页。
- 例外：不能用 5 次全量 `findAll` 后流式计算制造“工作台很快”的假象。

## 5. 接口分类

每个接口必须先归入以下一个类别。无法分类的接口不得提交。

| 类别 | 典型能力 | 返回规模 | 强制查询形状 | 禁止 |
| --- | --- | --- | --- | --- |
| `READ_DETAIL` | `/info`、详情页、单据详情 | 1 个根对象 + 有限摘要 | 1 次根查询 + 固定次数批量补充 | 在详情里加载持续增长的历史明细；逐行查关联 |
| `PAGE_LIST` | `/page`、增长型列表 | O(`size`) | 数据库 `LIMIT/OFFSET` 或游标 + 同条件总数 + 当前页批量装配 | `findAll + subList`；固定大页；逐行查询 |
| `PICKER_PAGE` | 关联选择、远程搜索 | O(`size`) | 关键词/筛选下推数据库 + 分页 + 批量回显 | 200 条全量后本地搜索 |
| `BOUNDED_LIST` | 固定枚举、单张单据有限配置、不可增长的分组 | O(`k`)，`k` 有业务上限 | 声明上限、排序和理由；SQL 至少带范围条件 | 以“业务不会增长”为借口省略上限 |
| `REPORT_SUMMARY` | 金额、计数、比例、排行、趋势、经营看板 | O(1) 或 O(有限分组) | 聚合/投影 SQL；必要时一条 SQL 多列 | 全量实体 + Java 循环求和；汇总嵌套汇总 |
| `EXPORT_JOB` | 导出、批量下载、长任务 | 独立任务/游标批次 | 独立查询、游标/分批、幂等任务 | 复用列表大页逐页拼接全量 |
| `WRITE_ACTION` | `/save`、`/update`、`/delete`、`/confirm` | 1 个业务动作 | 按目标对象加权限，批量校验，事务内一次落库 | 在写接口中顺带计算工作台全量指标 |
| `BATCH_ACTION` | 批量保存、批量分配、批量删除 | O(`N`)，必须声明上限 | 一次批量加载 + 内存 Map 校验 + `saveAll/deleteAll` 或批量 SQL | 循环内 `findById/save/delete`；循环内查重 |

### 5.1 读取接口的最低契约

- 使用登录员工/业主身份，数据范围由服务端确定，不能信任前端 `companyId/empId/ownerId`。
- 分页返回真实 `current/size/total/totalPages` 语义；实际 `size` 必须回传。
- 汇总返回 `scope`、`asOf`、指标值和完整性/失败语义。
- 列表只返回页面真实消费字段，不能把完整实体图作为通用读模型。
- 接口失败必须返回可恢复错误，不得用 0、空数组或当前页结果冒充完整事实。

## 6. 查询链设计

### 6.1 先声明增长模型

编码前必须把每一层数据标成以下之一：

| 模型 | 例子 | 允许的查询 |
| --- | --- | --- |
| O(1) | 单条详情、单行汇总、单个状态 | 固定 SQL 数，聚合/主键查询 |
| O(`pageSize`) | 列表当前页、选择器当前页 | 分页 SQL + 批量补充 |
| O(`groupCount`) | 按 7 个状态、12 个月分组 | 聚合/投影 SQL，分组数由业务枚举或查询上限约束 |
| O(`N`) | 一次批量保存、批量分配 | `N` 有明确上限，批量加载/写入，禁止逐条查库 |
| O(全部) | 全量历史、全公司明细、无限导出 | 读取接口禁止；导出用独立任务/游标分批 |

### 6.2 编码前写查询链

在 Provider 或 `CHG-*` 中记录：

```text
Provider:
接口类别:
主对象:
数据增长模型:
主查询:
总数查询:
批量装配查询:
汇总/分组查询:
最大返回行数:
最大 SQL 条数:
是否随 size/数据量增长:
权限条件:
稳定排序:
异常/空值语义:
```

### 6.3 禁止规则

1. **禁止循环内查库**：`for/while`、`forEach`、`stream.map/flatMap` 内不得调用 Repository、Mapper 或触发 LAZY 关联查询。
2. **禁止 N+1 装配**：先得到当前页 ID，再用一次批量 `IN` 查询关联；关联数量超过单条 SQL 合理上限时按固定批次切分，但批次数量不能随租户总量无限增长。
3. **禁止全量实体算指标**：合计、计数、比例、Top-N、趋势、逾期/未收等判定必须用聚合/投影 SQL。
4. **禁止固定大页冒充全量**：`PageRequest.of(0, 100/200/500)` 只能作为已声明上限的有限列表，不能配 Java 过滤和 `subList`。
5. **禁止分页后再 Java 过滤**：筛选、排序、权限、状态、门店/团队范围必须与主查询一致下推数据库。
6. **禁止重 JOIN 换 SQL 条数**：关联只看摘要或少量字段时使用投影/批量查询；`@EntityGraph` 不得堆全套对象图。
7. **禁止汇总嵌套汇总**：工作台需要多个指标时复用聚合层，不能顺序调用多个重型 `report/workbench/overview`。
8. **允许的内存计算仅限业务公式**：成本、毛利、完整性等公式可以批量取数后计算，但循环内零查询，且不得改变 `ProjectCostContext`、权限或快照口径。
9. **只读事务不加锁**：`readOnly=true` 链路禁止悲观锁；业务并发统一用 Redisson，遵守 `DEC-029`。
10. **响应必须最小化**：列表和驾驶舱只下发页面判断、动作、交接、确认、留证或对账所需字段；嵌套关联只给摘要。

### 6.4 批量装配模板

```text
1. 主查询：按筛选、权限、稳定排序和 Pageable 取当前页 ID/投影
2. 收集当前页 ID
3. 批量查关联表：WHERE tenant = ? AND owner_id IN (...)
4. 在内存建立 Map<ID, List<Summary>>
5. 按当前页顺序组装字段
6. 汇总指标走独立聚合 SQL，不从当前页明细 reduce
```

关键不是“SQL 一定只有几条”，而是：**SQL 条数不能随 `size` 或业务明细总量增长；返回行数必须符合声明的 O(1)、O(`size`) 或 O(有限分组) 模型。**

## 7. 业务编排边界

### 7.1 一个接口只解决一个用户目标

| 场景 | 正确方式 |
| --- | --- |
| 打开列表并查看金额/状态摘要 | 一个 `PAGE_LIST` + 一个 `REPORT_SUMMARY`；或专门读模型，但指标仍由聚合层产生 |
| 编辑工资单并发放 | 分为编辑 `WRITE_ACTION`、确认 `WRITE_ACTION`、发放 `WRITE_ACTION`，每步有状态和幂等 |
| 页面需要项目、合同、变更和成本四类事实 | 若必须同屏一致，建立专用读模型，复用统一聚合 Context；不得顺序调用四个完整重接口 |
| 跨页面低相关能力（如详情、导出、统计） | 拆成独立 Provider，不在一个接口里用多个可空参数分支 |
| 批量保存设计分项 | 一次加载已存在分项和项目库条目，内存 Map 校验，批量写入；禁止逐行查库 |

### 7.2 读写分离

- GET/查询 Provider 不得产生业务副作用，不得顺手修复数据、补建任务或写缓存作为事实来源。
- 写 Provider 在事务内只完成本次业务动作和必要审计；外部调用、长任务和大报表不得长时间占用写事务。
- 写成功后返回最小业务结果，并明确下一次回读的 Provider；不得把整页工作台重算塞进写响应。

### 7.3 流程不等于接口

审批、确认、发放、作废、整改等流程按业务动作拆开：

```text
状态校验 → 权限/数据范围 → 幂等/并发控制 → 业务写入 → 审计/事件 → 返回下一步
```

禁止用一个 `/process`、`/workbench` 或带大量可选参数的全能接口同时承担多个动作。状态机、金额和权限口径以业务智能体裁决为准，技术实现不得自行简化。

### 7.4 页面组合与接口组合

页面可以组合多个读模型，但必须满足：

- 首屏关键请求通常不超过 5 个；
- 同一业务事实不能由多个接口用不同口径计算；
- 某个模块失败时只显示该模块“暂不可确认”，不能让整页伪 0；
- 所有模块的 `asOf` 或数据延迟能解释；
- 请求数量与响应体大小进入页面性能证据。

## 8. 典型反模式与改造方向

| 反模式 | 当前代码形态 | 后果 | 改造方向 |
| --- | --- | --- | --- |
| 固定大页 | `PageRequest.of(0, 500)` + Java 过滤 + `subList` | 漏数、全量扫描、分页语义错误 | SQL 分页 + 筛选/排序下推 |
| 项目流查子表 | `projects.stream().flatMap(p -> orderRepo.findByProject(p))` | SQL 随项目数增长 | 采购单按项目范围分页，明细批量 `IN` |
| 业主动态逐项目查 | 遍历可访问项目，每项目查 200 条动态 | N+1 + 排序失真 + 总页数失真 | 以可访问项目 ID 集合作为 SQL 子查询分页 |
| 工作台 Java 汇总 | 5 类实体 `findAll` 后 `filter/count/reduce` | 全量行、CPU/GC、页面对数据量敏感 | 每指标聚合 SQL；状态用 `SUM(CASE WHEN)` |
| 写入前循环查重 | 批量保存时逐行 `findBy...` | 批量接口退化为 N+1 写 | 一次批量加载 + Map 校验 |
| 万能接口 | 一个 Provider 同时列表、统计、详情、导出和多角色分支 | 逻辑复杂、难测、耦合高 | 按用户目标拆 Provider；专用读模型仅服务同屏一致 |
| 汇总套汇总 | 工作台依次调用多个重型 report | 延迟相加、SQL 相乘 | 共享聚合层/一次多指标 SQL |
| 重 JOIN 换条数 | 为降 SQL 堆完整关联图 | 单 SQL 变慢、响应体变大 | 页面投影 + 批量装配，按 L1 指标验证 |
| 前端 reduce | 页面从当前页或固定大页求和 | 截断后金额错误、跨端不一致 | 服务端 `REPORT_SUMMARY` |
| 详情装历史 | `/info` 返回全部合同行、动态、日志、附件 | 详情越用越慢 | 根对象 + 有限摘要；历史列表独立分页 |

## 9. 性能与验收门禁

### 9.1 预算

| 类别 | P95 | P99 | max | SQL 防劣化线 |
| --- | ---: | ---: | ---: | ---: |
| 核心读取 API | ≤500ms | ≤1000ms | ≤2000ms | ≤30 条 |
| 普通读取 API | ≤800ms | ≤1500ms | ≤3000ms | 按接口声明 |
| 页面首屏 | 有效数据 ≤2s | 可交互 ≤3s | 关键路径请求 ≤5 个 | 另记录响应体 |
| 10× 数据量 | 预算仍成立 | — | — | SQL 结构和返回行数不随明细总量线性增长 |

SQL 条数是防劣化辅助指标，不是优化方向。成功判据只能是 L1 用户感知、响应体大小和可解释的页面行为；SQL 变小但 P95 未改善或响应体变大，应回滚并重新分层测量。

### 9.2 必测矩阵

| 维度 | 必测 |
| --- | --- |
| 数据规模 | 0 条、1 条、不足一页、恰好一页、超过一页、最后一页、10× 数据 |
| 查询形状 | SQL 条数是否随 `size` 增长、返回行数是否符合声明模型、是否随业务总量增长、慢查询/执行计划 |
| 权限 | 跨企业、跨门店/团队/本人、业主义务、越权 ID、伪造筛选 |
| 业务 | 正常、空数据、失败、部分失败、重复提交、历史快照、状态不允许 |
| 响应 | 字段白名单、响应体大小、序列化、关闭 OSIV 后无懒加载异常 |
| 页面 | App/Web 真实页面、首屏请求数、网络失败、Console 错误 |

### 9.3 性能定位顺序

必须遵守 `rules.md` §0.5：

1. 端到端采样 ≥10 次，记录 P95、TTFB、响应体；
2. 按传输、服务端、存储分段，只优化实测占比最大的一段；
3. 同环境、同数据、同并发做改动前后对比；
4. 连续 2 次无改善，停止该类优化并重新测量；
5. 只有 L1 指标改善才计入收益。

## 12. 机器与人工门禁

已存在：

```bash
# 汇总/报表类 N+1、全量求和、重 EntityGraph 静态门禁
mvn -q -Dtest=SummaryImplementationRulesTest test

# Provider 响应字段与序列化契约
python3 scripts/audit-provider-response-contract.py --check
```

新增/修改 Provider 时至少执行以下静态扫描，并逐项分类：

```bash
rg -n 'findAll\(|subList\(|PageRequest\.of\(0,\s*(100|200|500)|Math\.min\(size,\s*(100|200|500)' src/main/java
rg -n 'for\s*\(|while\s*\(|\.map\(|\.flatMap\(' src/main/java
```

静态命中不等于缺陷；但“新文件或新分支出现上述模式且没有场景卡、查询链和验收证据”时，代码评审必须阻断。后续若新增自动查询门禁，必须同时提供负向自测，不能以脚本存在替代端到端性能测量。

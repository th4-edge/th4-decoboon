# 35 · 业务对象选择器与选择结果展示规范

> 状态：生效并强制执行
> 适用范围：`th4-decoboon-web`、`th4-decoboon-app`，以及后续复用同一业务对象的 Admin 页面
> 业务依据：`DEC-021/022/023/024/025/026/028`、`BR-019/020/021/022/023/024/026`
> 评审门禁：`T15`（业务概念选择器）、`T16`（表单分区与结果确认）、`T17`（适用时单据化表单）
> 上位工程规范：`AGENTS.md`、`docs/design/31-一后端多端同源架构规范.md`
> 本规范解决：业务对象数据量增长后，不能用普通下拉承载选择；选择完成后不能只回显名称或“已选择”。

---

## 1. 一句话结论

员工、项目、客户、房屋、报价、合同、工人、供应商、应收、应付、材料计划、模板、账务分类等业务对象，**不得使用原生 `<picker>`、`el-select`、`JzSelectField` 或可筛选下拉承载选择**；必须按业务对象构建专用选择器，并在来源页面使用全宽业务结果卡或明确的结果摘要展示已选事实。

统一的是：

- 选择入口；
- 业务筛选语义；
- 服务端搜索、分页和数据权限；
- 选择、取消、清除、更换；
- 加载、空、失败、无权限、上下文失效；
- 一次性回传；
- 已选结果摘要；
- 保存时服务端重新校验。

不统一的是：

- 项目、员工、客户、房屋等对象的视觉结构；
- App/Web 的页面形态；
- 项目卡片、树、表格、列表、复合选择器的具体布局。

---

## 2. 非目标与边界

1. 不构建一个包揽项目、员工、客户、房屋的“万能业务对象选择器”。
2. 不把所有固定枚举都改造成大卡片。状态、类型、优先级、付款账户等固定短字典仍可使用传统 `select` / `JzSelectField`。
3. 选择器只返回对象引用和展示摘要，不在客户端直接推进业务状态。
4. 选择结果不代表授权；保存时必须由服务端重新校验租户、角色、门店、负责人、项目参与关系、对象状态和业务前置条件。
5. 页面不得因旧业务规则展示项目编号、合同编号、员工编号等系统内部编号；遵循 `DEC-095` / `BR-060`。接口和审计字段保留，界面默认隐藏。
6. 不复制金额、成本、利润、状态机或默认业务值到选择器。
7. 本规范不改变现有业务对象、权限、金额、成本或状态事实。

---

## 3. 控件选择决策树

```text
目标值是否为后端固定枚举或稳定封闭短字典？
├─ 是
│  ├─ 普通字段：原生 select / JzSelectField / el-select
│  └─ 极少选项且是单据主判断：紧凑 radio / segment / checkbox 视觉组，保持单值语义
└─ 否
   ├─ 是否为当前父对象的不可增长子集合？
   │  ├─ 是，且总数 ≤50、随父对象一次返回、无独立搜索和权限差异
   │  │  └─ 可使用有界子集合选择；仍须显示全部候选、状态、禁用原因
   │  └─ 否：进入业务对象选择器
   └─ 业务对象选择器
      ├─ 是否远程、可增长、分页、权限过滤或需要比较？
      │  ├─ 是：专用业务对象选择器
      │  └─ 否：少量直接可见选项
      └─ 选择后是否改变表单上下文？
         └─ 是：来源页面显示全宽已选业务卡，并处理依赖失效
```

### 3.1 明确禁止的下拉场景

以下对象**无论当前租户只有 1 条还是 1 万条，一律使用专用选择器**：

- 项目；
- 员工；
- 客户；
- 房屋；
- 报价；
- 合同；
- 工人；
- 供应商/合作方；
- 应收、应付、收款、付款；
- 材料计划、材料模板、施工/付款计划模板；
- 报价分项、项目库；
- 账务分类。

禁止写法：

```vue
<!-- Web：禁止 -->
<el-select v-model="ownerId" filterable placeholder="选择负责人" />

<!-- App：禁止 -->
<JzSelectField :range="employees.map(item => item.name)" @change="pickOwner" />

<!-- App：禁止 -->
<picker :range="projects.map(item => item.name)" @change="pickProject" />
```

### 3.2 允许使用传统选择的场景

- 固定业务枚举：状态、来源、类型、优先级、方向、用途、账户类型；
- 日期、月份、时间；
- 当前对象的有界子集，例如单个项目下的阶段、施工区域、量房空间；
- 当前客户下的少量房屋，在 T15 明确声明为 `bounded-child`，且一次性返回、不会独立增长、无需搜索；
- 当前登录人获授权的少量门店，在 T15 明确声明为 `bounded-organization-list`。

“当前没有超过 20 条”不是允许下拉的理由。是否允许由数据概念和增长方式决定，不由今天的数据量决定。

## 4. 专用业务选择器必须满足的完整生命周期

```text
空态
-> 打开立即展示候选
-> 责任人/组织/状态/类别等业务导航
-> 搜索精细定位
-> 服务端分页/加载更多
-> 比较业务摘要
-> 选择或取消
-> 来源页面显示已选业务卡
-> 更换/清除
-> 上游上下文变化时清空或重新校验
-> 保存时服务端复核
```

### 4.1 入口

- 入口必须是一个明确的业务对象字段，不使用自由文本代替对象引用。
- 入口必须区分：未选、已选、加载中、失败、已锁定、失效需重新确认。
- 已选入口不得只显示名称；至少展示名称和关键状态。
- 清除必须独立可操作，不与打开选择器冲突。
- 禁用时必须说明原因，例如“已签约不可更换项目”“当前角色无权选择薪酬员工”。

### 4.2 打开首屏

- 打开后立即加载并展示候选，不能只给搜索框或空白面板。
- 首屏优先级：责任维度/组织 -> 状态或阶段 -> 类别/层级 -> 时间/金额/风险 -> 搜索。
- 搜索是精确定位，不是唯一导航。
- 默认筛选必须在界面可见并可一键重置。
- 常用对象可以提供快捷区，但不得替代完整筛选和搜索。

### 4.3 搜索与分页

- 远程业务对象必须使用服务端关键词、筛选和数据库分页。
- 默认每页 20 条，选择器列表硬上限建议 50 条。
- 使用“加载更多”或无限滚动；不允许 `findAll`、`size: 200`、拉取 40/50/200 条后在客户端过滤来冒充搜索。
- 搜索输入需防抖；请求必须可取消或使用请求序号防止旧响应覆盖新结果。
- 搜索不能清空左侧/顶部业务筛选；重置筛选和清空搜索必须是两个动作。
- 选择器返回的总数、是否还有更多数据必须来自服务端分页结果。

### 4.4 状态

每个选择器必须覆盖：

- 加载：骨架或明确加载态；
- 真实为空：区别于筛选为空、从未创建、无权限；
- 筛选为空：说明调整条件；
- 接口失败：显示“暂不可确认”并保留原选择，提供重试；
- 无权限：说明原因和可恢复路径；
- 部分失败：筛选字典失败时不得静默变成全量；
- 失效：对象已停用、已删除、跨范围或状态不再允许选择时，显示不可选原因；
- 长列表：分页、搜索和滚动稳定；
- 极端值：长名称、空名称、超大金额、0 金额、负数禁止值、状态缺失。

### 4.5 选择、取消、清除和更换

- 点击候选后返回稳定对象引用和展示摘要。
- 取消不修改原选择。
- 清除必须显式回传 `clear`。
- 选择/清除必须使用一次性通道，旧结果不得在下次进入页面时覆盖新值。
- 更换上游对象后，所有依赖下游对象必须清空并重新校验。
- 选择失败或候选刷新失败时，不得静默清空当前有效选择。

### 4.6 服务端复核

保存或提交时必须重新校验：

- 租户和企业归属；
- 角色、门店、团队和个人数据范围；
- 项目参与关系；
- 对象状态是否允许该业务动作；
- 上下游对象是否匹配；
- 金额、成本、利润和业务事实是否仍由服务端权威计算。

## 5. 业务对象专用表达

以下字段是“最低业务摘要”，不是要求把全部字段塞进卡片。按角色权限和页面任务裁剪，但不得只剩名称。

| 业务对象 | 候选必须可比较的事实 | 已选结果至少展示 |
| --- | --- | --- |
| 项目 | 名称、客户、地址、状态、阶段、设计师、项目经理、合同金额（有权限时）、正常/接管来源 | 名称、客户、地址、状态、阶段、设计师、项目经理；不得显示内部项目编号 |
| 员工 | 姓名、头像、岗位、门店、团队、在职状态 | 姓名、岗位、门店、状态；团队按业务历史口径展示；不得展示薪酬等敏感信息，不显示员工编号 |
| 客户 | 姓名、负责人、阶段、小区/地址、最近跟进 | 姓名、阶段、负责人、小区/地址、最近跟进；不得显示客户编号 |
| 房屋 | 客户归属、小区、楼栋、房号、面积、户型、状态、量房信息 | 客户、完整房屋摘要、面积、户型、状态 |
| 报价 | 客户、房屋、金额、状态、设计师、确认状态 | 客户、房屋、金额、状态、设计师；不得显示内部报价编号 |
| 合同 | 客户、房屋、金额、签约/生效状态、付款与施工计划摘要 | 客户、金额、状态、关键计划摘要；不得显示内部合同编号 |
| 工人 | 姓名、工种、状态、必要联系方式 | 姓名、工种、状态；敏感账号信息不展示 |
| 供应商/合作方 | 名称、合作状态、结算方式、账期、有效日期 | 名称、合作状态、结算方式、账期 |
| 应收 | 项目、类型、到期日、应收/已收/待收、状态 | 项目、类型、待收金额、到期日、状态 |
| 应付 | 项目、类型、对方、到期日、应付/已付/未付、状态 | 项目、类型、未付金额、到期日、状态 |
| 员工待发应付 | 员工、工资/提成类型、期间、应付/已发/待发、工资单来源 | 员工、类型、期间、待发金额、状态 |
| 原收款 | 项目、客户、核销节点、金额、日期、账户、有效/冲正状态 | 项目、客户、金额、日期、账户、核销节点 |
| 账务分类 | 一级/二级完整路径、方向、启用状态 | 完整路径、方向、启用状态 |
| 报价分项/项目库 | 分类树、品牌/系列/规格、区域、单位、价格、数量、可报价条件 | 名称、规格、区域、单位、数量和可报价阻断原因 |

### 5.1 项目选择器

- Web 使用引导式布局：左侧门店/设计师/项目经理，顶部状态/来源，主区项目卡片，搜索最后使用。
- App 使用独立项目选择页：顶部搜索，状态/来源/设计师筛选，项目卡片和加载更多。
- 打开即展示项目，不允许先要求搜索。
- 状态必须按业务状态中文展示，不允许直接显示英文枚举。
- 已选项目在表单中占整行，名称可换行，金额、负责人、阶段和操作区不得被长名称挤压。
- 1024px 下 Web 仍要可比较和可选择；更窄端按 App 形态表达。

### 5.2 员工选择器

- 必须支持姓名搜索、岗位、门店、状态筛选；团队按当前业务事实决定是否显示。
- Web 每个调用点必须显式声明 Provider 语义：普通组织目录使用 `user/employee/page`，薪酬/考勤/提成等薪酬域场景使用 `payroll/employee/page`；禁止依赖组件默认值。
- 必须使用员工对象选择器，不得在转交负责人、指派设计师、项目经理、任务负责人、付款发放工人等页面用 `el-select` / 原生 picker。
- 候选和已选摘要都不能展示工资、提成、银行卡等敏感事实。
- 按业务场景限定候选角色，例如项目经理只能选择项目经理/企业负责人，履约支持只能选择财务/企业负责人。
- 新付款、付款补录等产生新业务事实的工人场景必须锁定仅在职工人；查看历史时可展示停用状态，但不得允许重新选择。
- 即使当前员工少于 20 人，也不能以“数据少”为理由改用普通下拉。

## 6. 来源页面的选择结果展示

### 6.1 表单字段与筛选器要区分

**表单中的业务对象**：

- 使用全宽已选业务卡；
- 展示对象名称、关键状态和 2–5 个业务事实；
- 独立展示“更换”“清除”；
- 不得仅显示“已选择员工”“已选项目”“已选择工人”；
- 长名称可换行，操作区固定，不得横向溢出；
- 对下游金额、阶段、权限或计划有影响时，在结果区说明影响，但不重算正式金额。

**列表筛选中的业务对象**：

- 可以使用紧凑已选筛选条，但仍必须显示对象名称和关键状态；
- 必须明确显示当前正在使用的筛选条件，并提供清除；
- 空结果不得把筛选对象误显示成全量；
- 筛选结果数量和汇总必须继承同一筛选事实。

### 6.2 已选业务卡最低结构

```text
对象名称 + 状态
关键业务事实 1 / 关键业务事实 2 / 关键业务事实 3
[更换] [清除]
```

不得使用：

```text
已选择项目
已选择员工
已选择工人
```

这类没有业务识别能力的回显。

### 6.3 结果确认区

- 提交前必须让用户确认：选择了谁/哪个对象、对象当前状态、会影响的业务结果、失败后的恢复路径。
- 稳定单据动作按 `T17` 使用结果对象驱动的主界面，避免“表单区 + 重复预览区”。
- 结果区展示服务端权威金额或“暂不可确认”，不得用客户端计算伪装正式结果。
- 已选对象变化后，结果区必须立即标记需重新确认，直到服务端返回最新结果。

## 7. App/Web 形态差异

| 维度 | Web | App |
| --- | --- | --- |
| 选择器载体 | 对话框、抽屉、全屏选择层 | 独立选择页或全屏底部面板 |
| 项目布局 | 左侧责任维度、顶部状态/来源、主区卡片 | 顶部搜索、横向筛选、纵向卡片、加载更多 |
| 已选结果 | 全宽业务卡，支持键盘操作 | 全宽业务卡，大触控区，安全区/回退保持 |
| 筛选 | 多条件并行、桌面密度 | 条件折叠或横向滚动，首屏仍展示数据 |
| 键盘 | 焦点陷阱、Enter/Space、Escape、焦点归还 | 触控、返回键、页面恢复 |
| 长列表 | 固定选择区域滚动 + 加载更多 | 独立滚动 + 触底加载 |
| 状态 | 七态 + 1024/1280/1440 渲染 | 七态 + 多机型、弱网、真机 |

两端可以不同形态，但必须保持同一对象名称、筛选语义、状态中文、回传字段、权限结果和错误恢复语义。

---

## 8. 数据与 Provider 约束

1. 同一业务能力复用同一 Provider，不允许 App/Web 各自新增同义接口。
2. 业务选择器必须使用该业务对象的权威分页/搜索 Provider，不得依赖通用员工列表、项目列表全量拉取后再过滤。
3. Provider 必须保留租户、门店、团队、负责人、项目参与关系和角色范围裁剪。
4. 前端禁止信任传入的 `companyId`、`empId`、`ownerId`、`projectId` 作为授权依据。
5. 选择器返回摘要只能用于展示和用户确认，不能替代服务端保存时读取权威对象。
6. 新增或修改选择器前，必须填写 T15 并取得 T06/T12 业务裁决；涉及表单时补 T16，稳定单据补 T17。
7. 新增业务概念必须登记到对应端的业务概念注册表；登记状态必须与实现真实状态一致。

## 9. 自动化与验收门禁

### 9.1 静态门禁必须有语义，不得只靠变量名

必须能识别：

- `<el-select v-model="ownerId|designerId|employeeId|projectId|customerId|workerId|partnerId">`；
- `<JzSelectField :range="employees/projects/partners...">`；
- App 原生 `<picker>` 绑定远程业务对象；
- 远程对象选择器使用 `size: 200`、`findAll`、客户端全量过滤；
- 已选对象只显示“已选择某某”；
- 业务概念注册表、路径和实际实现不一致。

门禁必须提供负向自测。至少包含：

- `el-select v-model="ownerId"` 必须失败；
- `JzSelectField :range="employees.map(...)"` 必须失败；
- 项目/员工专用选择器缺失分页标记必须失败；
- 正确的固定枚举 `select` 不得误报；
- 正确的专用选择器不得误报。

### 9.2 行为验收

每个业务对象选择器至少覆盖：

- 0 条、1 条、21 条、200+ 条数据；
- 首屏展示；
- 组合筛选；

## 13. 反模式

以下行为一律禁止：

1. 项目、员工、客户、房屋等业务对象使用普通下拉。
2. 用 `filterable` 包装普通下拉冒充业务选择器。
3. 首屏只有一个搜索框。
4. 每次打开一次性加载 200 条后本地过滤。
5. 把项目状态、阶段、金额、负责人拆成多个无关联下拉。
6. 选择后只显示名称或“已选择某某”。
7. 更换客户后继续保留旧房屋、旧方案或旧报价。
8. 选择失败时静默清空原有有效选择。
9. 用选择结果直接改变业务状态或跳过服务端校验。
10. App/Web 对同一业务对象使用不同筛选含义。
11. 只做静态扫描，不做真实页面和真机验收。
12. 项目、员工选择器只显示内部编号而没有业务名称和事实。

## 2. 产品定位与目标客户

### 2.1 产品定位

`P 产品描述`：装得清不是设计渲染工具，也不是传统进销存 ERP，而是面向中小家装企业、以报价为经营中枢，连接客户、设计、合同、项目、材料、变更和财务的经营型数字化系统。

可拆成三句对外候选表达，但需产品负责人批准：

- 报价即预算：签约时看到收入、成本、毛利和变更基线。
- 项目可追溯：客户、房屋、报价、合同、施工、验收和回款形成事实链。
- 经营可复制：把设计师、项目经理和业务员的经验沉淀为企业标准。

依据：

- `docs/product/00-装得清产品与定价白皮书.md` §0.1、§2.1、§12。
- `docs/装得清整体业务体系设计说明书.md` §0、§1。
- `docs/design/00-实施总览与领域边界.md` §2。

### 2.2 目标客户

| 客群 | 典型规模 | 核心需求 | 推荐版本 | 证据 |
| --- | --- | --- | --- | --- |
| 微型团队 | 3 至 8 人、1 家门店、少量项目 | 先规范报价 | 免费版 / 基础版 | `P` 白皮书 §1.2 |
| 单店成长型装企 | 8 至 25 人、1 家门店、多项目并行 | 报价标准化、项目透明、回款可控 | 基础版 / 专业版 | `P` 白皮书 §1.2 |
| 区域多店装企 | 25 至 80 人、2 至 5 家门店 | 跨店经营、角色权限、项目风险 | 专业版 / 旗舰版 | `P` 白皮书 §1.2 |
| 连锁和集团客户 | 80 人以上、多店或多品牌 | 组织复制、供应链协同、经营驾驶舱 | 旗舰版 / 企业版 | `P` 白皮书 §1.2 |

**边界：** 当前没有已授权的真实客户画像、访谈原话或分层成交数据。以上只能作为内部产品定义，不能宣称“已服务多少家某类客户”。

### 2.3 老板购买理由

`P 产品描述`：老板购买的应是经营结果，而不是功能数量：

- 少漏一项报价，减少直接损失。
- 少一次延期和返工，提高项目毛利。
- 提前知道应收逾期，改善现金流。
- 看清门店和项目经理的真实经营质量。
- 复制优秀设计师和项目经理的做法。
- 员工离职时不丢失客户、报价和过程资产。

依据：`docs/product/00-装得清产品与定价白皮书.md` §1.3、§6.4、§9.4。

`P` 当前产品设计描述的完整链路：

```text
获客/线索 → 客户 → 房屋 → 量房 → 诉求与设计

→ 项目/阶段/任务 → 现场汇报与节点留证 → 验收
→ 材料/采购/到场 → 应收/收款/应付/付款/结算 → 经营复盘
```

## 8. 主要缺口与需要用户补充

1. 独立演示企业、演示员工、演示客户和演示项目。
2. 可重复重置的演示数据，不包含真实姓名、手机号、地址和小区。
3. 微信登录、真实 appid、隐私协议、订阅消息和业主自助链路的最终上线状态确认。
4. 客户-房屋-设计-报价-合同-项目-材料-财务全链路当前实测证据。
5. 当前 App 版本的无数据截图、成功态截图和错误态截图。
6. 真实支付、退款、开票、对账和订阅续费是否对外承诺的明确边界。

1. 品牌片头、片尾、字幕样式、封面模板和统一 CTA。
2. 产品操作录屏和讲解口径。
3. 老板、设计师、项目经理、财务四类核心角色的用户语言。
4. 真实客户访谈视频或可引用的文字证言。
5. 数据脱敏规范、画面审核规范和跨渠道发布检查清单。

## 9. 来源、版权、真实性与公开表达风险

| 风险 | 禁止或谨慎表达 | 建议处理 |
| --- | --- | --- |
| 把演示当案例 | “某某客户使用后报价效率提升 X%” | 未获授权和实测前不使用客户名及效果 |
| 行业数字未核验 | “62% 业主一定遭遇隐性增项” | 先核对原报告，发布时给年份、口径和来源 |
| 价格未定 | 把白皮书价格作为正式承诺 | 标注“内部建议价，最终以正式商务政策为准” |
| 功能规划当已上线 | “支持全部 AI、支付、开票、自动续费” | 只讲已实现并经过验证的范围 |
| 安全能力过度承诺 | “银行级安全”“绝对不泄露” | 使用具体权限和边界，等待安全测试结果 |
| 效果承诺 | “用了就减少返工”“保证利润提升” | 改为“帮助记录、提醒和核算”，结果用真实数据证明 |
| 施工知识误导 | 一刀切的材料、间距、验收因果关系 | 由专业人员复核，保留来源和适用条件 |
| 来源和版权 | 直接截取品牌 PPT、客户现场、音乐和字体 | 建立素材台账、授权文件和下架机制 |

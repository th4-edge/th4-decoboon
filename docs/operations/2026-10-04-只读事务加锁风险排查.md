# 只读事务中执行加锁查询 · 风险排查

- 批次：`RISK-AUDIT-20261004`
- 触发缺陷：commit `bdc256a`
- 排查范围：`src/main/java` 全仓
- 环境：本地 dev（只读静态分析，未改业务代码）

## 1. 触发缺陷回顾

`customer/customer/info` 在 `@Transactional(readOnly = true)` 中经 `CustomerContext.findVisible`
调用带 `@Lock(PESSIMISTIC_WRITE)` 的 `CustomerRepository.findByCustIdAndCompany_ComId`，
实际执行 `SELECT ... FOR UPDATE`。MySQL 8 在只读事务中拒绝该语句：

```text
1792 Cannot execute statement in a READ ONLY transaction
```

接口最终对外暴露为 `未定义错误信息:{0}`。已于 `bdc256a` 修复（改用数据范围查询 + 无锁回退查询）。

## 2. 排查方法

1. 扫描全部 `*Repository.java`，收集带 `@Lock(LockModeType.PESSIMISTIC_*)` 的方法；
2. 在 `src/main/java` 中定位这些方法的**调用点**（`.<method>(` 形式）；
3. 对每个调用点向上查找最近的 `@Transactional` 注解与方法签名；
4. 对「无本地事务注解」的调用点，按**上下文注入变量名**精确定位上一层调用方，继续校验其事务注解。

> 说明：正则 + 逐层上溯的启发式分析，非完整调用图；跨模块反射/动态调用不在覆盖范围。

## 4. 结论

- **修复后，全仓不存在「只读事务内执行悲观锁」的同类缺陷。**
- 27 处加锁调用全部位于写事务中，符合 JPA 悲观锁必须处于事务内的要求。

## 5. 预防建议（未实施，待决策）

1. **只读路径禁止加锁**：约定 `@Transactional(readOnly = true)` 方法只能调用无 `@Lock` 的仓储方法；
   需要在只读流程里取行锁属于设计错误，应改为写事务或去掉锁。
2. **加静态守卫**：在 `verify`/CI 中增加检查——若某 `readOnly` 方法的直接调用链命中带 `@Lock` 的仓储方法则失败。
   现有 `verify:*` 只覆盖前端；后端缺少同类守卫。
3. **仓储命名约定**：`...ForUpdate` / `findLockedBy...` 已形成惯例，建议在 `rules.md` 明确：
   **凡带 `ForUpdate`/`Locked` 的查询，调用方必须处于写事务**。

## 6. 排查局限

- 启发式静态分析，无法覆盖反射、AOP 动态代理、跨模块调用与运行时条件分支；
- 未分析 `PESSIMISTIC_READ` 以外的锁语义（本次仅发现 WRITE）；
- 未覆盖 SQL 层手写 `FOR UPDATE`（非 `@Lock` 声明）。

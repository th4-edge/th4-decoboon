# 2026-10-13 增减项存量 Approved（旧「待客户确认」）收口手册

- 依据：`DEC-068`、`T12-BIZ-20261012-004`、`IMPLEMENT-20261013-003`（`EV-240`）、业务知识库 `PLAN-20261013-001`
- 目标环境：**生产**（主机与库名以 `docs/operations/` 运维台账为准）。开发 / test 环境数据不作为依据，**无需清点、无需演练**。
- 状态：**方案与工具已就绪，尚未执行任何收口**；生产库从开发机不可达，清点与执行必须在具备生产访问权限的机器（生产应用服务器）与发布窗口内进行。
- 变更类型：**逐单业务收口**（非 SQL 批量改状态），无 DDL

## 1. 为什么必须处理

`DEC-068` 后增减项**审批通过即生效**，`Approved`（旧口径「待客户确认」）不再产生，且 App / Web 的「登记客户确认」动作已全部删除。存量 `Approved` 单据因此**卡死**：

| 事实 | 依据 |
| --- | --- |
| 不能被再次审批 | `Update.call()` 对 `status != Pending` 直接抛「变更单已处理」 |
| 不能被 App/Web 收口 | 「登记客户确认」动作已随 `DEC-068` 移除 |
| 不会自动生效 | 新流程只处理 `Pending`；`approve()` 不会被这类数据触发 |
| 后果 | 合同当前额、应收、任务、材料计划、成本**全部不联动**；BOSS 报表「已生效金额」不含这些单；业主端显示「审批中」而企业内部其实早已审批 → 双方口径不一致 |

唯一合法通道：后端保留的历史入口 `project/contract-change/customer-confirm` → `ProjectContractContext.confirmCustomer()`。

## 2. 为什么不能用 SQL 批量改状态

`Approved → 已生效` 必须经过 `settle()`，它在**同一事务**内完成：合同当前额、项目合同额、**应收生成/冲减、施工任务生成/关闭、材料计划生成/关闭、成本重算**，并做幂等保护。

> 直接 `UPDATE db_contract_change SET status='CustomerConfirmed'` 会得到"合同换了、履约没换"的半套数据，并绕过应收联动 —— **禁止**。收口只有两条合法路径：调历史入口（推荐），或按新口径重发/作废。

## 4. 执行步骤

### 步骤 0 · 清点（生产，只读；在生产应用服务器上执行）
```bash
mysql -h 127.0.0.1 -uroot -p decoboon < 2026-10-13-增减项存量Approved清点.sql > 清点结果.txt
```
产出：§1 规模、§2 逐单清单（导出 `plan.csv`，至少保留 `change_id`/`com_id`/`change_no`）、§3/§4 风险单。

### 步骤 1 · 备份（必需）
`db_contract_change`、`db_project_contract`、`db_project`、`db_finance_receivable`，并记录备份路径（`--apply` 需要它作为人工确认凭证）。

### 步骤 2 · 干跑（不写）
```bash
python3 2026-10-13-增减项存量Approved收口.py \
  --api http://<host>:8090/api --plan plan.csv --accounts accounts.json --out report-dry.csv
```
逐单输出：`计划收口 / 跳过已生效 / 跳过非待收口 / 失败`。**核对 dry-run 清单与实际业务判断一致后再进入步骤 3。**

`accounts.json`：每个企业一个企业负责人账号（需满足入口的数据范围校验）
```json
{ "<com_id>": { "phone": "19900000001", "password": "***" } }
```

### 步骤 3 · 执行
```bash
python3 2026-10-13-增减项存量Approved收口.py \
  --api http://<host>:8090/api --plan plan.csv --accounts accounts.json --out report-apply.csv \
  --apply --backup /opt/decoboon/backups/pre-approve-settle-YYYYmmdd-HHMM.sql
```
特性：逐单独立请求；单条失败不中断（退出码 1 表示有失败项）；已生效单跳过（幂等）；输出 CSV 报告。

### 步骤 4 · 收口后核对
1. 每项目：合同当前额增量 = Σ 该企业已收口单 `amount`；
2. 每单：应收已生成/冲减、任务与材料计划已生成/关闭、成本已重算（成本不完整则利润为空）—— 用清点 SQL §5 复核；
3. 业主端该单显示「已生效」并显示金额；
4. `SELECT COUNT(*) FROM db_contract_change WHERE status='Approved'` 应为 0（或等于人工保留清单）；
5. 风险单（合同额转负 / 项目已完工 / 合同关闭）**不通过脚本收口**，转人工裁决。

## 5. 已验证行为（2026-10-13）

> 说明：脚本的**编排逻辑**已用本地 mock 服务逐场景实测；HTTP 契约（`/api` 前缀 + `token` 头 + `changeId` 入参）沿用本仓库既有运维脚本范式（`docs/acceptance/*/raw/scripts/`）。
> **未经生产真实调用**：首次生产执行务必先只跑 dry-run，确认清单与实际业务判断一致再执行 `--apply`。

| 场景 | 结果 |
| --- | --- |
| dry-run（4 单：2 Approved / 1 已生效 / 1 Pending） | `跳过已生效=1、跳过非待收口=1、其余为"计划收口"`，**0 次写调用** |
| `--apply`（带备份凭证） | 仅对 2 张 Approved 调用收口 → 收口成功=2，其余跳过 |
| 重复 `--apply` | 全部 `跳过已生效`（幂等，无重复联动） |
| `--apply` 缺 `--backup` | 直接拒绝执行 |
| 缺少某企业账号 | 该单失败、其余继续（不中断），退出码 1 |
| 清点 SQL 对真实 schema | 执行退出码 0、0 错误（语法与列名已核对；生产数据量以实际执行结果为准） |

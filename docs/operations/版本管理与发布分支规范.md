# 装得清代码版本管理与发布分支规范

> 状态：强制生效  
> 生效日期：2026-09-26  
> 适用范围：`th4-decoboon` 后端、`th4-decoboon-app` 小程序、`th4-decoboon-web` Web 端  
> 生产部署步骤：见 `docs/deploy/PRODUCTION.md` 与 `docs/design/migrations/19-生产发布基线.md`

## 0. 唯一模型

日常只允许下面这条主链：

```text
feature/* ─┐
           ├─> dev ──发布候选──> test ──验收通过──> prod ──部署──> 正式 tag
fix/*     ─┘
```

生产事故才允许走独立快捷链：

```text
prod ─> hotfix/* ─> test 环境验证(按 tag) ─> prod ─> test ─> dev
```

核心约束：

1. `dev` 是默认开发集成分支，新功能和小修复都先进入 `dev`。
2. `test` 只承接准备验收的发布批次，不能直接接收 `feature/*` 或普通 `fix/*`。
3. `prod` 是生产事实分支，只能承接已通过 `test` 验收的发布提交或已验证的 `hotfix/*`。
4. `master` / `main` 不再作为日常开发入口；完成迁移后仅作历史归档。
5. 任何生产发布必须有不可变的 Git tag、可追溯产物 SHA-256、发布记录和回滚点。
6. 禁止通过强推、重置或删除历史来“修正”长期分支。

## 1. 角色与责任

| 角色 | 必须负责 |
| --- | --- |
| 需求/产品负责人 | 冻结发布范围、确认业务口径、批准上线与暂缓项 |
| 发布经理 | 维护 `dev/test/prod`、控制合并顺序、创建 tag、执行发布清单 |
| 开发人员 | 从正确基线创建短分支、完成定向验证、提交可审查变更 |
| 验收人员 | 在 `test` 对应 RC 上验证，输出通过/不通过/阻断结论 |
| DBA/运维 | 迁移审计、备份、生产部署、健康检查、回滚和恢复 |
| 业务智能体 | 对涉及业务对象、状态、权限、金额、利润等变更提供 T05/T06 口径 |

同一人可兼任多个角色，但“开发自测”不能被表述为“独立验收”。

## 2. 分支定义

### 2.1 长期分支

| 分支 | 用途 | 允许来源 | 禁止事项 |
| --- | --- | --- | --- |
| `dev` | 日常集成、默认分支 | `feature/*`、`fix/*`、事故回灌 | 直接日常提交、强推、临时绕过测试 |
| `test` | 发布候选与验收 | `dev`、`hotfix/*` 的测试验证流程 | `feature/*`/`fix/*` 直接合并、无范围冻结的发布 |
| `prod` | 生产事实源 | `test` 的正式发布、已验收 `hotfix/*` | 普通功能分支直接合并、强推、移动历史 |
| `master`/`main` | 历史归档 | 无新来源 | 所有新开发与发布操作 |

迁移完成前，`master` 可以暂时保留，但必须进入冻结状态，并在所有引用迁移完成后归档或删除。日常默认分支必须切换为 `dev`。

### 2.2 短生命周期分支

| 类型 | 适用场景 | 命名示例 | 默认来源 | 默认去向 |
| --- | --- | --- | --- | --- |
| 大功能 | 新增业务能力、跨模块改造、对象/状态/权限/金额/迁移变化 | `feature/customer-batch-import` | `dev` | `dev` |
| 小变更/修复 | 小范围缺陷、文案、局部交互、低风险配置或文档 | `fix/quote-cost-guard` | `dev` | `dev` |
| 生产热修 | 生产 P0/P1、明确单根因、时间敏感 | `hotfix/payment-callback-verify` | `prod` | `prod` 并回灌 `test/dev` |

分支名必须使用小写 ASCII、短横线分隔，不使用中文、空格、日期和姓名。推荐格式：

```text
feature/<domain>-<business-slug>
fix/<domain>-<defect-or-scope-slug>
hotfix/<incident-or-domain>-<slug>
```

如果已有需求、缺陷或事故编号，可追加到末尾，例如：

```text
feature/customer-batch-import-req-20260926-001
hotfix/payment-callback-inc-20260926-001
```

### 2.3 大功能与小修复判定

优先判为 `feature/*`：

- 新增业务对象、字段、状态机、权限规则或对外接口。
- 跨两个及以上业务域、角色或客户端流程。
- 涉及金额、成本、利润、合同、账务、权限、数据范围或数据库迁移。
- 预期超过 1 个工作日或需要多轮验收。

可判为 `fix/*`：

- 已定义行为中的缺陷修复。
- 局部 UI、文案、校验、文档或配置修正。
- 单一业务域、无新增业务语义、无 DDL、可在短时间内验证。

无法判断时默认按 `feature/*` 处理。生产环境故障且必须绕过正常发版节奏时才使用 `hotfix/*`，不能把普通需求伪装成热修。

## 3. 提交规范

使用简洁的 Conventional Commits 前缀：

```text
feat(customer): 支持批量手机号导入预览
fix(quote): 修正成本缺失时的利润展示
docs(release): 记录 2026.09.26.1 发布范围
test(project): 补充跨企业越权用例
refactor(auth): 收敛登录会话状态
perf(statistics): 优化门店业绩聚合查询
build(release): 更新发布包迁移范围
chore(repo): 调整分支检查配置
revert(payment): 回退错误的回调验签改动
```

要求：

- 一个提交只表达一个可解释的目的，禁止把不相关业务、格式化、迁移和发布记录混在一起。
- 提交信息必须说明“改了什么”；涉及业务口径时写明需求/缺陷/事故编号。
- `release: ...` 只由发布经理在发布合并提交上使用。
- 不提交密钥、生产口令、证书私钥、真实客户隐私和大体积构建产物。
- 如果变更包含数据库脚本，必须同时说明执行顺序、回滚/补偿方式和受影响的存量数据。

## 4. 日常开发与合并门禁

### 4.1 开始开发

1. 从最新 `dev` 拉取：`git fetch --prune --tags origin`。
2. 创建 `feature/*` 或 `fix/*`。
3. 功能分支如果存活超过 3 个工作日，至少每 2 个工作日同步一次 `dev`；禁止长期脱离集成分支。
4. 一个分支只服务一个需求或一个明确缺陷；发现范围扩大时拆新分支。

### 4.2 合并到 `dev`

进入 `dev` 前必须具备：

- 分支来源和目标正确。
- 需求/缺陷边界明确，风险和非目标已说明。
- 后端完成相关测试；App/Web 完成类型检查、契约检查和构建。
- 数据库迁移已单独列出并通过评审。
- 无 P0/P1 遗留问题，无未关闭的高风险安全问题。
- 至少一次独立代码复核；单人开发时由另一 Agent 或人工完成结构化复核，不能自我声明“已复核”。

`feature/*`、`fix/*` 合并到 `dev` 推荐使用 squash 或 `--no-ff` 合并提交，合并后删除短分支。禁止通过直接 push 绕过合并门禁。

### 4.3 合并到 `test`

只有发布经理可以执行 `dev -> test`。进入 `test` 前必须具备：

- 本次发布范围已冻结，清单中每个分支都有来源和验证证据。
- `dev` 上相关自动化检查通过。
- 迁移脚本已经在隔离环境完成 dry-run 或明确标记为待 DBA 演练。
- 产品、开发和验收对本次不包含的范围有一致说明。
- 已创建 RC tag，测试和构建必须对应 tag，而不是个人工作目录。

合并方式必须使用 `--no-ff`，保留发布边界。禁止 squash、rebase 或逐条 cherry-pick 正常发布提交。

### 4.4 合并到 `prod`

只有发布经理可以执行 `test -> prod`。进入 `prod` 前必须具备：

- 验收人员对 RC tag 给出明确通过结论。
- 后端、App、Web 的发布顺序和接口兼容关系已确认。
- 生产迁移、配置、密钥、证书、备份和回滚点均已检查。
- 产品负责人和发布经理批准上线。
- 所有阻断项已关闭或形成书面接受记录。

合并方式必须使用 `--no-ff`，然后创建正式不可变 tag，再从 tag 或对应制品执行生产部署。

## 5. 正常发布流程

推荐按固定节奏批量发版，不为每个小改动单独占用一次生产发布窗口。

```text
1. 冻结范围：列出本次纳入的需求、缺陷、迁移和排除项
2. 集成：所有 feature/fix 合并到 dev
3. 建候选：发布经理把 dev 合并到 test，创建 vYYYY.MM.DD.N-rcM
4. 验证：验收人员在 test 环境对 RC tag 验证
5. 修复：发现问题回 dev，修完后重新合并 test，创建新的 RC tag
6. 批准：验收通过，产品与发布经理批准上线
7. 发布：test 合并 prod，创建 vYYYY.MM.DD.N，构建并部署对应制品
8. 验证：健康检查、核心业务冒烟、日志和监控观察
9. 归档：填写发布记录，保留制品、校验和、迁移账本和回滚点
```

RC 发现缺陷后禁止移动或覆盖旧 tag，必须创建 `-rc2`、`-rc3`。正式 tag 创建后也不得移动或删除；失败发布保留 tag 并记录失败原因。

### 5.1 发布经理命令示例

以下命令仅作为流程示例，执行前必须确认本地工作区干净、远端分支存在且保护策略已配置。

```bash
git fetch --prune --tags origin

# dev -> test（RC）
git switch test
git pull --ff-only
git merge --no-ff origin/dev -m "release: 2026.09.26.1 rc1"
git push origin test
git tag -a v2026.09.26.1-rc1 -m "release candidate v2026.09.26.1-rc1"
git push origin v2026.09.26.1-rc1

# 验收通过后 test -> prod
git switch prod
git pull --ff-only
git merge --no-ff origin/test -m "release: 2026.09.26.1"
git push origin prod
git tag -a v2026.09.26.1 -m "release v2026.09.26.1"
git push origin v2026.09.26.1
```

生产部署必须从正式 tag 对应的提交构建。当前后端打包命令为 `scripts/build-release.sh`，生产部署命令为 `scripts/deploy-prod.sh`；发布前必须补齐和检查脚本要求的迁移、配置和备份条件。

### 5.2 发布记录

每次生产发布必须在 `docs/operations/releases/` 新增记录，使用 `_发布记录模板.md`。至少包含：

- Release ID、范围、排除项和批准结果。
- 每个仓库的 branch、commit、tag、制品和 SHA-256。
- 每个迁移脚本的执行顺序、执行结果和校验值。
- 备份目录、回滚版本和健康检查证据。
- 小程序上传版本号、微信后台状态和未完成事项。
- 已知风险、监控项、观察窗口和后续动作。

Release ID 在多个仓库间必须一致；App/后端/Web 可以有各自构建版本号，但必须映射到同一个发布记录。

## 6. 生产热修

仅当生产出现服务不可用、数据/权限/资金风险、支付故障或严重业务阻断时启用。普通缺陷仍走 `fix/* -> dev -> test -> prod`。

热修流程：

1. 先判断是否可通过上一稳定制品快速回滚；能安全回滚时优先回滚，不抢写代码。
2. 从 `prod` 创建 `hotfix/*`，只包含最小根因修复和必要测试。
3. 构建 RC 制品并部署到 `test` 等价环境或隔离环境验证。不要为了部署测试环境而把整个 `test` 分支合并到 `prod`。
4. 明确记录复现、根因、影响范围、失败回滚和修复证据。
5. 验证通过后，把 `hotfix/*` 合并到 `prod`，创建补丁 tag，部署并完成生产冒烟。
6. 将 `prod` 回灌 `test`，再由 `test` 回灌 `dev`，防止下次发布把热修覆盖掉。
7. 24 小时内补齐发布记录、事故记录和后续根因改进项。

热修的时间盒默认不超过 30 分钟定位、2 小时修复；超过时间盒且无法确保安全时优先回滚并转为正常修复流程。

## 7. 回滚与撤销

- 应用发布失败优先切换上一稳定制品，禁止先重置 `prod` 或强推远端分支。
- 回滚决策由发布经理执行，产品负责人参与数据或业务影响判断。
- 数据库迁移不假设自动可逆；必须事先提供正向修复 SQL、备份恢复方案和验证查询。
- 代码需要撤销时创建 `hotfix/revert-*` 分支，按热修流程重新验证；禁止直接在 `prod` 上 revert 后推送。
- 已公开的 tag、发布记录和失败证据不得删除，只能追加“已回滚/已替代”状态。

## 8. 多仓库发布顺序

后端、App、Web 是三个独立 Git 仓库，不使用同一分支跨仓库提交。一个产品发布批次需要统一 Release ID，但各仓库维护自己的 tag、制品和发布记录。

默认兼容顺序：

1. 先确认数据库迁移与应用版本兼容窗口。
2. 发布后端，完成健康检查和接口兼容验证。
3. 发布 Web；小程序则先上传体验版，验证后再提交审核/发布。
4. 如果旧客户端仍在线，后端必须先兼容旧接口，再允许新客户端发布。

任何跨仓库契约变更必须同时列出后端、App、Web 的影响和最低兼容版本。

## 9. 分支保护最低要求

所有长期分支上线到远端后必须配置以下保护；当前没有自动平台能力时，由发布经理人工执行同等检查并留痕：

| 分支 | 禁止直接推送 | 禁止强推/删除 | 合并审批 | 必需检查 |
| --- | --- | --- | --- | --- |
| `dev` | 是 | 是 | 1 人/Agent 复核 | 测试、类型检查/构建、迁移检查 |
| `test` | 是 | 是 | 发布经理 | `dev` 来源校验、RC tag、验收计划 |
| `prod` | 是 | 是 | 发布经理 + 产品批准 | `test`/热修来源校验、备份、回滚点、发布记录 |
| `master`/`main` | 是 | 是 | 不接收新合并 | 仅历史只读 |

不得将“本地构建通过”作为生产发布门禁的唯一证据。

## 10. 从当前状态迁移

当前仓库尚未建立标准长期分支，且存在未拆分的工作区改动。迁移必须按以下顺序执行，不得直接在现有脏工作区上创建发布分支：

1. **冻结入口**：宣布 `master` 停止接收新功能；所有新工作等待分支初始化或使用已确认的临时归属。
2. **盘点工作区**：后端、App 分别把未提交改动按需求/缺陷拆分；不得把多个业务混在一个提交。
3. **确定生产基线**：选最近一次已部署且有回滚记录的 commit/tag 作为 `prod` 初始基线。
4. **建立环境分支**：从生产基线创建 `prod`，从 `prod` 创建 `test`，从已通过集成验证的候选创建 `dev`。初始时三者可以同源，但不能因此直接跳过门禁。
5. **设置默认分支**：远端默认分支改为 `dev`；`test`、`prod` 设置保护，`master` 改为只读归档。
6. **修复独立仓库**：Web 必须先建立自己的 `.git` 和远端仓库，禁止在 `/Users/zhangwei/.git` 或用户主目录仓库中管理 Web 代码。
7. **启用发布前检查**：至少接入构建、测试、迁移脚本存在性、分支命名和未提交工作区检查。
8. **首次演练**：先用一个低风险 `fix/*` 完整跑通 `dev -> test -> prod`，再迁入大功能发布。

迁移期间不得删除历史 tag、用户未审阅的未提交改动或其他 Agent 的工作分支。

## 11. 发版前检查清单

### 分支与范围

- [ ] `dev`、`test`、`prod` 名称和责任正确。
- [ ] `feature/*`、`fix/*` 已全部进入 `dev`，没有游离提交。
- [ ] 本次 Release ID 已冻结，排除项已写明。
- [ ] `test` 只接收 `dev`，`prod` 只接收已验收 `test` 或已验证热修。

### 验证与制品

- [ ] 后端测试、Provider 安全扫描、迁移脚本检查通过。
- [ ] App/Web 类型检查、契约检查、构建和分包检查通过。
- [ ] 生产制品从正式 tag 构建，SHA-256 已记录。
- [ ] 微信小程序版本号、上传状态和体验版验证已记录。

### 数据与回滚

- [ ] 迁移顺序、校验值、执行人和结果已记录。
- [ ] 生产备份目录和 `SHA256SUMS` 已校验。
- [ ] 上一稳定 release 和回滚负责人明确。
- [ ] 回滚演练或至少一次只读恢复验证有证据。

### 生产观察

- [ ] 健康检查、登录、核心主链、权限负向和文件/支付关键链路已验证。
- [ ] 日志、监控、磁盘、证书和定时任务无新增异常。
- [ ] 发布记录、事故记录和工作台记录已完成。

## 12. 禁止清单

- 禁止在 `dev`、`test`、`prod`、`master` 上直接开发或直接推送。
- 禁止把 `feature/*` 直接合并到 `test` 或 `prod`。
- 禁止把 `fix/*` 当作绕过验收的热修。
- 禁止对长期分支强推、重置或删除。
- 禁止移动、复用或删除已发布 tag。
- 禁止用未经提交的工作区构建生产制品。
- 禁止把多个无关需求、紧急修复和发布文档混在同一提交。
- 禁止在没有备份、回滚点或 DBA 评估时执行生产 DDL。
- 禁止把密钥、证书私钥、真实用户数据写入仓库或发布记录。

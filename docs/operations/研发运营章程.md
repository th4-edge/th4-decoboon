# 装得清研发运营章程

> 状态：生效
> 适用范围：`th4-decoboon` 后端、Web、App、Admin 与站点
> 目标：用最小必要流程，把正确变更安全送上生产，并让每次变更可追溯、可验证、可回滚、可复盘。
> 配套记录：`docs/operations/change-records/CHG-YYYYMMDD-NNN-<slug>.md`，模板见 `docs/operations/变更记录模板.md`。

## 1. 基本原则

1. **一次变更一张记录**。聊天、worklog、发布记录都不是变更事实的唯一载体，统一变更记录才是。
2. **风险决定流程**。不是所有变更都跑全量测试；按 L0–L3 选择最小充分验证。
3. **同一提交、同一制品**。构建一次，测试和生产的制品必须一致；禁止在不同环境重新从不同分支打包。
4. **职责分离**。开发负责实现和自测，测试负责独立结论，运维负责发布与回滚，业务智能体负责业务事实。
5. **证据优先**。命令结果、真实页面、接口响应、截图、提交号、制品 SHA、发布与回滚记录才算证据。
6. **热修必须回灌**。`hotfix` 修复必须进入 `prod/test/dev`，否则下一次发布不得通过基线门禁。
7. **不为单个事故无限加检查**。只有重复回归、跨端契约或不可逆风险，才新增强制门禁；新增门禁必须有负向测试。
8. **用户保留最终裁决权**。业务口径冲突、高风险权限/金额/迁移/删除、商业取舍和正式小程序发版由用户决定。

## 2. 角色与边界

| 角色 | 核心问题 | 必须产出 | 禁止事项 |
| --- | --- | --- | --- |
| 业务智能体 | 这是不是正式业务事实？ | 规则、前置条件、例外、证据 | 不写生产代码，不代替用户裁决 |
| 产品规划 | 谁使用、解决什么、怎样算完成？ | 场景、范围、验收标准 | 不自行改变业务口径 |
| 研发 | 最小正确改动是什么？ | 代码、自测、技术证据、提交号 | 不宣布独立验收通过 |
| 测试 | 按需求和风险是否真的工作？ | 正向/反向/越权/边界验证结论 | 不替开发修改生产代码 |
| 发布/运维 | 能否安全上线、观察和回滚？ | 制品、发布记录、健康检查、回滚点 | 不修改业务语义，不绕过门禁 |
| 研发过程负责人 | 为什么同类问题再次发生？ | 反模式、最短路径、质量指标与改进建议 | 不直接修改业务代码，不凭单次经验定论 |
| 用户 | 是否接受业务和商业风险？ | 高风险批准、方向取舍、正式发版 | 不被自动流程替代 |

试运营单人阶段允许同一人兼任多个角色，但 L2/L3 的开发自测不能表述为独立验收；L0/L1 以定向验证和真实冒烟为主，不强制独立验收。

## 3. 风险分级与最小验证

| 级别 | 典型变更 | 默认验证 | 发布要求 |
| --- | --- | --- | --- |
| L0 | 纯文案、样式、无业务语义的说明 | 受影响端构建 + 目标页面检查/截图 | 1–3 分钟验证目标；只发布受影响端，不跑无关后端全量 |
| L1 | 单点 BUG、局部校验、单 Provider 修复 | 定向测试 + 编译/构建 + 受影响链路冒烟 | 正常发布；热修走事故流程 |
| L2 | 跨模块、跨端、接口契约、普通功能 | 相关回归 + 跨端对账 + 真实页面验证 | 批次发布，记录跨端影响 |
| L3 | DDL/迁移、权限、金额/成本、支付、跨租户、删除 | 全量测试 + 备份 + 回滚验证 + 用户确认 | 必须人工确认后发布 |

文案如果改变业务含义、权限表达、金额口径或客户承诺，不得按 L0 处理；不涉及业务语义的 L0 不调用业务智能体，避免无效 Token 消耗。

## 4. 统一变更记录

每次新增、修改、修复或发布，都使用 `docs/operations/change-records/` 下的同一模板。

最低必填：

- 变更 ID、风险级别、负责人、状态；
- 目标、范围、非范围；
- 验收条件；
- 影响仓库与提交号；
- 验证命令/页面证据；
- 制品 SHA、发布环境和版本；
- 回滚点与结果；
- Token/智能体运行与耗时摘要（有数据则记录，不虚构）。

L0 可以将不适用项写“不适用”；L1 及以上没有变更记录不得发布。一个记录可覆盖后端、Web、App 多仓库的同一次发布，但必须逐仓库列出提交和制品。

## 5. 正常发布

```text
建变更记录
→ 风险分级
→ dev 实现与自测
→ 进入 test 形成发布候选
→ 只构建一次
→ 测试/验收
→ prod/test/dev 同步到同一提交
→ 部署同一制品
→ 生产冒烟与观察
→ 回写变更记录与过程经验
```

- 构建要求：工作区干净，`HEAD` 已进入 `origin/test`。
- 部署要求：产物 `SOURCE_COMMIT`、`origin/prod`、`origin/test`、`origin/dev`、当前 `HEAD` 完全一致。
- 关键跨端字段进入 `docs/operations/release-contracts.json` 的契约门禁。
- 发布后必须验证实际受影响的页面或接口，不以“脚本成功”代替业务可用。

## 6. 线上事故与热修

1. 先判断能否回滚；能安全回滚时优先恢复生产。
2. 建立事故记录与变更记录，冻结影响范围，不顺手修相邻问题。
3. 从 `prod` 拉 `hotfix`，只修一个根因，补定向测试。
4. 在测试环境验证，构建不可变制品，生产部署后完成真实冒烟。
5. 将修复回灌 `prod/test/dev`；未回灌不得进行下一次发布。
6. 24 小时内完成复盘，更新事故记录、变更记录和必要的 `EXP/ANT/PATH` 过程卡。

## 7. 智能体协作与 Token 纪律

- 智能体之间通过变更记录、事故记录、需求文档和代码提交交接，不依赖聊天记忆。
- 每个角色只读取完成本职所需的上下文；已有结构化记录时不得重复全仓扫描。
- 独立检查可并行；同一检查不得换一个智能体重复做三遍。
- 达到当前风险级别的门禁即停止，不无限扩写、不无边界补检查。
- 输出只保留结论、证据、失败项和下一步；完整日志留在文件，不倾倒到对话。
- 每周统计一次：有效变更的 Token/运行成本、返工次数、一次通过率。

## 8. 质量指标与复盘

至少跟踪：

- 发布前置时间；
- 变更失败率和线上逃逸缺陷；
- 首次验收通过率与返工次数；
- 平均恢复时间（MTTR）；
- 热修回灌遗漏次数；
- 每个被接受变更的 Token/智能体成本。

每周做一次 30 分钟内复盘；只沉淀有证据、可复用、带适用边界的过程经验。

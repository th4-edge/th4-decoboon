# 装得清版本号管理规范

- 生效日期：2026-10-28
- 当前正式版本：`1.0.72`
- 当前本地集成候选：`1.0.73`
- 当前正式版依据：微信小程序 `1.0.72 / versionCode 172` 已由用户确认正式发布；`1.0.73` 用于本轮本地全功能验证，未发布
- 适用范围：App、后端、Web、Admin 以及统一发布记录

## 1. 为什么需要两套版本

装得清是“一后端多客户端”，不能只用某一个客户端的版本号代表所有组件：

- 产品发布版本：面向业务和用户的统一版本，正式版为 `1.0.72`，本地集成候选为 `1.0.73`；
- 组件版本：每个仓库自己的可构建、可部署版本；
- 构建号：该组件实际构建对应的 Git 短 SHA；
- Release ID：跨仓库发布记录的唯一标识，格式沿用 `vYYYY.MM.DD.N`。

同一个产品发布版本可以对应不同组件版本，但必须映射到同一个 Release ID 和同一份发布记录。

## 3. 唯一真源

| 组件 | 组件版本唯一真源 | 产品版本来源 |
|---|---|---|
| App | `th4-decoboon-app/package.json#version` | 同组件版本；同步到 `src/manifest.json` |
| 后端 | `th4-decoboon/pom.xml#project.version` | 同组件版本；Maven 写入 JAR Implementation-Version |
| Web | `th4-decoboon-web/package.json#version` | `VITE_RELEASE_VERSION` |
| Admin | `th4-decoboon-admin/package.json#version` | `VITE_RELEASE_VERSION` |

禁止：

- 在页面或常量里另写一套组件版本；
- 用 `package.json` 中的历史版本代替实际部署版本；
- 用 App 版本号覆盖 Web/Admin 自身组件版本；
- 用 Git tag 代替发布记录或制品 SHA-256。

## 4. 版本变化规则

### 4.1 协调发布

App、后端、Web、Admin 同一批次正式发布时：

- 产品发布版本取 App 正式版本，例如 `1.0.72`；
- 后端、Admin 使用 `1.0.72`；
- Web 保留 Web 3.x 产品线，使用 `3.0.72`；
- 创建同一 Release ID 和统一发布记录；
- 四个组件分别记录 branch、commit、构建号、制品和回滚点。

### 4.2 单组件修复

只修复一个组件时：

- 只更新该组件版本和构建号；
- 产品正式版本是否递增由是否存在用户可见变更决定；
- 发布记录必须写明未变化组件仍对应的版本；
- 不得把一个后端的内部热修伪写成新的 App 正式版本。

### 4.3 小程序正式发布

Codex 只负责构建、开发版上传和体验版验证。用户在微信公众平台完成正式发布后，必须：

1. 将 App 产品版本登记为正式版本；
2. 将 `prod` 分支快进到正式发布提交；
3. 让 `test`、`prod` 指向同一正式发布提交；
4. 在统一发布记录中写入 App 版本、versionCode、正式发布时间和微信后台状态。

## 5. 构建号与可追溯性

- Web/Admin 在 Vite 构建时注入 Git 短 SHA；
- 后端发布包写入 `SOURCE_COMMIT`；
- App 发布记录写入构建提交和 `upload-info-*.json` SHA-256；
- 所有组件必须能通过 Release ID 回查到实际提交；
- 构建号不是产品版本，不得展示为用户需理解的业务版本。

## 6. 展示原则

- App：我的 → 关于装得清展示版本；
- Web：侧栏显示 `Web v3.0.72 · 发布 1.0.72`；
- Admin：侧栏显示 `v1.0.72 · 发布 1.0.72`；
- 后端：通过 `platform/system/status` 的 `appVersion` 读取构建版本；
- 构建号放在 `title`、运维详情或发布记录中，不占用普通用户主要视线。

## 7. 禁止事项

- 禁止版本号只存在发布文档、不进入组件制品；
- 禁止把 `1.0.0` 这类占位版本用于所有正式发布；
- 禁止通过移动 tag 修正版本；
- 禁止让用户通过询问研发才能知道当前 Web/Admin 版本；
- 禁止 `dev/test/prod` 使用不同版本却声称来自同一发布批次。

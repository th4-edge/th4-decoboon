# 试运营单人轻量协作与发版规范

> 状态：当前强制生效  
> 适用范围：`th4-decoboon`、`th4-decoboon-admin`、`th4-decoboon-app`、`th4-decoboon-web`  
> 优先级：与本文件之外的 lane、RC、验收或发布细则冲突时，以本文件为准  
> 适用阶段：装得清试运营、研发协作人数为 1 人、以成本和响应速度优先

## 1. 目标

在不牺牲生产安全、数据安全、权限和金额正确性的前提下，减少：

- 跨 lane 交接；
- 重复阅读规范和历史 worklog；
- 每次小修复都跑全量测试；
- 每次小改动都创建 feature/fix/RC/正式 tag；
- 重复发布记录和验收文档；
- 过长的工具输出、全文读取和多轮确认。

## 2. Token 与阅读纪律

默认只读：

1. `AGENTS.md`；
2. 本文件；
3. `_系统/协作/工作约定.md` 的“近期改动”；
4. 与任务直接相关的源码和最近一次发布记录。

只有以下情况才读 lane、完整 worklog、shared、rules 大段或历史验收：

- 用户明确要求；
- 生产事故；
- 大功能或重大架构调整；
- 涉及权限、金额、成本、支付、迁移或数据删除。

读取规则：

- 先 `rg -n` 定位，再读 30–80 行；
- 不全文 cat 大文件；
- 不重复读取已读内容；
- 工具输出只取结论、失败行和 diff；
- 同一问题最多推测一轮，禁止盲目连续试错。

## 3. 协作简化

默认不要求：

- 绑定 lane 或 session；
- 产品 -> 开发 -> 验收三 lane 交接；
- 独立 acceptance 智能体；
- 每次任务更新 shared/worklog；
- 为小修复创建交接包。

以下场景仍必须停下确认或走业务咨询：

- 新业务对象、状态机、角色权限或数据范围；
- 成本、利润、合同金额、支付、资源点数收费；
- 数据库 DDL、生产数据迁移或删除；
- 对外承诺、客户案例或宣传口径。

## 4. 变更分级与验证

| 级别 | 典型变更 | 默认验证 | 发版 |
| --- | --- | --- | --- |
| L0 | 文案、文档、无运行时逻辑的配置说明 | 不跑测试；UI 变更做构建 | 可随批次直接提交 |
| L1 | 单点 BUG、局部校验、局部 UI、单 Provider 修复 | 定向测试 + 编译/类型检查/构建 | 可直接从 `dev` 发布 |
| L2 | 跨模块功能、读模型聚合、批量逻辑、普通迁移 | 定向测试 + 核心回归 + 全量测试 | 按批次发布 |
| L3 | DDL、权限、金额/成本/利润、支付、跨租户、数据删除 | 全量测试 + 备份 + 回滚点 + 用户确认 | 发布后必须冒烟和观察 |

默认规则：

- 小修复不强制全量测试；
- UI 只做 `type-check` 和目标构建，不做所有端回归；
- 后端 L1 先跑单个测试类，改动稳定后再决定是否跑全量；
- 全量测试用于批量发版、L2/L3 或用户明确要求；
- 生产故障热修优先最短路径，但仍保留 L3 安全底线。

## 5. Git 与发版

### 5.1 分支

- `dev` 是默认工作分支；试运营单人阶段允许直接提交和推送 `dev`。
- 大功能可按需创建 `feature/*`，不强制。
- 生产事故才使用 `hotfix/*`。
- 小修复不要求单独分支，不要求 `--no-ff`。
- `test`、`prod` 在发布成功后快速同步到 `dev` 当前提交；不需要每次重放完整合并链。

### 5.2 发布

- L0/L1：提交 `dev` -> 构建相关产物 -> 部署 -> 冒烟 -> 快进同步 `test/prod`。
- L2：在 `dev` 完成测试后按批次发布。
- L3：必须从已确认提交构建，执行备份和回滚检查。
- 生产部署统一使用 `scripts/deploy-prod.sh`，失败自动回滚。
- Admin 静态资源可独立发布，后端和 Admin 无需强行同 tag。
- tag 按天、周或批次创建；不为每个 BUG 创建 RC 和正式 tag。
- 如用户要求严格控制，可临时恢复标准分支和 tag 流程。

## 6. 生产安全底线

无论单人模式如何简化，以下不能省：

- 生产部署必须保留上一稳定 release；
- DDL 或迁移必须备份、校验和记录；
- 密钥、证书、真实用户数据不得进入仓库；
- 金额、成本、权限、支付、跨租户必须有定向验证；
- 生产发布后必须有健康检查和核心路径冒烟；
- 同一事故单次最多发布 1 次，禁止循环重试；
- 无法回滚或无法验证时，只记录并等待人工处理。

## 7. 记录简化

- 同一话题只在 `_系统/协作/工作约定.md` 追加一行；
- 发布批次写一份 `docs/operations/releases/*.md`；
- 生产事故只归档可处理异常；
- 小修复不单独写验收报告；
- 开发和验收可由同一人在试运营阶段完成，但不得把“自测通过”写成“独立验收通过”。

## 8. 恢复严格流程的条件

出现以下任一条件时，恢复完整 lane、RC、独立验收和全量门禁：

- 研发协作者超过 1 人；
- 外部付费客户规模扩大或进入正式商用；
- 生产事故频率明显升高；
- 出现资金、权限、隐私或数据迁移高风险变更；
- 用户明确要求恢复严格流程。

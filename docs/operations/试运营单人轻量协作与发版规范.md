# 试运营单人轻量协作与发版规范

> 状态：当前强制生效  
> 适用范围：`th4-decoboon`、`th4-decoboon-admin`、`th4-decoboon-app`、`th4-decoboon-web`  
> 优先级：与本文件之外的 lane、RC、验收或发布细则冲突时，以本文件为准  
> 适用阶段：装得清试运营、研发协作人数为 1 人、以成本和响应速度优先

## 1. 目标

在不牺牲生产安全、数据安全、权限和金额正确性的前提下，减少：

- 跨 lane 交接；
- 重复阅读规范和历史 worklog；
- 每次小修复都跑全量测试；
- 每次小改动都创建 feature/fix/RC/正式 tag；
- 重复发布记录和验收文档；
- 过长的工具输出、全文读取和多轮确认。

## 1.1 研发运营章程与统一变更记录

- 本章程不替代具体技术规范，只统一“如何分级、谁来负责、如何交接、何时可以发布”。
- 每次变更按 `docs/operations/研发运营章程.md` 分为 L0–L3，并使用 `docs/operations/变更记录模板.md` 建立 `CHG-*` 记录。
- L0 纯文案/样式只跑受影响端构建和目标页面检查；L1 做定向测试与冒烟；L2/L3 再按风险升级。
- 发布必须使用同一制品，满足分支基线与跨端契约门禁；禁止为单次事故无限增加检查。

## 2. Token 与阅读纪律

默认只读：

1. `AGENTS.md`；
2. `docs/operations/研发运营章程.md`；
3. `docs/operations/变更记录模板.md`；
4. 本文件；
5. `_系统/任务/当前工作.md`（仅在有活跃任务时读取）；
6. 与任务直接相关的源码和最近一次发布记录。

只有以下情况才读 lane、完整 worklog、shared、rules 大段或历史验收：

- 用户明确要求；
- 生产事故；
- 大功能或重大架构调整；
- 涉及权限、金额、成本、支付、迁移或数据删除。

读取规则：

- 先 `rg -n` 定位，再读 30–80 行；
- 不全文 cat 大文件；
- 不重复读取已读内容；
- 工具输出只取结论、失败行和 diff；
- 同一问题最多推测一轮，禁止盲目连续试错。

## 2.1 默认工具预算

- L0：最多读 3 个文件、约 100 行；不跑测试。
- L1：最多读 8 个文件；一次定向测试 + 一次构建/类型检查。
- 工具输出只保留失败行、关键结论和 diff；编译日志默认 `tail -50`。
- 同一轮只做一次实现、一次验证、一次修复；超过预算说明问题复杂，需先收敛范围。
- 全量日志、完整文件和大段历史只在失败、事故或 L2/L3 变更时读取。

## 3. 协作简化

默认不要求：

- 绑定 lane 或 session；
- 产品 -> 开发 -> 验收三 lane 交接；
- 独立 acceptance 智能体；
- 每次任务更新 shared/worklog；
- 为小修复创建交接包。

以下场景仍必须停下确认或走业务咨询：

- 新业务对象、状态机、角色权限或数据范围；
- 成本、利润、合同金额、支付、资源点数收费；
- 数据库 DDL、生产数据迁移或删除；
- 对外承诺、客户案例或宣传口径。

## 3.1 产品问题剥离与专项会话（强制）

产品体系梳理、角色/业务矩阵、需求澄清和日常研发中发现关键问题时，不在当前梳理会话中顺手修复，必须：

1. 在 `docs/product/issue-governance/registry.json` 登记问题；
2. 在 `docs/product/issue-governance/issues/` 建立单项档案，记录事实、证据、影响、临时处理和待裁决问题；
3. 为问题创建或使用专项会话，先由装得清业务智能体按 T05 → T06/T12 完成裁决；
4. 取得裁决后才创建研发任务；研发完成不等于验收通过，必须进入独立验收；
5. 研发和验收完成后，回写问题档案、registry、业务知识库和相关产品矩阵。

适用问题至少包括：角色、权限、数据范围、总部/门店等组织派生身份、金额/成本/利润、支付、工资、凭证、跨端事实不一致、跨业务域缺陷。

未取得 T06/T12 前，只允许调查、影响分析和文档沉淀，不得修改代码、权限、DDL 或业务语义。当前产品梳理会话只保留问题链接，不承担该问题的研发闭环。

## 3.2 一后端多客户端同源门禁（强制）

- App、Web、Admin 共用唯一业务后端；同一能力必须复用同一 Provider，不得新增客户端专用同义业务接口。
- 跨端能力开发前必须列出：Provider、App 调用、Web 调用、权限、状态、金额/成本、异常恢复、两端验证。
- 前端只允许展现与交互差异；禁止硬编码正式业务值、复制业务公式、状态机或权限判断。
- 正式值缺失或接口失败必须显示“暂不可确认”并提供恢复路径，禁止用 0、22、空数组等兜底。
- 线上问题必须先完成生产闭环，再处理相邻扩展；不得用领域完整性阻塞当前事故修复。
- 只验证一端不得声称跨端对齐。完整规范见 `docs/design/31-一后端多端同源架构规范.md`。

## 4. 变更分级与验证

| 级别 | 典型变更 | 默认验证 | 发版 |
| --- | --- | --- | --- |
| L0 | 文案、文档、无运行时逻辑的配置说明 | 不跑测试；UI 变更做构建 | 可随批次直接提交 |
| L1 | 单点 BUG、局部校验、局部 UI、单 Provider 修复 | 定向测试 + 编译/类型检查/构建 | 可直接从 `dev` 发布 |
| L2 | 跨模块功能、读模型聚合、批量逻辑、普通迁移 | 定向测试 + 核心回归 + 全量测试 | 按批次发布 |
| L3 | DDL、权限、金额/成本/利润、支付、跨租户、数据删除 | 全量测试 + 备份 + 回滚点 + 用户确认 | 发布后必须冒烟和观察 |

默认规则：

- 小修复不强制全量测试；
- UI 只做 `type-check` 和目标构建，不做所有端回归；
- 后端 L1 先跑单个测试类，改动稳定后再决定是否跑全量；
- 全量测试用于批量发版、L2/L3 或用户明确要求；
- 生产故障热修优先最短路径，但仍保留 L3 安全底线。

## 5. Git 与发版

### 5.1 分支

- `dev` 是默认工作分支；试运营单人阶段允许直接提交和推送 `dev`。
- 大功能可按需创建 `feature/*`，不强制。
- 生产事故才使用 `hotfix/*`。
- 小修复不要求单独分支，不要求 `--no-ff`。
- `test`、`prod` 在发布成功后快速同步到 `dev` 当前提交；不需要每次重放完整合并链。

### 5.2 发布

- L0/L1：提交 `dev` -> 构建相关产物 -> 部署 -> 冒烟 -> 快进同步 `test/prod`。
- L2：在 `dev` 完成测试后按批次发布。
- L3：必须从已确认提交构建，执行备份和回滚检查。
- 生产部署统一使用 `scripts/deploy-prod.sh`，失败自动回滚。
- Admin 静态资源可独立发布，后端和 Admin 无需强行同 tag。
- tag 按天、周或批次创建；不为每个 BUG 创建 RC 和正式 tag。
- 如用户要求严格控制，可临时恢复标准分支和 tag 流程。

### 5.2.1 后端发版制品与类加载器门禁（强制）

- 生产后端 boot JAR 必须是 **thin JAR**：
  - `Main-Class: com.th4.edge.Application`；
  - 应用类位于 JAR 根目录；
  - 依赖通过 `Class-Path: ../lib/*` 加载；
  - 禁止包含 `BOOT-INF/classes/`。
- `spring-boot-maven-plugin` 的 repackage 产物必须使用独立 classifier（当前为 `boot`）。严禁把 `target/th4-decoboon-1.0.0-boot.jar` 或任何 Spring Boot loader JAR 放入生产 release。
- 生产发版只能使用 `scripts/build-release.sh` 生成的 assembly 包；即使手工组装 release，也必须先执行 `scripts/verify-release-boot-jar.py <release.tar.gz>`。
- `scripts/build-release.sh` 和 `scripts/deploy-prod.sh` 都必须执行制品门禁；任一处校验失败立即停止发版。
- 门禁至少校验：boot 目录仅有一个应用 JAR、`Main-Class` 正确、JAR 根存在 `com/th4/edge/Application.class`、不得包含 `BOOT-INF/classes/`。
- 事故依据（2026-10-24）：生产误用 Spring Boot repackage JAR，导致 `th4-framework` 与业务类分属不同 ClassLoader；JWT 校验中的 `Class.forName(audience)` 无法加载 `Employee`，异常被框架统一转换为 `tokenIsUndefined`，小程序与 Web 登录后均无法读取会话。

### 5.3 小程序发版边界

- Codex 只负责小程序构建、开发版上传和体验版发布/验证。
- 正式版提交审核与发布必须由用户本人在微信公众平台完成；Codex 不得点击“提交审核”或“发布”正式版，也不得代填审核测试账号。
- 上传完成后记录版本号、上传信息文件和体验版验证结果，停止在正式版动作之前。

## 6. 生产安全底线

无论单人模式如何简化，以下不能省：

- 生产部署必须保留上一稳定 release；
- DDL 或迁移必须备份、校验和记录；
- 密钥、证书、真实用户数据不得进入仓库；
- 金额、成本、权限、支付、跨租户必须有定向验证；
- 生产发布后必须有健康检查和核心路径冒烟；后端发布还必须验证登录后 `/api/auth/session/info` 返回成功会话，不能只验证未登录时的 `tokenIsUndefined`；
- 同一事故单次最多发布 1 次，禁止循环重试；
- 无法回滚或无法验证时，只记录并等待人工处理。

## 7. 记录简化

- 同一话题以 `CHG-*` 记录事实，`_系统/任务/当前工作.md` 只保留当前状态；历史按月或阶段归档，不追加到工作约定；
- 发布批次写一份 `docs/operations/releases/*.md`；
- 生产事故只归档可处理异常；
- 小修复不单独写验收报告；
- 开发和验收可由同一人在试运营阶段完成，但不得把“自测通过”写成“独立验收通过”。

## 8. 恢复严格流程的条件

出现以下任一条件时，恢复完整 lane、RC、独立验收和全量门禁：

- 研发协作者超过 1 人；
- 外部付费客户规模扩大或进入正式商用；
- 生产事故频率明显升高；
- 出现资金、权限、隐私或数据迁移高风险变更；
- 用户明确要求恢复严格流程。

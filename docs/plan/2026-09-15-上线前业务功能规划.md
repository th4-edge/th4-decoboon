> 规划日期：2026-09-15  
> 规划 lane：product-planning  
> 文档性质：基于当前工作区的**建议稿**，不是用户已批准的上线范围  
> 证据口径：当前源码、Provider 路由、实体、前端页面、测试执行结果、设计文档和联调记录

## 0. 执行摘要

### 0.1 当前结论

当前系统已经不是“只有设计、没有实现”的状态。后端已有 472 个 `com.th4.edge.decoboon` Java 文件、147 个 `com.th4.edge.tenant` Java 文件、176 条 `@Service` Provider 路由、65 个 `@Entity`；客户、房屋、量房、设计、报价、合同、项目、任务、材料、收付款、统计和订阅均有真实模型或已注册能力。当前 `mvn -o -q test` 为 **44 tests / 0 failures / 0 errors**。

但“主链可跑”仍不等于“可以上线”。当前最关键的断点不是继续增加业务模块，而是以下上线级缺口：

1. **业主同频链路没有后端身份闭环**。系统能生成业主邀请 token，但没有接受邀请、绑定业主身份、按项目授权、业主读取“我的家”和业主确认验收的完整后端能力。
2. **私有文件可能被公开访问**。`/upload/**` 被静态资源处理器整体暴露，谈单 PPT 下载入口也无需登录；报价、现场照片、合同材料等文件可能跨企业读取。
3. **生产配置和数据库发布不具备上线基线**。仓库中的生产配置仍指向本机数据库、明文凭证、`ddl-auto=update`，且没有完整生产 DDL 迁移链。
4. **小程序正式发布入口与合规未收口**。构建产物当前写入局域网 HTTP 地址；用户协议/隐私政策只有文本无落地页；声明了定位权限但没有实际调用。
5. **少数业务 Provider 未纳入统一安全/订阅过滤器**。尤其是 `project/task/update`，仍可能在订阅失效后绕过企业级写入闸门。
6. **在线支付具备代码骨架但未完成真实商户验证**。微信支付商户参数默认空，无法证明预下单、回调验签、履约和续费可在真实环境闭环。

### 0.2 建议首发形态

建议把 1～2 周首发明确定义为：

> **邀请制种子客户试用版：小程序单端，业主可绑定本人项目并完成阶段验收，企业内员工按四级数据范围使用核心经营主链；生产环境、文件权限和微信合规先封口；暂不对外承诺在线支付、自动续费、订阅消息、发票退款、PC 管理端。**

这个建议优先保证“真实项目能安全地给种子客户使用”，而不是把所有商业化能力一次性放出。若用户要求首发即收费或首发即提供微信订阅消息，则范围必须扩展为 **2～3 周**，不能仍按 1～2 周承诺。

### 0.3 推荐 1～2 周“上线前必做范围”

建议纳入：

- `PP-01` 业主身份、邀请接受和项目级授权。
- `PP-02` 业主“我的家”、进度、动态、验收确认。
- `PP-04` 私有文件访问控制。
- `PP-05` 生产配置、数据库迁移、备份与回滚基线。
- `PP-06` 小程序正式域名、HTTPS、隐私与用户协议合规。
- `PP-07` Provider 登录元数据与订阅权益封口。
- 对已实现的合同变更到履约主链执行真实环境回归，不重做业务设计。

条件纳入：

- `PP-08` 若首发收费，必须完成一个真实支付渠道；建议只支持微信支付，不同时做支付宝和自动续费。
- `PP-03` 若首发必须做到微信外的履约触达，必须完成至少“待验收、验收结果”两类订阅消息；否则首发只能承诺站内提醒和业主主动打开查看。

明确不纳入本轮：

- PC 管理端。
- 现场质量巡检、整改复检。
- 发票、退款、自动续费。
- AI/存储/短信/API 用量计费。
- 高级供应链对账、软装电器全量数据运营。

| PP-09 | 客户、房屋、项目、合同生命周期收口 | 4 | 4 | 4 | 4 | 4 | 状态快照和收尾规则不清会造成历史数据不一致 | P1 | 完工/流失/停工恢复链路不完整 |
| PP-10 | 合同变更到履约的真实 E2E 回归 | 4 | 3 | 4 | 4 | 4 | 页面入口、历史数据和并发确认仍未实测 | P1 | 单元测试已有，缺真实页面和数据库回归 |
| PP-11 | 现场巡检、问题、整改、复检闭环 | 4 | 3 | 2 | 3 | 4 | 新模型和流程较重，容易挤压首发稳定性 | P2 | 设计有，实体和 Provider 无 |
| PP-12 | 项目发票、退款、对账和财务审计 | 4 | 3 | 2 | 2 | 5 | 税务、退款和资金事实不可逆；需要明确财务规则 | P1 | 商业化售后需要，当前无对象链 |
| PP-13 | 用量计费、续费提醒和权益运营 | 4 | 2 | 2 | 2 | 3 | 需先确定各资源计量口径、价格和供应商成本 | P1 | 当前套餐权益可拦截，但用量和提醒未闭环 |
| PP-14 | 软装、电器主数据与模板运营 | 3 | 2 | 4 | 4 | 2 | 数据来源、品牌授权和运营责任未定 | P2 | 真实目录软装和电器数据为空 |
| PP-15 | PC 管理端与批量运营工作台 | 3 | 2 | 1 | 1 | 4 | 新端工程量大，渠道优先级未经用户确认 | P2 | 目录为空；是否为首发渠道需用户拍板 |

### 3.1 评分说明

- P0 表示不解决就不能安全地让真实种子客户使用，或不能完成正式提审/上线。
- “P0 条件”只在首发承诺付费或微信外主动触达时成立。
- P1 表示不影响首发试用，但会显著影响商业化、续费或规模化运营。
- P2 表示当前不上线也不破坏核心主链，适合首发稳定后迭代。

## 4. 建议的上线前范围

### 4.1 本期建议做什么

#### A. 业主同频闭环

目标链路：

```text
员工可见项目
  -> 生成一次性业主邀请 token
  -> 业主微信授权手机号
  -> 服务端校验 token、有效期、手机号和项目归属
  -> 绑定业主身份与项目授权
  -> 业主只能查看本人住房、进度、公开动态、待确认验收
  -> 业主确认或驳回验收
  -> 服务端推进阶段/项目状态并向内部人员生成通知
```

必须覆盖：

- token 只能消费一次，过期、撤销、已使用均不可再次接受。
- 一个微信用户可绑定多个项目；同一项目支持业务决定的多业主/共同业主，但必须显式建模，不能靠手机号猜测。
- 业主不能读取企业客户列表、报价成本、供应商价格、内部财务、员工名单或其他工地。
- 业主对验收只有确认/驳回，不得修改任务、材料、合同、金额或项目状态。
- 业主访问其他项目 ID 必须返回“资源不存在或无权访问”，不能泄露对象是否存在。
- 所有响应仍是实体、实体集合或分页；不新增 DTO/VO/请求包装类型。

#### B. 私有文件访问

必须覆盖：

- 取消 `/upload/**` 对整目录的无条件公开映射，或明确拆分公开静态资源与私有业务文件目录。
- 报价附件、设计方案、现场照片、合同/变更材料、谈单 PPT 通过带授权校验的 Provider 或短期签名 URL 访问。
- 文件记录必须有 `company`、业务归属和最小访问范围；不能只靠文件路径保护。
- 文件名不可作为授权依据；跨企业、跨项目、过期签名均必须拒绝。
- 现有已公开的 URL 要有迁移/失效策略，不能只修新文件。

#### C. Provider 安全与订阅权益封口

必须覆盖：

- 登录 Provider 继承 `Security`，当前员工通过 `@User` 注入。
- 业务写 Provider 必须进入 `SubscriptionAccessRequestFilter`；订阅到期、冻结、关闭后只允许查询和续费。
- `project/task/update`、`project/acceptance/page` 等未声明 `Security` 的接口完成元数据收口；公开的登录、邀请接受和支付回调要明确标注为白名单例外。
- 不靠前端隐藏按钮或页面守卫替代服务端校验。

#### D. 生产发布与数据安全

必须覆盖：

- 生产数据库、Redis、微信小程序/支付密钥全部环境变量或密钥管理注入，仓库不保留可用默认密钥。
- 生产用 `ddl-auto=validate` 或明确的发布模式，启用版本化迁移工具；至少补齐项目归属、合同变更、文件和业主授权相关迁移。
- 备份、恢复、回滚、发布前后校验和错误告警有可执行 Runbook。
- 生产 profile、端口、上传目录、日志目录、HTTPS 终止和域名配置不依赖开发机绝对路径。
- 上线前以真实生产等价库执行一次全量迁移和恢复演练。

#### E. 小程序正式发布与合规

必须覆盖：

- `VITE_API_BASE` 使用正式 HTTPS 域名，并确认微信合法 request/upload/download 域名。
- 用户协议、隐私政策有可访问页面和版本号；登录前可选择拒绝和退出；同意版本/时间可审计。
- 移除未使用的 `getLocation` 声明，或先完成定位功能和对应隐私披露。
- 小程序 appid、服务类目、隐私保护指引、客服、备案、图标与版本信息对齐。
- 真机验证弱网、冷启动、分包、登录、401、上传下载和分包返回。

#### F. 单一支付渠道，仅在首发收费时进入

若首发收费，建议只支持微信支付：

- 配置真实商户号、证书、API v3 密钥、回调地址和合法域名。
- 验证 `order/create -> order/prepay -> requestPayment -> callback -> fulfillOrder -> subscription/info` 全链路。
- 验证金额、订单号、商户号、openId、回调签名、重复回调和异常查询。
- 明确退款和开票的过渡方案；没有系统能力时必须由用户确认人工流程和对外口径。
- 支付宝、自动续费、多支付方式不在本轮。

### 4.2 本期明确不做什么

- 不重做已经存在的统一报价、合同、项目和财务模型。
- 不在本轮引入 DTO、VO、Controller 或新的 Request 包装层。
- 不同时开发 PC 管理端和微信支付之外的第二个支付渠道。
- 不做质量巡检、整改复检、AI 用量计费、开放 API、渠道分销。
- 不用前端隐藏按钮代替服务端权限。
- 不把硬编码密钥、生产密码或测试账号写入规划文档或代码示例。
- 不把“业主验收 UI 已画出来”当作“业主验收已可用”。

### 4.3 上线最低可接受标准

建议把下面十条作为“可上线”的最低门槛：

1. 新企业能完成注册、试用和企业资料建立。
2. BOSS 能邀请员工，员工能接受邀请并按角色进入。
3. 客户、房屋、量房、设计、报价、合同、项目、任务、材料、应收、收款、应付、付款主链能走通。
4. 业主能接受邀请并绑定项目，只能看到本人项目。
5. 业主能查看进度、公开动态和验收，能确认或驳回验收。
6. 项目、房屋、客户和合同关键状态只能由领域动作推进。
7. BOSS/店长/团队负责人/普通员工四角色、跨企业、伪造参数、越权详情/更新/删除均有自动化或验收证据。
8. 订阅到期后的写操作在服务端被统一拒绝。
9. 私有文件无法通过猜测路径跨企业访问。
10. 微信正式域名、HTTPS、appid、隐私协议、用户协议和小程序构建全部可用。

尚未具备支付、退款、发票、主动推送能力时，产品页面和对外话术必须明确“暂不支持”或“人工处理”，不能展示不可完成的入口。

## 6. 权限与合规要求

### 6.1 四角色数据权限矩阵

| 功能/对象 | BOSS | 门店店长 | 团队负责人 | 普通员工 |
| --- | --- | --- | --- | --- |
| 客户/房屋 | 当前企业全量 | 当前门店 | 当前团队 | 本人负责或显式授权 |
| 设计/报价 | 当前企业全量 | 当前门店 | 当前团队 | 创建人、负责人或设计参与关系 |
| 合同/项目 | 当前企业全量 | 当前门店归属项目 | 当前团队归属项目 | 项目参与关系（设计师/PM/履约专员等） |
| 合同变更 | 审批/客户确认/查看 | 当前门店相关项目只读或按授权动作 | 当前团队相关项目只读或按授权动作 | 只读或业务动作指定的项目范围 |
| 任务/材料 | 当前企业全量 | 当前门店项目 | 当前团队项目 | 本人项目参与关系 |
| 验收 | 查看、确认、督办 | 当前门店项目 | 当前团队项目 | PM/设计师按项目动作提交或复核，不能越过项目范围 |
| 财务 | 当前企业全量 | 当前门店只读或按已确认财务授权 | 当前团队不自动获得企业财务全量 | 无企业财务权限，仅查看被授权的业务摘要 |
| 订阅 | 创建、续费、支付 | 无写权限 | 无写权限 | 无写权限 |
| 私有文件 | 当前企业授权对象 | 当前门店授权对象 | 当前团队授权对象 | 当前项目/本人业务对象 |

说明：具体门店和团队角色能力必须继续以 `EmployeeRole` 和现有数据权限设计为真源；上表是上线验收口径，不替代服务端实现。

### 6.2 业主授权要求

业主不是员工角色，不能套用 `Self` 权限，也不能通过伪造 `customerId/projectId/companyId` 扩权。建议统一使用“当前微信身份 + 项目授权关系”：

- 业主只能读取被显式绑定的项目。
- 业主只能读取该项目对客户公开的动态、进度、验收和必要合同摘要。
- 业主不能读取企业内部客户列表、员工列表、报价成本、供应商价格、财务明细。
- 业主确认验收必须校验：当前身份、项目授权、验收单归属、待确认状态、重复提交。
- 支持的项目数量和共同业主规则必须由用户确认，不能通过手机号或姓名模糊匹配猜测。

### 6.3 强制负向测试

每个涉及个人、门店、团队、企业或项目归属的功能必须覆盖：

| 测试场景 | 期望 |
| --- | --- |
| BOSS 查询/更新本企业对象 | 成功；跨企业对象不可见 |
| 店长查询/更新本门店对象 | 成功；同企业其他门店不可见 |
| 团队负责人查询/更新本团队对象 | 成功；同企业其他团队不可见 |
| 普通员工查询/更新本人负责对象 | 成功；同团队无关对象不可见 |
| 项目经理读取非本人项目 | 拒绝，不泄露存在性 |
| 伪造 `companyId/storeId/teamId/ownerId` | 服务端覆盖或拒绝，不能改变实际归属 |
| 伪造业务主键访问详情 | 返回 404 或统一无权限结果 |
| 越权更新/删除 | 数据不变，返回 404/403 |
| 未登录访问业务 Provider | 返回 401，公开白名单除外 |
| 订阅到期写操作 | 查询可用；新增、邀请、修改、审批、验收、导出等按产品规则拒绝 |
| 业主跨项目访问 | 返回 404，不泄露其他项目 |
| 业主 token 重放/过期 | 拒绝，不产生重复授权 |
| 私有文件无登录/跨企业 | 拒绝，不返回文件内容 |
| 重复合同变更确认 | 不重复生成任务、材料计划、应收或成本记录 |

### 6.4 合规检查清单

- 小程序正式 appid、服务类目、备案和主体信息一致。
- 生产 API 为 HTTPS 合法域名，微信后台 request/upload/download 域名已配置。
- 用户协议、隐私政策、儿童/未成年人政策（如适用）、客服和投诉渠道可访问。
- 隐私政策实际覆盖手机号、微信身份、位置、照片、合同、财务和日志数据。
- 不声明未使用的定位权限；不在日志输出完整手机号、身份证、合同全文、支付密钥。
- 文件访问有租户和项目边界，公开文件与私有文件物理或逻辑隔离。
- 备份、恢复、数据导出和账号注销/数据删除流程有责任人。
- 生产密钥通过环境变量或密钥管理系统注入，不进入仓库和构建产物。

## 7. 开放问题（只能由用户拍板）

以下问题不能在规划阶段用技术假设替代业务决策：

1. **首发模式**：是邀请制种子客户试用，还是正式收费上线？若收费，微信支付商户是否已具备真实商户号和证书？
2. **首发渠道**：是否只发微信小程序？`th4-decoboon-web` 为空，PC 管理端是否为首发必须项？
3. **业主模型**：一个项目只有一名业主，还是支持夫妻/家庭共同业主？同一微信用户是否可同时关联多企业、多客户、多项目？
4. **验收效力**：业主一键确认是仅作为项目推进依据，还是需要形成可对外主张的签认/电子签证据？若需要法律效力，必须另行确定签名、实名、留证和撤回规则。
5. **支付与售后**：是否首发收费；支持微信支付、支付宝还是对公转账；退款、发票、自动续费和到期宽限期采用什么政策？
6. **触达承诺**：首发是否承诺微信订阅消息？若不承诺，业主如何知道有待验收，站内消息和电话是否可接受？
7. **数据与发布**：生产域名、云资源、数据库备份责任、隐私主体和数据处理者如何确定？迁移过程中历史客户/项目无负责人时由谁确认归属？
8. **首发功能边界**：白皮书中的软装/电器数据、质量巡检、财务发票/退款是否必须在上线首日出现？

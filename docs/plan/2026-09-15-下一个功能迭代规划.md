# 装得清下一个功能迭代规划

> 规划日期：2026-09-15
> 角色：Management Agent（当前同时承担调查、拆解与质量把关）
> 事实基线：工作区实际文件、可枚举 Provider 路由、现有测试与 `docs/运行错误记录-*.md`
> 代码变更边界：本规划只新增文档，不修改 `src/`

## 0. 执行结论

### 0.1 当前判断

客户-房屋主链已经具备真实可用雏形，并完成了以下正链路验证：

```text
客户 -> 房屋 -> 量房 -> 设计/目录 -> 报价 -> 客户确认
-> 合同 -> 生效 -> 项目 -> 材料计划/采购/到场/应付 -> 应收
```

证据包括 `docs/运行错误记录-2026-09-14报价响应与状态联调.md` 中真实客户、三套房屋、报价、合同、项目、三条应收计划和材料应付的联调记录，以及当前工程中已经注册的 43 条 `project/*` Provider 路由。

但是，目前不能把“正链路跑通”等同于“可用于下一轮功能扩张”。调查发现 3 组 P0 存量问题：

1. `pack` 和 `quote` 的部分路由未继承 `Security`，并直接信任前端传入的 `companyId`；其中 `pack/template/save` 可按请求写入任意企业。
2. 项目域 14 个 JPA 模型均未接入 `@DataPermission`，项目域没有一处使用 `DataScopeSpecification`；36 个文件、49 处使用 `findById(...)`，其中不少是在加载后补人工角色判断，违反最高优先级规范。
3. `Property.status`、`Project.status`、`Contract.status` 等关键状态存在直接由普通更新接口覆盖的入口，破坏“状态只能由领域上下文推进”的不变量。

### 0.2 下一迭代决策

用户已确认本轮不是二选一，而是同时完成：

> **C0：租户隔离与客户-房屋-合同主链权限封口**
> **C1：合同变更到任务、材料、成本、应收的履约闭环**

执行原则：

- C0 是 C1 的前置闸门，无权限边界的变更联动不能进入开发验收。
- C1 只做“客户已确认变更如何进入履约”这一条主链，不扩展到质量巡检、真实支付、开票或供应链高级能力。
- 预计 **10 个工作日，最多 2 个自然周**；C0 与 C1 的准备、测试夹具和前端适配需要并行推进。
- 如果第 7 个工作日 C0 权限矩阵仍未全部通过，C1 只保留已完成的模型和服务端骨架，不合并未验证的现场执行逻辑。

## 3. 存量缺陷与规范偏离（必须优先）

### P0-1：部分 `pack/quote` 路由没有登录保护，并信任前端 `companyId`

事实：

- `pack/template/save` 接口没有继承 `Security`：[Save 接口](../../src/main/java/com/th4/edge/decoboon/pack/service/templates/save/Save.java)（第 9 行）；实现直接使用前端 `companyId` 作为落库企业：[Save 实现](../../src/main/java/com/th4/edge/decoboon/pack/service/templates/save/support/Save.java)（第 36、53 行）。
- 同样问题存在于 `pack/template/info`、`pack/template/update`。
- `pack/line/page`、`pack/section/page`、`pack/template-item/page`、`quote/line/page` 的接口没有继承 `Security`，实现直接在 Criteria 请求上设置前端传入企业：[pack/line 接口](../../src/main/java/com/th4/edge/decoboon/pack/service/lines/page/Page.java)（第 9 行）、[pack/line 实现](../../src/main/java/com/th4/edge/decoboon/pack/service/lines/page/support/Page.java)（第 45、49 行）、[quote/line 接口](../../src/main/java/com/th4/edge/decoboon/quote/service/lines/page/Page.java)（第 7 行）、[quote/line 实现](../../src/main/java/com/th4/edge/decoboon/quote/service/lines/page/support/Page.java)（第 37、41 行）。
- 这直接违反 [`rules.md`](../../rules.md) §0.1：企业、角色、数据范围必须从登录员工重新推导，前端 `companyId` 只能视为不可信候选值。

风险：

- 未登录请求可能访问或修改企业套餐数据。
- 已登录的普通员工可通过替换 `companyId` 跨企业读取或写入。
- `pack/template/save` 是最严重路径，因为它不是“先查再判断”，而是直接使用请求中的企业落库。

### P0-2：项目主链未接入统一数据权限

事实：

- `project/model/*` 的 14 个模型没有任何 `@DataPermission`。
- `Project`、`ProjectContract`、`ContractLine`、`ContractChange`、`ContractChangeItem`、`PurchaseOrder`、`GoodsReceipt`、`MaterialPlan`、`ProjectStage`、`ProjectTask`、`Acceptance`、`TaskNode`、`ProjectReport` 等对象没有标准 `owner/store/team` 归属快照，或只有 `createdBy/manager/designer` 等业务角色。
- 项目域 36 个文件存在 `findById(...)`，共 49 处；项目域使用 `DataScopeSpecification` 的文件数为 0。
- `ProjectAccessContext` 通过 `if` 枚举 Boss、Finance、StoreManager、TeamLeader、Designer、Manager、Support、Customer.owner、Quote.createdBy 判断可见性：[ProjectAccessContext.java](../../src/main/java/com/th4/edge/decoboon/project/context/ProjectAccessContext.java)（第 25 行）。这套判断对当前页面可用，但没有统一进入 `DataScope`，也不满足规范要求的同查询权限条件。
- `project/contract/update` 直接 `findById(contractId)`，随后只校验同企业和“Boss/Designer”角色，没有校验该设计师是否属于合同对应项目：[Update.java](../../src/main/java/com/th4/edge/decoboon/project/service/contract/update/support/Update.java)（第 77 行）。

风险：

- 通用 `{model}-{service}` 路由对没有 `@DataPermission` 的模型不会自动应用企业、门店、团队、本人范围。
- 同一企业内其他门店、团队或无关设计师存在通过伪造主键触达合同、项目或采购对象的可能。
- 权限规则分散在多个 Provider 后，后续新增动作容易漏校验。
- 当前 `mvn test` 没有覆盖项目主链四角色、跨企业、伪造参数和越权详情/更新/删除。

### P0-3：关键状态可由普通更新接口直接覆盖

事实：

- `property/property/update` 直接接收 `PropertyStatus status` 并落库：[Update.java](../../src/main/java/com/th4/edge/decoboon/property/service/properties/update/support/Update.java)（第 63 行）。
- `project/project/update` 直接接收 `ProjectStatus status` 并落库：[Update.java](../../src/main/java/com/th4/edge/decoboon/project/service/projects/update/support/Update.java)（第 80 行）。
- 合同更新、项目状态、房屋状态与 `ProjectContext.refreshProject()`、合同上下文共同存在写入入口，状态所有权不唯一。

影响：

- 房屋可从任意状态直接跳到 `Completed`，绕过量房、报价、签约和施工闸门。
- 项目可跳过任务、验收和结算直接改状态，影响看板、应收、应付和结算。
- 与 [`docs/design/14-客户报价项目状态驱动逻辑.md`](../design/14-客户报价项目状态驱动逻辑.md) “状态只能由领域上下文推进”的原则冲突。

### P1-1：合同变更目前只同步金额和应收

`ProjectContractContext.confirmCustomer(...)` 当前只完成：

- 更新 `ProjectContract.currentAmount`；
- 更新 `Project.contractAmount`；
- 新增或冲减 `Receivable`；
- 将变更单改为 `CustomerConfirmed`。

证据：[ProjectContractContext.java](../../src/main/java/com/th4/edge/decoboon/project/context/ProjectContractContext.java)（第 129 行）。

没有根据变更行继续处理：

- 施工增减项对应的 `ProjectTask`；
- 材料增减项对应的 `MaterialPlan`；
- 成本变化对应的项目预算/成本；
- 后续采购需求、应付预测和项目执行变更状态。

因此正链路能签合同，但客户确认变更后，履约事实仍可能停留在原合同。

### P1-2：测试依赖外部种子数据，当前不满足可重复回归

当前结果：

```text
Tests run: 38
Failures: 0
Errors: 3
```

失败点：

- `DecoboonClosedLoopTest` 在测试库没有套餐时 `orElseThrow`；[DecoboonClosedLoopTest.java](../../src/test/java/com/th4/edge/decoboon/DecoboonClosedLoopTest.java)（第 81 行）。
- `FinanceClosedLoopTest` 依赖指定手机号账号和已有项目；[FinanceClosedLoopTest.java](../../src/test/java/com/th4/edge/decoboon/finance/FinanceClosedLoopTest.java)（第 61 行）。
- 测试配置连接本机 MySQL `zqsmart`；[application-test.yml](../../src/main/resources/application-test.yml)（第 6 行）。

这是“测试环境不可自举”的存量缺陷，不是业务断言失败。

## 5. 优先级评分

### 5.1 评分标准

所有维度按 1～5 分，分数越高越优先。权重如下：

| 维度 | 权重 | 说明 |
| --- | ---: | --- |
| 业务价值 | 30% | 对报价、合同、项目、回款、利润闭环的直接价值 |
| 用户阻塞程度 | 25% | 是否阻碍真实客户继续使用或上线 |
| 权限与安全风险 | 20% | 跨企业、越权、伪造参数、敏感数据暴露风险 |
| 实现成本可行性 | 15% | 5 分表示 1～2 周内可闭环，1 分表示明显超期 |
| 依赖与风险可控性 | 10% | 5 分表示前置少、现有模型可承接 |

### 5.2 评分矩阵

| ID | 候选 | 业务价值 | 用户阻塞 | 权限风险 | 成本可行 | 依赖可控 | 加权分 | 排序 |
| --- | --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |

### 6.3 C1：合同变更到履约闭环

#### A. 变更确认事务

客户确认变更时，在同一个事务内完成：

```text
ContractChange CustomerConfirmed
  -> 更新 ProjectContract.currentAmount
  -> 更新 Project.contractAmount
  -> 同步 Receivable
  -> 生成/调整施工任务
  -> 生成/调整材料计划
  -> 计算项目成本变化
  -> 形成后续采购需求或调整已存在的材料计划
```

重复确认、重复回调和重复提交必须幂等，不能重复生成任务、材料计划或应收。

#### B. 变更行到履约对象映射

| 变更类型 | 施工任务 | 材料计划 | 成本/应付 |
| --- | --- | --- | --- |
| 新增 | 新增任务，关联变更行 | 新增材料计划，关联变更行 | 记录成本增量，形成后续采购/应付预测 |
| 取消 | 取消未开始任务；已执行任务进入变更/差异处理 | 关闭未采购材料计划；已到场材料进入差异处理 | 记录成本冲减或差异 |
| 替换 | 原任务/材料计划保留历史并建立替代关系 | 原计划关闭或替换 | 记录新旧成本和差价 |
| 调整数量 | 调整未完成任务数量或生成执行变更 | 调整未采购数量 | 重算项目预算成本 |
| 调整价格 | 不直接改写历史报价行 | 形成价格/成本差异 | 重算项目预计成本，保留原合同行 |

规则：

- 已确认变更只允许读取，不允许 Provider 直接改写 `QuoteLine`、已确认报价或原合同行。
- 施工任务和材料计划必须能追溯 `ContractChangeItem`。
- 待审批、已驳回、已取消变更不得进入项目执行、采购和应收计划。
- 项目执行端只读取客户已确认的变更事实。
- 变更同步失败时整个事务回滚，不允许只改合同金额而现场仍保持旧范围。

### 9.2 历史合同、项目、采购的组织归属回填解释

这里的“回填”不是让前端补填，也不是根据当前登录人临时猜测，而是对已经存在的历史数据补上数据权限需要的固定快照字段：

```text
历史 Project / ProjectContract / PurchaseOrder
  -> 找到它关联的 Property
  -> company = Property.company
  -> owner   = Property.owner
  -> store   = Property.store
  -> team    = Property.team
```

具体规则：

1. 有 `Property` 时，一律以 `Property` 为根。
2. `Property.owner` 为空时，才读取同一企业下的 `Customer.owner`。
3. 合同没有直接 `Property` 时，通过 `Quote` 或 `Customer` 找到对应房屋后继承。
4. 采购没有直接 `Property` 时，通过 `MaterialPlan -> Project -> Property` 继承。
5. 子对象由最近父对象继承，不能跨企业复制归属。
6. 没有房屋、负责人为空、房屋与客户归属冲突、父对象链路断裂时，不自动写入；生成迁移问题清单，人工确认后补填。
7. 回填完成后执行全量校验：
   - 所有记录都有 `company`；
   - `store/team/owner` 要么已解析，要么在问题清单中；
   - 不存在跨企业继承；
   - 新数据保存时仍由服务端重新计算，不信任历史值。

示例：

```text
Property 3001
  company = A公司
  owner   = 张销售
  store   = 合肥店
  team    = 销售一组

Project 9001 -> Property 3001
  回填 company=A公司 / owner=张销售 / store=合肥店 / team=销售一组

PurchaseOrder 7001 -> MaterialPlan 6001 -> Project 9001 -> Property 3001
  同样继承上述四个归属字段

若 Property 3001 没有 owner，而 Customer.owner 也是空：
  记录 Project 9001 到“归属待确认”报告，不写入任何猜测的负责人
```

### 9.3 剩余风险

| 编号 | 风险 | 处理 |
| --- | --- | --- |

| R2 | 历史数据缺少房屋或负责人 | 迁移报告列出明细；不阻塞 C0 代码测试，但阻塞对应历史数据上线 |

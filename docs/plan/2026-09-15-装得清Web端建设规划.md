# 装得清 Web 端建设规划

> 规划日期：2026-09-15  
> 目标工程：`th4-decoboon-web`  
> 当前状态：目标目录为空，无 `package.json`、页面、路由或构建配置  
> 固定技术栈：Vite + Vue 3 + TypeScript + Element Plus  
> 规划 lane：product-planning  
> 文档性质：建设建议稿，不是已经批准的首版范围  
> 约束：不修改 `src/**`、不修改小程序、不创建 Web 代码

## 0. 执行结论

### 0.1 产品定位

Web 端建议定位为：

> **面向装企内部员工的桌面经营与履约管理台。**

与小程序分工：

| 端 | 主要职责 |
| --- | --- |
| 小程序 | 微信登录、现场移动操作、拍照/上传、任务推进、日报、验收、消息、业主同频、随时审批 |
| Web | 大批量列表、复杂筛选、主数据维护、报价/合同编辑、项目全局管理、财务核算、组织权限、经营分析、批量操作 |
| 业主端 | 首版继续只使用小程序，不进入 Web |

Web 不复制小程序的所有页面。移动端现场高频动作仍以小程序为准，Web 负责查看、汇总、编辑和大范围管理，并提供桌面端更高效的表单、表格、抽屉和批量操作。

### 0.2 当前基础

- 小程序已有 9 类角色：BOSS、店长、团队负责人、业务员、设计师、项目经理、项目支持、财务、业主。
- 小程序已有 62 个页面：主包 12 页、11 个分包共 50 页。
- 小程序已有角色矩阵、工作台动作、页面路由守卫、Provider 领域 API、协议/隐私页、业主授权和私有文件授权能力。
- 后端当前有 192 条 `@Service` Provider、67 个 JPA `@Entity`，主要业务 API 已存在；本次盘点执行 `mvn -o -q test` 为 72 tests、0 failures、0 errors。
- 本次小程序验证执行 `npm run verify:mp-weixin` 通过：类型检查通过、微信小程序构建通过、分包检查通过；主包 378,198 B、最大分包 154,634 B、总包 1,103,656 B。
- 后端当前登录主体是 `Credentials` + `Employee`，不是旧文档所述的 th4-admin `User` 表。
- 后端目前只有 `CredType.Wx`，没有密码字段、没有 Web 登录 Provider，也没有 `@Role/@View` 注册。
- 后端框架 `Login` 会把返回的 `User` 交给 `SecurityManager.sign(...)` 生成 Token；当前可用，但生产前必须补齐签名密钥、过期、注销和密码变更失效策略。

### 0.3 建议首版边界

Web 首版只服务企业内部员工，业主明确不进入。建议优先完成：

1. Web 登录、退出、当前用户、首次设置密码、修改密码、忘记密码/重置。
2. Web 后台壳、角色菜单、路由守卫、权限指令、统一错误处理和会话恢复。
3. 工作台、通知、企业/成员/邀请/角色管理。
4. 客户、房屋、量房、跟进。
5. 项目库、套餐模板、报价、合同、合同变更。
6. 设计诉求、方案、谈单 PPT。
7. 项目、阶段、排期、任务、现场日报、验收。
8. 应收、收款、应付、付款、台账、项目财务和结算。
9. 供应商、供货价、库存、出入库、采购和到场的基础操作。
10. 经营驾驶舱、业绩、目标、风险和站内通知。

首版建议只做列表/详情壳的部分：

- 高级经营分析下钻。
- 订阅订单、续费、退款、开票和渠道管理。
- 复杂供应链报表和劳务结算。
- 项目文件批量归档。

首版明确不做：

- 业主 Web 端。
- 移动端 OCR、定位打卡、拍照上传、微信授权替代。
- 质量巡检、问题整改、复检独立闭环。
- AI、API、ERP、Webhook、SSO。
- 多组织/SaaS 运营端。
- 短信之外的第二套找回密码渠道。

## 2. Web 信息架构

### 2.1 URL 与菜单原则

遵循后端 `rules.md` 的 `@Role / @View` 注册规范：

```text
role.home + @View.path = Web URL
```

建议角色首页：

| 角色 | role.home | Web 定位 |
| --- | --- | --- |
| BOSS | `/boss` | 全局经营和系统管理 |
| 店长 | `/store-manager` | 门店经营和设计调度 |
| 团队负责人 | `/team-leader` | 团队客户和项目协作 |
| 业务员 | `/marketer` | 个人客户和转化 |
| 设计师 | `/designer` | 量房、设计、报价和签约 |
| 项目经理 | `/pm` | 本人项目履约 |
| 项目支持 | `/project-support` | 材料、库存、采购、现场协同 |
| 财务 | `/finance` | 账务和结算 |

不注册业主 Web 首页，不注册 `customer` 的 `@View`。

实际 URL 示例：

```text
BOSS 客户管理：      /boss/crm/customers
店长客户管理：       /store-manager/crm/customers
设计师报价列表：     /designer/trade/quotes
项目经理项目详情：   /pm/projects/{projectId}
财务应收计划：       /finance/finance/receivables
```

菜单和路由由后端 `@View` 下发，前端只保留一个静态兜底路由映射和权限守卫。不得在前端维护第二套与后端不一致的角色菜单真源。

## 3. 角色体系与 Web 适用范围

### 3.1 Web 角色范围

| 角色 | 是否进入首版 | Web 适用范围 | 明确不做 |
| --- | --- | --- | --- |
| BOSS | 是 | 全量经营、组织、财务、订阅、权限和审批 | 不替代小程序微信授权 |
| 店长 | 是 | 门店客户/项目/团队/报价，财务只读 | 不进入企业级订阅管理 |
| 团队负责人 | 是 | 团队客户、项目、报价、派单、业绩 | 不管理全公司财务和门店 |
| 业务员 | 是 | 本人客户、跟进、量房、报价查看、本人项目 | 不编辑施工和财务 |
| 设计师 | 是 | 量房、设计、报价、合同签约、项目排期 | 不处理现场任务执行 |
| 项目经理 | 是 | 本人项目、阶段、任务、日报、验收、材料 | 不管理客户归属和财务核销 |
| 项目支持 | 是 | 项目、库存、采购、到场、退料、劳务协同 | 不修改合同金额 |
| 财务 | 是 | 应收、收款、应付、付款、台账、结算、项目财务 | 不编辑报价和项目执行状态 |
| 业主 | **否** | 继续使用小程序完成进度查看和验收 | 不提供 Web 登录、不进入 Web 菜单 |

业主是否进入首版：**明确不进入**。原因：

- 业主属于外部门户，Web 需要独立的域名、登录、隐私、文件和权限边界。
- 当前业主 API 只向 `CustomerAccess` 公开项目摘要、动态和验收，不适合直接暴露企业后台壳。
- 首版 Web 优先做企业内部效率和财务，不增加外部门户的认证与合规范围。

### 3.2 菜单与权限双层控制

1. 后端 `@View` 决定当前角色可见菜单。
2. Web 路由守卫检查登录态和路由能力。
3. `v-permission` 控制按钮/动作。
4. 服务端仍以当前 `Employee` 重新加载企业、角色和数据范围。
5. 菜单不可见不等于接口安全；隐藏按钮不构成权限。

## 6. Web 工程方案

### 6.1 基础依赖

固定依赖：

- `vite`
- `vue`
- `vue-router`
- `pinia`
- `axios`
- `element-plus`
- `@element-plus/icons-vue`
- `typescript`
- `vue-tsc`

可选但建议：

- `vitest`：权限、格式化、API 解码测试。
- `playwright`：登录、菜单、核心页面 E2E。
- `echarts`：经营驾驶舱图表，必须经过用户确认后再加入。

### 6.2 路由设计

`src/router/routes.ts` 只维护页面组件映射和静态兜底元数据，菜单真源来自后端 `@View`：

```ts
interface AppRouteMeta {
  title: string
  componentKey: string
  capability?: string
  menuKey?: string
  keepAlive?: boolean
}
```

路由守卫：

1. 无 token 且非公开路由 -> `/login`。
2. 有 token 但无当前用户 -> 调 `auth/session/info` 恢复会话。
3. 当前用户无菜单/能力 -> 跳转 403 或角色首页。
4. 动态路由加载失败 -> 404，不白屏。
5. 401 -> 清空 Pinia 会话、清 token、跳登录。
6. 403 -> 保留登录态、显示无权限页。
7. 订阅错误码 -> 显示续费提示，不误判为登录失效。

### 6.3 Pinia

```text
stores/session.ts
  token / credentials / employee / company / roles / permissions / ready

stores/permission.ts
  menus / routes / capabilities / loaded

stores/app.ts
  sidebar / breadcrumbs / current company / theme
```

数据权限和角色数据不进入前端 store 作为安全判断依据；store 只用于体验优化。

### 6.4 Axios

统一响应协议：

```json
{
  "success": true,
  "data": {},
  "errorCode": { "code": "400", "message": "..." }
}
```

要求：

- `baseURL = VITE_API_BASE`。
- 请求头携带框架配置的 token 字段。
- 响应拦截成功时直接返回 `data`。
- 401/业务 token 失效统一清理会话，只跳登录一次。
- 403 显示无权限，不清理登录态。
- 5xx 显示可重试错误，不自动重放写请求。
- 订阅模块错误显示升级/续费提示。
- 上传和下载复用统一鉴权；私有文件先调用 `file/private/grant`。

### 6.5 API 类型与禁止项

- TypeScript 类型名与领域实体一致，如 `Customer`、`Quote`、`Project`、`Page<Customer>`。
- 禁止新增 `XxxRequest`、`XxxResponse`、`XxxVO`、`XxxDTO` 作为后端接口包装。
- Provider 入参仍是实体或实体字段；筛选参数可作为函数参数或实体 `Partial`，不得形成独立传输层模型。
- 响应字段由后端 `@Properties` 控制；Web 不通过移除白名单来拿全量实体。
- 如 Web 需要与小程序不同的字段集合，新增明确的领域读服务/Provider 路由，返回实体、实体集合或分页并单独使用 `@Properties`。

### 6.6 环境变量


## 7. User 登录方案

### 7.1 当前实现事实

- `Credentials` 是当前平台登录主体，实现框架 `User<Long>`，当前 `CredType` 只有 `Wx`。
- `Employee` 也是框架 `User<Long>`，业务 Provider 通过 `@User Employee` 获取当前员工。
- 当前微信登录 Provider 是 `auth/session/login`，非微信用户首次登录需要手机号授权。
- `UserIdentityContext` 负责按微信 openId/phone 识别凭证、绑定 Employee、记录登录时间。
- `UserSecurityLog` 已有登录、绑定、加入、退出、风控日志模型，含 `ip` 和 `userAgent` 字段。
- 当前没有密码字段、密码哈希算法、登录失败计数、锁定时间、首次设置密码或 Password Provider。
- 当前没有 `auth/session/logout` Provider，也没有 Web 登录契约。
- 当前没有 `@Role/@View` 配置，Web 菜单无法由现有后端注册。

### 7.2 账号模型决策

建议采用：

> **一个手机号对应一个 `Credentials` 平台账户；Web 密码和微信身份绑定到同一账户；Employee 继续承载企业成员权限，不新增平行 User 表。**

原因：

- 避免一个员工同时存在“微信账户”和“Web 账户”两条 `Credentials`，导致企业归属、安全日志和会话不一致。
- 避免新增第二套租户关系。
- 符合当前代码中 `Credentials.employee` 和 `Employee.company/role` 的现实结构。
- 符合规则中“服务/实体驱动”的模型，不需要 DTO。

兼容规则：

- 老微信用户首次使用 Web：手机号匹配已有 `Credentials`，通过短信验证码验证手机号后设置密码。
- Web 新设置密码：写入同一 `Credentials`，不创建第二个账号。
- 以后再次微信登录：仍按 openId/phone 找到该账户，不因 Web 密码存在而生成新账户。
- 如果后续出现多个微信应用或多个 unionId 身份，再引入独立的 `CredentialIdentity` 关联实体；首版不同时实现两套模型。

### 7.3 `Credentials` 扩展建议

建议新增字段：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `passwordHash` | `String(255)` | BCrypt/Argon2 哈希，禁止明文 |
| `passwordAlgo` | `String(32)` | `bcrypt`、`argon2id`，用于未来迁移 |
| `passwordUpdatedAt` | `LocalDateTime` | 密码最后更新时间 |
| `failedLoginCount` | `Integer` | 连续失败次数，默认 0 |
| `lockedUntil` | `LocalDateTime` | 锁定截止时间 |
| `lastPasswordLoginAt` | `LocalDateTime` | 最近密码登录时间 |
| `mustChangePassword` | `Boolean` | 首次登录/重置后是否必须改密 |
| `passwordVersion` | `Integer` | 密码版本，用于会话失效策略 |

`Credentials` 仍保留：

- `phone`：手机号登录名，规范化后唯一。
- `status`：Active / Disabled / Deleted。
- `employee`：企业成员对象关联。
- `lastTime`：最近任意成功登录时间。

禁止：

- 不在 `Credentials` 中保存明文密码。
- 不使用 MD5/SHA1/sha256(username+password)。
- 不把 `passwordHash`、`failedLoginCount`、`lockedUntil` 放进任何 Provider 响应白名单。
- 不用 `@JsonIgnore` 隐藏密码；使用 `@Properties` 明确白名单。
- 不通过 `@Role(user=true)` 自动创建初始密码为角色 id 的账号。

### 7.4 密码算法与策略

推荐第一阶段：

- Spring `DelegatingPasswordEncoder`。
- 默认 `BCryptPasswordEncoder(12)`，存储格式带 `{bcrypt}` 前缀。
- 如团队要求 Argon2id，再引入 BouncyCastle，存储 `{argon2}` 并保留 `passwordAlgo`。
- BCrypt 支持未来通过 DelegatingPasswordEncoder 平滑升级。

密码策略建议：

- 长度 8～64，推荐至少 10。
- 至少包含字母和数字；是否要求特殊字符由用户确认。
- 禁止等于手机号、手机号后 6 位、身份证后 6 位、`123456` 等常见弱密码。
- 新旧密码不得相同。
- 密码只在 HTTPS 请求体中传输；日志和异常不得记录明文。
- 连续 5 次失败锁定 15 分钟；管理员解冻或等待自动解锁。
- 成功后清零失败次数和锁定期。

### 7.5 登录流程

推荐新增 Provider 路由：

```text
auth/session/web-login
```

- 公开入口，不继承 `Security`，加入 `ProviderSecurityValidator.PUBLIC_ROUTES` 白名单。
- Request 类型为 `Credentials`。
- 通过 `@AutoInject @NotEmpty @Length` 获取 `telNo`、`password`，不定义 Request 类。
- 按手机号查询账户，校验 `UserStatus`、Employee 状态和 `lockedUntil`。
- `BCrypt/Argon2` 校验密码。
- 失败：更新失败次数、锁定期，记录 `SecurityAction.Login` 失败日志。
- 成功：清零失败、更新 `lastPasswordLoginAt`/`lastTime`，记录成功日志。
- 返回 `Employee` 作为框架签名主体；没有有效员工时，Web 首版拒绝进入内部后台。
- 框架 `LoginTokenResponseFilter` 自动签名 Token，前端只接收 Token 和会话实体。

错误文案统一为“手机号或密码错误”，避免账号枚举。

### 7.6 退出、当前用户和会话

```text
auth/session/logout
```

- 继承框架 `Logout` 和业务 `Security` 标记。
- 调 `SecurityManager.logout` 或由框架 `LogoutTokenResponseFilter` 处理当前 Token 移除。
- 前端清空 Pinia、token 和用户信息。
- 记录 `SecurityAction.Logout`。

```text
auth/session/info
```

- 复用当前 Provider 路由。
- Web 端返回当前 `Credentials` + `Employee` + 企业/门店/团队最小白名单。
- 不返回密码、锁定次数、openId 等敏感字段。
- 每次页面刷新/首次进入后台调用一次。

Web Token 存储建议：

- 优先短时 Token + 内存/Pinia。
- 如需刷新恢复，使用 `sessionStorage` 而不是 `localStorage`。
- 不在 URL、日志、埋点和错误上报中携带 Token。
- 当前 th4 JWT 从请求头读取 token；如后续改为 HttpOnly Cookie，需要框架网关同步改造，不在 Web 前端单独实现。

### 7.7 首次设置、忘记和重置密码

#### 初始密码来源

禁止：

- 不允许默认密码等于手机号后 6 位。
- 不允许默认密码等于 `123456`。
- 不允许 BOSS 手动设置并获知员工密码。
- 不允许在代码或数据库中保存明文初始密码。

推荐：

1. **员工邀请**：BOSS 创建邀请，员工在 Web 通过邀请 ID + 手机号验证码设置自己的密码，服务端创建或绑定 `Credentials`，然后接受邀请。
2. **已有微信用户首次进入 Web**：通过短信验证码验证手机号，设置密码并写入同一 `Credentials`。
3. **企业已有员工未设置密码**：BOSS 只能触发“重发设置/重置验证码”，不能查看或指定密码。
4. 如果没有短信/VCode 服务，Web 首版不能安全上线密码找回和首次设置；只能暂停 Web 登录范围，不能降级为默认密码。

建议路由：

```text
invite/invitation/accept-web
auth/password/set-first
auth/password/forgot
auth/password/reset
auth/password/change
```

- `invite/invitation/accept-web`：邀请 + 短信码 + 新密码，公开入口。
- `auth/password/set-first`：已有账号第一次设置密码，手机号 + 短信码 + 新密码，公开入口。
- `auth/password/forgot`：发送重置验证码，只返回通用成功，不泄露账号是否存在。
- `auth/password/reset`：手机号 + 短信码 + 新密码，公开入口。
- `auth/password/change`：登录后修改，必须校验旧密码 + 新密码。

验证码要求：

- 5 分钟有效，单次消费。
- 同一手机号 60 秒内不可重复发送。
- 单手机号/单 IP 限制每小时请求次数。
- 错误尝试最多 5 次，超过后失效或进入冷却。
- 使用通用短信组件 `Sender/Validator`；业务 Provider 不接触厂商 AccessKey、Redis Key 或 HTTP 协议。
- 当前代码缺少 `components/sms`，这是 Web 密码链路的明确前置缺口。

### 7.8 安全框架前置条件

通过 `javap` 检查当前 `th4-framework-1.0.0.jar` 后确认：

- `LoginTokenResponseFilter` 会把登录 Provider 返回的 `User` 交给 `SecurityManager.sign`。
- `JwtSecurityManager` 使用签名密钥生成 `JwtToken`。
- Token 校验从请求头读取，注销和过期状态当前主要依赖内存态管理。
- 当前签名密钥是框架固定值，不是外部可配置密钥。

因此 Web 登录开发前必须先完成或明确替代方案：

1. 签名密钥改为环境变量/密钥管理，禁止使用框架固定值。
2. Token 过期时间可配置，并在多实例下生效。
3. 注销、密码修改、员工停用可以撤销既有会话。
4. Token 中至少包含稳定主体和版本/会话标识，或使用 Redis 会话/黑名单。
5. 关闭原有自动创建 `user=true` 账号和默认密码逻辑。
6. 当前 `Credentials`/`Employee` 认证主体与业务 `@User` 注入语义保持一致。

没有完成上述前置条件，不应把 Web 密码登录当作生产安全能力上线。

所有新增 Provider：

- 路由放 `tenant/user/service/auth/**` 或相应业务域。
- `@AutoInject` 字段获取手机号、验证码、密码等参数。
- 不新增 DTO/VO/Request 类。
- 公开入口必须在 `ProviderSecurityValidator.PUBLIC_ROUTES` 中显式声明。
- 响应使用实体和 `@Properties` 白名单。
- 密码、哈希、锁定状态和验证码绝不序列化。

### 8.2 服务端登录身份

- Web 登录成功后，优先返回 `Employee`，确保既有业务 Provider 可以继续通过 `@User Employee` 注入。
- 没有有效 Employee 的平台用户不能进入企业后台，只能进入单独的企业创建/加入流程。
- 每次 Web 请求由框架完成 Token 验证，业务 Provider 仍需调用 `TenantContext.requireEmployee` 并重新加载当前企业、角色、门店、团队。
- 不使用前端传入的 `companyId/empId/ownerId` 作为权限依据。

建议扩展 `SecurityAction`：

```text

PasswordFailure
PasswordChange
PasswordReset
PasswordSet
AccountLocked
Logout
```

`UserSecurityLog` 继续使用：

当前 `log(...)` 方法没有填充 IP/User-Agent，需要在认证请求过滤链中安全获取可信代理头并写入，不能信任任意客户端自报头。

### 8.4 数据迁移

建议新增：

```text
docs/design/migrations/21-web-user-password.sql
```

至少包含：

```text
ALTER TABLE db_tenant_credentials
  ADD COLUMN password_hash varchar(255) NULL,
  ADD COLUMN password_algo varchar(32) NULL,
  ADD COLUMN password_updated_at datetime NULL,
  ADD COLUMN failed_login_count int NOT NULL DEFAULT 0,
  ADD COLUMN locked_until datetime NULL,
  ADD COLUMN last_password_login_at datetime NULL,
  ADD COLUMN must_change_password tinyint(1) NOT NULL DEFAULT 0,
  ADD COLUMN password_version int NOT NULL DEFAULT 0;
```

迁移规则：

- 现有微信账号不写入猜测的默认密码，`password_hash` 保持为空。
- 现有员工首次 Web 使用必须走手机号验证和设置密码。
- `phone` 规范化后保持全局唯一；如需调整唯一约束，先盘点现有重复手机号。
- 生产库必须先执行迁移，再启动新版服务；生产禁止依赖 `ddl-auto=update`。
- 迁移脚本必须支持重复执行或由迁移账本管理，失败可追踪。
- 必须纳入 `docs/design/migrations/00-迁移账本.sql`、`run-migrations.sh.template` 和 `docs/design/migrations/19-生产发布基线.md` 的既有发布流程；存量库遵循 DBA 审计后 `adopt` 或完整差异迁移，不允许直接执行未审批增量。

### 8.5 `@Role/@View` 注册

当前后端没有 `@Role/@View`，Web 菜单无法注册。开发时必须新增后端配置类：

```text
tenant/user/configure/TeamLeaderViewConfigure.java
tenant/user/configure/MarketerViewConfigure.java
```

- `user=false`，不要自动创建默认密码账号。
- `component` 指向 Web 布局壳 `views/admin/Home.vue`。
- `@View.name` 全局唯一；同一功能多角色使用差异化菜单名。

- 业主不注册 Web View。
- 菜单登录后按当前角色从服务端下发。

### 9.7 API 复用规则

- 同一业务对象优先复用小程序现有 Provider。
- 如果 Web 需要不同字段集合，先确认现有 `@Properties` 是否仍满足最小字段；不满足时新增 Web 领域读服务或场景化 Provider，不取消原白名单。
- 列表查询必须分页，不能复制小程序中用于摘要的 `size=200/300` 兼容逻辑。
- 批量操作优先使用业务动作 Provider；没有批量能力时，不为前端临时包装跨域请求。
- 所有写操作重新从登录身份解析企业、门店、团队和角色。
- 不允许 Web 直接传 `companyId/ownerId` 决定数据归属。
- 文件必须通过 `file/private/grant` 获取短期 URL，上传后存回业务相对路径。

## 11. 验收标准

### 11.1 构建与基础质量

- `npm install` 可在干净环境成功。
- `npm run type-check` 通过。
- `npm run build` 通过，构建目录为 `dist/`。
- 无未处理 Promise 异常和白屏。
- 浏览器刷新、直接输入 URL、404 和 403 均有正确页面。

### 11.2 登录与安全

- 正确手机号密码登录成功并返回框架 Token。
- 错误密码统一提示，不泄露账号是否存在。
- 连续失败达到阈值后锁定，锁定时间结束后恢复。
- Disabled/Deleted 用户不能登录。
- 首次设置密码必须验证手机号验证码。
- 旧密码错误不能修改密码。
- 忘记密码不泄露账号存在性，验证码一次性且有过期时间。
- 修改密码后旧会话按产品规则失效。
- 退出后 Token 不可继续调用业务 Provider。
- 401 只跳转登录一次，写请求不自动重放。

### 11.3 权限菜单与路由

- 8 个员工角色登录后只看到后端 `@View` 下发的菜单。
- 直接访问未授权 URL 显示 403，不显示业务数据。
- 业主不能登录 Web。
- 菜单、路由、按钮三个层级权限一致。
- 服务端拒绝伪造 `companyId/storeId/teamId/ownerId`。
- BOSS、店长、团队负责人、普通员工分别满足企业、门店、团队、本人数据范围。
- 跨企业详情/更新/删除返回 404/403，数据无变化。

### 11.4 核心 CRUD

- 客户、房屋、跟进、量房可新建、编辑、筛选、查看详情。
- 设计诉求、方案、分项和谈单材料可保存、更新、下载。
- 项目库、套餐、报价、合同、变更可正确保存并刷新状态。
- 项目、阶段、任务、日报、验收可查看和执行授权动作。
- 应收、收款、应付、付款、台账、结算金额和状态一致。
- 供应商、供货价、库存和出入库操作不跨企业。
- 关键写操作均有 loading、防重复提交、成功/失败反馈。

### 11.5 响应字段最小化

- 密码、密码哈希、验证码、openId、unionId、Token 内部字段不出现在响应。
- 列表不返回无需展示的完整关联树。
- 关联对象使用 `@AllowProperties` 最小白名单。
- 不使用 `@JsonIgnore` 替代 `@Properties`。
- 具体 Provider 不新增 `@ServiceProperties` 来冒充权限控制。
- Web 需要的扩展字段通过明确领域 Provider 和目标实体的 `@Properties` 提供。

### 11.6 桌面端可用性

- 1280×720 和 1440×900 下操作区和表格可用。
- 长列表支持分页、排序、筛选和固定列。
- 表单支持键盘提交、ESC 取消、字段错误聚焦。
- 确认、审批、删除、结算和签约使用明确二次确认。
- 批量操作展示成功/失败明细，不静默吞错。
- 金额、日期、状态、负责人、项目编号格式一致。

### 11.7 后端验证

- 新增登录、密码、会话、菜单和权限 Provider 有正向/负向/幂等测试。
- `mvn -o -q test` 通过。
- 生产配置使用环境变量，不在代码中保存密码、私钥或测试商户号。
- Web 登录公开路由被显式加入安全白名单，其他路由必须 `Security`。
- 数据迁移可在生产等价库重复验证，失败账本和回滚路径明确。

## 12. 风险与待确认事项

### 12.1 已确认事实

- Web 目录为空，所有目录、构建和页面均需新建。
- 当前 `Credentials` 只有 `Wx`，没有密码能力。
- 当前没有 `@Role/@View`，Web 菜单不能直接使用现有后端下发。
- 当前没有短信代码，`docs/租户设计方案.md` 中的 `components.sms`、`user/sms/send` 尚未在当前代码中落地。
- 当前框架 Token 使用固定签名密钥和内存过期状态，生产前必须处理。
- 小程序已经具备完整角色矩阵和 192 条后端业务路由，Web 可以复用大部分领域 API。

### 12.2 需要用户确认

1. Web 是否只服务员工，业主是否永久不进 Web；本规划建议首版明确不进。
2. 初始密码采用“邀请 + 短信验证码后本人设置”，是否接受短信供应商和短信成本。
3. 是否允许 BOSS 触发员工重置验证码，但不查看员工密码。
4. 密码强度、锁定阈值和登录有效期。
5. 业务员、设计师、项目支持在 Web 中是否允许编辑，或仅查看。
6. 财务是否需要发票、退款、对账、导出和自定义报表；首版是否只做基础资金闭环。
7. 是否需要企业微信/SSO、扫码登录、短信登录；本规划只做手机号+密码。
8. 是否允许 Web 批量导入客户/项目库/供货价；当前需另立领域导入 Provider。

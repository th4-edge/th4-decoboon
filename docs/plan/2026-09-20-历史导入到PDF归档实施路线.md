## 1. 结论

这条线不是一个页面，而是一条跨领域事实链：

```text
历史数据进入系统
-> 合同和项目基础事实可追溯
-> 责任人、计划、应收和业主关系完成交接
-> 项目满足开工条件
-> 施工过程中形成应收、收款、应付、付款和成本事实
-> 每个关键节点生成 PDF 打印稿并归档
```

实施原则：

1. 先导入主数据，再导业务对象，最后导财务余额；
2. 每批导入先预览，再提交，保留批次、来源和错误明细；
3. 合同交接不新建第二套项目状态，使用真实项目字段派生“开工就绪”；
4. 项目开工必须有 PM、已确认计划和明确开工日期；
5. 财务只写管理台账和业务流水，不冒充法定会计总账；
6. PDF 只在打印和线下签署/盖章场景使用，不建设电子合同或电子签；
7. 所有跨对象联动必须幂等、可追溯、可回滚到修正动作。

已冻结决策：

- 历史合同只导入签署扫描件、合同金额基线和项目关联，不重建完整报价；
- 历史条款只归档，不参与状态判断；
- BOSS 可以批量邀请历史员工，员工接受后激活；
- 期初应收应付在月结前允许整批重导，月结后只能调整或冲正；
- 业主邀请、主材选材和首期款到账都不阻断首个阶段开工；
- 首期款到账仍是独立财务事实，不成为合同生效和项目开工的双重门禁；
- 主材选材仍然可以作为材料采购门禁。

## 3. 第一阶段：历史数据导入

### 3.1 导入分组与顺序

不得用一张大表同时导入所有对象。按依赖顺序分批：

```text
批次 1：组织与员工
批次 2：客户与房屋
批次 3：报价项目库、供应商、品牌和成本
批次 4：历史报价、合同和签署附件
批次 5：历史项目、阶段、任务和进度
批次 6：历史材料计划和采购
批次 7：应收、应付、收款、付款和资金余额
批次 8：历史单据和 PDF 附件归档
```

### 3.2 导入对象

#### 组织与员工

- 门店、团队、岗位和能力。
- 员工姓名、手机号、岗位、门店、团队、在职状态。
- 历史离职员工的只读保留或交接策略。
- 初始 BOSS 必须是已确认主体。
- BOSS 可以按角色、门店、团队批量创建员工邀请；员工本人接受后激活，未接受前不产生正式在职员工。
- 批量邀请需按手机号去重，保留来源员工编号 `legacyEmployeeId`，员工接受后完成历史数据的责任人映射。

#### 客户与房屋

- 客户姓名、电话、来源、状态、负责人、门店、团队。
- 多房屋客户的每套房屋必须独立建档。
- 房屋地址、小区、楼栋、房号、面积、户型。
- `legacyId` 用于历史系统 ID 去重和追溯。

#### 报价项目库与供应商

- 报价项目分类、单位、品牌、规格、售价、成本。
- 供应商、品牌关系、采购参考价。
- 成本字段只允许 BOSS、财务、材料等授权角色导入和查看。

#### 历史报价与合同

- 历史报价、版本、状态、客户接受事实。
- 历史合同只导入签署扫描件、合同编号、合同金额基线、签署日期、关联客户/房屋和可选关联项目。
- 历史合同不重建报价行、合同行、成本快照、收款计划、利润或完整合同状态机。
- 历史合同作为归档证据和项目金额基线存在，不进入新签合同的正常报价到立项流程。
- 合同条款只归档，不参与系统自动状态判断。

#### 历史项目

- 项目来源合同、客户、房屋、负责人、门店、团队。
- 当前状态、当前进度、实际开工和完工日期。
- 阶段、任务、已完成比例、材料计划。
- 无法确认归属的历史项目进入“待确认清单”，不自动猜测。

#### 财务期初与历史账务

- 应收余额、应付余额。
- 已收款、已付款、未收、未付。
- 资金账户期初余额。
- 项目实际成本和已归集成本。
- 历史冲减、退货、退款和调整事实。
- 期初余额必须作为独立来源，不得伪装成正常收款或付款。
- 月结前允许重新导入期初应收应付，新批次必须作废旧期初批次，不能叠加余额；月结后只能通过调整或冲正修正。

### 3.3 ImportBatch 数据契约

每个导入批次至少包含：

```text
batchId
company
importType
sourceFileName
sourceFileHash
templateVersion
status
totalRows
validRows
warningRows
errorRows
createdBy
startedAt
finishedAt
rollbackableUntil
```

状态：

```text
Uploaded
Validated
ReadyToCommit
Committing
Completed
PartiallyCompleted
Failed
RolledBack
Superseded
```

### 3.4 导入过程

```text
下载模板
-> 上传文件
-> 字段映射
-> 预览校验
-> 错误修正
-> 提交导入
-> 分块事务写入
-> 汇总结果
-> 可回滚窗口
-> 正式启用历史账务
```

规则：

- 预览阶段不写正式业务表；
- 每一行保存原始行号、原始值和错误原因；
- 重复导入使用 `company + importType + sourceFileHash + legacyId` 幂等；
- 导入完成后只有明确的“启用”动作才进入正式报表和财务余额；
- 历史导入的报价、合同归档、项目、收款、付款和流水必须保留来源批次；
- 已启用批次不得物理删除，只能冲正或重新导入修正批次；
- 期初应收应付在月结前可重导，最新启用版本作为当前期初余额，旧版本进入 Superseded 状态；
- 期初重导必须整批替换，不允许新旧期初叠加。

### 3.5 导入验收

- 重复上传同一文件不产生重复客户、合同、项目或流水；
- 跨企业 `legacyId` 不互相覆盖；
- 客户多房屋不串房屋；
- 历史合同金额、项目金额和应收应付余额可核对；
- 导入失败不产生半套数据；
- 错误明细可定位到文件、行号和字段。

## 4. 第二阶段：合同交接

### 4.1 触发

合同达到 `Signed` 或 `Effective` 后触发交接准备。项目交接清单是由真实对象派生的只读投影，不新建“交接状态机”。

### 4.2 交接清单

| key | 业务含义 | 数据来源 | 完成条件 | 责任人 |
| --- | --- | --- | --- | --- |
| `contract_archive` | 合同打印稿归档 | ProjectContract、DocumentRecord | 合同 PDF 已生成并归档 | BOSS/财务 |
| `payment_plan` | 收款计划确认 | Receivable | 收款计划已建立；首期款到账不作为开工门禁 | 财务 |
| `designer_ready` | 设计师交接 | Project.designer | 设计师已明确 | 系统/设计师 |
| `pm_ready` | PM 交接 | Project.manager | PM 已指派并有效 | BOSS/店长 |
| `support_ready` | 履约交接 | Project.support | 履约人员明确或按企业规则允许为空 | BOSS/PM |
| `schedule_ready` | 施工计划确认 | ProjectStage、SchedulePlan | PM 确认为正式基线 | PM |
| `customer_ready` | 业主协同准备 | CustomerAccess/Invite | 已邀请或明确暂不邀请；不阻断首个阶段开工 | PM/设计师 |
| `material_selection` | 主材选材准备 | MaterialSelection | 已创建首版选材任务或文本；不阻断首个阶段开工，但可阻断材料采购 | 设计师 |
| `material_plan` | 材料计划准备 | MaterialPlan | 已生成或确认材料计划 | PM/履约 |

### 4.3 交接完成定义

交接完成不等于项目已开工。它表示：

- 合同事实、金额和附件完整；
- 责任人和计划责任明确；
- 收款计划已建立，但首期款是否到账只形成财务风险提示；
- 项目具备进入开工确认的条件。

### 4.4 必须确认的规则

- 合同生效后自动带出设计师，但不能默认 PM 已完成；
- PM 未指派时，项目显示“已签约待接单”，不得从 PM 工作台消失；
- 合同变更、附件和付款条件使用同一合同版本；
- 历史项目也必须补齐责任人和计划，不能以“历史数据”为由绕过交接；
- 首期款到账、业主邀请和主材选材都不作为首个阶段开工的硬门禁；
- 主材选材仍是材料下单的正式规则门禁；
- 交接清单的完成状态必须在重新进入、刷新和跨页返回后重新读取。

## 5. 第三阶段：项目开工

### 5.1 开工前置

必须同时满足：

```text
合同已生效
+ 项目已创建
+ 项目有 PM
+ 施工计划已确认
+ 开工日期明确
```

不阻断首个阶段开工：

- 首期款未到账；
- 业主尚未邀请；
- 主材选材尚未确认。

其中首期款形成财务提醒，业主邀请形成协同提醒，主材选材仍可阻断材料采购。

### 5.2 开工动作

```text
PM 打开待开工项目
-> 核对合同和设计交底
-> 确认计划基线
-> 确认材料计划
-> 选择首个阶段
-> 点击开工
-> 阶段进入 Doing
-> 生成开工动态/通知
-> 项目进入 Ongoing
```

开工必须：

- 在服务端校验 PM 和数据范围；
- 使用幂等键防止重复开工；
- 同一项目只能有一个首个开工事实；
- 记录实际开工时间、操作人、阶段和证据；
- 失败时保留项目原状态，不产生半套任务和动态；
- 首期款未到账时只提示财务风险，不阻断阶段开工。

### 5.3 开工后的对象联动

```text
ProjectStage.Doing
-> Project.Ongoing
-> ProjectTask 可执行
-> MaterialPlan 可释放
-> 现场动态可发布
-> 收款计划按阶段触发
```

材料计划和应收计划不能在开工时重复创建；只允许激活、释放或补充来源。

### 5.4 开工验收

- 未指派 PM 不能开工；
- 计划未确认不能开工；
- 首期款未到账、业主未邀请、选材未确认可以开工；
- 重复点击只返回同一个开工事实；
- 阶段已开工后不能再次首次开工；
- 开工后项目、阶段、任务、材料、应收和动态状态一致；
- 跨门店、跨项目、伪造参数均被拒绝。

## 6. 第四阶段：财务记账

### 6.1 首期固定单据

首期只做：

```text
收款单
付款单
资金台账
应收明细
应付明细
月度汇总
```

### 6.2 应收流程

```text
合同签署/变更
-> 应收节点产生
-> 财务确认到期和金额
-> 收款登记
-> 核销应收
-> 写入资金流水
```

规则：

- 收款不能超过应收余额；
- 支持部分收款；
- 合同变更只调整未来未收节点；
- 已收历史不得无痕覆盖；
- 收据/收款单打印后保留打印记录。

### 6.3 应付流程

```text
采购到货/入库或费用形成
-> 应付产生
-> 财务确认付款条件
-> 付款登记
-> 核销应付
-> 写入资金流水
```

规则：

- 付款不重复增加材料成本；
- 同一到货可形成部分应付和部分付款；
- 退货、换货、扣款和折让形成调整事实；
- 错误账务使用冲销或调整，不物理删除。

### 6.4 资金台账和月度汇总

台账必须区分：

```text
收入
支出
应收未收
应付未付
账户余额
项目实际成本
项目结算金额
```

月度汇总必须可以从汇总穿透到单据、项目和原始业务事实。

### 6.5 期末处理

- 月结前检查未核销应收、未付款应付、异常 Ledger；
- 月结后历史流水不可直接修改；
- 需要调整时创建调整流水；
- 成本不完整时利润和毛利率保持空值；
- 项目结算必须满足应收应付清零和结算条件。

## 7. 第五阶段：PDF 归档

### 7.1 文档对象

```text
DocumentTemplate
DocumentRender
DocumentRecord
DocumentArchive
```

### 7.2 生成流程

```text
业务对象达到可导出状态
-> 解析企业模板或平台基线
-> 生成业务快照
-> 渲染 PDF
-> 计算文件哈希
-> 上传私有 OSS
-> 写入 DocumentRecord
-> 关联业务对象
-> 记录导出人、时间和打印次数
```

### 7.3 首期文档

- 报价单：客户版、内部版。
- 合同：合同打印稿、报价附件、付款计划、空白签署/盖章位。
- 材料：材料计划、采购单、到货验收单、供应商对账单。
- 财务：收款单、付款单、资金台账、应收明细、应付明细、月度汇总。

### 7.4 归档规则

- 每份 PDF 保存模板版本、业务对象、文件哈希、生成时间和操作人；
- 企业模板按企业隔离；
- 未配置企业使用平台行业基线；
- 打印重打更新次数，不覆盖原文件；
- 作废文件保留原件和作废原因；
- PDF 不替代业务状态事实，不提供电子签法律效力；
- 合同签署栏、手印位和盖章位保持空白，由线下打印、人工签署和实物盖章。

## 8. 技术架构

### 8.1 后端领域上下文

```text
ImportBatchContext
ProjectHandoffContext
ProjectContext
ProjectContractContext
FinanceAccessContext
DocumentRenderContext
DocumentArchiveContext
```

职责：

- `ImportBatchContext`：导入预览、幂等、提交、回滚和错误明细；
- `ProjectHandoffContext`：根据项目、合同、计划、应收和人员派生交接就绪状态；
- `ProjectContext`：项目、阶段、任务、材料和开工事务；
- `ProjectContractContext`：合同基线、金额、付款计划和合同版本；
- `FinanceAccessContext`：应收应付、收付款、核销和 Ledger；
- `DocumentRenderContext`：模板解析、字段注入、PDF 渲染和哈希；
- `DocumentArchiveContext`：私有文件、业务关联、下载授权、打印和重打记录。

### 8.2 数据约束

- 导入对象保存 `legacyId + importBatch`；
- 合同项目保持一份合同、一套房屋、一个项目；
- 项目开工使用唯一业务键和幂等键；
- 收款、付款、到货、变更、验收保存业务指纹；
- 文档记录不可覆盖，重打生成新的打印轨迹；
- 所有企业业务对象必须包含企业归属和权限索引。

### 8.3 跨端职责

| 端 | 职责 |
| --- | --- |
| App | 项目交接确认、PM 接单、开工、现场执行、材料确认、收款查看、PDF 分享 |
| 后端 | 状态、金额、权限、幂等、事务、文件渲染和归档 |

## 9. 分阶段路线

### P0-A：基线和导入

- 平台基线包；
- 企业单据资料；
- 导入批次、预览、错误行和幂等；
- 客户、房屋、合同、项目、财务期初导入。

### P0-B：合同交接

- 合同打印稿归档；
- Project 派生交接清单；
- PM/履约指派；
- 收款计划关联；
- “已签约待接单”工作台。

### P0-C：项目开工

- PM 接单；
- 施工计划确认；
- 首个阶段开工；
- 开工动态和幂等；
- 开工前置校验。

### P0-D：财务记账

## 10. 验收场景

### 场景 A：新签合同正常开工

```text
客户接受报价
-> 合同签署
-> 合同生效创建项目
-> 指派 PM
-> 确认计划
-> 确认首期应收
-> PM 开工
-> 收款单和台账生成
-> 合同打印稿归档
```

### 场景 B：历史项目导入后继续履约

```text
导入客户、房屋、合同、项目和期初应收
-> 补指派 PM
-> 补齐计划
-> 确认历史付款和未收余额
-> 下一阶段开工
-> 后续收款和归档
```

### 场景 C：异常和负向

- 重复导入不重复建客户、合同、项目或流水；
- 未指派 PM 不能开工；
- 重复开工只产生一个项目事实；
- 收款超过应收、付款超过应付被拒绝；
- 已作废单据不能继续使用；
- 跨企业、跨门店、跨项目访问被拒绝；
- 模板更新不改变历史 PDF 快照；
- 历史成本不完整时利润为空。

## 11. 需要冻结的决策

1. PDF 渲染库、字体和企业模板安全边界；
2. 历史合同归档与正式合同列表的展示边界；
3. 期初余额重导的允许时间窗口和月结锁定规则；
4. 材料采购对主材选材确认的强制程度；
5. BOSS 批量邀请与员工席位、订阅权益的关系。

---

## 12. 完成定义

只有同时满足以下条件，才视为这条线路打通：

- 历史数据可预览、可提交、可追踪、可回退；
- 合同交接状态由真实对象推导；
- PM 和计划完成项目开工前置；
- 开工动作幂等并正确更新阶段、任务、材料和应收；
- 财务收支、核销、台账和项目金额可对账；
- 报价、合同、材料和财务 PDF 可生成、打印、重打和归档；
- 所有文件企业隔离、短期授权、可审计；
- 三个租户画像完成正常、历史迁移、异常和越权验收。

## 13. 本期明确不做

- 电子合同、电子签、CA 证书和时间戳存证；
- 借贷凭证、会计科目和法定总账；
- 无来源的历史金额猜测和自动回填；
- 复杂供应商门户和大型 ERP 审批；
- 任意 HTML、脚本和 Word/PDF 底稿模板；
- 用测试通过替代真实业务验收。

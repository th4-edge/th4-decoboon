# 后端统计接口优化执行计划

> 日期：2026-10-31
> 状态：PAY-OPS-01 DEV_VERIFIED；等待真实页面、生产等价 P95 与独立验收
> 关联规范：`docs/design/34-后端接口查询与业务编排强制规范.md`
> 关联变更：`CHG-20261031-049`、`CHG-20261031-050`
> 业务事实：`BR-015`、`BR-025`、`BR-031`、`BR-058`、`DEC-016`、`DEC-036`、`DEC-037`、`MET-002`、`MET-004`、`MET-005`、`MET-006`

## 1. 结论

下一步不是全仓批量改 SQL，而是按一个垂直切片推进：

```text
先冻结指标契约
→ 测量当前接口
→ 改造一个工作台聚合
→ 同数据对账
→ 10× 数据验证
→ 真实页面回读
→ 再进入下一个工作台
```

首个切片选择：`PAY-OPS-01`，即 `payroll/workbench/report` 薪酬工作台聚合 SQL 化。

选择理由：

- `BR-015` 已确认工资、提成、应付、发放和工资条的主链路与金额关系；
- 当前接口有明确的 A1 静态违规：5 类实体全量加载后在 Java 中计数/求和；
- 该接口字段边界较小，适合作为“查询链 + 聚合 SQL + 同源对账”的样板；
- 财务工作台的“本月回款”、历史归档、经营利润和费用分摊仍有未冻结口径，不能先改实现再倒推规则。

## 2. 不做什么

- 本计划不一次性改造 543 个 Provider；
- 不为了方便改大页上限；
- 不把财务 `profitAmount`、`grossMargin` 或门店/公司经营利润在 `GAP-070` 关闭前写成确定值；
- 不静默统一 `MET-005` 中 Web/App 冲突的“本月回款”；
- 不把 SQL 条数下降当作性能完成；
- 不改变任何金额、成本、权限、状态、历史快照或对外口径；
- 不新增 DDL 或迁移。

## 3. 指标契约必须长什么样

每个正式统计字段必须登记以下信息，缺一项不得进入页面：

| 字段 | 要求 |
| --- | --- |
| 指标 ID | 稳定编号，如 `MET-006-RECEIVABLE` |
| 页面名称 | 用户看到的名称，不与内部同义词混用 |
| 业务定义 | 一句话说明回答什么经营问题 |
| 主源 | 唯一事实表/对象，如 `Receivable`、`Receipt`、`Payable`、`PayrollSheet` |
| 公式 | 明确的 SUM/COUNT/CASE WHEN，不使用“按情况” |
| 范围 | 企业、门店、团队、本人；全部门店是否含未归属 |
| 时间口径 | 归属于哪个月/哪一天，使用哪个时间字段 |
| 状态条件 | 包含哪些状态，排除哪些状态 |
| 分子/分母 | 比率类必须写清，0 分母返回什么 |
| 完整性 | 成本/数据缺失时返回 `null` 还是 0 |
| 排除项 | 结转、归档、作废、冲正、退款、内部往来等 |
| 下游动作 | 该数字促使用户做什么 |
| 对账 | 与哪个列表 `totalElements`、明细合计或资金台账对账 |
| 证据 | SQL、测试、API、页面和 10× 数据结果 |

### 3.1 统一返回语义

```text
count / amount
+ scope（公司/门店/未归属）
+ asOf（数据截止时间）
+ complete（是否完整）
+ reason（不完整原因）
```

禁止：

- 无数据返回 `null`，有数据返回 0，二者混用；
- 成本不完整时返回 0 利润；
- 汇总失败时返回当前页列表的 `reduce` 结果；
- 同一名称在列表、工作台、详情和驾驶舱使用不同公式；
- 前端二次求和生成正式指标。

## 4. 首个切片：PAY-OPS-01

### 4.1 目标

将 `payroll/workbench/report` 从：

```text
5 类实体 findAll
→ Java filter/count/reduce
→ 组装多个指标
```

改为：

```text
权限与门店范围解析
→ 6 条有界聚合/投影查询（5 个业务组）
→ 固定次数组装
→ 返回同一 PayrollWorkbenchReport
```

允许指标由多组 SQL 分别获取，不追求把所有表硬塞成一个重 JOIN。优先保证：**SQL 条数不随工资单、工资项、提成、应付、工资条数量增长**。

### 4.2 请求与范围

```text
period      YYYY-MM；未传时取当前月
storeId     可选；BOSS/总部财务可全部门店或单店；门店角色锁定本店
asOf        服务端生成；用于工资条/应付/提成状态截止
```

服务端必须复用 `PayrollAccessContext` 和 `StoreFilterContext`，不得信任客户端企业或员工范围。

### 4.3 当前业务规则与建议冻结口径

下表中的“现状”用于保证性能改造前后结果一致，不自动等于已批准的未来业务规则；标为“待确认”的字段必须先由用户或业务智能体裁决。

| 指标 | 当前实现/建议口径 | 主源 | 状态 |
| --- | --- | --- | --- |
| `pendingAttendanceCount` | 指定月份、当前门店范围内，考勤状态为 `Pending` 或 `Disputed` 的人数/记录数 | AttendanceSummary | 现状保留，待业务确认是否包含 `Draft/Rejected` |
| `currentPeriodHasSheet` | 当前期间是否存在工资单 | PayrollSheet | 已明确 |
| `draftSheetCount` | 当前期间 `Draft` 工资单数 | PayrollSheet | 已明确 |
| `pendingSheetCount` | 当前期间 `Pending` 工资单数 | PayrollSheet | 已明确 |
| `confirmedSheetCount` | 当前期间 `Confirmed` 工资单数 | PayrollSheet | 已明确 |
| `partialPaidSheetCount` | 当前期间 `PartialPaid` 工资单数 | PayrollSheet | 已明确 |
| `paidSheetCount` | 当前期间 `Paid` 工资单数 | PayrollSheet | 已明确 |
| `pendingEmployeePayableAmount` | 当前代码为 `Σ (应付金额 - 已付金额)`；员工工资只取目标期间，员工提成取当前未结清项。建议冻结为逐条 `max(应付-已付, 0)` | Payable | 现状保留；负数钳制、提成是否跨期间待确认 |
| `releasedUnpaidCommissionAmount` | 当前代码为 `Σ (已释放金额 - 已付金额)`，状态为 `Released/InPayment`。建议冻结为逐条 `max(已释放-已付, 0)` | CommissionItem | 主体口径与 `BR-015` 一致；负数钳制待确认 |
| `pendingPayslipCount` | 目标期间 `PendingPayment` 工资条数 | Payslip | 已明确 |
| `publishedPayslipCount` | 目标期间 `Published` 工资条数 | Payslip | 已明确 |
| 最近工资单 | `ORDER BY period DESC, sheetId DESC LIMIT 1` | PayrollSheet | 建议冻结稳定排序 |

### 4.4 查询链

```text
Q1 AttendanceSummary 聚合：待处理考勤数
Q2 PayrollSheet 聚合：当前期间状态计数
Q3 PayrollSheet 投影：最近工资单
Q4 Payable 聚合：员工工资/提成未付金额
Q5 CommissionItem 聚合：已释放未付提成
Q6 Payslip 聚合：待发/已发布数量
```

验收目标：

- 固定 6 条查询（5 个业务组，其中工资单含状态聚合与最近单投影），不随业务明细行数增长；
- 每个查询返回 O(1) 行；
- 门店、期间、权限条件全部进入 SQL；
- 结果与旧实现同数据集逐字段一致；
- 不加载完整实体，不逐行触发 LAZY；
- 响应字段仍使用现有 `@Properties` 白名单。

### 4.5 SQL 形状

示意，不直接替代业务实现：

```sql
SELECT
  COUNT(*) FILTER (WHERE status IN ('Pending','Disputed')) AS pending_count
FROM db_payroll_attendance_summary
WHERE com_id = :comId
  AND payroll_month = :period
  AND (:storeId IS NULL OR store_id = :storeId);
```

```sql
SELECT
  SUM(CASE WHEN status = 'Draft' THEN 1 ELSE 0 END) AS draft_count,
  SUM(CASE WHEN status = 'Pending' THEN 1 ELSE 0 END) AS pending_count,
  SUM(CASE WHEN status = 'Confirmed' THEN 1 ELSE 0 END) AS confirmed_count,
  SUM(CASE WHEN status = 'PartialPaid' THEN 1 ELSE 0 END) AS partial_paid_count,
  SUM(CASE WHEN status = 'Paid' THEN 1 ELSE 0 END) AS paid_count
FROM db_payroll_sheet
WHERE com_id = :comId
  AND period = :period
  AND (:storeId IS NULL OR store_id = :storeId);
```

```sql
SELECT COALESCE(SUM(GREATEST(amount - COALESCE(paid_amount, 0), 0)), 0)
FROM db_finance_payable
WHERE com_id = :comId
  AND (:storeId IS NULL OR store_id = :storeId)
  AND (
    type = 'EmployeeCommission'
    OR (type = 'EmployeeSalary' AND period = :period)
  );
```

实际实现应按数据库方言与索引调整，但必须保留相同的状态、期间、门店和空值语义。

### 4.6 索引检查

至少确认以下查询是否命中：

```text
db_payroll_attendance_summary(com_id, store_id, payroll_month, status)
db_payroll_sheet(com_id, store_id, period, status)
db_finance_payable(com_id, store_id, type, period, status)
db_payroll_commission_item(com_id, store_id, status)
db_payroll_payslip(com_id, store_id, period, status)
```

若现有索引不足，先记录执行计划和数据量，再决定是否新增索引；索引变更属于独立 DDL 批次，不能在本次聚合改造中夹带。

### 4.7 对账方式

在同一租户、门店、期间、截止时间下：

```text
旧 Context 结果
== 新聚合 SQL 结果
== 明细列表按条件累计
```

至少校验：

- 每个状态计数；
- 待付员工工资 + 提成；
- 已释放未付提成；
- 待发/已发布工资条；
- 最近工资单 ID、期间、状态、实发金额；
- 无数据、部分门店、跨店、空期间、错误期间格式。

### 4.8 性能证据

改造前后使用同一数据和同一会话：

```bash
curl -w 'ttfb=%{time_starttransfer} total=%{time_total} size=%{size_download}\n' ...
```

保存：

- P50/P95/P99/max；
- 响应体大小；
- SQL 条数；
- 最大返回行数；
- 10× 工资项/提成/应付数量；
- 门店切换和 0 数据场景；
- App/Web 页面回读。

## 5. 第二个切片：FIN-OPS-01

只有以下前提满足后才能开始：

1. `MET-005` 的“本月回款/回款额/已收金额/资金收入”命名和公式冻结；
2. 历史结转/归档项目是否排除冻结；
3. 0 基期、负现金余额、期初未承接的展示规则冻结；
4. `GAP-070` 关闭前，经营利润字段不输出确定金额；
5. `MET-007/011` 仍为草案时，不得用优化名义实现利润口径。

### 5.1 当前已稳定的财务工作台口径

以下来自 `MET-006` / `MET-002` / `BR-058`，性能改造必须保持：

| 指标 | 口径 |
| --- | --- |
| 应收金额 | `Σ Receivable.amount`，排除规则按已冻结归档口径 |
| 已收金额 | `Σ Receivable.receivedAmount`，必须与有效收款/冲正回算一致 |
| 待收金额 | `Σ max(应收 - 已收, 0)`，逐条不为负 |
| 应付金额 | `Σ Payable.amount` |
| 已付金额 | `Σ Payable.paidAmount` |
| 待付金额 | `Σ max(应付 - 已付, 0)`，逐条不为负 |
| 回款率 | `已收 ÷ 应收 × 100%`；0 分母不得伪装成 0% |
| 现金流 | `资金收入 - 资金支出`，不等于利润 |
| 账户余额 | `期初余额 + 累计资金收入 - 累计资金支出`；未承接期初必须显式标记 |
| 预计成本/毛利 | 只用 P1；成本不完整时毛利为 `null` |
| 动态成本/毛利 | P3 + P2 暂估 + 已确认人工/工资/提成/项目费用；不完整为 `null` |
| 最终成本/毛利 | 只使用 P3 和最终确认应计；未确认结算不得输出最终利润 |
| 项目毛利率 | 对应毛利 ÷ 对应收入；收入不大于 0 时 `null` |

### 5.2 当前不得直接写死的口径

| 问题 | 当前状态 | 临时处理 |
| --- | --- | --- |
| Web `monthReceiptAmount` 与 App `monthIncome` 同名不同义 | `MET-005` 冲突 | 保留字段但分别命名/标注，待统一 |
| 历史归档项目是否进入业务金额 | MET-006 待确认 | 按现有冻结实现保留，不能让聚合改造改变排除规则 |
| 负现金余额显示 | MET-006 待确认 | 未承接期初显示“期初未承接”，不得伪装成 0 |
| 0 基期/0 目标 | MET-006 待确认 | 返回 `null`/“暂无基期”，不得显示 0% |
| 公司经营利润 | MET-007 draft | `GAP-070` 关闭前不输出确定金额 |
| 门店经营利润 | MET-011 draft | 不按总部/公共费用强行分摊 |

### 5.3 财务聚合技术方案

原则：

```text
项目范围先下推
→ 按业务事实域分别聚合
→ 成本通过 ProjectCostContext 的批量投影
→ 利润只在完整性成立时计算
→ 列表另走 PAGE_LIST
```

不在一个 SQL 中重 JOIN 应收、应付、台账、凭证、成本、工资和项目；拆成多个有界聚合查询，避免重 JOIN 让单条 SQL 变慢。目标是查询结构稳定，不是 SQL 数量最少。

## 6. 第三个切片：分页接口

财务/薪酬完成后，再处理：

- `customer/report/page`
- `project/report/page|list`
- `project/purchase/page`
- `project/material-plan/page`
- `project/acceptance/page`

统一做法：

1. 权限范围变成 SQL 子查询或规范关联条件；
2. 筛选、搜索、排序、稳定键全部下推；
3. 数据库分页后才批量装配当前页摘要；
4. 历史明细独立 `PAGE_LIST`；
5. `totalElements` 与同筛选汇总对账；
6. 10× 数据、最后一页、越权、空数据验证。

## 7. 如何保证效率

### 7.1 正确性先于性能

- 先用旧实现生成黄金数据集结果；
- 新实现必须逐字段对账；
- 业务口径有任何变化，另立变更，不混入性能改造；
- 金额、成本、利润、权限和门店范围做负向测试。

### 7.2 查询结构有界

- 每个指标返回行数 O(1)；
- 每组聚合 SQL 条数固定；
- 不随工资项、合同行、应收、台账、提成数量增长；
- 列表当前页行数 O(`size`)；
- 批量装配只对当前页 ID 做固定批次 `IN`；
- 循环内零 Repository、零 LAZY。

### 7.3 索引与执行计划

- 每个聚合条件使用 `com_id` 最左的联合索引；
- 检查 `EXPLAIN` 是否走范围扫描/覆盖索引；
- 不使用 `SELECT *` 后 Java 过滤；
- 不在应用层拼接 SQL；
- 不新增数据库悲观锁。

### 7.4 用户感知验收

```text
核心读取 API：P95 ≤ 500ms，P99 ≤ 1000ms，max ≤ 2000ms
SQL：≤30 条，且结构不随数据量增长
页面：首屏有效数据 ≤2s，可交互 ≤3s，关键请求 ≤5 个
响应体：按字段统计字节占比，列表/驾驶舱最小白名单
```

只有 P95/首屏改善才算性能收益。SQL 从 100 降到 20 但 P95 不变，不能宣布优化完成。

| 测试 | 最低要求 |

| 单元测试 | 每个指标的状态、期间、门店、金额、空值 |

| 回滚 | 保留旧 Context 路径或可快速回退的提交点 |

## 9. 执行顺序

```text
1. 用户确认 PAY-OPS-01 指标契约
2. 采集旧接口 P95/响应体/SQL 基线
3. 写旧/新对账测试
4. 新增 Repository 聚合投影
5. 替换 PayrollWorkbenchContext 的全量加载
6. 定向测试 + 静态门禁
7. 10× 数据与同数据对账
8. App/Web 真实页面回读
9. 形成 CHG 证据，进入 FIN-OPS-01 口径冻结
```

## 10. 当前唯一建议动作

立即启动 `PAY-OPS-01` 的“指标契约冻结 + 基线测量”，仍不改运行时代码。

进入生产代码改造前，需要用户/业务确认四项：

1. `pendingAttendanceCount` 是否只包含 `Pending/Disputed`，还是也包含 `Draft/Rejected`；
2. 员工提成待付金额是否跨期间累计；
3. 应付/提成的未付金额是否逐条钳制为 `max(金额-已付, 0)`，禁止负余额；
4. 最近工资单并列时是否按 `sheetId` 倒序作为唯一稳定排序。

在四项未确认前，可以先做旧接口基线测量、SQL 数量观测和旧/新对账框架，但不得改变当前返回语义。

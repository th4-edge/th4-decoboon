> 版本：v1.0  
> 日期：2026-10-05  
> 状态：`baseline`（方法沉淀基线；经用户确认后可升级为跨端强制门禁）

>
> 业务信息架构执行标准：`docs/product/02-业务信息架构与字段闭环标准.md`。新增/修改字段必须先登记业务信息项，明确主源、消费者和闭合动作。

## 如何使用本文件

本文件解决四个问题：

1. **为什么这样做**：每一条规范背后的产品判断和事故教训。
2. **具体怎么做**：从场景、对象、状态、权限、账务到页面、组件、验收的完整动作。
3. **做到什么程度算完成**：每个阶段的冻结物、门禁和验收证据。
4. **如何复用到 Web 和其他产品**：把「装得清经验」抽象成可迁移的资产，而不是复制页面。

阅读顺序建议：

| 角色 | 必读部分 |
| --- | --- |
| 产品负责人 / 需求提出者 | §0 总纲、§1 理念、§2 八步法、§7 模板 |
| 产品经理 / 交互设计 | §1–§3、§7 场景卡/条件矩阵/页面冻结卡 |
| 前端 / 后端开发 | §2、§3.5–§3.8、§4 门禁、§5 反模式 |
| 验收 / 质量 / 审计 | §3.4、§3.9、§4、§5、§6.4 |
| 新端 / 新产品负责人 | §0、§1.7、§6 全套 |

一句话总纲：

> **产品不是功能集合，而是让每个角色在真实业务状态下，看清事实、知道下一步、能够安全完成、并留下可追溯结果的系统。**

## 0. 一页总纲

### 0.1 产品构建公式

```text
产品 = 真实场景 × 领域事实 × 角色权限 × 状态推进 × 端上体验 × 可验证证据
```

六个因子缺一不可。任何功能只要缺场景、缺事实源、缺权限、缺状态、缺体验或缺证据，都不能算交付。

### 0.2 一条主链、四个锚点、一条事实链

**一条业务主链**

```text
客户线索 -> 跟进/量房 -> 设计诉求 -> 设计方案 -> 报价 -> 客户确认
-> 合同/变更 -> 项目立项 -> 施工计划 -> 任务/节点 -> 现场留证/问题整改
-> 验收 -> 收款/付款 -> 成本/利润 -> 结算/经营报表
```

**四个业务锚点**

```text
客户锚点：线索、负责人、跟进、房屋、机会
房屋锚点：量房、设计、报价、合同、项目
合同锚点：报价快照、签约基线、签约价调整、变更、收款节点
项目/工地锚点：阶段、任务、动态、材料、验收、整改
```

**一条账务事实链**

```text
报价快照 -> 合同基线 -> 应收/应付 -> 收付 -> 成本 -> 结算/利润
```

业务主链回答「业务怎么走」，账务事实链回答「钱和成本在哪里形成、由谁留下、何时不可逆」。两条链必须同时设计，不能先做业务页面、后补账务口径。

### 0.3 用户界面只回答三件事（首屏三问）

任何页面首屏必须同时回答：

1. **我是谁**：当前员工、角色、数据范围（Company / Store / Team / Self + 项目参与）。
2. **当前有什么待处理**：属于我的待办、风险、逾期、等待他人、待决策；没有就明确说「当前无待处理」。
3. **下一步该做什么**：唯一主动作、为什么现在做、谁负责、完成条件、做完后进入什么状态。

### 0.4 三个不可伪造

| 不可伪造项 | 唯一合法来源 | 禁止做法 |
| --- | --- | --- |
| **完成状态** | 当前租户真实领域对象 + 明确完成谓词 | `done:true`、演示数据、前端本地布尔、接口 200 即完成 |
| **利润 / 成本** | `ProjectCostContext` 等统一账务上下文；成本不完整时利润为空 | 以 0 成本计算、展示伪利润、前端重算金额 |
| **权限 / 数据范围** | 服务端 `Security + @DataPermission + DataScopeSpecification` | 菜单隐藏代替鉴权、前端传 `companyId/empId/ownerId`、`findById` 后自行判断 |

### 0.5 端能力分工（App 与 Web 不是互相放大）

| 能力类型 | App（微信小程序） | Web（企业工作台） |
| --- | --- | --- |
| 现场执行 | **主战场**：拍照留证、到场确认、即时反馈、扫码 | 不做主要路径 |
| 批量 / 比较 / 对账 | 轻量下钻和查看 | **主战场**：批量导入、台账对账、版本比较 |
| 排期 / 审批 / 经营分析 | 查看、提醒、关键审批 | **主战场**：宽屏排期、审批流、经营驾驶舱 |
| 信息架构 | 角色 Tab + 对象推进 + 现场快捷视图 | 角色工作台 + 对象工作空间 + 上下文导航 |
| 业务事实 | 同一对象、状态、金额、权限 | 同一对象、状态、金额、权限 |
| 关系 | App 是同一事实的**现场视图** | Web 是同一事实的**宽屏效率视图** |

**铁律**：同一业务事实在 App、Web、报价、合同、项目和财务页面必须同源同口径。发现不一致，先建立 `DEF-*` 或 `GAP-*`，禁止用任一端的文案或前端兜底掩盖。

## 1. 设计理念：九条底层原则

### 1.1 角色决定工作台，而不是模块决定菜单

**理念**：不同岗位进入系统后，应该看到「我这个岗位今天要做什么」，而不是一张所有功能的目录。

**为什么**：中小装企角色边界容易重叠，但责任不能混。老板关注经营结果与风险，店长关注本店转化与履约，设计师关注设计与报价，项目经理关注现场与节点，财务关注资金与成本完整性。把所有模块铺给所有人，等于把判断成本转嫁给用户。

**怎么做**：

- 固定 7 类员工角色：`Boss / StoreManager / Designer / Marketer / Pm / Finance / TeamLeader`；禁止新增重复角色，履约、材料、采购职责并入 `Finance`。
- 数据范围默认矩阵：`Boss = Company`、`StoreManager = Store`、`TeamLeader = Team`、普通员工 = `Self` + 项目参与关系。
- 可见性三层缺一不算通过：菜单/入口隐藏 → 路由守卫 → 接口拒绝。
- 每个角色至少有一条可跑通的主链闭环，从进入工作台到完成一个真实业务结果。

**验收**：

- 每个角色首屏能回答首屏三问。
- 正向可见 + 负向不可见 + 跨租户拒绝均有用例。
- 菜单隐藏、路由深链、接口调用三条路径分别验证。

**反例**：

- 把专业列表（合同台账、报价项目库、财务流水）直接做成一级导航。
- 用「角色隐藏按钮」代替服务端数据权限。
- 新增角色解决职责问题，而不先问是否属于既有 7 类角色。

---

### 1.2 系统给下一步，用户不寻找功能

**理念**：使用者不应寻找功能；系统应根据角色、对象和业务状态，直接呈现当前事实、下一步、责任人、阻断项和结果。

**为什么**：家装业务是长链路、多角色交接、强状态依赖。用户真正需要的不是「菜单在哪里」，而是「这个客户现在能不能报价、为什么不能、该找谁、做完进入什么状态」。

**怎么做**：

- 每个对象页首屏固定回答五问：现在什么状态？谁负责、多久未推进、是否逾期？下一步最合理动作是什么？为什么不能继续、缺哪个前置事实或权限？完成后写回哪些对象、状态、金额或通知？
- 「下一步」必须由后端正式状态、前置条件和权限推导；前端不得自创状态机。
- 列表用于定位，详情用于推进；不允许用户为了完成同一业务动作在多个菜单间跳转。
- 页面切换后必须保留租户、项目、房屋、筛选项和操作进度等业务上下文。

**验收**：

- 主任务从进入页面到完成 ≤ 3 次操作。
- 每个可点控件都有确定结果：切换、跳转、打开、提交，或明确说明为什么不能点。
- 无死控件、无假 Tab、无「点了没反应」。

**反例**：

- 首页堆满同权入口，用户需要先理解功能名再判断先做什么。
- 状态不允许时按钮仍可点，点击后才报错。
- 跨对象阶段切换丢失 `customerId / propertyId / quoteId / projectId` 上下文。

### 1.3 场景先于功能，条件先于页面

**理念**：任何功能设计不得从数据表、字段清单或技术模型开始，必须先写清真实业务场景；任何场景必须先建立条件矩阵，再讨论功能。

**为什么**：家装软件的失败通常不是「少一个按钮」，而是场景没闭环：缺前置条件、缺异常处理、缺交接对象、缺账务落点。没有条件的页面描述，无法验收，也无法实现。

**怎么做**：

- 每个功能至少 2 个真实中小装企场景；全链批次至少 3 个租户画像：单店成长型、2–3 店成长型、小团队兼任型。
- 每个场景必须包含：使用人、触发事件、前置条件、当前线下做法、当前动作、系统下一步、责任人交接、异常处理、完成证据。
- 用 12 维条件矩阵刻画：角色、组织、阶段、对象、触发、前置条件、动作、状态变化、金额/成本、数据范围、例外、验收。
- 条件表达统一使用：

```text
当【角色】在【组织/数据范围】内，针对处于【状态】的【对象】，
且满足【前置条件】时，执行【动作】后，系统必须【状态变化/计算/留痕】；
若【例外条件】，则【阻断/降级/补偿】。
```

- 支撑页面设计的场景必须落到主链的明确一段；跨多段的场景拆成主场景和关联场景，不写成一个无法验收的大流程。

**验收**：

- 场景覆盖正常链、拒绝/返工链、跨租户负向链。
- 每个异常都有阻断、降级或补偿路径。
- 业务规则可追溯到业务知识编号；无编号的假设标记为 `GAP` 或待确认，不得伪装成事实。

**反例**：

- 「先做一个列表页，以后再补流程」。
- 只写理想路径，不写重复提交、并发、历史数据、权限不足、成本缺失。
- 把大型 ERP 的完整模型强加给中小装企。

### 1.4 业务事实唯一，同源同口径

**理念**：业务事实只有一个权威来源；代码存在不等于业务已验收，设计确认不等于功能已上线，市场反馈不等于产品事实。

**为什么**：一旦出现两套口径，App、Web、财务、营销就会互相矛盾。修复成本远高于第一次把口径写清楚的成本。

**怎么做**：

- 业务对象、状态、权限、金额、成本、利润、对外表达统一回 `zhuangdeqing-business` 核对。
- 来源权威顺序：用户明确决策与书面确认 > 已批准产品设计/规则/合同口径 > 已通过验收的测试与生产真实现象 > 当前代码/迁移/接口契约 > 产品文档/操作手册 > 市场材料/访谈/经验判断 > 推测与假设。
- 关键结论引用 `SCN/BR/SOL/MET/CAP/DEC/GAP/EV`，并说明状态与置信度。
- 发现冲突时建立 `GAP-*`，不得静默合并或选择更省事的版本。
- 「应然」写在产品与业务设计，「实然」沉淀到 `business-rules.md` 与 `user-guide.md`，冲突时先排查实然，再回改应然。

**验收**：

- 同一事实跨 App/Web/报价/合同/项目/财务可追溯且一致。
- 金额、成本、利润有公式、范围、分母、时间口径和缺失值处理。
- 对外表达只用 `verified` 且证据充分的内容。

**反例**：

- 前端用 `|| 0` 或 `list[0]` 掩盖后端缺失字段。
- 两个页面各算一遍金额，结果不一致。
- 用一个端的新文案去「解释」另一个端口径错误。

### 1.5 权限与账务是设计前置项，不是后补项

**理念**：多租户、数据范围、金额、成本、利润必须与页面方案同时设计。权限错一次就是数据事故，账务错一次就是信任事故。

**为什么**：权限和账务具有跨模块、不可逆、强审计属性。事后补权限或补账务，通常意味着重做领域关系、迁移数据和重验所有页面。

**怎么做**：

- 任何业务实体必须直接归属 `Company company`；禁止通过间接关联绕过企业归属。
- 关联用对象类型建模，例如 `Employee emp` 而不是裸 `Long empId`；所有业务实体必须含 `Company company`。
- 查询统一由 `@DataPermission` + `DataScopeRequestFilter` / `DataScopeContext` / `DataScopeSpecification` 处理；自定义详情、更新、删除禁止 `findById` 后自行判断。
- 保存时企业取登录员工所属企业；非 BOSS 的负责人强制为当前员工。
- 业务表按权限维度建立联合索引，`com_id` 始终最左。
- 金额/成本/利润必须走统一账务上下文；报价快照、合同基线、应收应付、收付、成本、结算各自有明确写入时点。
- 成本不完整时返回 `costComplete=false`，利润和毛利率为 `null`，页面显示「成本未完整」。

**验收**：

- 四角色 + 伪造参数 + 跨企业 + 详情越权 + 更新/删除越权测试完整。
- L3 高风险变更（DDL、迁移、权限、金额/成本/利润、支付、跨租户、数据删除）必须全量测试、备份、回滚点和用户确认。
- 任一应计成本缺失时不产生伪利润。

**反例**：

- 信任前端传入的 `companyId / empId / ownerId / storeId / teamId`。
- 只在列表接口加权限，详情/更新/删除越权。
- 把 `readOnly = true` 的事务链路调用带锁仓储，导致 MySQL 1792。

### 1.6 状态机在后端，端上只做呈现与提交

**理念**：阶段、任务、节点、验收等状态流转由 Provider/领域服务负责；端上提交业务对象或调用领域能力后重新拉取，不维护本地状态机。

**为什么**：状态机一旦分叉到前端，就会出现「App 能点、Web 不能点」「前端显示已完成、后端实际未完成」「刷新后回退」等问题。

**怎么做**：

- 状态推进统一由后端状态机与前置条件校验。
- 端上只做三件事：呈现事实、收集输入、调用领域 API；成功后重新读取。
- 完成态由真实领域对象推导；新增/编辑/删除/状态变化后必须重新读取或触发失效。
- 派生字段（`status`、`currentStageName`、计数、金额汇总、下一步）必须现场推导，不能作为事实源落库后再当作真相。

**验收**：

- 正向、反向、重复、边界、回退全矩阵通过。
- 返回页面、切换 Tab、重新登录后状态收敛。
- 业务动作 → 返回页面 → 状态正确，而不是只看接口 200。

**反例**：

- 前端布尔控制步骤完成。
- 页面本地维护 `currentStage`，与后端 `project.status` 冲突。
- 列表页缓存旧数据，返回后不刷新。

### 1.7 反堆砌：以闭环和证据衡量进度

**理念**：不以页面数、功能数、菜单数衡量进度；以「角色闭环数 + 效率指标 + 验收证据」衡量。

**为什么**：功能越多，用户判断成本越高，维护成本越高。对中小装企而言，能用、能闭环、能少培训，比功能全更重要。

**怎么做**：

- 每个新增页面/入口必须挂到某个角色的主链闭环上；挂不上就不建。
- 专业列表是能力，不是岗位主入口。
- App 不复制 Web 的批量与经营分析；Web 不把 App 信息流放大成卡堆。
- 默认路径只服务最高频场景；低频/高风险字段按需展开。
- 同一信息只表达一次；同一动作只有一个名称；同一页面只有一个主对象、一个主动作。

**验收**：

- 能回答「这个页面属于哪个角色、哪条主链、哪一步」。
- 主任务 ≤ 3 次操作，首屏 3 秒内回答三问。
- 页面没有重复区块、近义按钮、装饰性假控件。

**反例**：

- 用页面数量汇报进度。
- 客户详情同时出现「业务流程 / 设计转化 / 方案报价」三张同权卡片。
- 一个页面出现两个实心主按钮。

---

### 1.8 证据先于结论，渲染先于交付

**理念**：类型检查、构建成功、接口 200 都不构成产品可用证据；页面必须在真实设备/浏览器中按角色、状态、权限渲染并留证。

**为什么**：大量问题只在真实渲染、真实权限、真实数据状态或跨端交互中出现。静态检查只能证明代码结构，不证明用户体验。

**怎么做**：

- App：微信开发者工具真实 Mini Program 页面 + 至少 375/390/430 逻辑像素；禁止用 H5、Web、Mock、接口回放冒充。
- Web：真实浏览器 + 1440/1280/1024/768 四档；至少两轮「渲染 → 按反模式批判 → 修正 → 再渲染」。
- 每步记录：租户、角色、设备、时间、路由、入口、对象 ID、前置状态、动作、页面反馈、接口结果、状态变化、账务写入、截图/视频、恢复路径。
- 证据分级：`PASS / FAIL / BLOCKED / NOT_TESTED` 分开列出；阻塞不得包装成通过。
- 开发自测、独立验收、生产真实现象三者不得互相冒充。

**验收**：

- 页面交付附真实截图、URL/路由、账号角色、数据样本和状态矩阵。
- 高风险修复附 changed_files、测试、重启/部署证据、风险和待验收项。
- 未验证项明确标记，不用「应该可以」代替证据。

**反例**：

- 只有 `type-check` 通过就宣布页面完成。
- 用 Mock 数据证明业务闭环。
- 截图只拍理想态，不覆盖空态、失败、无权限、边界。

---

### 1.9 试运营轻量协作，但安全底线不降

**理念**：单人试运营阶段以成本和响应速度优先，简化 lane、交接、RC 和全量测试；但权限、金额、成本、支付、DDL、跨租户、数据删除的安全底线不变。

**为什么**：流程的价值是降低风险，不是制造仪式。小修复应走短路径，高风险变更必须走安全路径。

**怎么做**：

- 变更分级：

| 级别 | 典型变更 | 默认验证 | 发布要求 |
| --- | --- | --- | --- |
| L0 | 文案、文档、无运行时逻辑配置 | 不跑测试；UI 变更做构建 | 可随批次提交 |
| L1 | 单点 BUG、局部校验、局部 UI、单 Provider 修复 | 定向测试 + 类型检查/构建 | 可从 `dev` 发布 |
| L2 | 跨模块功能、读模型聚合、批量逻辑、普通迁移 | 定向测试 + 核心回归 + 全量测试 | 按批次发布 |
| L3 | DDL、权限、金额/成本/利润、支付、跨租户、数据删除 | 全量测试 + 备份 + 回滚点 + 用户确认 | 发布后必须冒烟和观察 |

- 小修复不强制全量测试、RC tag 和独立验收；L3 不适用简化门禁。
- 默认预算：L0 最多 3 个文件 / 约 100 行；L1 最多 8 个文件、一次定向测试、一次构建；工具输出只看关键行。
- 同一事故单次最多发布 1 次，禁止循环重试；无法回滚或无法验证时，只记录并等待人工处理。
- 恢复严格流程的条件：研发协作者超过 1 人、外部付费客户规模扩大或正式商用、生产事故频率升高、出现资金/权限/隐私/迁移高风险变更、用户明确要求。

**验收**：

- 每次任务明确变更级别。
- L3 有备份、回滚点、用户确认和冒烟记录。
- 「自测通过」不得写成「独立验收通过」。

**反例**：

- 以「单人模式」为理由跳过权限负向测试或金额回归。
- 小文案改动触发全量回归和多次交接。
- 生产故障热修直接改生产，不留 release 和回滚点。

## 2. 产品构建八步法（从场景到上线）

八步法把装得清 App 研发中验证有效的动作固化下来。App、Web 和后续产品都按同一套骨架执行，只在端专属环节做差异。

```text
S0 定边界
-> S1 读事实 + 建场景
-> S2 建主链 + 账务事实链
-> S3 建条件矩阵（12 维）
-> S4 定信息架构与页面契约
-> S5 冻结迭代包（R1/R2/R3 + 门禁）
-> S6 实现（后端领域 + 端上体验）
-> S7 验证（三链 + 证据）
-> S8 回写知识与沉淀规则
```

### S0 定边界

**目的**：先确定这次任务是什么、不是什么、影响谁、影响哪些对象和端。

**必须回答**：

1. 模式：新企入驻 / 全链推演 / 单需求迭代 / 体验评审 / 批量验证。
2. 当前状态与当前批次 ID。
3. 受影响对象、状态、Provider、页面、端。
4. 目标角色、数据范围、设备/浏览器。
5. 业务事实来源与证据编号。
6. 明确不做什么（out of scope）。
7. 变更级别（L0–L3）与所需门禁。

**输出**：边界卡。

**门禁**：边界不清、事实源不明、影响端不明时，不进入 S1。

---

### S1 读事实 + 建场景

**目的**：把「用户想做什么」翻译成可验收的业务场景。

**动作**：

1. 读业务事实源：`AGENTS.md`、`SKILL.md`、相关 SOP、`registry.json`、`SCN/BR/SOL/MET/CAP/DEC/GAP/EV`。
2. 读产品设计与代码现状、迁移、测试、验收和界面；只读当前任务必需部分。
3. 建立至少 2 个真实场景；全链批次建立至少 3 个租户画像。
4. 每个场景写全：使用人、触发事件、前置条件、当前动作、系统下一步、责任交接、异常处理、完成证据。
5. 区分「已验收 / 已实现 / 已确认 / 待验证 / 冲突 / 废弃」，不得混用。

**租户画像基线**：

| 画像 | 规模 | 重点验证 |
| --- | --- | --- |
| T-A 单店成长型 | 10–15 人、1 店、在施 3–8 个 | 上手成本、角色任务、报价到回款、现场履约 |
| T-B 2–3 店成长型 | 20–30 人、2–3 店、多团队 | Company/Store/Team/Self、跨店协作、转交、隔离、汇总 |
| T-C 小团队兼任型 | 3–8 人、角色兼任、数据容易不完整 | 缺失数据、历史迁移、职责兼任、异常恢复、低学习成本 |

**输出**：场景卡、租户画像卡。

**门禁**：场景缺前置条件、异常处理或完成证据时，不进入 S2。

---

### S2 建主链 + 账务事实链

**目的**：确保功能不是孤岛，而是主链上可连续推进的一步，并明确账务落点。

**动作**：

1. 把场景定位到主链的哪一段；跨段拆主场景和关联场景。
2. 画出业务对象链：谁触发、创建/读取/更新哪个对象、下一步交给谁。
3. 画出账务事实链：报价快照 → 合同基线 → 应收/应付 → 收付 → 成本 → 结算/利润；标明每一步的写入时点、快照规则和可回退性。
4. 标注状态变化：成功后哪些对象从什么状态进入什么状态。
5. 标注异常分支：拒绝、返工、变更、撤销、并发、重复提交、历史数据、跨租户。

**输出**：主链卡 + 账务事实链卡。

**门禁**：功能挂不上主链、账务落点不明、异常分支未定义时，不进入 S3。涉及金额/成本/利润时，必须有业务编号或建立 `GAP`。

---

### S3 建条件矩阵（12 维）

**目的**：把场景从「故事」变成「可实现、可测试、可验收」的条件集合。

**12 维条件矩阵**：

| 维度 | 必问问题 |
| --- | --- |
| 角色 | 谁发起、谁确认、谁执行、谁只读？ |
| 组织 | 公司、门店、团队、个人哪个数据范围？ |
| 阶段 | 客户、房屋、报价、合同、项目、任务、验收处于什么状态？ |
| 对象 | 主对象是什么，关联对象是什么，归属链是否完整？ |
| 触发 | 什么事件触发，人工还是系统？ |
| 前置条件 | 必须满足哪些数据、状态和权限才能开始？ |
| 动作 | 谁执行什么，服务端负责什么，端上只呈现什么？ |
| 状态变化 | 成功后哪些对象从什么状态进入什么状态？ |
| 金额/成本 | 金额从哪里来，公式是什么，是否快照，缺失值如何处理？ |
| 数据范围 | 按 Company/Store/Team/Self/参与关系如何隔离？ |
| 例外 | 重复、并发、历史数据、跨租户、缺数据、回退怎么办？ |
| 验收 | 哪些证据证明成功，哪些反例必须失败？ |

**条件优先级**：

1. 权限与租户隔离不满足：阻断。
2. 主对象归属或关联不完整：阻断或进入待确认。
3. 状态不允许：阻断，不接受前端绕过。
4. 主数据/成本缺失：按业务决定阻断，或输出 `null / 不完整`，禁止填 0 伪算。
5. 操作成功：必须写业务事实、状态和审计痕迹。
6. 操作失败：必须可理解、可恢复、可追踪。

**输出**：条件矩阵 + 权限矩阵 + 金额/账务卡 + 例外清单。

**门禁**：任一行无法回答、或回答依赖未确认假设时，要么发起一次业务咨询（最多 5 个阻塞问题），要么标记 `BLOCKED`，不进入 S4。

---

### S4 定信息架构与页面契约

**目的**：把条件矩阵转成「用户能看懂、能操作、能恢复」的界面结构。

**四条原点**：

1. 角色决定工作台，入口由角色 + 权限决定。
2. 首屏三问必须可答。
3. 可见性边界必须正确（内部角色 vs 客户/业主；成本/利润仅 Boss/StoreManager/Finance 可见）。
4. 一屏最多三层信息层级，不堆砌。

**页面唯一性契约（五条硬规则）**：

1. **一个页面只能有一个主对象**：主对象决定标题、身份、中央工作面、状态、主动作、版本和操作记录；其他对象只能作为范围选择、右侧上下文、关联入口、只读摘要或独立深链。
2. **一个状态只能有一个主动作**：`当前状态 -> 唯一主动作 -> 前置条件 -> 服务端处理 -> 新状态 -> 下一步`；其余动作降级为次级按钮或「更多」。
3. **跨对象只做上下文**：阶段切换是对象推进，不是换功能页；必须保留对象上下文；目标阶段无记录时明确显示恢复路径。
4. **页面身份唯一归属**：同一条标题信息只出现一次；禁止面包屑 + hero + 身份条重复表达。
5. **每个可点控件必须有确定结果**：切换、跳转、打开、提交，或明确说明为什么不能点；禁止死控件和假 Tab。

**页面原型（A–F，不允许为单页重新发明骨架）**：

| 原型 | 用途 |
| --- | --- |
| A 决策页 | 首屏给结论、风险、下钻 |
| B 行动队列页 | 我的待办、逾期、待决策 |
| C 对象工作空间 | 一个主对象 + 阶段推进 + 关联上下文 |
| D 专业列表页 | 台账、项目库、流水，支持筛选/批量/比较 |
| E 抽屉/表单页 | 单职责动作，不塞完整页面 |
| F 单据/文档页 | 合同、报价、凭证、PPT 等文档形态 |

**端专属设计**：

- App：角色 Tab + 对象推进 + 现场快捷操作；覆盖 loading / empty / error 三态；下拉刷新、上拉加载、到底提示；375/390/430 适配；安全区。
- Web：角色工作台 + 对象工作空间 + 上下文导航；覆盖 loading / empty / error / 无权限 / 会话过期五态（视觉上七类状态）；1440/1280/1024/768 四断点；键鼠可达；两轮渲染批判。

**输出**：页面冻结卡（页面类型、主对象、唯一主动作、页面结构、复用组件、状态设计、断点/机型、跨端一致点）。

**门禁**：G1 开工门禁 + G1.5 设计冻结门禁未通过，不写代码。

---

### S5 冻结迭代包（R1/R2/R3）

**目的**：在开发前把需求收敛成机器可检查、可交接、可验收的冻结包，避免跨角色反复沟通。

**三轮内迭代**：

| 轮次 | 焦点 | 关键问题 |
| --- | --- | --- |
| R1 因果 | 业务问题是否正确 | 业务问题、当前损失、目标结果、主对象、归属是否正确？ |
| R2 条件 | 条件是否完整 | 角色、状态、权限、金额、异常、幂等、历史数据、反向用例是否完整？ |
| R3 体验 | 体验是否可执行 | App/Web 职责、信息架构、下一动作、设备布局、反馈、规模化是否可执行？ |

**迭代包字段**（结构参考 `.agents/skills/zhuangdeqing-product-app-development/references/iteration-packet.example.json`）：

```text
packet_id | mode | status | decision_owner
scope: goal / in_scope / out_of_scope / fact_sources
tenant_profiles[] | scenarios[] | permission_cases[] | money_cases[] | ux_cases[]
acceptance: positive / negative / evidence / batch_policy
evidence_refs[] | business_questions[] | affected_lanes[]
marketing_evidence_boundary
```

**输出**：冻结迭代包 + 业务咨询单（如有）+ 风险与阻断清单。

**门禁**：

- 使用校验脚本验证迭代包结构。
- R1–R3 期间不跨 Agent 反复沟通；一次业务咨询只提真正阻塞、会改变对象/状态/权限/金额/验收结论的问题，最多 5 个。
- 有未决业务缺口时，包状态为 `blocked` 或 `iterating`，不得进入开发。

---

### S6 实现（后端领域 + 端上体验）

**实现顺序**：先领域与权限，后接口，再页面，最后体验细化。禁止先堆页面再补状态和权限。

**后端五条工程铁律**：

1. **服务 = Provider**：Provider 唯一取代 Controller，入参 `Request` 即领域实体，无 DTO。
2. **前端字段用 Provider 类成员变量 + `@AutoInject` + 校验注解**，不定义 Request 内部类（统计域例外）。
3. **对外响应 = 具体实体对象类型**（`Asset` / `List<Asset>` / `Page<Asset>`），不做 VO/DTO 包装。
4. **实体用对象关联建模**：`Employee emp` 而非 `Long empId`；所有业务实体必须含 `Company company`。
5. **实体序列化按服务用 `@Properties` 过滤**（通用路由用 `@ServiceProperties`），禁止 `@JsonIgnore`。

**Provider 命名**：`{领域}.service.{对象}.{能力}`；能力名固定 `page/list/info/save/build/update/delete/count/enums/tree/report/unique`；路由 `@Service("{域}/{对象}/{能力}")`。登录接口继承 `Security`；当前员工用 `@User` 注入。

**事务与懒加载**：生产保持 `spring.jpa.open-in-view: true` 兜底，但代码必须做到关闭 OSIV 也正确；事务外读取关联用 `@EntityGraph` / `JOIN FETCH` / `@Transactional(readOnly = true)`；只读事务链路禁止调用带锁仓储（`ForUpdate` / `findLockedBy` 必须在写事务）。

**前端工程铁律**：

1. 无 DTO 心智：视图直接消费领域实体，对象关联保持对象形态。
2. 权限先于渲染：菜单/路由/接口三层；服务端仍强校验。
3. 状态机在后端：端上提交后重新拉取。
4. 路由集中管理：所有跳转走集中路由常量，禁止魔法字符串；深链可刷新、直开、会话过期降级。
5. 品牌与 Token 唯一真源：App `src/uni.scss` / `src/styles/tokens.scss` + `JzBrandLogo`；Web `src/styles/tokens.scss` + `BrandLogo`。

**端上分层**：

```text
页面（呈现 + 收集输入）
-> composable / store（跨页交互状态）
-> domain api（领域能力，按领域拆分）
-> core/http（统一契约 { success, data, errorCode }）
```

页面只依赖对应领域 API，禁止直接 `uni.request` / `axios` / 拼 Provider 地址。

**输出**：changed_files、实现说明、自测结果、风险与未完成项。

**门禁**：App `npm run verify:mp-weixin`（类型检查 + 构建 + 分包守卫）；Web `verify:ui / verify:system / type-check / build`，涉及角色再跑 `verify:roles`，涉及经营层再跑 `verify:boss`。静态守卫通过不等于页面交付。

---

### S7 验证（三链 + 证据）

**三链并行**：

1. **正常链**：主链从头到尾可复现。
2. **拒绝/返工链**：报价被拒、合同变更、材料延期、质量整改、业主拒绝验收、逾期回款等。
3. **跨租户负向链**：伪造对象 ID、跨门店/团队/非参与人、替换参数、历史 token、批量导出、并发写入。

**验证矩阵**：

| 类型 | 必覆盖 |
| --- | --- |
| 功能 | 正常、重复、并发、边界、回退 |
| 权限 | 正向可见、负向不可见、跨租户拒绝、详情/更新/删除越权 |
| 状态 | 初始未完成、动作成功后返回、动作失败、可选完成、必做未完成、删除/停用回退、重复进入 |
| 金额 | 公式、快照时点、缺失值、跨页一致、成本不完整不产生伪利润 |
| 体验 | 机型/分辨率、空态、失败、弱网、键盘、安全区、长文本、权限提示 |
| 跨端 | App/Web 同一对象、状态、责任人、金额、下一步一致 |
| 兼容 | Web 共享后端改动不破坏 App 已依赖的路由、参数、字段语义、状态机、金额/权限口径、列类型 |

**证据粒度**：每步记录租户、角色、设备、时间、路由、对象 ID、前置状态、动作、页面反馈、接口/状态码、服务端状态变化、账务写入、截图/视频、期望/实际/偏差/影响/恢复路径。

**问题分级**：

- `P0`：越权、跨租户泄漏、资金/成本错误、主链错误、数据不可恢复。
- `P1`：关键角色无法完成任务、状态失配、重复记账、异常无恢复。
- `P2`：明显增加工作量、跨端口径不一致、交互误导、适配阻塞。
- `P3`：文案、视觉层级、低风险一致性或可访问性问题。

**输出**：验收矩阵 + 证据包 + `PASS / FAIL / BLOCKED / NOT_TESTED` 清单。

**门禁**：G2 交付门禁 + G3 视觉门禁未通过，不得表述为「页面已完成」；只有 acceptance 或用户指定责任方可出独立验收结论。

---

### S8 回写知识与沉淀规则

**目的**：让每次修复都变成下一次可复用的规则，而不是一次性补丁。

**动作**：

1. 业务口径变化：向业务智能体提出 `EV-*` / 知识卡更新建议，必要时建立 `GAP`。
2. BUG / 需求变更：按四角色流程沉淀：
   - 诊断工程师：复现、定位代码、写根因。
   - 修复工程师：改代码、加注释（标注历史坑点 FIX 编号）、跑门禁。
   - 资深业务观察者：从行业对标、销售→履约闭环、多角色权限与数据隔离、空态降级四维审查。
   - 流程沉淀官：更新 `log.md`、`business-rules.md`，操作口径变化时更新 `user-guide.md`。
3. 工程约束变化：同步更新 `AGENTS.md`、`rules.md`、Token 真源与校验脚本。
4. 同话题工作记录：在 `_系统/协作/工作约定.md`「近期改动」追加一行，不写重复交接包。
5. 发布批次：写 `docs/operations/releases/*.md`；生产事故归档可处理异常。

**硬性要求**：

- 不允许只改代码不沉淀。
- 不允许用 `|| list[0]`、`any`、静默兜底掩盖数据串号或权限问题。
- 涉及客户/项目/报价关联数据的详情页，必须按当前实体 ID 过滤，禁止全量拉取前端 find。
- 代码注释必须标注「历史坑：FIX-XXX」，防止后续维护者加回兜底。

## 3. 标准规范层：可直接执行的产品标准

### 3.1 场景与需求规格标准

任何需求规格至少包含以下 12 块：

```text
1. 批次 ID / 模式 / 状态 / 日期
2. 事实来源（业务编号、设计、代码、验收证据）
3. 租户画像与目标角色
4. 至少 2 个真实场景（全链 3 个租户画像）
5. 主链定位与账务事实链
6. 对象 / 状态 / 责任人 / 数据范围
7. 权限矩阵（正向 + 负向 + 跨租户）
8. 金额 / 成本 / 利润口径与缺失值处理
9. 信息架构 / 页面结构与唯一主动作
10. 异常、空态、失败、并发、幂等、回退
11. 验收矩阵与证据要求
12. 明确不做什么（out of scope）与待确认项
```

**需求冻结合格线**：

- 场景能闭环，不靠口头补录。
- 每个动作有前置条件、状态变化和留痕。
- 每个金额有来源、公式、快照时点、缺失值处理。
- 每个角色有可见/可操作/禁止三列。
- 每个异常有阻断、降级或补偿路径。
- 每个验收项有正向和反向。

---

### 3.2 对象、状态与责任标准

**对象建模**：

- 主对象必须唯一、可识别、可追溯；关联对象保持对象形态。
- 业务实体必须直接归属企业；归属是业务快照，转交/调店/调团队时必须明确更新规则。
- 一张业务表对应一个清晰领域对象；禁止用「一个大 JSON」或「前端拼装结构」替代领域建模。

**状态建模**：

- 状态机由后端定义，状态之间必须有明确触发动作、前置条件和责任人。
- 派生字段不得作为事实源；项目级状态与当前阶段不得互相矛盾。
- 状态推进方向明确；回退、撤销、重开必须有业务条件和审计留痕。
- 状态展示必须有统一语义色板；禁止一个状态在不同页面用不同颜色或文案。

**责任建模**：

- 每个对象有明确负责人（`owner`）；负责人变更必须留痕并影响数据范围。
- 每个待办/风险有责任人、截止时间、升级规则和下一步。
- 跨角色交接必须产生可被下一角色读取的事实，不能依赖口头或消息。

**客户/业主可见性边界**：

- 客户/业主侧只展示可公开的业务事实；不展示内部成本、供应商信息、员工隐私（手机号、绩效等）。
- 员工侧按数据范围裁剪；成本价、成本明细、利润、毛利率仅企业负责人、店长、财务可见。
- 不是「隐藏数字」，而是不生成无权限区块。

---

### 3.3 权限与数据范围标准

**四件事先定**：企业归属、角色能力、数据范围、操作动作。权限校验属于服务端强逻辑。

**三层可见性**：

| 层 | 要求 | 反例 |
| --- | --- | --- |
| 菜单/入口 | 无权限功能不暴露 | 菜单显示但点进去 403 |
| 路由守卫 | 深链接直开也降级 | 刷新页面绕过前端隐藏 |
| 接口拒绝 | 服务端强制校验 | 只靠前端隐藏按钮 |

**数据范围矩阵**：

| 角色 | 默认范围 |
| --- | --- |
| Boss | Company |
| StoreManager | Store |
| TeamLeader | Team |
| 普通员工 | Self + 项目参与关系 |

**硬性规则**：

- 当前企业、角色、门店、团队、员工一律从登录态加载；禁止信任前端传入的 `companyId / empId / ownerId / storeId / teamId`。
- 分页/列表/计数由统一过滤器追加范围；自定义详情/更新/删除用 `DataScopeContext + DataScopeSpecification`；禁止 `findById` 后自行判断。
- 保存时企业取登录员工所属企业；非 BOSS 负责人强制为当前员工。
- 业务表按权限维度建联合索引，`com_id` 最左。
- 每个有数据权限的领域补齐：四角色、伪造参数、跨企业、详情越权、更新/删除越权测试。

**权限矩阵模板**：

| 角色 | 数据范围 | 可见 | 可操作 | 禁止 | 负向用例 |
| --- | --- | --- | --- | --- | --- |
| Boss | Company |  |  |  |  |
| StoreManager | Store |  |  |  |  |
| TeamLeader | Team |  |  |  |  |
| 普通员工 | Self/项目参与 |  |  |  |  |
| 跨企业用户 | 无 |  |  | 全部拒绝 | 伪造对象 ID |

### 3.4 金额、成本与利润标准

**五条铁律**：

1. 销售价与成本价分离：销售价（`materialPrice` / `manualPrice` 等）与标准成本（`costPrice`）不得混用。
2. 项目成本统一由 `ProjectCostContext` 汇总；预计成本优先签约快照，实际成本优先采购到货/入库。
3. 任一应计成本缺失时 `costComplete=false`；利润与毛利率必须返回 `null`。
4. 实际材料成本只在到货/入库累计；领料与损耗只流转库存；退换货按类型冲减；禁止重复累计。
5. 历史价（`PartnerPrice`）不再作为标准成本必需来源。

**金额/账务卡模板**：

```text
金额名称：
业务来源：报价快照 / 合同基线 / 采购到货 / 收款登记 / 手工记账
计算公式：
快照时点：
数据范围：
周期与 asOf：
缺失值处理：
跨页一致性：报价 / 合同 / 项目 / 财务 / App / Web
权限：谁可见、谁可改
审计与回退：
```

**前端展示规则**：

- 金额统一走 `JzMoney` / `money()` 等统一格式化组件或函数，禁止页面自行拼接。
- 经营数字必须带口径、周期和数据截止时间 `asOf`。
- 成本不完整统一走 `CostIncompleteValue` 显示「成本未完整」，禁止 0 成本伪利润。
- 汇总金额以后端为准，前端不得用当前页记录重算全量。
- 数字使用等宽数字（`tabular-nums` / `tnum`），保证对齐和可读性。

### 3.5 可完成状态投影标准

适用于首次入驻、实施清单、待办、资料完整度、节点进度、审批进度、质量检查清单。

**编码前必须冻结**：

```text
key / label / required / source_provider / completion_predicate / count
/ refresh_triggers / next_action / 异常态
```

**完成事实规则**：

- 完成状态只能来自当前租户真实领域对象和明确谓词。
- 禁止 `done:true/false`、演示数据、接口 `success=true` 或仅前端本地布尔。
- 接口异常、数据缺失、分页无法证明全量时，状态为「暂不可确认」，不得折叠为确定完成或确定未完成。
- 分母区分必做与可选；可选完成不得改变必做分母、必做完成数和必做下一步。
- 新增、编辑、删除、停用、状态回退必须反映到下一次投影。
- 可变进度必须在页面重新显示、下拉刷新或跨页写入后重新读取，或使用明确失效机制收敛。

**验收最低矩阵**：

| 用例 | 预期 |
| --- | --- |
| 初始未完成 | 必做分母、完成数、下一步正确 |
| 动作成功后返回 | 状态收敛，计数增加，下一步更新 |
| 动作失败 | 显示「暂不可确认」并保留恢复路径 |
| 可选完成 | 必做分母不变 |
| 必做未完成 | 不得显示 100% 或完成 |
| 删除/停用回退 | 完成状态回退 |
| 重复进入 | 不重复计数、不错误推进 |

**反例**：`FIX-004 / ECD-008`，供应商步骤曾写死未完成且返回首页不刷新。

### 3.6 App（微信小程序）交互与视觉标准

**工程与目录**：

- 技术栈：uni-app + Vue3 `<script setup lang="ts">` + TypeScript + Vite；样式 SCSS scoped + Design Token。
- 主包只放启动页、登录/授权页、加入/创建企业页和 `TAB_PATHS` 中的自定义 Tab 页；其他业务页一律分包。
- 领域模块统一放 `src/domains/<domain>`，至少含 `model.ts / api.ts / meta.ts`；页面只依赖领域 API。
- 路由统一走 `src/config/index.ts` 的 `P.*`；禁止魔法路径字符串。

**Design Token（唯一真源）**：

- 当前真源 `src/uni.scss`；目标真源 `src/styles/tokens.scss`；迁移前禁止两套混用。
- 所有颜色、字号、间距、圆角、阴影、动效从 Token 取值；禁止硬编码色值/字号/圆角/阴影。
- 基准 750rpx；间距只用 8 的倍数（8/16/24/32/40/48/64/80）；页面左右安全边距统一 `$page-gutter`（32rpx）。
- 单页面圆角种类 ≤ 2；一屏实心主按钮 ≤ 1；辅助色（价格/优惠/限时/徽标）用量 ≤ 10%。
- 禁止纯黑 `#000` / 纯灰 `#999`；禁止 emoji、字符箭头、字符加号代替图标。
- 品牌 Logo 只用 `logo-export` 同一套 Mark，通过 `JzBrandLogo` 引用。

**交互状态**：

- 每个可交互元素定义 `默认 / active / disabled`；H5 额外 `hover / focus`。
- 所有异步数据展示覆盖三态：loading（骨架屏优先）、empty（插画 + 引导文案 + 引导按钮）、error（说明 + 重试）。
- 点击反馈 300ms 内出现；按钮防重复点击；破坏性操作二次确认。
- 长列表支持下拉刷新、上拉加载、到底提示；> 100 条分页或虚拟列表。
- 表单必填标记、失焦校验、错误提示在输入框下方；校验通过前提交按钮禁用；键盘不遮挡输入框。
- 引导/进度/待办遵循 §3.5。

**多端适配**：

- H5 容器 `max-width: 750px; margin: 0 auto`；底部固定元素加安全区；顶部自定义导航处理 `$safe-top`。
- 禁止 `document / window / localStorage`；统一 `uni.xxx`。
- 图片懒加载、占位、失败兜底；小程序图片域名白名单。
- 首批图标、组件、资源按需引入；组件单文件 ≤ 300 行，页面单文件 ≤ 500 行。

**分包纪律**：

- 主包 ≤ 2MB，单分包 ≤ 2MB，总包 ≤ 20MB。
- 禁止主包引用分包私有资源，禁止分包 A 引用分包 B 私有资源。
- 两包以上复用组件放主包 `src/components`；仅一个分包使用放分包私有目录。
- 新增业务模块优先新增独立业务分包，禁止「先放主包以后再迁移」。
- 提交前运行 `npm run verify:mp-weixin`（类型检查 + 构建 + 分包守卫）。

**多机型验收**：

- 至少 375、390、430 宽逻辑像素；覆盖安全区、状态栏、底部手势区。
- 检查长企业名、长中文、金额、日期、空态、加载、失败、键盘弹起和横竖屏边界。
- 禁止文字截断无提示、卡片互相覆盖、按钮跳出安全区、横向滚动、浮层遮挡主操作。

### 3.7 Web（企业工作台）交互与视觉标准

**产品定位**：Web 不是「页面集合」，是面向中小装企的高效经营 ERP。Web 只做宽屏优势：批量、比较、对账、排期、审批、经营分析；不复制 App 现场主路径。

**四条判定**：

1. 每个角色有一条可跑通的主链闭环。
2. 首屏可答三问，主任务 ≤ 3 次操作。
3. 同一业务事实在 App 与 Web 同源同口径。
4. 有真实渲染证据与独立验收结论。

**页面唯一性契约**：同 §2 S4。核心是「一个页面一个主对象、一个状态一个主动作、跨对象只做上下文、身份唯一归属、控件必有确定结果」。

**三层交互结构**：

```text
全局层：壳层导航 / 角色工作台 / 全局搜索与通知
对象层：对象身份条 / 阶段模式栏 / 中央工作面
动作层：抽屉 / 弹层 / 小表单，单职责，不塞完整页面
```

**设计语言（Quiet Enterprise）**：

- 层级：一屏最多三层。
- 颜色：90 / 9 / 1（主色克制、辅助色少量、状态色点睛）。
- 字阶冻结：正文最小 13px；禁止 9 / 9.5 / 10 / 10.5 / 11.5px。
- 断点冻结：1440 / 1280 / 1024 / 768。
- Token 真源 `src/styles/tokens.scss`；已废弃冷灰蓝调色板禁止新增。
- 页面不得自造卡片、状态标签、抽屉、空态、错误态；未登记组件不得新增。
- 可访问性：关键路径可仅用键盘完成；弹层 `Esc` 关闭并归还焦点；禁止 `outline: none`；不能只靠颜色表达状态。

**七类状态（缺一不可）**：加载、空、错误、无权限、会话过期、部分完成、完成。

**视觉批判循环（强制）**：

```text
渲染 -> 按反模式清单批判 -> 修正 -> 再渲染（至少两轮）
```

- 视觉量规 C1–C8：任一 < 3 不得交付；主链页面平均 ≥ 3.5。
- 视觉债务只减不增；禁止抬高 `scripts/ui-craft-baseline.json`。

**Web 页面门禁**：

- G1 开工门禁：场景、对象与状态、权限矩阵、金额口径、可完成状态投影、页面结构与复用、分辨率与跨端、App 线上兼容影响。
- G1.5 设计冻结：页面类型、唯一主行动、信息优先级（≤3 层）、构图模板、七类状态、设计意图七问。
- G2 交付门禁：工程检查、渲染证据、状态矩阵、权限负向、分辨率与键鼠、跨端一致、App 兼容回归、记录。
- G3 视觉门禁：C1–C8、两轮视觉批判、UI Craft Guard。

### 3.8 跨端一致性标准（App / Web / 其他端）

**最高优先级铁律**：App 线上兼容优先。Web 开发必须保证 App 正常运行，不破坏 App 现有逻辑。

**共享后端改动约束**：

- 不得改变 App 已依赖的 Provider 路由、请求参数、响应字段语义、状态机、金额/成本/权限口径、数据库列类型或既有业务行为。
- 共享后端改动必须向后兼容、先加法后迁移。
- 完成 App 类型检查/构建/关键链路回归后才能发布。
- 共享后端与 Web 发布发生风险时，以 App 线上稳定优先，立即停止或回滚 Web 相关改动。

**跨端对齐点**：

| 对齐项 | 要求 |
| --- | --- |
| 对象 | 同一业务对象、同一 ID、同一归属 |
| 状态 | 同一状态机、同一状态名、同一语义色 |
| 责任人 | 同一负责人、同一数据范围 |
| 金额 | 同一来源、同一公式、同一 `asOf` |
| 下一步 | 同一前置条件、同一完成条件 |
| 权限 | 同一角色/数据范围矩阵 |
| 术语 | 同一业务术语，不同端不造新词 |

**端能力分工矩阵**：同 §0.5。任何端的新页面必须回答「为什么在这个端做，而不是另一个端」。

**跨端回归门禁**：

- 共享后端改动必须列出受影响的 App 路由/字段/页面，并做关键链路回归。
- 无法证明 App 不受影响时，Web 页面不得进入编码。
- App 与 Web 不一致时建立 `DEF-*`，在 `_系统/协作/shared.md` 登记，禁止单端改文案掩盖。

---

### 3.9 工程质量标准

**通用红线**：

- 禁止 `any`；类型不明确用 `unknown` + 类型守卫。
- 禁止 `!important`、行内 style（动态计算除外）、index 作为 `v-for` key。
- 禁止静默兜底（`|| []`、`|| 0`、`list[0]`）掩盖后端缺失或数据串号。
- 禁止新增 mock、演示数据或页面内本地持久化。
- 禁止死代码、死控件、假 Tab、无 handler 的按钮。
- 禁止在页面维护业务状态机、重算业务金额、硬编码完成状态。

**命名与结构**：

- 组件 PascalCase；组件目录与文件同名；页面 kebab-case；变量/函数 camelCase；常量 UPPER_SNAKE_CASE；类型 PascalCase。
- CSS 使用 BEM；嵌套 ≤ 3 层；`:deep()` 仅用于覆盖第三方组件。
- 导入顺序固定：vue 核心 → 第三方 → 项目绝对路径 → 项目相对路径 → 类型。
- 页面逻辑抽 composable / domain API / store；能 `computed` 的不 `watch` 重复计算。

**事务与数据访问**：

- 只读事务链路禁止调用带锁仓储；`ForUpdate` / `findLockedBy` 必须在写事务。
- 涉及关联的测试显式 `open-in-view=false` 且不加 `@Transactional`。
- 长文本字段与迁移一致（`ddl-auto: update` 不改既有列类型，需补 `alter table ... longtext`）。
- 序列化按服务裁剪，关联对象用 `@AllowProperties` 最小白名单，避免对象循环。

**发布与回滚**：

- 生产部署统一使用 `scripts/deploy-prod.sh`，失败自动回滚到上一稳定 release。
- 长期分支只有 `dev / test / prod`；短分支合入后立即删除。
- 小修复不强制 RC tag；L3 必须从已确认提交构建，执行备份和回滚检查。
- 生产发布后必须健康检查和核心路径冒烟。

---

### 3.10 内容与文案标准

- 使用简洁业务语言，不写开发术语；禁止「状态 3」「记录 1」这类编号表达。
- 标题不超过 16 个中文字符；列表标题单行省略。
- 按钮用动词短语：`提交报价`、`保存方案`、`开始阶段`、`确认验收`。
- 同一动作只有一个名称；禁止「设计转化」与「开始设计转化」并存。
- 空态文案必须包含下一步；无权限文案必须解释原因；失败文案必须说明「发生了什么、为什么、如何恢复、谁负责」。
- 空值统一显示 `—`，不得「无 / 暂无数据 / 尚未录入」混用。
- 金额、面积、数量、编号等数字使用统一格式，长编号可折叠、可复制。

---

### 3.11 数据、隐私与审计标准

- 只使用专用测试企业、测试项目和合成数据做演示/录制；禁止把生产客户隐私用于营销或测试。
- 截图/视频/日志必须脱敏；CLI token、Cookie、登录凭证和敏感请求头不得写入日志。
- 删除、签署、付款、验收确认、邀请、消息发送等动作必须单独授权并定义回滚。
- 每个业务动作必须写业务事实、状态和审计痕迹；重要变更可追溯。
- 生产数据迁移/删除必须备份、脱敏变更记录、核验命令和回滚路径。

## 4. 统一质量门禁：G0–G4

在 Web 既有 G1 / G1.5 / G2 / G3 基础上，向前补 G0 需求门禁，向后补 G4 发布门禁，形成跨端统一的五道门。

```text
G0 需求门禁（场景与事实）
-> G1 开工门禁（条件与权限）
-> G1.5 设计冻结（页面与交互）
-> 实现
-> G2 交付门禁（工程与状态）
-> G3 视觉门禁（渲染与量规）
-> G4 发布门禁（兼容与回滚）
```

### G0 需求门禁（进入设计前）

- [ ] 至少 2 个真实场景；全链至少 3 个租户画像。
- [ ] 使用人、触发、前置条件、动作、系统下一步、异常处理、完成证据齐全。
- [ ] 主链定位明确；账务事实链（如涉及）明确。
- [ ] 业务事实来源有编号；冲突项建立 `GAP`。
- [ ] 明确不做什么。
- [ ] 变更级别（L0–L3）已判定。

**不合格的表现**：只有功能名、只有页面草图、只有数据表字段、直接进入编码。

---

### G1 开工门禁（编码前）

- [ ] 场景（≥2）冻结。
- [ ] 对象与状态：页面归属锚点、领域对象、Provider、状态来源、完成后重新读取方式。
- [ ] 权限矩阵：角色 × 数据范围 × 可见 × 可操作 × 禁止；含至少一条跨企业负向用例。
- [ ] 金额/账务：来源、公式、快照时点、`asOf`、缺失值处理、跨页一致。
- [ ] 可完成状态投影（如适用）：`key / label / required / 完成条件 / 异常态`。
- [ ] 页面结构与复用：页面类型、主行动唯一、次要动作降级、复用组件、五态处理。
- [ ] 分辨率与跨端：App 机型 / Web 断点；与另一端对齐点。
- [ ] App 线上兼容影响（Web/共享后端改动时）：是否触碰 App 依赖的契约，回归范围与证据。
- [ ] 候选迭代包通过结构校验。

**不合格的表现**：先写页面、权限后补、金额口径「大概这样」、完成状态写死。

---

### G1.5 设计冻结（编码前，UI 专项）

- [ ] 页面类型（决策页 / 行动队列 / 对象工作空间 / 专业列表 / 抽屉表单 / 单据文档）。
- [ ] 唯一主对象、唯一主动作、主行动降级方式。
- [ ] 信息优先级 ≤ 3 层；首屏能回答三问。
- [ ] 构图模板与复用组件清单。
- [ ] 七类状态设计：加载 / 空 / 错误 / 无权限 / 会话过期 / 部分完成 / 完成。
- [ ] 设计意图七问：给谁用、解决什么、为什么现在、主对象、主动作、完成后状态、异常怎么办。
- [ ] 设计 Token 与组件均来自唯一真源；无新 Token 未审批。

**不合格的表现**：直接套模板不考虑对象与角色、自造组件、自造颜色、多主对象、多 CTA。

---

### G2 交付门禁（交付前）

- [ ] 工程检查：类型检查、构建、守卫脚本（App `verify:mp-weixin`；Web `verify:ui/system`、`type-check`、`build`）。
- [ ] 渲染证据：App 真实 Mini Program 页面 + 多机型截图/录屏；Web 真实浏览器 + 四断点截图/URL。
- [ ] 状态矩阵：初始未完成、成功后返回、失败、可选完成、必做未完成、删除/停用回退、重复进入。
- [ ] 权限负向：四角色、伪造参数、跨企业、详情/更新/删除越权。
- [ ] 分辨率与键鼠/机型：App 375/390/430；Web 1440/1280/1024/768；安全区与键盘。
- [ ] 跨端一致：同一对象、状态、责任人、金额、下一步。
- [ ] App 线上兼容回归（如适用）。
- [ ] 记录：changed_files、verification、risks、next_action、acceptance_needed。

**不合格的表现**：类型检查通过即宣布完成；只测正向；不附截图/URL；只测一种分辨率。

---

### G3 视觉门禁（UI 专项，交付前）

- [ ] 两轮以上「渲染 → 批判 → 修正 → 再渲染」。
- [ ] 视觉量规 C1–C8：任一 < 3 不得交付；主链页面平均 ≥ 3.5。
- [ ] 无第二套设计语言、非 Token 颜色、< 13px 正文（Web）、< 24rpx caption（App）。
- [ ] 无死控件、假 Tab、重复标题、卡片堆砌、颜色单独表意。
- [ ] 视觉债务只减不增。

**不合格的表现**：仅凭代码判断视觉；未渲染就交付；新增债务不登记。

---

### G4 发布门禁（发布前/后）

- [ ] 变更级别与验证匹配：L0/L1 定向；L2 批次回归；L3 全量 + 备份 + 回滚 + 用户确认。
- [ ] 生产部署使用 `scripts/deploy-prod.sh`，保留上一稳定 release。
- [ ] 密钥、证书、真实用户数据未进入仓库。
- [ ] 发布后健康检查与核心路径冒烟。
- [ ] 失败自动回滚；同一事故单次最多发布 1 次。
- [ ] 发布记录写入 `docs/operations/releases/*.md`。
- [ ] 高风险修复等待独立验证，不自行宣布 `VERIFIED`。

---

### 4.1 完成定义（Definition of Done）

一个需求/迭代只有同时满足以下条件，才可称为完成：

1. 至少 2 个真实场景闭环；全链批次至少 3 个租户画像。
2. 角色、对象、状态、权限、金额、异常、幂等、审计条件完整。
3. 正向、拒绝/返工、跨租户负向三链可复现。
4. 页面有真实渲染证据，状态矩阵和权限负向通过。
5. App/Web 同源同口径，共享后端不破坏 App。
6. 业务口径、实现证据和独立验收结论不互相冒充。
7. 业务咨询、冲突、缺口和对外表达边界明确。
8. 所有结论可追溯到业务编号、代码/页面、测试/验收或用户决策。
9. 本轮的工程约束/业务规则/用户操作口径已按需回写。

## 5. 反模式与事故清单（违反即重写/阻断）

反模式来自实际 FIX、ECD、DEF、GAP 和审计经验。其价值在于：**看到模式就提前阻断，而不是等事故后再修**。

### 5.1 数据与权限类（P0 红线）

| 反模式 | 为什么危险 | 正解 |
| --- | --- | --- |
| 用 `list[0]` / 全量拉取前端 find 替代按 ID 过滤 | 详情页串号，A 客户看到 B 客户数据 | 按当前实体 ID 查询；后端按数据范围过滤 |
| `findById(id)` 后自行判断企业/负责人 | 详情/更新/删除越权 | `DataScopeContext + DataScopeSpecification` |
| 信任前端 `companyId/empId/ownerId` | 跨租户写入 | 从登录态加载企业、角色、门店 |
| 只做菜单隐藏，不做路由/接口校验 | 深链和接口越权 | 三层可见性缺一不可 |
| 跨域读取直接 `findById` | 绕过企业与数据范围 | 跨域查询也携带 `DataScopeSpecification` |
| 只测接口可调用 | 越权未被发现 | 四角色 + 跨企业 + 详情/更新/删除负向 |
| 调店/转交时不更新归属快照 | 数据范围错乱 | 明确并测试归属更新规则 |

### 5.2 状态与完成类

| 反模式 | 为什么危险 | 正解 |
| --- | --- | --- |
| `done:true`、前端本地布尔、演示数据 | 伪完成，误导经营决策 | 真实领域对象 + 完成谓词 |
| 返回页面不刷新可变状态 | 用户看到过期进度 | 重新显示/跨页写入失效机制 |
| 接口失败返回空数组 | 把「暂不可确认」伪装成「确定没有」 | 明确错误态与恢复路径 |
| 前端维护状态机 | App/Web 分叉、刷新回退 | 后端状态机，端上重新拉取 |
| 派生字段作为事实源 | 状态与阶段矛盾 | 现场从领域事实推导 |
| 项目级状态与当前阶段各自更新 | 页面自相矛盾 | 统一状态推导与校验 |

### 5.3 金额与成本类（P0 红线）

| 反模式 | 为什么危险 | 正解 |
| --- | --- | --- |
| 成本不完整按 0 计算利润 | 伪利润，经营误判 | `costComplete=false` → 利润 `null` +「成本未完整」 |
| 前端用当前页记录重算汇总 | 与后端口径不一致 | 汇总以后端为准 |
| 报价/合同/项目各算一套金额 | 跨页不一致，客户争议 | 报价快照 → 合同基线 → 项目/财务同源 |
| 实际材料成本重复累计 | 成本虚高 | 只在到货/入库累计；领料/损耗只流转库存 |
| 退换货不按类型冲减 | 成本错误 | 按退货类型冲减 |
| 历史价当标准成本必需来源 | 口径混乱 | `PartnerPrice` 不再作为标准成本必需来源 |

### 5.4 信息架构与交互类

| 反模式 | 为什么危险 | 正解 |
| --- | --- | --- |
| 一个页面多个主对象/多个同级主动作 | 用户不知道做什么 | 一对象一工作面、一状态一主动作 |
| 中央 Tab 混入客户/房屋/报价/合同/项目 | 对象上下文断裂 | 同一主对象的 Tab 才能同级 |
| 同一件事表达三遍 | 信息噪音，越改越乱 | 同一信息只表达一次 |
| 空态只说「暂无数据」 | 用户无路可走 | 插画 + 原因 + 引导按钮 |
| 无权限只说「无数据」 | 用户误解并反复尝试 | 解释原因与申请路径 |
| 死控件、假 Tab | 用户失去信任 | 每个可点控件有确定结果 |
| 先选功能菜单再选业务对象 | 增加判断成本 | 从对象/角色入口直接推进 |
| 一屏多个实心主按钮 | 主动作不明确 | 一屏一个实心主 CTA |
| 用颜色单独表达状态 | 无障碍与误读 | 颜色 + 文案 + 图标 |
| 抽屉塞完整业务页面 | 交互层级混乱 | 抽屉只做单职责小表单 |

### 5.5 工程与协作类

| 反模式 | 为什么危险 | 正解 |
| --- | --- | --- |
| 硬编码色值/字号/圆角/阴影 | 品牌与体验分裂 | 唯一 Token 真源 |
| 两套 Token / 两套壳层 / 两套路由 | 页面割裂、重复维护 | 一次性迁移，禁止长期双真源 |
| `any`、`!important`、index 作 key | 类型与样式债务 | 类型守卫、类名、稳定 key |
| 只改代码不沉淀 | 同类问题反复发生 | Fix 四角色流程 + 规则回写 |
| 自测通过写成独立验收通过 | 风险被掩盖 | 明确区分自测/验收/生产事实 |
| 小改动跑全量、大改动图省事 | 成本与风险都错配 | 变更分级 L0–L3 |
| Web 改坏 App 共享契约 | 线上 App 故障 | App 兼容优先；向后兼容；共享回归 |

### 5.6 跨端类

| 反模式 | 为什么危险 | 正解 |
| --- | --- | --- |
| 把 App 信息流放大成 Web 卡堆 | 宽屏效率低 | Web 做批量/对账/排期/分析 |
| 把 Web 批量页硬塞进 App | 现场体验差、包体大 | App 做现场快捷与即时反馈 |
| 两端各造一套术语 | 培训与沟通成本高 | 同一业务术语 |
| 用一端文案掩盖另一端错误 | 事实不一致 | 建 `DEF-*`，统一真源修复 |
| 共享后端先改语义再通知 | App 线上故障 | 先加法后迁移，App 回归后才发布 |

## 6. 复用与推广：从装得清 App 到 Web 和其他产品

### 6.1 可复用的「产品工厂」资产

装得清 App 的价值不只在于功能，而在于形成了一套可迁移的资产。后续做 Web、Admin 或新产品时，应优先复用这七层资产，而不是重新发明。

| 层 | 资产 | 复用方式 |
| --- | --- | --- |
| 事实治理层 | 业务知识库（`SCN/BR/SOL/MET/CAP/DEC/GAP/EV` + 证据注册表） | 所有产品共用同一事实源；新产品先建自己的事实源，但沿用治理结构 |
| 场景引擎层 | 12 维条件矩阵、主链定位、租户画像、场景卡模板 | 换行业时替换业务内容，保留方法结构 |
| 领域模型层 | `Company` 归属、对象关联、无 DTO、状态机在后端、快照与事实链 | 直接作为建模规范复用 |
| 权限骨架层 | 7 角色、Company/Store/Team/Self、三层可见性、DataScope 组件 | 换角色名与范围，保留鉴权骨架和负向测试方法 |
| 账务骨架层 | 报价快照 → 合同基线 → 应收应付 → 收付 → 成本 → 结算/利润；成本完整性 | 换行业金额模型时保留「快照 + 完整性 + 不伪造」原则 |
| 端体验层 | App/Web Design Token、组件清单、页面原型 A–F、状态设计、文案规范 | 组件和 Token 可按品牌替换，页面契约与状态覆盖直接复用 |
| 质量与协作层 | G0–G4 门禁、三链验证、证据链、Fix 四角色、变更分级 L0–L3 | 直接复用为交付与发布标准 |

### 6.2 新端接入清单

新增一个端（如平板、H5、桌面客户端、第三方小程序）时，按以下顺序落地：

**第一步：定位端职责**

- [ ] 这个端服务哪些角色？
- [ ] 它做现场执行、宽屏效率、经营分析，还是特定场景？
- [ ] 它与 App/Web 的分工边界是什么？
- [ ] 是否有能力做而另一个端不能做的独特价值？

**第二步：复用事实与权限**

- [ ] 不新建第二套业务对象、状态、金额口径。
- [ ] 复用同一 Provider 契约与数据范围。
- [ ] 明确深链、刷新、会话过期、无权限的降级路径。
- [ ] 共享后端改动遵守 App 线上兼容优先。

**第三步：建立端设计真源**

- [ ] 选择端专属页面原型与信息层级。
- [ ] 建立唯一 Token 真源与组件清单。

### 6.3 新产品 / 新业务冷启动清单

从 0 到 1 构建一个新产品或新业务域时，建议按以下顺序：

```text
1. 建事实源治理结构（AGENTS/SKILL/registry/知识卡模板）
2. 定义目标客户与租户画像（至少 3 类）
3. 画出行业主链与账务事实链
4. 定义角色与数据范围骨架
5. 选 1 条最高频主链做 0-1 闭环（不铺全模块）
6. 建端设计真源（Token/组件/页面原型）
7. 建权限/账务/审计底座
8. 建门禁与验收协议
9. 用 3 个租户画像跑正常/拒绝/跨租户三链
10. 沉淀规则、模板、组件，再复制到第二条主链
```

**关键判断**：

- 第一版不追求功能全，追求**一条主链真实闭环**。
- 先做「事实写入 + 状态推进 + 权限 + 账务」，再做「批量、报表、AI 增强」。
- 每新增一个模块，先问它挂在哪条主链、哪个角色、哪个状态。
- 专业能力可以作为独立能力建设，但不能直接占据一级导航。

### 6.5 AI 智能体协作标准

当前研发由 AI 智能体参与，因此方法必须包含「智能体如何协作」的标准。

**五种运行模式**：

| 模式 | 用途 |
| --- | --- |
| `tenant_onboarding` | 新企业入驻、团队、门店、席位、首个可执行项目 |
| `full_chain_simulation` | 一个具体房屋跑通线索到整改、账务和利润 |
| `feature_iteration` | 围绕一个业务断点完成场景、主链、权限、账务、交互、验收 |
| `ux_review` | 按角色、设备、状态检查信息层级、操作路径、反馈与可恢复性 |
| `batch_validation` | 3–5 个冻结需求或一个里程碑集中独立验证 |

**协作原则**：

- R1–R3 由当前责任 Agent 本地迭代，不向其他智能体逐轮同步。
- 一次业务咨询只提真正阻塞、会改变对象/状态/权限/金额/验收结论的问题，最多 5 个。
- 交给开发前必须有冻结包；交给验收前一次交付 3–5 个需求或完整里程碑。
- 只传事实源路径、差异、决策和验收证据，不复制整版知识库、聊天记录和重复代码。
- 不使用子 Agent 做可由本地单线程完成的普通创建、小改或重复阅读；确需并行时先明确授权并拆成互不重叠的写范围。
- 每次 Agent 通信必须回答「若不通信用会错误决策什么」；否则不发送。

**跨智能体问题闭环**：

```text
MKT_REPORTED -> BIZ_TRIAGE -> BIZ_DECIDED
-> DEV_IN_PROGRESS -> DEV_FIXED
-> LEARNING_ACK -> VERIFIED -> MKT_UNLOCKED
```

- 业务智能体负责事实裁决，产品研发负责实现，验收负责最终通过，学习智能体负责沉淀。
- 高风险修复等待 acceptance 或用户指定责任方独立验证。
- 不直接宣布 `VERIFIED` 或 `MKT_UNLOCKED`。

**业务咨询门禁**：涉及业务对象、状态机、角色权限、数据范围、金额、成本、利润、指标、客户可见性、场景匹配或对外口径时，必须先调用 `zhuangdeqing-business` 并读取规范事实源。

### 6.6 规范治理：总纲 + 分支，唯一真源

**反双真源原则**：

- 每个领域只有一个真源：业务口径回业务知识库；工程约束回各仓库 `AGENTS.md/rules.md`；Token 回 `tokens.scss`；页面标准回总纲；验收只由 acceptance 出具。
- 总纲定「必须遵守什么」，分支文件定「怎么实现」；冲突以总纲为准并回改分支。
- 修改总纲/真源必须给出：批次 ID、变更原因、受影响页面、迁移计划、回滚点。
- 文档数值必须与运行值一致；修改 Token 文档后同步检查 Token 源、组件和守卫脚本。
- 重复文档收敛为「一真源 + 引用」，禁止同内容多份分叉。

**规范演进节奏**：

```text
实践 -> 发现反例 -> 建 FIX/DEF/GAP -> 修正实现
-> 回写 business-rules / AGENTS / rules / 设计系统
-> 增加守卫脚本或验收用例 -> 下一轮复用
```

规范不是写一次就冻结的文档，而是随每次真实修复而增长的资产。

## 附录 B. 一页速查：装得清产品十条

1. **场景先于功能，条件先于页面**：没有 2 个真实场景和 12 维条件，不进入设计。
2. **角色决定工作台，权限先于渲染**：菜单、路由、接口三层缺一不可。
3. **一条主链、四个锚点、一条账务事实链**：业务与钱同时设计。
4. **首屏三问**：我是谁、当前有什么待处理、下一步做什么。
5. **一个页面一个主对象，一个状态一个主动作**：禁止多主对象、多 CTA。
6. **三个不可伪造**：完成状态、利润、权限必须来自真实领域事实。
7. **状态机在后端，端上只呈现与提交**：成功后重新读取。
8. **App 做现场，Web 做宽屏效率，事实同源同口径**：App 线上兼容优先。
9. **证据先于结论，渲染先于交付**：类型检查通过不等于页面可用。
10. **每次修复都沉淀规则**：只改代码不沉淀 = 下次继续踩坑。

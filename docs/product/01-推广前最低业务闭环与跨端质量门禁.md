# 装得清推广前最低业务闭环与跨端质量门禁

> 版本：v1.0  
> 日期：2026-10-28  
> 状态：执行中，适用于首发推广前的产品收口  
> 上位事实源：`AGENTS.md`、`rules.md`、`docs/design/31-一后端多端同源架构规范.md`、装得清业务智能体 `SCN/BR/DEC/CAP/EV`  
> 适用范围：App（微信小程序）、Web 企业工作台、后端 Provider、业主端  
> 定位：不是功能清单，而是“装得清什么时候可以被证明能推广”的统一关门标准。

---

## 0. 一句话标准

> **装得清首发推广前，必须让一个真实签约项目从合同生效、项目履约、现场留证、变更、材料、阶段验收与整改，到收款和成本回读，在 App、Web、业主端围绕同一事实完成最基本闭环；任何用于展示的信息都必须服务于判断、行动、交接、确认、留证或对账。**

首发只承诺一个入口场景：

> **签约才是装修的起点。装得清让签约后的工地，每个岗位对同一件事负责，业主看得见，老板接得住。**

其他能力可以存在，但在未通过本门禁前，不得作为推广主承诺。

---

## 1. 首发范围与非目标

### 1.1 首发范围

- 目标企业：10–30 人、单店或默认总店、在施项目 3–15 个的成长型装企。
- 目标角色：企业负责人、店长、设计师、项目经理、财务、业主。
- 核心主链：合同生效 → 项目 → 阶段/任务 → 现场留证 → 变更 → 材料 → 验收/整改 → 收款/成本。
- 首发产品面：App、Web、业主端和同一业务后端。
- 首发商业表达：签约后的工地同频，不把“全流程 ERP”作为首屏主叙事。

### 1.2 首发明确不作为阻塞项

以下能力可以保留现状或延期，但不能反向阻塞核心闭环，也不得在未验收时对外承诺：

- AI 设计、内容获客、素材授权和自动成片；
- 多门店横向对比与复杂总部费用分摊；
- 企业费用报销、复杂薪酬和法定会计总账；
- 售后、质保、复购的完整运营体系；
- 3D/2.5D 空间展示；
- 任何未冻结的行业效果数字、利润数字和客户案例。

### 1.3 首发不可承诺

- 不能承诺“绝不扯皮、绝不漏项、绝不返工”；
- 不能把“业务记录”说成“质量已经合格”；
- 不能把“成本可录入”说成“利润一定准确”；
- 不能把“业主可查看”说成“业主会审批每一个环节”；
- 不能把未完成独立验收的能力写成“已上线、已验收、已规模化”。

## 2. 最低业务闭环的唯一定义

### 2.1 核心闭环

```text
真实客户与房屋
→ 设计方案与报价版本
→ 合同签约并确认生效
→ 项目、阶段、任务和责任人
→ 现场节点留证与日报
→ 合同变更及其下游影响
→ 材料选材、计划、下单与到场记录
→ 阶段验收、业主确认或驳回、整改与复验
→ 应收、收款、应付、付款、成本完整性
→ 老板和财务回读项目结果
→ 业主在授权范围内回读同一事实
```

### 2.2 闭环成立的必要条件

一个项目必须同时满足：

1. 每一段都有正式业务对象和来源，不靠聊天、Excel 或前端本地状态补齐；
2. 每一次状态变化都有责任角色、时间、证据和下一步；
3. 变更、材料、验收和收付款能够回到同一项目；
4. App、Web、业主端对同一对象、状态、金额和下一步的结论一致；
5. 业务信息不是“存在即完成”，而是能被用户看见并推动下一步；
6. 失败、无权限、无数据和数据不完整有明确表达与恢复路径；
7. 有真实账号、真实项目、真实页面和可回读证据。

缺任何一条，都不能称为“最低业务闭环完成”。

## 3. 首发只允许一个入口场景和五个支撑场景

| 层级 | 场景 | 用户时刻 | 必须打穿的产品事实 |
| --- | --- | --- | --- |
| 入口 | 签约后工地不乱 | 合同刚生效，项目还没有真正被接住 | 合同生效、项目立项、负责人、阶段、任务、开工日、首个待办 |
| 支撑 1 | 改一项不再全链重问 | 客户增加、减少或替换一项 | 变更来源、审批/签认、合同、任务、材料、应收、成本 |
| 支撑 2 | 材料从选到到场有据 | 设计师选材，PM 等材料，财务对成本 | 选材、材料计划、采购、到场、应付/成本、异常 |
| 支撑 3 | 业主不再每天追进度 | 业主想知道做到哪、最近发生了什么 | 授权视图、阶段、现场证据、服务团队、下一步 |
| 支撑 4 | 验收整改不是一张纸 | PM 提交，业主确认/驳回，团队整改复验 | 验收轮次、问题、责任人、截止时间、复验结论 |
| 支撑 5 | 钱和经营结果能回读 | 老板/财务判断回款和这一单是否赚钱 | 应收、收款、应付、付款、成本完整性、利润为空规则 |

任何新增需求都必须回答：它增强了哪一个场景，而不是只增加一个页面或字段。

## 4. 信息作用门禁：没有作用的信息不得占据业务界面

### 4.1 每一块信息必须至少承担一种作用

| 作用 | 判断标准 | 允许的界面结果 |
| --- | --- | --- |
| 判断 | 帮用户判断正常、风险、逾期、成本不完整或状态异常 | 结论、风险、状态、原因 |
| 行动 | 直接触发或引导一个业务动作 | 唯一主行动、次级动作、处理入口 |
| 交接 | 告诉用户完成后由谁接棒、下一步是什么 | 责任人、下一步、截止时间 |
| 确认 | 明确谁需要确认、确认了什么、何时确认 | 确认卡、签认记录、验收轮次 |
| 留证 | 支撑事实追溯和争议处理 | 图片、附件、时间、操作人、来源 |
| 对账 | 支撑金额、成本、收付款和项目事实核对 | 金额、余额、来源单、差异和缺失项 |

### 4.2 不允许的信息

- 只有编号、状态 key、内部枚举和技术字段，没有角色需要用它做判断；
- 统计数字无法追溯到数据范围和更新时间；
- 显示了风险但不给处置动作；
- 显示了“待处理 N”但无法展开到具体事项；
- 显示了金额但没有来源、时间范围、缺失值处理和对账路径；
- 同一信息在 App 与 Web 语义不一致；
- 接口失败时用 0、空数组、默认状态或“暂无数据”伪装成功。

### 4.3 信息评审表

每个新页面或重构页面必须填写：

| 字段/区块 | 回答的用户问题 | 对应动作/判断 | 下游影响 | 数据来源 | 缺失时表达 |
| --- | --- | --- | --- | --- | --- |

没有填写完整，不得进入 UI 设计或开发。

### 4.4 字段契约门禁

任何新增或改造字段，必须同时满足：

| 项 | 必须回答 |
| --- | --- |
| 唯一主源 | 同一语义只允许一个正式事实源；其他位置只能是快照、投影或只读引用 |
| 维护角色 | 谁在什么阶段录入、修改或确认 |
| 必填条件 | 什么业务条件下必须填写，不填写会阻断哪个动作 |
| 下游消费者 | 哪个角色、页面、Provider、报告或业主视图会读取 |
| 下游动作 | 读取后产生什么任务、提示、阻断、确认、金额变化或状态变化 |
| 变化影响 | 修改后哪些对象、队列、计划、金额和成本要重新读取或重算 |
| 缺失策略 | 缺失时显示“暂不可确认”或阻断，不得用 0、空数组、默认枚举伪装 |
| 留痕与生命周期 | 是否需要证据、版本、确认人、时间和归档/失效规则 |

没有“唯一主源 + 下游消费者 + 业务动作”的字段，不得进入正式表单。

进入 AI Prompt、Excel 导出、详情页展示或搜索索引，不等于业务使用；只有改变对象、状态、责任人、任务、确认、金额或可对账事实，才算进入业务闭环。

## 5. 一后端多端同源门禁

### 5.1 强制一致

- 同一能力只有一个正式 Provider；
- 同一业务主键、筛选参数、状态、角色和动作语义一致；
- 同一金额、成本、利润和缺失值规则一致；
- 同一错误语义和恢复路径一致；
- 写成功后 App/Web 都回读服务端事实；
- 页面布局可以不同，业务结论不能不同。

### 5.2 每个跨端能力必须建立对账矩阵

使用 `docs/design/templates/app-web-provider-parity.md`，至少覆盖：

- Provider、请求、响应、枚举、空值；
- 权限、数据范围、状态机、金额/成本；
- App 页面、Web 页面和业主端投影；
- 正向、失败、无权限、空态、重复提交、越权和跨端一致性；
- 真实页面/真机证据和发布记录。

### 5.3 发布前硬阻断

- 一端能写、另一端不能写但未说明；
- 一端显示正式金额，另一端使用本地默认值或自算；
- 同一对象两端状态名称不同；
- 同一角色两端能力集合不同；
- 页面按钮存在而服务端无校验；
- 服务端允许而另一角色端错误暴露入口；
- 发现跨端差异后仍继续扩展功能，而不先关闭生产问题。

## 6. 页面与交互质量标准

### 6.1 所有核心页面必须回答三件事

1. 现在发生了什么？
2. 这对业务有什么影响？
3. 下一步由谁做什么？

### 6.2 三层信息结构

- L1：结论、风险、待决策事项，首屏直接可见；
- L2：关键依据、原因、影响范围，一次展开可见；
- L3：完整历史、审计、技术字段，进入抽屉或详情。

### 6.3 唯一主行动

- 每个页面只允许一个视觉最高优先级动作；
- 次要动作降级为次级按钮、行内操作或“更多”；
- 删除、作废、覆盖、批量修改必须说明影响范围并要求确认；
- 没有动作可做时，说明原因、责任人和恢复路径。

### 6.4 七类状态

每个核心页面必须覆盖：

1. 正常；
2. 加载；
3. 真实空态；
4. 加载失败；
5. 无权限；
6. 长内容；
7. 极端数值或缺失值。

### 6.5 App 细节基线

- 375×667、390×844、430×932 至少三档检查；
- 安全区、底部导航、返回路径、激活态正确；
- 可点击区域足够大，行内操作不拥挤；
- 文本不截断关键对象、金额、状态和下一步；
- 弹层关闭后回到原上下文；
- 相机、相册、弱网、重复提交和失败重试有真实证据；
- 不得出现 undefined、研发术语、裸枚举和不可执行待办。

### 6.6 Web 视觉基线

- 只使用 `src/styles/tokens.scss`；禁止新增无理由裸色值、裸字号、裸阴影和裸圆角；
- 中性画布 + 内容面 + 单一品牌强调色；
- 首屏不是入口目录，而是三秒结论、风险与主行动；
- 表格、三栏工作面、卡片和指标必须遵循统一页面母型；
- 同一产品不得同时混用四套互不一致的页面语法；
- 真实渲染 1440×900、1280×800、1024×768，无横向溢出；
- 设计、批判、修正、再渲染至少两轮，构建成功不等于 UI 通过。

## 7. 推广前七道门禁

| 门禁 | 必须通过的内容 | 证据 |
| --- | --- | --- |
| G0 范围冻结 | 只做一个入口场景、五个支撑场景；明确非目标 | 范围卡和问题总账 |
| G1 业务对齐 | 对象、状态、权限、金额和确认主体有正式来源 | `BR/DEC/SCN/T12` |
| G2 三端同源 | Provider、请求、响应、权限、状态、金额和回读一致 | 对账矩阵 + 契约测试 |
| G3 真实主链 | 一个真实项目按核心闭环完成并回读 | 账号、页面、接口、SQL、截图/录屏 |
| G4 信息有效 | 所有展示信息通过作用门禁 | 信息评审表 + 真实走查 |
| G5 体验达标 | App/Web 核心页面通过状态、交互和视觉门禁 | 多档截图 + 七态证据 + 批判记录 |
| G6 独立验收 | 正向、反向、越权、幂等、边界、跨端全部通过 | 独立验收报告 |
| G7 营销可用 | 每条对外表达能回到已验证事实和边界 | 事实映射 + 禁用话术检查 |

任何一道未通过，只能标记“产品验证中”，不能标记“可推广”。

## 8. 发布与推广判定

### 8.1 允许进入首发的条件

- G0–G7 全部通过；
- P0 = 0；
- 核心闭环相关 P1 = 0；
- 核心页面无未解决视觉/交互 P1；
- 三仓发布基线干净、可追溯、可回滚；
- App 体验版完成真实业主/员工走查；
- 正式小程序提审和发布仍由用户本人完成；
- 推广素材只引用已验证场景，不引用开发自测或概念原型。

### 8.2 允许“条件性首发”的例外

只有用户明确批准时，才允许带明确边界条件首发：

- 非核心域的 P1 有临时人工处置方案；
- 某项支撑能力标注“记录可用、自动化待完善”；
- 数据结构或性能风险有监控、降级和回滚；
- 营销明确不承诺未闭环能力。

条件性首发不能豁免 P0、权限、跨租户、资金/成本错误和核心状态错误。

## 9. 当前收口顺序

### 第一阶段：建立可控基线

1. 三仓分支、脏文件、提交范围和发布候选分离；
2. 修复失效的治理脚本和与最新业务决策冲突的检查；
3. 把 Web/App 静态门禁、构建、类型检查、全量测试跑通；
4. 建立问题总账和跨端对账矩阵。

### 第二阶段：打穿入口场景

选择一个真实项目，只打穿：

```text
合同生效 → 项目/阶段/任务 → 现场留证
→ 阶段验收/驳回 → 整改/复验 → 业主回读
```

### 第三阶段：补齐支撑断点

按“变更 → 材料 → 收款/成本”的顺序补齐下游联动，每次只做一个垂直切片。

### 第四阶段：UI 与营销证据

对核心页面完成两轮真实渲染批判，形成真实项目证据包，再更新官网、销售演示和内容素材。

---

## 10. 反模式

- 用新增功能掩盖已有闭环断裂；
- 用演示数据、Mock 或构建成功冒充用户可用；
- 用菜单隐藏代替服务端权限；
- 用本地默认值、0 成本、默认 22 天、前端求和冒充正式事实；
- 让同一个对象在 App/Web/业主端拥有不同状态或下一步；
- 页面堆满统计、编号和卡片，但没有唯一主行动；
- 发现 P0/P1 后继续扩展相邻业务；
- 先做营销承诺，再倒逼产品“补故事”；
- 把“有记录”说成“已产生管理效果”。

## 11. 完成定义

只有当以下条件同时成立，才可以在项目状态中写“推广前最低闭环完成”：

```text
一个真实项目完整走通
+ App/Web/业主端同源回读
+ 所有信息通过作用门禁
+ 核心页面真实渲染和交互通过
+ P0=0、核心 P1=0
+ 独立验收 PASS
+ 营销事实映射和不可承诺边界冻结
```

在此之前，统一状态为：

> **产品验证中，能力可用范围以具体页面和验收证据为准，尚不构成首发推广承诺。**

# 装得清业务信息架构与字段闭环标准

> 版本：v0.1 draft  
> 日期：2026-10-28  
> 业务事实源：装得清业务智能体 `BR-059`、`OBJ-010`、`00-治理/业务信息项注册表-v0.1.json`  
> 工程适用范围：后端实体/Provider、App、Web、业主端、Admin 和后续外部协作端

## 1. 目的

本规范把“业务信息项”作为产品、研发、测试和营销之间的共同语言。

以后不允许直接问：

```text
这个页面加什么字段？
```

必须先问：

```text
这是什么信息项？
它归哪个业务概念？
唯一主源在哪里？
谁维护？
哪些场景消费？
消费后触发什么业务动作？
变更、缺失、失败和归档怎么处理？
```

## 2. 强制信息项注册

任何新增或修改信息项，必须先登记：

```text
装得清业务智能体/00-治理/业务信息项注册表-v0.1.json
```

登记字段至少包含：

- `id`：稳定信息项 ID；
- `domain`：业务信息域；
- `name` / `definition`：业务名称与唯一定义；
- `concept`：唯一归属概念；
- `semantic`：`Primary / Reference / Snapshot / Projection / Derived / Evidence`；
- `source`：主源 Provider/动作；
- `maintainers`：维护角色；
- `applications`：场景、消费者、闭合动作；
- `visibility`：可见角色和数据范围；
- `lifecycle`：可改、冻结、版本、归档；
- `missingPolicy`：缺失和失败处理；
- `rules`：关联业务规则。

未登记的信息项不得进入正式表单、Provider 或页面研发。

登记与评审模板：`docs/product/templates/业务信息项登记与闭环评审单.md`。

## 3. 信息项在代码中的映射

### 3.1 实体

- 实体的正式业务字段必须能映射到至少一个信息项 ID；
- 同一语义不得在多个实体中形成可编辑主源；
- 快照字段必须以 `Snapshot` 语义标注来源和冻结点；
- 只读组合字段必须以 `Projection` 或 `Derived` 语义标注；
- 纯技术字段（主键、雪花 ID、审计时间、数据库版本）不进入业务注册表，但必须有工程说明。

### 3.2 Provider

- 请求字段必须说明对应的信息项与维护动作；
- 响应字段必须区分主源、快照、投影、派生和证据；
- 一次写入必须明确受影响的信息项集合；
- 写成功后必须回读正式事实；
- 不允许在没有信息项定义的情况下新增同义 Provider 参数。

### 3.3 App / Web / 业主端

- 同一信息项复用同一主源或同一服务端投影；
- 页面布局可以不同，信息定义和动作语义不能不同；
- `@Properties` / `@ServiceProperties` 的裁剪必须符合角色权限与信息可见性；
- 字段缺失、无权限、失败和过期必须对应 `missingPolicy`；
- 仅展示、不触发任何判断或动作的信息项，不得占据核心操作界面。

### 3.4 AI 与导出

- AI 读取不是业务使用的充分条件；
- 导出是快照或投影，不是新主源；
- AI 建议、导出文件和页面展示不得绕过正式确认写入业务事实；
- 对外分享必须按信息项的 `visibility` 和授权边界裁剪。

## 4. 快照、投影与派生实现规则

### 4.1 快照

必须包含：

- 来源对象与版本；
- 冻结时间；
- 冻结时的业务值；
- 创建人和变更来源；
- 上游变更后的处理策略。

不得只保存一份无来源文本。

### 4.2 投影

投影必须：

- 有唯一服务端构建器；
- 回源读取；
- 可证明数据新鲜度；
- 失败显示暂不可确认；
- 不保存为第二套业务事实。

### 4.3 派生

派生值必须：

- 由服务端公式生成；
- 有指标/公式来源；
- 明确分母、时间范围和缺失值；
- 前端不得重算正式金额、成本、利润、进度或风险等级。

## 5. 信息变更影响分析

修改一个信息项前必须输出：

| 项 | 内容 |
| --- | --- |
| 信息项 ID |  |
| 主源变更 |  |
| 快照影响 | 历史快照是否保留，未来快照是否变化 |
| 投影影响 | 哪些页面/报表/AI/导出需要重读 |
| 动作影响 | 哪些任务、状态、金额、成本、确认和提醒改变 |
| 数据迁移 | 是否需要回填、兼容或待确认 |
| 跨端影响 | App/Web/业主端/Admin |
| 反例 | 历史项目、缺数据、越权、失败、重复提交 |

没有影响分析，不得修改正式信息项。

## 6. 信息闭环验收

每个信息项至少需要：

1. 一个正向场景：从录入到下游动作结果可回读；
2. 一个缺失场景：显示暂不可确认或明确阻断；
3. 一个变更场景：主源变更后快照不回溯、投影重新读取；
4. 一个权限场景：无权限角色不能看到或修改；
5. 一个跨端场景：App/Web/业主端语义一致（适用时）；
6. 一个反例：不得通过重复录入、自由文本或前端默认值绕过。

## 7. 当前执行顺序

### 第一阶段：建立信息项主源

- 将 70 个 V0.1 信息项映射到当前实体/Provider；
- 标记 `primary / snapshot / projection / derived / evidence`；
- 列出缺失、重复主源和无消费者字段。

### 第二阶段：修复 P1 信息断链

优先：

1. 报价工艺/验收标准 → 合同 → 项目任务 → 验收；
2. 主材作业单规格 → 采购明细 → 到场核验；
3. 任务节点证据 → 验收证据包；
4. 验收问题 → 逐项整改任务；
5. 跟进内容/画像/预算 → 设计、谈单、报价和任务。

### 第三阶段：接入研发门禁

- 新增实体字段必须填写信息项 ID；
- 新增 API 字段必须说明主源/投影/快照；
- 新增表单必须填写场景、消费者和闭合动作；
- CI/评审增加信息注册表完整性检查；
- 真实页面验收增加“信息闭环”用例。

## 8. 当前边界

- 本规范为 `draft`，需用户评审后升级为正式强制标准；
- 不直接修改现有实体、状态机、金额或权限；
- 当前注册表覆盖核心业务主链，薪酬、报销、多门店经营和售后质保仍需继续补齐；
- 业务信息注册表是业务事实层，代码中的表结构仍是实现层，两者不得互相替代。

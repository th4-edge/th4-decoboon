# 装企历史数据承载 · 三条渠道可落地交互流程

> 文档编号：PLAN-20260921-IMPORT-CHANNEL-001
> 版本：v1.0
> 日期：2026-09-21
> 状态：suspended（导入产品需求已搁置）
> 依据：`DEC-004`（本次用户决策）、`DEC-001`、`GAP-001`、`OBJ-001`、`PLAN-20260920-FLOW-001`
；App 负责现场建档、拍照上传与查看；实施/客服使用后台代导入通道

> ⚠️ **状态：搁置（2026-09-21）** —— 用户明确历史数据导入不做产品化，产品以新客户为准；确有存量装企老数据时，由技术人员手动导入。本文档转为备查资料，不进入研发排期。
> 手动导入时的范围与字段口径仍可参照本文档。

## 1. 结论

中小装企的历史数据不在干净的表里，在 Excel、微信和纸质单据里（`DEC-001` 目标客户画像）。因此**不能把"翻译成我们的模板"这一步交给客户**。

承载方式固定为三条渠道，按客户能力分级：

| 渠道 | 名称 | 承载对象 | 客户动作 | 谁解决格式 |
| --- | --- | --- | --- | --- |
| A | 引导式建档 | 业务对象：在跑项目、合同基线、期初应收应付 | 逐条录 + 拍照上传附件 | 无需转换，表单约束 |
| B | 原表映射导入 | 主数据：报价项目库、供应商、品牌关系 | 上传自己的原表 + 确认映射 | 系统识别，客户确认 |
| C | 服务侧代导入 | 上述两者的兜底 | 提供文件 + 确认结果 | 装得清实施/客服承担 |

一条原则：**客户只负责"提供原始数据"和"确认结果"两件事。**

## 2. 渠道选择决策树

```text
要承载的是报价项目库 / 供应商 / 品牌关系这类主数据吗？
├─ 是 → 数据量是否 >= 50 条或客户已有干净 Excel？
│        ├─ 是 → 渠道 B（原表映射导入）
│        └─ 否 → 渠道 A 直接录入（少量主数据不值得走导入）
└─ 否（客户/房屋/合同/项目/期初应收应付等业务对象）
         ├─ 在跑业务条数 <= 20 → 渠道 A（引导式建档）
         └─ 在跑业务条数 > 20 或客户无法自助 → 渠道 C（服务侧代导入）
```

补充判定（任一满足即直接走渠道 C）：

- 客户无法提供可读的电子文件（只有纸质/微信图片）。
- 原表列名无法被系统识别，且客户无人力配合确认映射。
- 客户在跑业务 > 20 条，超出自助建档的合理工作量。

## 3. 渠道 A：引导式建档

### 3.1 定位

业务对象结构强、归属链复杂（`OBJ-001`：company → store → team → owner），而目标客户在跑项目只有 3–15 个（`DEC-001`）。少量、强结构的数据用**表单 + 附件**承载，比表格导入更稳。

### 3.2 角色与触发

| 项 | 内容 |
| --- | --- |
| 使用人 | BOSS（主导）、财务（期初往来）、项目经理/文员（项目明细） |
| 触发事件 | 决定启用装得清承接存量业务 |
| 前置条件 | 企业、默认总店、BOSS 已自动形成；报价项目库已有数据 |

### 3.3 交互流程

```text
进入「历史业务承接」清单
-> 选择要承接的客户（来自渠道 B 或手工新建）
-> 为该客户建立/确认房屋（一客户多房屋必须逐个建立）
-> 逐个建立「在跑项目」：项目名、关联房屋、负责人、当前阶段、开工日期
-> 挂接合同基线：合同编号、金额、签署日期、扫描件
-> 录入期初应收/应付余额
-> 每条完成后即时显示该条状态
-> 全部完成后进入「承接完成」汇总核对
```

### 3.4 列表与完成状态投影（按项目逐个投影）

| key | label | required | source_provider | completion_predicate | 异常态 |
| --- | --- | --- | --- | --- | --- |
| `customer` | 客户与房屋 | 是 | `customer/customer/page` + `property/property/page` | 客户存在且至少关联 1 套房屋 | 接口失败显示"暂不可确认" |
| `project` | 在跑项目 | 是 | `project/project/page` | 该项目存在且状态非终态 | 同上 |
| `owner` | 责任归属 | 是 | 项目/房屋归属字段 | store/team/owner 至少 owner 明确 | 归属缺失 → 待确认，不猜（`OBJ-001`） |
| `contract` | 合同基线 | 是 | 合同域 | 有合同编号 + 金额 + 关联项目 | 仅扫描件无金额 → 未完成 |
| `receivable` | 期初应收 | 条件必填 | 财务域 | 该项目存在应收记录或明确标记"无应收" | 未确认且未标记 → 未完成 |

- 必做分母按**当前企业需要承接的在跑项目数**动态生成，不是固定 3 或 5。
- 每条项目独立计算完成度，支持"部分承接"。
- 归属缺失、金额无法确认的条目进入**待确认队列**，不阻塞其他条目，但阻塞该条目的"承接完成"。

### 3.5 异常分支

| 异常 | 处理 |
| --- | --- |
| 项目归属不明确 | 进待确认队列，提示"请指定负责人"，不自动填充 |
| 一个客户多套房屋 | 强制选择具体房屋，禁止用第一套兜底 |
| 只有纸质合同 | 允许先建项目 + 上传扫描件，合同金额标记"待确认" |
| 金额无法确认 | 允许暂缺，该条目标记未完成，进入待补清单 |
| 重复提交 | 按 `company + 项目业务键` 幂等，第二次进入编辑而非新建 |

## 4. 渠道 B：原表映射导入

### 4.1 定位

主数据（报价项目库、供应商、品牌关系）量大、结构扁平，适合批量导入。**客户上传自己的原表，不要求改成我们的模板。**

### 4.2 交互流程

```text
① 下载「建议模板」或直接上传自己的 Excel/CSV
② 系统解析表头 + 抽样内容，给出列映射建议
③ 人工确认/修正映射（未识别的列可忽略或手动指定）
④ 预览校验：逐行显示将写入的对象、被识别的字段、错误原因
⑤ 修正错误行（改映射规则 / 下载错误行 / 直接忽略该行）
⑥ 提交导入（分块事务写入）
⑦ 返回结果：成功数、失败数、跳过数、失败明细可下载
⑧ 在「导入批次」中可查看来源、时间、操作人；窗口期内可整批回滚
```

### 4.3 两条入口，同一引擎

| 入口 | 说明 |
| --- | --- |
| 建议模板 | 系统提供 CSV（见《最小承载集字段冻结》），客户愿意用就用 |
| 原表直传 | 客户上传任意结构 Excel，走列映射 |

两者最终都进入同一套**校验 → 预览 → 提交**引擎，差别只在映射是否需要人工确认。

### 4.4 列映射规则

- 表头模糊匹配：列名同义词库（如"单价/销售价/报价/材料价"→ 销售价）。
- 内容抽样识别：金额列、日期列、手机号列按值域识别。
- 枚举值映射：客户自定义的类型值映射到系统枚举，无法映射进待确认。
- 品牌/分类归一：与已有主数据比对，相近项提示合并。

### 4.5 校验与错误行

- 逐行校验：必填、格式、值域、重复、归属。
- 预览阶段不写正式业务表。
- 错误行必须定位到**行号 + 字段 + 原因**，可导出修正后重新上传。
- 不因单行错误导致整批失败；但涉及金额、归属的错误行不允许静默跳过。

### 4.6 幂等

```text
company + importType + sourceFileHash + 业务键（code/legacyId）
```

同一文件重复上传不产生重复数据；已提交批次在窗口期内可整批回滚。

## 5. 渠道 C：服务侧代导入（正式服务能力）

### 5.1 定位

这是**中小装企最现实的通道**，也是本次决策明确要求产品化的能力。老板没时间研究映射，最自然的诉求是"我把表发你，你帮我弄进去"。

### 5.2 责任边界（必须摆正）

| 环节 | 责任方 |
| --- | --- |
| 提供原始数据 | 客户 |
| 确认导入结果 | 客户 |
| 文件解析、字段识别、清洗、映射、校验、写入 | 装得清实施/客服 |
| 异常兜底与口径答疑 | 装得清实施/客服 |

**客户不承担任何格式转换工作。**

### 5.3 交互流程

```text
① 客户在客户端提交「代导入申请」并上传文件（或由客服代收）
② 系统登记服务工单：客户、企业、导入类型、文件、提交时间
③ 实施/客服在后台解析文件并完成映射、清洗与预校验
④ 后台生成「导入预览」：将写入的对象与条数、异常清单
⑤ 客户确认预览结果（在客户端查看并确认，或书面确认留痕）
⑥ 实施/客服提交导入，系统分块写入并记录批次
⑦ 客户在客户端查看导入结果汇总
⑧ 异常条目进入待确认队列，由双方约定补录责任
```

### 5.4 客户确认节点（不可省略）

- 预览必须由客户确认后才允许提交，避免"代导入"变成责任黑洞。
- 确认动作留痕：确认人、时间、批次号、确认内容摘要。
- 金额、期初余额类数据必须客户确认，服务侧不得自行推定。

### 5.5 权限与留痕

- 代导入操作记录操作人（实施/客服账号）、时间、批次、变更前后条数。
- 代导入通道仅在平台运营域或受控后台可用，不开放给企业普通员工。
- 客户企业内操作人只看到结果，不看到服务侧内部映射过程。

## 6. 跨渠道共用规则

### 6.1 归属规则

```text
company -> store -> team -> owner
来源优先级：Property.owner/store/team/company
         -> 缺失回退 Customer.owner
         -> 子对象从最近父对象继承
```

- 归属缺失一律进**待确认**，禁止猜测负责人、门店或团队（`OBJ-001`）。
- 所有承载对象必须带 `company`，禁止裸外键。

### 6.2 统计隔离（本次决策）

- **历史导入的数据不参与经营指标**。
- 各类报表、转化率、毛利、排名等经营指标只统计正常业务主链产生的数据。
- 历史导入数据必须带来源标记（批次 + 来源类型），在指标查询中显式排除。
- 历史导入数据仍可用于：查看、追溯、继续履约、补录后续事实。

### 6.3 金额与成本口径

- 历史成本不完整时，利润与毛利率返回空值，不得按 0 计算（`MET-002`）。
- 期初应收应付作为独立来源，不伪装成正常收款/付款。
- 历史导入的报价/合同金额只作基线，不进入正常报价接受率统计（`DEC-001` 决策一）。

### 6.4 不做的事

- 已完工项目不导入，只做档案或不做（本次决策）。
- 不重建历史报价行、合同行、成本快照、收款计划。
- 不用测试通过替代真实客户数据验收。

## 7. 与现有能力的复用关系

| 现有能力 | 复用方式 |
| --- | --- |
| `statistic/onboarding/report` 状态投影 | 渠道 A 的项目级承接状态复用同一套 `done/todo/waiting/unknown` 契约 |
| `catalog/item/import` 报价项目库导入 | 作为渠道 B 主数据导入的既有实现基础，补齐 CSV 解析、预览、错误行 |
| `ImportBatch` 规划（`PLAN-20260920-FLOW-001`） | 渠道 B/C 的批次、幂等、回滚、状态机直接落地该契约 |
| OSS 私有存储与文件授权 | 合同扫描件、原始上传文件的存储与访问 |

## 8. 验收场景

| 编号 | 场景 | 期望 |
| --- | --- | --- |
| IA-01 | 15 人单店，8 个在跑项目走渠道 A | 逐条建档，归属缺失进待确认，全部完成后承接完成 |
| IA-02 | 客户上传结构完全不同的报价 Excel 走渠道 B | 列映射成功，预览正确，重复上传不产生重复数据 |
| IA-03 | 客户只有纸质合同走渠道 C | 客服代导，客户确认预览后提交，批次可追溯 |
| IA-04 | 历史导入数据出现在经营报表 | 必须被排除，报表数值不受影响 |
| IA-05 | 一客户多房屋导入 | 每套房屋独立建档，不串房屋 |
| IA-06 | 归属缺失的历史项目 | 进待确认，不被猜测赋给任意员工 |
| IA-07 | 历史成本缺失 | 利润与毛利率为空，不显示伪利润 |
| IA-08 | 跨企业导入 | 另一租户不可见，`legacyId` 不互相覆盖 |

## 9. 待研发确认项

1. 渠道 A 的"承接完成"是否需要独立对象，还是按项目派生投影（建议后者，不新增状态机）。
2. 渠道 C 的服务工单是否复用平台运营域，还是新建服务域。
3. 原表映射的字段同义词库初始范围（建议首批只覆盖报价项目库）。
4. 「历史来源标记」的落地字段与索引方式。

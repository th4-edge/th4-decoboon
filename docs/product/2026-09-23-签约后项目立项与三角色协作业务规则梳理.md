## 0. 结论先行（三句话）

1. **立项唯一合法入口是「已生效合同」**：报价 `Accepted` → 合同 `Signed`（必须录最终签约价）→ 合同 `Effective` → 系统自动生成项目、施工阶段、施工任务、材料计划、应收计划。业务规则禁止「无报价旁路」`[业务 BR-002 / DEC-001]`，代码强约束一致 `[代码]`。
2. **「施工计划节点」在本系统分三层**，必须区分清楚：
   - **阶段节点**：合同级施工计划快照的施工阶段（编码/名称/标准工期/计划起止/验收模式），生成项目阶段 `ProjectStage`；
   - **工艺任务**：阶段 × 区域 × 工艺 × 数量形成的可执行施工项 `ProjectTask`；
   - **影像节点**：任务的「施工进行 / 隐蔽工程 / 施工完成」留证 `TaskNode`。
3. **三角色由代码强制分工**：设计师=排期下发施工任务；项目经理=阶段开工、节点留证、提交验收；财务=应收、收款核销、应付账期、付款、结算。**阶段验收的确认/驳回只能由业主本人完成**，员工端确认接口直接 403 `[代码]`。

## 2. 状态轨道：从签约到项目结算

```text
报价 Accepted
   │  (Boss 签约，必须录最终签约价 signedAmount>0)
   ▼
合同 Signed ──(Boss 执行生效)──▶ 合同 Effective
   │                                   │
   │  签约同时冻结：合同行成本快照        │  同一事务内自动立项
   │  付款计划快照 / 施工计划快照        │
   ▼                                   ▼
                             项目 Preparing（待开工）
                                   │ 阶段开工
                                   ▼
                             项目 Ongoing（施工中）
                                   │ 阶段任务完成 → 提交验收
                                   ▼
                             项目 Accepting（待验收）
                                   │ 业主确认全部阶段
                                   ▼
                             项目 Finished → Settled（结算）

合同侧可后置进入：Active / Changing / Changed / Completed / Settled / Closed / Terminated
```

关键不变量 `[业务 DEC-002]` `[代码]`：

1. `Signed` ≠ `Effective`，**只有 `Effective` 可以建项目**。
2. 合同必须绑定报价，**不允许无报价项目运行分支**。
3. 一个房屋只允许一个项目（`该房屋已经生成唯一项目，不能重复立项`）；同一报价只能生成一次项目。
4. 合同签约后不能更换付款/施工计划（生效后 `ContractPlanContext.select` 直接拒绝）。
5. 项目状态、阶段状态、进度**全部由后端由下往上汇总**，前端不能直接写进度。

## 3. 项目立项：谁触发、校验什么、生成什么

### 3.1 两个合法入口 `[代码]`

| 入口 | Provider | 角色 | 说明 |
| --- | --- | --- | --- |
| A. 合同生效自动立项 | `project/contract/update`（`status=Effective`） | 仅 Boss | 合同生效时由系统生成项目草稿（名称=`客户名·地址`，地址取房屋地址）并立刻建项目；合同与项目互相回写 |
| B. 显式立项 | `project/project/save`（`quoteId` 必填） | Boss / 店长 / 团队（受数据范围） | 由报价发起，可指定 `name/siteAddr/designerId/managerId/supportId/startDate/planEndDate`；内部再次校验合同必须为 `Effective` |

> 入口 B 的 `quoteId` 在服务端先经 `ProjectAccessContext.requireQuote` 做企业+数据范围校验；`designerId/managerId/supportId` 必须是同企业且角色匹配（设计师=Boss/Designer、项目经理=Boss/Pm、履约负责人=Boss/Finance），否则 400。

### 3.2 立项校验清单（失败即阻断）`[代码 ProjectContext]`

| 校验 | 错误提示 |
| --- | --- |
| 报价非空 | `报价不能为空` |
| 合同存在且 `Effective` | `请先完成合同签约并生效，再创建项目` / `只有已生效合同可以创建项目` |
| 报价未生成过项目 | `该报价已经生成项目` |
| 报价有客户房屋 | `报价缺少客户房屋，请先建立并选择房屋档案` |
| 房屋未被其他项目占用 | `该房屋已经生成唯一项目，不能重复立项` |
| 房屋无其他已接受报价 | `该房屋已有其他客户确认报价` |
| 项目企业与报价企业一致 | `项目企业与报价企业不一致`(403) |

同时把同一房屋的其他 `Draft/Submitted/Accepted` 报价置为 `Superseded`（历史保留，不删除）。

### 3.3 立项一次性生成的对象 `[代码]`

| 生成对象 | 生成规则 | 初始状态 |
| --- | --- | --- |
| `Project` | 企业/客户/房屋/报价来自受检对象；金额取合同 `currentAmount`（缺失回退报价金额）；成本取合同行成本合计；`designer` 默认取报价创建人 | `Preparing`，进度 0 |
| `ProjectStage` | 优先按**合同施工计划快照**生成；无快照时按合同施工行兜底聚合并按权重分摊工期 | `Todo` |
| `ProjectTask` | 合同 `ItemType.Construction` 行 → 施工任务；`ItemType.Material` 行 → 材料计划（不生成任务） | `Todo` |
| `MaterialPlan` | 每条合同主材行一条计划，带选材快照、损耗率、需求时间=项目开工日 | `Planned` |
| `Receivable` | 按**付款计划快照**逐节点生成（见 §8.1）；无计划时兜底 30%/40%/30% | `Pending` |
| 副作用 | 报价置 `Converted`；房屋置 `Serving`；客户置 `Serving` | — |

幂等：`contract.project != null` 时重复调用不再建项目，只补应收计划；应收已存在时不再重复生成。

## 4. 按施工计划生成「施工计划阶段节点」

### 4.1 合同级施工计划快照（签约时冻结）`[代码 ContractPlanContext]`

- 模板来源：平台基线 `src/main/resources/baselines/construction-plan-baselines.json`，或企业自定义模板（迁移 `43-企业自定义付款与施工计划模板.sql`）；Boss 可发布/停用/设为默认。
- 签约时 `project/contract/update` 传 `constructionPlanCode`（默认 `RESIDENTIAL_STANDARD_8`）生成快照。
- 快照节点字段：`code / name / sort / defaultDays / plannedStart / plannedEnd / acceptanceMode / description`。
- **计划起止的算法**：以合同 `startDate/planEndDate` 为总窗口，按模板各阶段 `defaultDays` 占比分摊实际天数（向下取整四舍五入，最后一段吃剩余天数）；若合同未填日期，则按模板总天数推算。

平台基线两套计划 `[代码 + 数据]`：

| 模板 | 阶段节点（编码 / 名称 / 标准工期 / 验收模式） |
| --- | --- |
| `RESIDENTIAL_STANDARD_8` 住宅标准八阶段 | 开工交底 PREPARE 5d None → 拆除改造 DEMOLITION 5d 施工完成 → 水电施工 WATER_ELECTRIC 12d 验收通过 → 泥瓦防水 MASONRY 20d 施工完成 → 木作吊顶 CARPENTRY 18d 施工完成 → 油漆墙面 PAINTING 18d 施工完成 → 安装收尾 INSTALL 12d 施工完成 → 竣工保洁验收 COMPLETION 10d 验收通过 |
| `RESIDENTIAL_SIMPLE_5` 住宅精简五阶段 | 开工交底 5d → 水电施工 20d（验收通过）→ 泥木施工 35d → 油漆安装 20d → 竣工验收 10d（验收通过） |

### 4.2 项目阶段（ProjectStage）生成规则 `[代码 generateFromConstructionPlan]`

1. 逐条复制快照阶段 → `ProjectStage`：`name / stageCode / sort / plannedStart / plannedEnd`，`status=Todo`、`progress=0`、`weight=0`。
2. 随后按合同施工行把任务挂到对应阶段（见 §5）。
3. 按「该阶段施工任务成本合计 ÷ 全部施工任务成本」计算 `weight`（成本占比即阶段权重），用于项目进度加权。

兜底路径（合同没有施工计划快照时）：`generateFromContract` 按合同施工行分类关键词创建阶段，再 `scheduleStages` 按权重把总工期拆到各阶段。

### 4.3 阶段节点重排与开工 `[代码]`

| 动作 | Provider | 角色 | 规则 |
| --- | --- | --- | --- |
| 调整项目开完工日期（连带重排阶段计划） | `project/project/update` | Boss / PM | 校验完工不早于开工；`scheduleStages` 按阶段权重重算各阶段 `plannedStart/End`，并把日期回写合同 |
| 阶段开工 | `project/stage/update` | Boss / PM | 前置：合同非 Draft/PendingSign/Signed（即已生效）、项目已指定项目经理、开完工日期已确认、量房已 `Completed`；行级锁 + 幂等；写「阶段开工」对业主可见动态 |

> ⚠️ 阶段开工接口**只支持 `Todo → Doing`**，不支持直接改阶段计划日期；阶段日期变更只能通过项目日期重排（`project/project/update`）。

## 5. 「工艺任务」= 施工任务：生成与排期

### 5.1 术语对齐 `[业务 术语表]`

> 任务 = **阶段 × 区域 × 工艺 × 数量** 形成的可执行施工项；不等于报价行。

后端 `ProjectTask` 字段对应该定义 `[代码]`：

| 业务维度 | 字段 | 来源 |
| --- | --- | --- |
| 阶段 | `stage` | 合同施工计划阶段 / 兜底分类阶段 |
| 区域 | `zone` | 合同行 `spaceName`，或排期时选择的施工区域（`SpaceType` 枚举：卧室/厨房/客厅/餐厅/卫生间/阳台） |
| 工艺 | `craft`（文本）+ `catalogItem` | 施工项目录 `CatalogItem.craft`（`type=Construction`） |
| 数量/单位 | `quantity` / `unit` | 合同行，或排期时录入 |
| 计划 | `plannedStart` / `plannedEnd` | 自动取所属阶段计划起止；手工排期可单独指定 |
| 金额/成本 | `salePrice` / `cost` | 合同行（成本为签约冻结成本） |
| 责任人 | `owner` | 默认项目 `manager`，可指定 |
| 留证 | `evidenceUrls` / `conceal` | 现场证据；`conceal=true` 表示含隐蔽节点 |

`conceal` 自动判定规则 `[代码]`：任务名或目录编码包含 `隐蔽 / 水电 / 防水 / 布线 / 管路 / 龙骨` 之一即为隐蔽任务。

### 5.2 自动生成（立项时）`[代码 appendConstructionTask]`

合同 `ItemType.Construction` 行 → 关键词把行归入阶段 → 生成任务：

| 关键词 | 落到阶段编码 |
| --- | --- |
| 水电/强电/弱电 | `WATER_ELECTRIC` |
| 泥/瓦/防水/贴砖 | `MASONRY` |
| 木/吊顶 | `CARPENTRY`（无该阶段时回退 `MASONRY`） |
| 油漆/涂料/墙面 | `PAINTING` |
| 安装/设备 | `INSTALL`（无该阶段时回退 `FINISH`） |
| 拆除 | `DEMOLITION` |
| 竣/清洁 | `COMPLETION` |
| 其他 | `PREPARE`；完全没有匹配阶段时取第一个阶段兜底 |

### 5.3 设计师手工排期（核心协作动作）`[代码]`

- Provider：`project/task/save`（新增/更新）；删除 `project/task/delete`。
- 角色：`ProjectAccessContext.requirePlanEditor` → **项目设计师 / 项目经理 / 企业负责人**；其他角色 403（`只有设计师、项目经理或企业负责人可以编排施工计划`）。
- App 页面：`subpackages/project/pages/plan.vue`（施工计划总览）＋ `plan-edit.vue`（排期编辑器）。
- 排期交互：**从系统工艺库（施工项目录）选任务 → 关联「阶段 × 区域」→ 设定总量 → 下发项目经理**；支持关键字搜索、同一阶段多区域批量落位。
- 校验：`catalogId` 必须属于本企业（否则 404 `工艺任务不存在或无权访问`）；无 `catalogId` 且任务本身无目录时 400 `工艺任务不能为空`。

### 5.4 阶段权重与项目进度 `[代码]`

```text
阶段权重 weight = 该阶段施工任务成本合计 ÷ 全部施工任务成本合计 × 100
阶段进度 progress = 该阶段任务进度平均值
项目进度 = Σ(stage.weight × stage.progress) ÷ Σ(stage.weight)   （四舍五入）
```

## 6. 影像节点留证（施工进行 / 隐蔽工程 / 施工完成）

Provider：`project/task-node/save`；角色：**仅 Boss / PM** `[代码]`。

| 节点 | 触发条件 | 结果 |
| --- | --- | --- |
| `Start` 施工进行 | 任务必须为 `Todo`；必须上传照片/视频 | 任务 → `Doing`，进度 ≥10，写实际开工日 |
| `Conceal` 隐蔽工程 | 任务必须为 `Doing` 且 `conceal=true`；必须上传证据 | 进度 ≥55（隐蔽未确认不得进入完工） |
| `Finish` 施工完成 | 任务须为 `Doing/Accepting`；隐蔽任务必须先有 `Conceal` 节点；必须上传证据 | 任务 → `Accepting`，进度 90 |

通用规则：

1. **节点必传照片/视频**（无证据直接 400 `施工节点必须上传照片或视频`）。
2. 同一节点的键值唯一，重复提交 400 `该施工节点已经确认`（幂等保护）。
3. 每次节点确认都会：追加任务 `evidenceUrls`、刷新阶段与项目进度、生成一条**对业主可见**的现场动态 `ProjectReport`。
4. 任务推进接口 `project/task/update` 也限定 **Boss / PM**，且隐蔽任务直接进 `Accepting` 会被拒绝（必须先做隐蔽节点留证）。

## 7. 阶段验收与整改复验闭环

### 7.1 提交验收 `[代码 project/acceptance/save]`

- 角色：Boss / PM / Designer。
- 必填：现场照片或视频；有整改问题时必须给责任人和截止日期。
- 规则：阶段内任务全部完成（进度 100）后阶段才具备待验收条件；写 `Acceptance(Pending)`、阶段置 `Accepting`。

### 7.2 业主确认/驳回 `[代码 + 业务 BR-008 / SCN-010]`

| 项 | 口径 |
| --- | --- |
| 确认人 | **业主本人**（小程序授权会话，`customer/acceptance/update`） |
| 员工代录 | 员工端 `project/acceptance/update` 直接抛 403：`业主确认必须由业主本人通过小程序授权会话完成，员工不能代录` |
| 驳回 | 记录问题清单、整改责任人、整改截止日期；验收单 → `Rejected`，阶段回到 `Doing` |
| 复验 | 复用**同一阶段、同一张验收单**，以 `AcceptanceRound` 追加轮次；第 2 轮起必须带整改说明 + 整改后照片 |
| 次数 | 不限次数 |
| 账务 | 整改循环**不修改**合同、成本、应收、应付、结算与利润 |

阶段/项目状态汇总（`refreshProject`）`[代码]`：

```text
任务平均进度 → 阶段 progress
验收 Pending → 阶段 Accepting（项目 Accepting）
验收 Rejected → 阶段 Doing
验收 Confirmed → 阶段 Done + actualEnd
全部阶段 Done → 项目 Finished + actualEndDate
任一阶段开始（progress>0）→ 项目 Ongoing
```

## 8. 财务协作推进规则

### 8.1 应收计划（立项时自动生成）`[代码 generateReceivablePlan]`

- 有付款计划快照：逐节点生成应收，节点带 `triggerType / triggerStageCode / offsetDays / dueDate / amount`。
- `dueDate` 算法：`ContractSigned` 以签约日为基准；`StageStarted` 以该阶段计划开工日为基准；`StageAccepted` 以阶段计划完工日为基准；`ProjectFinished` 以计划竣工日为基准；再叠加 `offsetDays`。
- 无付款计划时兜底：签约款 30% / 开工款 40% / 竣工尾款 30%（备注“可由财务调整”）。

平台基线付款计划 `[代码 + 数据]`：

| 模板 | 节点 |
| --- | --- |
| `STANDARD_30_40_30` 标准三段式 | 合同签约款 30%（签约触发）→ 项目开工款 40%（PREPARE 阶段开始）→ 竣工尾款 30%（项目完工） |
| `PROGRESS_4_STAGE` 四段节点收款 | 签约 30% → 水电验收 25%（WATER_ELECTRIC 阶段验收）→ 泥木验收 25%（MASONRY）→ 竣工 20% |
| `FIRST_FINAL_50_50` 签约与竣工 | 签约 50% → 竣工 50% |

### 8.2 收款核销 `[代码 finance/receipt/save]`

- 角色：Boss / Finance（`requireEditor`）。
- 必须指定项目 + 应收节点；金额 >0 且**不得超过该应收节点未收余额**。
- 同一事务内完成：写 `Receipt` → 更新应收 `receivedAmount/status` → 写资金台账 `Ledger`。
- 幂等键：客户端 `idempotencyKey` 缺失时服务端按业务指纹生成；重复提交返回原收款，不再重复核销。

### 8.3 应付与账期 `[代码]`

- 采购下单即形成应付 `Payable`（不等到到货）；材料到场确认 `project/goods-receipt/save` 回填账期起算日与实际到期日（迁移 `55-应付账期到场回填.sql`）。
- 账期算法 `PayableDueDateContext`：`ReceiptDays` = 收货日 + 账期天数（默认 30）；`MonthlyCutoff` = 按截账日（默认 25 日，上限 28）归集后再顺延账期天数。
- 历史采购单无应付时自动补建，保证应付不缺失。

### 8.4 变更、结算与利润 `[代码 + 业务]`

- 合同变更经「发起 → Boss 审批 → 客户确认」后：更新合同 `currentAmount`、项目 `contractAmount`、刷新项目，并同步应收（增项生成「变更款」应收，默认 7 天到期）。
- 结算：`finance/settlement/save` 汇总合同额、变更额、扣减、预计成本、实际成本、利润、毛利率与 `costComplete`。
- 成本口径（`ProjectCostContext`）：签约后预计成本优先合同行冻结成本；实际成本优先采购到货/入库实际值；**任一应计成本缺失 → `costComplete=false`，利润与毛利率返回 `null`**，前端显示“成本未完整”。
- 权限：财务读 = Boss / Finance / StoreManager；财务写 = Boss / Finance。

## 11. 验收关注点（建议 acceptance 覆盖）

1. **正向**：报价接受 → 签约（最终价）→ 生效 → 项目自动生成 8 阶段 + 任务 + 材料计划 + 应收；金额/面积/成本与快照一致。
2. **反向**：未生效合同、无报价、重复立项、同一房屋第二个项目、跨企业 quoteId/empId —— 全部阻断且报错可读。
3. **排期**：设计师下发工艺任务（阶段 × 区域 × 数量）→ 项目进度加权正确；非项目设计师/财务/业务员调用 `project/task/save` 得 403。
4. **节点**：无证据提交节点被拒；隐蔽任务跳过隐蔽节点直接完成被拒；重复节点被拒。
5. **开工前置**：未指定项目经理、未确认开完工日期、未完成量房时开工被拒。
6. **验收**：员工代业主确认被拒；驳回 → 复验多轮留痕；整改轮次不改金额/成本/账务。
7. **财务**：收款不得超过应收余额；重复收款幂等；采购到场回填账期；成本不完整时利润为 `null`。
8. **数据范围**：四角色 + 跨企业 + 项目参与关系；PM 只能看本人负责项目（`ProjectManagerAccessContext`）。

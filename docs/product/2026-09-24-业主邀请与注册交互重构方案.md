# 业主邀请与注册交互重构方案（2026-09-24）

> 批次：`REQ-MH-INVITE-20260924`
> 来源：用户反馈（真实操作体验）——"客户邀请、员工邀请及注册用同一个页面；业务邀请进入未加入企业页还要填邀请码，下面还有创建企业，**非常违反产品要求，会引起业务很大的操作错误**"
> 事实来源：`zhuangdeqing-business` 规范库（`SCN/BR/DEC/GAP`）+ 代码核对 + 本方案 §1 现状证据
> 状态：**设计冻结待业务裁决**（§10 的 5 个问题未答复前不得进入实现）

## 1. 现状与问题（含证据）

### 1.1 现状：三种"进入"被塞进两个页面

| 入口 | 页面 | 当前行为 |
|---|---|---|
| 业主邀请 | `pages/invite/accept.vue` | 与员工邀请**同一页面**；靠 `query.type === 'customer' \|\| !!token` 推断是业主（**有 token 就认业主**） |
| 员工邀请 | `pages/invite/accept.vue` | 同一页面另一分支，需 `inviteId` |
| 未加入企业 | `pages/company/join.vue` | 要求**手动输入"邀请编号或邀请链接"**（`parseInvite()` 支持数字编号/链接/token 三种猜测式解析），**同页下方还有"创建企业"** |
| 注册企业 | `pages/auth/enterprise.vue` | 表单创建企业 |

登录后无身份时的跳转（`pages/auth/login.vue`）：
```ts
} else {           // 既不是员工，也没有业主授权
  loginAsUser(profile, token.token)
  uni.redirectTo({ url: P.companyJoin })   // → 未加入企业页（要填邀请码 + 创建企业）
}
```

### 1.2 问题（按严重度）

| # | 问题 | 后果 |
|---|---|---|
| P1 | **同一页面承担业主/员工两种邀请**，且用"有 token 就是业主"推断 | 参数一坏（token 丢失/串参数）就把业主当员工、员工当业主处理，**身份判定不可靠** |
| P1 | **未加入企业页要求手填邀请码**，且识别逻辑靠"猜"（数字=员工邀请，长串=业主 token） | 业主看不懂要填什么；员工不知道邀请码在哪；**输入错误直接进错流程** |
| P1 | 未加入企业页**同时出现"创建企业"** | 员工本想加入企业，误点创建企业 → **建出重复企业/错企业**，污染租户数据（不可逆） |
| P2 | 业主进入必须有邀请（token/inviteId） | 业主换手机、邀请过期、链接被转发都会卡住；且**已建档的老客户**也要走邀请 |
| P2 | 无企业用户每次登录都被推到"填邀请码" | 无法"先看看再说"，也无法表达"我有装修项目、我是业主" |
| P2 | **注册企业后无注销入口** | 误创建企业无法自助纠正，只能找运营 |

## 2. 目标原则

1. **身份由事实决定，不由参数决定**：业主身份来自"**客户档案里的手机号 + 该项目**"，不来自 token；员工身份来自"**企业邀请 + 手机号**"。
2. **一个入口只做一件事**：业主入口、员工入口、注册企业**三个独立页面**，不做"猜参数"。
3. **可退出、可重来**：允许"暂不属于任何企业"的中间态存在，下次登录再判定；创建企业后可注销。

## 3. 真实业务场景梳理（5 个）

> 人物与项目为合成示例；口径引用 `SCN-006`（签约后业主确认）、`DEC-009`（业主可见性）等。

### 场景 A｜业主收到装修公司邀请（主流）
- **使用人**：业主 王女士
- **触发**：设计师在项目里点"邀请业主"，发出一条带业主手机号的邀请
- **当前动作**：点开链接 → 落到 `invite/accept` → 若参数完好才走业主分支
- **系统下一步（目标）**：**专用业主页** → 一键"微信授权手机号" → 后端按**手机号 + 该项目**匹配客户 → 匹配成功直接进"我的家"
- **异常**：手机号与客户档案不一致 → 提示"未找到与您手机号匹配的装修项目，请联系您的设计师核对手机号"

### 场景 B｜业主没收到邀请，自己扫码/搜索进入（要支持的）
- **触发**：业主听说公司用了装得清，自己打开小程序
- **当前动作**：微信登录 → 被推到"未加入企业页"要求填邀请码（**业主根本不知道邀请码**）
- **系统下一步（目标）**：微信登录 → **授权手机号** → 后端按手机号在全平台范围内找"该手机号名下的客户/项目"
  - 恰好命中 **1 家企业** → 直接进"我的家"
  - 命中**多家企业** → 让业主选择"我要看哪个项目"（**不允许静默选第一家**）
  - 完全没命中 → 进"**选择页**"：① 我有装修项目（→ 提示联系设计师绑定/留资）② 我要注册装修公司（→ 企业注册）
- **异常**：手机号命中多家企业时若默认取一家 → **跨企业串号事故**（本项目 `AGENTS.md` 明令禁止）

### 场景 C｜员工被邀请加入企业
- **使用人**：设计师 李工
- **触发**：店长发员工邀请（邀请编号/链接）
- **当前动作**：落到同一邀请页，靠 `inviteId` 分支；若走成"未加入企业页"要手填邀请编号
- **系统下一步（目标）**：**专用员工页**（`inviteId` + 手机号授权）→ 校验手机号与邀请预留手机号一致 → 加入企业
- **异常**：手机号与邀请不符 → 明确提示"该邀请预留手机号与当前微信不一致，请联系邀请人"

### 场景 D｜无企业的普通用户打开小程序
- **触发**：既不是员工、也没有业主项目
- **当前动作**：每次登录都被推到未加入企业页
- **系统下一步（目标）**：展示"**选择页**"：① 我有装修项目 ② 我要注册装修公司 ③ 以后再说（**允许离开**）
  - 选"以后再说" → 记住"未归属"状态，**下次登录仍走同一个判定**（用户要求：没有注册企业的可以在下次登录时判定）
- **异常**：不得强制其注册企业；不得凭空创建企业

### 场景 E｜企业负责人要注销自己创建的企业
- **触发**：误创建 / 停止经营 / 想重新注册
- **当前动作**：**没有入口**（只能找运营）
- **系统下一步（目标）**：企业设置 → "注销企业" → 二次确认 + 输入企业全称核对 + 说明数据与订阅处理 → 提交注销
- **异常**：有在跑项目/未结款项/未到期订阅时必须**阻断并说明原因**（不能一键清空）
- **业务待裁决**：注销是"立即停用"还是"申请后由平台审核"；数据保留期；订阅与席位如何处理（见 §10 Q5）

## 4. 目标交互流程

### 4.1 页面拆分（一页一事）

| 页面 | 路由（建议） | 谁用 | 关键点 |
|---|---|---|---|
| 业主绑定/进入 | `pages/owner/enter`（新） | 业主 | **只用手机号**，不出现"邀请码/token"字样 |
| 员工加入企业 | `pages/invite/accept`（保留，**只服务员工**） | 员工 | 只认 `inviteId`；不再猜 token |
| 无归属选择页 | `pages/account/entry`（由 `company/join` 改造） | 无企业用户 | **删掉"填写邀请码"**；只保留"我有装修项目 / 注册企业 / 以后再说" |
| 注册企业 | `pages/auth/enterprise`（保留） | 新企业负责人 | **问企业信息，不问邀请码**（现状已无邀请码，需删除 `company/join` 上的入口混淆） |

### 4.2 微信登录后的统一判定（伪代码）

```text
登录成功（已拿到 session）
  ├─ 有在职员工身份？            → 进工作台
  ├─ 有业主授权（customerAccesses）？→ 进「我的家」
  └─ 都没有 → 用手机号做一次"身份探测"
        ├─ 手机号命中 1 家企业的客户且有项目 → 自动建立业主授权 → 进「我的家」
        ├─ 命中多家 → 进入"选择项目"页（列出项目让用户选）
        └─ 未命中 → 进「无归属选择页」
              ├─ 我有装修项目 → 引导（留手机号/联系设计师；命中后走上一分支）
              ├─ 我要注册装修公司 → 企业注册
              └─ 以后再说 → 记住未归属，下次登录重新判定
```
> 关键：**身份探测只在"当前无身份"时做一次**，不改变员工判定优先级；企业注册只在用户明确选择后发生。

### 4.3 文案原则（人性化）

| 场景 | ❌ 不要 | ✅ 改成 |
|---|---|---|
| 业主绑定页 | "请输入邀请码/邀请链接" | "验证手机号，进入我的家"（一句话说明：与装修公司登记的号码一致即可） |
| 手机号不匹配 | "邀请不可用" | "没找到与这个手机号匹配的装修项目。请让您的设计师核对登记的手机号，或换一个号码重试" |
| 无归属选择页 | "请输入邀请码加入企业" | "您还没有加入装修公司。您是业主还是装修公司？"（两个大按钮） |
| 员工加入 | "邀请编号" 裸字段 | "粘贴店长发您的邀请链接"（并提供"从微信聊天里点开"的说明） |
| 企业注册 | 与邀请混排 | 独立入口；标题"注册你的装修公司" |

## 6. 权限与安全（本方案最大风险区）

### 6.1 ⚠️ 跨企业串号风险（必须正面解决）

**"输入手机号 → 判断是不是业主"在没有企业上下文时是不安全的**：

- 同一个手机号可能在**多家企业**都有客户档案（例如业主在 A 公司装过、又找了 B 公司）；
- 若实现为"命中任意一条就建立授权并直接进入"，就会**把 A 公司的项目暴露给 B 公司的客户关系**，反之亦然 → **跨租户越权（P0）**。

**必须遵循：**
1. 匹配范围必须是"**该手机号名下的全部客户档案**"，并把命中的**企业/项目列给用户选择**，**禁止静默取第一条**；
2. 命中多家企业时，**每个项目单独授权**（一个 `CustomerAccess` 对应一个项目），不允许一次授权拿到全部；
3. 匹配只依据 `Customer.telNo`（客户档案登记号）与微信授权手机号**完全一致**；不做模糊匹配、不按姓名匹配；
4. 任何"未命中即创建客户/项目"的行为**一律禁止**（业主进入不产生业务事实）。

### 6.2 其他安全项

| 项 | 要求 |
|---|---|
| 手机号来源 | 只接受微信 `getPhoneNumber` 的 code 换取的手机号；**不接受前端直接传手机号字符串** |
| 员工判定优先 | 员工身份优先于业主身份；不允许用业主链路绕过企业数据范围 |
| 邀请去留 | 员工邀请仍必须 `inviteId` + 手机号一致；不接受"猜 token" |
| 审计 | 业主授权建立要留痕（来源、时间、命中的客户/项目、操作凭据） |
| 越权回归 | 覆盖：跨企业同号、跨门店、伪造手机号、重复绑定、解绑后重登 |

## 7. 异常与边界

| 场景 | 处理 |
|---|---|
| 微信未授权手机号 | 停在业主页，说明"需要验证手机号才能看到您的工地"，可重试；不得反复跳登录 |
| 手机号命中企业但项目已结束/归档 | 仍可进入「我的家」只读查看，不阻断 |
| 手机号命中多条客户档案（同企业多套房） | 列出房屋让业主选，不合并 |
| 同一个微信换绑手机号 | 解绑旧手机号的授权？→ 需裁决（§10 Q3） |
| 业主同时是某企业员工 | 按员工身份进入，另提供"我的家"入口（当前已有主页入口） |
| 邀请已过期/已撤销 | 走"无邀请进入"的同一路径（不报死） |
| 连续误输手机号 | 限制尝试频次，避免手机号枚举探测（**必须防枚举**） |
| 企业注销中 | 员工登录提示"企业正在注销"，只读；业主仍可回看历史 |

## 8. 验收标准（可测）

1. **页面隔离**：业主入口页面上不出现"邀请码/邀请链接/token"任何字样；员工入口不出现手机号以外的身份猜测逻辑（代码层 `invite/accept` 不再接受 `token`）。
2. **业主进入**：手机号与客户档案一致 → 直接进入「我的家」，全程 ≤2 次点击。
3. **多企业同号**：构造同一手机号在 2 家企业的客户档案 → 必须出现选择页，且**只能看到自己选中的那一个项目**（越权反向用例）。
4. **非业主**：手机号未命中 → 进选择页，**不产生任何业务事实**（客户/项目/授权计数不变）。
5. **无归属重复登录**：选择"以后再说"后再登录 → 仍进同一判定，不强制注册。
6. **注册企业**：注册页无邀请码字段；注册成功后成为该企业 Boss，可直接进入工作台。
7. **注销**：有在跑项目时注销被阻断并给出原因；无在跑项目时可提交注销，注销后（按裁决）不能再次登录或进入只读态。
8. **回归**：员工邀请流程不受影响；`invite/accept` 只处理员工。

## 0. 结论摘要

### 0.1 建设判断

装得清小程序已经正式上线，但当前运营管理端仍是“租户订阅与系统运维后台”，不是“小程序运营工作台”。

现状可概括为：

```text
有企业、套餐、订阅、审计、系统状态
缺小程序用户、渠道、生命周期、内容、触达、反馈、发布、实验和效果闭环
```

因此建议新增平台级“小程序运营域”，不与租户业务域混写：

```text
微信小程序产生的行为事实
-> 平台只读运营投影
-> 运营识别、分组、服务、内容、触达或实验
-> 审计与效果回看
-> 下一次运营动作
```

核心原则：

1. **平台运营端不是第二套租户业务端**。不能从小程序运营页直接改客户、报价、合同、项目、验收、成本和财务事实。
2. **小程序用户不等于企业客户**。需要区分访客、微信身份、手机号身份、员工、业主和企业经营者，不得用单一状态硬塞。
3. **同频不是全透明**。平台运营也必须遵守角色、企业、项目和字段边界，不能因为跨企业权限而读取客户正文、项目照片、成本或聊天内容。
4. **活跃不等于成功**。打开次数、页面访问和消息发送不能直接证明装企经营改善。
5. **先只读，后动作**。P0 先建立数据、队列、反馈、发布和审计；P1 才开放内容、消息、活动和实验。
6. **没有来源就不显示确定值**。埋点缺失、企业数据不可读、微信未授权和指标分母未定义时，界面必须显示“暂不可确认”，不能用 `0` 伪装。

### 0.2 现有事实与证据状态

| 事实 | 当前状态 | 依据 | 本文处理 |
| --- | --- | --- | --- |
| 小程序是多角色主业务端 | 已实现，具体链路成熟度不一 | `CAP-003`、`EV-005` | 作为运营对象，不复制业务实现 |
| 小程序 v1.0.7 已由管理员提交审核并正式发布 | 用户确认；后台截图和线上版本号证据待补档 | 小程序发布记录 2026-09-26 | 建立发布记录与证据归档 |

| 同频效果指标 | 待冻结 | `GAP-014`、`DEC-013` | 只提供候选观察项，不做统一效果分 |

### 0.3 本文建议的首发范围

**P0 可直接进入方案评审，但开发前需完成业务咨询单中的隐私和权限裁决：**

- 小程序运营总览；
- 小程序用户与渠道聚合；
- 旅程与激活运营队列；
- 小程序产品反馈与客服协同；
- 发布、合规、功能开关记录；
- 事件采集、指标口径、审计和权限；
- 与现有企业、订阅、使用进度和系统状态联动。

**P1 在 P0 稳定后开放：**

- 首页内容、公告、帮助中心版本化运营；
- 站内消息和微信一次性订阅消息任务；
- 受控运营活动与试用权益；
- 分组、实验和自动提醒。

**暂不进入本期：**

- 广告投放平台；
- 微信客服聊天记录抓取；
- 跨租户客户正文浏览；
- 现金券、积分商城、自动扣款和发票系统；
- 小程序代码自动审核或自动发布；
- 小程序内任意远程代码执行；
- 以小程序访问量替代企业经营指标。

## 1. 产品定位与目标

### 1.1 产品定位

小程序运营管理平台是面向平台运营团队的“用户经营、内容触达、服务质量和发布治理工作台”，围绕小程序生命周期运营，不替代租户内部的客户、项目、财务和协同系统。

一句话定义：

> 让平台团队看得见小程序用户如何进入、如何激活、在哪里受阻、需要什么服务，并能以有权限、有审批、有回滚、有审计的方式完成内容和触达运营。

### 1.2 目标

| 目标 | 目标说明 | 可验证结果 |
| --- | --- | --- |
| G1 统一观察 | 把小程序用户、渠道、版本、租户激活和反馈放到同一视图 | 运营可从总览下钻到企业或事件 |
| G2 统一口径 | 事件、指标、版本和状态只定义一次 | 页面、报表、导出和消息使用同一指标定义 |
| G3 生命周期服务 | 覆盖访客、注册、加入、激活、付费、续费、流失和召回 | 每家企业有明确服务队列和下一步 |
| G4 内容与触达可控 | 内容、消息和活动具备草稿、审核、发布、停用和回滚 | 每次发布可追溯、可撤销 |
| G5 反馈可闭环 | 产品反馈、技术异常和服务问题可分级、指派和回复 | 有状态、责任人、SLA 和结论 |
| G6 发布可治理 | 版本、合规、能力和配置有记录，不依赖个人记忆 | 发布前检查、发布后观察和回滚路径可见 |
| G7 权限不扩张 | 平台运营能力不突破租户数据边界 | 越权、跨租户和敏感字段测试通过 |

### 1.3 非目标

- 不在平台端替企业创建客户、跟进、报价、合同或项目。
- 不把小程序页面点击当成企业真实业务完成。
- 不新增普通员工角色，不改变现有 7 类企业员工角色。
- 不复制另一套用户、企业、客户、项目或消息主数据。
- 不承诺固定转化率、续费率和效率提升值；目标值必须由用户或正式业务口径确认。
- 不把 `draft`、`hypothesis` 或未验收内容上线成对外标准文案。

## 2. 现状与差距

### 2.1 当前运营端能力

当前 Admin 已具备：

| 分组 | 现有页面/能力 | 数据来源 | 关键限制 |
| --- | --- | --- | --- |
| 经营驾驶舱 | 平台运营总览 | `platform/dashboard/info` | 主要看企业、订阅、收入、席位和门店 |
| 客户成功 | 客户企业、订阅与续费 | `platform/tenant/**`、`platform/subscription/update` | 缺小程序用户、激活、渠道和服务队列 |
| 市场运营 | 增长运营、套餐策略 | `platform/dashboard/info`、`platform/plan/list` | 部分增长卡为静态运营叙事，缺真实小程序事件 |
| 平台运维 | 系统运维、操作审计 | `platform/system/status`、`platform/operation/page` | 审计动作枚举主要围绕订阅调整 |
| 企业侧 | 使用进度 | `statistic/success/report` | 只对企业 Boss 可见，平台未形成跨企业队列 |

### 2.2 能力差距矩阵

| 领域 | 当前能力 | 主要缺口 | 业务影响 | 本文建议 |
| --- | --- | --- | --- | --- |
| 运营总览 | 租户/订阅/收入趋势 | 无小程序活跃、渠道、版本、角色和反馈指标 | 无法判断小程序产品健康度 | 新增小程序运营驾驶舱 |
| 用户 | 租户员工与业主登录存在 | 无匿名访客、微信身份、手机号绑定、多角色覆盖面 | 看不到用户在哪一步流失 | 以身份覆盖面和事件聚合建模，不造单一身份状态 |
| 渠道 | 官网线索已采集 | 无扫码、分享、邀请、活动来源归因 | 不知道自己来的用户来自哪里 | 建立渠道链接、场景值和转化归因 |
| 注册/加入 | 企业注册、员工/业主邀请存在 | 无跨企业注册漏斗和失败诊断 | 运营只能看结果，看不到卡点 | 建立注册与邀请漏斗 |
| 激活 | 企业内有 7/14/30 天投影 | 平台无统一队列；完成谓词待冻结 | 客户成功动作靠人工发现 | 复用投影，建立平台运营队列 |
| 内容 | App 内帮助中心为前端内容 | 无平台内容版本、发布、审核和回滚 | 改内容要发版或改代码 | 建立平台内容中心 |
| 触达 | 四类业务订阅消息 | 无模板治理、消息任务、频控、送达记录 | 无法追踪触达效果，也可能误触达 | 建立业务通知与运营触达分层 |
| 活动 | 增长页有策略展示 | 无活动对象、受众、限制、权益、效果 | 活动靠人工和表格 | 建立受控活动中心 |
| 反馈 | 项目意见投诉、微信客服、帮助中心 | 无平台产品反馈工单和 SLA | 产品问题无法统一收敛 | 建立产品反馈工单，不抓取私聊 |
| 发布 | 本地发布记录 | 无平台版本台账、检查和回滚记录 | 版本、域名、模板和法律文本易漂移 | 建立发布与合规记录 |
| 实验 | 无 | 无功能开关、灰度、实验和守护指标 | 不能小范围验证又安全回退 | 建立白名单配置和实验框架 |
| 数据 | 业务统计与流量日志分散 | 无统一事件契约和指标字典 | 页面数字不可解释、不可比较 | 建立事件、指标和血缘定义 |
| 权限/审计 | 平台权限与订阅审计存在 | 不覆盖内容、消息、活动、发布和实验 | 高风险运营动作无闭环 | 扩展平台权限、双人审批和统一审计 |

### 2.3 不能直接继承的假设

1. 微信不会向平台提供“全部小程序用户列表”。只有用户经过本产品登录或授权后，平台才可能形成可识别身份。
2. 微信订阅消息是一次性授权。用户未授权、额度用尽或退订返回 `43101` 是正常状态，不是系统故障。
3. 小程序代码发布不能由本后台直接替代微信公众平台审核和发布；后台只能记录、校验和联动配置。
4. 平台运营权限再高，也不能绕过租户业务数据权限读取客户正文、项目照片、成本、合同内部信息或私聊。
5. 小程序访问次数不能直接代表装企经营成功。经营结果必须回到客户、报价、合同、项目和财务事实。

## 3. 真实业务场景推演

本章先于对象、字段和权限定义。以下场景描述“谁在什么事件下做什么、系统下一步做什么、异常如何处理”。

### 3.1 场景一：官网访客进入小程序并注册企业

| 维度 | 场景 |
| --- | --- |
| 使用人 | 潜在装企老板、平台市场增长、客户成功 |
| 触发事件 | 老板从官网“预约”或“体验小程序”入口进入，随后完成微信身份和手机号校验 |
| 当前动作 | 老板选择“我是装修公司，要注册企业”，填写企业信息并成为企业负责人 |
| 系统下一步 | 记录来源渠道、首次进入时间、身份步骤、注册结果；为企业建立客户成功队列；展示“先用一单对齐”的下一步 |
| 异常处理 | 手机号已绑定其他微信、手机号属于其他企业、重复注册、退出中途、微信会话失效时只显示可确认的事实，不自动合并企业或提升身份 |
| 运营结果 | 可知道“官网来源 -> 小程序访客 -> 手机号身份 -> 企业注册”的每一步和流失点 |

**边界**：`GAP-013` 未冻结前，官网 `SiteLead` 与小程序企业注册只做只读关联候选，不自动认定有效线索、客户或成交。

### 3.2 场景二：新企业 7 天未建立客户和房屋

| 维度 | 场景 |
| --- | --- |
| 使用人 | 客户成功、企业 Boss、平台运营主管 |
| 触发事件 | 企业注册后进入第 7 天，仍无客户和房屋事实 |
| 当前动作 | 客户成功在“激活队列”打开企业和使用进度，确认是缺资料、未邀人、不会操作还是无意向 |
| 系统下一步 | 标记服务优先级，生成或指派运营任务；企业侧看到“下一步做一件事”，而不是一张功能清单 |
| 异常处理 | 企业数据不可读时显示“暂不可确认”；负责人已停用时不自动联系；免打扰或无联系方式时进入待人工处理 |
| 运营结果 | 从公开使用进度到“可执行的客户成功队列”，且不新增企业业务状态 |

**依赖**：`GAP-019` 冻结前，系统不得显示“激活已完成”或统一首单对齐率，只显示现有里程碑的 `Done/Todo/Overdue` 事实。

### 3.3 场景三：业主在小程序反馈工地问题

| 维度 | 场景 |
| --- | --- |
| 使用人 | 业主、项目经理、平台产品/客服 |
| 触发事件 | 业主在本人项目中提交意见或投诉，或在帮助中心反馈“问题仍存在” |
| 当前动作 | 项目团队在租户项目内处理意见投诉；若是平台功能、性能或小程序的共性问题，用户选择允许平台使用脱敏诊断信息 |
| 系统下一步 | 租户反馈继续在项目内闭环；产品反馈进入平台工单，关联页面、版本、错误码、请求追踪号和租户标量快照 |
| 异常处理 | 未授权共享正文时不进入平台；跨企业内容不得展示；同一错误去重合并但保留来源数量；高风险投诉只显示升级信号，不把所有正文暴露给平台 |
| 运营结果 | 平台能发现版本性、区域性、机型性或共性问题，同时保持租户与业主隐私边界 |

### 3.4 场景四：内容运营发布首页公告

| 维度 | 场景 |
| --- | --- |
| 使用人 | 平台内容运营、运营主管、审计合规 |
| 触发事件 | 新产品能力上线、维护通知、法律文本更新或活动上线，需要在小程序呈现 |
| 当前动作 | 内容运营选择模板、受众、时间、跳转页和降级版本，提交审核 |
| 系统下一步 | 审核通过后按计划发布；小程序只读取平台允许公开的配置；发布后记录曝光、点击和异常；到期自动下线或人工停用 |
| 异常处理 | 目标页不存在、文案含未验证口径、图片不合规、审核驳回、发布冲突时禁止上线；线上异常可回滚到上一版本 |
| 运营结果 | 内容改动不依赖紧急发版，且可追溯、可撤回 |

### 3.5 场景五：提升阶段验收触达到达率

| 维度 | 场景 |
| --- | --- |
| 使用人 | 平台运营、项目经理、业主 |
| 触发事件 | 阶段验收待业主确认 |
| 当前动作 | 业务系统已有站内通知和一次性订阅消息；平台观察授权、发送、未订阅和失败分布 |
| 系统下一步 | 业务通知继续由业务事件触发；运营端只管理模板绑定、文案规范和发送记录；未订阅用户只通过站内/项目入口提醒，不重复骚扰 |
| 异常处理 | `43101` 记为未授权或额度耗尽；模板字段错误、超长或微信异常单独归档；不因触达失败回滚验收业务 |
| 运营结果 | 能区分“业务没发生”“用户未授权”“微信发送失败”和“用户已看到”，而不是把发送失败算成未确认 |

### 3.6 场景六：小程序版本发布后出现异常

| 维度 | 场景 |
| --- | --- |
| 使用人 | 平台发布负责人、SRE、开发、运营主管 |
| 触发事件 | v1.0.8 发布后发现上传失败率或页面错误上升 |
| 当前动作 | 发布负责人查看版本采用率、受影响页面、错误指纹、反馈聚类和依赖状态 |
| 系统下一步 | 暂停相关功能开关或内容配置，回滚非代码配置；必要时提交微信新版本热修；保留事故与发布关联 |
| 异常处理 | 小程序旧版本仍可能被用户使用；无法回退已发布代码时，只能配置降级和引导更新，不能假装已回滚 |
| 运营结果 | 版本问题能关联到用户影响、反馈、配置和发布动作，形成发布复盘 |

| 数据类别 | 默认处理 | 可访问角色 | 禁止事项 |

| 客户/项目正文 | 平台端默认禁止 | 仅在明确授权的升级处理中临时读取 | 全量浏览、搜索、导出 |
| 项目照片/验收证据 | 平台端默认禁止 | 技术问题需用户授权脱敏样本 | 复制到运营素材库 |
| 聊天/客服内容 | 本期不接入 | 无 | 抓取私聊或冒充客服 |
| 配置和发布 | 版本化保存，不放密钥 | 发布负责人、审计 | 在数据库保存 AppSecret/API v3 Key |

### 4.4 四条硬边界

1. `db_platform_*` 与租户表禁止外键；租户读取统一经 `TenantDataAdapter` 或正式只读投影。
2. 平台运营动作只能写平台运营对象，不能借“客服”名义修改客户、报价、合同、项目、验收、成本或财务。
3. 敏感查看、导出、内容发布、消息发送、权益发放和配置发布必须写统一审计。
4. 审计记录不可在运营端删除；操作原因、前后值、审批人和目标快照必须保留。

## 6. 功能需求

### 6.1 小程序运营总览

#### 6.1.1 页面目标

让运营负责人在 30 秒内回答：

- 小程序今天/本周是否有足够用户进入；
- 新用户走到了哪一步；
- 哪些企业已经激活、待激活或存在风险；
- 哪些内容或消息正在产生影响；
- 哪些版本、错误或反馈需要立即处理；
- 哪一项动作最值得先做。

#### 6.1.2 页面结构

| 区域 | 内容 | 数据来源 | 交互 |
| --- | --- | --- | --- |
| 顶部状态条 | 当前线上版本、发布时间、微信审核状态、核心依赖状态 | 发布记录、系统状态 | 点击进入发布与合规 |
| 核心指标 | 活跃用户、身份绑定、企业注册、激活企业、付费转化、反馈解决 | 事件聚合、租户投影、订阅 | 点击下钻到对应列表 |
| 生命周期漏斗 | 访客 -> 微信身份 -> 手机号绑定 -> 加入/注册企业 -> 角色激活 -> 首单对齐 -> 付费 | 事件和服务端事实 | 每段显示绝对值、转化率和缺失分母 |
| 企业服务队列 | P0 风险、7/14/30 天逾期、临期、反馈升级 | 使用进度、订阅、反馈 | 指派、查看、记录服务动作 |
| 内容与触达 | 在线内容、待审核内容、消息送达/未授权/失败 | 内容、消息任务 | 查看详情、暂停或回滚 |
| 技术与反馈 | 小程序错误、版本分布、反馈聚类 | 事件、发布记录、反馈 | 进入反馈或版本详情 |
| 运营动态 | 最近发布、发送、活动、调整和审批 | 平台审计 | 只读，可筛选 |

#### 6.1.3 指标显示规则

- 每个指标必须显示口径名称、时间窗和更新时间。
- 分子存在、分母不存在时返回 `null` 和“暂不可确认”，不显示 `0.00%`。
- 微信数据、客户端埋点和服务端业务事实分开显示，不能把不同来源硬合并成一个“总用户数”。
- 同比或环比缺少上期基线时不显示伪增长。
- 所有数值卡片可下钻到证据列表，不允许只有数字没有来源。

#### 6.1.4 权限与异常

- 默认只对 `MiniProgramDashboardRead` 开放。
- 普通运营只看到聚合；敏感企业明细需额外权限。
- 数据延迟超过阈值时显示“数据截至时间”，不能把延迟数据伪装成实时。
- 采集异常时显示“数据暂不可确认”，保留近一次有效快照和恢复时间。

### 6.2 用户与渠道

#### 6.2.1 用户模型

不使用单一的“用户状态机”，使用身份覆盖面：

```text
匿名访客
+ 微信身份
+ 手机号身份
+ 企业员工身份
+ 业主身份
+ 企业经营者身份
```

同一自然人可能是多企业员工或多个项目业主，因此“员工”和“业主”不是互斥状态。

#### 6.2.2 用户列表

| 字段 | 说明 | 脱敏/权限 |
| --- | --- | --- |
| 用户标识 | 平台内部伪匿名 ID | 所有人可见 |
| 微信指纹 | `openId` 派生指纹，不显示原文 | 默认可见 |
| 手机号 | 掩码 `138****1234` | 敏感权限后可见 |
| 身份覆盖面 | 微信、手机号、员工、业主、企业负责人 | 聚合权限 |
| 关联企业 | 企业名称快照、角色、状态 | 按企业范围 |
| 首次进入/最近活跃 | 事件时间 | 聚合权限 |
| 来源渠道 | 官网、分享、扫码、邀请、订阅消息、搜索、未知 | 聚合权限 |
| 当前版本/机型 | 小程序版本、基础库、设备摘要 | 技术权限 |
| 最近反馈/错误 | 关联工单或错误指纹 | 服务权限 |

支持操作：按渠道、身份、角色、版本、企业、时间和活跃状态筛选；导出仅允许聚合，不允许导出明文手机号和 openId。

#### 6.2.3 渠道与场景

必须支持以下渠道：

- 官网预约和官网小程序入口；
- 员工邀请、业主邀请；
- 微信群/朋友圈分享；
- 线下二维码、物料二维码；
- 搜索和自然访问；
- 订阅消息回跳；
- 合作方活动链接；
- 客服引导；
- 未知来源。

渠道链接记录：

```text
channelCode
sourceType
campaignCode
inviterType
inviterKeyHash
scene
targetPage
startAt/endAt
status
```

每次访问和转化使用同一 `channelCode`，不得用页面参数临时拼接后丢失归因。

#### 6.2.4 用户详情

用户详情分四个区域：

1. **身份**：微信、手机号、员工、业主、经营者覆盖面；不显示凭证原文。
2. **旅程**：首次访问、登录、注册、加入、角色激活、关键业务动作。
3. **企业**：企业快照、订阅状态、角色激活和最近业务事实摘要。
4. **服务**：反馈、运营任务、消息送达和最近操作。

#### 6.2.5 用户合并与例外

- 平台不得自动把两个手机号、微信身份或企业身份合并。
- 同一微信切换账号、手机号换绑、员工离职、业主项目结束都必须保留历史快照。
- 冲突身份进入“待人工确认”，支持记录判断依据和审批。
- 合并必须幂等、可追溯，合并后不可删除原事件。
- 未授权或不可确认的身份不进入营销受众池。

### 6.3 旅程与激活

#### 6.3.1 生命周期阶段

平台显示以下阶段，但阶段只是运营投影，不写入租户业务状态：

```text
未进入
已进入未认证
已认证未归属
已加入/注册企业
角色未激活
业务已开始
已激活
付费转化
续费/扩容
流失风险
```

#### 6.3.2 激活队列

| 队列 | 触发条件 | 首要动作 | 责任人 | 完成条件 |
| --- | --- | --- | --- | --- |
| 新注册未建客户 | 第 7 天仍无客户和房屋 | 联系并选择一个真实业务问题 | CustomerSuccess | 建立最小事实或确认无继续意愿 |
| 有客户无推进 | 第 14 天无报价/合同 | 检查卡点并指导下一步 | CustomerSuccess | 形成正式报价/合同或记录阻塞 |
| 未邀请关键角色 | 第 7 天除 Boss 外无成员 | 帮助邀请关键岗位 | CustomerSuccess | 至少关键角色建立或记录原因 |
| 角色长期未激活 | 岗位已配置但无业务事实 | 按角色给下一步 | CustomerSuccess | 岗位产生真实业务事实或转为待观察 |
| 付费临期 | 7/30 天内到期 | 续费方案和价值复盘 | CustomerSuccess | 续费、扩容、延期决策或关闭原因 |
| 高风险流失 | 高风险等级 | 24 小时内联系 | CustomerSuccess/OpsManager | 形成可追踪结论 |

#### 6.3.3 下一步动作

系统从现有事实推导“下一步”，但不自动替企业操作：

- 缺客户/房屋 -> 建立客户和房屋；
- 缺报价 -> 进入设计/报价工作台；
- 缺合同 -> 处理报价确认与签约；
- 缺项目 -> 合同生效并立项；
- 缺财务事实 -> 完成收款或应付款项；
- 缺业主同频 -> 建立项目授权和验收确认；
- 缺角色使用 -> 邀请或重新指派责任角色。

#### 6.3.4 一单对齐视图

在 `GAP-019` 完成裁决前，页面只展示候选结构：

| 节点 | 建议 key | 建议完成条件 | 状态 |
| --- | --- | --- | --- |

### 6.4 内容与公告

#### 6.4.1 内容类型

| 类型 | 用途 | 是否可平台统一 | 是否可企业覆盖 |
| --- | --- | --- | --- |
| 首页 Banner | 产品能力、活动、公告 | 是 | 待业务裁决 |
| 公告条 | 维护、法律、版本和重要提示 | 是 | 否，法律类不可覆盖 |
| 帮助中心文章 | 使用帮助和异常处理 | 是 | 后续按角色扩展 |

| 版本说明 | 新版本变化和兼容提示 | 是 | 否 |
| FAQ | 高频问题 | 是 | 后续按角色扩展 |
| 法律文本 | 用户协议、隐私政策 | 是 | 否 |

#### 6.4.2 内容状态机

```text
Draft -> PendingReview -> Approved -> Scheduled -> Published -> Offline -> Archived
                         |-> Rejected -> Draft
Published -> RolledBack -> Archived
```

规则：

- 已发布版本不可原地修改，修改必须产生新版本。
- 发布、停用、回滚均需权限、原因和审计。
- 计划发布时间到点后生效；发布失败保留草稿和失败原因。
- 线上内容必须支持一键回滚到上一有效版本。
- 跳转页、图片、法律文本版本和文案口径在发布前校验，校验失败禁止发布。

#### 6.4.4 受众规则

允许按以下维度组合：

- 角色：企业负责人、员工、业主、匿名访客；
- 身份覆盖面：仅微信、已绑手机号、已加入企业、已有项目；
- 企业生命周期：未注册、试用、付费、临期、过期、流失风险；
- 套餐/门店/席位状态；
- 小程序版本和平台；
- 渠道来源；
- 地区（仅在合法、必要且已授权时）。

禁止把成本、利润、员工手机号、客户正文、openId 等敏感字段用于受众筛选或文案变量。

### 6.5 触达中心

#### 6.5.1 触达分层

| 层级 | 示例 | 触发者 | 授权 | 是否可由运营编辑 |
| --- | --- | --- | --- | --- |
| 业务通知 | 验收待确认、任务逾期、材料到货 | 业务事件 | 现有业务规则 | 仅模板和文案规范 |

| 紧急通知 | 安全、重大故障、法律变化 | 平台负责人 | 合法必要范围 | 走紧急流程和审计 |

#### 6.5.2 消息任务

支持：

- 站内消息或小程序消息中心；
- 微信一次性订阅消息；
- 短信暂不纳入本期，除非另有供应商、预算和合规裁决；
- 预览、测试发送、定时发送、取消、暂停、分批和失败重试。

任务状态：

```text

                         |-> Rejected -> Draft
Scheduled/Sending -> Paused -> Cancelled

```

#### 6.5.3 发送规则

- 用户未授权或一次性额度耗尽时，标记 `Unsubscribed` 或 `NoQuota`，不标记系统失败。
- 同一运营场景有频控、静默时段和退出机制；具体阈值待业务裁决。
- 业务通知和运营触达分开发送记录，不能把同一次业务通知重复算作运营活动成果。
- 发送信息不得包含客户隐私、成本、合同内部金额、密钥或未授权业务数据。
- 支持按企业或用户停用运营触达，并保留审计。

| `mp.first_order.alignment.rate` | 首单对齐率 | 满足首单完成谓词企业数 / 有效注册企业数 | `GAP-019` 阻塞 | 入驻效果 |
| `mp.owner.participation.rate` | 业主参与率 | 有查看/确认/反馈动作的业主数 / 已授权业主数 | `GAP-014` 阻塞效果解释 | 同频观察 |
| `mp.trial.paid.rate` | 试用转付费率 | 观察窗内转为付费的企业数 / 到期或观察窗企业数 | 需业务确认 | 商业转化 |

| `mp.release.error.rate` | 版本错误率 | 版本错误事件数 / 版本有效启动数 | 候选 | 发布健康 |

### 7.7 缺失值和异常规则

1. 分母为 0 时返回 `null`，显示“暂不可确认”，不返回 `0%`。
2. 事件采集失败时，显示数据截至时间和“不完整”标记。
3. 微信接口不可用时，业务判定不受影响，仅触达指标进入未知。
4. 租户数据权限不可读时，不计算该企业指标，不把漏数当成零。
5. 同一用户跨企业存在时，企业指标按企业快照分别统计，平台级去重使用伪匿名主体。
6. 客户端和服务端来源同名指标必须注明来源，不能混用。

## 8. 页面级交互要求

### 8.1 小程序运营总览

- 顶部显示数据截至时间和线上版本。
- 六个指标卡：活跃、身份绑定、注册、激活、付费、反馈。
- 一个生命周期漏斗，支持按时间、渠道、版本、企业规模筛选。
- 一个服务队列，按 P0/P1/P2 排序。
- 一个版本健康区，展示版本占比、错误、反馈和回滚入口。
- 一个运营动态区，展示最近发布、发送、活动和审批。
- 没有数据的指标仍保留卡片骨架，显示缺失原因和恢复链接。

### 8.2 用户与渠道

- 主列表使用筛选器和分页，默认不显示明文身份。
- 用户详情是侧滑抽屉，先显示脱敏身份和旅程，再显示授权后企业摘要。
- 渠道表按渠道、访问、注册、激活、付费分层展示。
- 渠道详情可查看链接、二维码、场景、负责人和有效期。
- 导出仅支持聚合；敏感导出需二次确认和审计。

### 8.3 旅程与激活

- 顶部提供生命周期分段和搜索。
- 主视图是“企业队列 + 推荐动作”，不是图表墙。
- 企业详情显示 7/14/30 天里程碑、角色激活、风险原因和最近业务事实摘要。
- 支持指派、备注、设置跟进时间和关闭服务任务。
- 所有“完成”均引用已有业务事实；不得点击按钮直接变成完成。

### 8.4 内容与公告

- 左侧内容列表，右侧编辑器或版本详情。
- 编辑器必须有预览、版本、受众、时间、目标页和回滚点。
- 发布前展示校验清单：文案、法律、跳转、图片、敏感字段和回滚。
- 发布后显示生效范围、曝光、点击、错误和停用按钮。
- 已发布内容只读；修改必须复制新版本。

### 8.5 反馈与服务

- 默认按 P0/P1、SLA、状态、来源和版本排序。
- 详情展示反馈摘要、脱敏上下文、技术诊断、处理记录和相关发布。
- 支持分派、状态变化、回复、重复合并、升级和重新打开。
- 平台产品反馈与租户项目反馈视觉上有明显边界。
- 关闭前必须填写结论；涉及租户处理的不能由平台代为关闭。

### 8.6 发布与合规

- 版本列表展示版本号、审核、发布、采用率、错误率和状态。
- 详情展示检查清单、证据、后端版本、迁移和回滚方案。
- 发布前检查未通过时不能标记为可发布。
- 发布后进入观察期，观察失败生成事件并引导降级。
- 不放密钥；证据只是文件或路径引用。

### 8.7 触达中心

- 任务编辑分为受众、模板、内容、时间、频控、预览和提交审核。
- 预览必须显示最终小程序文案和数据字段。
- 测试发送需要单独权限，测试记录与正式发送分开。
- 任务列表显示审批、发送、送达、未授权、失败和取消。
- 不支持无条件群发，不允许绕过用户授权。

### 8.8 活动中心

- 活动以目标和受众开头，不以优惠配置开头。
- 权益、时间、限制和终止条件为必填。
- 活动运行后展示入口、参与、完成和守护指标。
- 活动停止后不可继续发放权益。
- 活动详情标注“运营观察，不代表经营改善”。

### 8.9 实验与开关

- 开关和实验分开管理；开关是运行配置，实验是验证假设。
- 实验页面先显示假设、指标和守护条件。
- 发布前显示影响范围、默认值和回滚路径。
- 结束后必须形成“采纳/不采纳/无结论”，不能永久挂着。

### 9.2 客户端采集入口

匿名访问和小程序事件不能复用平台用户权限，应提供独立入口，例如：

```text
mini/telemetry/save
mini/telemetry/batch
mini/telemetry/config
```

要求：

- 允许匿名，但必须限流、校验字段白名单、限制单批大小。
- 禁止上传客户正文、图片、成本、合同金额和完整 openId。
- 事件失败不得影响登录、业务提交和页面展示。
- 采集配置必须有版本、开关和采样规则。
- 服务端关键事实优先于客户端事件，不能只依赖埋点。

### 9.3 租户数据适配

平台只读企业激活、角色、订阅和小程序身份状态时：

- 扩展 `TenantDataAdapter` 或新增明确的只读适配器；
- 返回值使用标量快照模型，不引用 `Company`、`Employee`、`Credentials` 等租户实体；
- 平台表只保存 `companyIdSnapshot`、企业名称快照等标量字段；
- 聚合在 `@Transactional(readOnly = true)` 或独立报表读取中完成；
- 禁止在 RequestFilter、无事务组件或前端拼接权限。

### 9.5 服务端实现约束

若进入开发，必须遵守 `AGENTS.md` 和 `rules.md`：

- 服务是 Provider，入参是领域模型，不定义 DTO/VO；
- 登录平台接口继承 `Security`，当前平台用户通过 `@User` 注入；
- 平台权限集中校验，不在 Controller/前端散落角色判断；
- 返回具体实体或 `Page<实体>`，使用 `@Properties` 按能力裁剪；
- 平台表无租户外键，不存租户实体关联；
- 关联对象使用显式快照或最小字段投影，不使用 `@JsonIgnore`；
- 懒加载在事务外禁止访问；必要关联预取或显式物化；
- 所有写 Provider 具备幂等、审计和异常恢复路径。

## 11. 验收标准

### 11.1 业务正确性

1. 平台总览的企业、激活、角色和订阅数据与企业侧使用进度同源同口径。
2. 企业生命周期只读投影不新增、不覆盖企业业务状态。
3. 一单对齐指标在 `GAP-019` 冻结前不显示确定完成率。
4. 同频效果在 `GAP-014` 冻结前只显示候选观察项，不形成统一效果分。
5. 订阅、权益、点数动作调用正式服务，不伪造订单、回款或发票。
6. 内容、消息、活动、发布和开关均有状态、审批、审计和回滚路径。
7. 反馈状态不等于租户业务状态，平台不代企业关闭投诉或整改。

### 11.2 数据与指标

1. 每个指标可追溯到事件定义、分子、分母、时间窗、来源和刷新时间。
2. 分母为零返回未知，前端显示“暂不可确认”。
3. 客户端重复事件按 `eventId` 幂等。
4. 服务端关键事实不依赖客户端埋点。
5. 数据延迟和采集缺失有明确标识。
6. 聚合导出不含明文手机号、openId 和客户正文。
7. 同用户跨企业统计按企业快照拆分，平台聚合按伪匿名主体去重。

### 11.3 权限与安全

1. 租户员工或企业账号访问 `platform/mini/**` 被拒绝。
2. 无对应权限的平台用户无法查看、写入、导出或发送。
3. 平台跨企业访问使用独立平台令牌和权限，不复用租户数据范围。
4. 平台表没有租户外键或租户实体关联。
5. 日志、审计、页面和导出不出现完整 openId、AppSecret、密钥或私钥。
6. 敏感查看、导出和身份合并有不可删除审计。
7. 高风险动作发起人与审批人不能相同。
8. 修改订阅、权益和消息授权不能绕过正式服务与审批。

### 11.4 运营交互

1. 运营总览在 30 秒内可识别本期最重要队列。
2. 激活队列能按 7/14/30 天、风险和角色筛选。
3. 内容编辑可预览、版本化、审核、发布和回滚。
4. 消息任务可预览、测试、限频、分批、暂停和取消。
5. 反馈工单可分派、回复、升级、合并和重新打开。
6. 发布检查未通过时不能标记为已发布。
7. 系统异常时显示原因、影响和恢复路径，不用空白页或 0 掩盖。

### 11.5 反向与边界用例

1. 未授权订阅消息：不发送、不记系统故障、不阻断业务事务。
2. 模板字段超长：发送前校验失败并阻止任务。
3. 内容目标页不存在：不能发布，保留失败原因。
4. 功能开关读取失败：使用安全默认值。
5. 微信服务异常：业务事实不回滚，触达进入失败或待重试。
6. 同一反馈重复提交：聚类合并但保留来源次数。
7. 同一手机号冲突：进入待人工确认，不自动合并企业。
8. 企业数据权限不可读：显示暂不可确认，不将企业算成零活跃。
9. 已发布内容被非法修改：拒绝原地修改并要求新版本。
10. 审计目标企业被删除：平台审计仍能显示标量快照。

## 12. 实施路线

### 12.1 P0：可观察、可服务、可审计

目标：先形成安全运营底座，不追求全自动。

交付：

- 平台小程序域和数据边界；
- 用户、渠道、企业旅程和事件聚合；
- 小程序运营总览；
- 激活队列和运营任务；
- 产品反馈工单；
- 发布与合规台账；
- 指标字典、权限、审计和基础导出；
- 与现有企业、订阅、使用进度和系统状态联动。

退出条件：

- 可以回答“用户从哪里来、停在哪一步、哪些企业需要服务、最近版本是否健康”；
- 没有跨企业越权、敏感字段泄露和伪完成；
- 关键指标可以追溯且不显示虚假确定值。

### 12.2 P1：可配置、可触达、可实验

目标：让运营动作可控地影响小程序内容和用户旅程。

交付：

- 内容中心与公告；
- 站内消息、微信一次性订阅消息任务；
- 活动中心与非现金权益联动；
- 功能开关和实验；
- 自动化服务队列；
- 预览、审批、频控、停止和回滚；
- 内容和触达效果分析。

退出条件：

- 内容、消息、活动和开关全流程有审批和回滚；
- 未授权用户不被错误触达；
- 高风险权益动作全部走正式服务与审计；
- 实验不外溢到金额、权限和状态机。

### 12.3 P2：可预测、可规模化

候选：

- 用户分群与生命周期自动化；
- 渠道质量和内容策略优化；
- AI 辅助运营摘要和异常聚类；
- 客服知识库联动；
- 企业健康预测；
- 小程序 + 官网 + Web + Admin 全产品漏斗；
- 运营动作与业务结果的受控归因。

P2 不改变 P0/P1 的权限、隐私和业务真源边界。任何效果预测必须标注为建议，不替代经营事实。

## 14. 最终建议

建议按以下顺序推进：

```text
业务裁决
-> P0 只读运营底座
-> 独立验收
-> P1 内容/触达/活动/实验
-> 真实样本复盘
-> P2 自动化与规模化
```

P0 的第一价值不是“运营人员看到更多图表”，而是：

1. 知道用户和企业卡在哪里；
2. 知道哪个企业下一刻需要谁做服务；
3. 知道当前版本、内容和反馈是否健康；
4. 任何动作都能追溯、暂停和回滚；
5. 不越权、不伪造、不把活跃当成经营结果。

在业务咨询单完成回答前，允许开展产品原型、字段清单、事件字典和权限设计，不允许对外发送运营消息、发布法律内容、发放权益或把待冻结指标写进正式运营报表。

## 15. GAP-013 / GAP-014 / GAP-019 专项处置建议

> 本节是产品规划建议，不是业务智能体正式裁决。只有业务智能体回写 `DEC-*` 或用户明确确认后，才能把“建议口径”升级为正式规则。

### 15.1 GAP-013：官网线索承接与客户经营主链联动

#### 15.1.1 问题本质

当前 `SiteLead` 是“装得清 SaaS 潜在装企预约”，字段包括称呼、联系方式、关心问题、补充说明、来源页面、来源渠道和同意沟通；现有租户 `Customer / Property` 是“装企自己的装修客户与房屋”。

因此不能默认：

```text
官网 SaaS 装企线索 -> 某个装企下的 Customer -> Property
```

这会把平台招商线索错误放进租户业务主链，也无法回答“谁跟进、何时转企业、由谁承接”。

#### 15.1.2 建议的正式对象拆分

| 线索类型 | 示例 | 目标主链 | 是否进入租户 Customer/Property |
| --- | --- | --- | --- |
| 企业潜客 | 装企老板预约演示、咨询报价和经营问题 | SiteLead -> PlatformProspect -> Company 注册/试用/付费 | 否 |
| 业主/消费者线索 | 业主咨询装修、上传户型、申请 AI 方案 | 只在明确产品入口且授权后进入某装企的 Customer/Property | 是，但必须有明确承接企业和授权 |
| 合作方线索 | 渠道商、服务商、供应商合作 | PlatformProspect/PartnerPipeline | 否 |
| 普通咨询 | 非装企、非业主、无效或骚扰 | SiteLead，标记无效或关闭 | 否 |

本文建议本期只定义“企业潜客”链路，业主/消费者入口另立咨询，不与官网装企预约混用。

#### 15.1.3 建议归属与状态

**归属模式**：平台公共线索池，由平台市场增长或客户成功人员领取，不在第一阶段直接转给某家租户。

建议状态：

```text
New
-> Contacted
-> Qualified
-> InvitedToMiniProgram
-> TrialOrDemo
-> ConvertedToCompany
-> Invalid
-> Closed
```

保留现有 `New / Contacted / Closed` 兼容，新增状态必须由业务确认。

#### 15.1.4 建议去重键

优先级：

```text
标准化手机号
+ 企业名称（有则参与）
+ 官网来源和最近提交时间
```

处理规则：

- 相同手机号重复提交不新增独立潜客，追加提交事件并保留原线索；
- 同一手机号不同企业名称时进入“待确认”，不自动合并；
- 线索被删除或撤回授权时，保留最小审计事实，不继续触达；
- 任何情况下不把多个手机号自动合并成一个自然人。

#### 15.1.5 建议转化方式

```text
SiteLead
-> 人工确认有效
-> 绑定小程序企业注册/体验账号
-> 小程序完成身份或企业注册
-> 回写 companyId 标量快照
-> 进入试用/付费/客户成功队列
```

明确不做：

- 不自动创建租户 `Customer`；
- 不自动创建 `Property`；
- 不自动指定企业、门店、团队或员工；
- 不把表单提交等同于有效线索或付费客户。

#### 15.1.6 建议 SLA

以下阈值是建议默认值，需用户或业务智能体确认：

| 动作 | 建议 SLA | 超时处理 |
| --- | --- | --- |
| 首次响应 | 4 个工作小时内 | 升级市场负责人 |
| 首次有效沟通 | 1 个工作日内 | 进入待回访 |
| 无活动回收 | 7 个自然日 | 回到公共池或关闭 |
| 小程序邀请未完成 | 3 个自然日 | 二次提醒或人工跟进 |
| 试用到期前提醒 | 7 个自然日 | 进入续费/转化队列 |

#### 15.1.7 建议指标

| 指标 | 公式 | 边界 |
| --- | --- | --- |
| 表单提交量 | 提交事件数 | 不代表有效线索 |
| 有效线索数 | `Qualified` 去重潜客数 | 由人工确认标准定义 |
| 首次响应率 | SLA 内首次响应数 / 有效线索数 | 不能替代成交率 |
| 小程序邀请率 | 进入小程序的企业潜客数 / 有效线索数 | 需同一 `siteLeadId` 关联 |
| 企业注册率 | 完成企业注册数 / 有效线索数 | 企业注册是事实，不自动等于试用 |
| 试用转化率 | 完成试用企业数 / 有效线索数 | 分母和时间窗待确认 |
| 付费转化率 | 付费企业数 / 有效线索数 | 沿用订阅和订单口径 |

#### 15.1.8 临时处理

在 `GAP-013` 正式冻结前：

- 官网线索只做平台可见的原始预约和人工跟进；
- 小程序运营总览只显示“官网来源进入小程序”的候选关联；
- 不自动写入租户客户与房屋；
- 不外宣称“官网线索已自动进入客户主链”。

### 15.2 GAP-014：同频效果指标与验收标准

#### 15.2.1 问题本质

同频不是一个可直接用“次数、点击、消息减少”衡量的单一功能，而是：

```text
同一业务事实
+ 正确角色
+ 可见范围
+ 下一步
+ 确认留痕
```

如果把“查看次数、消息数量、页面停留、业主活跃”合成一个分数，会制造无法解释的效果结论。

#### 15.2.2 建议采用三层指标

**第一层：机制合格门槛（验收必须通过）**

| 检查项 | 建议完成谓词 | 不通过处理 |
| --- | --- | --- |
| 事实同源 | 关键业务事件有唯一对象、来源和最新状态 | 验收不通过 |
| 下一步明确 | 相关责任角色看到下一步或明确无待办 | 验收不通过 |
| 确认责任 | 由正确角色完成关键确认并留痕 | 验收不通过 |
| 数据边界 | 角色只看职责范围，越权访问被拒绝 | 验收不通过 |
| 变更覆盖 | 业务变化影响对象已明确列出或标记未完成 | 不显示“已覆盖” |

这些是“是否可用”的机制检查，不是经营效果指标。

**第二层：可观察过程指标（只说明流程表现）**

| 候选指标 | 候选公式 | 解释边界 |
| --- | --- | --- |
| 交接可见率 | 下游角色看到事件数 / 应有下游角色可见事件数 | 不代表沟通效率提升 |
| 确认留痕率 | 有角色、时间、对象和结果的确认数 / 关键确认数 | 是合规和可追溯指标 |
| 重复确认率 | 同一事实重复确认次数 / 关键确认数 | 不代表用户满意度 |
| 变更影响覆盖观察值 | 已明确受影响对象数 / 应影响对象数 | 不应对外称经营改善 |
| 业主自助完成率 | 独立完成查看/确认/驳回的数 / 已授权任务数 | 不代表投诉下降 |
| 复验可见率 | 能看到整改复验结论的业主任务数 / 应复验任务数 | 仅说明交付透明度 |
| 越权拒绝数 | 被拒绝的越权访问次数 | 用于安全观察，不等于用户体验好 |

**第三层：业务结果指标（必须另有业务证据）**

- 项目按期率；
- 返工率；
- 客户投诉率；
- 验收一次通过率；
- 回款及时率；
- 经营改善或利润变化。

第三层不得从同频系统操作数据直接推导，必须回到项目、验收、质量、财务和真实样本证据。

#### 15.2.3 试点设计建议

在用户未确认前，只作为产品实验方案：

| 维度 | 建议 |
| --- | --- |
| 样本 | 3–5 家成长型装企，至少 10 个在跑项目 |
| 周期 | 启用前 2 周基线，启用后连续观察 4 周 |
| 对象 | 岗位同频和业主同频分开，不合成总分 |
| 对照 | 同企业历史流程或未启用链路的项目，不宣称因果 |
| 结论 | 机制是否可用、用户是否能独立完成、异常和阻塞在哪里 |
| 不可得出 | 投诉下降、利润提升、全员效率提升等未经对照的结果 |

#### 15.2.4 建议的可视化

不要显示一个“同频 82 分”：

```text
岗位同频：机制通过 / 待验证
业主同频：机制通过 / 待验证
数据边界：通过 / 失败
观察指标：分业务链展示
效果结论：待样本 / 不足以判断
```

#### 15.2.5 临时处理

- 对外只讲设计原则、可验证机制和权限边界；
- 不做减少比例、提升比例、满意度或利润提升承诺；
- 运营报表只展示“流程是否可用”和候选过程指标；
- 只有独立验收和足够样本后，才形成同频效果结论。

### 15.3 GAP-019：一单对齐最小成功标准与角色确认矩阵

#### 15.3.1 建议的首单对象优先顺序

一条新装企可能同时有客户、报价和在跑项目。建议系统按以下顺序选择：

```text
在跑项目
-> 已生效合同
-> 已产生客户决策的报价
-> 客户+房屋
```

选择原则：

1. 优先选择已经有真实业务事实、最容易看到下一步的对象；
2. 不为了完成引导伪造客户、报价、合同或项目；
3. 企业可以选择更低层级对象，但页面必须说明会少看到哪些链路；
4. 同一企业允许多次对单，但某次活动的完成只针对本次选中对象。

#### 15.3.2 建议最低字段

| 路径 | 最低事实 | 可缺省但必须显示 |
| --- | --- | --- |
| 在跑项目 | 项目、客户、房屋、当前阶段、项目经理 | 合同金额、未结应收应付、成本完整性 |
| 合同/报价 | 客户、房屋、报价或合同、当前状态、责任角色 | 具体成本、材料、收付款明细 |
| 客户+房屋 | 客户、房屋、负责人、来源或诉求 | 设计、报价、合同、项目 |
| 业主同频 | 业主、项目、授权范围 | 企业内部成本和供应商信息 |

缺字段一律进入“待确认/缺失”，不得以空值或猜测值推进。

#### 15.3.3 建议角色确认矩阵

| 路径 | 必要角色 | 可选角色 | BOSS 代确认 |
| --- | --- | --- | --- |
| 在跑项目 | BOSS、项目经理 | 设计师、财务、材料/履约 | 负责人缺失且未建立可代确认，必须留痕 |
| 合同/报价 | BOSS、设计师 | 店长、团队负责人、财务 | 设计师未建立或离职时可代确认业务摘要 |
| 客户+房屋 | BOSS、客户负责人 | 设计师、店长 | 客户负责人未建立可代确认归属 |
| 业主同频 | 业主本人 | 项目经理、BOSS | 不允许代业主确认验收、驳回或整改结论 |

BOSS 代确认的边界：

- 只适用于企业内部事实初始归属和缺口确认；
- 不替代业主验收、客户确认、金额真实性、成本完整性和付款事实；
- 必须记录 `confirmedBy=Boss`、`actualOwner=missing`、原因和时间；
- 原责任人建立后，历史代确认仍保留，不自动改写。

#### 15.3.4 建议完成谓词

“已完成教程”不等于“一单对齐完成”。建议完成谓词为：

```text
ObjectSelected
AND MinimumFactsEvaluated
AND RequiredRolesResolved
AND NextActionAssigned
AND AtLeastOneFormalBusinessActionCompleted
```

其中最后一项按路径解释：

| 路径 | 可计为正式业务动作 |
| --- | --- |
| 在跑项目 | 确认接管基线、明确当前阶段/剩余工作、确认责任角色或形成首任务 |
| 合同/报价 | 提交正式报价、形成客户决策、合同生效或生成新的正式版本 |
| 客户+房屋 | 建立客户和房屋、完成首次跟进或预约量房 |
| 业主同频 | 业主在本人项目查看、确认或驳回，且服务端留痕 |

打开页面、观看教程、填写演示数据、点击“我已了解”均不计为完成。

#### 15.3.5 建议激活率分母

同时区分两个分母，避免通过删掉无效企业抬高激活率：

```text
运营激活率 =
满足完成谓词的合格新企业数
÷ 观察周期内注册且去重的合格企业数

服务有效率 =
满足完成谓词或已形成明确无继续意愿结论的企业数
÷ 分配客户成功跟进的企业数
```

默认排除：

- 平台内部测试企业；
- 明确标记为垃圾、重复、误注册且经审批的企业；
- 未完成企业注册的未归属微信/手机号用户。

不得仅因“没有使用意愿”就从运营激活率分母中删除；应在服务有效率或流失结论中单独表达。

#### 15.3.6 幂等、退重进与并发

- 每家企业每轮对齐生成独立 `OnboardingRun`，业务状态只做只读投影；
- 重复进入恢复本轮进度，不重复创建客户、报价、项目或任务；
- 退出不删除事实，重新进入从当前正式业务事实重新计算；
- BOSS 与角色并发确认同一事实时使用乐观锁或幂等键；
- 对齐完成由业务事实谓词推导，不允许前端直接写 `done=true`；
- 完成后业务事实被修改，后续展示“需要复核”，不自动回退已完成历史。

#### 15.3.7 责任边界

| 现有对象 | 保留职责 | 一单对齐不做什么 |
| --- | --- | --- |
| `OnboardingChecklist` | 首次入驻任务投影 | 不新增第二套状态机 |
| `Carryover` | 在跑项目承接业务 | 不替代承接基线和财务确认 |
| 需要我处理 | 角色待办投影 | 不复制第二套待办 |
| 报价/合同/项目 | 正式业务事实 | 不写演示值、不伪造完成 |
| 客户成功任务 | 平台运营服务 | 不向租户伪装成业务状态 |

#### 15.3.8 临时处理

在 `GAP-019` 正式冻结前：

- 平台只显示现有 7/14/30 天里程碑和角色激活事实；
- 一单对齐页面只能做候选原型或专用测试企业；
- 不显示统一首单对齐率、首次价值时间或效率承诺；
- 不将对齐结果写入报价、合同、项目、验收和财务状态。

### 15.4 三项 GAP 的联动关系

```text
GAP-013
官网 SaaS 潜客
-> 企业注册、试用和客户成功
-> 进入 GAP-019 的一单对齐

GAP-019
确定首单对象、最低事实、角色确认和完成谓词
-> 产生客户/房屋/报价/合同/项目事实
-> 可在 GAP-014 中观察岗位同频和业主同频

GAP-014
只验证同频机制是否可用和过程是否可见
-> 不以操作数据直接推出经营改善
```

建议决策顺序：

1. 先冻结 `GAP-013` 的线索归属、状态和转化边界；
2. 再冻结 `GAP-019` 的首单对象、最低字段、角色矩阵和完成谓词；

### 15.5 对当前产品方案的影响

- 在 `GAP-013` 未冻结前，官网渠道指标只显示“预约、联系、进入小程序”的候选链路；

### 16.8 手机号权限与隐私

用户明确要求前期运营人员查看负责人手机号，但必须采用最小权限和可审计设计：

| 角色 | 列表手机号 | 完整手机号 | 导出 | 说明 |
| --- | --- | --- | --- | --- |
| OperationsManager | 遮罩 | 按权限揭示 | 审批后 | 可处理服务 |
| CustomerSuccess | 遮罩 | 所属企业按权限揭示 | 默认禁止 | 主要服务角色 |
| GrowthOperator | 遮罩 | 默认禁止 | 仅聚合 | 不在未分配时看号码 |
| BillingOperator | 遮罩 | 仅订阅相关 | 默认禁止 | 不用于营销 |
| SreOperator | 不显示 | 禁止 | 禁止 | 只看技术摘要 |
| Auditor | 脱敏 | 可看访问审计 | 只读审计 | 不用于业务联系 |
| SuperAdmin | 遮罩 | 按需揭示 | 高风险管理 | 仍需审计 |

建议规则：

1. 列表默认显示掩码 `138****1234`。
2. 有 `TenantOwnerPhoneReveal` 权限的人点击“查看完整手机号”，输入查看原因后方可显示。
3. 揭示行为记录企业快照、操作人、时间、字段、原因和来源页面。
4. 完整手机号不进入日志、埋点、URL、导出默认值或消息内容。
5. 复制完整手机号与揭示使用同一审计动作。
6. 如果支持导出，只允许经审批的脱敏导出；全量联系电话导出需要更高权限和审批。
7. 负责人离职或停用后，历史手机号仍可能存在，但默认不计入有效联系池；需按隐私保留规则处理。
8. 联系记录必须显示“谁、何时、何种方式、结果、下一步”，不能只改一个状态。

### 16.9 多负责人处理

当前数据允许多个 `Boss`。页面处理规则：

- 所有 `Active Boss` 都列为当前负责人；
- 按最近登录时间、加入时间和姓名稳定排序；
- 不自动删减或覆盖原负责人；
- 只有一个有效负责人时显示“当前负责人”；
- 多个时显示“负责人 (N)”，详情全部展开；
- 联系人手机号按每个负责人独立展示和审计；
- 管理员转任负责人后，保留原负责人历史，最新有效负责人按员工状态和角色实时读取。

### 16.10 数据刷新与时间口径

- 企业注册时间：`Company.createTime`，使用 `Asia/Shanghai` 展示。
- 负责人加入时间：`Employee.joinedAt`，为空时显示 `Employee.createTime`。
- 最近登录时间：该负责人所有有效 `Credentials.lastTime` 的最大值。
- 从未登录：所有关联凭证 `lastTime` 均为空，显示“从未登录”。
- 登录时间与活跃时间分开：`lastTime` 是登录，`mp_app_launch` 是活跃；不得把登录时间写成活跃时间。
- 页面数据允许有缓存，但必须显示“数据截至时间”和刷新按钮。
- 企业转让、负责人变更、员工离职后，按最新有效归属重新读取，不缓存旧负责人覆盖新负责人。

### 16.13 验收用例

1. 企业通过小程序注册成功后，入驻台账能查到企业名称、注册时间和当前负责人。
2. 负责人手机号与企业注册时使用的手机号一致。
3. 三个负责人时全部列出，不覆盖原负责人。
4. 微信登录或密码登录成功后，最近登录时间更新为最新时间。
5. 从未登录的负责人显示“从未登录”，不显示 `null` 或 1970 年。
6. 7 日未登录筛选能覆盖过去 7 天边界，不包含未来或错误时区数据。
7. 无 `TenantOwnerPhoneReveal` 权限时只得到遮罩号码。
8. 揭示完整手机号后产生一条不可删除审计记录，包含原因、操作人和企业快照。
9. 复制完整手机号和导出行为同样记录审计。
10. 租户员工 token 访问入驻台账接口被拒绝。
11. CustomerSuccess 未分配的企业不可通过修改 `companyId` 越权读取。
12. 企业名称、负责人、手机号、注册时间和登录时间都能从真实服务端事实刷新，不依赖前端本地缓存。
13. 手机号在日志、URL、埋点和默认导出中不出现完整值。
14. 负责人离职后不再作为有效联系对象，但历史服务记录仍可追溯。

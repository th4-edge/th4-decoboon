> 文档编号：PRODUCT-MEASURE-20261001-01  
> 版本：v1.0  
> 状态：`frozen_for_development`（用户 2026-10-01 明确要求冻结）  
> 日期：2026-10-01  
> 范围：Web 设计师量房工作台、待办中心量房任务、客户详情量房入口、量房录入与调整预约  
> 上位事实：`OBJ-001`、`SCN-001`、`BR-001`、`CAP-002`、`SOL-004`  
> 用户裁决：2026-10-01 会话中明确设计师录入客户、直接录入量房、工作台信息架构及“关注点”边界

## 0. 结论先行

量房工作台不是一个“量房管理页面”，而是围绕具体房屋执行量房任务的角色工作台。

必须冻结以下原则：

1. **Customer、Property、Measure、Requirement 是四个不同事实来源。**
2. **量房责任与设计责任不是同一个责任字段。**
3. 设计师录入客户时，客户负责人、业务员和设计负责人默认都是本人。
4. 已预约量房必须进入设计师待办，并允许调整时间和录入量房结果。
5. 工作台左栏选客户，中栏看客户与房屋事实，操作通过右侧动作或动作抽屉执行。
6. 中栏不得再嵌套另一个完整业务页面。
7. 不允许新增“量房关注点”作为独立领域对象。
8. 房屋现场事实写入 `Measure`，客户诉求写入 `Requirement`，设计师判断写入对应结论字段。
9. 列表、待办、工作台、详情必须使用同一套量房责任口径。
10. 页面不得用空数组掩盖接口失败或权限不完整；必须显示“暂不可确认”。

## 1. 业务问题

### 1.1 当前问题

- 设计师作为业务员录入客户后，客户和房屋已经存在，但量房工作台可能看不到。
- 客户已经预约量房，待办中心却可能没有量房任务。
- 已预约客户仍被推荐“预约当前房屋量房”。
- 点击“录入量房”后先进入归档页或列表页，再二次点击，违反工作台理念。
- 量房录入报“未指定设计师”，但客户本来就是设计师本人录入。
- “量房关注点”同时混入房屋事实、客户诉求和设计师判断，事实边界不清。
- 中栏嵌入完整量房管理页，导致左、中、右区域职责重复。

### 1.2 目标结果

- 设计师打开量房工作台即可看到本人负责或参与的量房任务。
- 已预约量房在待办中心和工作台中同时可见。
- 量房动作从待办或详情直接打开，不需要先去归档页。
- 量房事实、客户诉求和设计师判断有唯一来源。
- 客户、房屋、量房记录的责任归属可以解释和追溯。
- 验收可以通过角色、状态、房屋边界和多租户负向用例复现。

## 2. 术语与对象边界

### 2.1 Customer 客户

用途：

- 承载经营关系、联系方式、来源、负责人、阶段和客户画像。
- 是客户诉求和经营跟进的上游对象。

必须包含：

- `company`：所属企业。
- `owner`：客户经营负责人。
- `designer`：客户级设计负责人事实；设计师本人录入客户时默认本人。
- `store/team`：归属快照。

### 2.2 Property 房屋

用途：

- 量房、设计、报价、合同和项目的共同执行载体。
- 客户可以有多套房屋，所有量房动作必须绑定具体房屋。

必须包含：

- `customer`：所属客户。
- `owner`：房屋数据负责人。
- `salesman`：营销/业务负责人。
- `designer`：设计负责人；由客户设计负责人继承，或后续正式指派。
- `latestMeasureAt`：最近一次完成量房时间。
- `status`：待量房、量房中、已量房及后续设计/项目状态。

### 2.3 Measure 量房记录

用途：

- 记录某套房屋的一次预约或完成事实。
- 记录房屋现场事实和量房执行结果。

字段边界：

| 字段 | 含义 |
| --- | --- |
| `scheduledAt` | 计划上门时间 |
| `completedAt` | 实际完成时间 |
| `measureTime` | 兼容投影：预约时为预约时间，完成时为完成时间 |
| `status` | `Scheduled / Completed / Cancelled` |
| `owner` | 数据负责人 |
| `designer` | 量房对应的设计责任事实 |
| `executor` | 实际执行人 |
| `originalStructure` | 原始结构 |
| `dimensions` | 量房尺寸 |
| `sitePhotos` | 现场照片 |
| `structureImages` | 结构图 |
| `customerRequirements` | 本次量房记录中的客户诉求摘要 |
| `designerConclusion` | 本次量房的整体设计师结论 |

### 2.4 Requirement 客户诉求

用途：

- 记录客户明确要什么、不要什么，以及设计回应。
- 不与 Measure 合并，不替代房屋现场事实。

字段边界：

- `kind`：诉求 / 排斥点。
- `category`：功能、风格、材料、预算、工期、质量、其他。
- `priority`：优先级。
- `status`：落地状态。
- `detail`：客户原始描述或已确认表达。
- `response`：设计师回应。
- `confirmedAt`：确认时间。

### 2.5 不允许的概念

不得新增以下独立对象：

- 量房关注点。
- 量房事项。
- 设计关注点。

“量房关注点”只能作为页面分组或过渡文案，不能建实体、表、状态机或独立 Provider。

## 3. 角色与责任

### 3.1 角色矩阵

| 角色 | 登记客户 | 约定/调整量房 | 录入量房 | 设计默认归属 | 可见范围 |
| --- | --- | --- | --- | --- | --- |
| Boss | 是 | 是 | 是，但不得代录已指定设计师的量房 | 可由负责人明确指派 | 全企业 |
| StoreManager | 是 | 是 | 是，但不得代录已指定设计师的量房 | 可指派本门店设计师 | 本门店 |
| TeamLeader | 是 | 是 | 受指定设计师规则约束 | 可指派本团队设计师 | 本团队 |
| Marketer | 是 | 是 | 是，但不得代录已指定设计师的量房 | 不默认 | 本人客户 |
| Designer | 是 | 是 | 是 | 本人 | 本人负责、本人营销、本人设计的客户和房屋 |
| PM | 否 | 否 | 否 | 不适用 | 可只读项目参与范围内的量房事实 |
| Finance | 否 | 否 | 否 | 不适用 | 按财务和项目范围只读 |

### 3.2 量房责任

量房责任与设计责任分离。

量房池可见对象包括：

- 当前员工是 `Property.designer`。
- 当前员工是 `Property.owner`。
- 当前员工是 `Property.salesman`。
- 当前员工是 `Customer.owner`。
- 当前员工是 `Customer.designer`。
- 当前员工是项目设计师且项目已立项。

同一房屋必须去重。

### 3.3 设计责任

设计池只包含正式设计责任对象：

- `Property.designer` 为当前员工；或
- `Customer.designer` 为当前员工；或
- `Project.designer` 为当前员工。

不得因为设计师兼业务负责人，就自动让房屋进入正式设计工作台。

### 3.4 设计师录入客户默认归属

当 `current.role == Designer` 且本人成为客户负责人时：

```text
Customer.owner = 设计师本人
Customer.designer = 设计师本人
Property.owner = 客户 owner
Property.salesman = 客户 owner
Property.designer = 客户 designer
```

设计负责人无需人工再次指定。

管理者明确把客户负责人转交给设计师时，是否同时转交设计责任必须走正式指派动作，不作为本规格的默认行为。

## 4. 状态机

### 4.1 客户状态

```text
New / Following
  -> PendingMeasure
  -> Quoted
  -> Signed
  -> Serving
  -> Finished
  -> Lost
```

量房工作台不得直接修改客户状态；状态由量房、设计、报价和归属动作驱动。

### 4.2 房屋状态

```text
PendingMeasure
  -> Measuring
  -> Measured
  -> Designing
  -> Quoted
  -> Contracted
  -> Serving
  -> Completed
```

### 4.3 量房状态

| 状态 | 判定 | 业务含义 | 页面下一步 |
| --- | --- | --- | --- |
| 未预约 | 无 `Scheduled` 且无 `Completed` | 尚未形成上门计划 | 预约量房 |
| 已预约 | 存在 `Scheduled` Measure，且无完成记录 | 已确认上门时间 | 调整时间 / 录入量房 |
| 已预约·逾期 | 存在 `Scheduled` Measure，预约时间超过 4 小时且仍未完成 | 风险提示：逾期（不改变动作可用性） | 录入量房（主）/ 调整时间（并列） |
| 量房进行中 | Property.status = `Measuring`，存在执行责任 | 设计师/执行人已经接手 | 录入量房 |
| 已量房 | 存在 `Completed` 或 `Property.latestMeasureAt` | 量房事实已形成 | 进入设计 |
| 已取消 | Measure.status = `Cancelled` | 原预约取消，不形成量房事实 | 重新预约 |

### 4.4 状态优先级

```text
Completed > Measuring > Scheduled > Pending
```

不得出现：

- 已预约后仍推荐“预约当前房屋量房”。
- 已完成量房后仍推荐“录入量房”。
- 已取消预约被当成已完成或从未预约。

## 5. 工作台信息架构

### 5.1 左栏：客户与量房任务选择

显示：

- 客户姓名。
- 房屋小区/地址/编号。
- 面积和户型。
- 预约时间或待约定。
- 量房状态。
- 按“正在进行 / 已逾期 / 今日 / 未来已预约 / 待预约”分组。

操作：

- 搜索客户、小区、电话。
- 切换当前量房对象。
- 切换逾期、今日、全部。

左栏不承载客户详情和录入操作。

### 5.1.1 左栏排序规则

列表必须先分组，再组内排序。分组优先级固定为：

```text
正在进行 > 已逾期 > 今日待上门 > 未来已预约 > 待预约
```

| 分组 | 判定 | 组内排序 |
| --- | --- | --- |
| 正在进行 | Property.status = Measuring 且未完成量房 | scheduledAt 升序；无预约时由业务兜底时间决定 |
| 已逾期 | Scheduled Measure 的时间早于当前时间，且未完成、未在执行 | scheduledAt 升序，逾期越久越靠前 |
| 今日待上门 | scheduledAt 属于今天且尚未到达或尚未完成 | scheduledAt 升序 |
| 未来已预约 | scheduledAt 晚于今天结束时间 | scheduledAt 升序 |
| 待预约 | 没有有效 Scheduled Measure | pendingMeasureAt / measureRequestedAt / customer.createdAt 升序，等待越久越靠前 |

同组同一时间时，统一使用：

```text
客户等级 A > B > C
-> 停留天数降序
-> 最近跟进时间升序
-> customerId / propertyId 升序
```

排序规则必须同时用于设计师量房工作台、待办中心量房任务和其他角色量房工作台，不得各页面自行使用创建顺序或接口返回顺序。

### 5.2 中栏：本次量房必须关注的客户与房屋事实

必须展示：

- 客户联系方式、来源、阶段、归属人。
- 房屋地址、小区、楼栋、房号、面积、户型。
- 预约时间和量房记录。
- 客户画像和关注重点。
- 客户诉求。
- 最近跟进记录。
- 已形成的量房结果。

不得：

- 嵌入完整量房管理页。
- 重复一个客户档案页。
- 在同一区域重复展示左栏列表和右栏动作。

### 5.3 右栏：当前量房动作

未完成量房：

- 调整预约时间。
- 录入量房信息。
- 补充量房信息。
- 刷新状态。

已完成量房：

- 进入设计方案。
- 查看量房记录。

右栏负责解释“当前为什么需要处理”和“下一步做什么”。

### 5.4 动作抽屉

调整预约时间和录入量房使用动作抽屉，不进入新的页面层级。

从以下入口点击“录入量房”：

- 待办中心。
- 客户详情下一步。
- 客户房屋卡片。
- 设计师量房工作台。

必须携带：

```text
customerId
propertyId
record=1
```

工作台加载后必须：

1. 选中对应客户和房屋。
2. 加载该房屋的预约记录。
3. 自动打开录入量房抽屉。

从 `measureAction=schedule` 进入时，必须自动打开调整预约抽屉。

### 5.5 设计师工作台菜单

设计师的跨阶段工作台不再使用顶部阶段切换条作为唯一入口，左侧菜单固定为：

```text
设计工作台
  ├── 量房工作台
  ├── 方案设计工作台
  ├── 报价工作台
  ├── 签约工作台
  ├── 施工协同工作台
  ├── 材料选材工作台
  └── 增减项工作台
```

要求：

- 每个工作台有独立路由，避免共用同一路径后依赖页面内部状态切换。
- 材料选材工作台默认打开材料选材面板。
- 增减项工作台默认打开设计变更/合同增减项面板。
- 顶部阶段切换条不再承担主要导航职责。
- 菜单选中态、面包屑和页面标题必须与当前工作台一致。

## 6. 动作规则

### A1 登记客户

- 客户姓名、手机号必填。
- 设计师本人录入时，负责人和设计负责人默认本人。
- 企业、门店、团队和负责人由系统按当前员工重新计算。

### A2 建立房屋

- 详细地址必填。
- 房屋必须属于当前客户。
- 房屋负责人、营销负责人和设计负责人从客户与当前员工继承。
- 多套房屋时，量房动作必须明确 `propertyId`。

### A3 预约/调整量房

- 必须关联客户和具体房屋。
- 预约时间必须晚于当前时间。
- 已预约且未完成时，再次保存必须更新原 `Scheduled` Measure，不得产生重复预约。
- 保存后待办中心和工作台必须刷新预约时间。

### A4 录入量房

- 必须关联当前房屋的 `Scheduled` 或当前待完成 Measure。
- 已完成量房不得重复形成新的完成记录。
- 已指定设计师时，只能由指定设计师完成。
- 未指定设计师但当前设计师是客户或房屋负责人时，默认补齐当前设计师后完成。
- 完成后：
  - Measure.status = `Completed`。
  - `completedAt` 和 `measureTime` 写入完成时间。
  - Property.status 进入 `Measured`。
  - Property.latestMeasureAt 更新。
  - 客户进入设计/报价后续路径。

### A5 补充量房信息

页面必须区分：

- 房屋现场信息：写入 Measure 或对应量房记录字段。
- 客户诉求/排斥点：写入 Requirement。
- 设计师判断：写入 `Measure.designerConclusion` 或 `Requirement.response`。

不得把三类内容写入一条名为“量房关注点”的客户诉求。

## 7. 待办中心生成规则

量房待办来源为明确的业务事实：

```text
exists Measure.status = Scheduled
AND 当前员工可负责该客户或房屋
AND 当前房屋尚未完成量房
```

显示内容：

- 标题：完成量房 · 房屋编号。
- 描述：客户、地址、面积、预约时间。
- 优先级：按预约日期计算逾期、今日、三日内、普通。
- 操作：录入量房。
- 跳转：直接到量房工作台并设置 `record=1`。

去重规则：

- 同一 `propertyId` 只生成一条当前待办。
- 同一房屋存在多条历史 Scheduled 时，取有效的最近一条。
- Completed 后移除量房待办。

失败规则：

- 房屋列表或量房记录加载失败时显示“量房状态暂不可确认”。
- 不得显示“没有量房任务”替代失败结果。

---

## 8. 权限与一致性

- 服务端为最终权限边界。
- 前端不得重新定义另一套量房可见性。
- 量房列表、详情、待办、工作台必须复用同一责任判断。
- 跨企业、跨门店、跨团队、非参与员工不得通过参数绕过。
- 设计师作为业务负责人时，可查看本人客户和房屋的量房记录；设计权限另行判断。
- 接口失败和权限不足必须区分展示：
  - 权限不足：无权限及恢复路径。
  - 加载失败：暂不可确认和重试入口。
  - 真实为空：显示空状态并说明下一步。

## 9. 异常与恢复

| 场景 | 系统行为 |
| --- | --- |
| 房屋没有预约 | 推荐预约量房 |
| 已预约但要改期 | 打开调整动作并回显原预约时间 |
| 已预约且到达执行阶段 | 推荐录入量房 |
| 已预约但已超过预约时间（逾期） | **不取消录入入口**：主行动仍为「登记量房结论」，同时保留「调整预约时间」（改约/重排）；逾期只影响风险等级与队列排序，不隐藏录入动作 |
| 已完成量房 | 推荐进入设计 |
| 未指定设计师但设计师本人负责客户 | 默认补齐本人为设计负责人 |
| 未指定设计师且当前为纯业务员 | 提示由负责人/店长指定设计师 |
| 多房屋客户 | 必须显式选择当前房屋 |
| 数据加载失败 | 显示暂不可确认，不生成假空状态 |
| 重复提交完成量房 | 返回原完成记录，不重复落库 |
| 取消预约 | 记录 Cancelled，允许重新预约 |

## 11. 非目标

本规格不引入：

- 接单、拒单、上门中额外状态。
- 量房关注点实体。
- 独立量房任务实体。
- 设计师兼业务员时自动进入正式设计池。
- 前端自行推断可见性。
- 通过归档页完成量房动作。
- 用空数据替代接口失败。

## 12. 研发落地要求

### 12.1 后端

- 客户创建：设计师本人录入时默认设计负责人本人。
- 房屋创建：继承客户设计负责人。
- 预约量房：更新已有 Scheduled Measure，补齐当前负责设计师。
- 完成量房：未指定设计师时按当前负责设计师自愈补齐。
- 房屋列表：设计师合并本人负责、本人营销、本人设计房屋并去重。
- 量房分页：保证当前责任设计师可读。

### 12.2 前端

- 左侧：客户选择。
- 中栏：客户详情、房屋详情、画像、诉求、跟进、量房记录。
- 右栏：调整预约、录入量房、进入设计。
- `record=1`：自动打开录入量房。
- `measureAction=schedule`：自动打开调整预约。
- 移动端和窄屏：中栏优先，右栏下移，不丢失操作。

### 12.3 测试

必须覆盖：

- 设计师本人录入客户后预约和完成量房。
- 已预约客户出现在待办和工作台。
- 调整预约时间。
- 直接打开录入量房。
- 多房屋客户。
- 纯业务员无设计负责人时阻断。
- 跨企业负向。
- 接口失败、空状态、重复提交。

## 13. 当前冻结结论

1. 量房工作台采用“左选择、中事实、右动作”的信息架构。
2. 量房责任与设计责任分开，量房池允许设计师兼业务员进入。
3. 设计师录入客户默认设计归本人。
4. 已预约量房必须支持调整时间和录入量房。
5. 录入量房必须直达工作台并自动打开动作，不允许归档页二次点击。
6. “量房关注点”不是新业务概念，现场事实、客户诉求和设计师判断必须分开。
7. 待办中心以 Scheduled Measure 为量房任务事实。
8. 页面不得用空数组或静态文案掩盖真实错误。

本规格冻结后，后续变更必须另行修订文档版本，不允许在实现中静默改变对象边界、状态机、角色责任或验收口径。

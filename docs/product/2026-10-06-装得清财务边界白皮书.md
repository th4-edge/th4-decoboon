# 装得清财务边界白皮书（L1 / L2 / L3 + 红线）

> 状态：正式（DEC-016 业务事实裁决，用户 2026-10-06 确认）
> 修订：2026-10-12 由业务智能体 `DEC-065`（用户 2026-10-12 裁决）修订 §9 角色与权限边界：财务数据范围由企业收窄为归属门店、多门店企业保留总部财务、财务工作台增加门店维度、店长取得与门店财务一致的本店记账写权限
> 定位：装得清财务能力边界的统一口径，供产品、研发、验收、运营、销售、市场共用
> 对外策略：§1、§2、§8 可作为对外表达口径；§3–§7、§9–§12 为内部策略，未经业务智能体过滤不得直接对外
> 关联：`DEC-016`、`EV-063`、`27-财务记账体系全景与口径总纲`、`08-财务域业务闭环设计`、`17-签约后自动记账与经营核算设计`、`23-财务账务理念对齐与手工记账边界设计`、`2026-10-06-员工工资与公司利润融入方案`、`2026-10-06-装企入驻账务承接与账务体系对齐方案`
> 业务依据：`GAP-002` 决策三（目标客户）、`SOL-002`、`SOL-005`、`SOL-007`、`SOL-008`、`MET-002`、`DEC-005`、`DEC-006`、`BR-007`

---

## 1. 一句话结论

> **装得清管项目和钱，不管税和账。**

装得清的财务边界是**项目经营账 + 资金台账 + 经营核算**，不是法定会计总账、税务系统或完整 HR。

| 边界 | 定义 | 归属 |
| --- | --- | --- |
| **L1 必须承载** | 项目经营事实的最小完整闭环 | 基础版财务模块 / 专业版及以上 |
| **L2 可承载但要轻量、可关停** | 员工工资、公司经营利润、门店经营视图 | 专业版及以上或高级财务包 |
| **L3 明确不承载** | 法定会计、税务、社保、完整 HR、复杂成本会计 | 不入产品范围 |

**一条红线**：装得清输出的任何数字，都不能被用户误当成会计、税务或审计依据。

## 2. 受众与判断依据

依据 `GAP-002` 决策三、业务总览和产品白皮书：

| 维度 | 事实 |
| --- | --- |
| 团队规模 | 10–30 人 |
| 门店 | 1–3 家 |
| 年产值 | 约 800 万–5000 万 |
| 在施项目 | 3–15 个 |
| 管理现状 | 老板深度参与报价、成本和回款；主要使用 Excel + 微信 |
| 核心痛点 | 报价漏项、变更扯皮、项目利润不清、回款不准 |
| 财务能力 | 通常 1 名财务/出纳，法定账与税务多由代账或会计负责 |
| 参与角色 | 老板 + 设计/业务负责人 + 项目经理 + 财务/材料角色 |

因此装得清财务能力只服务一个问题：

> 让老板看清**每个项目赚不赚钱、钱收回来没有、还欠谁、账上还有多少钱**。

不服务会计和代账要解决的问题。

## 3. L1 必须承载（核心经营账）

L1 是"业务流程自然产生、不填就无法经营"的事实，属于必须承载范围。

| 能力 | 关键对象 | 回答的问题 | 依据 |
| --- | --- | --- | --- |
| 合同与应收 | `ProjectContract`、`Receivable` | 该收多少、什么时候收 | `08`、`17` |
| 收款与核销 | `Receipt` | 钱收回来没有、哪笔未收 | `08`、`17` |
| 采购与应付 | `PurchaseOrder`、`Payable` | 该付多少、欠谁 | `08`、`17` |
| 付款与核销 | `Payment` | 付了没有、余额多少 | `08`、`17` |
| 项目成本与毛利 | `ProjectCostContext`、`Settlement` | 这单赚不赚 | `SOL-002`、`MET-002` |
| 人工/班组成本 | `Payable(Salary)`、`Partner`、`Worker` | 工人/班组结算与项目人工成本 | `SCN-009`、`OBJ-003` |
| 资金台账与现金流 | `Ledger` | 账上还有多少钱、现金流 | `08`、`23` |
| 凭证套打 | `VoucherRecord` | 收付款留档与重打 | `DEC-005` |
| 期初承接与双轨对账 | `OpeningBalance`、期初应收应付 | 存量客户能不能接进来 | `SOL-005`、入驻承接方案 |

L1 规则：

1. 能追溯到合同、采购、工资、材料计划的金额，必须走来源单据，禁止手工记账。
2. 一笔业务只写一次事实；应收≠收入、应付≠成本、付款≠成本。
3. 成本不完整时，毛利为 `null`，显示"成本未完整"，禁止按 0 计算。

## 4. L2 可承载，但必须轻量、可关停

L2 是"有价值但不是每家都必需、且容易越界"的能力，必须满足前置条件才允许做。

| 能力 | 承载边界 | 前置条件 |
| --- | --- | --- |
| 员工工资 | 固定工资 + 简单提成 + 最小考勤 + 实发；**发薪与成本归集** | 工资单确认计成本；项目/企业归属唯一；工资敏感权限独立 |
| 公司经营利润 | 项目毛利 + 非项目收入 − 企业费用，**经营参考口径** | 成本完整性传导；往来剔除；期间口径；不叫净利润 |
| 门店经营视图 | 门店范围的项目、资金、人员经营结果 | 门店数据范围由服务端强制；跨店不可见 |

L2 硬规则：

1. **可关停**：企业可以不启用公司经营利润或员工工资，主链仍然闭环。
2. **口径透明**：每个数字能说明来源、公式、完整度和缺失值。
3. **不越界**：不做个税/社保申报，不做 HR 全模块，不做复杂成本分摊。
4. **不误导**：公司利润显示为"经营利润（参考）"，不叫财务净利润。
5. **权限独立**：工资是独立敏感维度，不能只靠前端隐藏或菜单权限。

L2 与 L1 的关系：L2 只是把 L1 的事实汇总成**管理层视图**或补齐**人工成本来源**，不能反向要求 L1 改口径迁就 L2。

## 5. L3 明确不承载

| 不承载 | 原因 |
| --- | --- |
| 法定会计总账、会计科目、借贷分录、财务报表 | 客户有代账和会计，装得清不做第二套会计账 |
| 税务申报、发票管理、税负分析 | 法定责任，超出产品边界 |
| 社保、公积金代缴与申报 | 法定责任，超出产品边界 |
| 完整 HR（招聘、劳动合同、排班、考勤打卡、绩效体系） | 不是 10–30 人装企的日常经营主链 |
| 复杂成本会计（作业成本、多级分摊、标准成本差异分析） | 数据要求超出目标客户能力 |
| 合并报表、多币种、集团财务 | 面向大型企业，不是当前受众 |
| 银行直连对账、票据管理、全面预算 | 低频高复杂度，收益不匹配 |
| 取代客户原账本、逐笔还原历史科目 | 入驻承接已明确"三本账分离" |

## 6. 一条红线与四条"不可说"

**红线**：装得清输出的任何数字，都不能被用户误当成会计、税务或审计依据。

对外表达：

**可以说**

- 装得清管项目和钱：项目毛利、回款、应付、资金和项目成本。
- 装得清把销售价、成本价、实际成本分口径管理，成本不完整时不显示假利润。
- 装得清按"项目毛利 + 非项目收入 − 企业费用"口径展示公司经营利润（参考），往来不计入。

**不可说**

- 装得清替代财务核算、审计、税务申报、个税或社保代缴。
- 装得清展示的是财务净利润或税务利润。
- 使用后利润一定提高、成本绝对准确。
- 装得清能还原客户原账本或与会计科目一一对应。

## 7. L2 功能五道门禁

任何 L2 能力进入研发前，必须逐条回答，任一不过则不做：

1. **受众门禁**：10–30 人的老板/财务会不会每月真的使用？
2. **数据门禁**：数据是否在业务流程中自然产生，而不是额外填表？
3. **口径门禁**：能不能一句话讲清公式与来源，且不被误当会计口径？
4. **责任门禁**：会不会增加法定、税务或审计责任？
5. **闭环门禁**：去掉它，L1 主链是否仍然闭环？若去掉就断链，它应归 L1 而非 L2。

## 8. 版本与商务归属

| 边界 | 版本归属建议 | 说明 |
| --- | --- | --- |
| L1 核心经营账 | 基础版财务模块（`Finance`）/ 专业版及以上 | 对齐现有"财务模块包 ¥2,980/年"与专业版闭环 |
| L2 员工工资、公司经营利润 | 专业版及以上或高级财务包 | 不放入免费版；具体价格与权益以另行定价决策为准 |
| 免费版 | 仅报价基础链路，不含财务闭环 | 对齐白皮书"免费版窄而深"原则 |
| L3 | 不入产品范围 | 由客户会计/代账/专业系统承接 |

> 版本归属只确定"能力放在哪一档"，不改变现有价格，也不构成新的对外价格承诺；价格调整必须另行决策并做套餐版本快照。

## 9. 角色与权限边界

| 角色 | 财务可见范围 |
| --- | --- |
| BOSS | 全公司项目经营、资金、公司经营利润 |
| 总部财务 | 全企业项目经营、资金与公司经营利润；承载跨店汇总、合并与公司经营利润（参考）（`DEC-065`） |
| 门店财务（`Finance`） | 归属门店的项目经营、资金、成本与毛利；本店工资核算与发放（`DEC-065`） |
| 店长 | 本店项目与资金；**本店记账写权限，边界与门店财务一致**（不含 BOSS 专属的作废、更正、冲正重记）；本店员工个人工资（企业可配置、留痕、敏感字段脱敏）（`DEC-065`） |
| 团队负责人 | 本团队相关经营视图（待口径冻结） |
| 员工本人 | 仅本人工资条、本人考勤、本人提成 |
| 工人/班组 | 走工人工资链路，不进员工薪酬权限 |

规则：

1. 企业/门店/团队/负责人只能从登录员工加载，禁止信任前端参数。
2. 工资敏感字段（银行卡、身份证、个税明细）默认仅 BOSS/财务可见。
3. 越权按"不存在或无权访问"处理，不泄露他人财务事实是否存在。
4. 店长看本店员工个人工资应作为企业配置项，不是硬编码固定权限。
5. 门店范围由服务端强制（`comId AND storeId`）；财务账号必须归属门店，未归属不得访问财务域。
6. 财务工作台必须支持门店维度：BOSS/总部财务可选「全部门店」并下钻单店；门店财务/店长锁定本店，非法 `storeId` 一律驳回。

## 10. 能力与受众符合度

| 能力 | 契合度 | 判断 |
| --- | --- | --- |
| 项目毛利 / 成本完整性 | 高 | 直击"项目利润不清" |
| 应收 / 回款 | 高 | 直击"回款不准" |
| 应付 / 资金现金流 | 高 | 老板控资金、防超付 |
| 工人工资 / 班组结算 | 高 | 项目人工成本，直接影响毛利 |
| 凭证套打 | 高 | 已有客户习惯 |
| 期初承接 / 双轨对账 | 高 | 存量客户迁移必需 |
| 员工工资（固定+考勤+提成+实发） | 中 | 有需求，须防长成 HR/薪酬引擎 |
| 公司经营利润 | 中 | 老板想要，但数据基础弱，须防误读为净利润 |
| 法定会计 / 税务 / 社保 | 低 | 受众交外部处理，不做 |

## 11. 越界反模式清单

1. 把公司经营利润直接叫"净利润"，不标完整度和期间。
2. 为了让利润好看，用 0 成本或 0 费用补齐缺失数据。
3. 让员工工资既进项目成本又进企业费用。
4. 把员工工资塞进手工记账或复用工人工资口径。
5. 为了"功能完整"加个税、社保、发票、总账科目。
6. 要求客户把历史原账逐笔搬进装得清。
7. 用前端隐藏代替服务端权限，或让店长/员工越范围看工资。
8. 把 L2 能力做成免费版或基础版默认首屏，造成认知和定价冲突。
9. 用"系统输出的就是真实利润"作为销售话术。
10. 先做复杂考勤、打卡、绩效、多级分摊，再考虑目标客户是否真的需要。

## 12. 变更流程

1. 任何新增/放宽财务边界（新对象、新口径、新权限、新指标）必须先在业务智能体登记 `GAP`/`DEC`。
2. 不得由研发、销售或营销单方面把 L3 能力写成产品事实或对外承诺。
3. 边界变更必须同步更新：本白皮书、`27-财务记账体系全景与口径总纲`、`00-装得清产品与定价白皮书`、相关 `DEC`/`MET`/`BR`。
4. 变更后必须运行 `python3 05-自动化/knowledge.py validate` 和 `index`。
5. 涉及金额、成本、利润、权限的边界变更，保持全量测试与用户确认。

## 13. 对外可摘录段落

> 装得清面向 10–30 人、1–3 店的成长型中小家装企业，做的是项目经营账和资金台账：把合同、应收、采购、应付、收付款、项目成本和项目毛利连成一条可追溯的事实链。

> 装得清不做客户的会计账，也不做税务和社保申报。它负责让老板看清每个项目赚不赚钱、钱收回来没有、还欠谁、账上还有多少钱。

> 成本不完整时，装得清不显示假利润，而是提示"成本未完整"。

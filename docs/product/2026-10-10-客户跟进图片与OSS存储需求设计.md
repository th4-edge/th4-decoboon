> 关联实现：`CustomerFollow`、`customer/customer-follow/save`、`file/private/grant`、`FileScope`、App 客户跟进页、Web 客户跟进组件

## 0. 结论摘要

本需求是在现有“客户跟进记录”上增加**多图片证据附件**能力：

1. 客户跟进仍是一条独立业务事实，图片是该跟进记录的附件，不单独形成跟进记录、不改变客户阶段、风险、金额或统计口径。
2. 每条跟进 P0 建议最多 9 张图片；文字跟进内容仍为必填，图片选填。图片不能替代跟进内容，除非用户另行确认允许“纯图片跟进”。
3. 图片对象保存到阿里云 OSS 私有 Bucket，业务实体只保存 OSS 对象键，不保存永久公网 URL。
4. App 和 Web 共用同一套服务端契约：上传走 `file/private/grant`，保存走 `customer/customer-follow/save`，读取展示走 `customer/customer-follow/page` 返回的对象键和短期访问地址。
5. 图片权限继承其所属跟进记录/客户的数据范围，不新增角色、不放宽跨企业、跨门店、跨团队或跨负责人权限。
6. P0 仅企业内部员工可见；业主端不展示客户跟进图片，除非后续单独确认客户可见性。
7. 保存跟进仍沿用现有副作用：`New -> Following`、休眠客户写跟进自动唤醒、更新 `lastFollowAt` 与 `nextFollowAt`；图片必须在同一事务中随跟进记录一起落库。
8. 已保存的跟进记录为追加型审计事实，P0 不支持修改或删除图片；更正应新增跟进记录并说明更正原因。

## 1. 业务问题与目标

### 1.1 当前问题

现有 `CustomerFollow` 只有：

- 跟进方式 `way`
- 跟进内容 `content`
- 下次跟进时间 `nextFollowAt`
- 跟进员工 `emp`
- 客户、企业、门店、团队归属

业务员、设计师、店长在电话、微信、到店、拜访、量房前后，常需要留下现场照片、户型图、材料参考、沟通截图或现场问题照片。没有图片时：

- 只能把照片存在个人微信/相册，无法形成企业可复用证据；
- 交接给设计师、店长、项目经理时信息断层；
- 后续设计、报价、签约缺少上下文；
- 管理者无法判断跟进是否真实、完整；
- 客户经营记录无法沉淀为企业资产。

### 1.2 本需求目标

在不改变客户主链和跟进状态机的前提下，让：

- 业务员、设计师、店长、企业负责人可以在写跟进时录入多张图片；
- 图片保存到阿里云 OSS，按企业、客户跟进范围隔离；
- 跟进记录支持缩略图展示、全屏预览、按期刷新访问地址；
- App 与 Web 使用同一业务事实、同一权限口径和同一展示顺序；
- 历史文字跟进不被破坏，新老数据兼容。

### 1.3 非目标

P0 不做：

- 独立“图片素材库”或跨客户复用素材；
- 图片编辑、裁剪、水印、批注、OCR、AI 识别；
- 跟进图片对业主/客户可见；
- 图片参与风险分、客户等级、金额、成本、利润或转化率计算；
- 已完成跟进记录的图片编辑、删除、替换；
- 多图片排序拖拽（按选择顺序保存即可）；
- 视频、PDF、Office 附件（本需求只做图片）；
- 跨企业共享或跨租户复制图片；
- 对外宣称“已上线”“已验收”的能力。

## 4. 角色、数据范围与权限

### 4.1 写权限

P0 图片写权限**不新增角色**，必须与最终冻结后的 `follow/save` 动作策略一致。

当前标准文件 `business-action-policies.json` 中 `follow/save` 注册角色为：

- Boss
- StoreManager
- Marketer
- Designer

数据范围按客户主对象：

| 角色 | 可写图片的客户范围 |
| --- | --- |
| Boss | 本企业 |
| StoreManager | 本门店 |
| Marketer | 本人负责客户 |
| Designer | 本人负责、被指派或参与范围内的客户 |

`TeamLeader`、`Pm`、`Finance` 不因本需求获得写跟进或写图片权限。当前 App `permission.ts` 对部分角色存在 `act:followCustomer` 的历史差异，必须在研发前建立并关闭 `GAP-*`；本设计不替该冲突做扩权裁决。

### 4.2 读权限

- 图片随所属 `CustomerFollow` 和 `Customer` 的数据权限返回。
- 员工能读取某条跟进记录，才能读取该记录的图片。
- 跨企业、跨门店、跨团队、跨负责人的直接图片路径访问必须返回 404 或无权限，不泄露对象存在性。
- 图片路径不是授权凭证；不能凭 OSS 对象键绕过 `file/private/grant`。

### 4.3 业主/客户可见性

P0 明确建议：**业主端不可见客户跟进图片**。

原因：

- 当前 `SCN-001` 把跟进定义为内部客户经营证据；
- 部分跟进可能包含内部判断、报价策略、聊天截图或非客户授权材料；
- 需要客户可见时应另行走“交付附件/客户可见动态”业务规则，不得复用内部跟进权限。

### 4.4 动作权限矩阵

| 动作 | Boss | StoreManager | Marketer | Designer | TeamLeader/Pm/Finance |
| --- | --- | --- | --- | --- | --- |
| 上传跟进图片并保存跟进 | 允许（企业范围） | 允许（本店范围） | 允许（本人负责） | 允许（负责/指派/参与范围） | 不允许（除非 `follow/save` GAP 另行裁决） |
| 查看跟进图片 | 允许（企业范围） | 允许（本店范围） | 允许（本人负责） | 允许（负责/指派/参与范围） | 按客户既有数据范围只读，前提是该角色能读客户和跟进 |
| 修改/删除历史图片 | 不允许 | 不允许 | 不允许 | 不允许 | 不允许 |
| 业主查看 | 不允许 | 不允许 | 不允许 | 不允许 | 不允许 |

## 5. 业务对象与字段设计

### 5.1 主对象

`CustomerFollow`（客户跟进记录）。

### 5.2 图片字段方案

#### P0 推荐：图片对象键列表

在 `CustomerFollow` 增加：

```java
@ElementCollection
@CollectionTable(
    name = "cust_customer_follow_image",
    joinColumns = @JoinColumn(name = "follow_id"))
@OrderColumn(name = "sort_no")
@Column(name = "url", length = 512, nullable = false)
private List<String> images;
```

补充瞬态展示字段：

```java
@Transient
private List<String> imageUrls;
```

字段口径：

| 字段 | 类型 | 含义 | 规则 |
| --- | --- | --- | --- |
| `images` | `List<String>` | OSS 对象键列表 | 最多 9 个；按用户选择顺序；只保存对象键，不保存临时预签名 URL |
| `imageUrls` | `List<String>` | 当前请求生成的短期访问地址 | 不落库；由服务端按权限签发；URL 过期后前端可重新签发 |
| `requestId` | `String(64)` | 写跟进幂等号 | 同一表单只生成一次；重复提交返回同一条跟进 |
| `followId` | `Long` | 跟进主键 | 图片子表外键 |
| `sort_no` | `int` | 图片顺序 | 从 0 或 1 开始，展示顺序稳定 |

为什么不把图片直接拼成 JSON 字符串：

- 不符合对象/集合建模习惯；
- 无法稳定排序；
- 无法对单张对象键建立唯一约束和索引；
- 不利于后续按业务对象授权。

#### 备选：独立 `CustomerFollowImage` 实体

只有在以下情况才升级为独立实体：

- 必须记录每张图片的原文件名、上传人、上传时间、大小、内容类型；
- 必须支持单张图片审计、替换、隐藏或删除；
- 必须按图片维度做权限或客户可见性控制。

若采用独立实体，字段至少包括：`imageId`、`company`、`follow`、`objectKey`、`originalName`、`contentType`、`size`、`sort`、`uploadedBy`、`createTime`。P0 不建议，避免把简单证据附件做成大型 ERP 附件中心。

### 5.3 DDL 建议

```sql
-- 客户跟进图片：只存 OSS 对象键
CREATE TABLE cust_customer_follow_image (
  follow_id BIGINT NOT NULL,
  url VARCHAR(512) NOT NULL,
  sort_no INT NOT NULL,
  PRIMARY KEY (follow_id, sort_no),
  UNIQUE KEY uk_customer_follow_image_url (url),
  KEY idx_customer_follow_image_follow (follow_id),
  CONSTRAINT fk_customer_follow_image_follow
    FOREIGN KEY (follow_id) REFERENCES cust_customer_follow (follow_id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

-- 幂等号：同一客户跟进表单重复提交不产生重复有效记录
ALTER TABLE cust_customer_follow
  ADD COLUMN request_id VARCHAR(64) NULL,
  ADD UNIQUE KEY uk_customer_follow_company_request (com_id, request_id);
```

说明：

- `url` 实际保存 OSS 对象键，不保存 `https://...` 永久地址。
- `request_id` 可为空以兼容历史记录；新请求必须由前端生成。
- MySQL 唯一索引允许多个 `NULL`，历史数据不冲突。
- 这是 DDL 变更，必须单独执行备份、迁移、全量验证和回滚。

### 5.4 模型关系

```text
Company 1 ── N CustomerFollow
Customer 1 ── N CustomerFollow
Employee 1 ── N CustomerFollow (emp)
CustomerFollow 1 ── N CustomerFollowImage(objectKey)
CustomerFollowImage(objectKey) ──> OSS 私有对象
```

图片不单独挂 `Project`：客户跟进发生在签约前后，当前主对象仍是客户；如果后续确认跟进必须绑定具体房屋/项目，应新增独立决策，不在此需求中猜测。

## 6. 状态与业务一致性

### 6.1 不新增状态

本需求不新增客户状态、不新增跟进状态、不改变 `CustStatus`。

### 6.2 保存跟进仍沿用现有副作用

保存带图跟进必须与纯文字跟进保持一致：

- 客户为 `New`：保存后进入 `Following`；
- 客户为 `Dormant`：写跟进后按 `BR-036` 唤醒到休眠前状态；
- 更新客户 `lastFollowAt`；
- 按请求更新 `nextFollowAt`；
- 触发原有风险和待办重算；
- 不因“有图片”跳过任何状态校验。

### 6.3 图片不参与的业务

图片不得：

- 改变客户阶段；
- 改变风险等级、逾期、今日跟进或沉睡客户判断；
- 改变金额、成本、利润、报价或合同事实；
- 改变休眠排除/恢复规则；
- 增加跟进次数（跟进次数按 `CustomerFollow` 记录数，不按图片数）；
- 成为量房完成、设计方案完成、报价提交或签约的证据替代品。

## 7. 上传、OSS 与私有访问设计

### 7.1 OSS 路径

新增 `FileScope`：

```java
CustomerFollow("客户跟进图片")
```

对象路径复用现有企业文件策略：

```text
companies/{comId}/files/customerfollow/{yyyy}/{MM}/{uuid}.{ext}
```

规则：

- `comId` 只能来自登录员工，不能接受前端传入；
- 客户跟进不强制绑定项目，因此 `projectId` 为空；
- 文件名使用 UUID，不在 OSS 路径暴露客户姓名、手机号或小区信息；
- Bucket 保持私有；
- 不调用 `PutObjectAcl` 放开对象；
- 业务实体只保存对象键。

### 7.2 上传时序

```text
选择本地图片
→ 前端压缩/校验
→ file/private/grant（multipart，businessType=CustomerFollow）
→ OSS 私有写入
→ 返回 path（对象键）+ 短期 URL
→ 前端保存 path 列表
→ customer/customer-follow/save（content + images + requestId）
→ 后端校验权限/路径/数量/重复
→ 同一事务写跟进、图片关联、客户状态副作用
→ 返回跟进记录 + imageUrls
```

### 7.3 访问时序

```text
打开跟进列表/详情
→ customer/customer-follow/page 返回 images + imageUrls
→ App/Web 使用短期 URL 展示缩略图
→ 点击缩略图全屏预览
→ URL 过期或加载失败
→ file/private/grant（businessType=CustomerFollow, businessId=followId, paths=[对象键]）
→ 服务端按所属 CustomerFollow 和客户数据范围重新授权
→ 返回新短期 URL
→ 前端替换并重试一次
```

### 7.4 文件类型与大小

P0 建议冻结值：

| 项 | 建议值 | 说明 |
| --- | --- | --- |
| 单条跟进图片数 | 最多 9 张 | 与现有验收、动态、整改图片上限一致 |
| 单张大小 | ≤ 10 MB | App 默认压缩；超限阻断并给出原因 |
| 单条总大小 | ≤ 30 MB | 防止移动网络下长时上传 |
| 支持格式 | jpg / jpeg / png / webp | 保证 App 与 Web 都能预览；HEIC 由前端压缩转换 |
| 内容校验 | 扩展名 + MIME + 图片头校验 | 不能只相信扩展名；非图片直接拒绝 |
| 文件命名 | UUID | 不保留用户原文件名到 OSS 路径 |

### 7.5 私有下载与签名

- 继续使用 `file/private/grant` 和 `file/private/download`。
- 签名有效期沿用现有默认 300 秒，不新增永久 URL。
- `imageUrls` 只存在于响应/前端内存，不落库。
- 过期后必须重新签发，不能把过期地址写回业务字段。

## 8. API / Provider 契约

### 8.1 保存跟进

Provider：`customer/customer-follow/save`

请求新增：

| 字段 | 类型 | 必填 | 规则 |
| --- | --- | --- | --- |
| `customerId` | Long | 是 | 服务端校验可见范围 |
| `way` | FollowWay | 否 | 缺省 Other，成功结果不变 |
| `content` | String | 是 | 仍按现有 `@NotEmpty`；最长 512 |
| `nextFollowAt` | String | 否 | 仍按现有规则校验 |
| `images` | List<String> | 否 | 最多 9 个 OSS 对象键；去重；不能为空字符串 |
| `requestId` | String(64) | 是 | 前端每次表单生成一次，用于幂等 |

处理规则：

1. 校验 `customerContext.requireVisible(customerId, current)`。
2. 校验 `images` 数量、格式、去重。
3. 校验每个对象键以 `companies/{currentComId}/files/customerfollow/` 开头。
4. 按 `requestId` 幂等重放：已存在直接返回已有跟进，不重复唤醒客户、不重复写状态日志。
5. 创建 `CustomerFollow`，写入文字、图片对象键、跟进人和归属快照。
6. 按现有逻辑处理休眠唤醒、客户状态、`lastFollowAt`、`nextFollowAt`。
7. 事务提交后返回值包含 `images` 与 `imageUrls`。

错误建议：

| 场景 | 错误码 | 文案 |
| --- | --- | --- |
| 图片超过 9 张 | 400 | 单条跟进最多上传 9 张图片 |
| 单张超过 10MB | 400 | 单张图片不能超过 10MB |
| 非图片格式 | 400 | 仅支持 JPG、PNG、WEBP 图片 |
| 图片重复 | 400 | 同一跟进不能重复添加同一张图片 |
| 路径不属于当前企业 | 403 | 图片不属于当前企业或无权使用 |
| 客户无权访问 | 404 | 客户不存在或无权访问 |
| requestId 重复且内容不同 | 409 | 请求已处理，请刷新后重试 |

### 8.2 跟进分页

Provider：`customer/customer-follow/page`

请求仍为：

```json
{
  "customerId": 123,
  "current": 1,
  "size": 20
}
```

响应新增：

```json
{
  "followId": 456,
  "way": "Phone",
  "content": "客户确认周六到店",
  "nextFollowAt": "2026-10-18 10:00:00",
  "images": [
    "companies/179.../files/customerfollow/2026/10/uuid1.jpg",
    "companies/179.../files/customerfollow/2026/10/uuid2.jpg"
  ],
  "imageUrls": [
    "https://.../file/private/download?path=...&expires=...&signature=...",
    "https://.../file/private/download?path=...&expires=...&signature=..."
  ],
  "imageCount": 2,
  "emp": { "empId": 1001, "name": "黄贤杰" },
  "createTime": "2026-10-10 15:20:00"
}
```

规则：

- `images` 是稳定对象键，前端可保存/重签；
- `imageUrls` 是当前请求生成的短期地址，不作为业务字段回写；
- `imageCount` 是只读派生字段，等于 `images.size()`；
- 默认 `size=20`，最大 50，避免 200 条跟进 × 9 张图片造成响应体过大；
- 排序仍按 `createTime` 倒序。

### 8.3 私有文件授权

Provider：`file/private/grant`

上传调用：

```json
{
  "businessType": "CustomerFollow",
  "file": "<multipart>"
}
```

授权刷新调用：

```json
{
  "businessType": "CustomerFollow",
  "businessId": 456,
  "paths": ["companies/.../uuid1.jpg"]
}
```

后端必须：

1. 按 `businessId` 加载 `CustomerFollow`；
2. 校验跟进所属企业与当前员工一致；
3. 校验跟进所属客户对当前员工可见；
4. 校验请求路径确实在该跟进 `images` 中；
5. 只返回授权范围内的短期 URL。

### 8.4 接口不新增的能力

P0 不提供：

- `customer/customer-follow/update` 修改历史跟进；
- 图片删除 Provider；
- 业主端跟进图片查询 Provider；
- 公开 OSS URL；
- 跟进图片批量导出/打包下载。

## 11. 异常、边界、并发与幂等

### 11.1 上传异常

| 场景 | 处理 |
| --- | --- |
| 未授权相册/相机 | App 提示去微信设置开启权限 |
| 断网/上传域名未配置 | 保留表单和已成功图片，提示具体上传失败原因 |
| 部分图片上传成功、部分失败 | 成功图片保留对象键；失败项可重试；未全部成功不允许保存 |
| 用户取消选择 | 不报错、不生成空图片、不改变现有选择 |
| 图片对象键失效 | 服务端返回 404；前端不显示伪成功 |
| 签名 URL 过期 | 重新调用 `file/private/grant`，最多自动重试一次 |

### 11.2 保存异常

| 场景 | 处理 |
| --- | --- |
| 客户越权/不可见 | 404 或 403，不泄露客户是否存在 |
| 图片路径不属于当前企业 | 403，阻断保存 |
| 图片超过 9 张/重复/格式不对 | 400，指出具体原因 |
| 并发写同一客户 | 沿用 `RedissonLock` 分布式锁；冲突返回 409 |
| 重复点击保存 | 同一 `requestId` 幂等返回已有跟进 |
| 事务失败 | 跟进、图片关联、客户状态全部回滚；OSS 对象由清理任务处理 |
| 休眠客户写跟进 | 图片与跟进一起成功后才唤醒；失败不唤醒 |

### 11.3 幂等要求

- 同一表单的 `requestId` 在保存成功前保持不变；
- 同一 `(com_id, request_id)` 只允许一条 `CustomerFollow`；
- 重复保存不得重复写图片关联、状态日志、客户状态或下次跟进时间；
- 若同一 `requestId` 内容不一致，返回 409，要求刷新后重试；
- 不同表单即使用户选择相同图片，也不得复用同一对象键（对象键 UUID 天然不同）。

### 11.4 并发与事务

```text
上传图片：OSS 写入，不进入业务事务
保存跟进：RedissonLock(customer-status:{comId}:{customerId})
→ 校验客户可见
→ 校验图片路径
→ 写 CustomerFollow + images
→ 更新 Customer + 状态日志
→ 提交事务
```

图片上传不能放在数据库事务里长时间持锁；数据库事务只负责保存对象键和业务事实。

## 12. 安全、性能、存储与清理

### 12.1 安全

- Bucket ACL 保持私有；不调用 `PutObjectAcl` 放开对象；
- 业务实体不保存永久公网 URL；
- 所有图片访问必须经过 `file/private/grant` 授权；
- 签名 URL 有效期 300 秒，不写入数据库；
- 图片对象键不能作为权限凭证；
- 预签名 URL 过期返回 401/403；
- 业主账号访问内部跟进图片必须 404；
- 跨租户、跨门店、跨团队、非本人负责客户不能通过 followId 或 path 越权；
- 客户跟进图片不进入公开素材库或宣传池；
- 图片路径不含客户姓名、手机号、小区等个人信息。

### 12.2 性能

- `customer/customer-follow/page` 默认 20 条、最大 50 条；
- 图片缩略图由 OSS/CDN 或预签名 URL 加载，不经过业务应用服务回源；
- 跟进文字和图片列表不得因图片加载失败而整体失败；
- 页面 P95 目标按 `BR-025` / `DEC-027` 执行；
- 列表只返回必要字段，不返回原图二进制；
- 客户端不循环请求每条跟进的图片授权；分页响应一次性返回当前页图片短期 URL；
- 每页图片总量大时，前端只渲染可视区域或使用懒加载。

### 12.3 存储与清理

- 未保存跟进即上传的图片属于孤儿对象；
- 建议新增清理任务或 OSS 生命周期策略：
  - 24 小时内未被 `cust_customer_follow_image` 引用的 `customerfollow` 对象可回收；
  - 或保留 7 天作为误操作恢复窗口后回收；
  - 具体天数待用户确认。
- 历史文字跟进无图片，不迁移、不补空图片表；
- 已保存跟进图片不物理删除；
- 客户删除、企业注销或合规删除时，按数据保留规则另行处理 OSS 对象。

### 12.4 审计

- 跟进记录保留 `emp`、时间、方式、内容、下次跟进时间；
- 图片属于该跟进记录，保留对象键、顺序、归属；
- 图片上传时间和上传人默认等同父跟进保存时间和跟进员工；
- 若需要“每张图片上传人/原文件名/大小”审计，升级为独立 `CustomerFollowImage` 实体；
- 修改/删除历史跟进图片不提供接口。

## 18. 对外表达边界

### 可以说

- 装得清支持在客户跟进中记录多张现场图片；
- 图片存储在企业私有的阿里云 OSS 对象空间；
- App 和 Web 可以查看同一客户跟进记录及图片；
- 图片访问受企业、门店、团队和负责人数据范围控制；
- 图片不会改变金额、成本和利润口径。

### 不可说

- “客户可见跟进图片”（P0 不可见）；
- “支持图片永久公开链接”；
- “图片可用于跨企业复用/宣传”；
- “有图片即证明客户高意向/已成交”；
- “已上线/已验收”直到生产发布和独立验收完成。

### 必须附条件

- 单条最多 9 张、单张最长 10MB 等限制；
- 图片格式限制；
- 图片是跟进证据，不是客户承诺或成交承诺；
- 权限按登录员工真实数据范围裁决，前端隐藏按钮不替代服务端校验。

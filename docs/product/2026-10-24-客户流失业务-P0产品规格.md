# 客户流失业务 P0 产品规格

> 日期：2026-10-24  
> 状态：用户确认实施，研发中  
> 依据：`DEC-042`、`BR-036`、`DEC-052`、`OBJ-001`、`BR-001`、`DEC-066`、`DEC-080`  
> 适用范围：后端、Web、App；签约前客户经营

## 1. 业务定义

客户在签约前明确选择其他装修公司、明确拒绝、自装或装修计划取消时，结束本轮客户经营机会，标记为 `Lost（已流失）`。

- 客户生命周期仍只有一个 `Lost` 终态。
- 流失发生的业务阶段、原因、范围、对手和操作完整留痕。
- 量房、设计、报价、合同草稿等历史事实不删除、不回退、不重置。
- `Lost` 不进入逾期跟进、今日跟进、量房、设计、谈单、签约等活跃工作台。
- 客户通过“已流失”筛选、客户详情和流失历史继续可见、可统计、可恢复。
- 客户改选其他公司不得使用 `Dormant`；无明确结论的暂缓、联系不上或计划未定才使用休眠。

## 2. 真实场景

### 场景一：量房后改选其他公司

| 项 | 内容 |
| --- | --- |
| 使用人 | 设计师 |
| 触发事件 | 房屋已完成量房，设计尚未交付，客户表示已选择其他装修公司 |
| 当前动作 | 在“待我设计”工作区打开“标记流失”，确认本次房屋、`Design` 阶段和原因 `ChoseOtherCompany` |
| 系统下一步 | 保存流失记录；如果这是该客户唯一在途房屋，客户状态置为 `Lost`；退出全部活跃队列；保留量房事实 |
| 异常处理 | 若客户只是暂缓装修或预算未定，应使用休眠；若合同已签署，必须走合同终止/关闭 |

### 场景二：谈单中客户已与其他公司签约

| 项 | 内容 |
| --- | --- |
| 使用人 | 设计师、业务员、店长、企业负责人或财务 |
| 触发事件 | 方案与报价均已沟通，客户明确已在其他公司签约，但本合同尚未签署 |
| 当前动作 | 在“待我谈单”或“待我签约”工作区标记流失，记录阶段、原因、竞争对手和客户原话 |
| 系统下一步 | 结束本轮经营；报价接受等历史事实保留；不再进入待谈单/待签约；不计入签约金额 |
| 异常处理 | 若已存在已签署合同，不得标记客户流失，转入合同终止、退款或关账流程 |

### 场景三：一客户多房屋，仅一套流失

| 项 | 内容 |
| --- | --- |
| 使用人 | 设计师或客户负责人 |
| 触发事件 | 客户房屋 A 改选其他公司，房屋 B 仍在本司设计 |
| 当前动作 | 选择“本次房屋”标记房屋 A 流失 |
| 系统下一步 | 只排除房屋 A；客户仍保持活跃，房屋 B 继续进入对应工作台 |
| 异常处理 | 所有在途房屋都流失或客户明确整体不再装修时，才将客户状态置为 `Lost` |

## 3. 状态与对象

### 3.1 客户状态

```text
New / Following / PendingMeasure / Quoted / Dormant
  -> Lost
Lost -> 恢复 -> New / Following / PendingMeasure / Quoted
Signed / Serving / Finished -> 不允许标记客户流失
```

`Lost` 是当前经营轮次的终态，不是客户档案永久不可恢复。

### 3.2 流失记录

新增 `CustomerLoss`：

- 客户、房屋；
- 流失范围：`Customer / Property`；
- 流失阶段：`FollowUp / Measure / Design / Negotiation / Signing`；
- 流失原因及说明；
- 竞争对手名称；
- 流失前客户状态；
- 流失时间、操作人、角色；
- 幂等请求号；
- 恢复时间、恢复人、恢复后状态、恢复说明；
- 恢复幂等请求号。

### 3.3 历史事实

- 不物理删除客户。
- 不删除或重置量房、设计、报价、合同和跟进。
- 不将房屋状态伪装成“流失”；房屋继续展示最后一次真实执行状态。
- 客户已被整体标记流失时，历史报价不能计入签约金额或签约成功数。

## 4. 权限与数据范围

| 角色 | 标记流失 | 恢复 | 数据范围 |
| --- | --- | --- | --- |
| 企业负责人 Boss | 允许 | 允许 | 本企业 |
| 店长 StoreManager | 允许 | 允许 | 本门店 |
| 业务员 Marketer | 允许 | 允许 | 本人负责客户 |
| 设计师 Designer | 允许 | 允许 | 本人负责或指派/参与客户 |
| 财务 Finance | 允许 | 允许 | 按 `DEC-080` 企业/门店范围 |
| 团队负责人、项目经理 | 拒绝 | 拒绝 | 既有只读/业务范围 |

服务端通过 `CustomerContext.requireVisible` 和登录员工重新解析企业和数据范围；不接受前端传企业、门店、负责人。

## 5. 接口与跨端同源

| 能力 | Provider | 请求要点 | 响应 |
| --- | --- | --- | --- |
| 标记流失 | `customer/loss/save` | customerId、propertyId、scope、stage、reasonCode、expectedStatus、requestId | CustomerLoss |
| 恢复流失 | `customer/loss/update` | lossId、restoreStatus、nextFollowAt、restoreNote、requestId | CustomerLoss |
| 流失历史 | `customer/loss/page` | customerId、current、size | Page<CustomerLoss> |

客户 `page/info/overview` 返回当前活跃流失摘要；活跃队列不 join 流失明细，只使用状态和单房流失存在性过滤。

## 6. 工作台规则

以下队列统一排除客户整体 `Lost` 和已流失房屋：

- 待我跟进；
- 待我量房；
- 待我设计；
- 待我谈单；
- 待我签约；
- 设计师今日主线队列。

已流失客户仍进入：

- “全部客户”；
- “已流失”筛选；
- 客户详情；
- 客户经营阶段计数；
- 流失阶段、原因和金额分析。

## 7. 查询负担

- 五个活跃队列只增加 SQL 条件或单房流失 `NOT EXISTS`，不增加请求数。
- 客户列表/经营投影按当前页或企业范围批量查询活跃流失摘要，禁止逐客户查询。
- 流失历史按客户分页。
- 客户列表如需展示流失原因，一次批量查询当前页记录，不产生 N+1。

## 8. 验收标准

### 正向

- 客户整体流失：状态 `Lost`、下次跟进清空、写状态日志、退出全部活跃队列。
- 单房流失且其他房屋在途：客户仍活跃，仅该房屋退出队列。
- 所有在途房屋流失：客户自动置为 `Lost`。
- 恢复：流失记录标记恢复；没有剩余活跃流失时客户回到指定/原阶段。
- Web/App 同一 Provider、同一错误语义、同一权限和同一阶段枚举。

### 反向

- 已签约、施工中、已完工客户禁止标记流失。
- 未关闭合同阻断客户整体/对应房屋流失。
- 缺少阶段、原因、Other 说明、房屋或存在跨客户房屋时拒绝。
- 跨企业、跨门店、非本人客户返回 404/403。
- 重复请求号幂等，不得重复生成流失记录。

### 边界

- 历史 `Lost` 且无流失记录：显示“流失信息待确认”，不得推断原因。
- 多房屋客户不得因单房流失被整体排除。
- 接口失败显示“暂不可确认”并提供重试，不以空数组伪装成功。
- 小程序正式版提审和发布仍由用户本人完成。

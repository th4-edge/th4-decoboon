## 1. 一句话产品命题

> **装得清是装企老板围绕“一单”进行客户转化、项目交付和经营兑现的经营主控台：提前发现风险、明确责任和下一步，并让所有关键数字回到同一业务事实。**

这里的“一单”是产品聚合视角，不是新增业务实体。它由客户、房屋、报价、合同、项目、履约和财务事实共同构成，不改变任何现有对象归属和状态机。

## 2. 目标用户与非目标

### 2.1 首要服务对象

- 10–30 人、1–3 家门店的成长型装企老板。
- 一人装企或老板亲自承担多个内部岗位的场景。
- 店长、财务、设计师、项目经理等角色是执行面；老板是经营结果和关键阻断的责任面。

### 2.2 产品不解决

- 不替老板做商业决策，不替代业主/客户确认。
- 不做法定会计总账、税务申报、审计报告和完整 HR。
- 不做通用 OA、纯审批平台或功能大全。
- 不以“每个角色都有页面”作为产品完成标准。
- 不承诺使用后利润必然提升或企业必然增长。

### 2.3 通用前提与事实边界

- 验收必须来自当前租户的真实业务对象；演示对象必须显式标记，不能作为客户价值证据。
- 客户、房屋、报价、合同、项目、收付款、成本和利润的事实主源仍是现有领域对象与 Provider；本文不新增字段或第二套事实源。
- 权限和数据范围最终由服务端判定；前端入口、页面能力和菜单不能代替授权。
- 业务状态按现有状态机推进；任何“经营视图”都不得覆盖或伪造正式状态。
- 历史快照、已生效合同、已发生收付款和已确认成本不得被后续展示需求改写。
- 重复提交、并发更新和对象失效必须可识别；动作完成后按服务端事实回读。
- 本文没有新增业务信息项。若后续新增，必须先登记唯一业务信息项 ID，明确主源、维护角色、消费者和闭合动作。

## 3. 三件经营问题

| 编号 | 经营问题 | 老板要得到的结果 | 产品命题 |
| --- | --- | --- | --- |
| `OWN-P1` | 哪一单值得推进、哪一单正在丢失？ | 知道机会在哪里、为什么停、谁接下一步 | 客户转化不是客户列表，而是每一单的连续推进 |
| `OWN-P2` | 哪一单正在失控、谁能让它恢复？ | 在损失扩大前发现交付阻断并完成处置 | 项目交付不是事后填表，而是风险前置和责任闭环 |
| `OWN-P3` | 这一单到底赚不赚钱、钱在哪里？ | 每笔钱和每项成本可解释，项目结果可信 | 财务不是第二套录入，而是业务事实的自动核算与对账 |

这三项不是三个平级模块，而是同一单的三个阶段：

```text
客户转化 -> 项目交付 -> 经营兑现
   获客       履约        现金与利润
```

老板从任一阶段进入，看到的都应是同一单、同一事实和同一责任链。

## 4. OWN-P1：客户转化不是列表，而是每一单的连续推进

### 4.1 老板问题

> 哪些客户值得我今天花时间？哪些正在悄悄流失？卡在报价、合同、量房还是没人跟进？下一步由谁完成？

### 4.2 产品承诺

老板不需要进入多个岗位页面拼凑事实，就能对每一个重点机会回答：

1. 当前处于什么业务阶段；
2. 最近一次有效推进会是什么、何时发生；
3. 当前卡点是什么，缺事实、缺决策还是缺责任人；
4. 当前责任人是谁，下一步动作是什么；
5. 完成后会进入什么状态，由谁接棒。

### 4.3 必须由系统承担

- 聚合客户、房屋、量房、设计、报价、合同和跟进事实，提供同一单的状态投影。
- 阶段、停留、风险、责任人、下一步和允许动作来自服务端，不由前端按字段自行推导。
- 从机会卡片可以直接进入对象工作面，完成当前主行动，并回读对象新状态。
- 失败、无权限、数据缺失和对象已变化必须给出恢复路径，不得显示伪空或伪零。

### 4.4 验收场景

使用真实企业、真实账号，至少选择一个正常推进机会和一个停滞/流失风险机会：

```text
BOSS 打开经营入口
-> 找到两个重点机会
-> 不看设计/业务员独立列表，也能说明阶段、卡点、责任人和下一步
-> 进入其中一个机会完成一个真实主行动
-> 下一责任角色能收到同一事实
-> 返回后看到新状态、下一步和时间线
```

### 4.5 硬验收

- 验收样本内，重点机会的阶段、责任人、下一步和阻断原因可确认率达到 100%。
- 报价/合同关键事实与现有 Provider 一致，前端不重算正式金额或状态。
- 同一推进动作完成后，下一责任角色无需重新录入同一事实。
- 接口失败、无权限、真实空态、对象失效四类状态可区分。
- 只有总数、漏斗或卡片入口，不能下钻到具体机会和动作，判为不通过。

## 5. OWN-P2：项目交付不是事后填表，而是风险前置和责任闭环

### 5.1 老板问题

> 哪一单今天最可能延期、停工、验收不过或客户投诉？问题是什么、影响谁、谁负责恢复、下一步什么时候完成？

### 5.2 产品承诺

老板看到的不是“项目列表 + 红黄绿标签”，而是一条可处置的风险链：

```text
风险对象
-> 触发事实
-> 对进度/客户/资金/利润的影响
-> 当前责任人
-> 唯一主行动
-> 阻断与恢复路径
-> 完成后回读
```

### 5.3 必须由系统承担

- 统一项目当前阶段、任务、节点证据、验收、整改、材料、变更和交接事实。
- 风险原因、责任人、时限、下一步和允许动作由服务端投影。
- 老板可以从经营风险直接进入项目对象工作面，处理完继续下一项，保留筛选和上下文。
- 一人装企老板承担多个岗位动作时，仍按原状态机逐步推进和留痕。

### 5.4 验收场景

使用至少一个真实在建项目和一个发生阻断/风险的项目：

```text
BOSS 进入风险入口
-> 选中风险项目
-> 看到风险原因、影响、责任人和唯一主行动
-> 进入现有项目工作面完成允许动作
-> 系统回读项目状态、风险、任务和下一步
-> 返回队列继续处理下一项，原筛选和位置仍在
```

### 5.5 硬验收

- 风险项不能只有颜色或标题；必须同时给出原因、责任人、下一步和恢复路径。
- 动作成功后以服务端回读结果为准，不得用写接口响应覆盖完整项目读模型。
- 重复提交、并发变化、无权限、接口失败和阻塞均有明确结果。
- 项目当前状态、关键金额和下一责任人与 App/Web 同 Provider、同语义。
- “老板看过风险”不构成完成；必须产生业务状态变化、责任交接或可追溯处置记录。

## 6. OWN-P3：财务不是第二套录入，而是经营事实的自动核算与对账

### 6.1 老板问题

> 这一单合同多少、已收多少、还欠多少？成本是否完整？毛利能不能算？现金和利润为什么不是一个数？为什么还要回 Excel 再算一遍？

### 6.2 产品承诺

一笔业务事实只写一次，再由不同口径形成不同投影：

| 账本/投影 | 回答 |
| --- | --- |
| 合同与收入账 | 签了多少、变更后多少、应收多少、已收多少 |
| 成本与利润账 | 预计/动态/最终成本、应付、项目毛利和完整性 |
| 资金与现金账 | 实际收付、余额、净现金流 |
| 风险与核校账 | 哪些来源不一致、逾期、缺成本或超预算 |

财务和老板看到同一笔金额时，可以回答：

1. 这个数字来自哪条业务事实；
2. 是否已经实际发生；
3. 是否进入现金流、成本或利润；
4. 缺失时缺什么、谁负责补齐；
5. 出错时应从哪个来源单据更正或冲正。

### 6.3 替代 Excel 的最低成功标准

不是“系统里有财务菜单”，而是：

- 业务动作自动形成财务事实，财务不重复录入。
- 项目账、资金账、应收应付和利润投影可以互相对账。
- 每个关键金额可以下钻到合同、采购、到货、收款、付款、工资或调整来源。
- 成本不完整时利润为空，不生成伪利润。
- 月度关账仍在 Excel 二次汇总、重算或补录，则不能宣称替代 Excel。
- Excel 可以作为导出和过渡承接工具，但不能成为系统经营结果的外部计算器。

### 6.4 验收场景

选择一个成本完整项目、一个成本不完整项目，并覆盖一次真实收付款：

```text
老板与财务打开同一项目
-> 合同额、应收、已收、应付、已付、成本完整性一致
-> 任一关键金额下钻到来源事实
-> 成本完整项目显示对应阶段毛利
-> 成本不完整项目显示“成本未完整”，利润为空
-> 收付款与台账一一对应
-> 财务完成一次不依赖 Excel 重录/重算的关账演练
```

### 6.5 硬验收

- 同一收付款不得生成重复台账；有效收付款与台账来源必须守恒。
- 失败时不得显示 0；未知、无权限、空数据和部分失败必须区分。
- P1/P2/P3 成本口径不得混用；实际成本、应付和付款不得互相冒充。
- 金额、比例、时间必须带范围和口径；公司/门店经营利润未冻结时不得展示确定值。
- 验收样本内，关键金额可追溯率和 App/Web 回读一致率均须为 100%。

## 7. 两个真实装企场景

### 场景 A：15 人、两家门店的成长型装企

- 使用人：企业负责人。
- 触发：早上查看当天经营阻断。
- 当前动作：发现一个高价值客户停留过久，一个在建项目成本不完整，一个应收已逾期。
- 系统下一步：把三个问题关联到各自“一单”，给出责任人、影响和主行动。
- 异常：部分接口失败时显示“暂不可确认”，保留其他可用事实和恢复路径。
- 成功结果：老板完成一次客户推进和一次项目处置，财务补齐一个成本来源，所有结果可回读。

### 场景 B：一人装企

- 使用人：同时承担业务、设计、项目、财务内部动作的老板。
- 触发：新客户当天咨询，需要从登记推进到量房、报价、合同和项目。
- 当前动作：在同一单上下文内连续完成多个岗位动作。
- 系统下一步：每次只给当前唯一主行动；状态逐步推进；操作人、承担能力、前后状态和时间完整留痕。
- 异常：不得因为同一人操作而跳过客户接受、合同生效、项目立项或高风险确认。
- 成功结果：老板不切换岗位系统，也不会重复录入；一单事实和下一状态连续。

## 8. 总体验收矩阵

| 验收维度 | 通过条件 | 不接受 |
| --- | --- | --- |
| 一单事实 | 验收样本内，老板可回答三件经营问题 | 只有模块入口、统计卡或流程说明 |
| 数字可信 | 关键金额和状态可回到 Provider 与业务来源 | 前端公式、默认值、伪零和伪利润 |
| 操作减负 | 同一事实不在多个页面重复录入 | 系统成为 Excel 之外的第二次抄写 |
| 异常处置 | 每个异常有原因、责任人、下一步和恢复路径 | 红黄绿标签、看过即完成 |
| 跨端同源 | App/Web 同账号同对象同状态同金额 | 仅验证一端或文案近似 |
| 责任留痕 | 动作人、承担能力、前后状态、时间和来源可追溯 | 同人操作跳过节点或不可追溯 |
| 真实价值 | 真实企业、真实账号、真实 Provider、真实业务对象 | Mock、静态截图、演示数据单独过关 |

验收样本内的建议量化门槛：

- 一单关键事实可确认率：`100%`
- 关键金额可追溯率：`100%`
- App/Web 关键事实一致率：`100%`
- 异常项具备责任人和下一步的比例：`100%`
- 因系统缺失导致的重复录入次数：`0`
- 项目利润应显示为空时被伪算为确定值的次数：`0`

这些门槛只用于产品验收，不得直接转成对外效率或收益承诺。

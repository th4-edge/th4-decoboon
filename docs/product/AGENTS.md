# docs/product — 产品与业务文档规范

> 根目录 `AGENTS.md` 同时生效。本目录只定义产品需求、业务方案和验收口径，不得用当前代码行为反推业务事实。

## 1. 业务事实来源

- 业务对象、状态、角色权限、数据范围、金额/成本/利润和对外口径以全局技能 `zhuangdeqing-business` 及其 `BR/DEC/OBJ/EV/GAP` 为准。
- 涉及正式业务变化时先提交 `T05 → T06/T12`；未裁决前只允许调研、证据整理和需求澄清。
- 发现口径冲突登记 `GAP-*`，不得自行选择更省事的版本。

## 2. 需求必须写清

- 至少两个真实中小装企场景：使用人、触发事件、当前动作、系统下一步、异常处理。
- 前置条件、状态变化、责任人、权限范围、历史数据、幂等和失败恢复。
- 信息的唯一主源、维护角色、应用场景、下游消费者和闭合业务动作；新增信息项必须引用或登记唯一 ID。
- 完成条件必须由当前租户真实领域对象推导；区分必做与可选，接口异常表达为“暂不可确认”，禁止用 `done:true`、空数组或演示数据伪装完成。

## 3. 闭环与跨端

- 首发范围围绕“签约后工地不乱”；变更、材料、业主、验收和钱只作为支撑场景，不并列扩展。
- 核心能力必须在 App、Web、业主端和后端具备同 Provider、同权限、同状态、同金额/成本语义和同事实回读。
- Web 核心页面必须通过唯一 Token 真源和真实渲染视觉门禁；App 核心页面必须通过多机型、七态、弱网和真机证据门禁。
- 页面信息必须服务于判断、行动、交接、确认、留证或对账；只有字段、数字、状态或入口时不算交付。
- 未完成范围冻结、真实项目闭环、独立验收和营销事实映射前，状态只能是“产品验证中”，不得宣称完整闭环、已验收或可规模化推广。

## 4. 专用入口

- 推广前关门标准：`docs/product/01-推广前最低业务闭环与跨端质量门禁.md`
- 业务信息架构：`docs/product/02-业务信息架构与字段闭环标准.md`
- 复杂业务域：直接读取领域 `state.json`、`00-charter.md`、`10-reconciliation.md`，状态工具使用 `scripts/domain_state.py`。
- 营销内容和使用内容 Skill 当前已归档暂停；恢复前必须经用户明确确认并更新 Skill Registry。两者不定义产品事实、不改页面、不直接发布。

## 二、最严重的问题不是“提示多”，而是提示对象错了

界面提示只能服务四类用户问题：

1. 现在发生了什么事实？
2. 我现在需要做什么？
3. 为什么不能继续？
4. 如何恢复、找谁处理？

如果一句话主要在说明“代码怎么实现、数据从哪里来、页面为什么不负责、验收矩阵怎样、当前研发批次有没有裁决”，它就不属于产品界面。

本次最典型的问题有以下几类。

### 1. 直接暴露研发过程与验收状态

- Web 工作台首页直接展示代码路径 `src/roles/workbenchHome.ts`。
- Web 工作台卡片展示“对象锚点”“待业务确认”“尚未通过业务裁决”。
- Web 材料业务说明展示“字段字典”“未决业务事项”“不等于业务已全部验收；以对账矩阵为准”。
- Web 报价动作直接写“待业务裁决（T06）”。
- Web 项目经理工作台直接写“按 BR-008 在工作区提交”。
- App 量房页面直接写 `DEC-069`。
- App 成片页面直接写 `P0 使用多视频片段服务端渲染`。

这些内容应留在代码注释、产品文档、验收报告或内部管理端，不应出现在装企经营界面。

### 2. 把后端/前端实现细节当作业务说明

- “服务端试算”“服务端已保存”“服务端重算”“服务端回读”。
- “由服务端核销并写入资金台账”。
- “金额由服务端最终校验”“状态与金额由服务端裁决”。
- “前端不提交”“前端不猜测”“不用空数组伪造完成”。
- “读时投影”“经营投影”“服务端量房任务投影”。

用户关心的是：金额是否准确、这次操作是否成功、下一步是谁做什么；不需要知道请求由哪一端处理。

### 3. 把测试防线写进用户文案

- “不会用兜底话术伪装成功”。
- “经营动态只展示真实业务事实，不会用演示数据填充”。
- “不显示虚构项目或默认第一条”。
- “不使用第一条兜底”。
- “不用前端推算或假数据”。

“不造假数据”应当是研发和验收约束，不是产品卖点或用户提示。界面只需诚实呈现真实空态、失败态和恢复路径。

### 4. 把内部产品战略词直接当用户语言

“同频”已经作为产品定位和内部解决方案被确认（`DEC-013`），但这不意味着它天然适合作为界面标签。业主看到“业主端只读同频”“审批通过后自动同频”，无法立即知道：

- 谁会更新？
- 什么时候更新？
- 我能看到什么？
- 有异议找谁？

面向用户应使用“进度同步”“审批通过后自动更新”“如对变更内容有疑问，请联系设计师”等结果语言。

### 5. 用负向说明解释“为什么没有某个按钮”

- “增减项不是业主在线确认”。
- “材料到场不需要业主确认”。
- “为什么这里没有‘确认到场’按钮”。
- “记录边界”。

这类文案是在解释产品设计边界，不是回答业主当前最关心的问题。可以保留必要的业务结论，但不应以“系统事实/记录边界/为什么没有按钮”的方式展开。

## 三、业主端原例审计

相关业务事实是正确的：增减项由内部形成，企业审批通过后生效；业主端只读查看，不将业主确认建模为系统事实（`BR-035`、`DEC-068`，均为 approved/high）。问题在于事实正确、表达对象错误。

`owner-change.vue` 中至少有以下 6 个界面位置：

| 位置 | 当前文案 | 问题 |
|---|---|---|
| 页面空态 | “本页只读展示变更结果” | 解释页面职责 |
| Hero 补充信息 | “审批通过后自动同频” | 内部产品术语 |
| 变更留痕副标题 | “企业审批生效后，业主端只读同频” | 研发边界 + 内部术语 |
| 卡片标题 | “增减项不是业主在线确认” | 负向解释系统模型 |
| 卡片正文 | “变更由设计师或授权角色在内部发起……业主端展示变更结果” | 内部流程和端边界 |
| 卡片来源 | “企业审批 · 业主只读” | 系统视角标签 |

建议改为：

```text
区块标题：变更记录
副标题：审批通过后生效

审批中：
本次变更正在审批。审批完成后会自动更新合同金额和后续安排，无需您操作。

已生效：
本次变更已于 2026-10-15 审批生效。
如对变更内容有疑问，请联系设计师。
```

同类的业主端内部表达还出现在：

- 材料计划：“只展示业主可见的计划事实”“记录边界”“为什么这里没有确认到场按钮”。
- 报价：“本页展示系统已经同步的登记结果”“当前同步结果尚未返回登记人……”
- 选材：“系统展示设计师登记后的选材版本”“当前同步结果尚未返回……”
- 量房区域：“快照长”“快照宽”。
- 业主入口：“项目进度同频”。

## 四、Web 端判断

Web 的问题明显重于 App，并且不是局部的：

- App 100 个候选中，43 个属于系统实现解释；Web 334 个候选中，239 个属于系统实现解释。
- Web 角色配置、工作台卡片、项目/报价/合同/量房/财务页面普遍使用“服务端事实、投影、回读、待业务确认”作为产品文案。
- Web “材料业务说明”页面公开了字段字典、蓝图层未决项和对账矩阵语言，且该入口对 Boss、店长、财务开放。
- Web 报价、合同变更和量房页面大量出现 `T06`、`BR-008`、`DEC-*`、`服务端试算` 等过程语言，说明页面仍带有明显的研发自检界面属性。

Web 当前更像“业务能力验收控制台”，还不是可以直接交给装企老板、店长和财务长期使用的商业工作台。这是本轮审计最重要的判断。

## 五、为什么会发生

1. **把“证明实现正确”当成了界面任务。** 为了证明没有假数据、没有越权、没有前端兜底，研发约束被直接写进页面，形成了“技术自证式文案”。
2. **缺少角色语言转换。** 需求和技术事实被直接搬进界面，没有分别回答业主、老板、店长、设计师、财务“此刻看到什么、要做什么”。
3. **缺少文案门禁。** 类型检查、构建和契约测试都通过了，但没有一项检查会在生产 UI 出现 `服务端`、`Provider`、`BR-008`、`待业务确认` 时阻断发布。
4. **“暂不可确认/待业务确认”被滥用。** 诚实的缺失态是对的，但它应表达用户可理解的事实缺失，而不是把研发交付状态暴露给业务用户。
5. **没有区分内部文档与产品界面。** 字段字典、业务蓝图、验收矩阵本身有价值，但应进入内部知识库、实施培训或运营后台，而不是企业业务菜单。

## 六、整改原则

### 1. 先保留正确业务事实，再换表达

不能为了“清爽”删掉必要的阻断原因和恢复路径。例如：

- “合同尚未生效，暂时不能发起增减项”可以保留。
- “已进入采购，换材请走增减项”可以保留。
- “成本未完整，利润暂不可确认”必须保留。
- “缺少客户参数”不能保留，应改为“页面信息不完整，请返回客户列表后重新打开”。

### 2. 建立四句式文案

每个提示最多回答以下一项或两项：

```text
事实：现在是什么状态
动作：您需要做什么
阻断：为什么不能继续
恢复：如何重试或找谁
```

回答不了以上问题的“说明”，默认删除。

### 3. 禁止技术自证

生产 UI 禁止出现：

```text
服务端、前端、后端、接口、Provider、API、投影、回读、状态机、幂等、兜底
P0、G1、G3、BR-*、DEC-*、GAP-*、T05、T06
业务裁决、待业务确认、对账矩阵、字段字典、对象锚点、唯一主行动、接棒
假数据、演示数据、空数组、默认第一条、前端不、后端不
```

“同频”不作为普通界面状态词；客户界面统一改为“进度同步 / 结果同步 / 自动更新”。

### 4. 错误码与界面文案分离

后端可以返回稳定错误码和业务原因，但前端必须映射为角色可执行文案。禁止把 `items/filename 参数`、`字段配置 JSON`、`缺少 quoteId`、`P0 服务端渲染暂只支持……` 原样弹出。

### 5. 增加构建门禁

建议新增 `npm run check:client-copy`：

- 扫描 `.vue` 模板文本、常用展示属性和 `.ts` 可见文案常量。
- 生产路由默认禁止上述词表。
- 仅允许明确标注的内部管理路由或员工预览安全提示豁免。
- 对错误码中可能透传给用户的文案做黑名单检查。
- 在 App/Web 构建前运行。

## 八、后端透传文案风险

除 App/Web 源码外，后端还有一批可能被前端原样弹出的研发语言。本轮没有把它们并入前端 434 的计数，但整改时必须一并处理。已确认的代表项包括：

- `ContentRenderContext`：“服务端渲染至少需要一条视频素材”“P0 服务端渲染暂只支持视频片段”。
- `DesignTemplateFormulaContext`：公式错误里直接出现 `DEC-062`。
- `MaterialAssistantContext`：向业务用户说明“不信任前端传入的 companyId/empId/projectId”“字段字典”等实现口径。
- `catalog/.../Import`：“items 列表或 filename 参数至少一项必填”。
- `quote/.../Save`：“设计报价或套餐报价参数不完整”。
- 文档模板配置相关接口直接返回 JSON、字段配置、缺少 key 等开发术语。

这类文案应改为稳定错误码 + 前端角色文案映射，不能在生产业务界面直接透传。

## 九、审计边界

- 本次只做源码级产品文案审计，没有修改 App/Web 代码。
- 明细 CSV 是候选清单，不等同于独立验收结论。
- 正常业务说明、法定协议、必要阻断原因、异常恢复文案和员工预览安全提示没有作为“研发提示”计入整改结论。
- 下一次整改后，应按角色逐页做真实界面复核，不能只用源码替换和构建通过代替渲染验收。

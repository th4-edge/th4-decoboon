# 客户到诉求：录入信息下游使用审计

> 日期：2026-10-28  
> 范围：客户登记 → 跟进 → 客户画像 → 房屋 → 量房 → 客户诉求  
> 关联：`PI-20261028-001`、`SCN-001`、`OBJ-007`、`DEC-003`  
> 性质：当前产品实现审计，不是业务验收，不新增业务事实
>
> 后续审计：`docs/product/audits/2026-10-28-设计到成本录入信息下游使用审计.md`。两批累计 39 个问题点。

## 一、结论

本段共审计 **52 个用户可见录入字段/语义组**：

| 分类 | 数量 | 含义 |
| --- | ---: | --- |
| 直接进入后续业务动作 | 25 | 改变对象、状态、队列、权限、任务、报价或交付事实 |
| 证据/历史留痕字段 | 5 | 照片、附件、跟进方式等，有追溯价值，但不直接推动下一步 |
| 未产生业务动作或重复录入 | 22 | 只被保存、展示、评分或 AI Prompt 消费，未进入设计、报价、合同、材料、项目或验收动作 |

22 个问题点中：

- P1：12 个，造成关键信息断链或重复录入；
- P2：7 个，信息只进入 AI/评分/展示，未形成岗位动作；
- P3：3 个，低频展示或备注字段价值不足。

因此，用户举例的“量房录了很多、后续没用”“跟进和诉求录了、后续没有应用”不是个别现象，而是当前前段产品设计的结构性问题。

## 二、判定标准

一个字段只有满足以下任一条件，才算“进入业务链”：

1. 触发或阻断下一步动作；
2. 进入下游对象并被后续角色使用；
3. 改变队列、风险、责任人、状态或时间；
4. 参与报价、合同、材料、任务、验收、金额或成本计算；
5. 成为必须留证、对账或客户确认的正式证据。

以下情况不算真正使用：

- 只在客户详情或档案页回显；
- 只用于客户评分数量，实际值不参与判断；
- 只进入 AI Prompt，但 AI 结果不进入主链；
- 复制到另一个自由文本字段，仍靠人重新阅读；
- 存在状态和确认时间，但没有门禁、队列或下游动作。

## 五、5 个证据型字段

以下字段不是“死字段”，但当前录入成本和业务价值不匹配：

| 字段 | 当前作用 | 问题 |
| --- | --- | --- |
| 跟进方式 `Follow.way` | 历史展示 | 未用于渠道分析或客户行为判断 |
| 跟进图片 | 历史证据 | 与跟进内容、诉求、设计素材没有联动 |
| 量房现场照片 | 留证、AI 参考、业主旅程 | 与设计参考、施工交底和验收证据分开使用 |
| 结构图 | 留证、数量展示 | 没有成为设计必须引用的结构依据 |
| 量房附件 | 留证、数量展示 | 附件类型、用途、下游消费者不明确 |

这 5 项不应简单删除，而应改为自动归档、自动关联和按需展示，避免用户重复上传和重复解释。

## 六、根因

### 1. 表单驱动，而不是决策驱动

字段按“可能有用”收集，没有按“谁会用它做什么”设计。结果是录入界面完整，业务链没有消费者。

### 2. 自由文本承担了结构化职责

跟进内容、量房客户诉求、量房设计师结论都是长文本。它们可读，但不能自动生成：

- 客户诉求；
- 设计任务；
- 报价提醒；
- 材料或工艺约束；
- 下一步动作。

### 3. 同义事实多源录入

- 客户地址/面积 vs 房屋地址/面积；
- 跟进内容 vs 结构化诉求；
- 量房客户诉求 vs 客户诉求模块；
- 量房尺寸文本 vs 原始区域实测；
- 画像风格 vs 设计方案风格；
- 付款偏好 vs 付款计划。

多源录入后没有主源和同步规则，导致用户重复填、系统无法判断哪一个有效。

### 4. AI/评分被误当成业务使用

字段进入 AI Prompt 或客户评分，只能证明“技术上有读取”，不能证明“业务上产生作用”。如果没有设计任务、报价提示、跟进队列或客户确认，仍然属于信息断链。

### 5. 缺少字段生命周期

字段没有定义：

- 谁维护；
- 何时必填；
- 哪个业务动作消费；
- 不填写时阻断什么；
- 变化后谁收到什么任务；
- 何时归档或失效。

### 6. 缺少“下游消费者”验收

当前测试主要验证字段能保存、能读取、权限正确，未验证：

```text
录入该字段 → 哪个下游页面/Provider 读取 → 触发什么动作 → 形成什么可核验结果
```

## 七、需要新增的字段契约

后续每个录入字段必须填写：

| 项 | 要求 |
| --- | --- |
| 唯一主源 | 同一语义只允许一个正式事实源 |
| 维护角色 | 谁在什么阶段录入/修改 |
| 必填条件 | 什么情况下必须填写，否则阻断哪个动作 |
| 下游消费者 | 哪些角色、页面、Provider 读取 |
| 业务动作 | 读取后产生什么任务、提示、限制或确认 |
| 变化影响 | 修改后哪些对象、队列、报价或计划需要重算/重新读取 |
| 缺失策略 | 缺失时显示“暂不可确认”，不得补默认值 |
| 留痕策略 | 是否需要图片、确认人、时间、历史版本 |
| 退出策略 | 何时不再要求录入、归档或删除 |

只有“唯一主源 + 下游消费者 + 业务动作”同时成立，字段才允许进入正式表单。

## 八、建议处理顺序

### 第一批：先关闭重复录入和关键断链

1. 跟进内容允许生成结构化诉求/下一步，不再只保存长文本；
2. 画像风格/人口/环保/顾虑转成设计约束与谈单任务；
3. 客户预算进入报价超预算提示，而不是只参与评分；
4. 量房客户诉求合并到 `Requirement` 唯一主源；
5. 量房尺寸合并到 `MeasureRegion` 唯一主源；
6. 诉求状态和确认时间进入设计/报价/方案完成门禁。

### 第二批：清理低价值字段

- 性别、客户备注、房屋备注、微信号、诉求来源逐项裁决：
  - 有明确动作则保留并接入下游；
  - 没有明确动作则降级为可选备注或删除。

### 第三批：证据字段一体化

- 跟进图片、量房照片、结构图、附件统一进入项目证据流；
- 设计、施工交底、验收直接按来源引用，不再重复上传。

## 九、当前边界

- 本审计只覆盖客户到诉求前段，不代表整条主链完整统计。
- 22 是当前可逐项复核的问题点下限，不是随意估计。
- 字段进入 AI Prompt 不等于业务应用；AI 结果是否真正进入设计、报价和项目，仍需单独审计。
- 本审计不删除任何字段，不修改状态机和业务规则。

## 十、下一步

继续按同一方法扫描：

```text
设计 → 报价 → 合同 → 项目 → 任务 → 材料 → 验收 → 收付款 → 成本
```

预计仍会存在同类问题，尤其是自由文本、附件、备注、计划和派生指标。最终应形成全业务“字段—下游消费者—业务动作”总台账，并作为推广前最低闭环门禁的一部分。

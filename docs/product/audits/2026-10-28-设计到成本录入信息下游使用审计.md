## 五、为什么这些是“信息失效”而不是简单缺功能

### 1. 上游已经有正式事实，却没有下游消费者

例如报价行已经有工艺和验收标准，但合同行没有保存，项目任务没有引用，验收单也不读取。用户会认为“报价里写了”，现场却拿不到。

### 2. 下游重新录一遍，导致多源

- 合同付款条件与付款计划；
- 项目动态中的问题与整改问题；
- 任务节点证据与验收现场证据；
- 主材作业单规格与采购单/到场记录；
- 客户跟进内容与客户诉求。

### 3. 有状态或字段，但没有门禁

- 客户签认证据可以保存，但不是生效门禁；
- 验收问题可以记录，但没有逐项关闭；
- 开票要求可以填写，但没有开票闭环；
- 拉群/安装时间可以填写，但没有提醒和计划联动。

### 4. AI/导出/展示被误认为业务闭环

进入 AI Prompt、Excel 或详情页只能证明“被读取”，不能证明“改变了下一步”。正式业务动作仍必须落到对象、状态、责任人、时间、金额或验收证据。

## 六、跨段影响

| 上游录入 | 下游应有结果 | 当前风险 |
| --- | --- | --- |
| 设计说明/风格 | 合同范围、项目任务、材料标准、验收说明 | 只存在于设计和谈单稿 |
| 报价工艺 | 合同快照、项目任务工艺、现场交底 | 项目可能读取当前材料库而非签约快照 |
| 报价验收标准 | 项目任务标准、阶段验收检查项 | 验收依赖 PM 重新填写问题 |
| 主材作业单规格 | 采购单、到场核验、退换货依据 | 采购明细缺失颜色/尺寸/工艺等关键条件 |
| 任务节点影像 | 阶段验收证据包 | PM 重复上传，证据链断开 |
| 验收问题 | 逐项整改任务、责任人和复验 | 整单闭环，问题漏项难追 |
| 合同付款条款 | 应收节点、到期日、收款提醒 | 文本与实际应收计划各走一套 |
| 开票要求 | 待开票、已开票、归档 | 只显示是否需开票，没有流程 |

## 七、建议的修复顺序

### 第一优先：签约快照与执行事实

1. 合同行保存 `craft`、`criterion` 快照；
2. 项目任务只使用合同/变更快照生成工艺和验收标准，不回读当前材料库作为正式执行口径；
3. 阶段验收读取任务验收标准，并要求逐项检查，不允许只有整单照片。

### 第二优先：材料下单到采购到场

1. 采购明细保存作业单行的颜色、尺寸、型号、玻璃和工艺快照；
2. 到场记录按采购明细核验规格；
3. 退换货、结算和成本均引用同一采购明细。

### 第三优先：证据复用

1. 验收自动汇总阶段内任务/节点证据；
2. 业主驳回问题生成逐项整改事项；
3. 复验逐项回读，而非只上传整单照片。

### 第四优先：删除或改造无效字段

- 设计费/管理费：要么进入金额公式，要么删除；
- 合同付款条件和付款计划：确定唯一主源；
- 主材拉群/安装时间：接入提醒或项目计划，否则降为备注；
- 项目动态正文：明确只作留证，不宣称能自动生成风险；
- 开票字段：接入开票状态与附件，否则不进入正式表单；
- 任务备注：合并到交底/验收标准或降为备注。

## 八、审计边界

- 本批以当前代码和前端入口为准，不把 AI Prompt 消费自动视为业务完成。
- 不把所有“只展示字段”判为错误；证据字段、审计字段和备注字段必须结合职责判断。
- 未对工人工资、员工薪酬、费用报销和复杂多门店经营做本轮同等深度扫描。
- 后续仍需真实项目走查，确认代码中存在的引用是否在页面和实际业务动作中真正发生。

## 九、累计结论

```text
客户到诉求：22 个问题（P1 12 / P2 7 / P3 3）
设计到成本：17 个问题（P1 7 / P2 8 / P3 2）
当前累计：39 个问题（P1 19 / P2 15 / P3 5）
```

这说明装得清已经出现了典型的“信息系统化”问题：**录入比消费快，表单项比业务动作多，档案比闭环完整**。推广前必须把“字段是否有下游消费者、是否改变下一步”作为正式门禁。

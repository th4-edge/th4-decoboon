## 1. 总裁决

Web 设计师转化工作空间锁定为：

```text
客户与房屋上下文
-> 设计版本
-> 报价版本对比
-> 客户反馈与异议
-> 合同交接
-> 增减项影响
-> 选材确认
```

Web 的定位是：

> 设计师最后一公里转化指挥台 + 客户沟通准备与事实记录中心 + 跨角色交接工作空间。

Web 不是未经裁决的客户 IM、短信或微信客服系统；客户正式接收、确认和后续渠道仍按正式产品边界执行。

## 2. 五问答复

### Q1 Web 客户沟通的边界是什么？

**答复：采用候选口径 A。**

Web 负责：

- 沟通前准备：整理客户诉求、决策人、关注点、方案和报价版本。
- 沟通材料组织：确定本次展示的设计版本、报价版本、合同/变更/选材材料。
- 沟通结果记录：客户反馈、异议、设计师回应、承诺事项和下一步。
- 跟进推进：形成内部待办、责任人和截止时间。
- 跨角色交接：把客户反馈和待决策事实交给 Boss、店长、财务或其他责任人。

Web 不直接负责：

- 作为新的微信、短信或 IM 消息渠道自动触达客户。
- 代替客户完成正式确认。
- 绕过 App/业主端已有授权和身份机制。
- 把客户口头反馈自动转换为报价接受、合同同意或选材确认。

例外：如未来要增加 Web 直接触达客户能力，必须另行建立渠道、授权、隐私、撤回、审计和用户决策，不纳入本批次。

### Q2 是否新增正式“沟通轮次/客户反馈/异议/承诺”对象？

**答复：P0 不新增独立业务对象和状态机。**

P0 使用：

- `CustomerFollow` 作为沟通事实主记录；
- 现有客户画像、设计诉求和量房结论作为客户关注点来源；
- 设计版本、报价版本、合同、增减项和选材记录作为“本次展示了什么”的对象引用；
- `TalkPlan` 作为谈单材料的历史能力，不反向成为正式状态机。

允许在 `CustomerFollow` 上补充最小结构化字段，用于表达：

- 本次沟通阶段；
- 展示对象类型与对象引用；
- 展示版本；
- 客户反馈；
- 客户异议；
- 设计师承诺；
- 下一步动作；
- 下次跟进时间。

字段扩展必须由后端实体、迁移和 Provider 正式承载，前端不得私建第二套沟通对象。

补充约束：

- 沟通记录不是报价、合同、变更或选材状态。
- 异议关闭不等于客户接受报价或合同。
- 承诺事项不得包含未经授权的价格、工期或质量保证。
- 正式对象建立前，不建设独立“客户异议工作流”或“沟通审批流”。
- `SOL-004` 的 `DesignFeedback` 仍作为 AI 设计转化后续对象方向，不等同于本批次通用沟通记录。

### Q3 `SOL-004` 的报价解释、异议话术、会后摘要和跟进建议在 Web 是 P0 还是 P1？

**答复：人工和规则化能力进入 P0；AI 生成辅助仍为 P1。**

P0 允许：

- 系统聚合事实，形成沟通准备卡。
- 设计师手工填写报价解释要点和客户关注点。
- 用固定模板记录会后摘要、异议和下一步。
- 根据正式规则提示“待客户确认、待签约、待选材、待跟进”等下一步。
- 展示设计/报价/合同/变更/选材版本差异，供设计师向客户解释。

P0 不允许：

- AI 自动生成正式报价解释并直接发送给客户。
- AI 自动承诺价格、优惠、工期、材料或施工结果。
- AI 自动判断客户已经接受。
- 把 AI 推测写成客户确认诉求。

P1 再评估：

- AI 报价解释草稿；
- AI 异议话术建议；
- AI 会后摘要；
- AI 跟进建议；
- AI 客户模拟和设计师训练。

所有 AI 内容必须标记来源、置信度和待审核状态，进入正式设计、报价、合同或施工依据前必须由责任角色确认。

### Q4 Web 可以完成哪些客户确认和合同动作，代录需要什么证据？

**答复：Web 可以承载内部动作和交接，不得代替客户做正式确认。**

| 动作 | Web P0 口径 |
| --- | --- |
| 设计诉求维护 | 设计师按本人负责范围维护 |
| 设计方案维护 | 设计师按权限维护，正式设计事实需责任确认 |
| 报价创建、保存、提交 | 设计师按报价权限执行；金额必须来自服务端快照 |
| 报价接受/驳回 | 由客户正式确认；Web 只能记录反馈、待办和交接，不直接替客户确认 |
| 合同生成、签约、生效 | 由具备合同权限的角色执行；设计师只能发起、准备或交接 |
| 增减项 | 内部审批与客户正式确认分离；Web 可以展示影响和推进交接 |
| 选材确认 | 设计师维护选材文本；客户正式确认沿用业主端/正式确认路径 |
| 代录 | 只有正式规则允许的代录场景才能使用；必须记录代录人、原始确认人、渠道、时间、原因和证据 |

硬性限制：

- `Signed` 与 `Effective` 分离，只有生效合同可以创建项目。
- 未接受报价不得进入正常合同主链。
- 选材确认不改变报价、合同、成本和库存数量。
- 采购已锁定后不得直接换材，必须按 `BR-009` 引导发起增减项。
- 所有正式动作仍需服务端权限、状态机和幂等校验。

### Q5 `ProjectSupport` 是正式员工角色还是岗位能力？

**答复：不作为第 8 类正式员工角色。**

正式员工角色维持：

```text
Boss / StoreManager / TeamLeader / Marketer / Designer / Pm / Finance
```

`ProjectSupport` 定义为：

- 履约/材料岗位工作台能力；
- 项目参与关系和任务责任；
- 按项目、门店、团队和采购/材料职责授予的操作权限；
- 不进入员工基础角色数量、组织角色选择和通用角色切换。

Web 实现要求：

- 删除或收口 `ProjectSupport` 作为独立 `EmployeeRole` 的业务语义。
- 履约/材料工作台通过能力、项目参与关系和职责加载。
- 现有代码兼容字段如暂时无法删除，只能作为过渡，不得继续扩展为新角色。
- 后端、Web、App、报表和测试的正式角色口径统一为 7 类员工角色。

若业务后续确需独立员工角色，必须重新调整 `rules.md`、角色枚举、权限矩阵、邀请、组织、统计、Provider 和验收基线，不能只改 Web 菜单。

## 3. 锁定结果

产品设计可以冻结以下内容：

- 设计师转化工作空间为 Web P0 第一个垂直样板。
- 页面主链锁定为：客户与房屋 → 设计版本 → 报价版本对比 → 客户反馈与异议 → 合同交接 → 增减项影响 → 选材确认。
- 客户沟通在 Web 中是内部准备、记录、跟进和交接，不是消息渠道。
- P0 不新增正式沟通对象和状态机，使用 `CustomerFollow` 扩展和已有版本对象引用。
- AI 谈单辅助整体保持 P1。
- 正式客户确认和合同生效仍按正式权限执行。
- `ProjectSupport` 不新增为第 8 类员工角色。

## 1. 业务问题

- 当前场景：装得清微信小程序已经正式上线，平台运营端目前主要围绕租户、订阅、套餐、审计、系统状态展开，缺少小程序用户、渠道、激活、内容、触达、反馈、发布和数据闭环。
- 用户/角色：平台运营主管、客户成功、市场增长、平台负责人、审计合规；间接影响装企 Boss、员工和业主。
- 现有处理方式：运营动作主要依赖人工整理、静态页面、平台日志、订阅调整和外部表格；小程序端已有登录、邀请、订阅消息、使用进度和项目反馈，但未形成跨企业运营工作台。
- 希望解决的问题：让平台能够完整观察并运营“访客进入 -> 身份建立 -> 企业注册/加入 -> 角色激活 -> 首单对齐 -> 付费/续费 -> 反馈改进 -> 新版本发布”的小程序生命周期，同时不越权、不伪造业务状态、不把运营数据当成经营结果。

## 2. 涉及条件

- 主对象：小程序匿名访问事件、微信身份、手机号绑定身份、企业注册/邀请、角色激活投影、小程序内容、运营消息任务、运营活动、小程序产品反馈、发布记录、实验/功能开关、平台运营任务。
- 关联对象：Company、Employee、Credentials、Customer、Property、Quote、Contract、Project、CustomerFeedback、Subscription、SiteLead、PlatformUser、PlatformOperationLog。
- 当前/目标状态：当前没有统一的小程序运营对象与状态；目标是新增平台运营域状态，不新增或覆盖租户业务状态。
- 组织与数据范围：平台独立组织、部门、用户和权限；租户数据仅通过 `TenantDataAdapter` 或平台只读投影读取；不得建立平台表与租户表外键。
- 权限：需要新增小程序运营读、内容发布、消息发送、活动发布、反馈处置、发布确认、实验开关、导出等动作权限；高风险动作是否必须双人复核需裁决。
- 金额/成本/指标：试用转付费、续费、回款、AI 点数等沿用现有订阅和点数口径；小程序活跃、激活、角色激活、首单对齐、内容点击、消息送达等需要冻结公式、分母、时间窗和缺失值处理。

## 4. 候选方案

详细推荐口径见主方案第 15 章“GAP-013 / GAP-014 / GAP-019 专项处置建议”。

1. 先建设只读运营闭环：事件采集、用户/渠道聚合、激活队列、反馈工单、发布记录和审计，不开放批量营销和业务写入。
2. 在只读闭环稳定后，再开放受控内容、站内消息、微信一次性订阅消息、运营活动和功能开关，全部带审批和回滚。
3. 不建设独立 CDP、广告投放平台、微信客服聊天库或租户业务第二状态机。

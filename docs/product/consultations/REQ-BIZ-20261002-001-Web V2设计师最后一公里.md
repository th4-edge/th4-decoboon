## 1. 业务问题

用户已确认 Web 端允许比 App 更重，并明确设计师的设计、报价、合同、增减项、选材和客户沟通是 Web“最后一公里”转化能力。当前正式知识存在以下边界：

- `SOL-004` 将报价解释、异议话术、会后摘要和跟进建议列为 P1，尚未实现和验收。
- 当前 Web 产品技能默认客户沟通和业主确认首选 App/业主端，Web 只做内部查看和记录；用户希望把客户沟通纳入 Web 核心能力。
- 客户沟通轮次、客户反馈、异议和承诺目前没有冻结的正式对象或状态。
- Web 代码存在 `ProjectSupport`，与项目固定 7 类员工角色规则冲突。

## 2. 涉及条件

- 主对象：Customer、Property、Measure、Requirement、Design、Talk、Quote、ProjectContract、ContractChange、MaterialSelection、MaterialPlan。
- 候选沟通事实：展示版本、客户反馈、异议、设计师回应、承诺事项、下一步、责任人和截止时间。
- 组织范围：Company/Store/Team/Self/ProjectParticipation。
- 金额边界：客户沟通不得改变报价、合同、成本、利润、选材和采购事实；正式变化必须走对应业务动作。
- 跨端边界：Web 与 App 的状态、金额、责任人和下一步必须同源。
- 审计边界：谁记录、何时记录、客户原话与设计师判断如何区分、如何撤回和纠正。

## 3. 需要业务智能体回答

1. Web 客户沟通是设计师内部准备、展示记录、异议管理和跟进中心，还是直接承担客户消息触达？客户正式接收和确认在哪个端？
2. 是否新增正式“沟通轮次/客户反馈/异议/承诺”对象？P0 能否先只使用 `CustomerFollow`、`DesignRequirement`、`TalkPlan` 和版本快照做只读投影？
3. `SOL-004` 的报价解释、异议话术、会后摘要和跟进建议在 Web 属于 P0 还是 P1？人工模板与 AI 草稿的边界是什么？
4. 报价接受、合同签署/生效、增减项确认、选材确认分别在哪个端完成？Web 是否允许代录，需要什么证据和审计？
5. `ProjectSupport` 是正式员工角色还是岗位能力？如果保留，如何同步角色、数据范围、Provider 权限、报表和 Web 验证脚本？

## 4. 候选建议，需业务裁决

- P0 先按“Web 负责沟通准备、展示组织、反馈记录和跟进推进；客户正式接收与确认走 App/业主端”实现只读投影和记录，避免直接新增消息渠道。
- 在正式对象冻结前，不新增前端沟通状态机，不把客户口头反馈自动转换为报价接受、合同同意或选材确认。
- AI 谈单内容仅作为待审核草稿，必须标记来源和不可承诺边界。
- 维持固定 7 类员工角色，将履约/材料作为岗位能力或项目参与关系；如需正式新增角色，必须全链路同步调整。

## 5. 影响与截止时间

- 影响的模块：Web 设计师工作台、客户与房屋对象页、设计/报价/合同/变更/选材、跨端通知、数据权限和验收。
- 不确认会阻塞：设计师最后一公里 G1、客户沟通对象、Web 消息边界、角色导航和 Provider 设计。
- 最晚决策时间：任何页面编码或 Provider 扩展前。

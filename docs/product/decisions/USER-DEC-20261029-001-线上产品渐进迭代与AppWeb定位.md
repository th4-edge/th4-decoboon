# USER-DEC-20261029-001 · 线上产品渐进迭代与 App/Web 定位

- 决策日期：2026-10-29
- 决策人：用户
- 状态：`APPROVED`
- 类型：产品定位、跨端职责、迭代方式、负责人角色梳理边界
- 影响范围：负责人域、后续全角色梳理、App/Web 功能规划、原型与研发计划

## 1. 用户确认

1. 装得清是线上产品，产品迭代必须保留连续性和过渡过程，不能以新版原型全盘否定既有设计。
2. App 的定位是手机端高频使用：
   - 方便、快捷、时效性强；
   - 适合现场、外出、即时查看与处理；
   - 不追求承载完整复杂的桌面交互视图。
3. Web 的定位是电脑端低频、深度使用：
   - 有设备和应用门槛，使用频率相对较低；
   - 适合完整信息、复杂交互、批量处理、比较、对账和深度操作。
4. 当前 App 底部 `工作台 / 客户 / 项目 / 财务 / 我的` 已从一定角度覆盖装企完整业务，是成立的现有产品基础。
5. 当前负责人 Web/App 设计和交互已经满足基本装企需求。
6. 本次角色梳理的目标不是更换交互视角或重构信息架构，而是：
   - 细化真实业务场景；
   - 落地具体业务流程；
   - 验证现有功能是否完整、正确、可恢复；
   - 以增量方式补强产品价值。

## 2. 强制约束

- 不把五域经营台、对象抽屉或岗位内切换作为默认生产改造前提。
- 不删除、重命名或替换现有 Web 菜单、App 五 Tab、专业页面和深链。
- 新增能力优先采用“原位增强、追加入口、渐进披露”，不得先更换用户路径。
- App 继续优先高频、快捷和时效；Web 继续优先完整、复杂和对账。
- App/Web 的业务事实、权限、状态和金额仍必须同源。
- 任何界面改版必须先列出：
  1. 当前用户习惯；
  2. 真实问题证据；
  3. 最小改动；
  4. 回滚路径；
  5. 用户验证方式。
- 未经过真实场景核验的“新视角”只能作为探索稿，不得进入生产研发。

## 3. 对负责人梳理的执行要求

负责人梳理改为：

```text
现有产品能力盘点
→ 真实角色场景细化
→ 当前功能路径核验
→ 缺口与问题登记
→ 最小增量改造
→ App 高频场景验证
→ Web 深度场景验证
→ 用户确认后发布
```

首批必须覆盖：

1. 负责人移动端高频场景：即时查看经营状态、定位风险、完成轻量处理、回读结果。
2. 负责人 Web 深度场景：跨项目比较、批量处理、财务与成本核对、组织与标准检查。
3. 既有功能负向验证：无权限、接口失败、成本不完整、状态冲突、跨门店范围。
4. 现有用户路径兼容验证：原菜单、Tab、返回路径、筛选和深链不丢失。

## 4. 明确废止的默认方向

- 废止“以五域 IA 替换现有导航”作为负责人默认改造方案。
- 废止“先做全产品新壳层，再补业务场景”的实施顺序。
- 废止“只换交互视角、业务内容不变”的展示型改版。

## 5. 后续动作

1. 建立 `BOS-C2 负责人现有产品场景细化与功能核验`。
2. 先梳理 2–4 个移动端高频场景和 2 个 Web 深度场景。
3. 每个场景核对当前页面、Provider、权限、状态、金额、异常和回读。
4. 只把验证发现转成定向修复或增量需求。
5. 在真实用户路径跑通前，不进入负责人 UI 重构。

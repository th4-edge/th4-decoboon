# 合同与增减项履约 · 业务域章程

- Domain：`contract-change`
- Owner：codex
- Created：2026-10-17
- North Star：合同生效、增减项审批与合同、任务、材料、应收和成本的同源联动形成可追溯闭环。

## 1. 业务问题

- 当前场景：合同生效后，客户提出新增、减少或替换分项；企业需要在不篡改原合同事实的前提下完成审批与履约重算。
- 谁遇到问题：设计师负责承接诉求，项目经理负责履约，Boss/店长/财务负责审批和金额结果，客户需要只读同频。
- 当前损失/风险：原合同行被直接改写、减项超当前有效剩余、待审批占用不可见、替换差额错误、任务/材料/应收不同步、历史数据被伪算、成本缺失被当成 0。
- 希望达到的结果：变更单可追溯，来源范围可计算，审批一次生效，合同/任务/材料/应收/成本同事务联动，客户只读同频，历史事实不改写。

## 2. 目标角色

| 角色 | 主要目标 | 关键动作 | 不负责什么 |
| --- | --- | --- | --- |
| 设计师 | 承接客户变更诉求并形成变更单 | 选择动作、来源分项、目标分项与工程量，提交审批 | 不审批、不修改成本可见范围 |
| 项目经理 | 反馈现场事实并协助代录 | 在数据范围内代录、执行新增/减项后的任务和材料 | 非默认发起人、不审批 |
| Boss | 控制合同与履约风险 | 审批、查看全额与成本 | 不替代业主线下意愿表达 |
| 店长 | 审批本店变更并看经营结果 | 本店审批、查看本店数据 | 不跨店审批 |
| 财务 | 核对金额、应收与成本 | 审批范围内变更、核对合同额/应收/成本 | 不决定客户选材内容 |
| 客户/业主 | 知悉本人项目的变更结果 | 只读查看“审批中/已生效”和已生效金额 | 不形成单据、不审批、无系统内确认动作 |
| System | 维持范围、金额、状态与联动 | 计算当前有效剩余、校验并发、生成派生事实 | 不自行发明业务规则 |

## 3. 本期范围

- 必须做：合同生效后的 `新增分项 / 减项 / 替换`，当前有效剩余与待审批占用，目标快照，审批生效，任务/材料/应收/成本联动，客户只读同频，幂等与越权。
- 暂时不做：报价阶段清单修订、阶段验收业主确认规则。
- 明确排除：价格单独调整入口、直接改写原报价/合同行、自动审批、自动付款、正式发布。

## 4. 主链

```text
合同生效且项目未完工
→ 设计师/授权角色选择新增/减项/替换
→ 服务端返回当前有效剩余与待审批占用
→ 形成一张 ContractChange + 多条 ContractChangeItem
→ 企业审批（Boss/财务/本店店长）
→ 同一事务更新合同额、应收、任务、材料计划、成本
→ 已生效，客户只读同频
→ 异议新建反向变更，不修改已生效事实
```

## 5. 关键不变量

1. 顶层动作只有新增分项、减项、替换；新入口不提供调价。
2. 原 `QuoteLine` 和原 `ContractLine` 永久保留，不直接改写。
3. 减项/替换按当前有效剩余并扣除待审批占用；审批时再次复核来源基线。
4. 多条明细合并为一张变更单、一次审批、一次履约联动。
5. 新增/替换目标必须来自启用 `CatalogItem` 并冻结完整目标快照。
6. 已生效不可撤回或删除；客户异议通过新建反向变更处理。
7. 业主确认不是系统事实；系统只保留发起人、时间、审批与同频结果。
8. 成本缺失时 `costComplete=false`，利润与毛利率为 `null`。
9. 并发变更使用 RedissonLock 等分布式锁，禁止数据库悲观锁。

## 6. 金额/成本/权限边界

- 金额：服务端是当前有效剩余、待审批占用、差额和合同当前额的唯一权威。
- 成本：仅 Boss/店长/财务可见；设计师/PM 不可见成本与成本变化。
- 权限：发起为设计师主责，Boss/店长/PM 可代录；审批为 Boss/财务/本店店长。
- 跨租户/数据范围：变更与派生对象继承项目 `company/store/team/owner`，伪造 ID 返回无权限。

## 7. 成功指标

- 产品：变更单一次审批生效率、客户同频可见率。
- 数据质量：超减阻断率、待审批占用冲突发现率、历史不可推导项显式阻断率。
- 业务结果：变更后合同/应收/任务/材料/成本同源一致率。
- 安全：跨企业/跨门店/越权访问 0，重复审批/重复生效 0。

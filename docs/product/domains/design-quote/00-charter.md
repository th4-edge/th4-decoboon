# 设计方案与设计报价审视 · 业务域章程

- Domain：`design-quote`
- Owner：codex
- Created：2026-10-21
- Phase：SCENARIOS_READY
- North Star：设计方案成为客户房屋下可持续编辑、可计算当前报价、可被负责人/店长/财务按数据范围审视的唯一设计事实；设计师负责推进，经营角色不靠列表猜测价格与风险。

## 1. 业务问题

- 当前场景：设计师在 App/Web 维护区域、设计分项和报价；企业负责人、店长、财务没有统一的“按设计师/房屋/客户查看当前设计报价”的 Web 视图。
- 谁遇到问题：设计师无法在任务列表快速判断“这套方案现在值多少钱”；负责人无法判断设计工作是否形成可成交报价；店长无法在本店范围内发现价格、成本和推进异常；财务无法在报价进入合同前核对成本完整性和金额结构。
- 当前损失/风险：
  - App 设计工作台卡片只有方案数、诉求、量房等执行信息，不展示价格；
  - Web `DesignSchemeRail` 只展示面积、空间数、设计项数和状态，不展示金额；
  - App 方案列表虽然读取正式报价金额，但没有报价时直接显示“待报价”，看不到方案已有的设计计算金额；
  - 现有“当前报价”筛选逻辑分散在前端，按 accepted → converted → 非 rejected 的顺序自行挑选，缺少单一服务端口径；
  - 经营角色缺少跨客户/跨设计师的设计报价审视入口；
  - 设计详情响应中存在成本字段未按角色统一裁剪的风险。
- 希望达到的结果：
  - 设计师看到“当前方案计算价”和“当前正式报价”并可直接继续设计/报价；
  - BOSS、店长、财务可在 Web 按数据范围审视设计方案、当前报价、成本完整性和异常；
  - App 和 Web 使用同一服务端读模型，不再各自猜测当前报价。

## 2. 目标角色

| 角色 | 主要目标 | 关键动作 | 不负责什么 |
| --- | --- | --- | --- |
| Designer | 推进方案并随时看到价格结果 | 编辑区域/分项；查看方案计算价；生成/继续报价 | 不看标准成本和毛利；不替客户确认报价 |
| Boss | 审视全企业设计报价质量 | 按设计师/门店/客户/房屋筛选；打开方案与报价；必要时进入编辑 | 不在审视列表中直接改金额；不绕过报价/合同主链 |
| StoreManager | 审视本店设计报价质量 | 按本店设计师/客户/房屋筛选；查看成本完整性；必要时进入本店方案编辑 | 不跨店；不在列表中直接改金额 |
| Finance | 从运营管理视角了解报价金额与成本状况 | 查看当前报价、成本完整性、价格构成和异常；发现问题后跳转现有报价/设计工作面 | 不编辑设计/报价；不产生审批、核价、退回或通过与拒绝动作 |
| TeamLeader | 审视本团队方案推进与报价 | 按团队范围只读查看 | 不跨团队；不默认获得成本或写权限 |
| Marketer | 查看本人客户的设计推进 | 只读查看方案和报价状态 | 不看成本；不编辑设计和报价 |
| Pm | 签约后理解设计/报价来源 | 只读查看与本人项目相关的方案快照 | 不参与签约前报价调整 |

## 3. 本期范围

### 必须做

1. 冻结“设计方案”“方案计算价”“正式报价”“当前报价”的对象和金额口径。
2. App 设计工作台、App 方案列表、Web 方案卡统一展示当前价格信息。
3. Web 新增面向 BOSS、店长、财务的“设计方案审视”列表，可按设计师、门店、客户、房屋、状态和异常筛选。
4. 审视详情同时展示方案价格、正式报价版本、成本完整性和阻断项；设计师不返回成本字段。
5. 当前报价由服务端统一解析，前端不得自行遍历报价并挑选。
6. 所有角色继续按 Company/Store/Team/Self 和客户负责人关系访问。
7. 列表与详情使用聚合查询，禁止逐方案查询报价和分项导致 N+1。

### 暂时不做

- 不新增设计方案状态；
- 不新增报价审批、核价、退回、通过或拒绝状态；
- 不改变报价接受、合同签署和项目立项主链；
- 审视页只读，不承担任何流程推进或审批职责；
- 不做合同变更、采购价或项目实际成本审视；
- 不重构设计编辑器、报价工作簿或 AI 效果图。

### 明确排除

- 不用方案计算价替代正式报价；
- 不用 0 成本计算毛利；
- 不把内部成本、毛利暴露给设计师、业务员、项目经理或业主；
- 不允许财务直接改设计分项或正式报价；
- 不以列表卡片操作替代进入对象工作面。

## 4. 主链

```text
客户 + 房屋
→ 量房事实
→ 设计方案（区域 + 设计分项）
→ 方案计算价（实时销售侧汇总）
→ 生成正式报价（版本快照）
→ 报价草稿/提交/接受/拒绝
→ 经营角色在设计审视视图中核对金额与成本
→ 合同前决策
→ 客户接受报价
→ 合同/项目（后续主链）
```

## 5. 关键不变量

1. 设计方案必须绑定客户与房屋；同一房屋可有多个方案，不能跨房屋混用。
2. 方案计算价 = 当前设计分项销售金额合计；正式报价金额 = 对应报价快照按折扣、税费、设计费、管理费等计算后的金额，两者必须分字段展示。
3. 一个方案可对应多个报价版本；列表中的“当前报价”必须由服务端统一返回，不能由 App/Web 各写一套选择顺序。
4. 方案或设计分项发生变化后，已有报价是否过期必须由服务端依据内容修订事实判断，不能只比较更新时间。
5. 标准成本、成本和毛利只对 BOSS、店长、财务开放；其他角色响应中不返回。
6. 成本缺失或待补时，毛利和毛利率必须为 `null`，显示“成本未完整”，禁止用 0 替代。
7. 经营角色的“审视”仅为数据查看，不新增状态、待办或写动作；发现问题后回到现有设计/报价/成本工作面处理。
8. 所有列表、详情、筛选、计数和聚合必须使用同一数据范围。

## 6. 金额/成本/权限边界

- 金额：
  - `designCalculatedAmount`：当前设计分项销售金额合计，实时重算；
  - `quoteAmount`：当前正式报价的客户可见金额；
  - `subtotal`、`discount`、`taxAmount`、`designFee`、`managementFee` 作为报价构成字段；
  - “当前价格”优先展示正式报价；无正式报价时展示方案计算价并明确标注。
- 成本：
  - `costAmount`、`costComplete`、`grossProfit`、`grossMargin` 仅 BOSS、店长、财务可见；
  - 设计师只看销售价和销售金额；
  - 成本不完整时利润与毛利率不得计算。
- 权限：
  - 设计师只能写本人负责方案；
  - BOSS 企业范围，店长本店范围，财务按既有总部/门店范围；
  - 经营角色的审视页默认只读，进入编辑必须有单独动作和明确提示；
  - 财务在既有数据范围内只读查看销售金额、成本和毛利，不产生审批类动作；具体字段展示以角色裁剪规则为准。
- 跨租户/数据范围：
  - 跨企业、跨门店、跨团队和他人客户方案统一返回 403/404；
  - 不接受前端传入的 companyId/ownerId 作为授权依据。

## 7. 成功指标

- 产品：
  - 设计师从任务列表 1 次点击即可看到当前价格；
  - BOSS/店长/财务可在 2 层导航内进入设计报价审视；
  - 审视详情无需跳转报价页即可回答“当前报价多少、成本是否完整、为何未形成报价”。
- 数据质量：
  - 列表价格与详情/正式报价金额一致率 100%；
  - 无正式报价时明确显示计算价，不显示“待报价=无金额”；
  - 成本不完整时伪毛利为 0。
- 业务结果：
  - 设计完成到报价生成的平均停留时间下降；
  - 经营角色在合同前发现成本/价格异常的比例可统计。
- 安全：
  - 设计师/业务员/项目经理响应中成本字段为 0；
  - 跨店、跨企业负向用例 100% 拒绝；
  - 列表接口 SQL 条数不随方案数增长。

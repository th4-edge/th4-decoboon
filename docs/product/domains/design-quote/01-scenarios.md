# 设计方案与设计报价审视 · 真实业务场景

## 场景 A：设计师在 App 现场看到方案当前报价

| 项 | 内容 |
| --- | --- |
| 使用人/角色 | 设计师 |
| 触发事件 | 量房完成、客户诉求已录，设计师在 App 中继续设计 |
| 前置条件 | 客户与房屋存在；量房完成；方案属于当前设计师 |
| 当前动作 | 在设计工作台打开当前房屋，修改区域/分项工程量 |
| 系统下一步 | 服务端重算方案计算价；卡片和方案详情同步更新金额；有正式报价时显示当前报价版本与状态 |
| 成功结果 | 设计师无需猜测价格，直接判断当前方案是否达到可谈单条件 |
| 异常/恢复 | 区域待实测、公式待修订或分项价格缺失时显示阻断标签；不把阻断项计入已计算金额并允许返回补齐 |
| 涉及对象 | Customer、Property、Measure、Design、Space、DesignItem、Quote |
| 状态变化 | 设计状态不因查看金额变化；方案推进仍使用既有 Draft/Ready/Presented/Selected |
| 金额/成本/权限 | 展示销售侧金额；不返回标准成本与毛利 |
| 证据/来源 | `BR-001`、`OBJ-005`、`DEC-062`、`DEC-063`、当前 App 设计工作台与方案列表实现 |

## 场景 B：店长在 Web 审视本店设计报价

| 项 | 内容 |
| --- | --- |
| 使用人/角色 | 店长 |
| 触发事件 | 周经营复盘或客户即将谈单，店长需要检查本店设计报价质量 |
| 前置条件 | 店长有本店数据范围；方案至少完成区域和部分分项 |
| 当前动作 | 打开 Web「设计方案审视」，按设计师、客户、房屋、设计状态和“成本未完整/待补尺寸/客户驳回”筛选 |
| 系统下一步 | 列表展示当前正式报价；无正式报价时展示方案计算价；对成本未完整、报价过期、客户拒绝等情况生成风险标签 |
| 成功结果 | 店长找出本店需要设计师补齐或重新报价的方案，并进入方案工作区处理 |
| 异常/恢复 | 跨店请求返回 403/404；部分数据读取失败显示“暂不可确认”与重试，不显示 0 元或空列表 |
| 涉及对象 | Design、DesignItem、Quote、Employee、Customer、Property |
| 状态变化 | 审视只读不改变状态；进入方案编辑后沿用既有编辑状态机 |
| 金额/成本/权限 | 查看销售金额、成本、毛利；成本不完整时利润为 `null` |
| 证据/来源 | `BR-028`、`DEC-065`、`DEC-075`、当前 Web `DesignSchemeRail` 与 BOSS/店长路由 |

## 场景 C：财务在报价进入合同前核价

| 项 | 内容 |
| --- | --- |
| 使用人/角色 | 财务 |
| 触发事件 | 设计师提交正式报价前，财务需要确认金额、成本和异常 |
| 前置条件 | 财务在其总部/门店数据范围；正式报价已生成 |
| 当前动作 | 在 Web「设计方案审视」打开方案，查看报价金额、折扣、税费、成本完整性和设计分项构成 |
| 系统下一步 | 展示正式报价与方案计算价的差异，标记成本未完整、报价过期、分项价格缺失等风险 |
| 成功结果 | 财务确认该报价是否具备进入合同前决策的数据基础 |
| 异常/恢复 | 成本或报价接口失败时显示“暂不可确认”，禁止显示利润 0；未定价分项引导设计师/财务从各自工作面补齐 |
| 涉及对象 | Design、DesignItem、Quote、QuoteLine、CatalogItem |
| 状态变化 | P0 只读，不新增“财务审核通过/驳回”状态；是否允许标记核价待裁决 |
| 金额/成本/权限 | 财务可看成本与毛利；不能编辑设计或报价 |
| 证据/来源 | `BR-003`、`DEC-016`、`DEC-065`、`DEC-075` |

## 反向场景

- 越权：设计师访问他店/他企业方案必须 404/403；财务不能跨店；业务员只能看本人客户。
- 重复提交/幂等：审视页没有写动作；后续若增加核价反馈，重复提交必须幂等并保留审计。
- 跨租户/跨项目：方案必须同时匹配客户、房屋和租户；外部伪造 designId 不得泄露价格或成本。
- 数据缺失：没有量房、没有区域、没有分项、没有报价时分别说明缺什么，不能统一显示“暂无数据”。
- 状态不满足：设计 Draft 不能直接生成正式报价；报价 Accepted/Converted 后方案锁定。
- 金额/成本不完整：待补尺寸、公式待修订、成本缺失、显式 0 成本、正式报价过期必须分别识别；禁止用 0 成本计算毛利。

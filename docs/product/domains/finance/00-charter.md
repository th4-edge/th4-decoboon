## 1. 业务问题

### 1.1 当前场景

装得清已经把应收、收款、退款、应付、付款、费用、资金台账、项目成本、结算、工资提成和凭证等能力做进了 App/Web/后端，但这些能力目前主要以“财务菜单 + 独立列表 + 独立表单”的方式累积，财务角色实际上横跨：

- 企业资金与往来；
- 项目成本、利润与结算；
- 客户回款与信用风险；
- 报价成本、合同付款计划与变更影响；
- 材料下单、到场、结算与供应商应付；
- 费用报销、工资提成与付款；
- 经营分析、风险处置与凭证归档。

当前把“角色入口”和“业务域归属”混在一起，导致 `/finance/*` 同时承载财务专业能力、材料能力、报价能力、项目能力和薪酬能力，页面重复、对象重复、动作重复。

### 1.2 谁遇到问题

| 使用者 | 当前问题 |
| --- | --- |
| 总部财务 | 需要跨门店看经营与资金，但首屏更像功能目录，难以三秒判断“今天先处理哪笔钱、哪个项目、哪个风险” |
| 门店财务 | 需要在本店完成记账、对账、材料结算和薪酬协同，但入口受企业级/门店级语义混杂影响 |
| 企业负责人 BOSS | 财务是经营管理的重要抓手，但当前财务页面与经营总览、项目、材料、薪酬之间缺少统一事实链 |
| 店长 | 允许本店记账和处理部分高危动作，但财务页面的读写层级、只读薪酬边界和高危动作提示不够稳定 |
| 其他业务角色 | 与财务的交接常停在“提交了”“付款了”，缺少可回读的下一步、影响对象和责任人 |

### 1.3 当前损失与风险

1. **角色认知成本高**：财务打开后先看到菜单和大量卡片，而不是待回款、待到付、成本不完整、异常流水等经营问题。
2. **业务事实被页面割裂**：同一项目在项目页、项目账本、应收、应付、台账、凭证之间多入口并存，容易重复对账或张冠李戴。
3. **能力复用不足**：材料下单、报价、客户、项目等跨域能力在财务壳层重复投影，未来每增加一种角色或入口就会再复制一套。
4. **口径信任风险**：汇总页与列表页可能使用不同聚合口径；成本、利润、现金流容易被混读。
5. **动作风险**：作废、更正、冲正、付款、退款、结算、质保释放等高危动作与普通编辑动作并列，缺少统一安全门与回读。
6. **跨端风险**：App/Web 对同一角色、同一业务能力的入口、字段、状态和异常恢复不一致。

### 1.4 希望达到的结果

财务角色不再是“财务菜单集合”，而是一个可复用的经营控制面：

```text
经营事实
→ 发现异常/待办
→ 进入同一业务对象
→ 执行当前唯一主行动
→ 回读财务与业务结果
→ 交接下一责任人
```

同一业务能力在 App/Web、BOSS/总部财务/门店财务/店长之间复用同一 Provider、同一领域对象、同一状态机、同一金额/成本口径和同一错误恢复路径；页面只按角色任务和数据范围投影。

## 2. 角色定义

### 2.1 角色口径

装得清只有一个固定员工角色 `Finance`：

```text
Finance + 默认总店 → 总部财务 → Company 数据范围
Finance + 非默认门店 → 门店财务 → Store 数据范围
```

BOSS 是内部岗位能力超集，但不是新的财务角色；店长拥有本店记账能力和部分高危动作，但不是财务角色。不得新增“企业财务”“门店财务”重复角色。

### 2.2 财务角色的三层职责

| 层级 | 财务职责 | 典型能力 | 边界 |
| --- | --- | --- | --- |
| 财务专业主责 | 对资金、往来、成本、利润、结算和凭证事实负责 | 应收、收款、退款、应付、付款、费用、台账、期初、对账、成本完整性、结算、凭证 | 不做税务、法定会计、发票管理、完整 HR |
| 业务经营共管 | 对影响经营结果的业务动作提供财务控制 | 客户回款风险、报价成本、合同付款计划、合同变更影响、材料下单与结算、供应商主数据、报价项目库 | 不替代设计师、项目经理、业务员做专业决策 |
| 经营观察与行动 | 从财务视角发现经营异常并推动责任人处置 | 现金、账龄、成本不完整、低毛利、超预算、逾期、异常现金流、收入成本背离 | 指标必须可追溯；口径未冻结时不得显示确定金额 |

### 2.3 目标角色与权限范围

| 角色 | 主要目标 | 关键动作 | 不负责/不得越界 |
| --- | --- | --- | --- |
| 总部财务 | 在全企业范围控制资金、往来、成本和经营风险 | 查看全企业、按门店下钻、记账、收付款、费用、结算、材料下单与结算、凭证 | 不做法定会计/税务；不作废更正冲正重记；不能最终确认/作废工资单；不能做企业治理和角色放开 |
| 门店财务 | 在本店范围完成记账和财务经营协同 | 本店记账、收付款、费用、结算、材料下单与结算、凭证 | 不看跨店合计；不做高危冲正/作废/更正；不能最终确认/作废工资单 |
| BOSS | 对企业全部经营结果负责 | 财务内部能力超集，可执行财务高危动作、薪酬最终确认与正式治理动作 | 不能冒充业主/客户确认；不能跳过状态机和审计 |
| 店长 | 负责本店经营和本店记账 | 本店普通记账、部分本店高危动作、查看本店经营与薪酬构成 | 不做跨店操作；不能最终确认/作废/发放员工工资；不作企业治理 |
| 其他员工 | 仅使用其业务角色能力 | 提交费用、办理业务、查看被授权信息 | 不访问财务读写能力，不查看成本/利润等敏感字段 |

## 4. 业务主链

```text
业务来源事件
（合同生效 / 合同变更 / 采购下单 / 费用审批 / 工资单确认 / 提成确认）
→ 形成应收或应付义务
→ 收款、付款、退款、冲正或费用支付
→ 核销往来并写资金台账
→ 按项目/门店/企业归集成本与收入
→ 计算项目成本完整性与毛利
→ 项目结算/质保释放
→ 生成凭证并归档
→ 经营分析、异常处置、下一责任人交接
```

横向控制链：

```text
数据范围/角色权限
→ 来源唯一性与幂等
→ 金额/成本/利润口径
→ 安全门/审计/回读
→ App/Web 同源
```

## 5. 关键不变量

1. **角色不等于业务域**：财务可见能力不等于都归 `/finance`，跨域能力必须复用原领域对象与工作面。
2. **一笔业务只写一次事实**：应收≠收入、应付≠成本、付款≠成本、收款≠收入确认。
3. **来源决定对象**：能追溯到合同、变更、采购、工资、提成、费用的金额必须走来源单据，禁止手工绕开。
4. **资金事实不可物理删除**：冲正、退款、作废、更正必须保留原事实、原因、操作人、前后快照和幂等键。
5. **成本不完整不计算伪利润**：任一应计成本缺失时 `costComplete=false`，利润与毛利率为 `null`，页面显示“成本未完整”。
6. **历史快照不回写**：合同、报价、采购、工资、结算、凭证采用当时快照；后续主数据变化不得回写冻结事实。
7. **服务端裁决权限和范围**：前端入口只做可见性；总部财务、门店财务、店长、BOSS 的数据范围统一由服务端计算。
8. **跨端同源**：同一能力必须同一 Provider、同状态、同金额、同权限、同错误与同恢复路径。
9. **确定性开放**：口径未冻结、数据缺失、接口失败、字段不完整时显示“暂不可确认”，不得用 0、空数组或旧值伪装事实。
10. **页面复用以对象和任务为中心**：先选页面母型，再组合能力，不从数据库实体生成 CRUD 页面。

## 6. 金额/成本/权限边界

### 6.1 金额

- 应收余额 = 应收金额 − 已收金额；
- 应付余额 = 应付金额 − 已付金额；
- 未结清应收/应付、逾期和账龄使用服务端口径；
- 收款、付款、退款、冲正、核销和凭证金额均取服务端事实；
- 前端不得自行计算正式余额、利润、毛利率或经营结果。

### 6.2 成本与利润

- 项目成本按预计、动态、最终三态区分；
- 项目毛利与毛利率由 `ProjectCostContext` 唯一计算；
- 企业费用不进入项目毛利；
- 公司/门店经营利润仍受 `GAP-070` 和 `MET-007/011` 约束，口径冻结前不得展示确定金额；
- 已确认结算不得无痕重算，历史差异走新版本或调整事实。

### 6.3 权限

- 查看财务与单据：BOSS、总部财务、门店财务、店长（限范围）；
- 新增/编辑应收、收款、应付、付款、台账、结算、质保释放、期初：BOSS、总部财务、门店财务、店长（限范围）；
- 手工流水作废、更正/冲正重记和收款冲正：BOSS/总部财务全企业、门店财务/店长本店（`DEC-099`）；
- 薪酬最终确认/作废/退回：BOSS；
- 薪酬复核和员工工资/提成发放：BOSS、财务，按薪酬规则；
- 店长只读本店薪酬构成，不得确认、作废、发放；
- 财务可维护报价项目库、客户经营、供应商主数据、材料下单与结算，具体边界按 `DEC-079/080/084`。

### 6.4 跨租户与数据范围

- 企业和门店只能从登录员工加载；
- 总部财务 Company 范围；门店财务/店长 Store 范围；
- 跨企业、跨店、跨项目或无效记录返回 403/404，不泄露存在性；
- 门店筛选是展示维度，不是授权本身；
- 门店财务和店长不得通过筛选、深链、导出、选择器或并发探测看到跨店合计。

## 7. 成功指标

### 7.1 产品指标

- 财务现有菜单逐项完成“角色—页面—功能—回读”验收，每项结论可追溯。
- 财务打开首屏后 3 秒内能回答：现金是否安全、今天先处理什么、哪个项目成本不完整、下一步找谁。
- 任一财务待办都能进入唯一业务对象工作面，动作完成后能回读往来、台账、成本和状态。
- 同一能力在不同角色的页面复用同一 Provider 和业务对象，不新增同义 API。
- 财务专业页面与其他业务域页面职责清晰：财务域只拥有财务事实，不复制客户/报价/合同/项目/材料/薪酬工作面。
- 现有布局、菜单、页面职责、深链和 App Tab 在升级后保持兼容。

### 7.2 数据质量

- 应收、应付、收付款、台账、凭证和项目账本的同对象金额可相互解释；
- 来源缺失、重复来源、成本不完整、账龄待确认、历史门店为空等异常显式呈现；
- 所有派生数字带截止时间、范围、口径和缺失值处理。

### 7.3 业务结果

- 逾期应收减少、待付计划更可预测、资金缺口更早发现；
- 项目成本不完整项更快归零；
- 财务与业务人员的交接从“口头通知”转为可回读动作；
- 门店财务和总部财务在同一套口径下协同。

### 7.4 安全

- 跨租户/跨店/越权负向用例通过；
- 高危动作 100% 有原因、审计、幂等和回读；
- 接口失败、无权限、真实空态、部分失败和冲突态可区分。

## 10. 章程结论

财务域的第一性问题不是“还缺哪些财务功能”，而是：

> **财务角色如何在不复制其他业务域的前提下，成为企业经营事实的控制面、解释面和行动面。**

本域后续所有需求、蓝图、页面、Provider 和验收，必须同时回答：

```text
这个能力归哪个业务域主责？
财务是主责、共管、监控还是只读？
它使用哪个现有对象和 Provider？
它在什么角色任务中投影成什么页面？
动作完成后回读什么事实、交给谁？
```

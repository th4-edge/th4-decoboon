## 0. 结论先行

### 0.1 当前问题的根因

当前 `/finance/*` 同时承载了五种不同性质的内容：

1. **财务专业能力**：应收、收款、应付、付款、费用、台账、凭证、结算；
2. **跨域经营能力**：客户、报价项目库、合同付款计划、项目核算、材料下单与结算、薪酬；
3. **经营观察能力**：现金、账龄、成本完整性、利润参考、门店经营；
4. **单据/档案能力**：凭证、模板、打印、重打；
5. **设置能力**：分类、账户、供应商主数据、标准成本、期初。

把这些内容都当作“财务菜单项”后，系统必然出现：

- 同一对象多入口：项目在项目页、项目账本、应收、应付、台账、凭证中重复出现；
- 同一动作多页面：收款/付款/退款/冲正/费用/工资分散为多个列表和抽屉；
- 角色投影复制业务域：客户、报价、材料、薪酬各自在 `/finance` 下又长一套页面；
- 页面语法不统一：指标卡、表格、三栏工作面、抽屉和设置表单混用；
- 用户不知道先做什么：首页像功能目录，不像经营控制台；
- 复用无法成立：新增门店、角色、端或能力时只能继续复制。

### 0.2 应该建立的统一模型

```text
企业业务域（主责对象和事实）
        +
角色任务投影（谁在什么场景看什么、做什么）
        +
统一页面母型（驾驶舱 / 队列 / 对象 / 账本 / 单据 / 档案 / 设置）
        +
共享交互原语（对象身份、金额、状态、证据、安全门、回读）
        =
可复用的财务经营工作台
```

核心判断：

> **业务域决定事实归属，角色决定任务投影，页面母型决定交互复用。**
> 不能再用 URL 前缀或菜单分组来决定业务域。

## 1. 财务角色的完整定位

### 1.1 一句话职责

> 财务是企业经营事实的控制者、解释者和行动推动者：确保钱、往来、成本、利润、结算和凭证可追溯，并用这些事实推动业务责任人完成下一步。

### 1.2 财务不等于“会计软件操作员”

财务角色在装得清中承担三层职责：

| 层级 | 回答的问题 | 核心能力 | 交付结果 |
| --- | --- | --- | --- |
| 经营控制 | 钱是否安全、经营是否有风险 | 现金、账龄、预算外的成本缺口、异常流水、逾期应收/应付 | 今日行动与风险处置 |
| 业务核算 | 每单赚不赚钱、钱是否收付清楚 | 合同收入、应收、收款、应付、付款、费用、材料成本、人工成本、结算 | 项目经营结果 |
| 业务协同 | 业务动作是否按财务边界发生 | 客户回款、报价成本、合同付款、变更影响、材料下单/结算、供应商主数据 | 跨角色交接与闭环 |

### 1.3 时间尺度上的工作

| 时间 | 财务需要回答 | 主要工作面 |
| --- | --- | --- |
| 每天 | 今天先处理哪三笔钱/哪三个异常 | 财务经营台、回款队列、付款队列、异常流水 |
| 每周 | 哪些客户/项目/供应商在恶化 | 账龄、项目成本完整性、供应商往来、材料结算 |
| 每月 | 费用、薪酬、资金和项目结算是否闭合 | 费用报销、薪酬发放、月度对账、项目结算 |
| 每季/经营复盘 | 哪些门店/项目/客户在赚钱，哪些在拖累经营 | 经营分析、门店/公司经营结果、风险与目标 |

## 2. 企业业务域全景

### 2.1 企业价值主链

```text
获客与线索
→ 客户与房屋
→ 量房与设计
→ 报价
→ 合同与变更
→ 项目立项与履约
→ 材料与供应链
→ 验收与交付
→ 财务经营与结算
→ 经营分析与复购
```

### 2.3 跨域规则

1. 一个业务对象只能有一个主域和主源。
2. 财务可以拥有业务动作权限，但不能因此复制对象页面。
3. 跨域页面必须复用原域的 Provider、字段、状态机和错误语义。
4. 财务只增加视角、筛选、字段裁剪、角色动作和回读范围，不新建同义 API。
5. 如果某能力确实由财务主责但对象属于其他域，机制应为“财务操作面板嵌入原对象工作面”，而不是新开 `/finance/<object>`。

## 3. 财务能力架构

### 3.1 能力分级

| 级别 | 含义 | 财务权限 |
| --- | --- | --- |
| M | 主责管理 | 可创建、修改、确认、关闭，按状态机和危险级别执行 |
| O | 共同操作 | 在授权范围内参与业务动作，但不改变业务域主事实 |
| C | 控制/核对 | 可检查、阻断、退回、标注异常，但不拥有业务决策 |
| V | 观察分析 | 只读；不得修改或伪造来源 |
| X | 明确排除 | 不承载，不得出现在产品承诺中 |

## 4. 财务核心业务对象与事件模型

### 4.1 核心模型

```text
业务来源事件 SourceEvent
  ├─ 合同生效/变更
  ├─ 采购下单/到场/结算
  ├─ 费用审批
  ├─ 工资单确认
  └─ 提成确认
        ↓
财务义务 Obligation
  ├─ Receivable（应收）
  └─ Payable（应付）
        ↓
资金运动 CashMovement
  ├─ Receipt（收款）
  ├─ Payment（付款）
  ├─ Refund（退款）
  └─ Reversal（冲正）
        ↓
核销与分配 Allocation
  ├─ 收款 → 应收
  ├─ 付款 → 应付
  └─ 费用/工资/材料 → 项目/企业成本
        ↓
不可变资金流水 Ledger
        ↓
业务凭证 Voucher / 档案
        ↓
经营快照 Snapshot
  ├─ ProjectCostContext
  ├─ Settlement
  └─ Company/Store Operating Reference（待冻结）
```

### 4.2 对象主源

| 业务事实 | 唯一主源 | 财务使用方式 | 禁止做法 |
| --- | --- | --- | --- |
| 合同金额/变更 | `ProjectContract`、`ContractChange` | 形成应收基线、付款计划和收入口径 | 在项目/财务页面手填合同额 |
| 应收 | `Receivable` | 回款计划、余额、逾期、账龄 | 用收款记录反推或前端汇总 |
| 收款 | `Receipt` | 核销应收、写台账、生成凭证 | 用项目已收字段手填 |
| 应付 | `Payable` | 付款计划、余额、逾期、成本线索 | 把付款、采购价直接当成本 |
| 付款 | `Payment` | 核销应付、写台账、生成凭证 | 重复付款或前端修改余额 |
| 费用 | `Expense` | 审批、唯一应付、付款、成本归属 | 手工企业费用绕过费用闭环 |
| 资金流水 | `Ledger` | 现金流、账户余额、凭证来源 | 物理删除或前端补算 |
| 成本 | `ProjectCostContext` | 预计/动态/最终成本和毛利 | 前端公式或 0 成本兜底 |
| 结算 | `Settlement` | 项目最终经营结果和质保 | 直接改已确认结算 |
| 凭证 | `Voucher` | 打印、重打、归档 | 重打生成新凭证号 |
| 薪酬 | `PayrollSheet` / `PayrollItem` | 复核、应付、发放 | 将工人工资 Payable 冒充员工工资 |
| 提成 | `CommissionItem` | 计提、释放、发放、负向调整 | 与工资混成不可追溯金额 |
| 发票 | `Receivable.invoiceRequired/invoiceNo` 及附件（待正式裁决） | 只作元数据/证据 | 发票管理、查验、税额计算、进项抵扣 |

| 来源事件 | 自动形成/更新 | 是否写资金流水 | 财务页面应回读 |
| --- | --- | --- | --- |
| 合同生效 | 合同收入基线、应收计划、预计成本 | 否 | 项目核算、应收计划、成本完整性 |

### 4.4 状态与动作原则

- 状态名以业务事实源、代码和迁移三方核对结果为准；本蓝图不新增状态。
- 页面必须从服务端读取状态，不得在前端推导完成度。
- 主行动必须由当前状态、角色、数据范围、来源、余额和完整性共同决定。
- 任何动作完成后必须回读：对象状态、金额/余额、下游对象、审计事件、下一责任人。
- 状态不满足时，页面显示阻断原因和恢复路径，而不是隐藏入口造成“系统没反应”。

## 5. 页面投影体系

### 5.1 页面存在理由

一个财务页面只有同时满足以下条件才允许存在：

1. 它回答一个角色的一个明确问题；
2. 它围绕一个有唯一身份的业务对象；
3. 它有一个与当前状态匹配的唯一主行动；
4. 它能回读动作后的业务事实；
5. 它能交给下一责任人或继续处理下一对象；
6. 它不是另一个页面的列表复制或字段复制。

## 6. 页面信息结构与交互规则

### 6.1 驾驶舱页

首屏只回答四个问题：

1. 现金是否安全？
2. 今天最需要处理的收入/支出/风险是什么？
3. 哪些项目成本或利润暂不可确认？
4. 唯一主行动是什么？

建议信息层级：

```text
L1 结论带：现金安全 + 最大风险 + 今日主行动
L2 解释层：回款、付款、成本完整、异常流水四组证据
L3 明细层：对象队列、时间趋势、来源和口径说明
```

禁止：

- 用四张同权重 KPI 卡片作为首屏主体；
- 把“功能入口”当“经营结论”；
- 在首屏放设计说明、口径长文、英文 eyebrow；
- 图表没有一句话结论。

### 6.2 行动队列页

```text
左侧/上方筛选 → 中间对象/账本 → 右侧状态引导 → 安全门/回读
```

必须显示：

- 当前范围（全部门店/单店）和数据截止时间；
- 筛选条件、结果数量、清除筛选；
- 对象身份（项目/客户/供应商/员工）；
- 金额、到期日、状态、责任人、来源；
- 当前唯一主行动及其前置条件；
- 批量动作的影响范围。

### 6.3 对象工作面

财务对象工作面统一为：

```text
对象身份条
→ 当前财务结论
→ 当前主行动
→ 金额/往来/成本事实
→ 来源链与证据
→ 相关业务对象
→ 审计与历史
```

前三项必须在首屏可见；来源链和历史默认折叠。任何对象工作面都不以“完整字段表”作为主体。

### 6.4 账本/对账页

账本不是实体 CRUD 表格，而是“核对与行动”的工作台：

- 列按财务判断优先：对象、期间、应收/应付、已收/已付、未结、到期、来源、责任人、状态；
- 支持按项目、客户、供应商、门店、期间、来源、状态筛选；
- 支持冻结对象身份列和批量选择；
- 行点击进入对象工作面，而不是先跳无上下文详情；
- 批量动作前显示影响金额、门店、来源和凭证条件；
- 不允许前端分页后自行汇总全量数据。

### 6.5 事务单据

收款、付款、退款、费用、结算、期初、发放共用同一单据壳层：

```text
业务上下文头
→ 影响对象与金额
→ 关键字段
→ 来源与证据
→ 风险/完整性提示
→ 唯一主行动
→ 提交中/成功/失败/冲突
→ 回读结果与下一交接
```

长表单分段，失败保留输入；高风险动作进入安全门。

### 6.6 七类 UI 状态

| 状态 | 财务页面要求 |
| --- | --- |
| 正常 | 结论、金额、状态、截止时间、来源可确认 |
| 加载 | 布局稳定；长加载说明当前阶段 |
| 空 | 区分未创建、筛选无结果、无业务待办 |
| 失败 | 说明失败对象、保留上下文、提供重试/替代路径 |
| 无权限 | 说明角色/范围原因和申请路径，不伪装空数据 |
| 长内容 | 长名称、多项目、多来源可展开；主对象不丢失 |
| 极端值 | null、0、负数、超大金额、跨年、超多条目可解释；不用 0 代替未知 |

## 9. 与现有页面的差异结论

### 9.1 当前页面事实

- Web 财务相关页面 22 个，App 财务子包页面 23 个；存在多套列表、抽屉、对象页。
- Web 财务菜单当前按“今日 / 客户 / 资金收付 / 往来与账本 / 凭证与归档 / 报价与成本 / 薪酬 / 项目核算 / 帮助”组织，注册 24 个菜单项（含客户、报价项目库、材料、薪酬、帮助等跨域入口），角色能力被菜单化。

```text
+ 现有收款/付款/费用/薪酬入口（逐项验收）
+ 现有资金台账/项目核算/凭证入口（逐项验收）
+ 现有客户/报价/材料/设计等跨域入口（按角色保留）
+ 共用客户/报价/合同/项目/材料/薪酬对象事实
```

> 本结构描述能力关系，不是要新建或替换页面。是否原位优化，必须以菜单验收结论和用户确认为准。

### 9.3 不应继续做的事

- 为每个实体新增一个 `/finance/*` CRUD 列表；
- 为每个角色复制一套业务对象详情；
- 用卡片墙代替结论；
- 用多个 KPI 卡片代替行动队列；
- 用前端本地状态或金额计算补足服务端缺口；
- 在高危动作和普通编辑之间使用同一视觉层级；
- 把材料、报价、薪酬对象复制到财务域后再做“同步”。

## 12. 验收门槛

在财务域可以进入页面原位优化前，必须完成：

1. 当前菜单逐项验收结论形成：角色、页面、Provider、主行动、七态、权限和回读有证据；
2. 业务冲突只登记：`FIN-Q01/FIN-Q03/FIN-Q06/FIN-Q08` 需要时由业务答复或明确阻断；
3. Provider 对账：App/Web 每个能力对应的 Provider、字段、权限、错误码和回读范围有矩阵；
4. 对象归属对账：每个页面能指向唯一主域、唯一对象、唯一主源；
5. 金额/成本口径：每个金额、余额、利润和指标有来源、公式、缺失值；
6. UI 母型冻结：驾驶舱、队列、对象、账本、单据、档案、设置七种母型；
7. 七态覆盖：正常、加载、空、失败、无权限、长内容、极端值；
8. 真实渲染：1440/1280/1024 至少各一轮截图与视觉批判；
9. 路径兼容：现有菜单、路由、深链、返回和筛选不丢失；
10. 独立验收：正向、反向、越权、重复、跨店、金额边界、成本不完整。

## 13. 结论

财务角色需要的不是“更多页面”，而是一个稳定的经营事实体系：

```text
业务域主源
→ 财务事件与义务
→ 收付款/费用/薪酬/结算
→ 台账、凭证、成本与利润
→ 经营判断与对象行动
```

页面只是这个体系的投影。只有先把业务域、能力、对象、状态、动作、回读和交接冻结，财务页面和交互才可能真正复用、稳定和可验收。

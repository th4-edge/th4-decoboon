# 财务经营与项目核算 · 渐进升级与菜单验收计划 v0.2

## 北向目标

以财务角色为经营控制面，统一项目资金、成本利润、往来核校与业务协同，形成可复用、可追溯、可交接的财务工作台体系。

## 1. 推进原则

1. **先验收、后优化、最后才判断是否需要研发**：本轮以现有布局、菜单、页面和后端为基线，不新建系统、不重做导航、不调整后端业务逻辑（`USER-DEC-20261029-007`）。
2. **一次一个入口/任务链**：Web 按菜单、App 按底部 Tab/首页快捷入口逐项完成角色、页面、功能、七态、权限、返回和回读验收。
3. **现有页面优先**：跨域能力复用原域页面/Provider；只做原位增强和渐进披露，禁止复制页面和同义 API。
4. **真实证据**：每项验收必须有真实角色、真实页面、真实 Provider、七态和回读证据；接口 200/构建通过不等于验收通过。
5. **风险分级**：本阶段只做菜单与页面验收，不改后端；发现金额/成本/利润/权限/跨店缺口时只登记，另行确认。
6. **不边做边扩**：未完成当前菜单结论，不进入下一个菜单；未经用户确认，不把验收发现扩展为后端改造。

先验 `FM-01 业务工作台`，因为它决定财务角色打开系统后是否知道“今天先处理什么”。随后按资金闭环顺序验收：

### 3.2 小程序

```text
AT-01~06 财务角色底部 Tab
→ AT-03 财务首页
```

双端验收均不直接改页面，只回答：

- 当前菜单/入口是否应该存在；
- 当前页面是否能完成财务任务；
- 当前页面是否复用了正确的业务对象和 Provider；
- 当前布局和用户路径是否需要保留；
- 最小优化是什么，是否必须另行处理后端；App 是否需要补齐，还是属于 Web 深度能力。

## 4. 依赖与顺序

```text
B0 业务域/能力体系
→ B1-W/B1-A Web 菜单与小程序入口逐项验收
→ B2 页面信息层级与交互基线
→ B3 按菜单原位最小优化
→ B4 升级后回归与 App/Web 对照
→ B5 后端缺口另行裁决（不默认进入）
```

可并行但不建议的项：

- 真实 UI 视觉基线与业务文档同步；
- Provider 字段对账与页面母型设计；
- App/Web 的同源字段矩阵与组件清单。

不得并行：

- 在菜单/入口验收前改导航、Tab 或页面结构；
- 在页面基线前重做财务首页；
- 在用户确认前修改后端逻辑；
- 在 Provider 对账前复制页面；
- 在 `GAP-070/071` 未解决前上线确定利润；
- 在 UI 安全门冻结前上线高危动作。

## 5. 每批退出条件

每批必须满足：

1. 业务来源和未决问题明确；
2. 对象、状态、动作、权限和金额口径有来源；
3. App/Web 字段对账完成；
4. 真实页面/接口证据完成；
5. 七态覆盖；
6. 正向、反向、越权、重复、跨店、边界验证；
7. 完成后回读下游对象；
8. 对账矩阵无本批 `UNMAPPED/STALE`；
9. 状态、历史和下一动作已回写。

## 6. 回滚与止损

- 文档批次：可直接回退文档提交，不影响运行；
- 页面批次：保留旧路由/深链和默认入口，功能开关或兼容路由退出；
- Provider 批次：不得改变既有字段语义；如需新增字段，保留兼容别名并做旧数据回归；
- 金额/成本/权限批次：必须具备备份、回归、回滚路径和用户确认；
- UI 改版：优先在现有页面内做兼容式改造，不一次性删除旧导航；
- 同一指标连续 2 次优化无改善则停止该类优化，重新端到端测量；
- 视觉改造超过 3 轮仍未达到 3 分门槛，回到信息架构和任务链重审。

# 客户页面规则冻结候选 v2

- 日期：2026-10-29
- 状态：`PENDING_USER_VALIDATION`
- 修订原因：用户指出 Web 不应采用三栏对象工作面，客户页面应采用角色化客户卡片场景，参考小程序客户 Tab 的统计、分组和卡片信息层级
- 替代：`15-customer-page-rule-freeze-candidate-v1.md`
- 约束：只冻结产品规则，不进入页面编码，不调整后端逻辑

## 1. 核心理解

> 客户页面不是传统后台对象页，也不是左中右三栏工作面，而是围绕不同角色场景组织的客户卡片页面。

客户是装企内部最重要的业务桥接点：从客户可以识别人员归属、客户阶段、经营变化，并进入设计、报价、合同、项目和财务业务链。

客户页面的阅读顺序应是：

```text
角色场景统计
→ 数据范围与查询条件
→ 客户归属分组
→ 客户卡片
→ 客户详情/业务链/下一步
```

而不是：

```text
左侧对象列表
→ 中间客户 360
→ 右侧动作栏
```

## 2. 冻结规则

### R1 客户页面是全员的客户查询入口

所有内部角色都可以查询客户，但受现有租户、组织、数据范围、客户关系和字段权限约束。

```text
可查询 ≠ 可看全部字段
可查询 ≠ 可做全部动作
可查询 ≠ 可跨门店/跨租户
```

### R2 客户页面采用客户卡片场景，不采用三栏布局

Web 和小程序均以客户卡片为主工作单元。客户卡是桥接点，不是简单实体列表项。

客户卡片负责：

- 识别客户；
- 识别客户归属和协同人员；
- 识别当前阶段、风险、最近/下次跟进；
- 识别当前业务链摘要；
- 显示当前用户可进行的下一步；
- 点击进入客户详情和业务链。

### R3 不同角色必须有不同场景投影

客户页面不是所有角色共用一套统计和一套卡片。

角色投影至少包括：

- 场景统计；
- 默认筛选；
- 客户归属分组；
- 客户卡业务摘要；
- 当前主行动；
- 只读协同信息；
- 数据范围。

### R4 企业负责人和店长使用同一客户经营口径，但数据范围不同

#### 企业负责人

- 关注全企业客户变化，用来感受当前经营情况；
- 可查看全部门店，也可按门店下钻；
- 展示客户经营统计；
- 按客户负责人/业务员分组；
- 客户卡显示负责人、设计师、阶段、风险、跟进、报价/签约/项目摘要和下一步。

#### 店长

- 同样关注客户经营变化，但只看本店；
- 需要补充本店客户统计；
- 按本店客户负责人/业务员分组；
- 统计公式与企业负责人保持一致，数据范围收窄为本店；
- 不得看到其他门店或跨店合计；
- 页面必须明确“本店口径”。

#### 数据口径原则

```text
同一指标定义
+ 不同数据范围
+ 不同比较范围
≠ 每个角色一套指标算法
```

### R5 客户深度绑定业务员，负责人分组是核心结构

客户归属负责人/业务员是客户经营的主要组织维度。

负责人分组应展示：

- 负责人；
- 客户数；
- 风险客户数；
- 待跟进数；
- 已签约/项目客户数；
- 本组客户卡。

企业负责人看全企业负责人分组；店长看本店负责人分组；业务员看本人客户；设计师、项目经理、财务等按客户关系或业务链投影，不默认套用销售负责人分组。

### R6 客户卡片必须承担“桥接点”职责

客户卡片至少包含四层信息：

#### 身份层

- 客户姓名；
- 手机号（按权限脱敏）；
- 小区/地址；
- 客户阶段；
- 客户等级/风险。

#### 关系层

- 负责人/业务员；
- 设计师；
- 项目经理；
- 归属门店；
- 当前责任人。

#### 经营层

- 最近跟进；
- 下次跟进/停留天数；
- 报价/签约/项目摘要；
- 当前业务链状态；
- 角色相关财务/项目摘要（按权限）。

#### 行动层

- 当前下一步；
- 唯一主行动；
- 阻断原因；
- 进入客户详情/关联业务。

### R7 角色场景投影

| 角色 | 统计 | 默认分组/筛选 | 客户卡重点 | 主要动作 |
| --- | --- | --- | --- | --- |
| 企业负责人 | 全企业客户经营统计 | 全部门店/单店；负责人分组 | 阶段、风险、负责人/设计师、跟进、签约/项目、下一步 | 查看、进入对象、处理经营阻断 |
| 店长 | 本店客户经营统计 | 本店负责人分组 | 本店阶段、风险、负责人/设计师、跟进、签约/项目、下一步 | 查看、转交、指派、处理本店阻断 |
| 财务 | 财务相关客户统计 | 全企业或本店；财务关注筛选 | 合同、项目、应收、待收/逾期、当前财务责任 | 查看应收、登记收款、相关业务协同 |
| 业务员 | 我的客户工作统计 | 本人客户/跟进状态 | 跟进、量房、报价、签约、下一步 | 写跟进、预约量房、维护客户 |
| 设计师 | 我的设计客户工作统计 | 本人/被指派客户 | 房屋、量房、设计、报价、下一步 | 进入设计、推进方案 |
| 项目经理 | 项目关联客户统计 | 我的项目客户 | 项目、工地、阶段、验收、下一步 | 进入工地、推进工序/验收 |

> 角色动作是否可用仍由服务端能力投影决定，本表不新增权限。

### R8 客户详情是卡片下钻，不是三栏工作面

客户卡片点击后进入客户详情：

- 客户身份与协同人员；
- 多房屋；
- 当前房屋业务链；
- 跟进时间轴；
- 当前角色主行动和下一步。

客户详情可以采用页面、抽屉或标签区，但不得把 Web 首页重新变成左中右三栏工作台。

### R9 客户详情展示业务链摘要，不复制专业工作台

业务链包括：

```text
量房 → 设计 → 报价 → 合同 → 项目/工地 → 验收 → 收付款
```

客户页只显示状态、责任人、更新时间、金额摘要和入口。专业编辑仍在对应业务页面完成。

### R10 有操作能力的人看下一步，无操作能力的人看协同信息

有动作：

```text
客户卡 → 当前主行动 → 阻断原因 → 完成回读 → 交接
```

无动作：

```text
客户卡 → 客户业务链摘要 → 当前责任人 → 可查看的专业工作面
```

### R11 Web 是对小程序场景的桌面增强，不是另一套信息架构

Web 采用相同的业务阅读顺序：

```text
统计 → 范围/搜索/筛选 → 负责人分组（适用角色） → 客户卡片 → 客户详情
```

Web 的增强只体现在：

- 更高信息密度；
- 更多列卡片网格；
- 批量选择和批量处理；
- 多条件筛选；
- 排序和对比；
- 键盘操作；
- 导出/打印；
- 横向业务链对比；
- 更完整的客户详情页。

Web 不采用：

- 三栏对象工作面作为客户首页；
- 大而全的客户 360 替代客户卡片；
- 复制 Boss KPI 卡墙给所有角色；
- 只按实体字段生成表格。

### R12 客户页面不复制专业工作面

不承载：

- 设计方案编辑；
- 报价编辑；
- 合同签约；
- 项目施工；
- 验收整改；
- 财务台账与结算。

### R13 保留现有路径

- 财务保留现有「客户」菜单和 `/workbench/customers`；
- 不新建 `/finance/customers`；
- 保留现有客户、房屋、跟进、转交、指派等深链；
- 本阶段不调整后端逻辑、权限、金额、成本、状态机或 DDL。

### R14 Web 与小程序同事实

两端共用：

- 客户身份；
- 客户归属；
- 客户阶段；
- 负责人/设计师/项目经理；
- 跟进；
- 业务链摘要；
- 角色动作投影；
- 错误语义和回读。

布局可以不同，事实和口径必须一致。

## 3. 企业负责人客户 Tab 的可复用结构

```text
客户经营标题
→ 角色统计
→ 门店范围
→ 搜索
→ 负责人分组
→ 阶段/跟进筛选
→ 排序
→ 客户卡片
```

客户卡片：

- 姓名、阶段、等级；
- 风险；
- 负责人、设计师；
- 小区、面积、预算；
- 上次跟进、停留、下次跟进；
- 报价/签约金额、项目；
- 下一步。

## 4. 店长客户 Tab 的补强思路

当前小程序店长客户 Tab 复用了非 Boss 的普通列表逻辑：

- 有门店范围；
- 有跟进任务统计；
- 有阶段筛选；
- 没有企业负责人那种客户经营统计；
- 没有本店负责人分组。

应补强为：

```text
本店客户统计
→ 本店负责人分组
→ 搜索/阶段/跟进筛选
→ 本店客户卡片
```

统计与企业负责人同口径，但数据范围锁本店。

## 5. 财务客户页面的场景投影

财务客户页面采用同一客户卡片体系，但卡片重点不同：

```text
客户身份
+ 负责人/设计师/项目经理
+ 当前阶段
+ 合同/项目摘要
+ 应收/待收/逾期摘要
+ 当前财务责任人
+ 当前财务下一步
```

财务页面首层统计建议围绕：

- 有合同客户；
- 有项目客户；
- 有应收客户；
- 待收客户；
- 逾期客户。

统计是否已有服务端数据，需要菜单验收和 Provider 对账；没有则登记 `BACKEND_GAP`，不在前端手算或伪造。

财务主行动优先级：

1. 当前客户有逾期/待收 → 查看应收/登记收款；
2. 当前客户已签约未立项 → 查看合同和项目阻断；
3. 当前客户项目在途 → 查看项目财务/下一收款节点；
4. 当前客户无财务业务 → 只读业务链和协同人；
5. 客户资料影响财务流程 → 维护客户资料（如现有权限允许）。

## 6. Web 布局方向

```text
┌────────────────────────────────────────────┐
│ 页面标题 + 角色场景说明 + 数据范围         │
├────────────────────────────────────────────┤
│ 角色统计：3–5 个，不是通用 KPI 卡墙         │
├────────────────────────────────────────────┤
│ 搜索 + 门店范围 + 阶段/跟进/业务筛选 + 排序 │
├───────────────┬────────────────────────────┤
│ 负责人分组     │ 客户卡片网格/列表            │
│（仅适用角色）  │ 身份、关系、经营、下一步      │
└───────────────┴────────────────────────────┘
点击客户卡 → 客户详情（房屋、业务链、跟进）
```

这里最多是“分组导航 + 卡片主区”两区，不是三栏工作面。

## 7. 需要用户验证的判断

1. 客户页面以客户卡片为主，采用“统计 → 查询/筛选 → 负责人分组 → 客户卡”的小程序思路，而不是三栏布局。
2. 企业负责人有全企业客户经营统计和负责人分组。
3. 店长需要本店客户经营统计和本店负责人分组，指标定义与企业负责人一致，数据范围不同。
4. 客户深度绑定业务员，负责人分组是负责人/店长角色客户经营的主要组织方式。
5. 财务客户页采用同一客户卡片体系，但卡片重点转为合同、项目、应收/待收/逾期和财务下一步。
6. 客户卡点击进入客户详情与业务链，不在客户首页展开专业工作台。
7. Web 仅做桌面密度、批量、筛选、对比、排序和导出增强，不另起一套信息架构。
8. 本阶段保留现有客户菜单、路由和 Provider，不改后端逻辑。

## 8. 本轮不做

- 不新建三栏客户工作台；
- 不新建 `/finance/customers`；
- 不修改现有后端；
- 不重新设计全站导航；
- 不在规则确认前开始视觉设计。

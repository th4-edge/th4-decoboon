## 3. 当前 UI 审查

### P0：品牌与产品识别不一致

1. Web 壳层仍使用单字“装”作为品牌标记：
   - `th4-decoboon-web/src/layouts/RoleAreaShell.vue`
   - 违反 `rules.md` §12：不得用“装/清”单字方块冒充 Logo。
2. App 品牌主色为 `#16A394`，Web 品牌主色为 `#2f7d5a`。
   - 可以保留端侧明暗差异，但必须是同一品牌色系；
   - 当前缺少成文的 Primitive / Semantic / Component Token 层级，容易被感知为两个产品。

### P0：负责人能力超集被直接映射成 UI 导航

- BOSS 权限上是内部岗位能力超集；
- 当前 Web BOSS 菜单与首页仍混有店长、团队视角卡片；
- 用户会在“负责人经营台”和“岗位工作台集合”之间来回切换；
- 应由“经营总览 + 业务对象 + 亲自处理”替代“所有岗位入口平铺”。

### P1：字阶过小，长期使用成本高

- Web 多个壳层与业务页面仍出现 11px 文本；
- App 大量标签使用 `18rpx` / `20rpx`，在 375px 设备约 9–10px；
- 这些字号适合作品集展示，不适合高频企业工作台；
- 建议：正文 14–16px，辅助文字最小 12px；移动端输入框 16px，避免 iOS 自动放大。

### P1：卡片过多，层级同质

- App 有 145 个页面/子页面使用 `jz-card`；
- Web 30 个视图出现 card / panel / surface 组合；
- 卡片本身不是问题，问题是“每个 section 都是同权重卡片”；
- 会导致负责人无法快速区分主任务、支持信息和历史信息。

### P1：列表表达不稳定

- App 首页混合统计卡、快捷入口、项目卡、风险事件和经营动态；
- Web 工作台混合 Hero 卡、工作台入口卡、事实条和 KPI；
- 同一业务集合没有稳定使用 table / row list / card list / feed 中的一种；
- 需要通过 layout recipe 固化集合模式。

### P1：错误态被空数据吞掉

App 存在多处：

```ts
catch(() => [])
catch(() => null)
catch { value = [] }
```

例如门店选择、项目详情关联数据、业主旅程等。  
风险：

- 服务失败被显示成“没有数据”；
- 与“业务真实为空”混淆；
- 负责人无法判断是数据缺失、无权限还是接口故障。

### P1：主行动数量不稳定

- Web 静态扫描存在大量 `type="primary"` / primary class 引用；
- 不代表同一屏全部可见，但需要逐页验证“一屏一个主行动”；
- 业务动作应靠近对象，不应全部堆在页面右上角。

### P1：Token 漂移

静态扫描当前约发现：

- App 205 个色值字面量/片段；
- Web 468 个色值字面量/片段。

数字包含渐变、状态色与部分片段，不能直接等同于缺陷数量，但说明页面和组件仍存在绕过 Token 的风险。  
目标不是“零 hex”，而是所有界面色必须能映射到语义 Token。

### P2：数据可读性不足

- 金额、数量、比例、日期缺少统一的等宽数字和右对齐规则；
- 状态标签颜色种类多，文字层级与颜色层级不稳定；
- 图表缺少统一单位、基准线和缺失态表达。

### P2：跨端与可访问性基础设施不足

- 当前生产壳层没有统一 dark / light 主题；
- 没有统一语言切换机制；
- 焦点态、触控高度、移动端底部导航和抽屉恢复行为未形成统一组件规则。

## 4. 我会怎样重设计

### 4.1 视觉方向

```text
Engineering operations console
+ 经营台账的可信感
+ 深色矿物表面
+ 单一生机绿强调
```

不是通用蓝紫 SaaS，不是玻璃拟态，不是传统 ERP。

### 4.2 页面结构

| 页面 | Layout | 目标 |
| --- | --- | --- |
| 经营总览 | `dashboard-overview` | KPI、负责人决策、经营信号、事件流 |
| 业务推进 | `data-table-workspace` | 对象队列、阶段、责任人、风险、下一步 |
| 项目对象 | object workspace | 对象身份、唯一主行动、任务、关系、观测、时间线 |

### 4.3 三条交互原则

1. **管理先于执行**：负责人先看结果、风险、责任人，不先选择岗位功能。
2. **对象先于岗位**：需要亲自处理时，从客户/项目/资金对象进入，在对象内切换业务员、设计师、项目经理或财务方式。
3. **事实先于样式**：金额缺失、成本未完整、利润口径未确认时，不填 0，不造确定值。

## 5. Dig UI Token 摘要

### Dark

```css
--dig-bg:#06121a;
--dig-bg-soft:#0b1b26;
--dig-surface:rgba(11,27,38,.82);
--dig-text:#ecf3f8;
--dig-text-muted:#8aa0b2;
--dig-accent:#37d67a;
--dig-border:rgba(138,160,178,.16);
```

### Light

```css
--dig-bg:#f2f6f3;
--dig-surface:rgba(255,255,255,.9);
--dig-text:#0b1d16;
--dig-text-muted:#52665b;
--dig-accent:#159c63;
--dig-border:rgba(11,29,22,.13);
```

### 规则

- 主/次按钮、输入、筛选控件使用 pill；
- 最小触控高度 44px；
- 面板圆角 16px，大面板 24px；
- 12px 为最小辅助文字，正文 14–16px；
- 状态不能只靠颜色；
- 一屏一个主行动；
- 不使用卡片嵌套卡片。

## 7. 验证结果

- 1440×1000、1024×900：三页无页面级横向溢出。
- 390×844：手机壳层完整，内容在手机内部滚动。
- 浏览器控制台：0 error / 0 warning。
- 可见文字：无小于 12px 的文本。
- 主题、语言、页面、抽屉、角色动作交互通过。
- 键位焦点可见。
- 页面按 `dashboard-overview`、`data-table-workspace` 和对象 workspace 结构组织。

## 8. Dig 工具链说明

- 未修改 Dig catalog 或 render 资产，因此不需要同步 catalog render。
- 运行 `npm run validate:renders` 时，当前安装的 Dig UI skill 自身报告缺少 `SKILL.zh-CN.md`、`references/*.zh-CN.md`、`references/local/styles/.gitkeep` 等本地化资产。该问题属于共享 skill 安装完整性，不是本原型页面错误。
- 本交付按本地可用的 Dig Markdown 规则完成页面 preflight。

## 9. 下一步迁移建议

1. 先以本原型确认 visual language 和 owner IA；
2. 固化 Token 到 App/Web 的唯一设计源；
3. 把当前三个样板页拆成可复用 blocks；
4. 按页面模板迁移：
   - 客户经营；
   - 设计报价；
   - 合同签约；
   - 项目履约；
   - 材料变更；
   - 验收整改；
   - 财务与组织；
5. 每页完成 1440/1024/390 渲染、截图和状态评审后才能进入正式 UI 验收。

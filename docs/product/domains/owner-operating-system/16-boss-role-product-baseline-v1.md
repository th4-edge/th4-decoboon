> 日期：2026-10-29  
> 基线：本地集成版 `1.0.73`（后端 `ce5f295`、Web `ef56107`、App `f2fb91e`）  
> 状态：`CURRENT_STATE_AUDITED / PROTOTYPE_READY_FOR_REVIEW / USER_DECISION_PENDING`  
> 性质：角色、业务能力、信息架构和跨端现状对账；不是代码修改，不是 UI 验收，不是业务验收，不代表已发布。  
> 关联问题：`PI-20261029-001`  
> 业务事实：`BR-028`、`BR-030`、`CAP-004`、`CAP-005`、`SCN-016`、`MET-002/004/005`、`GAP-070`

## 1. 本次梳理结论

装得清当前已经向企业负责人提供了较完整的内部业务能力，问题不在“缺一大片功能”，而在四件事尚未收口：

1. **权限能力被直接映射成导航结构**：BOSS 在权限上是内部岗位能力超集，但负责人工作台不应等价于业务员、设计师、项目经理、财务菜单的并集。
2. **负责人首屏分裂**：App 已有“指标 + 风险项目 + 经营动态”的负责人首页；Web 首页仍是通用场景卡片，独立经营总览页面又没有明确导航入口。
3. **同一角色不同事实入口**：App 首屏消费 `statistic/boss/workbench`，Web 经营总览消费 `statistic/boss/business/report`，两端尚未形成一张经过字段对账的负责人经营工作面。
4. **“有入口”仍不等于“能判断和处置”**：部分页面展示对象总量或模块入口，但没有完整回答负责人当前最关心的问题：发生了什么、影响什么、谁负责、下一步做什么、失败后怎么恢复。

因此，BOSS 产品改造的正确起点不是继续堆功能，而是先冻结：

```text
负责人经营总览
→ 业务对象与阻断
→ 亲自处理
→ 动作后回读
```

岗位能力继续保留，但岗位切换应从“一级导航”降为“对象上下文中亲自处理的方式”。

## 2. 角色定义

### 2.1 一句话职责

> 企业负责人不是所有岗位的操作员，而是对企业经营结果、关键阻断、资金成本、组织责任和企业标准负责的人。

### 2.2 负责人持续回答的五个问题

| 问题 | 对应空间 | 核心事实 |
| --- | --- | --- |
| 今天最需要处理什么？ | 经营总览 | 风险、超期、待决策、经营变化、数据新鲜度 |
| 业务停在哪里、谁负责、下一步是什么？ | 业务推进 | 客户、设计、报价、合同、项目、材料、变更、验收 |
| 钱和成本是否健康？ | 企业经营 | 签约、回款、应收、应付、成本完整性、项目毛利、目标 |
| 企业按什么标准做下一单？ | 经营标准 | 报价库、模板、主数据、单据模板 |
| 谁在什么范围做什么？ | 组织管理 | 企业、门店、员工、邀请、权限、交接、审计 |

### 2.3 明确边界

- BOSS 可以在本企业 Company 范围执行内部岗位能力超集，但必须保持原业务状态机并逐步留痕（`BR-028`）。
- BOSS 不能冒充业主确认、客户签认或平台运营。
- 成本不完整时，项目毛利和毛利率不得展示确定值。
- 公司/门店经营利润在 `GAP-070` 关闭前只能显示“口径待确认”，不得展示确定金额。
- “负责人视角”不是新增角色，也不是新增权限；它是同一身份、同一权限下更符合经营决策的信息组织方式。

## 3. 真实业务场景

本节复用负责人域已确认的场景，不另造业务规则。

### 场景 A：多店负责人处理今日经营阻断

- 使用人：多门店装企负责人。
- 触发：早上打开工作台，需要判断今天先处理什么。
- 当前动作：查看签约、回款、风险项目、逾期应收、材料超领、变更异常，选择一个对象处置。
- 系统下一步：给出服务端事实、风险原因、责任人、唯一主行动和动作后回读结果。
- 异常：部分数据失败、成本不完整、利润口径未确认时必须显式展示，不能用 0 或空数组兜底。
- 业务依据：`SCN-016`、`BR-030`、`MET-002/004/005`。

### 场景 B：一人装企负责人连续完成一单

- 使用人：一人装企负责人，同时承担业务、设计、项目、财务内部动作。
- 触发：新客户咨询并要求当天量房、尽快报价。
- 当前动作：在同一对象上下文内切换业务员、设计师、项目经理、财务的“亲自处理方式”。
- 系统下一步：身份和能力范围不变，业务状态逐步推进，每一步保留操作人和动作。
- 异常：不得因同一人操作而跳过报价接受、合同生效、项目立项、业主确认等节点。
- 业务依据：`BR-028`、`BR-030`、`CAP-005`。

### 场景 C：负责人在移动端处理现场阻断

- 使用人：外出的企业负责人。
- 触发：收到材料未到场、任务延期或变更待处理提醒。
- 当前动作：在 App 查看经营指标、风险项目、责任人和下一步，进入对象完成允许的动作。
- 系统下一步：Web 打开同一对象时显示同一状态、金额、责任人和时间线。
- 异常：弱网、接口失败、权限不足、对象已变化时必须显示恢复路径，不得伪装空态。
- 业务依据：`SCN-016`、`CAP-004`、一后端多客户端同源规范。

## 4. 目标信息架构

### 4.1 负责人一级空间

```text
经营总览
业务推进
企业经营
经营标准
组织管理
```

这五个空间是负责人的“观察和判断层”，不是新增业务对象。

### 4.2 三层工作面

```text
L1 经营层：结论、风险、目标、数据新鲜度
L2 对象层：客户 / 项目 / 合同 / 应收 / 员工等业务对象
L3 执行层：当前状态下的唯一主行动、岗位执行方式、完成后交接
```

### 4.3 App / Web 的合理差异

| 维度 | Web | App |
| --- | --- | --- |
| 默认目标 | 经营判断、比较、批量、对账、组织治理 | 今日判断、移动处置、现场回读 |
| 信息密度 | 高密度表格、趋势、并列比较 | 单任务优先、风险优先、少层级 |
| 交互 | 多栏、批量、键盘、打印导出 | 点击直达、底部导航、弱网恢复 |
| 能力边界 | 同一 Provider、同一权限、同一状态、同一金额 | 同一 Provider、同一权限、同一状态、同一金额 |

“交互不同”不能成为一端能力缺失、只读替代写、字段不一致或异常恢复缺失的理由。

## 6. 当前问题清单

### BOSS-R0-F01 · P1 · Web 负责人首页角色错位

- `HOME_WORKBENCHES.Boss` 第一条为“本店经营结果”，场景文案写的是“店长查看本店……”。
- BOSS 打开 Web 首页即可能看到店长语义，破坏角色认知和负责人经营入口可信度。
- 结论：进入研发前必须先冻结负责人首页卡片/IA，不应直接修文案了事。

### BOSS-R0-F02 · P1 · 负责人首屏分裂

- App：负责人工作台 = 经营指标 + 风险项目 + 经营动态。
- Web：主页 = 通用场景卡片；经营分析 = 漏斗、转化、渠道、区域。
- 两端没有一个共同的“今天最重要的事实 + 风险 + 下一步”首屏模型。
- 结论：需要 BOSS 统一经营总览，而不是继续维护三套首屏。

### BOSS-R0-F03 · P1 · 同一角色、不同首屏 Provider 尚未对账

- App 首屏使用 `statistic/boss/workbench`。
- Web 经营总览使用 `statistic/boss/business/report`。
- 并非要求两个接口相同，但必须明确：哪些字段是同一事实、哪些是不同分析口径、两端在哪里显示同一对象和状态。
- 结论：建立 BOSS Provider/字段对账矩阵后再改页面。

### BOSS-R0-F04 · P1 · 部分补充数据失败被空态吞掉

- App 负责人首页对材料计划、业务承接等补充数据使用 `catch(() => [] / null)`。
- 风险：接口失败可能被显示成“没有数据”，与真实业务为空混淆。
- 结论：首屏必须区分真实空、接口失败、无权限和部分数据暂不可确认。

### BOSS-R0-F05 · P1 · 负责人默认导航仍是岗位菜单并集

- Web 当前依赖 `业务工作台 / 客户经营 / 商务财务 / 项目工地 / 经营分析` 等分组进入大量岗位页面。
- 这保留了功能可达性，但不符合“经营总览 → 业务对象 → 亲自处理”的负责人主模型。
- 结论：保留深链和专业工作面，重组默认入口；不删除业务能力。

### BOSS-R0-F06 · P1 · 内容获客缺少 Web 负责人入口

- 当前能力清单 `BIZ-23`：内容获客主要是移动端，Web 无明确负责人入口。
- 结论：先作为跨端缺口登记，是否在本期补齐由负责人 IA 冻结后决定，不在本批直接编码。

### BOSS-R0-F07 · BLOCKED · 经营利润与风险阈值未冻结

- `GAP-070` 未关闭：公司/门店经营利润、费用分摊、期间、未归属门店费用口径不能确定展示。
- `GAP-BOS-002` 未关闭：负责人观测阈值是否允许企业配置尚未裁决。
- 结论：不得在首个切片中发明利润金额或阈值；可先展示已存在的事实和“口径待确认”。

## 7. 首个改造切片建议：BOS-R1

### 名称

**负责人统一经营总览（只读判断 + 处置入口）**

### 目标

让 BOSS 在 App/Web 打开后先看到同一套经营事实和同一组风险对象，并能进入现有处置工作面，而不是先面对岗位菜单全集。

### 范围内

1. 以 `statistic/boss/workbench` 为负责人首屏事实源，复用现有 App 合同，不为 Web 新建同义业务接口。
2. Web 首页调整为负责人经营总览入口；经营分析作为总览内的事实/解释层或独立下钻，不再与总览争夺默认入口。
3. 修正 BOSS 首页中店长语义卡片，不保留角色错位文案。
4. 展示签约额、回款额、项目毛利、在建项目、风险项目、经营动态、数据日期与负责人操作入口。
5. 成本不完整时继续显示“成本未完整”；金额、状态、责任人与 App同源。
6. 风险项目可进入已有 `/workbench/risk` 或对象工作面；首片不新增审批、支付、权限或业务状态机。
7. 补齐正常、加载、空、失败、无权限、长内容、极端值七态表达。

### 非范围

- 不修改公司/门店经营利润公式。
- 不新增风险阈值、金额公式、员工角色或数据范围。
- 不新增客户端专用 Provider。
- 不重构全部负责人专业页面。
- 不把现有岗位能力从 Web 删除；只调整负责人默认入口与主行动。
- 不在本片完成微信小程序正式发版。

### 前置

- 用户确认 BOSS 默认一级空间为“经营总览 / 业务推进 / 企业经营 / 经营标准 / 组织管理”。
- 用户确认“岗位视角”降为对象上下文内的执行方式，不作为负责人一级导航。
- 形成 BOSS Provider 字段对账矩阵。
- 对新增/变更字段完成业务信息项登记；无业务消费者的字段不得进入页面。

### 退出条件

- 同账号、同企业在 App/Web 首屏读取同一 `boss/workbench` 事实，签约额、回款额、项目毛利、在建项目、风险对象数量和更新时间可对账。
- Web 首页不再出现店长语义卡片。
- 任一风险对象可进入既有风险队列或对象工作面，返回后保留筛选和上下文。
- 成本不完整、接口失败、无权限、空队列四类状态不混淆。
- Web 1440/1280/1024 真实渲染与 App 目标设备渲染证据齐全。
- 类型检查、构建、定向接口测试和跨端回读通过。
- 未完成独立验收前不宣称“负责人工作台已完成”。

## 9. 结论

负责人是当前全角色改造的基准角色。先把负责人从“内部岗位能力超集”转成“经营判断 + 对象处置 + 亲自执行”，这套模型才能复用到总部财务、店长、门店财务、设计师、业务员、项目经理和业主。

当前不宣布负责人端已完成，也不把 1.0.73 本地集成能力算作正式上线能力。

## 11. 2026-10-29 用户反馈后的兼容性纠偏

用户明确指出：`unified-v1.html` 与当前已上线产品的导航、首屏和交互路径差距过大，必须先考虑现有客户的使用习惯，不能把大改作为默认方案。

### 11.1 纠偏结论

1. `unified-v1.html` 仅保留为**方向探索和工作面样板**，不再作为生产改造的默认信息架构。
2. 不以“经营总览 / 业务推进 / 企业经营 / 经营标准 / 组织管理”五域替换现有 Web 菜单或 App Tab。
3. 保留现有 Web 角色菜单、工作台入口、专业页面、深链和 App 的 `工作台 / 客户 / 项目 / 财务 / 我的` 使用习惯。
4. 优先修复事实错误和最小闭环，不做全产品换壳。

### 11.2 推荐默认路线：兼容式 BOS-C1

```text
保留现有导航与页面
→ 修正 BOSS 首页店长语义卡片
→ 在现有首页增加负责人经营判断与风险入口
→ Web 复用 statistic/boss/workbench
→ 风险对象进入现有风险队列/业务页面
→ 真实用户走查后再决定是否调整 IA
```

### 11.3 三档改造强度

| 方案 | 是否保留现有 IA | 变更范围 | 当前建议 |
| --- | --- | --- | --- |
| A 仅修错与数据同源 | 完全保留 | 首页文案、经营入口、Provider 字段对账 | 最低风险，可先做 |
| B 现有首页内嵌经营判断 | 完全保留 | A + 首页判断带 + 风险队列入口 | **推荐默认** |
| C 五域经营工作台 | 大幅改变 | 导航、首页、对象交互、移动端结构 | 仅作研究方向，需用户走查后再议 |

### 11.4 习惯保护门禁

- 现有公众号/培训/客服话术提到的菜单名称不随意改名。
- 用户常用入口不得从原层级消失；新增入口优先追加，不替换。
- Web 继续以左侧导航和专业工作台为主，不改成单页经营大屏。
- App 继续保留现有底部 Tab；手机端不复制 Web 五域壳层。
- 首轮改造只增加信息，不迁移用户已完成的任务路径。
- 真实客户走查未通过前，不把探索稿进入生产研发。

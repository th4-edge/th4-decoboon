# 装得清产品体系基线 · 业务域章程

- Domain：`product-system-baseline`
- Owner：codex
- Created：2026-10-22
- North Star：以角色、业务域、功能、对象概念和跨端展示的同源基线，支撑产品持续扩展、变更影响识别与规则一致性

## 1. 业务问题

- 当前场景：装得清已从 0-1 形成 App、Web、后端和平台运营端的基础版本，但角色、业务域、功能、对象概念和跨端展示不断迭代，局部修改容易引发业务联动、权限口径、状态口径和页面展示不一致。
- 谁遇到问题：企业负责人、店长、团队负责人、业务员、设计师、项目经理、财务、业主，以及后续维护产品与研发的负责人。
- 当前损失/风险：同一角色在不同端的能力边界不清；同一业务事实在不同页面可能使用不同名称、状态、金额或下一步；新增功能时难以识别受影响的角色、对象、接口、页面、测试和验收范围。
- 希望达到的结果：建立一套可追溯、可对账、可恢复的产品体系基线。以后任何角色、业务域、功能、对象概念或页面变更，都能定位影响面，并经过业务事实源和跨端口径门禁。

## 2. 目标角色

本域的目标不是新造角色，而是把现有角色事实拆成可对账的层：

| 角色/主体 | 主要目标 | 关键动作 | 不负责什么 |
| --- | --- | --- | --- |
| 企业负责人 Boss | 看经营、管组织、控资金与关键风险 | 全企业内部能力超集；关键审批、资金、治理 | 不能替代业主本人验收；不能跳过状态机 |
| 店长 StoreManager | 独立经营本门店 | 本店客户、设计、报价、合同、项目、材料、财务、员工与经营分析 | 不自动获得企业治理；不跨店 |
| 团队负责人 TeamLeader | **角色冻结，仅历史兼容** | 不新增应用能力；存量账号处置走专项问题 | 不再作为后续产品目标角色 |
| 业务员 Marketer | 获客、登记、跟进与转化 | 客户、房屋、跟进、预约量房、内容获客 | 不负责最终报价、签约和资金确认 |
| 设计师 Designer | 量房、设计、报价和签约发起 | 量房、设计、报价、谈单、合同发起、项目协作 | 不确认合同生效；不确认财务收付 |
| 项目经理 Pm | 现场履约与验收推进 | 接项目、计划、任务、现场留痕、材料到场、验收申请、整改 | 不修改售价和财务归属；不代业主确认 |
| 财务 Finance | 资金、台账、成本、薪酬和项目核算 | 应收应付、收付、退款、供应商往来、工资、凭证、成本 | 不自动获得工资单确认；不自动获得企业治理 |
| 业主/客户 Owner | 知晓本人项目并完成授权确认 | 查看本人项目事实、阶段验收确认、意见反馈 | 不看其他项目；不参与企业内部经营数据 |
| 平台运营 PlatformUser | 管租户、订阅和平台运营 | 跨企业只读、套餐与订阅管控 | 不进入租户业务主链，不拥有租户内部审批权 |
| 工人/供应商 | 作为履约对象被企业管理 | 当前不默认拥有租户自助账号 | 不默认为系统内登录角色 |

## 3. 本期范围

- 必须做：
  1. 建立角色分类、角色矩阵、角色 × 业务域责任矩阵、角色 × 数据范围矩阵；
  2. 盘点 App、Web、后端和业务知识库的角色事实；
  3. 识别角色命名、能力、数据范围、高风险动作和跨端展示的冲突与缺口；
  4. 为后续业务矩阵、功能矩阵、对象概念规则和跨端一致性审计提供稳定底座。
- 暂时不做：新角色、权限变更、业务状态变化、金额成本口径变更、页面重构、接口改造。
- 明确排除：正式版小程序发布；生产数据操作；对外能力承诺；没有业务裁决支撑的规则改写。

## 4. 主链

```text
角色与身份事实
→ 组织/数据范围
→ 业务责任
→ 功能与动作能力
→ App/Web 页面与展示
→ 服务端校验与审计
→ 同一业务事实回读
→ 变更影响与验收证据
```

本域不直接推进一单装修，而是治理“所有装修业务角色和事实如何被产品一致表达”。

## 5. 关键不变量

1. 角色不等于数据范围，数据范围不等于动作能力；三者必须分别建模、分别校验。
2. 持久化员工角色保留七类枚举兼容；后续产品目标为六类活跃角色，TeamLeader 冻结且不再新增应用能力。
3. 同一业务对象、状态、金额、成本、责任人和下一步，App/Web/后端必须同源同口径。
4. 每类能力在 App/Web 必须具备一致且完整的强制边界；交互可不同，能力、权限和业务结果不得缺失。
5. 材料员/履约人员统一归入财务角色，不新增第八类员工角色。
6. 普通员工不支持通用多岗；一个员工只有一个主岗位。项目责任关系不扩大员工主岗位权限。
7. Boss 是内部业务能力超集，但不包含业主确认、客户签认、平台运营等外部主体能力。
8. 店长是“业务能力对齐 + 本门店范围”，不是“缩小版 Boss”；企业治理能力仍按正式决策保留边界。
9. 门店财务与总部财务不是两个重复枚举角色；总部财务由正式组织归属和范围规则派生。
10. 页面隐藏不是权限；菜单、路由、按钮、接口、数据范围、响应字段和审计必须分层校验。
11. 没有任何角色可以在缺少前置状态、金额完整性、幂等和留痕条件时推进高风险业务节点。

## 6. 金额/成本/权限边界

- 金额：报价、合同、应收、应付、收付、退款、工资和提成均以服务端领域事实为准，前端不得重算或伪造。
- 成本：成本完整性由统一上下文判断；成本不完整时利润和毛利率返回空，禁止以 0 代替。
- 权限：`@DataPermission` 管数据范围，`@Properties` 管响应字段；二者不可互换。
- 跨租户/数据范围：企业、门店、团队、本人、项目参与关系、业主项目授权分别校验；不信任前端传入的企业、员工、负责人或门店标识。
- 高风险动作：合同生效、客户删除、财务作废/更正/冲正、工资单确认、业主验收确认必须单独纳入动作矩阵。

## 7. 成功指标

- 产品：形成一份可执行的“角色—业务域—功能—对象—跨端”基线，而不是功能清单。
- 数据质量：角色、数据范围、业务责任和动作能力都能追溯到业务编号、代码或页面证据。
- 业务结果：新增或修改一个业务点时，能明确受影响角色、对象、状态、金额、页面和验收用例。
- 安全：跨企业、跨门店、跨团队、非项目参与、无业主授权五类负向边界均可被矩阵覆盖。

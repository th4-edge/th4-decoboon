# 一人多岗与底层角色模型分析

> 日期：2026-10-22
> 状态：已冻结。用户 2026-10-22 确认“普通员工不支持通用多岗，只保留单主岗 + BOSS 超集 + 项目责任关系”。
> 结论先行：**装得清当前底层不涉及通用“一人多固定岗位”模型；它只支持“一个员工一个主岗位 + BOSS 内部能力超集 + 项目责任关系”。**

## 一、当前底层实际是什么

| 层次 | 当前模型 | 代码/业务证据 | 是否支持多岗 |
| --- | --- | --- | --- |
| 员工岗位 | `Employee.role` 是单个 `EmployeeRole` 字段 | `src/main/java/com/th4/edge/tenant/user/model/Employee.java` | 否 |
| 数据库 | `db_tenant_employee.role` 是单值枚举 | `docs/design/migrations/50-合并履约专员与财务角色.sql` | 否 |
| 数据范围 | 从当前员工唯一岗位推导 `DataScopeType` | `DataScopeContext.resolve` | 否；岗位决定默认范围 |
| BOSS | BOSS 取所有内部岗位能力的并集 | `BR-028`、`DEC-032` | 是“超集”，不是多角色关系 |
| 项目责任 | 项目分别保存 designer、manager、support | `Project`、项目创建/更新 Provider | 是“项目责任关系”，不是员工多岗位 |
| 项目成员视图 | 从项目责任人和报价/客户关系实时派生 | `project/member/list` | 不构成独立授权真源 |
| 指定能力 | 内容运营等可作为能力授予 BOSS/店长/指定员工 | `DEC-060`、内容获客裁决 | 局部能力授权，不是通用岗位多选 |

## 二、四种容易混淆的情况

### 情况 A：只有 BOSS 一个人的装企

**已有支持。**

```text
BOSS 以单一 Boss 岗位登录
→ 获得内部岗位能力超集
→ 连续完成客户、设计、报价、合同、项目、材料、财务等内部动作
→ 每一步独立留痕，不跳过状态机
→ 仍不能冒充业主确认
```

这是当前“一人多岗”的主要业务承载方式，依据为 `BR-028`、`DEC-032`、`ANS-BIZ-20261007-020`。

### 情况 B：一个非 BOSS 员工同时担任设计师和项目经理

**当前不支持完整的双岗位权限。**

例如员工主岗位是 Designer，即使被项目指派为 `manager`，某些只按 `EmployeeRole.Pm` 判断的动作仍会拒绝；反过来主岗位是 Pm，也不能天然获得 Designer 的报价编辑能力。

项目字段可以同时指向同一员工，但这只描述项目责任，不是全局岗位授权。

### 情况 C：财务兼任材料员/履约人员

**已经有正式口径支持。**

`DEC-074` 明确“材料员与财务是同一角色”，历史 `ProjectSupport` 已通过迁移 50 统一为 `Finance`。项目 `support` 字段继续表达履约负责人，不新增第八角色。

### 情况 D：员工临时获得一项能力

**当前只存在局部能力授权，没有统一能力授权模型。**

例如内容运营可以先作为权限能力，由 BOSS/店长或指定员工兼任；但它不是所有业务域通用的“第二岗位”。

## 三、由此带来的现实影响

1. 一人装企能跑通，因为 BOSS 是显式超集。
2. 3-10 人企业若要求非 BOSS 员工同时做设计、项目、采购或财务，当前只能：
   - 把员工设为一个主岗位，再依赖该岗位已有的项目关系能力；
   - 或由 BOSS 承接缺失动作；
   - 或把员工拆成多个账号/多个员工档案，但这会破坏责任归属和审计一致性。
3. 项目成员列表不能作为“多岗位已支持”的证据，它只是责任人视图。
4. 如果未来引入通用多岗，必须新增员工-岗位关系、主岗位、生效时间、数据范围、能力并集和审批责任，不应只在前端增加角色多选。

## 四、已冻结的业务结论

用户已于 2026-10-22 确认，当前阶段正式采用：

```text
单主岗位
+ BOSS 内部能力超集
+ 项目设计师/项目经理/履约负责人责任关系
+ 少量明确的能力授权
```

当前不引入通用多岗位模型，原因：

1. 现阶段七类岗位和 BOSS 超集已能覆盖一人装企和多数小团队；
2. 通用多岗会同时改变数据范围、审批主体、动作责任、审计和菜单路由，属于高风险模型变更；
3. 项目级责任关系已经能表达“这个项目上谁负责什么”，不必把所有责任都提升为员工固定岗位；
4. 如果过早支持多岗，容易出现“同一员工同时制单、审批、收款”但责任不可解释的问题。

## 五、通用多岗若未来重新开启，最低需要新增什么

当前明确不做；以下仅保留为未来影响评估：

| 需要新增/调整 | 原因 |
| --- | --- |
| EmployeeRoleAssignment | 一个员工可拥有多个岗位及生效时间 |
| 主岗位标识 | 决定默认首页、默认数据范围和组织展示 |
| 岗位级数据范围 | 不同岗位可能有 Company/Store/Team/Self 差异 |
| 能力并集与冲突规则 | 多个岗位同时具备审批/收付能力时如何合并 |
| 审批责任选择 | 当前动作以哪个岗位身份执行，必须写入审计 |
| 前端角色切换/岗位上下文 | App/Web 需要明确当前岗位，而不是混用一个角色标签 |
| 权限负向用例 | 同一自然人多岗不能形成不受约束的自审自付 |

## 六、冻结结果

- **普通员工：不允许通用多岗。**
- **BOSS：保留内部岗位能力超集。**
- **项目设计师/项目经理/履约负责人：仅表达项目责任关系，不改变员工主岗位。**
- 后续如需变更，必须先新建业务裁决，不在现有角色模型上临时扩展。

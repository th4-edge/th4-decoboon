# 企业财务与门店财务角色支持现状分析

> 日期：2026-10-22
> 状态：现状分析，不是新业务裁决。
> 问题台账：`docs/product/issue-governance/issues/PI-20261022-001-总部财务与门店财务门店维度未闭环.md`（已从产品梳理主线剥离，进入专项会话流程）。
> 结论先行：**系统没有“企业财务”和“门店财务”两个员工角色，只有一个 `Finance`。企业财务在正式业务口径中称“总部财务”，由“财务岗位 + 归属默认总店”派生为企业范围；门店财务由“财务岗位 + 归属非默认门店”派生为本店范围。**

> 最终闭环（2026-10-23）：`PI-20261022-001` 已 `CLOSED`。业务裁决见 `DEC-081`，真实 dev App/Web 页面与独立验收 PASS，证据见 `docs/acceptance/runs/20261022-finance-organization-real/README.md` 和 `docs/acceptance/runs/20261022-finance-organization-scope/02-acceptance-record.md`。

## 一、概念定义

| 业务概念 | 系统承载方式 | 是否独立角色 | 数据范围 |
| --- | --- | --- | --- |
| 企业财务 / 总部财务 | `Employee.role = Finance` 且 `Employee.store.defaultStore = true` | 否 | Company，全企业、全部门店 |
| 门店财务 | `Employee.role = Finance` 且 `Employee.store.defaultStore = false` | 否 | Store，本企业本门店 |
| 店长记账 | `Employee.role = StoreManager` | 否 | Store；可做本店记账和部分本店高危动作 |
| 企业负责人 | `Employee.role = Boss` | 是 | Company |

关键区别：

```text
总部财务不是 Boss：数据范围相同，但企业治理和部分高危动作不同。
门店财务不是店长：记账能力接近，但店长另有本店管理、审批和高危动作边界。
```

## 二、后端数据范围实现

### 2.1 角色枚举

`EmployeeRole.Finance` 的默认数据范围是 `Store`：

```java
Finance("财务", DataScopeType.Store)
```

这说明“财务”首先被视为门店归属岗位，而不是天然企业级岗位。

### 2.2 总部财务派生

`DataScopeContext.resolve` 对财务增加了一条明确派生规则：

```text
Finance
+ store.defaultStore = true
→ DataScopeType.Company
```

因此：

- 财务归属默认总店：看全企业；
- 财务归属普通门店：只看本店；
- 财务没有门店：不成立，数据库 `Employee.store` 非空兜底；
- 单门店企业：默认总店财务的 Company 范围与该店 Store 范围等价。

### 2.3 财务域权限分层

`FinanceAccessContext` 当前大致分为：

| 能力 | 允许角色 | 数据范围 |
| --- | --- | --- |
| 财务查看 | Boss、Finance、StoreManager | 由 `DataScopeContext` 决定 |
| 普通记账 / 收款 / 付款 | Boss、Finance、StoreManager | Company 或 Store |
| 财务高危动作（作废、更正、冲正重记、收款冲正） | Boss、Finance、StoreManager | Boss/总部财务全企业；门店财务/店长本店；范围由服务端数据权限裁决 |
| 收款冲正 | Boss、StoreManager | Boss 全企业；店长本店 |
| 工资单确认 | Boss | 全企业 |
| 工资单发放 | Boss、Finance | 按数据范围 |

财务角色内部不再按“总部/门店”重复判断，范围统一由 `DataScopeContext` 派生。

### 2.4 门店维度解析

`StoreScope.resolve` 负责把请求中的门店参数与当前数据范围合并：

- Company 范围：不传 / `0` = 全部门店；传具体门店 = 该企业内任一门店；
- Store 范围：不传或传本店 = 本店；传其他门店 = 403；
- 门店筛选是查看维度，不是授权本身；
- 非法门店不静默忽略，避免误读为全部门店。

### 2.5 已有验证证据

已有后端测试覆盖：

- `FinanceStoreScopeTest`：总部财务 Company、门店财务 Store、跨店拒绝、店长记账；
- `FinanceStoreScopeHttpAcceptanceTest`：真实 HTTP 登录态、Provider、序列化和跨店负向；
- `StoreReportRoleScopeHttpAcceptanceTest`：总部财务/门店财务在门店经营报表中的范围；
- `EmployeeRoleContractTest`：七类固定员工角色，不重新引入 `ProjectSupport`。

这些证据说明：**核心数据范围模型已经实现并有测试基础**，不等同于完整产品操作闭环已经验收。

## 三、账号和门店归属如何形成

### 3.1 企业注册

企业注册时自动创建一家默认总店：

```text
Company
→ Store(defaultStore = true)
→ Boss(store = 默认总店)
```

### 3.2 财务账号如何得到总部/门店范围

当前邀请逻辑是：

```text
邀请人 store → Invite.store → 接受邀请后的 Employee.store
```

即新员工继承邀请人的门店，没有独立的“目标门店”入参。

因此实际效果是：

- BOSS 在默认总店发起财务邀请 → 财务继承默认总店 → 总部财务；
- 门店店长在本店发起财务邀请 → 财务继承本店 → 门店财务；
- 团队负责人可邀请成员，但受团队范围限制。

### 3.3 当前组织配置缺口

后端 `company/member/update` 支持传入 `storeId`，但：

- App 员工详情页修改岗位时只提交 `role`，没有门店选择；
- Web 当前没有对应的员工组织维护页面；
- BOSS 无法在邀请表单中直接指定目标门店，只能继承自己的门店；
- 门店新建接口固定 `defaultStore=false`，当前没有“调整默认总店”的业务入口；
- 门店停用规则提示“可先另设默认总店”，但代码中没有设置默认总店的 Provider。

结果：

> 数据范围规则存在，但“如何正确创建总部财务/门店财务、如何调店、如何更换总部财务锚点”尚未形成完整可操作闭环。

## 四、App/Web 展示现状

### 4.1 App

App 财务首页根据 `store.defaultStore` 区分展示：

| 账号 | 页面标题 | 门店筛选 |
| --- | --- | --- |
| 门店财务 | 本店财务记账台 | 无 |
| 总部财务 | 财务工作台 | 财务首页当前无门店筛选 |
| 店长 | 本店财务记账台 | 无 |
| BOSS | 财务工作台 | 财务首页当前无门店筛选 |

App 已有共享门店范围模块 `domains/identity/storeScope.ts`，其设计本身已支持：

- BOSS 和总部财务切换门店；
- 门店财务和店长锁定本店。

但该模块当前主要接入客户、成员、经营分析等页面，财务首页及多数财务子页没有统一接入。

### 4.2 Web

Web 财务壳层显示：

```text
财务 · 全公司
或
财务 · 本门店
```

并通过共享门店上下文显示门店筛选：

- Company 范围的 BOSS/总部财务：期望可看全部门店并下钻任一门店；
- Store 范围的门店财务/店长：锁定本店。

Web 财务页已有一部分接入门店维度，但 `RoleAreaShell` 仍保留以下提示：

```text
本页按数据范围取数，暂不随门店维度收窄
```

说明并不是所有财务页面都支持总部财务按门店下钻。

## 五、当前发现的断点

### F1：总部财务拿不到全部门店候选

`user/store/list` 当前的企业级视角判断仍然是：

```text
只有 BOSS 返回全部门店
```

但总部财务的数据范围已经是 Company。结果是总部财务虽然能看到全企业汇总，却无法从前端门店列表拿到其他门店选项，难以按门店下钻。

这是当前最明确的后端概念不一致：

```text
DataScope = Company
但 StoreList = 仅 BOSS 企业级
```

### F2：App 财务页未接入门店维度

总部财务在 App 上可以看企业范围数据，但财务首页没有门店筛选，无法像 Web 目标设计那样切到单店。与“App/Web 每类能力一致且完整”的用户裁决冲突。

### F3：财务账号创建路径不完整

邀请继承邀请人门店，无法显式选择目标门店。BOSS 想新建一个非默认门店财务时，当前 UI 没有直接路径；后端虽有 `storeId` 更新能力，但前端未暴露。

### F4：调店能力未产品化

后端成员更新支持 `storeId`，但 App 员工详情没有门店编辑，Web 没有员工组织维护页面。财务调店后数据范围会即时变化，却没有可见的操作入口、影响提示和审计说明。

### F5：默认总店不可调整，但文案暗示可调整

门店停用校验提示“如需关店请先另设门店并调整默认总店”，但当前只有新建门店 `defaultStore=false` 和启停接口，没有调整默认总店的 Provider。总部财务的组织锚点因此无法正常迁移。

### F6：财务子页门店维度覆盖不完整

Web 有一组已接入门店维度的财务页，也有页面明确提示“不随门店维度收窄”。这会导致总部财务在不同财务页面看到不同深度：
- 有的页面支持全部门店/单店；
- 有的页面只按当前账号总数据范围取数；
- 用户难以判断当前数字到底是全公司、当前门店还是某个筛选门店。

### F7：角色名称与范围名称没有形成稳定展示规范

当前角色名都是“财务”，范围只显示“全公司/本门店”。正式业务词是“总部财务/门店财务”，但 UI 没有稳定的身份标签。用户容易把“财务角色”和“财务数据范围”混为一谈。

## 六、建议的目标口径

### 6.1 保持一个 `Finance` 角色

不建议新增 `EnterpriseFinance`、`StoreFinance` 两个枚举。建议保持：

```text
EmployeeRole = Finance
+ store 归属
+ 派生财务范围类型
```

如果需要向前端展示，可由服务端返回只读投影：

```text
financeScopeType = Headquarters | Store
financeScopeLabel = 总部财务 | 门店财务
```

该投影是派生字段，不是新角色，不允许前端自行传给服务端用于授权。

### 6.2 统一门店列表判定

`user/store/list` 不应继续按 `role == Boss` 判断企业级视角，而应复用 `DataScopeContext`：

```text
DataScope.Company → 返回企业全部门店
DataScope.Store → 只返回本店
```

### 6.3 明确财务账号创建和调店入口

至少需要产品裁决：

1. BOSS 邀请财务时是否必须显式选择目标门店；
2. 门店店长是否只能邀请本店财务；
3. 财务调店是否必须由 BOSS 操作，是否需要影响提示和二次确认；
4. 默认总店是否允许调整，若允许，谁可操作、如何审计。

### 6.4 App/Web 统一门店范围体验

App 财务首页和财务子页应接入共享门店范围：

- 总部财务：全部门店 + 单店下钻；
- 门店财务：锁定本店；
- BOSS：全部门店 + 单店下钻；
- 店长：锁定本店。

每个财务页面必须明确显示当前范围，不允许同一套金额在不同页面出现不同分母却使用相同标题。

## 七、当前结论

```text
业务概念：已确认
数据范围：已实现并有测试
账号归属：部分实现
组织配置：不完整
App 展示：门店财务部分支持，总部财务门店维度不完整
Web 展示：框架已接入，但门店候选和页面覆盖不完整
最终判断：核心权限模型可用，产品操作闭环尚未完整
```

不能简单说“已经支持企业财务和门店财务”，也不能说“完全没支持”。准确表述是：

> **底层已经用同一个 Finance 角色支持两类数据范围，但总部财务的组织配置、门店候选、调店、默认总店调整和跨端一致展示尚未闭环。**

# 装得清业务分类与经营矩阵 v0.1

> 日期：2026-10-22
> 状态：`draft`，用于替代“角色 × 所有业务”为第一入口，形成“业务域 → 能力组 → 对象/事实 → 角色 → App/Web”的主视图。
> 原则：先看企业实际在经营什么，再看谁有权限操作；角色矩阵只作为权限对账层，不作为产品结构主视图。

## 一、为什么要换角度

原来的“角色 × 16 段业务”适合检查权限覆盖，但不适合回答：

- 这个功能到底属于标准配置、日常经营、组织管理还是财务事实？
- 为什么报价项目库、客户报价、合同金额、项目成本看起来都像“报价/财务”，但实际不是同一层？
- 为什么付款计划模板、合同付款计划、项目应收计划在三处出现？
- 为什么同一功能会同时出现在企业负责人、设计师、财务的菜单里？

因此需要建立统一的业务分层：

```text
一级业务域
→ 二级能力组
→ 业务对象/事实
→ 标准/模板/真实业务/财务事实
→ 角色责任
→ App/Web 落位
```

## 二、四个一级业务域

| 一级域 | 定义 | 核心判断 | 典型对象 |
| --- | --- | --- | --- |
| EOP 企业运营 | 企业面向未来业务定义的标准、模板、主数据和共享经营资料 | “企业以后按什么标准做” | 报价项目库、套餐模板、付款计划模板、施工计划模板、单据模板、供应商/材料主数据 |
| EMG 企业管理 | 管理企业主体、组织、人员、权限、订阅和安全边界 | “谁能代表企业、谁属于哪个组织、谁可以做什么” | Company、Store、Team、Employee、Invite、Role、Subscription、Audit |
| BIZ 业务运营 | 围绕客户和具体项目发生的真实业务行为与履约事实 | “这一单现在进行到哪一步” | Customer、Property、Design、Quote、Contract、Project、Material、Change、Acceptance |
| FIN 财务运营 | 由真实业务和企业运营产生、可核对可归集的资金、成本、利润和凭证事实 | “这笔钱是什么、归谁、何时形成、是否可结算” | Receivable、Receipt、Payable、Payment、Ledger、Payroll、Voucher、ProjectCost |

## 三、最重要的分层规则

### 3.1 标准/模板、业务单据、财务事实必须分开

| 业务概念 | 所属层 | 说明 |
| --- | --- | --- |
| 报价项目库 | EOP 企业运营 | 企业级价格/成本/工艺标准，未来报价引用它 |
| 客户报价 | BIZ 业务运营 | 针对具体客户、房屋、设计方案形成的报价单据 |
| 合同金额 | BIZ 业务运营 | 客户签约形成的合同事实 |
| 应收计划 | FIN 财务运营 | 合同生效后形成的收款权利和到期安排 |
| 付款计划模板 | EOP 企业运营 | 企业默认付款节点和比例 |
| 合同付款计划 | BIZ 业务运营 | 签约时从模板复制并冻结到合同 |
| 应收计划 | FIN 财务运营 | 合同付款计划落成应收事实，实际收款再核销 |
| 施工计划模板 | EOP 企业运营 | 企业标准阶段、工期和验收方式 |
| 项目施工计划 | BIZ 业务运营 | 具体项目实际排期与任务 |
| 项目实际成本 | FIN 财务运营 | 采购到货、结算、工资等形成的成本事实 |

### 3.2 示例链路

```text
企业运营标准
→ 业务运营实例
→ 财务运营事实
```

报价：

```text
报价项目库/套餐/成本标准
→ 设计方案分项
→ 客户报价
→ 合同金额
→ 项目成本/应收/利润
```

付款：

```text
付款计划模板
→ 合同付款计划快照
→ 应收计划
→ 收款/核销
→ 资金台账/凭证
```

施工：

```text
施工计划模板
→ 项目阶段/任务计划
→ 现场节点留证
→ 阶段验收/整改
→ 完工结算
```

薪酬：

```text
薪酬方案/提成规则
→ 考勤/提成事实
→ 工资单
→ 应付/付款
→ 工资条/凭证
```

## 八、当前分类下的关键术语规范

| 术语 | 只应表示 | 不应混用 |
| --- | --- | --- |
| 报价项目库 | 企业级标准价格/成本/工艺项目 | 客户报价单 |
| 客户报价 | 具体客户/房屋的报价单据 | 报价项目库 |
| 付款计划模板 | 企业级默认付款节点 | 合同付款计划、应收计划 |
| 合同付款计划 | 签约时冻结到合同的付款安排 | 当前实际应收、已收款 |
| 应收计划 | 财务运营中的收款权利和到期安排 | 合同付款条件文本 |
| 施工计划模板 | 企业级施工阶段/工期标准 | 项目实际施工计划 |
| 项目施工计划 | 具体项目的阶段、任务和日期 | 模板本身 |
| 企业费用 | 非项目归集的企业运营支出 | 项目成本 |
| 项目成本 | 归属于具体项目的预计/实际成本 | 企业费用 |
| 报销 | 员工或企业费用发生的独立业务流程 | 仅有一张报销模板/手工流水 |
| 业务凭证 | 收款、付款、工资、报销等业务事实的打印凭证 | 法定会计记账凭证 |

## 九、当前分类暴露出的结构性问题

1. **企业运营没有作为独立产品层被清晰表达**：报价库、套餐、付款计划、施工计划、凭证模板散落在不同模块，用户难以建立“企业标准层”的统一认知。
2. **模板与实例缺少统一链路**：付款计划模板→合同快照→应收计划、施工计划模板→项目计划还没有被统一表达成同一条标准链。
3. **企业管理与业务运营边界混杂**：员工、邀请、门店、角色在部分页面与客户/项目页面交叉出现。
4. **财务运营缺少企业费用与报销的独立业务对象**：当前有企业费用分类、手工流水和报销模板，但没有完整的报销申请/审批/付款闭环。
5. **角色矩阵过度膨胀**：把角色直接铺到所有功能上，导致看不出业务主次；后续应以业务域主责角色为主，再做角色能力对账。
6. **App/Web 页面按业务域不均衡**：内容获客、部分企业管理、财务门店维度仍存在单端或部分覆盖。

## 十、后续矩阵结构

从本文件开始，后续按以下顺序推进：

```text
一级业务域
→ 二级能力组
→ 对象/状态/金额事实
→ 角色责任
→ App/Web 功能落位
→ 页面与信息规则
```

角色矩阵不再单独作为主视图，而是保留为“权限对账表”。业务矩阵、功能矩阵和跨端矩阵均从这张业务架构出发。

## 十一、待确认事项

1. “企业运营”是否作为正式产品一级名称，还是改为“企业标准运营/经营标准”？
2. “报价财务库”具体指报价项目库、成本库，还是二者统称？
3. 企业费用报销是否需要独立的申请、审批、付款和凭证闭环，还是继续只作为手工企业费用和付款模板？
4. 套餐模板、方案模板是否全部归入企业运营，还是允许企业/项目两级模板？
5. BIZ-10 售后与复购是否作为当前基础版本的一级能力，还是后续扩展项？

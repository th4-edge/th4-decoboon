# B2C-2 设计方案、报价、合同矩阵 v0.1

> 日期：2026-10-22
> 状态：`draft`，业务运营 A 的第二切片。
> 范围：设计方案、设计方案版本、客户报价版本、合同基线与合同变更来源。
> 与专项关系：报价统一视图复用 `PI-20261022-006`；合同事实追踪复用 `PI-20261022-009`；统一实现由 `PI-20261022-010` 推进。

## 一、主链

```text
房屋/量房原始区域
→ 设计方案
→ 设计方案版本
→ 报价
→ 报价版本
→ 客户接受报价
→ 合同基线
→ 合同行快照
→ 项目
→ 合同变更
```

关键事实：

- 量房与原始区域是方案的事实输入；
- 设计方案版本化，方案变化后可重新生成报价；
- 报价保存独立快照和版本，不能随方案或主数据变化回写；
- 只有客户接受的报价可进入合同；
- 合同必须绑定报价；
- 合同行保存报价行快照；
- 合同生效后才能创建项目；
- 合同变更是独立对象，不回写原报价。

## 二、设计方案

### 2.1 当前对象

| 对象 | 当前定位 |
| --- | --- |
| Design | 面向单个客户和房屋的一套设计方案主档 |
| Space | 方案区域，继承或覆盖原始区域实测值 |
| DesignItem | 方案分项，引用报价项目库并保存方案快照 |
| Requirement | 客户诉求 |
| TalkPlan | 谈单 PPT / 方案讲解产物 |
| DesignTemplateVersion | 方案实例化的设计模版版本 |

### 2.2 状态

```text
Draft
Ready
Presented
Selected
Archived
```

状态由商务主链向前推进：客户接受报价、合同签约/生效、项目立项可把 Ready/Presented 推进为 Selected；不得回退 Selected/Archived。

### 2.3 版本

当前 `Design.version` 是数值字段，每个版本是一条独立 Design 记录；`designId + version` 共同表达一个方案版本。

**当前风险：**

- 新方案版本号按 `company + customer` 的方案数量递增；
- 同一客户多套房屋时，不同房屋的方案可能共用一个客户级版本序列；
- 方案副本会生成新 Design 记录并将 version 重置为 1；
- 当前没有明确的 `sourceDesignId` / `parentVersionId` 表达“版本来自哪一版”。

因此“方案版本”和“方案副本”当前需要严格区分，后续应冻结版本编号作用域。

### 2.4 事实输入

- Space 的区域面积/周长来自实测或覆盖；
- `AreaSource` 和 `ValueOrigin` 必须保留；
- 设计模版参考值、历史估算值不能冒充实测事实；
- DesignItem 引用 CatalogItem，但保存价格/成本/公式/工艺快照；
- 方案实例化后历史报价不随设计模版修改而回溯。

### 2.5 App/Web

- App 有设计方案工作台、方案编辑、区域/分项、AI 设计和谈单；
- Web 有设计方案工作区、区域/分项、模版实例化和报价联动；
- 两端均有设计对象，但页面结构和信息优先级不同；
- 设计方案应遵循统一业务对象视图，不在报价/合同页面复制完整方案明细。

## 三、报价

### 3.1 当前对象

| 对象 | 当前定位 |
| --- | --- |
| Quote | 客户报价聚合和快照 |
| QuoteLine | 报价行快照，绑定 DesignItem/CatalogItem/Space/PackageLine |
| QuoteComponent | 价格/成本组件 |
| QuoteGroup | 区域、类型等展示投影 |

### 3.2 状态

```text
Draft
Submitted
Accepted
Rejected
Superseded
Converted
```

规则：

- 已提交报价只读，修改需生成新版本；
- 已拒绝报价不可原地修改，通过 `quote/save + sourceQuoteId` 生成新 Draft；
- Superseded 只作历史，不再推进；
- 客户接受后才能进入合同；
- 同一房屋已有接受/转项目报价后不能继续新增正式报价；
- 报价金额、成本、公式由服务端保存快照。

### 3.3 版本

- 每个 Quote 记录有 `version`；
- 设计报价的 version 按 `designId` 下已有报价数递增；
- 套餐报价按 `房屋 + 套餐模板` 或 `客户 + 套餐模板` 递增；
- 自定义报价按房屋递增；
- 当前只有 version 数值，没有显式 `sourceQuoteId` / `supersededById` 持久化；
- 历史版本关系主要通过同一 design/property/customer 和时间顺序推断。

**风险：**

- 同一设计方案的报价历史可推断，但不是显式父子关系；
- 统一对象视图需要显示“上一版/当前版”，不能只依赖时间倒序；
- 如果同一客户/房屋出现多个报价序列，version 语义需要进一步明确。

### 3.4 报价模式

```text
Package
Custom
Hybrid
```

- Package 来自套餐模板；
- Custom 来自设计方案分项或手工范围；
- Hybrid 来自设计方案 + 套餐；
- 不同模式的来源和成本完整性必须分别判断。

### 3.5 App/Web/业主

- App 有报价列表、详情、编辑、套餐调整、报价工作台；
- Web 有报价工作区和 Excel 式表格；
- 业主端有报价只读视图；
- 报价页面统一规则由 `PI-20261022-006` 处理，本文件不重复定义分组/字段细节。

## 四、合同

### 4.1 当前对象

| 对象 | 当前定位 |
| --- | --- |
| ProjectContract | 合同基线、签约事实、项目来源 |
| ContractLine | 报价行签约冻结快照 |
| ContractPaymentPlan | 合同付款计划快照 |
| ContractConstructionPlan | 合同施工计划快照 |
| ContractChange | 合同变更事实 |
| Project | 合同生效后的唯一履约项目 |

### 4.2 状态

```text
Draft
PendingSign
Signed
Effective / Active
Changing
Changed
Completed
Settled
Closed
Terminated
```

现状：

- 设计师发起合同；
- BOSS/店长确认签约；
- BOSS/店长确认生效并生成项目；
- 合同必须绑定客户接受的报价；
- 合同行引用 `sourceQuoteLine` 并保存字段快照；
- 合同变更不回写原报价和签约行。

### 4.3 合同版本

`ProjectContract` 当前没有独立 `version` 字段。当前合同事实由以下组成：

```text
合同基线
+ 签约金额
+ 当前合同金额
+ 合同行快照
+ 付款计划快照
+ 施工计划快照
+ ContractChange 变更历史
```

因此当前更准确的说法是：

- **合同基线**；
- **合同当前事实**；
- **合同变更历史**；

而不是“合同 V1/V2”。如果统一对象视图要显示合同版本，需要先确认合同版本模型，不应给当前合同强行加一个前端版本号。

### 4.4 App/Web/业主

- App 合同页有合同金额、范围、变更、付款、选材和项目进度；
- Web 合同交接/合同档案有合同、报价、方案、签约资料和阶段轨迹；
- 业主端合同事实来自统一对象/旅程投影；
- 合同事实追踪由 `PI-20261022-009` 统一处理。

## 五、版本链对账

| 层级 | 当前身份 | 版本语义 | 来源绑定 | 当前问题 |
| --- | --- | --- | --- | --- |
| 设计方案 | designId + version | 一条 Design 记录是一版 | 设计模版版本；量房/区域来源在 Space | 版本按客户累计，缺 sourceDesignId |
| 报价 | quoteId + version | 一条 Quote 记录是一版 | designId、packageTemplate、property | 缺显式 sourceQuoteId/supersededBy |
| 合同 | contractId | 无独立 version | quoteId、客户、房屋、项目 | 合同版本语义未冻结 |
| 合同行 | lineId | 快照 | sourceQuoteLine | 历史快照可追溯，但需要统一展示 |
| 合同变更 | changeId | 独立变更事实 | 合同、项目 | 变更后金额与当前合同金额需同源 |

## 七、当前结构问题

### DQC-X01：设计方案版本号作用域不清

版本号按客户累计，而业务对象以房屋为根。多房屋客户下可能出现“另一套房屋的方案导致本房屋版本跳号”。

### DQC-X02：方案版本与方案副本没有显式来源关系

复制方案会新建记录并重置 version，但没有 `sourceDesignId`/`parentVersionId`，难以在事实追踪中区分版本、副本和独立新方案。

### DQC-X03：报价版本缺显式上一版关系

`sourceQuoteId` 只作为重报请求入参，生成后没有持久化为来源字段；统一视图只能按 design/property 和时间推断历史。

### DQC-X04：合同没有独立版本字段

合同基线 + 变更历史可以追溯，但不能简单称为“合同 V1/V2”。需要冻结合同版本语义，或统一使用“合同基线/当前合同/变更历史”。

### DQC-X05：跨对象版本的展示口径不统一

设计方案、报价、合同、项目页面分别用 version、status、currentAmount、sourceVersion 等字段表达历史，统一对象视图需要统一“当前版本/历史版本/已替代/已生效”的语言。

### DQC-X06：设计和报价的统一视图尚未接入

设计方案还没有对应的统一对象视图契约，报价统一视图正在 `PI-20261022-006/010` 推进；两者需共用事实追踪规则。

## 八、待业务/产品确认

1. 设计方案版本编号是否按 `customer + property`，而不是仅按 customer？
2. 方案复制是否必须形成“副本来源”关系，且 version 如何编号？
3. 报价版本是否必须持久化 `sourceQuoteId` 和 `supersededById`？
4. 合同是否引入独立版本，还是保持“合同基线 + 变更历史”语义？
5. 统一对象视图中的“版本”是否统一采用 `objectId + version`，合同使用 `baselineId + changeRevision` 的等价表达？
6. 业主端合同/设计方案展示哪些版本与上游摘要？

## 九、结论

```text
设计方案：有版本，但作用域和来源关系需冻结
报价：有版本，但上一版关系未显式持久化
合同：无独立版本，依赖合同基线和变更历史
合同行：已保存报价行快照
跨对象版本追踪：可部分推断，尚未显式化
```

这批问题的核心不是新增页面，而是冻结对象身份和版本语义，保证统一对象视图、项目事实追踪和合同事实追踪不会把“版本、副本、快照、变更”混为一谈。

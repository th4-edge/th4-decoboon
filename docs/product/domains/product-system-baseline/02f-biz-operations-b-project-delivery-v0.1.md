## 一、结论先行

1. **项目立项的唯一正常入口是已生效合同。** 合同必须绑定报价，报价不能直接生成项目；合同生效后系统创建唯一项目，并生成项目阶段、施工任务、材料预计划和应收计划。`[业务 BR-002] [代码 ProjectContext]`

2. **施工执行分为三层，不能混为一个“任务状态”。**
   - 合同级施工计划快照中的阶段；
   - 阶段 × 区域 × 工艺形成的施工任务；
   - 任务的施工进行/隐蔽工程/施工完成影像节点。
   `[业务 SCN-003] [代码 ContractConstructionStage / ProjectStage / ProjectTask / TaskNode]`

3. **合同变更审批通过即生效。** 新口径不再把业主确认建模为系统事实；审批通过在同一事务内更新合同当前金额、项目合同额、应收、任务、材料计划与成本影响，驳回/撤回不改生效事实。`[业务 DEC-068 / BR-041] [代码 ProjectContractContext]`

4. **主材履约是两张单据、一个事实源。** 作业单面向厂家/施工侧，不带价格与账期；采购单面向财务/供应商，可无价下单并形成暂估应付。1 张作业单可派生 N 张采购单，全部行必须回追 `MaterialPlan`；作业单行还必须显式回追对应采购明细。`[业务 DEC-072 / DEC-073 / DEC-088] [代码 MaterialSheetContext / MaterialPurchaseContext]`

5. **阶段验收必须由业主本人确认或驳回。** 员工只能提交验收与证据；同一阶段复用同一张验收单，整改/复验按轮次追加，不碰金额、成本、应收、应付和利润。`[业务 DEC-007 / DEC-015] [代码 ProjectContext / customer acceptance Update]`

6. **当前最大问题不是“功能是否存在”，而是履约状态和跨端能力没有形成同一完整契约。**
   - 合同阶段快照有 `acceptanceMode`，项目阶段没有承接该字段；
   - 项目有 `Suspended` 状态，却缺少正常的停工/复工业务动作；
   - App 已有较完整的施工排期、节点留证、日报、作业单维护和到场确认，Web 以查看/审批为主，相关动作明显缺失；
   - 主材作业单定义了 `Settled/Closed`，但结算事实目前没有回写作业单状态；
   - `MaterialReturn` 主要由合同减项自动生成，独立退换货/补发异常路径已由 `DEC-088/BR-054` 冻结，待实现。

## 二、对象关系与唯一事实源

```text
Customer
→ Property
→ Quote
→ ProjectContract（合同基线 + 当前金额 + 变更历史）
→ Project（唯一经营单元）
   ├─ ProjectStage（阶段执行事实）
   │  └─ ProjectTask（施工任务）
   │     └─ TaskNode（施工进行 / 隐蔽工程 / 施工完成留证）
   ├─ ProjectReport（现场动态 / 日报 / 打卡 / 通知）
   ├─ Acceptance（阶段唯一验收单）
   │  └─ AcceptanceRound（首次验收 + 整改复验轮次）
   ├─ ContractChange（变更单）
   │  └─ ContractChangeItem（来源行 + 目标快照 + 差额）
   ├─ MaterialPlan（合同/变更形成的需求行）
   │  ├─ MaterialSelection（选材版本）
   │  └─ MaterialOrderSheet（作业单）
   │     └─ MaterialOrderSheetItem（安装位置、数量、时间、签字）
   ├─ PurchaseOrder（采购单）
   │  └─ PurchaseOrderItem（价格、数量、结算价）
   ├─ GoodsReceipt（到场记录）
   ├─ MaterialAdjustmentOrder（退换货/补发异常处置）
   │  ├─ MaterialReturn（退货冲减）
   │  └─ StockMovement / PartnerCredit（下钻事实）
   └─ CustomerFeedback（意见、投诉、售后入口）
```

## 三、履约主链与状态机

### 3.1 合同生效到项目

```text
Quote Accepted
→ Contract Signed
→ Contract Effective
→ 系统创建唯一 Project
→ 生成 ProjectStage / ProjectTask / MaterialPlan / Receivable
```

代码与业务约束：

- 合同必须绑定报价；
- 一个房屋只允许一个项目，一个报价只允许生成一次项目；
- 只有 `Effective` 合同可以立项；
- 项目创建后合同与项目互相回指；
- 项目合同额取合同当前金额，面积优先取房屋面积，成本建立签约快照；
- 同房屋其他已接受/已转化报价不得并存。`[代码 ProjectContext#createFromEffectiveContract]`

### 3.2 项目状态

| 状态 | 业务含义 | 当前触发来源 |
| --- | --- | --- |
| `Preparing` | 待开工 | 立项默认、阶段尚未开始 |
| `Ongoing` | 施工中 | 阶段开工或任务推进后汇总 |
| `Suspended` | 已停工 | 审批生效的 `ProjectSuspension`；历史在跑承接兼容 |
| `Accepting` | 待验收 | 有阶段进入待验收 |
| `Finished` | 已完工 | 全部适用阶段完成 |
| `Settled` | 已结算 | 财务项目结算关闭后回写 |

关键不变量：

- 项目进度由阶段权重和任务进度汇总，不接受前端直写；
- 项目状态由下游事实驱动；活动停工单是覆盖事实，阶段/任务刷新不得覆盖 `Suspended`；复工后按当前事实重推 `Preparing/Ongoing/Accepting/Finished`；
- 全部适用阶段 `Done` 才可进入 `Finished`；
- 财务关闭结算时才可进入 `Settled`。`[代码 ProjectContext#refreshProject / finance settlement Update]`

**裁决与实现缺口：** `DEC-087 / BR-053` 已冻结停工单、审批、原因、责任、预计复工日、影响范围、通知和恢复路径；当前后端仍无正常停复工 Provider，且 `refreshProject` 可覆盖 `Suspended`。实现由 `PI-20261022-014 / GAP-066` 跟踪。

### 3.3 阶段、任务、节点

```text
ProjectStage: Todo → Doing → Accepting → Done
                         └──── 驳回 ──── Doing
ProjectStage: Todo → NotApplicable（可撤销）
ProjectTask:  Todo → Doing → Accepting → Done
                              └─ reopen → Doing
TaskNode:     Start / Conceal / Finish，每个任务每类节点最多一次
```

当前规则：

- 阶段开工要求：合同已生效、阶段有施工任务、项目已指定项目经理、开完工日期齐全、项目已完成量房；
- 无合同施工任务的阶段不得“开工 + 拍照”假装完成，只能核对合同施工行或判定为本项不涉及；
- 判定本项不涉及必须填写原因，并从项目进度分母剔除；
- 施工任务只能来自合同施工行或已生效合同变更，不允许排期页手工造任务；
- 排期只调整阶段、区域、计划起止、责任人、优先级和备注；数量、名称、工艺、金额与成本变化必须走增减项；
- 施工进行/隐蔽/完成节点必须上传照片或视频；隐蔽任务未确认隐蔽节点不得完成；
- 已取消任务不进入未完成分母，但取消必须有合法来源、原因、操作人和审计；
- `None`：任务与证据满足后系统自动完成，不生成业主待办；
- `ConstructionDone`：PM 内部确认完成，BOSS/本店店长可代确认，不生成业主待办；
- `AcceptanceDone`：员工提交验收，业主本人确认或驳回；
- 三种模式均须从合同阶段快照继承到 `ProjectStage`，日期重排不得改模式。`[业务 DEC-087 / BR-053；代码 stage Update / task Save / TaskNode Save / ProjectContext#submitAcceptance]`

**裁决与实现进展：** `PROJ-STATE-D1` 已新增 `ProjectStage.acceptanceMode`、合同快照复制、历史回填和 App/Web 只读展示，开发自测通过；MySQL 迁移、真实页面和独立验收未完成。`PROJ-STATE-D2` 的三种完成分流仍未实现，整体由 `PI-20261022-014 / GAP-066` 跟踪。

### 3.4 合同变更

```text
Pending
├─ 审批通过 → CustomerConfirmed（历史字面量，业务语义=已生效）
├─ 审批驳回 → Rejected
└─ 发起人撤回 → Cancelled
```

当前规则：

- 发起人：BOSS、店长、项目经理或本项目设计师；
- 审批人：BOSS、财务或本店店长；数据范围仍由服务端强制；
- 审批通过是唯一生效门槛；
- 生效时联动：合同 `currentAmount`、项目 `contractAmount`、应收、任务、材料计划、成本差异；
- 来源数量/金额在设计后发生变化时，审批重新校验来源基线，避免静默变更客户已确认金额；
- 已生效变更不得回写原报价与合同签约快照。`[业务 DEC-055 / DEC-068 / DEC-076 / BR-041] [代码 ContractChange Update / ProjectContractContext]`

设计侧事实：

- 变更单保存来源行/来源变更项、来源剩余数量/金额、来源时点、目标目录项快照；
- 新增/替换目标价格与成本由服务端解析，前端不能自由覆盖；
- 减项、整项取消和替换均保留来源关系；
- 已经开始或已采购的履约范围通过差异任务、差异材料或退货冲减承载，不能删掉历史事实。`[代码 ContractChangeFulfillmentContext / MaterialDeductionContext]`

### 3.5 阶段验收与整改

```text
员工提交验收
→ Approval Pending
→ 业主本人确认 → Confirmed → 阶段 Done
→ 业主本人驳回 → Rejected → 阶段 Doing
→ 员工整改后提交复验 → Pending
→ 循环追加 AcceptanceRound
```

当前规则：

- 只有 BOSS、项目经理或项目设计师可提交阶段验收；
- 阶段任务必须全部完成，且提交时必须上传现场证据；
- 业主确认/驳回必须由业主本人通过授权会话完成，员工入口固定返回 403；
- 驳回必须选择整改类型、提交问题与问题图片；
- 整改责任人固定为当前项目经理，项目经理为空时禁止驳回；
- 整改截止日期由整改类型对应的服务端期限计算，不再由业主自由选择；
- 第二轮起必须填写整改说明并上传整改后照片；
- 同一阶段复用同一张 `Acceptance`，历史轮次只追加不覆盖；
- 验收与整改不改金额、成本、应收、应付和利润。`[业务 DEC-007 / DEC-015 / 用户 2026-09-23 整改责任人裁决] [代码 ProjectContext / customer acceptance Update]`

### 3.6 主材履约状态

#### 材料计划

```text
Planned（待选材）
→ ReadyToOrder（已选材/可下单）
→ PartiallyOrdered / Ordered
→ PartiallyArrived / Arrived
→ Closed / Cancelled
```

- `Requested/Approved` 为历史兼容，不再写新数据；
- 选材进入采购后锁定；换材必须走增减项；
- 合同选材来源的计划行没有“已选材（现场确认）”记录时不得下单。`[业务 DEC-008 / DEC-056] [代码 MaterialPlanStatus / MaterialSelectionContext]`

#### 主材作业单

```text
Draft → Measuring → Measured → Submitted
→ PartiallyOrdered → Ordered → PartiallyArrived → Arrived → Settled → Closed
任意未采购态 → Cancelled
```

- 作业单行只能来自材料计划；
- 作业单承载型号、颜色、尺寸、安装位置、测量/配送/安装时间、签字、图片；
- 正式契约要求价格、账期、供应商决策落在采购单侧；
- `Pricing` 仅历史兼容，不再写入；价格未定由采购/结算 `priceState` 表达；
- `Settled`：有效到场量均被未撤销结算覆盖，退货/补发/换货/价差已处理；不等待应付付清或项目结算；
- `Closed`：`Settled` 后显式关闭，且无未结采购、到场、异常、价差或配送/安装事项；
- 行上的成本/采购/结算价只允许服务端只读投影，不能写入或参与计价；Designer/PM/业主不可见；
- 作业单行必须显式关联采购明细，不能只靠材料计划回溯；
- 当前 Web 只有财务下单队列，无作业单新建、编辑、测量、提交、取消、导出和到场入口。`[业务 DEC-072 / DEC-073 / DEC-088 / BR-054] [代码 MaterialSheetContext / MaterialSheetPriceProjectionContext] [裁决 PI-20261022-015]`

#### 采购、到场、结算、退货

```text
作业单提交
→ 财务选供应商/交付方式/价格（价格可空）
→ 创建 PurchaseOrder + PurchaseOrderItem
→ 确认下单形成应付/暂估应付
→ 到场累计 receivedQuantity，回填应付账期
→ 采购价形成暂估成本
→ 结算价修正应付与实际成本
```

- 交付方式分“供应商直送工地”和“入仓库”；只有入仓进入库存；
- 无价/混合价下单形成暂估应付，禁止用 0 冒充真实价格；
- 到场确认人：本项目项目经理或项目设计负责人任一方；BOSS/店长/财务为兜底；
- 已到货扣减必须生成 `MaterialReturn` 冲减应付与成本；
- 退货余款先冲同供应商其他应付，仍有余款进入供应商往来余额；
- 破损、错发、少发、色差、补发、换货和无合同减项退货统一由 `MaterialAdjustmentOrder` 承载；
- 合同减项与现场异常共用该工作流；`MaterialReturn/GoodsReceipt/StockMovement/Payable/PartnerCredit` 是下层事实；
- 补发不重复形成应付/成本；入仓退补走库存，直送只记数量和到场事实；
- 业主不确认材料到场/异常，只在影响材料、时间或需重新选择时查看只读摘要。当前实现尚未落地。`[业务 DEC-088 / BR-054 / DEC-MP-01/02/07] [代码 GoodsReceipt Save / MaterialDeductionContext / MaterialSettlementContext]`

### 5.1 跨端判断

- 同一角色在同一能力上的“能否执行”必须一致；`PD-X1` 已补齐 Web 施工排期、节点留证和日报的静态写动作，但仍待真实页面/独立验收；作业单与到场动作仍由 `MAT-X2` 处理。
- 不同端可以有不同的信息密度和主操作布局，但不能一端完整执行、另一端只能查看。
- `DEC-088/BR-054` 已明确：没有强制业务动作天然 App-only；摄像头/相册/定位等设备能力可在 App 原生，Web 必须有文件上传、手工说明、失败重试等等价闭环。“查看 + 回 App 处理”不满足完整。
- 施工排期、节点留证、日报、作业单全生命周期和到场确认均为双端强制能力；日报发布限 PM + BOSS/本店店长。
- 业主 Web 入口尚未裁决，因此“业主 Web missing”暂不直接判缺陷；需由 `RQ-05` 专项冻结。
- 当前跨端结论来自静态路由与页面代码，没有真实浏览器/真机截图与操作证据，不能对外宣称已完成一致性验收。

## 六、项目事实追踪接入要求

项目视图至少应形成以下事实节点：

```text
来源：客户、房屋、归属、量房
售前：设计方案版本、报价版本
签约：合同基线、签约金额、付款/施工计划快照
履约：项目、阶段、任务、节点证据、现场日报
材料：选材版本、作业单、采购、到场、异常处置（退货/补发/换货）、结算
变更：变更单、目标快照、当前合同额、下游联动
验收：阶段验收、整改轮次、业主确认
财务：应收、收款、应付、付款、成本、利润完整性
售后：意见投诉、交付/质保事实
```

每个事实节点必须包含：

- `objectType + objectId + version`；
- 当前状态/状态名/下一步/阻断原因；
- `projectId / customerId / propertyId`；
- 业务发生时间与系统记录时间；
- 责任人与门店/团队；
- 金额、数量、进度、成本完整性；
- 来源节点与下游影响；
- 证据与统一对象视图跳转；
- 角色字段白名单与数据范围。

材料履约固定拆为五个独立事实节点族：

| 节点族 | 身份/业务号 | 状态与版本 |
| --- | --- | --- |
| 作业单 | `sheetId + sheetNo` | 生命周期状态；`templateVersion` 是呈现版本，另保留状态事件序列 |
| 采购单 | `purchaseId + purchaseNo` | 采购状态 + 价格状态；按状态事件追溯 |
| 到场 | `receiptId` | append-only 到场事实，不覆盖历史 |
| 异常处置 | `adjustmentId + adjustmentNo` | `Draft/PendingSupplier/Confirmed/Executing/Completed/Rejected/Cancelled`，保留执行事件序列 |
| 结算 | `settlementId + settlementNo` | 有效/已撤销；撤销形成反向链，不覆盖原结算 |

`MaterialReturn`、`StockMovement`、`PartnerCredit` 是异常处置/结算节点的下钻事实，不单独升格为项目事实树。五个节点的字段、排序和投影接入 `PI-20261022-010`，不得另造第二套事实模型。

当前 `project/project/info`、`project/project/overview`、`customer/project/journey/info`、合同工作台和 App 项目详情分别组装履约摘要，尚未形成单一项目事实投影。该问题由 `PI-20261022-008`、`PI-20261022-009`、`PI-20261022-010` 协同处理，本批不另造第二套契约。

## 十一、验收最低要求

### 项目与施工

- 合同未生效不能立项；重复报价/重复房屋不能形成第二项目；
- 项目阶段、任务来源可追溯合同行或生效变更行；
- 阶段开工前置和本项不涉及判定可正反验证；
- 项目状态、阶段状态、任务进度、节点证据同源；
- 三种验收模式主体、任务门禁、完成路径和异常恢复可正反验证；
- 合同快照模式与项目阶段执行模式可追溯，日期重排不改模式；
- 无需验收与施工完成模式不产生业主假待办；业主验收只允许业主本人确认/驳回；
- 停工/复工只有审批入口，重复动作幂等，非法状态转换和跨店/跨企业操作被拒绝；
- 停工原因、责任、预计复工日、影响范围、通知和审计可查询；
- 停工期间任务推进/新下单/新验收阻断，已到场、既有 Pending 验收、合同变更和财务事实按例外执行；
- 停工不自动改合同基准、应收到期和材料日期，复工按事实重推项目状态。

### 阶段验收

- 任务未完成不得提交；
- 无证据不得提交；
- 员工代业主确认固定拒绝；
- 驳回后原验收单保留、轮次追加、复验材料必填；
- 验收/整改前后金额、成本、应收、应付和利润不变；
- 业主多项目、跨项目、撤销授权后不可访问。

### 材料履约

- 作业单行全部来源材料计划；
- 合同选材计划未选材不得下单；
- 有价/无价/混合价下单对应应付与暂估应付正确；
- 1 作业单→N 采购单、部分下单、分批到场可逐行对账；
- 直送不入库存，入仓生成库存；
- 到货不重复形成应付，只回填账期；
- 结算价修正成本且不重复累计；
- 已到货扣减必须形成退货并冲减应付/成本；
- 作业单 `Settled/Closed` 与采购/到场/异常处置/结算事实一致；应付付款、项目结算不得误作门槛；
- 结算撤销、关闭撤销形成反向事实，不覆盖历史；
- 作业单价格只读投影不参与计价，Designer/PM/业主不可见；
- 退货/补发/换货支持部分数量、供应商确认、证据和库存/应付/成本/往来对账；补发不重复形成应付或成本；
- 采购价、标准成本、结算价、合同售价四者不混用。

### 跨端与事实追踪

- 同一项目、同一对象在 App/Web/业主端状态、金额、数量和下一步一致；
- 一端不能展示“已完成”而另一端仍有待办；
- 强制能力在 App/Web 均有写入口和同一 Provider 结果；没有“只读 + 回另一端”的强制能力；
- 项目事实节点可跳转到统一对象视图并保留项目/合同/报价版本；
- 宿主页不复制完整明细、不在前端重算金额或合并分组；
- 真实页面、真机/多分辨率、接口契约和越权用例齐备后才可声明通过。

## 十二、结论

B2D 表明装得清已经具备“合同 → 项目 → 阶段/任务 → 材料 → 变更 → 验收”的业务骨架，且多项高风险规则已经在后端形成强约束。但当前履约域仍不是一套完整、可跨端复用、可追踪的业务系统：

```text
施工事实可推进，但阶段验收策略丢失；
项目可运行，但停工/复工不可运营；
材料可下单/到场/结算，但作业单状态未闭合；
App 可执行，Web 多处只能看；
合同变更已联动，但项目/合同/材料事实仍由多套投影拼装。
```

# 项目事实追踪设计 v0.1

> 日期：2026-10-22
> 状态：U5-A/U5-B1/U5-B2 后端契约与聚合、U5-C App PHASE 已 `DEV_VERIFIED`；U5-D~F 页面、越权和独立验收待推进。
> 目标：以项目为经营根节点，串联量房、设计、报价、合同、增减项、选材、施工、验收、财务和售后事实。

## 一、核心概念

项目事实追踪不是：

- 把所有业务对象重新塞进项目详情；
- 用一张大表复制各领域数据；
- 只看最新对象；
- 由前端拼接各接口后猜测上下游。

项目事实追踪是：

```text
项目 Project
→ 事实节点索引
→ 每个节点绑定来源对象 + 版本
→ 显示摘要、时间、状态、责任人、证据
→ 点击进入对应统一对象视图
```

项目是事实的**索引根**，不是所有事实的所有者。量房仍属于 Measure，设计仍属于 Design，报价仍属于 Quote，合同仍属于 Contract，选材仍属于 MaterialSelection。

## 二、事实链主图

```text
客户 Customer
→ 房屋 Property
→ 量房 Measure / 原始区域
→ 设计方案 Design / DesignVersion
→ 报价 Quote / QuoteVersion
→ 合同 ProjectContract / ContractVersion
→ 项目 Project
→ 施工计划 ProjectPlan / Stage / Task
→ 主材选材 MaterialSelection
→ 材料计划/下单/到货/结算 MaterialPlan / Purchase / Receipt
→ 增减项 ContractChange
→ 阶段验收/整改 Acceptance / Rectification
→ 应收/收款/应付/付款/成本/利润
→ 交付/售后/复购
```

## 三、事实节点模型

每个项目事实节点至少包含：

| 字段组 | 内容 |
| --- | --- |
| 身份 | nodeId、nodeKey、factType、objectType、objectId、业务编号 |
| 版本 | version、versionId、current、当前/历史/已替代 |
| 状态 | status、statusName、nextAction、阻断原因 |
| 关系 | projectId、customerId、propertyId、parentNodeId、影响对象 |
| 时间 | businessTime（业务发生时间）、recordedAt（系统记录时间） |
| 责任 | owner/actor、门店、团队 |
| 摘要 | title、summary、amount、quantity、progress、costComplete、profitAmount、grossMargin |
| 证据 | 图纸/照片/文件/签名/审计引用 |
| 权限 | 可见角色、字段白名单、数据范围 |
| 跳转 | 统一对象视图路径、宿主上下文、返回路径 |

## 四、事实节点分组

### 4.1 按业务阶段

| 阶段 | 事实节点 |
| --- | --- |
| 来源 | 客户、房屋、来源与归属 |
| 售前 | 量房、原始区域、诉求、设计方案、报价版本 |
| 签约 | 客户接受报价、合同、合同版本 |
| 履约 | 项目、计划、阶段、任务、现场日报、选材、材料计划和采购 |
| 变更 | 增减项、变更明细、生效金额 |
| 验收 | 阶段验收、整改、复验、业主确认 |
| 财务 | 应收、收款、应付、付款、成本、利润、结算 |
| 售后 | 交付、质保、维保、意见投诉、复购 |

### 4.2 按事实链

事实卡必须能回答：

```text
它从哪里来？
它当前对应哪个版本？
它影响了什么？
它被哪个后续事实引用？
它现在是否仍然有效？
下一步由谁处理？
```

示例：

```text
量房 V2
→ 方案 V3
→ 报价 V2
→ 合同 V1
→ 项目 P1
→ 变更 C1
→ 应收/成本重算
```

## 五、项目视图建议结构

### 5.1 首屏

```text
项目身份
+ 当前状态/阶段/进度/风险
+ 客户与房屋
+ 当前责任人
+ 唯一主行动
+ 事实完整度提示
```

### 5.2 事实追踪主体

推荐四种视图：

1. **阶段视图**：按售前、签约、履约、变更、验收、财务、售后组织；
2. **时间线视图**：按业务发生时间展示事实；
3. **关系图/链路视图**：展示对象之间的来源、派生、影响和核销关系；
4. **异常视图**：只显示缺失、过期、冲突、未生效、成本不完整和待处理事实。

### 5.3 事实卡

每个事实卡包括：

- 对象身份和版本；
- 当前状态；
- 关键金额/数量/时间；
- 来源和下游影响；
- 责任人；
- 最后更新时间；
- 证据入口；
- 主跳转。

例如：

```text
设计方案 V3
状态：已定稿
区域：6 个 · 分项：84 项
→ 生成报价 V2
查看设计方案
```

```text
报价 V2
状态：客户接受
金额：¥286,400
来源：设计方案 V3
→ 合同 V1
查看统一报价视图
```

## 六、当前实现基础

### 6.1 已有能力

- `project/project/info` 返回项目、客户、房屋、来源报价摘要和财务进度；
- `project/project/overview` 返回项目经营聚合、风险、进度和合同阶段；
- App 项目详情加载合同、验收、材料健康、选材和施工上下文；
- Web 项目工作面加载项目、阶段、任务、现场记录和验收；
- `CustomerJourneyContext` 已按量房、设计、报价、合同、增减项、材料、施工、验收、付款、意见组织业主事实；
- 报价已有 `QuoteViewContext` 可作为统一对象视图基础。

### 6.2 当前缺口

1. 项目详情没有统一的事实节点模型；
2. 内部项目视图和业主旅程使用不同模型；
3. 项目 `info` 主要返回来源报价摘要，不返回完整事实链；
4. 事实节点没有统一版本、来源、影响对象和跳转契约；
5. App/Web 项目页各自加载不同上下文，事实完整度可能不同；
6. 合同、设计、量房等事实可能只以链接或摘要出现；
7. 当前没有统一的“事实缺失/过期/冲突”状态；
8. 业主旅程自建 `PriceGroup` 等模型，与统一对象视图存在重复。

### 6.3 U5 后端当前实现（2026-10-23）

- `project/project/info` 已返回瞬态 `ProjectFactTrace`，覆盖固定 8 阶段、来源缺口和角色成本裁剪。
- `BusinessFactNode.current + nodeKey` 已支持当前/历史/替代/作废折叠；`ProjectFactTraceContract.nodeKeyGroups()` 提供同卡分组。
- `ProfitSettlement` 仅继承已存在 `Settlement` 快照的金额、利润和毛利率，不重算；无结算快照不生成空白卡。
- 后端证据：`docs/acceptance/runs/20261023-unified-object-view-u5b2/README.md`。
- App 项目详情已新增 PHASE 分段，消费同一事实索引并支持阶段折叠、历史折叠和返回锚点。
- 尚未完成：Web/业主页面消费、真实 Provider HTTP、跨企业/门店越权、端到端 SQL 预算和 U5-F 独立验收。

## 七、事实追踪与统一对象视图的关系

```text
项目事实追踪 = 索引 + 关系 + 当前状态 + 影响范围
统一对象视图 = 单个对象的完整事实 + 分组明细 + 场景适配
```

两者组合：

```text
项目视图
→ 看事实链和摘要
→ 点击“设计方案 V3”
→ 进入统一设计方案视图
→ 返回项目事实链，仍停在原节点
```

项目页面不得复制统一对象视图的所有明细，否则会再次产生口径分裂。

## 八、权限与视图分层

| 场景 | 可看事实 | 不可看内容 |
| --- | --- | --- |
| BOSS | 全企业项目事实链 | 不可替代业主确认 |
| 店长 | 本店项目事实链 | 跨店、企业治理 |
| 设计师 | 本人/参与项目事实链 | 成本、财务高危动作 |
| PM | 参与项目履约事实链 | 售价修改、成本敏感字段 |
| 财务 | 项目账务事实链 | 非财务业务写入 |
| 业主 | 授权项目的销售、进度、材料、验收、付款事实 | 成本、利润、内部公式、内部动作 |

## 九、验收标准

1. 任一项目事实节点都能追溯到来源对象和版本；
2. 项目视图与对象统一视图的事实一致；
3. 上下游关系可解释，不靠人工拼接；
4. 历史版本、已被替代版本和当前有效版本有明确标识；
5. 业主端只显示授权事实和销售字段；
6. App/Web 项目页面的事实集合可对账；
7. 事实缺失、过期、冲突时明确提示，不用空数组伪装；
8. 跳转后返回保留项目 ID、事实节点和视图状态；
9. 真实项目端到端场景覆盖量房→设计→报价→合同→变更→选材→验收→财务；
10. 契约测试覆盖同一项目在不同角色和端的核心事实。

## 十、待 T05/T06/T12 裁决

1. 项目事实链是否以“业务发生时间”还是“系统记录时间”为主排序；
2. 项目视图默认显示全部阶段还是只显示已发生/当前阶段；
3. 业主端事实链是否包含售后、质保和复购；
4. “事实完整度”如何定义和展示；
5. 每个对象节点允许展示哪些摘要字段；
6. 项目事实链是否需要独立的 `ProjectFactTrace` 领域投影模型；
7. 事实链的查询性能与分页/缓存边界。

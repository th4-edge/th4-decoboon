# 合同事实追踪设计 v0.1

> 日期：2026-10-22
> 状态：用户已确认合同应可追踪量房、设计方案、报价等上游事实；节点/权限/字段细节待专项裁决。
> 目标：把合同定义为“签约事实收敛点 + 项目履约起点”，并复用统一业务对象视图。

## 一、合同在事实链中的位置

```text
客户 Customer
→ 房屋 Property
→ 量房 Measure / 原始区域
→ 设计方案 Design / DesignVersion
→ 报价 Quote / QuoteVersion
→ 合同 ProjectContract
→ 项目 Project
→ 施工计划/任务
→ 选材/材料/采购/验收
→ 增减项
→ 应收/收款/成本/利润
```

合同视图有两类事实：

### 上游：签约依据

- 客户；
- 房屋；
- 量房记录及区域/实测摘要；
- 设计方案及版本；
- 客户接受/登记的报价及版本；
- 付款计划快照；
- 施工计划快照；
- 报价 PDF、方案/谈单材料、合同附件。

### 下游：履约影响

- 项目；
- 合同变更；
- 选材/材料计划/采购/到货；
- 阶段验收/整改；
- 应收/收款、应付/付款、成本/利润、结算；
- 交付与售后。

## 二、合同事实追踪模型

```text
ContractFactTrace
├── contract
├── upstream
│   ├── customer
│   ├── property
│   ├── measureSnapshot
│   ├── designVersion
│   └── quoteVersion
├── downstream
│   ├── project
│   ├── changes
│   ├── selections
│   ├── materialFacts
│   ├── acceptances
│   └── financeFacts
└── versions
    ├── current
    ├── signed
    ├── effective
    └── historical
```

每个节点仍遵循 `05-project-fact-trace-design-v0.1.md` 的统一事实节点字段：

- 来源对象与 ID；
- 版本；
- 状态；
- 业务时间；
- 记录时间；
- 责任人；
- 摘要；
- 证据；
- 上下游关系；
- 统一对象视图跳转。

## 三、合同页建议结构

### 3.1 首屏

```text
合同身份
+ 客户/房屋
+ 合同状态
+ 最终签约额
+ 当前合同金额
+ 已收/未收
+ 当前项目状态
+ 唯一主行动
```

### 3.2 签约依据

按上游顺序展示：

```text
量房摘要
→ 设计方案 V3
→ 报价 V2（客户接受）
→ 合同 V1
```

每一项只显示：

- 名称/编号/版本；
- 状态；
- 关键摘要；
- 来源时间/责任人；
- “查看统一视图”入口。

示例：

```text
量房记录
最近量房：2026-10-18 · 执行人：陈晨
区域：6 个 · 实测区域：4 个 · 待补：2 个
查看量房记录

设计方案 V3
状态：已定稿
风格：现代简约 · 区域 6 · 设计分项 84
查看设计方案

报价 V2
状态：客户接受
金额：¥286,400
查看统一报价视图
```

### 3.3 合同事实

- 合同编号、签约额、当前额、状态；
- 签约/生效时间；
- 付款计划快照；
- 施工计划快照；
- 合同范围；
- 合同 PDF/附件；
- 变更后金额。

### 3.4 履约与账务

- 项目；
- 当前阶段/进度；
- 增减项；
- 选材/材料；
- 验收/整改；
- 应收/已收/待收；
- 应付/成本/利润完整性。

## 四、版本绑定规则

1. 合同必须绑定明确的 `quoteId + quote.version`；
2. 报价若有设计方案，必须绑定明确的 `designId + design.version`；
3. 设计方案若由量房实例化，必须能追溯其使用的量房/区域快照；
4. 合同、项目、业主端不得展示“最新报价/最新设计”替代签约依据；
5. 合同变更只影响当前合同金额及下游事实，不回溯改写签约报价快照；
6. 直接签约补录必须显示“无设计来源/签约基线报价”的来源状态，不能伪装为正常设计方案报价；
7. 在跑项目承接必须显示承接来源和历史基线，不进入正常首版报价接受率。

## 五、场景适配

| 场景 | 合同事实范围 | 跳转 |
| --- | --- | --- |
| 合同工作台 | 合同 + 上游签约依据 + 下游履约摘要 | 量房、设计、报价、项目、变更、材料、验收 |
| 项目详情 | 合同摘要 + 项目履约事实 | 统一合同视图 |
| 客户 360 | 客户/房屋下合同版本和状态 | 统一合同视图 |
| 业主端 | 合同、报价、量房/设计摘要、项目进度、验收、付款 | 只读统一视图 |
| PDF | 合同正文、签约依据摘要、附件 | 客户版字段白名单 |
| 财务/核算 | 合同额、变更额、应收/成本/利润 | 财务事实视图 |

## 六、当前实现基础

### 已有能力

- `ProjectContract` 绑定客户、房屋、报价、项目；
- `project/contract/info` 和 `project/contract/workbench` 返回合同、报价摘要、付款计划、施工计划、变更、项目进度、选材和财务摘要；
- App 合同页有合同范围、变更、项目进度、选材/材料入口；
- Web 合同交接有报价、方案、签约材料、合同 PDF 和阶段轨迹；
- `CustomerJourneyContext` 已组织量房、设计、报价、合同、变更、材料、施工、验收、付款事实。

### 当前缺口

1. App 合同页没有量房、设计方案、报价统一视图的完整上游链；
2. Web 合同交接依赖 `quote.designId` 查询设计，但没有量房摘要和统一事实节点；
3. 合同信息、项目信息、客户旅程各有一套合同/报价摘要投影；
4. 合同范围、报价版本、设计版本、量房快照之间没有统一的来源关系模型；
5. 当前没有统一的“签约依据”区块和版本标识；
6. 业主端的合同事实来自旅程模型，与内部合同工作台字段不同；
7. 直接签约补录、在跑项目承接等来源状态需要在合同事实链中明确显示。

## 七、验收标准

对同一合同：

1. 合同视图能看到客户、房屋、量房、设计、报价摘要；
2. 合同绑定的报价版本、设计版本、量房快照可追溯；
3. 不显示最新版本替代签约依据；
4. 下游项目、变更、选材、验收、财务事实与合同关联；
5. 合同变更不回溯改写签约报价快照；
6. 业主只看到授权销售事实；
7. 合同详情与统一报价视图金额一致；
8. App/Web/业主端合同事实集合可对账；
9. 缺量房、缺设计、直接签约补录等异常来源有明确提示；
10. 项目/合同跳转保留合同、报价和项目 ID。

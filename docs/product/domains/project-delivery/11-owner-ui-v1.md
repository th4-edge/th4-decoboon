## 1. 产品命题

业主打开小程序时，不需要先理解“量房、设计、报价、合同、材料、验收”这些内部业务对象。

系统先回答三个问题：

1. 我家现在到哪一步了？
2. 现在有没有需要我做的事？
3. 如果我想继续了解，应该从哪里看？

业务对象退到第二层，作为可追溯的“家的记录”。

## 2. 信息架构

采用四个主 Tab + 中央标志性入口：

| 位置 | 名称 | 职责 |
| --- | --- | --- |
| 1 | 我的家 | 当前状态、需要我做的事、家的记录、服务团队、近期进展 |
| 2 | 进度 | 施工节点、计划时间、当前状态、现场记录 |
| 中央 | 装修历程 | 从量房到验收的完整过程叙事，采用深色沉浸层 |
| 4 | 我的钱 | 应付、已付、待付、下一节点与付款计划 |
| 5 | 家档案 | 量房、设计、报价、合同、增减项、选材、验收、付款档案 |

中央入口不是第五个普通 Tab，而是装得清的特色价值入口，因此在视觉上凸起并使用品牌深色。

## 3. 关键场景

### 场景 A：业主日常打开

- 使用人：业主本人
- 触发：想确认家里施工是否正常
- 当前动作：打开“我的家”
- 系统下一步：展示当前阶段、整体进度、预计完工和需要业主处理的事项
- 异常处理：journey 暂不可确认时显示“正在同步/点击重试”，不得伪装成无事项

### 场景 B：阶段验收待确认

- 使用人：业主本人
- 触发：装企提交阶段验收
- 当前动作：从首页焦点卡进入验收
- 系统下一步：展示现场证据、验收说明和本人确认入口
- 异常处理：员工预览只读，不出现代确认路径

### 场景 C：查看钱和档案

- 使用人：业主本人
- 触发：想核对付款或回看合同/材料记录
- 当前动作：进入“我的钱”或“家档案”
- 系统下一步：金额统一使用应付/已付/待付口径，档案按业务过程分类
- 异常处理：缺失数据明确显示“待同步/待确认”，不编造金额与日期

## 4. 视觉原则

- 深松石绿代表企业履约与过程存证，暖白作为信息阅读层。
- 首屏使用 narrative hero，而不是仪表盘指标墙。
- 重要事实用一句人话表达，数字只作辅助。
- 中央“装修历程”使用深色沉浸层，与业务页面形成价值分层。
- 卡片层级克制：首屏 1 个焦点卡、记录区两列、时间线纵向推进。
- 不使用 emoji、字符箭头和临时图标；继续使用 `JzIcon` 与 `JzBrandLogo`。

## 5. 数据映射

| 界面事实 | 来源 | 规则 |
| --- | --- | --- |
| 当前阶段、进度、预计完工 | `Project` / `CustomerJourney` | 直接使用服务端事实，前端不推算新日期 |
| 待我处理 | `CustomerJourney.actions` | 为空即无待办，不制造伪任务 |
| 验收待确认 | `acceptance.status = pending/statusName` | 只提示，不代业主确认 |
| 家的记录 | journey sections | 量房/设计/报价/合同/变更/材料/施工/验收/付款 |
| 服务团队 | `journey.team` | 仅姓名与岗位，不展示个人手机号 |
| 我的钱 | payment section facts/items | 应付/已付/待付；不展示成本、利润、供应商价 |
| 家档案 | journey sections | 只做索引与摘要，不复制内部数据 |

## 6. 当前不做

- 不伪造“未来 7 天”逐日计划；需等排期与业主可见口径冻结后接入。
- 不新增逐项验收点数据结构；继续使用现有验收单与轮次事实。
- 不新增质保起算、档案权属或长期保留承诺。
- 不让员工预览执行业主确认、投诉、分享等写动作。
- 不把中央装修历程做成无数据源的营销页。

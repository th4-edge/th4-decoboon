# GAP-034 决策包：施工计划、排期与现场汇报

日期：2026-10-17
状态：`WAITING_USER_DECISION`
影响批次：`project-delivery B1 → B2`

## 0. 结论先行

核心事实已经明确，不需要重新裁决：

- 排期任务唯一来源 = 本项目合同/报价施工行，或已生效增减项；
- 合同基准完工日锁定，排期只产生预计完工日；
- 超窗必须生成计划偏差；
- 空阶段必须区分“本项不涉及”和“应有任务但缺失”。

仍需要用户拍板的是 5 个实现语义冲突，下面给出推荐选项。

## 1. 阶段计划两套算法

### 现状

- `recalculatePlanFromSchedule`：任务排期 min/max 驱动阶段/项目计划；
- `scheduleStages`：项目更新时按阶段权重重拆工期；
- 同一个项目先后触发可能得到不同的阶段计划。

### 选项

- A（推荐）：合同基准计划只读；项目阶段执行计划只由排期任务驱动；项目级重排只能作为“基准变更/计划偏差确认”，必须留版本。
- B：保留项目级重排，排期任务只做局部覆盖；需要定义优先级，复杂度更高。
- C：两套算法并存，按入口决定；会产生无法解释的日期分叉，不建议。

### 推荐理由

与 DEC-048 的“基准层 / 执行层 / 预测层”一致，也能让合同承诺和现场变化分开。

## 2. acceptanceMode 是否落到 ProjectStage

### 现状

`acceptanceMode` 只在合同施工计划快照，项目阶段不可见，导致业主验收触点可能丢失。

### 选项

- A（推荐）：立项时将 `acceptanceMode` 从合同施工计划快照复制到 `ProjectStage`，后续基准变更时更新并留版本。
- B：继续只在合同快照读取；项目阶段查询时回连合同快照；实现简单但跨层查询和业主可见性易错。

### 推荐理由

项目阶段是施工与验收的实际执行对象，验收模式必须随阶段可见、可追溯。

## 3. 现场动态 / 施工日报发布角色

### 现状

节点留证限 Boss/店长/PM；现场动态发布仅要求项目可见，角色可能过宽。

### 选项

- A（推荐）：现场动态/施工日报由 PM、Boss、本店店长发布；设计师可查看，不可代发；业主只读。
- B：所有项目参与人都可发布；灵活但现场事实责任不清。
- C：仅 PM 发布；店长/老板无法代发，异常时恢复路径不足。

### 推荐理由

现场事实需要明确责任人，同时保留老板/店长的管理代发能力。

## 4. 取消任务是否进入阶段验收门禁

### 现状

`Cancelled` 任务是否计入阶段验收前置未冻结。

### 选项

- A（推荐）：已取消任务不计入“未完成任务”分母，但取消必须有原因、操作人、时间和来源；阶段验收必须证明取消来自合同变更或合法计划调整。
- B：取消任务仍阻断验收，直到人工确认；安全但容易形成死锁。
- C：取消任务直接忽略且不留痕；不可接受。

### 推荐理由

既避免取消任务阻塞验收，又保留取消事实和责任链。

## 5. 工艺库与阶段/区域绑定

### 现状

企业工艺库可作为主数据，但项目排期不得从工艺库直接造任务；阶段/区域绑定形态仍不统一。

### 选项

- A（推荐）：工艺库只服务报价项目库和合同施工行；项目排期只读合同施工行，不直接绑定企业工艺库；区域来自合同行/房屋区域快照。
- B：项目排期仍可选工艺库，但必须由系统即时生成合同外变更；等于把变更入口前置到排期页，复杂度高。

### 推荐理由

与 DEC-049 的唯一入口一致，避免绕过报价和增减项。

## 6. 建议的冻结顺序

1. 阶段算法统一；
2. acceptanceMode 落 ProjectStage；
3. 现场动态/日报发布角色；
4. 取消任务验收门禁；
5. 工艺库边界。

前 1–2 项决定 B2 数据结构与排期算法，应优先拍板；后 3 项可并行整理验收用例，但不能在未裁决前编码。

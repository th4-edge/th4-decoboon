# 装得清产品问题治理与长期档案

> 状态：现行产品研发治理流程。
> 目标：产品体系梳理和日常研发中发现的问题不被丢掉，也不打断当前梳理节奏；每个关键问题都有独立档案、业务裁决、研发任务和验收回执。

## 1. 适用范围

以下问题必须进入本台账：

- 角色、权限、数据范围、组织归属；
- 同一业务事实在 App/Web/后端口径不一致；
- 状态机、金额、成本、利润、应收应付、工资、凭证；
- 客户、房屋、报价、合同、项目、材料、验收等核心对象定义或展示冲突；
- 已实现但与正式业务口径不一致；
- 影响多个角色、多个页面或跨端闭环的体验/信息架构问题；
- 需要业务智能体裁决的 `GAP`、`DEC`、`BR` 或用户决策。

普通文案、局部样式和单点低风险问题可以走日常轻量修复，但修复后仍应在本台账登记结果链接。

## 2. 核心原则

```text
发现不等于修复
页面现状不等于业务规则
业务裁决先于研发
研发完成不等于验收通过
```

1. 当前产品梳理会话只负责发现、记录、建立问题档案和链接；不顺手展开修复。
2. 每个关键问题使用独立问题 ID，形成独立档案，不依赖聊天记忆。
3. 需要业务裁决的问题，必须进入专项会话，向 `zhuangdeqing-business` 提交 `T05`，取得 `T06/T12` 后才能确定研发范围。
4. 研发任务必须从已裁决口径生成，包含对象、状态、权限、金额、App/Web 范围、验收条件和回滚点。
5. 验收必须独立于开发自测；关键问题至少覆盖正向、反向、越权、重复提交、跨租户/跨门店和跨端一致性。
6. 完成后回写业务知识库、产品档案、问题台账和验收证据。

## 3. 状态流

```text
FOUND
→ ARCHIVED
→ T05_REQUESTED
→ BIZ_DECIDED
→ DEV_QUEUED
→ DEV_IN_PROGRESS
→ DEV_VERIFIED
→ ACCEPTANCE
→ CLOSED
```

异常状态：

- `DEFERRED`：当前不修，保留原因和重启条件；
- `REJECTED`：业务或产品明确不做；
- `BLOCKED`：缺少业务裁决、环境或证据；
- `REGRESSED`：验收或线上回归失败，重新进入研发。

## 5. 问题档案必备字段

每份 `issues/PI-*.md` 至少包含：

- 问题 ID、标题、发现时间、来源会话；
- 严重级别和当前状态；
- 业务场景、角色、对象、页面、Provider；
- 当前事实与证据路径；
- 与正式业务口径的差异；
- 用户/业务影响；
- 临时处理，避免错误行为继续扩大；
- T05 问题；
- T06/T12 裁决；
- 研发任务与变更范围；
- 测试、构建、真实页面和独立验收证据；
- 关闭条件、回滚和后续风险。

## 6. 专项会话规则

命中以下任一条件，应创建或使用专项会话：

- 新角色、角色合并、权限或数据范围变化；
- 角色派生身份不清，例如总部财务/门店财务；
- 金额、成本、利润、支付、工资、凭证语义变化；
- 跨 App/Web/后端的事实不一致；
- 影响多个业务域或需要 DDL；
- 问题超过一个垂直切片。

专项会话提示词见 `templates/DEDICATED-SESSION-PROMPT.md`。

专项会话必须：

1. 先读取问题档案和业务事实源；
2. 填写 T05 并完成 `zhuangdeqing-business` 同步；
3. 在 `T06/T12` 前只做调查、方案和影响分析，不修改代码；
4. 根据裁决拆分研发任务，一次一个可交付切片；
5. 开发完成后提供测试/构建/页面证据；
6. 交由独立验收，未验收不得标记 `CLOSED`；
7. 回写 `registry.json`、问题档案和业务知识库。

## 7. 与产品体系基线的关系

- 产品体系基线负责长期矩阵和统一口径；
- 本台账负责收集问题、跟踪裁决和研发验收；
- 产品矩阵发现冲突时，只在矩阵中标记 `GAP/DEF` 并链接问题 ID；
- 问题修复完成后，再把稳定结论回写产品矩阵，避免未裁决内容污染主基线。

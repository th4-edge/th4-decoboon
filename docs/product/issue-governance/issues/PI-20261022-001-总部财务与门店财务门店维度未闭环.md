## 一、问题摘要

系统当前只有一个固定员工角色 `Finance`。总部财务和门店财务不是两个角色，而是通过“财务岗位 + 归属门店是否为默认总店”派生：

```text
Finance + 默认总店 → Company / 总部财务
Finance + 普通门店 → Store / 门店财务
```

核心数据范围规则已经实现并有后端测试，但账号创建、门店候选、调店、默认总店调整和 App/Web 门店维度尚未闭环。

## 二、已确认的正式口径

- `DEC-065`：财务默认归属门店；默认总店财务为企业范围；门店财务为本店范围。
- `DEC-075`：店长可执行本店记账与部分本店高危动作，但财务与店长不是同一角色。
- `DEC-074`：材料员/履约人员与财务为同一角色。
- `DEC-080`：财务客户经营入口和动作与 BOSS/店长对齐，但财务数据范围不变。
- 用户 2026-10-22：普通员工单主岗；BOSS 内部能力超集；项目和门店责任关系不构成多岗。
- 用户 2026-10-22：App/Web 的每类强制能力必须一致且完整。

| 财务域权限 | BOSS/Finance/店长可查看和记账；高危动作仅 BOSS/店长 |

## 四、已识别的产品缺陷/缺口

### DEF-FIN-01：总部财务无法获取全部门店候选

`DataScope = Company`，但 `user/store/list` 仍只把 BOSS 视为企业级视角。总部财务拿不到其他门店选项，无法在前端按门店下钻。

### DEF-FIN-02：App 财务页未接入门店维度

总部财务在 App 可看企业范围数据，但财务首页和多数子页没有全部门店/单店切换。

### DEF-FIN-03：财务账号创建不能指定目标门店

邀请记录继承邀请人门店，App 邀请页无门店选择。BOSS 不能直接邀请某个非默认门店的财务。

### DEF-FIN-04：调店能力未产品化

后端成员更新接口支持 `storeId`，App 员工详情只发送岗位，Web 无员工组织维护页面。财务调店缺少入口、影响提示和审计展示。

### DEF-FIN-05：默认总店无法调整

默认总店是总部财务的组织锚点，但当前只有新建和启停门店，没有调整默认总店的 Provider。停用提示与实际能力不一致。

### DEF-FIN-06：Web 财务页门店维度覆盖不完整

部分页面支持全部门店/单店，部分页面明确“不随门店维度收窄”，导致同一套财务数字的分母不稳定。

### DEF-FIN-07：总部财务/门店财务没有稳定展示名

UI 角色名均为“财务”，只通过数据范围显示“全公司/本门店”。正式业务术语“总部财务/门店财务”尚未形成稳定展示规范。

## 五、影响

- 总部财务能看到企业汇总，但不能可靠下钻单店；
- 财务账号可能因邀请人门店不同而被错误创建成总部财务或门店财务；
- 财务调店和 HQ 锚点迁移缺少产品路径；
- App/Web 同一财务能力不完整，违反用户 2026-10-22 跨端裁决；
- 用户在页面上难以判断当前金额属于全公司还是某门店；
- 未见证据表明当前存在跨店数据泄漏，主要问题是能力不完整、组织配置不可控和口径展示不稳定。

## 六、临时处理

在专项会话完成业务裁决和研发验收前：

1. 不宣称总部财务和门店财务已完整支持；
2. 不在当前产品梳理会话中顺手修改权限、组织或页面；
3. 对总部财务用户，明确其数据范围是全企业；门店下钻缺失作为已知问题；
4. 门店归属调整由后端能力/人工操作前，必须核对 `Employee.store.defaultStore`，避免创建错误范围的财务账号；
5. 不把“财务 = 全公司”或“财务 = 本店”写死到新的页面或文案中。

### 已冻结规则

1. 保留单一 `Finance` 角色；总部财务/门店财务由归属门店派生。
2. BOSS 邀请财务必须显式选择目标门店；店长只能邀请本店财务；团队负责人、财务不得邀请财务。
3. 仅 BOSS 可跨店调整财务；身份即时变化；不要求原因、二次确认、交接或专用审计；历史对象不回溯。
4. 默认总店由企业创建时形成，有且仅有一个，不允许变更或切换；企业后续创建的门店永远为非默认门店。
5. 总部财务/BOSS 可查看全企业及指定门店；门店财务/店长仅本店。
6. 工资、提成、薪酬、供应商往来、退款、主材、项目账本、凭证按组织结构支持门店范围，App/Web 必须一致。

## 九、验收最低要求

### 9.1 测试主体与数据

- 企业 A：默认总店 D、普通门店 A1、普通门店 A2；
- 企业 B：默认总店 X、普通门店 X1；
- 账号：BOSS、总部财务（D）、门店财务（A1）、店长（A1）、普通员工（A1）；
- 所有写操作用开发/测试数据，禁止在生产真实账号上试调店或默认总店。

### 9.2 正向用例

1. 总部财务与 BOSS 的 `user/store/list` 返回 A 企业全部门店，并可对全部门店/单店分别取数；
2. 门店财务与店长只返回 A1，财务页面锁定本店且无跨店合计；
3. BOSS 邀请总部财务到 D、邀请门店财务到 A2，接受邀请后 `Employee.store` 与派生范围正确；
4. 财务调店后总部/门店身份即时变化；历史客户、项目、合同、财务单据的门店快照不变；
5. 若开放默认总店调整：BOSS 可将 D 切换到 A2，企业始终恰好一家默认总店，旧/新总部财务身份与审计可解释；
6. App 与 Web 同一财务页、同一日期/筛选、同一门店维度下数字一致；
7. UI 稳定显示派生身份与当前范围，不只显示“财务”。

### 9.3 反向与异常用例

1. 门店财务/店长请求他店或全企业数据返回 403/404，不以空数组伪装无权限；
2. 跨企业 `storeId`、伪造 `companyId/empId` 一律拒绝；
3. 店长邀请他店财务、团队负责人/财务邀请财务（按 T06 冻结边界）被拒；
4. 非 BOSS 调整默认总店被拒；
5. 财务调店未满足交接/确认/原因要求时被拒，且无部分写入；
6. 重复邀请、重复调店、重复默认总店切换和并发提交不产生重复身份变化或重复审计；
7. 接口失败时显示“暂不可确认”并保留重试/恢复路径，不得展示空列表或 0 金额冒充成功；
8. 单门店企业不出现无意义门店控件，行为与改造前等价。

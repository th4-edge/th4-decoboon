## 一、问题摘要

设计方案有 version 字段但版本号按客户累计；方案副本没有显式来源关系。报价有 version 字段但重报后没有持久化 sourceQuoteId/supersededById。合同没有独立版本字段，依赖合同基线、报价行快照和 ContractChange 历史。三者不能都用简单的“V1/V2”解释。

## 二、临时处理

专项裁决前：

1. 不修改设计版本编号规则；
2. 不新增报价 source 字段或合同版本字段；
3. 不把合同变更解释成合同新版本；
4. 不在页面用时间倒序冒充显式版本关系；
5. 不复制设计方案/报价/合同完整明细到统一视图。

## 三、T05 待裁决问题

1. 设计方案版本编号是否应为 `company + customer + property`？
2. 方案复制是否必须记录 sourceDesignId/parentVersionId，副本是否占用正式版本号？
3. 报价是否必须持久化 sourceQuoteId/supersededById，版本历史是否按显式链展示？
4. 合同是否引入独立版本，还是保持“合同基线 + 变更历史”？
5. 统一对象视图如何表达合同版本/合同变更修订？
6. 业主端展示哪些设计和报价版本？

## 五、验收最低要求

- 设计版本按正确作用域编号；
- 副本与版本有明确来源；
- 报价历史可显式追溯；
- 合同基线/当前合同/变更历史不混淆；
- 所有版本可在统一视图回读；
- 业主端不暴露内部版本敏感字段；
- 真实页面和契约测试通过。

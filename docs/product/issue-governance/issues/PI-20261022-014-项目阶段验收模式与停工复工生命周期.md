## 一、问题摘要

项目履约域有两个对象生命周期没有被完整承接：

1. **阶段验收模式丢失**：合同施工阶段快照已有 `StageAcceptanceMode`（`None / ConstructionDone / AcceptanceDone`），但项目阶段 `ProjectStage` 没有对应字段。当前所有有施工任务的阶段都进入同一条“任务完成后提交业主验收”的路径，无法区分无需验收、施工完成即完成、需要业主验收三种情况。
2. **项目停工/复工不可运营**：`ProjectStatus.Suspended` 已有状态、统计、风险预警和承接写入，但正常项目没有停工/复工 Provider、原因、责任人、预计复工日、影响范围、通知和恢复路径。停工只能被动展示，不能形成可追踪业务事实。

这两个问题都会直接影响项目状态、阶段完成条件、业主待办、计划偏差、材料和财务的下游判断，不能由研发自行补状态或从页面现状推断。

## 二、当前代码事实

### 2.1 阶段验收模式

- `ContractConstructionStage.acceptanceMode` 存在并进入合同施工计划快照；
- `ConstructionStageTemplate` / `CompanyConstructionStage` 均有验收模式；
- `ProjectStage` 当前字段只有 `status/progress/plannedStart/plannedEnd/actualStart/actualEnd/NotApplicable`，没有 `acceptanceMode`；
- `ProjectContext.submitAcceptance` 对适用阶段统一要求全部任务完成，并进入业主验收；
- 合同快照的验收模式在项目阶段生成后无法回读和参与完成判定。

### 2.2 停工/复工

- `ProjectStatus.Suspended` 存在；
- 项目总览、PM/店长统计、风险队列、业主旅程均能识别停工；
- 在跑项目承接 `CarryoverApplyContext` 可把承接基线写成停工；
- 正常项目 Provider 没有设置 `Suspended` 的动作，也没有恢复为 `Preparing/Ongoing/Accepting` 的恢复动作；
- 停工期间任务、阶段、材料下单、验收、应收和合同变更的阻断边界未冻结。

## 三、业务影响

- 无需业主验收的阶段仍可能等待业主，形成假待办；
- 需要业主验收的阶段可能与内部完成阶段混用同一状态语义；
- 项目“待验收/施工中/停工”在并发动作下可能互相覆盖；
- 停工无原因、无责任、无预计复工日，风险队列只能看结果不能处理；
- 停工对合同基准完工、预计完工、计划偏差、应收到期、材料订单、验收轮次的影响无法统一；
- App/Web 可能各自补不同的停工入口和恢复规则。

## 四、临时处理

专项裁决前：

1. 不新增 `ProjectStage.acceptanceMode` 字段或迁移；
2. 不按阶段名称猜测是否需要业主验收；
3. 不增加项目停工/复工按钮、接口或状态流转；
4. 不修改项目状态汇总、计划偏差、应收到期和通知逻辑；
5. 页面继续显示当前统一下游结果，但不得把“待验收”解释为正式验收策略；
6. 所有新结论必须先进入 T05 → T06/T12。

## 五、初始 T05 问题（已由 T06 回复）

1. `StageAcceptanceMode.None / ConstructionDone / AcceptanceDone` 的准确业务语义分别是什么？
2. `None` 是否是任务完成即阶段完成，还是仍需 PM/店长确认完成？
3. `ConstructionDone` 与 `AcceptanceDone` 分别由谁确认，是否需要业主本人？
4. 合同阶段快照的验收模式是否必须原样复制到项目阶段？合同变更/重排后是否更新执行阶段模式？
5. 项目停工由谁发起、审批、执行、恢复？BOSS、店长、PM、财务的边界分别是什么？
6. 停工是否要求原因分类、责任方、说明、预计复工日、附件、业主可见摘要和通知？
7. 停工期间应阻断哪些动作：阶段开工、任务推进、节点留证、业主验收、材料下单、到场、合同变更、应收到期？
8. 停工时已有待验收或整改轮次如何处理？恢复后是否继续原阶段、原验收单和原轮次？
9. 停工/复工是否生成计划偏差？是否重算预计完工、应收到期和材料要求到场日？
10. 停工/复工是否需要留痕、审计、业主端展示和跨端恢复路径？

## 五-A、T06/T12 裁决结果

业务答复：`ANS-BIZ-20261022-008`  
研发交接：`T12-BIZ-20261022-008`  
业务决策：`DEC-087`、`BR-053`  
实现缺口：`GAP-066`

| 裁决项 | 结论 |
| --- | --- |
| `None` | 不生成阶段验收或业主待办；有效任务和证据满足后系统自动完成阶段 |
| `ConstructionDone` | 项目经理内部确认施工完成，BOSS/本店店长可代确认；不生成业主待办 |
| `AcceptanceDone` | 员工提交，业主本人确认/驳回；员工不得代确认 |
| 合同快照继承 | 立项时复制到 `ProjectStage`；日期重排不改模式；生效后的变化仅来自合同变更并影响未开始阶段 |
| 停工发起/审批 | PM 发起，店长/BOSS 审批；PM 不得自批；财务和其他业务角色不得停复工 |
| 停工必填 | 原因、责任方、说明、预计复工日、影响范围、业主摘要、附件条件和审批审计 |
| 停工阻断 | 阶段开工、任务推进、节点推进、新验收、新材料下单、整改施工阻断；到场、既有 Pending 验收、合同变更、财务事实例外 |
| 验收恢复 | 原阶段、原验收单、原轮次继续；停工期间不新开轮次 |
| 计划/应收/材料 | 停工不自动顺延；客户原因走合同工期变更，非客户原因走计划偏差；正式基准变化才重算应收到期 |
| 通知/审计/跨端 | 申请、审批、日期变化、复工、通知和回执全留痕；三端消费同一服务端投影 |

## 七、验收最低要求

- 三种验收模式均有明确主体、完成条件和异常恢复；
- 合同快照模式与项目阶段执行模式可追溯；
- 无需验收阶段不产生业主假待办；
- 需业主验收阶段必须由业主本人确认；
- 停工/复工只有一个合法入口，重复动作幂等，非法状态转换被拒绝；
- 停工原因、责任、时间、预计复工日和影响范围可查询；
- 停工/复工对阶段、任务、材料、应收、计划和通知的影响可对账；
- App/Web 状态、金额、待办和恢复路径一致；
- 真实页面、真机/浏览器、接口和越权证据齐备。

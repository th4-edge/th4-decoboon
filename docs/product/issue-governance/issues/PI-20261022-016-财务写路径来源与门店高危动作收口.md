## 一、问题摘要

财务域已有较完整的应收、应付、收付款、退款、台账、结算和凭证对象，但写路径存在三类需要统一收口的问题：

1. **来源边界**：`finance/receivable/save` 和 `finance/payable/save` 可以手工创建多种应收/应付类型，当前没有强制来源单据和来源类型，可能绕过合同、采购、工资单或合同变更闭环。
2. **门店范围**：部分按 ID 修改的财务写接口只校验企业，没有统一按目标对象门店执行数据范围校验；同企业门店财务/店长可能通过已知 ID 修改他店财务对象。
3. **跨端与角色**：App 有收款冲正、Web 无入口；Web 店长可见凭证生成，但后端只允许 BOSS/财务；期初资金和账龄入口在两端不完整。

这些问题不是单一页面缺陷，而是财务事实主权、数据范围和动作主体没有形成同一写路径契约。

## 二、当前代码事实

### 2.1 手工来源

- `finance/receivable/save` 可由 BOSS/财务/店长创建任意其他应收，并自动绑定项目合同，但没有 `sourceType/sourceId`，也没有合同应收上限校验。
- `finance/payable/save` 可创建 Material、Salary、Project、Supplier、EmployeeSalary、EmployeeCommission、Expense、Other 等类型；仅材料计划关联可选，未强制已有采购/工资/合同来源。
- `Ledger.save` 已有较严格的“手工只补无来源账务”文字拦截，但应收/应付保存没有同等来源门禁。

### 2.2 按 ID 写入的门店范围

静态检查发现以下路径未统一使用 `DataScopeContext + DataScopeSpecification` 校验目标对象：

- `finance/receivable/update`：`findById` 后仅校验企业；
- `finance/payable/update`：`findById` 后仅校验企业；
- `finance/payment/save`：单笔/多笔付款按应付 ID 加载，未统一校验应付所属门店；
- `finance/refund/save`：按原收款 ID 加载，除企业外未统一校验原收款门店；
- `finance/settlement/update`：按结算 ID 加载，除企业外未统一校验项目/结算门店；
- `document/voucher/build`：按企业加载流水 ID，未显式按当前门店范围过滤。

这与 `DEC-065` / `DEC-081` 的门店范围规则和 `AGENTS.md` 的“自定义详情/更新/删除必须使用 DataScopeContext + DataScopeSpecification”冲突。

### 2.3 角色和跨端

- `VoucherContext.build` 只允许 BOSS/Finance；
- Web `useFinanceAccess().canWrite` 包含店长，台账页显示“生成凭证”按钮；
- App 有 `receipt-reversal`，Web 无收款冲正入口；
- App 有期初资金完整页面，Web 只有 API 和工作台摘要；
- 后端有 `finance/aging/report`，App/Web 均未接页面。

## 三、业务影响

- 可绕过采购/工资/合同变更形成重复应收或应付；
- 同企业跨店读写财务单据，违反门店财务/店长本店范围；
- 高风险财务动作在 App/Web 不一致，用户切换端会失去处置路径；
- 店长看到可执行按钮但被后端拒绝，形成误导；
- 账龄、期初资金和高危动作没有统一的能力矩阵，不利于后续验收。

## 四、临时处理

专项裁决/研发前：

1. 不新增应收应付手工类型；
2. 不扩大财务写接口的门店范围；
3. 不放宽收款冲正、退款、结算、凭证的高危动作主体；
4. 不在 App/Web 单端补“临时替代入口”；
5. 不把 `PartnerPrice` 退场与本问题混在一起，仍由 `PI-20261022-004` 推进；
6. 不以页面按钮可见作为权限依据。

### 8.1 来源与手工类型

1. 手工应收只允许“其他应收”；
2. 手工应付只允许“其他应付”和“费用支出”；
3. 首期款、进度款、尾款、质保金必须来自合同付款节点或已生效合同变更；
4. 材料款、工人工资、员工工资、员工提成、项目款、供应商款必须来自采购、工资项、提成项、劳务结算或历史承接；
5. 一个自动来源最多生成一条应收/应付；重复来源必须返回原事实或明确冲突；
6. 手工其他应收不改变合同额，也不受合同应收计划上限约束，但不得用合同节点类型伪装。

### 8.2 门店范围

1. 所有按 ID 财务写入必须以目标对象门店为业务范围；
2. 门店财务、店长只能写本店；跨店返回 403/404；
3. BOSS、总部财务可操作全企业，但不同门店的应付、流水或凭证不得合并为一张单；
4. 来源对象、项目、目标单据、核销/台账/凭证必须同企业；需要门店的对象必须同店；
5. 空门店历史对象不得由门店角色自动认领，只能按明确迁移策略处理。

本次静态核对在原清单外新增确认：

- `finance/ledger/update` 未调用 `requireLedgerScope`；
- `finance/settlement/retention-release` 只校验企业；
- `OpeningBalance` 无 `store` 字段，现有唯一键无法区分门店；
- `finance/payment/save` 多笔付款只校验首张应付项目，核销明细门店取操作人门店。

### 8.3 凭证角色

- BOSS、总部财务、门店财务、店长可生成、查看和重打权限范围内的凭证；
- 店长、门店财务限本店；总部财务/BOSS 全企业；
- 模板配置、凭证生成、凭证重打为独立能力；
- 来源流水、凭证记录和多笔合并必须同门店。

### 8.4 App/Web 强制边界

- 收款冲正、期初资金、账龄均必须 App/Web 双端完整可达；
- 两端同角色、同门店、同金额、同状态、同阻断、同异常恢复和同审计；
- 期初资金按门店归属，历史空门店显示待核验；
- 账龄共用 `finance/aging/report`，到期日缺失进入“待确认账龄”，分母为 0 显示暂无基期。

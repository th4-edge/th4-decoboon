## 一、问题摘要

设计师 App 的底层业务页面已能承载客户、设计、报价、签约、项目和履约协作，但一级信息架构仍停留在旧模型：

```text
工作台 / 设计 / 报价 / 项目 / 我的
```

用户已冻结目标模型：

```text
工作台 / 客户 / 签单 / 项目 / 我的
```

当前“客户”和“签约”不是设计师 Tab，进入后底部导航会错误回落到“工作台”；五个业务阶段也没有统一为“下一次动作队列”。同时，App 与 Web 对量房、设计、谈单、签约的查询参数、分页、风险和下一步存在差异。

本问题不新建一套业务页面，也不改变角色权限；目标是把现有能力按已冻结的信息架构重组，并形成 App/Web Provider 对账基线。

## 三、业务影响

1. 设计师无法从一级导航稳定理解“客户经营、签单推进、项目履约”三块职责。
2. 客户和项目超过一页后，搜索结果、阶段计数和筛选结果可能不完整，形成错单、漏单和伪计数。
3. App 自行重算风险和下一步，会与 Web/后端产生同对象不同结论。
4. 未量房对象进入待设计、已生效项目仍留在待签约等阶段边界问题，可能让设计师跳过前置事实或重复处理。
5. 合同页出现写动作，破坏“项目内只读合同”的用户已确认边界。

## 四、临时处理

在 D2 实施和独立验收前：

- 不新增同义 Provider；
- 不扩大 Designer 权限；
- 不修改金额、成本、状态机、DDL 或合同写语义；
- 不把当前工作区的量房候选实现直接宣称为已验证基线；
- 不把“页面有入口”当作五阶段闭环完成。

## 五、T05 待裁决问题

以下问题进入编码前需由业务事实源裁决：

1. **待我设计的入站资格**：是否必须存在已完成量房事实？无房屋、已预约未量房、量房完成未出结论分别应进入哪个队列？
2. **待我签约的出站条件**：合同生效并立项后是否立即离开待我签约，只从项目详情查看合同？还是保留历史筛选？
3. **待我跟进的服务端分桶**：逾期、今日、3 天内、未安排是否作为正式服务端队列参数，避免 App/Web 各取 100 条后本地分桶？
4. **待我量房双入口**：客户 Tab 与签单 Tab 同时进入时，是否复用同一页面，仅以来源上下文决定返回路径和 Tab 激活态？

在取得 `T06/T12` 前，只允许完成 D2 导航壳层和纯展示对账，不改变入站/出站队列语义。

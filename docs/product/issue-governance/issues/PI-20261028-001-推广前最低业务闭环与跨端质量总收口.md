## 一、问题摘要

装得清已经具备较完整的业务对象和页面，但当前仍不满足首发推广条件。问题不是单一功能缺失，而是：

1. 三仓发布基线不干净，无法确定唯一发布候选；
2. App/Web/后端的跨端治理门禁尚未全部通过；
3. 部分治理脚本仍冻结旧业务决策，与最新角色信息架构冲突；
4. Web 存在研发术语、裸枚举和大页固定值等明显质量问题；
5. Web 视觉 Token 没有真正收口，页面语法和视觉一致性不足；
6. 大量业务信息存在展示，但未证明能推动判断、行动、交接、确认、留证或对账；
7. 核心业务域仍有多个 P0/P1 未完成独立验收；
8. 没有以一个真实项目证明“合同生效 → 现场 → 验收整改 → 业主回读 → 收付款/成本”的最基本闭环。

## 四、已确认的缺口

### 4.1 发布候选不唯一

三仓均存在未提交改动或与远端分叉。当前无法回答：

- 首发版本由哪个 commit 构建；
- 哪些脏文件属于首发；
- 哪些属于后续功能；
- 如果发布失败，回滚到哪个已验证基线。

### 4.2 门禁与业务决策脱节

App `check:home` 仍检查旧设计师首页顺序，而业务侧已形成由 `DPR-D01` 起头的设计师信息架构决策。治理脚本必须绑定当前决策版本，不能把旧实现固定成永久正确答案。

### 4.3 信息作用未验收

当前已有页面、字段和统计，但没有逐项证明：

- 信息是否帮助判断；
- 是否能触达下一步；
- 是否明确责任人；
- 是否能留证；
- 是否能对账；
- 失败时能否恢复。

专项审计已完成两批：

- `docs/product/audits/2026-10-28-客户到诉求录入信息下游使用审计.md`：客户登记到客户诉求前段 52 个录入字段/语义组中，22 个未产生业务动作或形成重复录入；P1 12、P2 7、P3 3。
- `docs/product/audits/2026-10-28-设计到成本录入信息下游使用审计.md`：设计、报价、合同、项目、任务、材料、变更、验收和收付款链路新增确认 17 个信息断点；P1 7、P2 8、P3 2。

当前全链首轮累计 39 个可逐项复核的问题点：P1 19、P2 15、P3 5。该数量是字段/信息簇级下限；工人薪酬、费用报销、复杂多门店经营和真实页面行为仍需后续专项验证。

### 4.4 Web 视觉与页面语法不统一

当前 Web 同时存在指标看板、表格、三栏工作面、卡片目录等页面语法。仅修局部 CSS 不能解决“丑”，必须按页面母型、信息层级、Token、七态和真实渲染门禁统一重建核心页面。

### 4.5 基本闭环没有真实项目证据

已有大量领域测试和开发证据，但尚缺一个真实项目同时覆盖：

```text
合同生效 → 项目/阶段/任务 → 现场留证
→ 变更 → 材料 → 阶段验收/驳回 → 整改/复验
→ 收付款/成本完整性 → 业主授权回读
```

## 五、影响

- 不能安全判断哪个版本可推广、可回滚；
- 同一业务事实可能在 App/Web/业主端表现不同；
- 用户看到大量信息，但不知道今天先做什么；
- Web 视觉不达标会直接降低销售演示和企业付费意愿；
- App 细节缺陷会让现场人员失去信任并回到微信群/Excel；
- 提前推广会把开发缺陷放大成客户口碑和交付事故。

## 六、临时处理

1. 暂停新增非核心功能和跨域扩展；
2. 三仓先冻结首发范围，清点脏文件并分域提交/隔离；
3. 修复与最新业务决策冲突的治理脚本；
4. 关闭 Web 当前静态门禁失败；
5. 建立核心闭环对账矩阵和真实项目走查；
6. 在 G0–G7 全部通过前，不得对外宣称“完整闭环”“已验收”“可规模化”。

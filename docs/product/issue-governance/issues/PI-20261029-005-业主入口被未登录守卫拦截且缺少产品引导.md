| 项 | 内容 |
| --- | --- |
| 问题 ID | `PI-20261029-005` |
| 当前状态 | `DEV_VERIFIED_PENDING_USER` |
| 严重级别 | P1 |
| 发现日期 | 2026-10-29 |
| 来源 | 用户点击“我是业主，进入我的家”无反馈 |
| 所属领域 | 公共路由、业主入口、产品引导 |
| 变更记录 | `CHG-20261029-010-owner-entry-public-guide` |

## 根因

`roles/guard.ts` 在未登录时只放行业主 `/pages/auth/*`，业主入口 `/pages/owner/enter` 被静默拦截，点击没有反馈。

## 影响

- 已受邀业主从首页点击可能无法继续；
- 未受邀用户不知道装得清是什么、为什么需要邀请；
- 用户会把“无授权”误解为系统故障；
- 不利于从业主视角建立产品价值和信任。

## 处理

1. 新增公共页面白名单：首页、业主入口、邀请页、未归属页、协议/隐私、关于、业主分享页。
2. 无邀请的业主入口改成产品说明页：
   - 装得清是装企项目协同工具；
   - 授权后可看进度、照片、材料变更、付款计划、验收与整改；
   - 说明如何通过装修公司邀请/项目码进入；
   - 明确不向业主推荐装修公司；
   - 提供返回首页和切换账号。
3. 有邀请但未预览项目时，仍显示手机号验证按钮。
4. 不增加业主公开注册或平台触点。

## 业主入口引导模型

### 1. 不先判断“是不是业主”

手机号授权前，系统无法确认微信用户与项目的关系。页面不能直接显示“你不是业主”，否则既可能误伤已受邀业主，也会泄露“某手机号是否存在客户档案”这类本不应暴露的信息。

统一表达为：

> 当前微信还没有可进入的装修项目。

“是否为业主”只在手机号验证和项目授权校验完成后由服务端确认。

### 2. 按入口上下文分流

| 入口状态 | 页面反馈 | 主行动 | 不做什么 |
| --- | --- | --- | --- |
| 无邀请、未登录 | 说明装得清是装修公司的项目协同工具，展示进入后可见内容与进入条件 | 返回首页；按装修公司邀请卡片或项目码重新进入 | 不要求公开注册，不采集手机号，不请求项目数据 |
| 有业主邀请、未验证 | 显示“项目邀请已收到”和验证步骤 | 手机号快捷登录，核对预留手机号后进入本人项目 | 不在授权前展示项目事实 |
| 有项目码、未验证 | 说明项目码用途和身份核对方式 | 手机号快捷登录并校验客户档案手机号 | 不把项目码当作身份凭据 |
| 微信已绑定装修公司员工 | 明确提示业主端需由业主本人微信进入 | 更换微信；员工从企业入口登录 | 不把员工会话降级或冒充业主 |
| 邀请失效/号码不一致 | 说明具体原因和可执行恢复路径 | 联系装修公司项目负责人重新发送或核对号码 | 不显示泛化“进入失败”，不暴露是否存在其他客户 |
| 已是业主 | 直接进入我的家 | 查看本人项目 | 不重复接受邀请或重复授权 |

### 3. 对业主做“价值说明”，不做“平台获客”

业主入口需要回答“这是什么、我为什么需要、我现在能做什么”，但表达必须遵守业主端是装企容器的边界：

- 叙事主体是当前装修公司，装得清是项目协同与记录存证工具；
- 价值用业主能感知的结果表达，例如施工进度、现场照片、材料与变更、付款计划、阶段验收和整改记录；
- 引导动作是打开装修公司发来的邀请卡片或项目码，不是“立即注册装得清”；
- 不推荐其他装修公司，不生成平台销售线索，不主动触达未授权业主；
- 后续营销素材可采用“装企品牌 + 装得清记录能力”的联合叙事，但不能把业主端包装成独立的装得清获客产品。

这并不削弱营销价值。它把营销重点从“拉业主注册平台”转为“帮助装企把真实履约过程变成可感知的服务品牌”，既培养业主对透明履约的期待，也不破坏装企与业主之间的服务关系。

## 验证

- H5 点击后 URL 正确进入 `/pages/owner/enter`。
- 无邀请页产品说明完整。
- 邀请场景按钮存在。
- 390×844 无横向溢出。
- 契约、类型检查、构建和分包 PASS。

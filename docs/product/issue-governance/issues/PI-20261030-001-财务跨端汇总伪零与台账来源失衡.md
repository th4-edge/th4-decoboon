## 一、问题摘要

在同一个隔离企业、同一个后端和同一角色下：

1. App 应收、收款、付款页面顶部汇总在接口失败时显示 0，但列表仍有真实记录；Web 同页返回正确金额。
2. 台账存在来源层不守恒：同一 ¥748.73 收款生成两条台账，另有 ¥500 付款没有台账，导致净现金流偏差 ¥1,248.73。
3. 手工应收/应付页面暴露 `BR-055` 明确禁止的类型；后端对应 Save Provider 未见手工来源/类型白名单校验。

## 二、当前事实

| 维度 | Web | App | DB/API |
| --- | ---: | ---: | ---: |
| 应收总额 | ¥135,672.23 | ¥0 | ¥135,672.23 |
| 应收已收 | ¥14,225.87 | ¥0 | ¥14,225.87 |
| 应收待收 | ¥121,446.36 | ¥0 | ¥121,446.36 |

| 付款 | ¥9,500 / 19 | ¥0 / 0 | ¥9,500 / 19 |

- 收款来源台账：¥14,225.87，比有效收款多 ¥748.73；重复来源 1 笔。
- 付款来源台账：¥9,000，比业务付款少 ¥500；缺台账 1 笔。
- 空门店应收 ¥748.73、空门店应付 ¥2,000、空门店项目 1 个，导致全公司数不等于 A/B/C 三店合计。

## 三、证据

- 页面与文本：`raw/screenshots/`、`raw/notes/`
- API：`raw/api/finance-*.json`
- SQL 不变量：`raw/sql/accounting-invariants-latest.json`
- 复跑脚本：`check-accounting-invariants.sh`
- 跨端根因：App `receivables/receipts/payments` 使用 `financeApi.summary()`，Web 对应页使用部门 report。

## 四、业务影响

- 财务和 Boss 在 App 端会把有业务数据误读为 0，无法判断今日回款与付款。
- 台账净现金流不正确，无法作为资金对账依据。
- 手工应收/应付可生成错误来源类型的财务事实，破坏“应收≠收入、应付≠成本”的来源边界。
- 跨端同源与业务闭环均不能通过。

## 五、修复门禁

1. App 应收、收款、付款汇总改用与 Web 相同的部门报告，或统一使用已验收的公司汇总 Provider；失败时显示“暂不可确认”。
2. 台账写路径保证 `source + sourceId` 唯一；重复提交幂等；付款必须唯一写台账；补历史双记/缺记修复脚本或迁移。
3. 手工应收仅允许其他应收；手工应付仅允许其他应付/费用支出；前端选项与后端 Save 双重校验。
4. Web 对 `outstanding=0` 不展示“登记收款”。
5. 店长台账文案与实际能力一致，不得写“只读”同时暴露写动作。
6. 空门店历史对象提供 BOSS/总部财务核验与迁移处置入口。

## 六、验收最低要求

- Web/App 同角色、同数据范围、同页面汇总金额一致。
- 汇总失败、项目查询失败、凭证失败均不得显示 0。
- 重复收款、重复付款、并发提交均不生成重复台账。
- 每条有效收付款与台账来源一一对应。
- A+B+C 三店合计与全公司差额可由“未归属门店”明确解释。
- 手工受限类型在页面不可选、接口直调也拒绝。
- 成本不完整时利润和毛利率继续为空。

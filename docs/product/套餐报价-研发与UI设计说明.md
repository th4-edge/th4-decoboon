## 1. 一句话结论

> 套餐是企业预先配置的报价模板，套餐报价是客户和具体房屋在某一版本、某一时点形成的不可覆盖商务快照。

系统必须同时守住五条线：

1. 套餐模板是企业标准，客户报价是客户事实，两者不能混为一张表。
2. 套餐牌价是折前价，折扣率单独记录和应用。
3. 金额、成本、税金和调整差额由服务端计算，前端只做预览和交互。
4. 报价先形成 `Draft`，调整完成后提交；提交后只读；驳回后新建版本，不覆盖旧版本。
5. 正常业务不绕过报价：接受报价后签合同，合同签约并生效后才创建项目。[已实现/业务已确认]

## 2. 业务问题与设计目标

### 2.1 要解决的真实问题

中小装企常见问题：

- 每个设计师使用自己的 Excel，套餐口径和价格逻辑不一致。
- 套餐名称相同，但包含项目、品牌、规格、数量和排除项不明确。
- 客户扣减、升级、替换后，原始套餐、调整原因和最终金额无法追溯。
- 套餐模板修改后，历史报价被误解或被动变化。
- 设计分项和套餐项目重复或冲突，形成重复报价。
- 老板只能看到总价，无法判断成本是否完整、报价是否可解释。
- 业务员、设计师、项目经理和财务看到同一报价时，数据权限和成本可见性不清。

### 2.2 设计目标

- 让套餐可复用、可解释、可追溯。
- 让套餐报价从客户+房屋+套餐+面积+折扣稳定生成。
- 让套餐、设计、客户报价、合同、项目和财务使用同一业务事实链。
- 让不同角色只看到本岗位需要的数据，成本不因前端隐藏而失去服务端保护。
- 让页面可以直接回答“当前是什么状态、下一步做什么、谁来做、异常怎么办”。

### 2.3 明确不做什么

- 不把完整大型 ERP 的仓库、批次、税率、供应商门户和复杂审批平铺到套餐首屏。
- 不让前端直接提交报价总价、成本或调整差额作为最终事实。
- 不让套餐模板直接成为合同或项目。
- 不用 `0` 成本计算伪利润。
- 不在当前阶段为每个企业建设完全独立的报价引擎；先以统一模型+可配置字段满足主流场景。
- 不把套餐分区等同于设计方案的房间区域。两者可以匹配，但不是同一对象。

## 3. 领域对象模型

### 3.1 对象层级

```text
企业标准层
CatalogItem 企业可售项目库
  └─ PackageTemplate 套餐模板
       ├─ PackageSection 套餐分区
       ├─ PackageLine 套餐标准项目行
       ├─ PackageTemplateItem 套餐差价项定义
       └─ PackageRule 差价/规则配置

客户事实层
Quote 客户报价版本
  ├─ QuoteLine 报价行快照
  ├─ QuoteComponent 报价行销售/成本组件快照
  ├─ QuoteAdjustment 调整事实（目标设计；当前以 QuoteLine 角色表达）
  └─ 版本链接/历史关系（目标设计）

下游履约层
Quote Accepted
  └─ ProjectContract 合同
       └─ ContractLine 合同成本/金额快照
            └─ Project 项目
```

### 3.2 核心对象职责

| 对象 | 业务回答 | 是否客户事实 | 变化边界 |
| --- | --- | --- | --- |
| `CatalogItem` | 企业能卖什么、标准销售价和成本价是什么 | 否 | 企业主数据可持续维护 |
| `PackageTemplate` | 企业预先定义的标准整装方案是什么 | 否 | 模板变化只影响未来生成的新报价 |
| `PackageSection` | 套餐按什么客户可理解的分组展示 | 否 | 只负责套餐展示结构，不等同设计空间 |
| `PackageLine` | 某套餐在标准面积下包含什么、多少、允不允许扣减 | 否 | 来自有效 `CatalogItem` |
| `PackageTemplateItem/PackageRule` | 后续可配置的差价、升级和替换规则 | 否 | 当前能力不完整，不能假装已自动计算 |
| `Design/DesignItem` | 这个房屋的设计方案实际选了什么、做多少 | 方案事实 | 设计修改不能回写已快照报价 |
| `Quote` | 某客户、某房屋、某时点收到的报价版本是什么 | 是 | `Draft` 可调，提交后只读 |
| `QuoteLine` | 报价总价在项目上的分解、成本和来源是什么 | 是 | 随草稿调整；提交后冻结 |
| `QuoteComponent` | 某报价行的材料、人工、运输、服务等组成是什么 | 是 | 报价行冻结合同后不改 |
| `ProjectContract` | 客户确认后的正式经营约定是什么 | 是 | 签约时冻结合同金额和签约成本 |
| `Project` | 合同生效后的履约单元是什么 | 是 | 只能从有效合同创建 |

### 3.3 对象关系图

```text
CatalogItem
  ├─ 被 PackageLine 引用
  └─ 被 DesignItem 引用

Customer 1 ── N Property
Property 1 ── N Quote
Quote N ── 1 PackageTemplate（来源引用）
Quote N ── 1 Design（套餐/自定义/混合模式可不同）
Quote 1 ── N QuoteLine
QuoteLine N ── 0..1 DesignItem
QuoteLine N ── 0..1 PackageLine
QuoteLine N ── 0..1 CatalogItem
QuoteLine 1 ── N QuoteComponent

Quote Accepted ── 1 ProjectContract
ProjectContract Effective ── 1 Project
```

核心不变量：

- 报价必须绑定明确的 `Customer + Property`。
- 套餐报价必须绑定当前企业有效套餐。
- 报价行必须保存生成时的展示、数量和价格快照，不能只保存来源 ID。
- 同一房屋最多一份客户确认报价，最多一个项目。
- 合同金额调整必须通过合同变更，不通过修改历史报价实现。

## 4. 真实业务场景闭环

### 场景一：负责人建立标准套餐，设计师快速报价

- 使用人：BOSS、设计师。
- 触发事件：企业需要把常用整装方案标准化，避免每单重新组价。
- 当前动作：BOSS 在 App 新建套餐，填写标准面积、折前牌价、默认折扣，建立分区和项目行；设计师选择客户、房屋、套餐、实际计价面积和本次折扣。
- 系统下一步：服务端按面积比例计算折前金额，按折扣计算折后金额，按税率计算报价合计和成本，生成 `Draft`，并生成套餐项目行快照。
- 异常处理：套餐无有效项目行、面积小于等于零、客户和房屋不一致、套餐已停用或不属于当前企业时阻断创建。

### 场景二：同一客户有多套房屋

- 使用人：设计师。
- 触发事件：客户同时装修婚房和父母房，两套房屋报价口径不同。
- 当前动作：设计师在报价创建页必须显式选择房屋，不能依赖客户默认房屋。
- 系统下一步：报价、合同、项目和后续收款均绑定该房屋；其他房屋的报价不覆盖本次报价。
- 异常处理：未选房屋、选择了其他客户房屋、房屋已有确认报价或项目时阻断，并给出明确下一步。

### 场景三：客户扣减、升级和增项

- 使用人：设计师。
- 触发事件：客户不需要原套餐某项，希望升级瓷砖并增加中央空调。
- 当前动作：设计师在 `Draft` 报价中执行扣减、升级、替换和增项，选择来源项目、数量和调整原因。
- 系统下一步：服务端重新计算折前小计、折扣、税金、报价合计和成本；基础行保留历史，不以物理删除掩盖调整。
- 异常处理：已提交或已接受报价不能调整；不可扣减项不能扣减；调整后金额或数量非法时阻断；并发修改时以服务端最终状态为准。

### 场景四：设计方案与套餐形成混合报价

- 使用人：设计师。
- 触发事件：客户选择了标准套餐，但设计方案在区域和分项上做了个性化调整。
- 当前动作：设计师在完成方案后选择套餐生成混合报价，系统匹配套餐行与设计分项。
- 系统下一步：形成 `Matched / PackageOnly / DesignOnly / QuantityChanged / Deduct / Upgrade / Replace` 差异，设计师逐项确认、忽略或调整。
- 异常处理：仍存在 `Pending` 差异时禁止提交；自动匹配不确定时必须保留为人工待确认，不得静默选择。

### 场景五：报价进入合同、项目和财务

- 使用人：BOSS/合同权限角色、项目经理、财务。
- 触发事件：客户接受报价。
- 当前动作：生成合同，签约并标记生效。
- 系统下一步：合同冻结金额和签约成本，项目从生效合同创建；报价变为 `Converted`，报价行进入合同/项目基线。
- 异常处理：合同未签约或未生效不能创建项目；成本不完整时利润和毛利率返回空值并显示“成本未完整”，不得用零成本计算。

## 5. 套餐模板设计

### 5.1 `PackageTemplate` 字段

| 字段 | 业务含义 | 规则 |
| --- | --- | --- |
| `templateId` | 套餐主键 | 雪花 ID，企业内唯一 |
| `company` | 企业归属 | 必填，服务端固定为当前企业 |
| `name` | 套餐名称 | 必填，建议包含适用面积或范围 |
| `area` | 标准面积 | 大于 0，表示牌价所对应的基准面积 |
| `price` | 套餐牌价 | 大于等于 0，必须是折前价 |
| `discount` | 默认折扣率 | `0 < discount <= 1`，例如 `0.9` |
| `cost` | 标准成本估算 | 服务端由项目行计算，不接受前端覆盖 |
| `items` | 套餐项目行 | 至少一行才可正式使用 |
| `measures` | 差价项规则 | 目标设计；当前存有模型不代表自动计价已完成 |
| `criterions` | 适用范围/说明 | 建议包含包含项、排除项和风险说明 |

`[禁止]` 把已经打完折的成交价直接填入 `price`，否则系统再次应用折扣会形成重复优惠。

### 5.2 `PackageSection` 字段

| 字段 | 业务含义 | 规则 |
| --- | --- | --- |
| `groupId` | 分区主键 | 雪花 ID |
| `name` | 分区名称 | 如全屋基础、厨房、卫生间、主材区 |
| `spaceTypes` | 适用空间类型 | 用于混合报价匹配，不等同于实际房间 |
| `maxDeleteNum` | 可扣减数量上限 | `[目标设计]` 当前未参与服务端计价/校验 |
| `priority` | 展示顺序 | 越小越前 |

### 5.3 `PackageLine` 字段

| 字段 | 业务含义 | 规则 |
| --- | --- | --- |
| `item` | 来源报价项目 | 必填，必须属于当前企业且有效 |
| `section` | 所属套餐分区 | 必填 |
| `name/brand/spec/unit` | 套餐内展示快照 | 默认继承目录项目，可做套餐展示覆盖 |
| `quantity` | 数量说明 | 可读文本，不等于最终计价数量 |
| `quantityFactor` | 标准面积数量系数 | 大于 0，是当前计价的核心数量字段 |
| `pricingMethod` | 计价方式 | 材料+人工、仅材料、仅人工、固定总价 |
| `included` | 默认是否包含 | 生成报价时默认是否纳入 |
| `deductible` | 是否允许扣减 | 影响客户扣减是否可执行 |
| `criterions` | 项目说明 | 用于报价解释和谈单 |
| `sort` | 排序 | 分区内稳定排序 |

### 5.4 数量设计

标准面积下的报价行有效数量：

```text
lineQuantity = quantityFactor × (quoteArea / template.area)
```

数量系数必须表达“标准套餐在这个标准面积下包含多少”，不能把客户房屋实际工程量直接写死到模板中。

推荐配置示例：

| 项目 | 单位 | 数量系数 | 业务解释 |
| --- | ---: | ---: | --- |
| 客餐厅瓷砖 | ㎡ | 35 | 100㎡标准套餐包含约 35㎡ |
| 厨房柜体 | m | 3.5 | 标准厨房柜体长度 |
| 卫生间防水 | ㎡ | 12 | 标准卫生间防水面积 |
| 全屋开关插座 | 个 | 42 | 标准数量 |

### 5.5 模板状态和版本

`[目标设计]` 推荐套餐模板增加：

- `status`：`Draft / Active / Archived`。
- `revision`：模板修订号。
- `effectiveAt / archivedAt`：启用和归档时间。
- `lastUsedQuoteCount` 或按需查询使用情况，不把统计结果当作业务事实。

规则：

- 只有 `Active` 套餐可用于新报价。
- 已被历史报价引用或已生成的套餐行不允许物理删除；应停用或归档。
- 模板更新只影响之后新建的报价，不能回写历史 `Quote`/`QuoteLine`。
- 如果需要对历史报价做完整审计，应保存套餐名称、标准面积、牌价、默认折扣和套餐修订号快照。

当前代码已有“套餐行存在历史报价时禁止删除”的保护，但尚无正式套餐生命周期和修订机制。[部分实现]

## 6. 报价模式与生成流程

### 6.1 三种模式

| 模式 | 入口 | 必选上下文 | 典型场景 |
| --- | --- | --- | --- |
| `Package` | 报价列表/套餐模板 | 客户、房屋、套餐、实际计价面积、折扣 | 标准化整装快速报价 |
| `Custom` | 设计方案 | 已具备区域和分项的完成方案、折扣 | 高度个性化设计报价 |
| `Hybrid` | 设计方案的确认报价页 | 设计方案、套餐模板、折扣 | 套餐基线+设计差异 |

### 6.2 套餐报价标准流程

```text
选择客户
  -> 选择该客户名下房屋
  -> 选择生效套餐
  -> 填写实际计价面积
  -> 选择本次折扣
  -> 服务端计算金额/成本/税
  -> 生成 Quote Draft
  -> 处理扣减/升级/替换/增项
  -> 服务端重算
  -> 确认无待处理差异
  -> 提交客户
  -> 客户接受或驳回
  -> 接受后创建合同
  -> 合同签约并生效
  -> 创建项目
```

### 6.3 报价创建前置条件

- 当前员工已登录且拥有报价创建能力。
- 客户属于当前企业数据范围。
- 房屋属于所选客户且在当前企业数据范围。
- 套餐属于当前企业、处于可用状态、项目行有效。
- 实际计价面积大于 0。
- 折扣率在 `(0,1]` 范围内。
- 同一房屋不存在已接受或已转化报价，不存在项目。
- 混合报价必须满足设计方案状态和分项完整性要求。

### 6.4 重复报价规则

- 套餐报价版本按“同一企业 + 同一客户 + 同一套餐模板”递增。[已实现]
- 自定义报价版本按同一设计方案递增。[已实现]
- 客户驳回后通过 `sourceQuoteId` 生成新 `Draft`，原报价保持 `Rejected`。[已实现]
- 同一房屋最终只允许一份 `Accepted/Converted` 报价；客户接受其中一份时，同房屋其他草稿或已提交报价转为 `Superseded`；同房屋存在其他已接受报价时必须阻断。[已实现]
- `[目标设计]` 新报价应保存 `rootQuoteId` 和 `sourceQuoteId`，用于把多个版本归并为一个报价机会；当前仅有递增版本，没有稳定机会根节点。

## 7. 金额、成本和利润口径

### 7.1 套餐基准计算

```text
areaRatio = quote.area / template.area
packageUndiscountedAmount = template.price × areaRatio
discountedAmount = packageUndiscountedAmount × quote.discount
taxAmount = discountedAmount × quote.taxRate
quote.amount = discountedAmount + taxAmount
```

示例：

```text
标准面积：100㎡
套餐牌价：158,000 元
实际计价面积：118㎡
本次折扣：0.90
面积比例：1.18
折前金额：186,440.00 元
折后金额：167,796.00 元
暂按 5% 税：8,389.80 元
客户报价合计：176,185.80 元
```

### 7.2 套餐成本

```text
lineCost = CatalogItem.costPrice × PackageLine.quantityFactor × areaRatio
templateCost = Σ lineCost
quoteCost = Σ 有效报价行成本
```

成本含义：

- 套餐标准成本是报价参考成本，不是采购到货后的实际成本。
- 目录成本变化后，历史报价不能回写。
- 实际材料成本只在采购到货/入库等实际事实发生时累计。
- 人工、辅料、运输、安装、定制生产等缺失时，必须标记成本不完整。

### 7.3 报价行金额分摊

套餐是整体牌价报价，但报价行必须能向客户解释。

推荐口径：

```text
lineUndiscountedAmount = packageUndiscountedAmount × allocationWeight / Σ allocationWeight
Σ lineUndiscountedAmount = packageUndiscountedAmount
```

`allocationWeight` 推荐优先使用：

1. 明确的套餐行分摊权重；
2. 目录销售参考价 × 有效数量；
3. 成本分摊权重仅用于内部看得懂的分析，不作为客户售价唯一依据。

当前实现按成本占比分摊；当总成本为零时平均分摊。[现状]  
该行为存在风险：成本不完整时仍会影响客户看到的分项售价。建议建立 `allocationBasis` 并禁止无说明的平均分摊，直到业务确认。为避免逐个报价行四舍五入后出现 1 分钱差异，建议最后一个报价行吸收尾差，并校验行金额合计严格等于套餐折前金额。

### 7.4 调整项目计算

| 动作 | 服务端处理 | 金额影响 | 成本影响 |
| --- | --- | --- | --- |
| 扣减 | 原基础行标记为不包含，保留历史 | `-原行分摊金额` | `-原行成本` |
| 增项 | 新增目录项目行 | `+新项目金额` | `+新项目成本` |
| 升级 | 原基础行不包含，新增新项目行 | `新项目金额-原行分摊金额` | `新项目成本-原行成本` |
| 替换 | 同升级，但记录替换语义 | `新项目金额-原行分摊金额` | `新项目成本-原行成本` |
| 赠送 | 作为赠送行，销售金额为零，成本保留 | 不增加客户应付 | 计入成本 |
| 数量变化 | 在基础行外增加调整行或按确认差异重算 | 按差额重算 | 按差额重算 |

规则：

- 调整前进入 `Draft`，提交后不得再改。
- 不可扣减项不能执行扣减。
- 调整后报价合计不能小于零。
- 任何调整都必须保存原因、来源行、替代项目和操作记录。[目标设计：当前主要依赖 QuoteLine 状态，尚无独立 QuoteAdjustment 审计对象]
- 折扣应先作用于调整后的折前小计，不能对不同来源行悄悄使用不同折扣，除非另有正式业务规则。

### 7.5 成本完整性

`[强制]` 成本完整性不能只看“总成本大于零”。

目标判定：

```text
costComplete = 所有应计成本行都有明确成本来源
```

任一应计成本缺失：

- `costComplete = false`
- `grossProfit = null`
- `grossMargin = null`
- UI 显示“成本未完整”
- 不得用 `0` 代替缺失值形成利润。

当前实现使用“报价小计为零或总成本大于零”作为完整性判断，无法识别“部分行有成本、部分行缺失”的情况。[现状缺口，P0]

### 7.6 利润口径

`MET-002` 当前为 `draft/medium`，因此本文只给出候选公式，不宣布冻结：

```text
grossProfit = 可用于利润分析的收入基数 - 完整成本
grossMargin = grossProfit / 可用于利润分析的收入基数
```

必须先由业务/财务裁决：

- 收入基数使用折后含税金额、折后不含税金额，还是合同确认收入。
- `designFee`、`managementFee` 是否进入报价小计。
- 税率是固定 5%、按企业配置，还是按项目/合同确定。
- 变更、赠送、退款和税费如何进入利润。

在裁决前，UI 不应把当前“报价金额减报价成本”直接称为最终毛利。

## 8. 状态机、版本和锁定规则

### 8.1 报价状态机

```text
Draft
  └─ submit -> Submitted
                  ├─ accept -> Accepted
                  │               └─ contract effective -> Converted
                  └─ reject -> Rejected

Rejected -> sourceQuoteId 新建 Draft
Superseded：被同一房屋其他确认报价替代，只保留历史
Converted：已进入合同/项目链，不允许再次编辑或驳回
```

### 8.2 状态动作矩阵

| 当前状态 | 允许动作 | 禁止动作 | 页面主操作 |
| --- | --- | --- | --- |
| `Draft` | 调整、重算、提交 | 客户接受、生成合同、直接转项目 | 提交客户 |
| `Submitted` | 接受、驳回 | 修改行、直接立项 | 客户接受/驳回 |
| `Accepted` | 生成合同、查看 | 改价、改基础行、重复接受 | 生成合同 |
| `Rejected` | 生成新版本 Draft | 原地复活、直接合同 | 改版重报 |
| `Superseded` | 查看历史 | 推进状态、编辑 | 查看历史 |
| `Converted` | 查看合同/项目 | 编辑、驳回、再确认 | 查看项目 |

### 8.3 关键不变量

- 同一房屋最多一份 `Accepted/Converted` 报价。
- 同一报价最多生成一份合同和一个项目。
- 合同未签约、未生效不能创建项目。
- 报价提交后不能再修改金额或项目行。
- 报价行来源可以引用主数据，但价格、成本、数量、名称、规格必须保存快照。
- 套餐模板修改、目录价格修改和目标项目停用不得回写历史报价。
- 混合报价存在 `Pending` 差异时不能提交。
- 所有状态推进必须由服务端校验，前端按钮隐藏不能替代权限和状态校验。

### 8.4 版本设计建议

当前代码可以使用“每个版本一条 `Quote` 记录”实现不可覆盖：

```text
Quote V1 Rejected
Quote V2 Rejected
Quote V3 Accepted
```

`[目标设计]` 增加稳定的机会关系：

- `rootQuoteId`：同一客户+房屋+来源机会的根报价。
- `sourceQuoteId`：直接上一版。
- `version`：版本号。
- `unique(com_id, root_quote_id, version)`：防止并发生成重复版本。
- `submittedAt / decidedAt / convertedAt`：用于指标、时效和历史追溯。[当前缺失]

如果未来需要同一机会下多个渠道、多个报价包或版本级明细树，再考虑拆出 `QuoteVersion`；当前中小装企阶段不建议为一个概念再增加一层不可见层级。

## 9. 权限与数据范围

### 9.1 权限原则

- 企业归属、门店、团队、负责人由服务端从登录员工和来源对象计算。
- 前端传入的 `companyId/empId/storeId/teamId/ownerId` 只能作为候选参数，不能直接信任。
- 套餐配置写权限与企业报价配置权限分开。
- 成本字段和报价金额字段分开控制。
- 数据范围回答“能不能查到这条报价”，成本能力回答“能不能看到成本和利润”。
- 服务端必须先拒绝越权，再做业务校验；无数据范围时统一返回 404，有权限但状态不合法返回 400/403。

### 9.2 角色与能力矩阵

| 角色 | 套餐模板 | 套餐报价创建 | 报价调整 | 状态推进 | 成本/利润 | 下游 |
| --- | --- | --- | --- | --- | --- | --- |
| BOSS | 企业内维护 | 企业内创建 | 企业内草稿调整 | 提交/接受/驳回/签约 | 可见 | 企业级经营 |
| 店长 | 只读；模板写权限当前仅 BOSS | 本门店范围内 | 本门店草稿 | 本门店状态 | 成本能力按企业配置 | 门店经营 |
| 团队负责人 | 只读 | 本团队范围 | 本团队草稿 | 本团队状态 | 默认不展示利润 | 团队推进 |
| 设计师 | 只读使用 | 本人负责客户/房屋 | 本人草稿 | 提交，接受/驳回按授权 | 默认不可见成本 | 方案与报价 |
| 业务员 | 只读 | 不可创建 | 不可调整 | 仅查看业务流转 | 不可见成本 | 客户漏斗只读 |
| 项目经理 | 只读来源报价 | 不可创建 | 不可调整 | 不可推进报价 | 只查看项目采购执行价，不查看综合毛利 | 项目履约 |
| 财务 | 只读或按授权 | 不通过报价页创建 | 不通过报价页调整 | 不推进客户决策 | 可见成本/完整性 | 应收、应付、结算 |
| 合同权限角色 | 只读报价 | 不可创建 | 不可调整 | 可签约/生效（按正式矩阵） | 按合同权限 | 项目立项 |

说明：

- 当前代码对业务员、项目经理等已有部分只读/403 保护。[部分实现]
- 当前套餐详情和报价详情响应中包含成本字段，且静态 `@Properties` 无法按角色变化，存在成本泄露风险。[P0 缺口]
- 财务和店长的最终数据范围、合同签约角色矩阵仍需业务正式裁决。

### 9.3 数据归属与索引

套餐、报价和报价行都必须有 `company`。报价及其行应具备：

```text
company / store / team / owner
```

建议索引：

```text
(com_id, quote_id)
(com_id, store_id, quote_id)
(com_id, team_id, quote_id)
(com_id, emp_id, quote_id)
(com_id, customer_id, quote_id)
(com_id, property_id, quote_id)
(com_id, design_id, quote_id)
(com_id, package_template_id, quote_id)
```

`quote_line` 至少保证：

```text
(com_id, item_id)
(com_id, quote_id, item_id)
```

如果历史归属快照与实时组织变化需要同时查询，应明确按快照查询，禁止使用员工当前门店/团队临时推导历史报价归属。

## 10. 后端 Provider 与接口契约

### 10.1 工程原则

- 服务即 Provider，不建立 DTO/VO。
- 请求实体通过 `@AutoInject + 校验注解` 获取，复杂保存使用 `@ModelSaveInject`。
- 对外响应返回实体或实体集合，不用包装 DTO。
- 具体 Provider 用 `@Properties` 控制字段，禁止 `@JsonIgnore`。
- 需要登录的 Provider 使用 `@User` 获取当前员工。
- 写接口必须做状态、企业归属、数据范围和幂等校验。
- 关联读取使用 `@EntityGraph`、`JOIN FETCH` 或事务内预取，不能依赖 OSIV 兜底。

### 10.2 当前 Provider 路由

| 路由 | 用途 | 关键规则 |
| --- | --- | --- |
| `pack/template/page` | 套餐模板列表 | 当前企业可见 |
| `pack/template/info` | 套餐详情 | 返回项目行和成本，成本需按角色拆分 |
| `pack/template/save` | 新建套餐 | BOSS，服务端算成本 |
| `pack/template/update` | 更新套餐 | BOSS，重算成本 |
| `pack/section/page` | 分区列表 | 当前企业 |
| `pack/section/save` | 保存分区 | BOSS |
| `pack/section/delete` | 删除分区 | 分区有项目行时拒绝 |
| `pack/line/page` | 项目行列表 | 当前企业 |
| `pack/line/save` | 保存项目行 | BOSS，校验项目有效 |
| `pack/line/delete` | 删除项目行 | 已生成历史快照时拒绝 |
| `pack/template-item/page` | 差价项列表 | 当前企业 |
| `pack/template-item/save` | 保存差价项 | BOSS |
| `quote/save` | 创建套餐/自定义/重报 | 服务端计算金额 |
| `quote/page` | 报价列表 | 按角色数据范围 |
| `quote/info` | 报价详情 | 仅可见数据范围 |
| `quote/update` | 状态推进 | 只允许合法状态 |
| `quote/line/page` | 报价行 | 仅可见报价 |
| `quote/line/save` | Draft 调整/差异确认 | 仅 Draft，服务端重算 |
| `quote/line/delete` | 删除 Draft 调整项 | 基础包含项不能直接删除 |

### 10.3 请求与响应语义

`quote/save` 需要区分三种情况：

1. 套餐报价：
   - `customerId`
   - `propertyId`
   - `packageTemplateId`
   - `area`
   - `discount`
   - 可选 `empId`，仅 BOSS 指定负责人时有效。
2. 自定义设计报价：
   - `designId`
   - `discount`
   - 客户、房屋、负责人由设计和服务端推导。
3. 驳回重报：
   - `sourceQuoteId`
   - 服务端验证来源必须是 `Rejected`，复制快照并生成新 `Draft`。

`quote/line/save` 需要表达：

- `quoteId`
- `itemId`（调整或差异行）
- `baseLineId`（被扣减、升级或替换的基础行）
- `catalogItemId`（新增/替换项目）
- `quantity`
- `deduct`
- `role`：`Base / Option / Upgrade / Add / Deduct / Replace / Gift`
- `differenceStatus`：`Pending / Confirmed / Ignored`

响应必须至少返回：

- 报价头汇总：`subtotal / discount / taxRate / taxAmount / amount / cost / costComplete / status / version`。
- 报价行：来源、角色、差异、数量、金额、成本、组件、是否包含。
- 调整后的区域/施工/材料/其他分组视图。
- 当前允许的下一步动作所需状态，不由前端自行猜。

### 10.4 错误语义建议

| 场景 | 返回语义 |
| --- | --- |
| 无角色能力 | `403`，例如业务员创建报价 |
| 有权限但不在数据范围 | `404`，不泄露对象是否存在 |
| 对象状态不合法 | `400`，附明确业务原因 |
| 跨企业/伪造归属 | `403` 或 `404`，按安全策略统一 |
| 重复提交产生相同结果 | 目标为幂等返回当前事实，不重复生成项目/合同 |
| 成本缺失 | 不阻断查看，但阻断利润计算并返回 `costComplete=false` |

## 11. 前端 UI 设计

### 11.1 端职责

- App：套餐配置、现场快速新建报价、草稿调整、差异确认、即时反馈。
- 两端必须显示同一业务事实；不得各自计算一套报价总额、折扣或成本。

### 11.2 App 页面地图

| 页面 | 主要角色 | 内容 | 下一步 |
| --- | --- | --- | --- |
| 套餐模板列表 | BOSS、店长 | 名称、标准面积、牌价、成本、参考毛利、可使用状态 | 新建、编辑、生成报价 |
| 套餐配置 | BOSS | 基本信息、分区、项目行、数量系数、可扣减、成本检查 | 保存、校验、启用 |
| 新建报价 | 设计师 | 客户、房屋、套餐、面积、折扣、金额预览 | 生成 Draft |
| 报价详情 | 设计师、负责人、PM | 状态、客户房屋、套餐快照、行明细、调整、合同/项目入口 | 提交、处理差异、查看下游 |
| 报价调整 | 设计师 | 基础行、扣减、升级、替换、增项、差异确认、成本提示 | 保存并重算 |
| 混合报价确认 | 设计师 | 设计方案上下文、套餐选择、面积比例、折后金额、差异预估 | 生成 Hybrid Draft |

关键 UI 规则：

- 套餐牌价和折扣必须分开展示；不要只显示一个无法解释的最终总价。
- 金额预览标明“以服务端计算为准”。
- 多房屋客户必须突出当前房屋，不显示“客户默认房屋”。
- 成本只对成本权限角色展示；无权限时布局不能留下空白成本占位。
- 提交按钮在存在 `Pending` 差异、金额不合法或状态不允许时禁用，并显示具体阻断原因。
- 报价行要显示“来源套餐/设计、原值、调整后值、差额、成本状态”。
- 加载失败显示“状态暂不可确认”，不得用空列表表示确定无数据。
- 从详情返回列表、下拉刷新或重新进入页面必须读取最新状态。

### 11.4 关键状态文案

| 内部状态 | 用户文案 | 主操作 |
| --- | --- | --- |
| `Draft` | 编制中 | 继续调整/提交客户 |
| `Submitted` | 待客户决策 | 客户接受/客户驳回 |
| `Accepted` | 客户已接受 | 生成合同 |
| `Rejected` | 客户已驳回 | 改版重报 |
| `Superseded` | 已被其他报价替代 | 查看历史 |
| `Converted` | 已转项目 | 查看合同/项目 |
| `Pending` 差异 | 待确认设计差异 | 确认/忽略/调整 |
| `costComplete=false` | 成本未完整 | 补成本/暂不计算毛利 |

### 11.5 交互约束

- 调整操作必须二次确认，并显示本次差额和重算结果预览。
- 删除调整行只删除调整产生的行；基础包含行必须通过扣减处理。
- 重报必须在原报价详情中明确显示“以 Vx 为基准确认生成新版本”。
- 提交后页面进入只读态；不得保留可点击但无权限的编辑入口。
- 金额和成本使用等宽数字与固定小数位，避免视觉跳动。
- 异常态必须保留恢复路径：重试、返回详情、修改 Draft、联系负责人或发起变更。

## 12. 指标、审计和可完成状态

### 12.1 报价接受率

根据 `DEC-001` 和 `MET-001`：

```text
最终报价接受率 =
最终接受或已转项目的机会数
÷ 已经接受、转项目或拒绝的有效机会数
```

规则：

- 草稿、待决策和替代报价不计入最终分母。
- 首版报价接受率按首版报价版本单独统计。
- 待决策报价量、合同签约率、项目转化率分别展示。
- 需要记录 `submittedAt`、`decidedAt`、可能还需要 `convertedAt`。[当前缺失]
- 同一客户+房屋的机会去重，不能简单按所有报价行数计算。

### 12.2 调整审计

`[目标设计]` 每次扣减、升级、替换、增项和差异处理至少记录：

- 操作人。
- 操作时间。
- 报价版本。
- 来源行。
- 调整类型。
- 调整前后金额和成本。
- 原因和备注。
- 是否客户可见。
- 是否已确认。

当前服务端主要把调整结果保存在 `QuoteLine` 的角色、差异和金额字段中，缺少独立审计实体。[缺口]

### 12.3 可完成状态投影

套餐列表的“可使用”和配置步骤的“完成”必须由真实领域对象推导：

- 基本信息完成：名称、标准面积、牌价、默认折扣有效。
- 分区完成：至少一个有效分区。
- 项目行完成：至少一个有效项目行。
- 成本完成：每个应计项目有明确成本来源。
- 可使用：套餐处于 `Active` 且满足以上默认条件。
- 可选配置未完成不得改变必做分母。
- 接口失败显示“状态暂不可确认”，不得伪造成“未完成”。

### 13.2 必须在研发前处理的差异

| 编号 | 问题 | 影响 | 建议 |
| --- | --- | --- | --- |
| `DQ-01` | 报价利润是否含税、税率是否固定 5% | 毛利和客户报价都可能错误 | 业务/财务裁决后再实现利润 |
| `DQ-02` | `designFee`、`managementFee` 当前存在但不进计算 | 报价总额与页面预期不一致 | 决定纳入 `QuoteLine` 或统一公式 |
| `DQ-03` | `PackageTemplateItem/PackageRule` 已建模但未用于自动差价 | 规则展示与实际计算不一致 | 明确启用范围或从首版 UI 移除自动化承诺 |
| `DQ-04` | `maxDeleteNum` 未参与扣减校验 | 用户以为有扣减上限 | 要么实现，要么标为说明字段 |
| `DQ-05` | 成本完整性只判断总成本是否大于零 | 部分缺失时误报完整 | P0 改为逐行成本完整性 |
| `DQ-06` | 成本字段在部分员工响应中可见 | 越权泄露成本 | 拆分成本 API/响应，不能只隐藏前端 |
| `DQ-07` | 没有任何 `rootQuoteId/sourceQuoteId` | 多版本无法稳定归并机会 | 增加根报价和来源报价链接 |
| `DQ-08` | 缺少提交、决策、转化时间 | 接受率和时效无法正式统计 | 增加状态时间字段 |
| `DQ-09` | 套餐无生命周期和修订号 | 模板变更后无法解释历史口径 | 增加 `Draft/Active/Archived + revision` |
| `DQ-10` | 套餐价格和行主数据只靠引用 | 修改主数据可能影响历史展示 | 补齐快照字段并控制序列化 |
| `DQ-11` | 状态推进并发/幂等未完全定义 | 重复点击可能产生冲突或重复事实 | 明确重复请求返回规则和唯一约束 |
| `DQ-12` | 直接签约补录尚无完整报价来源 | 特殊业务可能被迫绕过报价 | 按 `BR-002` 生成签约基线报价，不等同普通报价 |

### 13.3 待业务正式裁决

1. 收入基数是否含税，毛利和毛利率最终公式。
2. 设计费和管理费是否作为报价行进入统一小计。
3. 税率是企业固定、项目配置还是合同约定。
4. 哪些角色能看标准成本、报价成本、签约成本和项目毛利。
5. 套餐扣减是否允许直接降低总价，还是必须经过审批。
6. 升级/替换的客户展示是“原项+新项+净差额”，还是只展示最终项目。
7. 套餐模板停用、归档和历史报价引用后的编辑规则。
8. 报价有效期、客户决策期限和超期处理。
9. 财务和店长的最终数据范围及合同签约角色矩阵。

## 15. 验收清单

### 15.1 套餐模板

- [ ] 标准面积、牌价、默认折扣均必填且范围合法。
- [ ] 套餐牌价按折前价解释，折扣单独应用。
- [ ] 新增/删除项目行后标准成本重新计算。
- [ ] 停用或无效的 `CatalogItem` 不能被加入有效套餐。
- [ ] 套餐行已生成历史报价快照后不能物理删除。
- [ ] 修改模板不会改变已有报价的金额、成本和明细。

### 15.2 套餐报价

- [ ] 多房屋客户必须显式选择房屋。
- [ ] 报价绑定客户、房屋、套餐、面积、折扣和负责人。
- [ ] 服务端计算折前金额、折扣、税金、报价合计和成本。
- [ ] 报价行金额总和与套餐折前金额一致。
- [ ] 生成后状态为 `Draft`，提交前可调整。
- [ ] 提交后报价行、金额、成本不可修改。
- [ ] 驳回后可以生成新版本，旧版本保持只读。

### 15.3 调整和混合报价

- [ ] 扣减只能作用于允许扣减的基础行。
- [ ] 升级和替换同时保留原行和新行关系。
- [ ] 增项必须来自有效目录项目。
- [ ] 每次调整后汇总、税金和成本全部重算。
- [ ] 存在 `Pending` 差异时提交失败并给出具体项目。
- [ ] 差异确认、忽略和调整后可以再次提交。
- [ ] 非法数量、金额为负或来源跨企业时失败。

### 15.4 权限和成本

- [ ] BOSS 可维护当前企业套餐，跨企业访问失败。
- [ ] 店长、团队负责人、设计师、业务员、项目经理、财务的列表数据范围符合矩阵。
- [ ] 业务员不能创建或调整报价。
- [ ] 无成本权限角色的报价响应不包含成本、成本完整性和毛利字段。
- [ ] 伪造 `company/store/team/owner` 参数不能扩大数据范围。
- [ ] 跨企业客户、房屋、套餐、目录项目组合被拒绝。

### 15.5 状态和下游

- [ ] 只有 `Accepted` 报价可以生成合同。
- [ ] 合同未签约或未生效不能创建项目。
- [ ] 重复接受、重复合同、重复立项不产生重复事实。
- [ ] 项目金额与合同/报价快照一致。
- [ ] 成本不完整时项目利润为空，页面显示“成本未完整”。
- [ ] App 和财务页面显示的金额、状态和成本完整性一致。

### 15.6 UI 和异常

- [ ] 首次进入、刷新、失败重试、返回详情均能读取最新状态。
- [ ] 空数据、接口错误、无权限和状态不允许有不同文案。
- [ ] 金额、数量、百分比使用稳定格式。
- [ ] 提交、调整、确认差异有加载中、成功、失败和重试状态。

## 17. 最终判断

套餐报价的产品核心不是“填一个套餐总价”，而是建立一条可追溯的经营链：

```text
企业标价和成本
  -> 套餐模板
  -> 客户房屋报价快照
  -> 套餐/设计调整
  -> 客户确认
  -> 合同成本冻结
  -> 项目实际成本和利润
```

研发和 UI 只有在对象、状态、金额、权限、异常和验收六类条件同时明确后，才应进入新的功能实现。当前最优先的不是继续增加页面，而是先处理成本完整性、成本可见性、报价快照/版本链、税率与利润口径这四项基础事实。

> 本文不能替代独立验收、业务裁决或生产证据。出现新冲突时，应由业务智能体建立新的 `GAP-*`/`DEC-*`，再由产品、研发和验收按同一版本执行。

# 装得清运营管理端业务闭环设计

> 版本：1.0  
> 日期：2026-09-16  
> 适用工程：`th4-decoboon-admin`、`th4-decoboon`  
> 读者：产品、市场推广、客户成功、平台运维、开发、验收

## 1. 建设目标

装得清运营管理端不是普通后台，而是平台从“产品可用”走向“客户可经营、系统可运维”的统一工作台。它必须同时回答三类问题：

1. **市场问题**：哪些装企最可能成功使用装得清，应该用什么价值主张、渠道和方案触达？
2. **客户成功问题**：哪些企业正在试用、临期、触顶、冻结或流失，下一步服务动作是什么？
3. **平台运维问题**：服务器、数据库、缓存和应用是否稳定，是否存在异常、容量和发布风险？

管理端以企业为经营对象，以订阅为商业对象，以人工操作为审计对象，以系统指标为稳定性对象。

## 2. 角色与权限

| 角色 | 范围 | 允许能力 | 禁止能力 |
|---|---|---|---|
| 平台运营负责人 | 全平台企业 | 查询企业、查看订阅、人工续费、套餐/席位/门店/状态调整、查看审计、查看系统状态 | 查看员工凭证、客户隐私正文、密钥、连接串 |
| 普通企业 Boss | 本企业 | 原有租户 Web/小程序能力 | 进入平台运营端，查询其他企业，人工调整订阅 |
| 普通员工 | 按租户数据范围 | 原有业务能力 | 平台管理与跨企业查询 |
| 运维脚本 | 服务器 | 只读采集、受控发布、失败回滚 | 绕过平台审计直接修改业务订阅 |

平台权限白名单：

- `Company.platform = true`
- 当前登录员工 `EmployeeRole.Boss`
- 登录员工属于平台运营企业
- Provider 必须继承 `Security`
- 普通租户手工构造请求也必须返回 `403`

平台运营权限属于基础设施例外，不复用普通租户 `Company/Store/Team/Self` 数据范围；例外必须集中在 `PlatformAdminContext`，禁止散落到各 Provider。

## 3. 核心对象

| 对象 | 作用 | 关键状态 |
|---|---|---|
| `Company` | 企业主体与平台运营企业标记 | 正常企业 / 平台运营企业 |
| `Subscription` | 企业商业权益与有效期 | Trial / Active / Expired / Frozen / Closed |
| `Plan` / `PlanVersion` | 套餐与历史权益快照 | 上架 / 下架；版本不可回写 |
| `Employee` | 当前登录员工与操作人 | Active / Suspended / Resigned |
| `PlatformOperationLog` | 人工订阅调整审计 | 不可在管理端删除 |
| `SystemStatus` | 运行时资源与依赖快照 | UP / DOWN / DEGRADED |

## 4. 业务闭环

### 4.1 获客到试用

1. 市场端识别高匹配装企：多店扩张、报价混乱、设计到交付链路断裂、财务与供应链失控。
2. 售前使用“报价效率 30 分钟体验”或经营诊断建立价值感知。
3. 企业注册后获得 14 天专业版试用。
4. 客户成功关注试用激活，不仅看注册量，还要看是否完成：成员邀请、客户建档、设计/报价、项目创建。
5. 若 3 天内未完成关键动作，进入客户成功队列。

**核心指标**：注册企业数、试用激活率、关键动作完成率、试用转付费率。

### 4.2 试用激活到付费转化

1. 运营端按企业识别当前套餐、剩余天数、席位/门店使用、风险等级。
2. 客户成功根据企业阶段选择基础版、专业版或旗舰版。
3. 套餐表达必须与后端权益快照一致，禁止销售承诺未实现功能。
4. 线下成交可走人工管控；线上成交继续走订单与支付回调。
5. 所有人工赠送、折扣和扩展权益必须填写原因，并留下合同/审批依据。

**核心指标**：试用转付费率、平均成交周期、首单客单价、套餐结构。

### 4.3 使用增长与扩容

触发扩容的明确信号：

- 席位使用率达到 80% 及以上；
- 门店数量达到当前权益上限；
- 多门店经营已影响报价、项目、财务和供应链协同；
- 客户已出现跨店管理需求，而非仅“预购未来”。

运营端允许后台调整席位/门店加购数。调整后必须：

- 立即影响生效权益；
- 记录调整前后值；
- 保留操作原因；
- 如涉及线下回款，同步财务流水，不由管理端伪造支付订单。

**核心指标**：席位使用率、门店使用率、扩容转化率、扩容收入。

### 4.4 续费与流失预警

风险分层：

| 风险 | 条件 | 服务动作 |
|---|---|---|
| P0 高风险 | 已到期、冻结、关闭 | 24 小时内回访，确认回款、服务意愿和流失原因 |
| P1 临期 | 7 日内到期 | 电话触达 + 续费方案 + 关键价值复盘 |
| P2 观察 | 8-30 日内到期 | 产品内提醒 + 客户成功跟进 |
| 健康 | 30 日以上且使用正常 | 案例共创、增购、转介绍 |

人工续费规则：

- 从当前到期日续期；已过期则从当前时间开始计算。
- 套餐切换必须引用最新套餐版本。
- 恢复为 `Active` 前必须确保服务期未到期。
- 冻结、关闭、恢复均必须填写原因。
- 每次变更写 `PlatformOperationLog`。

### 4.5 客户成功到转介绍

1. 对高使用率、长期稳定、关键闭环完整的企业标记为标杆候选。
2. 邀请参与案例、行业分享和转介绍。
3. 通过管理端记录续费、扩容和成功动作，形成可复用的客户成功剧本。
4. 标杆案例回流到营销内容，但不得泄露客户隐私数据。

## 5. 系统运维闭环

### 5.1 观测对象

- CPU 使用率、核数、系统负载；
- JVM 已用内存、最大堆、运行时长；
- 磁盘总量/已用；
- MySQL 连接有效性；
- Redis PING；
- 应用进程；
- HTTPS、微信支付证书等外部到期风险（由运维 Runbook 维护）。

### 5.2 处置链路

1. 管理端采样或告警发现异常。
2. 使用 `bash scripts/prod-monitor.sh collect "30 minutes ago"` 只读采集。
3. 按错误指纹归档，判断是流量、配置、外部依赖还是代码缺陷。
4. 仅高置信、单根因、可回滚、不涉及 DDL/密钥/权限放宽/资金语义的问题允许自动修复。
5. 生产发版只能使用 `scripts/deploy-prod.sh`，失败回滚到上一 release。
6. 事故复盘回写 `docs/operations/incidents/registry.json`。

### 5.3 运维原则

- 先止血，再定位，最后修复。
- 不在故障窗口直接改数据库结构。
- 不把管理端作为 SSH、数据库或日志明文浏览器。
- 管理端不返回密钥、连接串、服务器密码和客户隐私正文。

## 6. 营销与运营支持

管理端为市场推广提供以下数据与动作：

- 按状态识别试用、付费、临期和流失客户；
- 查看套餐结构和潜在升级客户；
- 形成行业画布、渠道转化和增长实验看板；
- 给客户成功提供“今日动作”队列；
- 把已成功的客户经营路径沉淀为案例和销售话术。

营销推广不直接修改企业业务数据。所有促销权益必须经过订阅调整审计。

## 7. 审计模型

每次人工订阅调整记录：

- 操作人：`operator.empId`
- 目标企业：`company.comId`
- 动作：`Renew / PlanChange / SeatAdjust / StoreAdjust / StatusChange / Freeze / Unfreeze`
- 目标类型与目标标识
- 操作摘要
- 变更前后快照
- 操作原因
- 操作时间

审计索引：

- `(com_id, log_id)`
- `(com_id, create_date_time, log_id)`
- `(emp_id, create_date_time, log_id)`

## 8. 接口契约

| 路由 | 用途 | 写操作 |

## 9. 失败与边界

- 企业不存在或为平台企业：返回 404。
- 非平台运营账号：返回 403。
- 未登录：返回 401。
- 没有任何调整项：返回 400。
- 套餐不存在或下架：返回 400。
- 恢复 Active 但服务期已过：返回 400。
- 并发人工调整：使用订阅悲观锁，避免覆盖。
- Redis/数据库不可达：系统状态接口仍返回快照，但对应服务标记 DOWN。

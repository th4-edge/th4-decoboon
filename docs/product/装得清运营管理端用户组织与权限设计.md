# 装得清运营管理端用户组织与权限设计

> 版本：1.0  
> 日期：2026-09-16  
> 适用范围：`th4-decoboon-admin`、`th4-decoboon` 平台域  
> 目标：明确平台运营团队的组织层级、岗位角色、权限边界、数据范围、审批关系和账号生命周期。

## 1. 设计原则

1. **业务主体不混用**：平台运营使用独立 `PlatformOrg`，客户企业使用租户 `Company`；两者不共享表、外键、认证或实体关联。
2. **认证体系独立**：平台操作员使用 `PlatformUser + PlatformOrg + PlatformDepartment` 登录，禁止复用租户 `Employee/Credentials`。
3. **权限服务端优先**：前端菜单隐藏只能改善体验，所有 `platform/*` Provider 必须通过 `PlatformAccessContext` 做岗位能力校验。
4. **最小权限**：市场、客服、财务、SRE 和审计岗位不默认拥有全部权限。
5. **职责分离**：查看审计的人不能任意删除审计；提交订阅调整的人与最终审计人分离。
6. **跨域读取受控**：只有 `com.th4.edge.platform` 允许跨企业查询；平台实体不得持有租户实体，租户数据统一通过 `TenantDataAdapter` 转为标量快照。
7. **敏感信息不下发**：平台端不返回密码哈希、AccessKey、数据库口令、微信支付密钥和客户隐私正文。
8. **人工操作必审计**：续费、套餐、席位、门店、冻结、恢复和关闭必须写 `PlatformOperationLog`。

## 2. 目标组织架构

```text
独立平台运营组织（PlatformOrg）
├── 平台负责人 / 超级管理员
│   ├── 平台运营主管
│   │   ├── 客户成功组
│   │   │   ├── 客户成功经理
│   │   │   └── 实施陪跑顾问
│   │   └── 商业化运营组
│   │       ├── 套餐运营
│   │       └── 续费运营
│   ├── 财务运营
│   ├── 市场增长
│   └── 平台可靠性 / SRE
└── 独立审计
```

组织关系建议：

| 层级 | 业务含义 | 建议载体 |
|---|---|---|
| 平台运营组织 | 平台运营主体 | `PlatformOrg` |
| 一级中心 | 客户成功、商业化、SRE、财务 | `PlatformDepartment` |
| 岗位组 | 客户成功组、续费运营组 | `PlatformDepartment` |
| 操作人员 | 登录与操作主体 | `PlatformUser` |
| 权限角色 | 可执行能力集合 | `PlatformRole + PlatformPermission` |
| 数据范围 | 可查看的企业与字段 | 平台级 + 字段级授权 |
| 审批关系 | 敏感动作会签/复核 | 目标 `PlatformApproval` |

> 平台独立组织、部门、用户、岗位和能力模型已经落地。当前初始化器只创建首个 `SuperAdmin`，其他岗位可通过后续 `platform/user/*` 管理 Provider 创建，不将租户 `EmployeeRole` 复用为平台岗位。

## 3. 组织岗位职责

### 3.1 平台负责人 / Super Admin

职责：

- 管理平台运营组织和平台账号。
- 查看全部企业、订阅、审计和系统状态。
- 执行高风险订阅动作。
- 审批大额赠送、长期冻结、异常恢复和关闭。
- 不再直接依赖共享超级账号，正式上线后应一人一号。

权限：全部。

### 3.2 平台运营主管 / Operations Manager

职责：

- 负责客户成功、续费和商业化的日常运营。
- 审核客户成功经理的套餐和权益调整。
- 关注流失、风险、续费池和套餐结构。
- 协调财务、销售和交付。

权限：企业读取、订阅读取、续费、套餐调整、席位/门店扩容、审计查看。

限制：不能管理平台账号；大规模赠送需负责人审批。

### 3.3 客户成功经理 / Customer Success

职责：

- 维护客户健康档案，判断试用激活和使用深度。
- 发起续费提醒、扩容建议、服务回访。
- 记录客户流失原因和成功动作。

权限：企业读取、订阅读取、有限续费/席位/门店调整、本人客户动作查看。

限制：不能关闭订阅、不能修改财务敏感字段、不能查看全量审计。

### 3.4 财务运营 / Billing Operator

职责：

- 核对订单、回款、退款和对账。
- 处理线下回款登记和异常订单确认。
- 查看套餐收入、MRR、订单履约状态。

权限：财务指标读取、企业订阅读取、订单核对、续费确认。

限制：不能查看系统私密配置；不能修改业务客户正文。

### 3.5 市场增长 / Growth Operator

职责：

- 维护客户画像、渠道策略、增长实验和套餐市场表达。
- 观察试用、转化、续费和套餐分布。
- 推动案例、转介绍和行业内容。

权限：脱敏企业聚合数据、套餐读取、增长数据读取。

限制：不能查看客户联系方式；不能直接修改订阅；不能导出企业隐私明细。

### 3.6 平台可靠性 / SRE

职责：

- 监控 CPU、内存、磁盘、JVM、MySQL、Redis 和应用进程。
- 处理发布、回滚、容量和异常告警。
- 维护 Runbook 和事故复盘。

权限：系统状态读取、发布/回滚审计读取、企业只读摘要。

限制：不能修改业务订阅；不能在管理端执行任意 Shell 或 SQL。

### 3.7 审计与合规 / Auditor

职责：

- 抽查人工订阅变更、审计日志、越权访问和异常操作。
- 审核平台账号生命周期和权限变更。
- 验证操作原因与合同/审批依据。

权限：全量审计读取、只读企业/订阅摘要、系统状态只读。

限制：不能执行订阅修改；不能删除或篡改审计。

## 5. 数据范围设计

### 5.1 企业范围

平台角色可以跨企业，但必须按岗位进一步限制：

- Super Admin：全部企业。
- Ops Manager：全部企业的订阅与经营摘要。
- Customer Success：分配给自己的客户企业或主管指定的客户池。
- Billing：与订单/回款相关的企业。
- Growth：聚合数据或脱敏样本。
- SRE：最小企业摘要，重点为技术健康度。
- Auditor：全部企业的审计只读。

当前平台范围由 `PlatformOrg + PlatformRole + PlatformPermission` 控制；平台表与租户表无外键，租户数据只能经过 `TenantDataAdapter` 读取。

### 5.2 字段范围

按字段分组授权：

| 字段组 | 示例 | 默认开放 |
|---|---|---|
| 企业基础 | 企业ID、名称、简称、地区、规模 | 运营类岗位 |
| 订阅权益 | 套餐、状态、到期日、席位、门店 | 客服/运营/财务 |
| 财务 | 订单号、金额、支付渠道、履约状态 | 财务、运营主管 |
| 审计 | 操作人、原因、前后值 | 审计、运营主管 |
| 系统 | CPU、内存、依赖服务、版本 | SRE、负责人 |
| 隐私 | 客户电话、项目正文、员工凭证 | 平台端默认禁止 |

### 5.3 操作范围

模块权限必须由“读取 + 写动作 + 审批阈值”三段组成：

```text
是否可以进入页面
  + 是否可以读取具体字段
  + 是否可以执行写动作
  + 是否需要第二人审批
```

不能仅用菜单权限代替数据权限。

## 6. 账号生命周期

| 阶段 | 操作 | 责任 |
|---|---|---|
| 入职 | 创建 PlatformUser、绑定平台组织与部门、分配平台岗位 | Super Admin |
| 发证 | 设置 BCrypt 初始密码，强制首次修改 | Super Admin |
| 调岗 | 修改平台角色，不复制历史权限 | Super Admin |
| 离岗 | 停用 PlatformUser、回收岗位和登录状态 | Super Admin |
| 审计 | 保留操作历史和账号日志，不物理删除 | Auditor |
| 紧急 | 冻结账号、终止 token、记录原因 | Super Admin + Auditor |

平台账号不得与客户企业员工共用手机号。手机号已属于客户企业时，初始化器会拒绝自动提升。

## 7. 审批与职责分离

### 7.1 必须双人复核的动作

- 超过 365 天的免费赠送。
- 将 `Closed` 直接恢复为 `Active`。
- 单次赠送超过 3 个席位或 1 家门店。
- 关闭高价值企业。
- 修改折扣/合同价关联的权益。
- 平台账号授权与回收。

### 7.2 职责分离

- 发起人不能同时审批自己的高风险动作。
- 财务操作员不能直接执行全量订阅关闭。
- SRE 不能修改订阅。
- Auditor 不能执行订阅写操作。
- Super Admin 的每次高风险操作仍写不可删除审计。

### 8.1 数据库隔离硬约束

平台数据库表：

- `db_platform_org`
- `db_platform_department`
- `db_platform_user`
- `db_platform_operation_log`

租户数据库表：

- `db_tenant_company`
- `db_tenant_employee`
- `db_tenant_credentials`
- `db_tenant_store`
- `db_tenant_team`
- `db_tenant_subscription`
- `db_tenant_plan`
- 其他 `db_tenant_*` / `db_*` / 客户业务表

强制约束：

1. `db_platform_*` 与租户表之间禁止建立任何外键。
2. 平台 JPA 实体禁止声明 `Company/Employee/Credentials/Subscription` 等租户实体关联。
3. 平台 token 与租户 token 使用不同 User 类型，禁止互相调用对应端。
4. 平台用户密码只存于 `db_platform_user.password_hash`，不得读取租户 `Credentials`。
5. 租户数据只允许由 `TenantDataAdapter` 在事务内读取，并立即转换为 `PlatformTenant/PlatformSubscription/PlatformPlan` 标量快照。
6. `PlatformOperationLog.target_com_id`、`target_sub_id` 是没有外键的历史快照；即使租户数据被删除，平台审计也不依赖租户表。
7. 任何新增平台表必须通过“无租户外键”元数据检查测试。

## 9. 目标 Provider 权限模型

建议增加：

- `platform/operator/info`：返回当前操作员、组织岗位和 capability 列表。
- `platform/operator/page`：Super Admin 查询平台账号。
- `platform/operator/save`：创建/调整平台岗位。
- `platform/operator/update`：停用、恢复、调岗。
- `platform/operation/page`：只读审计。

所有 Provider 调用：

```text
requirePlatform()
  -> requireOperator()
  -> requireCapability(...)
  -> execute business action
  -> write PlatformOperationLog
```

前端根据 `capabilities` 控制菜单和按钮，但服务端必须再次校验。

## 10. 落地阶段

### Phase 1：已实现

- 独立 `PlatformOrg / PlatformDepartment / PlatformUser`。
- 独立 `platform/auth/login`、`platform/auth/info`、`platform/auth/logout`。
- `PlatformRole + PlatformPermission` 能力矩阵。
- 全企业查询、订阅人工管控、审计和系统监控。
- 环境变量初始化第一个 SuperAdmin，默认关闭。
- 平台与租户数据库无外键，租户查询通过 `TenantDataAdapter` 标量映射。

### Phase 2：用户管理界面

- 新增 `platform/user/page/save/update` 和部门管理 Provider。
- 前端增加平台用户、部门和岗位管理。
- 增加字段级脱敏、审批阈值和客户成功负责人分配。

### Phase 3：治理化

- 接入第二人审批、工单和合同依据链接。
- 审计与客户合同、回款、服务记录关联。
- 配置岗位轮换、访问复核和异常行为告警。
- 对导出、批量操作和敏感字段访问单独审计。

## 11. 当前版本的运行边界

当前版本可以真实运行，平台账号完全是独立账号。运行期间必须遵守：

- 不创建共享匿名账号。
- 台账和数据库不得把平台组织写入 `db_tenant_company`。
- 不将平台域名开放给普通租户。
- 不把租户 Employee 账号用于平台登录。
- 初始化账号完成后关闭 `PLATFORM_BOOTSTRAP_ENABLED`。

# 装得清测试策略

## 1. 目标

证明真实岗位人员能够只通过 App、Web 和业主端页面，按装得清正式业务规则完成关键工作，并保证同一业务事实在后端、角色视图、端面和数据范围下保持一致。

测试的第一问题不是“按钮是否存在”，而是：

> 谁在什么业务状态下，能否完成正确动作，系统是否产生正确、可回读、可恢复、可对账的业务结果？

## 2. 分层策略

| 层级 | 验证对象 | 不能替代什么 |
| --- | --- | --- |
| `L0 环境与数据预检` | 提交、租户、账号、夹具、备份、服务健康 | 不能证明业务正确 |
| `L1 契约与不变量` | Provider、状态机、权限、金额、幂等、SQL 不变量 | 不能用 API 通过替代页面可用 |
| `L2 真实页面` | 当前角色可见入口、按钮、表单、反馈和恢复 | 不能用页面通过替代权限/金额/数据库对账 |
| `L3 跨角色与跨端` | 同一事实在 App/Web/业主端/Boss/店长/财务的交接与同源 | 不能把单端验证称为跨端完成 |
| `L4 高风险与非功能` | 跨租户、成本利润、并发、性能、弱网、真机和人工见证 | 不能用自动化证据替代真人/业主确认 |

## 3. 角色覆盖

目标角色：Boss、StoreManager、Marketer、Designer、Pm、Finance、Owner。TeamLeader 只做历史兼容检查，不新增业务动作。

每个角色至少验证：

1. 一条本角色核心正向流程；
2. 一条不应拥有的操作或数据范围；
3. 一条跨角色交接；
4. 一条空态、失败、刷新或恢复；
5. 一条重复操作/状态冲突。

## 4. 业务覆盖

V0.1 八个区域：

1. 客户与房屋；
2. 设计方案与报价；
3. 合同与合同变更；
4. 项目阶段与施工任务；
5. 材料选材、作业单、采购与到场；
6. 阶段验收与整改；
7. 应收、收款、应付、付款、成本与结算；
8. 工作台、正确引导与跨端事实同源。

## 5. 测试类型

- `happy`：正常主链；
- `negative`：字段、业务门禁和非法输入；
- `permission`：角色、数据范围、跨租户；
- `order`：乱序、跳步、刷新和回退；
- `concurrency`：重复提交、并发占用和幂等；
- `recovery`：请求失败、页面重试、重新进入；
- `boundary`：空、最大、缺失、代价/成本不完整；
- `parity`：App/Web/业主端/Provider 同源；
- `nonfunctional`：性能、弱网、真机、可访问性。

## 6. 环境策略

| 跑道 | 用途 | 写权限 |
| --- | --- | --- |
| `local-fixture` | 破坏性、阶段组合、极端边界、压测 | 受控写 |
| `prod-twin` | 昭青科技专用测试企业完整闭环 | 当次授权写 |
| `prod-readonly` | 线上麦鸿形态、入口、权限和口径参照 | 禁止写 |
| `prod-controlled-write` | 白名单测试租户最终验证 | 单独审批 |

## 7. 证据原则

- 页面结论必须有真实页面路径、角色、端面、截图和操作前后状态；
- 金额、权限、状态必须有页面 + API + DB 三方或明确说明的证据；
- 高风险动作必须有操作者真实性证据；
- AI 模拟不能写成真人验收；
- 业主确认、电子签、真实支付和正式发布不因测试脚本存在而自动获权。

## 8. 独立性原则

测试用例作者、执行者和修复者不得用“开发自测”冒充独立验收。修复后必须用新的 `RUN-*` 记录复验；复验不得复用修复前的绿灯。

## 9. 退出准则

一个计划只有同时满足以下条件才可标记 `PASS`：

1. 计划范围内 P0 用例 100% 执行并通过；
2. P1 无未接受阻断项；
3. 关键 happy、negative、permission、order、concurrency 均有证据；
4. App/Web/业主端涉及的能力完成同源对账；
5. 金额、成本、状态和权限不变量通过；
6. 未覆盖项、阻塞项和残余风险显式列出；
7. 证据可定位、可复现、与当前代码版本匹配。

# 测试风险模型

## 1. 优先级

| 级别 | 判定 | 默认门禁 |
| --- | --- | --- |
| `P0` | 跨租户/越权、资金与成本错误、核心状态不可恢复、主链断裂、伪完成/伪利润 | 必须通过；失败即 `FAIL/BLOCK` |
| `P1` | 高频岗位无法完成、关键交接断裂、跨端口径不一致、重复记账、明显错误引导 | 必须通过或有用户书面接受 |
| `P2` | 恢复路径、空态、性能、可访问性、信息层级和一般交互问题 | 可条件通过，但必须登记残余风险 |
| `P3` | 文案、视觉细节和低风险一致性问题 | 可进入后续批次修复 |

## 2. 风险维度

```text
角色范围 × 数据范围 × 端面 × 对象状态 × 动作影响 × 金额敏感度 × 可逆性
```

以下组合默认升一级：

- 涉及跨企业、跨门店、跨团队、本人和项目参与关系；
- 涉及合同金额、报价快照、成本、利润、应收、应付、收付款、结算；
- 涉及删除、作废、冲正、权限变更、签约、验收确认、正式发布；
- 涉及不可逆外部副作用；
- 同一事实在多个端或多个角色出现，且口径可能分叉。

## 3. 选测规则

每次变更至少选择：

1. 变更对象的自身正向用例；
2. 一条非法状态或权限拒绝；
3. 一个上游来源和一个下游消费者；
4. 同一事实的主要跨端回读；
5. 若涉及写操作，验证重复提交和刷新恢复。

## 4. 不做的过度测试

不为追求“用例数量”重复执行同一组合；不因低风险文案逐页跑全量；不把内部 SQL 条数、Provider 数量或菜单数量当作业务通过率。

# 测试用例规范

## 1. 用例 ID

```text
TC-<AREA>-<ROLE-GROUP>-<FLOW>-<NNN>
```

示例：`TC-FIN-FINANCE-RECEIPT-001`。

## 2. 必填字段

| 字段 | 要求 |
| --- | --- |
| `id` | 全局唯一、稳定、不复用 |
| `title` | 以用户目标命名，不以页面功能命名 |
| `priority` | `P0/P1/P2/P3` |
| `area` | 与覆盖模型一致的业务区域 |
| `roles` | 实际执行角色和数据范围 |
| `surfaces` | `Web/App/Owner/API` |
| `scenarioTypes` | happy/negative/permission/order/concurrency/recovery/boundary/parity |
| `businessRuleIds` | 预期结果的事实来源，不得为空；支持 BR/DEC/SCN/OBJ/MET 与 USER-DEC |
| `fixture` | 使用的阶段夹具或独立数据集 |
| `preconditions` | 租户、账号、对象状态、金额/成本前置 |
| `steps` | 页面动作或验证步骤，动作写清角色和端面 |
| `expectedPage` | 页面应显示的结论、下一步和异常 |
| `expectedState` | 对象、状态、金额、权限、责任人的结果 |
| `expectedInvariants` | 可被 API/DB/对账验证的不变量 |
| `forbiddenOutcomes` | 明确禁止的错误结果 |
| `providerRoutes` | 必须存在的同源 Provider，至少一条 |
| `pageTargets` | 页面入口，格式 `web:/path`、`app:/path`、`owner:/path` |
| `evidenceRequired` | 截图、网络、接口、SQL、视频、人工见证 |
| `executionMode` | `manual/e2e/contract/probe/hybrid` |
| `status` | `READY/BLOCKED/STALE/UNMAPPED` |

## 3. 预期结果纪律

- 预期结果必须来自 `BR/DEC/SCN/OBJ/MET/USER-DEC`；
- 当前页面行为、现有接口返回和数据库现状不能反过来证明业务正确；
- 业务规则存在冲突时，用例标 `BLOCKED` 并关联 `GAP-*`；
- 页面、接口和数据库只允许作为同一条业务事实的不同证据面，不允许互相替代。

## 4. 端面与证据不可替代

页面、Provider 和数据库不是三个可以互相顶替的结论，而是同一业务事实的三个观察面：

| 观察面 | 能证明什么 | 不能证明什么 |
| --- | --- | --- |
| 页面 | 真实角色能否看见入口、操作、反馈、恢复并回读到正确对象 | 不能证明权限、金额或数据库事实一定正确 |
| Provider/API | 同一动作是否走同源规则、返回契约和错误语义 | 不能证明页面实际调用、展示、重置或提交了正确对象 |
| DB/账务不变量 | 状态、金额、唯一性和事务结果最终是否守恒 | 不能证明用户能从页面完成动作或理解失败原因 |

因此：

- 声明 `Web/App/Owner` 端面的用例，PASS 必须有真实页面路径、交互动作、操作前后页面状态和结果回读；
- 只有 API 200、SQL 结果、日志或静态代码检查，不能把页面用例判为 PASS；
- 只有页面截图，不能把涉及金额、权限、状态或事务的用例判为 PASS；
- 页面显示对象、最终提交对象、接口接收对象和 DB 结果必须能一一对应；任一环节出现旧员工、旧月份、旧项目、旧金额或旧附件，均为交互缺陷。

## 5. 真实交互场景最低覆盖

每个涉及录入、编辑或动作提交的业务域，除单一 happy path 外还必须覆盖：

- **入口与时序**：从菜单、列表、详情、通知、返回栈、刷新后重新进入；
- **重复进入**：关闭、取消、保存成功、保存失败后再次打开；
- **对象切换**：员工、客户、项目、月份、门店、账户、供应商等上下文切换；
- **旧响应**：对象 A 请求未返回时切换到对象 B，A 的迟到响应不得覆盖 B；
- **页面回访**：返回上一页、切页签、切后台、刷新、断线重连后的页面状态；
- **乱序与回退**：跳步、逆向操作、重复点击、失败后重试、状态已变化再操作；
- **角色交接**：同一对象在 BOSS/店长/财务/员工/业主之间切换后，可见动作和数据范围一致；
- **跨端同源**：同一事实在 App/Web/业主端显示、提交和回读的对象与状态一致。

只按定义好的单一业务流程执行通过，不能代表真实业务可用。

## 6. 表单生命周期强制检查

每个新建/编辑表单至少执行以下生命周期矩阵；涉及 P0 财务、工资、合同、收款、付款、成本或权限字段时全部为阻断项：

| 阶段 | 必测结果 |
| --- | --- |
| 首次打开 | 新建状态为空；编辑状态只水合当前对象真实数据 |
| 输入后关闭/取消 | 未保存值不得在下次打开时残留 |
| 再次打开 | 重置为新上下文；不得复用上一次员工、项目、月份、金额、备注、附件或选择器结果 |
| 切换对象 | 旧对象字段清空；依赖字段和默认值按新对象重新加载 |
| 旧请求返回 | 旧响应不得覆盖新对象的页面、字段、提交上下文或错误提示 |
| 保存失败 | 仅保留当前上下文输入，提示可恢复，不产生半成品事实 |
| 保存成功 | 退出编辑态，列表/详情回读到最终提交对象 |
| 返回/刷新 | 页面重新水合真实事实，不恢复已放弃草稿 |

还必须验证：页面显示的对象 = 最终提交的对象 = Provider 接收的对象；切换员工、月份、项目、账户或门店后，最终提交不得混入任何旧上下文值。

## 7. 反向用例最低要求

每个业务区域至少覆盖一种：

- 越权或跨范围；
- 非法状态跳转；
- 重复提交；
- 缺失前置或错误字段；
- 失败后的恢复；
- 金额/数量超过边界；
- 历史快照被错误回写。

## 8. 证据最低要求

| 用例类型 | 最低证据 |
| --- | --- |
| 页面正向 | 操作前后截图 + 页面路径 + 角色 + 状态回读 |
| 页面负向 | 拒绝提示截图 + 网络响应/日志摘要 + 状态未变化 |
| 金额/成本 | 页面 + Provider + DB 对账 |
| 权限 | 允许账号正向 + 拒绝账号负向 + 数据范围 |
| 跨端 | App + Web/业主端同事实截图与接口摘要 |
| 并发/幂等 | 两次请求或双击证据 + 唯一事实计数 |
| 表单生命周期 | 打开/重开/切换/取消/失败或成功的前后截图 + 交互序列 + 页面回读 |
| 旧响应竞态 | 请求 A/B 网络顺序 + 最终页面对象 + 最终提交对象 |

建议在结果文件中显式记录 `steps`、`actualPage`、`actualState`、`evidence` 和 `page-result`；文件名或口头说明不能代替结构化回读。

## 9. PASS 判定

页面用例只有同时满足以下条件才能记为 `PASS`：

1. 用例声明的角色、端面、页面入口和数据范围与执行一致；
2. 有实际操作序列，不是只打开页面或只读接口；
3. 有操作前、操作后页面状态/截图，能回读关键字段；
4. 页面显示对象、提交对象、Provider 接收对象一致；
5. 用例要求的状态、金额、权限或 DB 不变量有对应证据；
6. 失败、重试、切换对象、旧响应或跨端场景按用例要求覆盖；
7. 未执行、缺环境或缺业务裁决的项目明确标记 `BLOCKED/STALE`，不得用“功能正常”代替。

开发自测、接口通过、数据库通过、截图齐全均只代表相应证据面通过，不能单独宣称页面验收、独立验收或业务验收通过。

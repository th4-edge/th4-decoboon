# 财务账务业务域专项测试门禁

- 版本：`v0.1`
- 状态：`ACTIVE`
- 建立日期：2026-11-04
- 适用：薪酬、应收、应付、收款、付款、退款、冲正、费用、成本、结算、台账、凭证和财务汇总
- 来源缺陷：`CHG-20261104-001`、`EV-433`
- 业务事实源：`装得清业务智能体`

## 1. 门禁目标

本门禁不只验证页面能够打开或接口返回成功，而是证明：

> 同一个业务事实从来源单据进入财务域后，状态、权限、金额、成本、付款、台账、凭证和报表始终唯一、同源、可解释、可追溯、可恢复。

财务域任何 P0 失败均不得发布；P1 必须有业务负责人书面接受或修复通过。

## 2. 缺陷模型

财务域高风险缺陷统一归入以下模型：

| 类型 | 典型表现 | 必测问题 |
| --- | --- | --- |
| 状态不同源 | 上游状态、下游事实、页面投影不一致 | 谁才是事实源 |
| 状态绕过 | 普通接口直接写 InPayroll、Paid、Confirmed | 是否只能通过合法动作迁移 |
| 上下游锁定错误 | 上游已锁定但页面可改；或下游已删除但上游仍锁定 | 锁定与恢复是否原子 |
| 非法回溯 | 已确认、已发放事实仍可无痕修改 | 是否走冲正、作废或下期调整 |
| 幂等缺失 | 重复确认、重复付款、重复生成应付 | 是否只产生一次财务事实 |
| 金额不守恒 | 应收、应付、付款、台账、成本互相不等 | 是否存在唯一金额勾稽公式 |
| 权限投影错误 | 页面隐藏但 API 可调；或允许角色依赖接口 403 | 页面、主接口、依赖接口是否同权 |
| 数据范围错误 | 门店财务跨店修改、跨租户读取 | 是否只从登录员工解析范围 |
| 跨端枚举/字段错误 | InPayroll 被转成 inpayroll | 后端、Web、App 是否同状态 |
| 审计缺失 | 修改、删除、作废、冲正无原因和前后值 | 是否可追溯责任 |
| 失败恢复缺失 | 请求失败、并发、页面停留后状态损坏 | 是否能安全重试或回读 |

## 3. 门禁分级

| 门禁 | 内容 | 阻断级别 |
| --- | --- | --- |
| `FG0 基线与数据预检` | 提交、制品、账号、租户、数据夹具、备份、业务规则版本 | 不通过禁止执行 |
| `FG1 状态与契约不变量` | 状态机、权限、唯一约束、金额公式、幂等、审计 | P0/P1 失败即阻断 |
| `FG2 真实页面闭环` | Web/App 真实角色操作、异常、恢复、回读 | P0/P1 失败即阻断 |
| `FG3 跨端与跨角色` | App/Web/API/DB 同源，BOSS/财务/店长/员工交接 | 不得以单端通过代替 |
| `FG4 账务对账` | 应收/应付/付款/成本/台账/凭证/报表逐层勾稽 | 不平即阻断 |

## 4. 强制执行规则

### 4.1 业务事实先行

- 每条用例必须有 `BR/DEC/SCN/OBJ/MET` 来源；
- 业务口径存在冲突时，用例必须是 `BLOCKED`；
- 不允许用当前页面表现反推正确业务结果。

### 4.2 四层证据

涉及状态、金额和权限的用例，必须同时具备：

```text
页面证据 + Provider 证据 + DB/账务不变量证据 + 操作前后状态
```

仅有截图、仅有接口 200、仅有 SQL 都不能判定通过。

### 4.3 权限正反验证

每个允许动作必须验证：

- 允许角色成功；
- 拒绝角色得到约定 403/404；
- 跨企业、跨门店、跨团队均拒绝；
- 页面动作、主 Provider、依赖 Provider 同权。

### 4.4 真实用户时序

必须模拟真实操作顺序，包括：

- 先录入后确认；
- 先确认后生成；
- 先生成后修改；
- 提交复核后再次生成；
- 删除草稿后重新生成；
- 页面停留、快速切月、刷新、重复点击；
- 失败后重试；
- 已确认/已发放后要求纠错。

### 4.5 数据修复边界

- 生产真实企业默认只读；
- 破坏性用例只在专用测试租户或经单独审批的 `prod-controlled-write` 执行；
- 任何生产回填必须备份、事务演练、回滚验证和用户确认；
- 已发放工资不得直接改历史，只能走既定作废或下期调整。

## 5. P0 阻断项

以下任一失败，财务域结论必须为 `FAIL/BLOCKED`：

1. 跨企业、跨门店、跨团队越权；
2. 普通更新接口可绕过状态机；
3. 已确认或已发放事实可无痕修改；
4. 重复确认、重复付款、重复台账；
5. 工资项、应付、付款、台账金额不守恒；
6. 成本不完整时仍计算利润或允许结算；
7. 考勤/工资项/工资单状态互相矛盾；
8. 页面允许动作与 API 权限不一致；
9. 财务异常导致部分事务成功、部分失败；
10. 缺少必要审计或无法定位责任人和历史值。

## 6. 核心不变量

| ID | 不变量 |
| --- | --- |
| FIN-INV-01 | 同一员工同一工资月份只有一条考勤 |
| FIN-INV-02 | 同一企业同一工资月份只有一张当前有效工资单 |
| FIN-INV-03 | 考勤只允许合法状态迁移，InPayroll 只能由工资单生成产生 |
| FIN-INV-04 | 工资项存在时考勤必须为 InPayroll |
| FIN-INV-05 | Draft 删除后考勤恢复 Confirmed，且不残留孤儿工资项 |
| FIN-INV-06 | Pending 只能由 BOSS/店长退回，财务不能重建降级 |
| FIN-INV-07 | 工资单确认后每员工只有一条工资应付 |
| FIN-INV-08 | 应付、付款、台账、工资条幂等且金额一致 |
| FIN-INV-09 | 已发放工资不得反改，差异进入下期调整 |
| FIN-INV-10 | 应收、已收、退款、冲正满足金额守恒 |
| FIN-INV-11 | 材料、应付、付款、成本分层勾稽且不重复 |
| FIN-INV-12 | 成本不完整时利润和毛利率为空 |
| FIN-INV-13 | 页面、Provider、DB 对同一状态和动作的结论一致 |
| FIN-INV-14 | 所有高风险动作有操作人、原因、前后状态和时间 |

## 7. 用例覆盖要求

### 7.1 表单交互状态生命周期

财务新建和编辑表单必须作为独立门禁对象，不能只验证保存接口：

- 新建打开：必须为空状态；
- 编辑打开：只允许水合目标对象的真实数据；
- 关闭或取消：未保存数据不得在下次打开时继续出现；
- 切换员工、项目、月份、门店或账户：依赖字段必须清空，默认值必须按新上下文重新加载；
- 切换对象后旧请求返回：不得覆盖新对象数据；
- 保存成功：退出当前表单状态；
- 保存失败：仅保留当前上下文的输入，供同一用户重试；
- Web 与 App：同一对象切换和重开行为必须一致。

页面显示对象、最终提交对象和接口接收对象必须完全相同。任何旧员工、旧月份、旧项目、旧金额或旧附件进入新对象，均按 P0/P1 交互缺陷处理。

机器门禁同时强制检查：

- 表单生命周期用例必须声明 `page_path`、`before_after_screenshot`、`interaction_sequence` 和 `state_readback`（竞态用例以 `network_trace` 替代状态回读）；
- 声明 `Web/App/Owner` 端必须存在对应端面的页面目标；
- 页面用例 PASS 必须存在真实交互步骤、页面回读和可解析的 `page-result`，不能只有 API/SQL/静态代码证据；
- 缺少考勤重开/切换、旧响应竞态、通用财务表单或 App 同源用例时，财务专项门禁直接失败。

每个财务发布至少覆盖：

- 1 条上游来源 → 下游财务事实；
- 1 条非法状态跳转；
- 1 条允许角色和 1 条拒绝角色；
- 1 条重复提交或并发；
- 1 条失败恢复；
- 1 条页面 + API + DB 对账；
- 1 条 Web/App 同源；
- 1 条金额或成本边界；
- 1 条历史/跨期调整。

## 8. 用例状态

- `READY`：业务规则、Provider、页面和夹具可定位；
- `BLOCKED`：缺业务裁决、账号、环境或回滚条件；
- `STALE`：业务规则或制品版本变化；
- `UNMAPPED`：缺少 Provider、页面或规则。

## 9. 缺陷等级

| 等级 | 财务域判定 |
| --- | --- |
| P0 | 越权、重复账、资金错误、成本/利润伪造、不可恢复状态、已发历史被反改 |
| P1 | 主流程阻断、跨端不一致、状态/金额对账失败、关键恢复缺失 |
| P2 | 高频交互错误、分页/性能/恢复提示问题 |
| P3 | 低风险文案和视觉问题 |

## 10. 退出准则

财务域可标记 `PASS` 必须同时满足：

1. P0 用例 100% 通过；
2. P1 无未接受阻断；
3. 状态机、权限、金额、幂等和审计不变量全部通过；
4. Web/App/Provider/DB 完成同源对账；
5. 失败、并发、重复提交和旧页面场景有证据；
6. 生产只读或受控写入边界没有被突破；
7. 未覆盖项、残余风险和人工验收边界明确；
8. 独立验收结论不晚于本次制品提交。

## 11. 结论口径

- `PASS`：门禁范围内通过；
- `CONDITIONAL_PASS`：只允许 P2/P3 条件通过，且必须有明确接受记录；
- `FAIL`：任一 P0 失败；
- `BLOCKED`：业务规则、环境、身份或数据不可用；
- 开发自测、自动化通过、页面冒烟均不得表述为独立验收或业务验收。

02

总体架构设计思路

一条主线：后端以「领域模型驱动」替代 MVC 的「接口翻译」；App 以「领域分包 + 角色开放」消费后端 Provider，状态机与权限永远在后端。

2.1 后端：th4 领域模型驱动的五条铁律

铁律传统 MVCth4 领域模型驱动
入口Controller + @RequestMappingProvider（框架自动扫描 @Service 注册路由，无 Controller）
入参DTO / VO / Query 对象领域模型实体（Customer、Quote…），工程中不存在 DTO
字段获取@RequestBody DTO + getterProvider 成员变量 + @AutoInject + 校验注解
响应VO / Result 包装实体对象（Customer、Page<Customer>）
实体关联裸外键 Long id对象关联：Employee emp + @ManyToOne(LAZY)
序列化控制@JsonIgnore / 手写 VO具体 Provider 用 @Properties；通用 ModelService 用 @ServiceProperties
权限登录后即可访问@DataPermission 四级数据范围，每次查询服务端强约束
一句话记忆：服务 = 为实体服务；入参 = 实体；字段 = AutoInject；响应 = 实体；关联 = ManyToOne；具体 Provider 序列化 = @Properties。

2.2 后端三层包结构（components / tenant / decoboon）

边界一句话：components 决定「怎么发」，业务领域决定「何时发、发给谁、发完后做什么」；tenant.access 承载全部数据权限公共能力，业务域只声明与编排。

2.3 App 端：领域分包 + 角色开放

依赖方向单一：pages → domains/*/api + roles/permission → core/http → 后端 Provider。禁止页面直接 uni.request 或拼接路由。

03

后端核心设计

从 Provider 的「为谁服务」出发，逐层展开服务声明、注解体系、数据权限闭环、实体规范与序列化控制。

3.1 Provider 模式：服务 = 为实体服务

声明（接口）

// customer/service/cust/save/Save.java（接口）
public interface Save extends Provider<Customer, Customer>, Security {
}

Request 直接是实体类型（无 DTO）；需要登录的接口继承 Security。

实现（support 包）

// customer/service/cust/save/support/Save.java
@Service("customer/customer/save")   // 路由
@Scope(ScopeTypes.PROTOTYPE)
public class Save implements ...Save {
    @User private Employee employee;   // 登录员工
    @AutoInject @NotEmpty private String name;
    @AutoInject private Long ownerId;
    public Customer call(@ModelSaveInject Customer request) {
        Employee current = tenantContext.requireEmployee(employee);
        Employee owner = customerContext.resolveOwner(current, ownerId, current);
        customerContext.applyOwnership(request, owner);
        request.setStatus(CustStatus.New);   // 服务端覆盖安全字段
        return customerRepository.save(request);
    }
}

Provider 注解体系

注解职责要点
@Service("域/对象/能力")注册 Provider 路由（框架扫描 Spring @Service + Provider 接口的 bean）不用 @Component；路由不再带 decoboon/ 前缀
@AutoInject把请求 JSON 展开的同名变量注入 Provider 成员变量支持别名、对象封装、集合/枚举/日期；前端字段一律走它
@ModelSaveInject / @ModelUpdateInject按请求变量组装/合并模型对象（标注在 call 参数上）不落库、不做数据权限；save/persist 与归属覆盖由 Provider/切面完成
@User注入当前登录 Employee（框架校验合法性）Request=Employee 用参数注入；其他 Request 用字段注入；禁止与 @AutoInject 混用
@NotNull/@NotEmpty/@Length调用前声明式校验禁止在 call() 里手写 if null throw
@ServiceName声明通用 ModelService 能力名（page/save/…）仅框架通用 CRUD 使用；自定义业务 Provider 禁用
通用 CRUD 优先走框架 ModelService：URL 约定 {model}-service（如 user-save、user-update），覆盖 build/save/update/delete/info/page/list/tree/enums/count/unique/report；只有通用能力覆盖不了的业务动作才写自定义 Provider。

3.3 实体规范：对象关联建模

实体骨架

@Note("客户") @Description("…") @Model @Entity
@DataPermission
@Table(name = "cust_customer", indexes = {…四级联合索引…})
public class Customer extends AuditModel {
  @Id @GeneratedValue(strategy = IDENTITY)
  private Long custId;               // 主键简洁

  @ManyToOne(fetch = LAZY) @JoinColumn(name="com_id", nullable=false)
  private Company company;            // 对象关联，禁止裸外键

  @Keyword @Column(length=32, nullable=false)
  private String name;                // 全局搜索可命中
}

关键规则

  • 关联 = 对象 + @ManyToOne(LAZY)：Employee emp，数据库列由 @JoinColumn 显式指定
  • 时间字段按用途选择：参与年/月/季度统计的用框架 DateTime（@Embedded + @AttributeOverrides）；纯日期标记用 LocalDateTime/LocalDate；审计时间 @CreateTime/@UpdateTime + DateTime；纯流水（如 BalanceLedger.createTime）用 LocalDateTime
  • 枚举实现 Enumerable<T> 放 configure 包，命名简洁（SubStatus 而非 SubscriptionStatus）
  • 可搜索字段加 @Keyword：前端全局搜索（Ctrl+K）对 @Keyword 的 String 字段做 OR 模糊匹配，跨关联递归
  • 禁止：实体写业务逻辑、@JsonIgnore、裸 Long 外键、统计时间用 LocalDateTime
  • 金额/大小用 @Unit("万元") 标注

3.4 序列化控制：@Properties 与 @ServiceProperties 边界

场景机制示例
具体自定义 Provider类上直接 @Properties（ignore 敏感字段 / allow 白名单）@Properties(allow=@AllowProperties(model=Customer.class, properties={"custId","name","owner"}))
框架通用 {model}-{service} 路由（无自定义 Provider）模型或统一配置上 @ServiceProperties(uris=…, properties=@Properties(…))@ServiceProperties(uris={"user-save","user-update"}, properties=@Properties(ignore=…password,salt))
关联对象裁剪@AllowProperties 白名单最小字段Employee 只允许 empId/name，不透传完整归属树
轻量化响应原则（强制）：page/list 只返回列表展示、筛选、跳转字段；info 返回详情页实际字段；save/update 返回前端更新本地状态的最小实体。关联对象只有在页面确实展示时才返回——列表与详情不得复用同一套「大而全」配置。@ServiceProperties 只管返回什么，管不了查得到什么，权限由 @DataPermission 体系负责。

3.5 租户、用户与订阅

组织模型

  • 租户 = Company；Employee（员工，实现框架 User）归属 company + store + team，角色 EmployeeRole
  • 注册只创建一家默认总店（Store.defaultStore=true），前端默认不展示门店维度；多门店是套餐权益（Plan.maxStores 控制）
  • 登录链路：user/sms/send（阿里云 DYPNS 验证码）→ user/login / user/register / user/invite / user/accept
  • 登录主体通过 JPQL 构造为普通 Employee 实体（非 Hibernate 代理）

订阅约定

  • 主体 Subscription，主键 subId，状态 SubStatus（Trial 起步）
  • 剩余可用天数不落库：serviceEndTime - now 动态计算；禁止 balanceDays 字段与每日递减
  • 续费/试用只维护 serviceEndTime / plan / status / trialActivated；BalanceLedger 保留变动天数与快照供审计（createTime 用 LocalDateTime）
  • 平台订阅账务与项目账务（finance 域）严格分离

04

App 前端核心设计

uni-app（Vue3 + TS + Vite）微信小程序端：领域分包消费后端 Provider，角色驱动可见域，页面不承载任何持久化与状态机。

4.1 领域分包：每域 model / api / meta

标准结构

src/domains/project/
├── model.ts   // 前端领域实体（对象关联保持形态）
├── api.ts     // 封装 Provider 路由 + normalize 适配

4.2 HTTP 协议与适配层

// src/core/http.ts 核心协议
export interface ProviderEnvelope<T> {
  success: boolean;  data: T;
  errorCode?: { code: string; message: string };
}
// POST {apiBase}{uri}，header 带 token
// 成功(200~299 && success) → resolve(data)
// 401 → logout + 重登；500 → 服务不可用；业务错误 → reject(message)

// 列表统一解包：Page<T> → T[]
export function listOf<T>(result: PageResult<T> | T[]): T[]

后端业务异常统一 HTTP 200 + {success:false,errorCode}，页面必须在异步边界 try/catch 并用 toastError 展示后端 message；列表初始化也不能漏 catch。

normalize 适配：后端实体 → 前端语义模型

// domains/project/api.ts 片段
const PROJECT_STATUS: Record<string, Project['status']> = {
  Preparing: 'preparing', Ongoing: 'ongoing', Suspended: 'suspended',
  Accepting: 'accepting', Finished: 'finished', Settled: 'settled' };
export function normalizeProject(raw: RawRecord): Project {
  return { ...raw, id: String(raw.id ?? raw.projectId ?? ''),
    address: raw.address ?? raw.siteAddr ?? '',
    status: PROJECT_STATUS[enumValue(raw.status)] || 'preparing',
    customer: raw.customer ? normalizeCustomer(raw.customer) : undefined, … };
}

适配层只做字段协议映射（projectId→id、siteAddr→address、枚举对象→字符串），不在页面创建 VO/DTO；后端 Provider 应逐步对齐目标字段。

4.3 角色与权限（roles 层）

角色目录 catalog.ts

  • ROLE_META：10 员工岗位 + 业主客户（角色名/短名/品牌色/描述）
  • ROLE_TABS：同一套页面按角色返回不同 Tab（marketer 见客户，pm 见履约，finance 见财务）
  • ROLE_ACTIONS：工作台快捷入口按角色声明，页面不再堆叠角色判断
  • 新增角色只需改 EmployeeRole + ROLE_META + ROLE_TABS + ROLE_ACTIONS + permission 矩阵

能力矩阵 permission.ts

Capability 语义：view: 查看 / edit: 编辑 / act: 动作。如 view:finance、edit:plan、act:acceptConfirm。boss 拥有全量能力，customer 仅有 view:myProjects / view:contract / act:acceptConfirm / view:notice。

前端矩阵只管可见性。AGENTS.md 与后端约定一致：列表先过 visibleProjects()，服务端仍必须按 Company / ProjectMember / 数据归属强制过滤——前端隐藏菜单不构成权限。

4.5 页面模式与设计系统

页面约定

  • onShow 重新拉取 Provider 数据，不依赖本地缓存状态；下拉刷新 / 返回均重新获取
  • 页面只提交业务对象或调用领域能力（如 scheduleApi.confirmNode），状态流转交给后端后重新拉取
  • 跳转统一 P.* 路由常量（src/config/index.ts），禁止魔法字符串
  • 表单/汇报/上传组件只收集输入后调用领域 API，不在组件内维护业务状态
  • 正式 UI 禁止 emoji / 字符箭头 / 字符加号，统一用 JzIcon.vue 线性图标

品牌 Token（uni.scss）

  • 主色 $jzb-primary: #16A394，深色 #0E8A7D；语义色 success/warning/danger 各带 soft 底色
  • 文字四档 $jzb-text-1~4、边框、页面底色、阴影、圆角、间距全套 token
  • 页面只组合 src/styles/base.scss 与 src/components（JzButton/JzCard/JzTag/JzProgress/JzAvatar/JzEmpty/JzReportCard/JzIcon…），禁止散落自造颜色

5.3 业务动作边界

状态机只存在于后端：业务动作优先保存对应实体（如客户确认验收保存 AcceptanceConfirm），由后端监听器/Context 推进状态（验收确认 → 阶段 Done → 项目状态刷新），App 只重新拉取。禁止在前端直接改下一阶段状态，也禁止页面维护本地状态机。
错误约定：后端业务异常统一 HTTP 200 + {success:false, errorCode:{code,message}}；App 的 http.ts 将其转为 Promise reject，页面用 try/catch + toastError 展示后端 message；401 统一登出重登。接口越权统一 404「不存在或无权访问」。

心智模型总结

把整套工程浓缩为可迁移的设计原则，新功能开发前先过一遍。

后端：五条铁律 + 权限先行

  • 服务 = 为实体服务：Request/Response 都是实体，杜绝翻译层
  • 字段 = AutoInject：声明式校验，不在 call() 里做空值判断
  • 关联 = 对象：@ManyToOne(LAZY)，序列化用 @Properties 裁剪
  • 权限 = 服务端强约束：@DataPermission + 统一过滤器/切面，四级范围与角色集中绑定
  • 状态机 = Context 收敛：实体只承载数据，业务状态变化统一由领域 Context 推进（如 ProjectContext）

App：五条铁律对齐

  • 无 DTO 心智：直接消费领域实体，normalize 只做字段协议适配
  • 权限先于渲染：角色决定可见域，服务端仍强制校验
  • 状态机在后端：页面只提交动作后重拉
  • 路由集中管理：P.* 常量，禁止魔法字符串
  • 品牌统一：$jzb-* token，页面不散落自造样式
一句话贯穿全工程：「后端决定查得到什么（@DataPermission 数据权限）与返回什么（@Properties 序列化），App 决定看得到什么（角色/能力矩阵）与操作什么（领域 API）；两层永远不互相替代。」

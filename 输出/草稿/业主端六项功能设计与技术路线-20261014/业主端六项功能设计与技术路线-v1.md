### 0.3 业主写操作：**既有模式，沿用即可**（原稿曾误判为空白，已更正）

**结论：业主身份上下文已经存在，并已在生产链路上验证。六项功能沿用同一模式，不需要新建机制。**

既有实现（`customer/service/acceptance/update/support/Update.java` —— 业主验收确认）：

```java
@Service("customer/acceptance/update")
@Scope(ScopeTypes.PROTOTYPE)
public class Update implements ...Update {

    @User                                   // 注意：不是 Employee
    private User<?> principal;

    @AutoInject @NotNull private Long acceptanceId;
    @AutoInject @NotNull private Boolean confirmed;

    private final CustomerAccessContext accessContext;
    private final DistributedLock distributedLock;   // Redisson 分布式锁
    ...
}
```

`CustomerAccessContext` 提供的能力：

| 方法 | 作用 |
| --- | --- |
| `requireCredential(User<?> principal)` | 取得业主凭证 |
| `activeAccesses(Credentials)` | 该业主的全部有效授权 |
| `requireAccess(Credentials, projectId)` | 校验业主对该项目的访问权 |
| `requireProject(Credentials, projectId)` | 取项目（进而取 `project.getCompany()`） |
| `attachSession(Credentials)` | 绑定会话 |

由此得到业主写操作的四条固定写法：

1. **鉴权**：`@User User<?> principal` + `accessContext.requireProject(credential, projectId)`；
   **不使用** `@User Employee`，**不使用** `DataScopeSpecification`（那是员工侧机制）。
2. **企业归属**：取 `project.getCompany()`，而**不是**"登录员工所属企业"。
3. **并发**：统一 `DistributedLock`（Redisson），禁止 `@Lock` / `FOR UPDATE`（`DEC-029`）。
4. **幂等**：同一结果重复提交必须幂等（既有实现已按此处理）。
5. **字段白名单**：`@Properties` + `@AllowProperties` 显式列举业主可见字段（`ECD-011`）。

**六项功能中的 4 项业主写操作（自查提交、材料确认、验收确认、投诉）全部沿用此模式。**

仍需注意的两个差异点：

- 漏项自查的**平台清单**查询属于平台域只读，不走 `CustomerAccessContext`，需单独限定平台运营权限。
- 360 全景的**验收门禁**应加在**员工侧提交验收**的 Provider 上，而不是业主确认侧。

### 0.4 共同技术规范（th4 铁律落地）

```text
Provider 接口   {领域}.service.{对象}.{能力}      接口名 = 能力名（一个单词）
Provider 实现   {领域}.service.{对象}.{能力}.support.{能力}
路由            @Service("{域}/{对象}/{能力}")
能力名          固定集合：page/list/info/save/build/update/delete/count/enums/tree/report/unique
实体            继承 AbstractModel；@Model+@Note+@Entity+@Table；@Id+@SnowflakeId
                @EntityListeners(SnowflakeEntityListener.class)
关联            @ManyToOne(fetch=LAZY) + @JoinColumn；业务实体必须含 Company company
序列化          @Properties 按 page/list/info/save/update 裁剪；禁止 @JsonIgnore
索引            com_id 最左：(com_id, 业务主键) / (com_id, store_id|team_id|emp_id, 业务主键)
并发            禁止 @Lock(PESSIMISTIC_*) / FOR UPDATE；统一 RedissonLock
统计            聚合/投影 SQL；禁止全量实体 + Java 循环；列表带 LIMIT
迁移            ddl-auto:update 不改既有列类型；长文本需补 alter table ... longtext
```

## 1. 漏项自查表

### 1.1 业务流程

```text
报价进入"待客户确认"
-> 业主端出现入口「开工前先对一下」
-> 按本户真实条件（面积段 / 房间数 / 户型）匹配行业清单
-> 业主逐项勾选：我家有 / 我家没有 / 不确定
-> 系统只提示"这 3 项你没确认，建议问设计师"
-> 可一键问设计师（复用既有诉求链路）
-> 结果留痕，绑定当时的清单版本
```

### 1.2 关键裁决（`ANS-BIZ-20261014-002`）

- 清单知识**归平台**，不进租户隔离范围；企业仅可**补充**本企业项。
- 勾选结果**只作提示与沟通依据**，**不得自动加项、不得作为减项依据**。
- 不得承诺"用了就不会漏"。

### 1.3 对象设计

**平台侧（`com.th4.edge.platform` 域，非租户数据）**

| 对象 | 关键字段 |
| --- | --- |
| `ChecklistTemplate` | templateId、code、name、houseType、areaMin、areaMax、roomCount、version、status、publishedAt |
| `ChecklistTemplateItem` | itemId、template、category(Enum)、name、description、commonLevel、sort |

**租户侧**

| 对象 | 关键字段 |
| --- | --- |
| `QuoteChecklistRun` | runId、company、quote、customer、template、templateVersion、runAt、status |
| `QuoteChecklistAnswer` | answerId、company、run、**itemSnapshot**（category/name 冗余）、result(Enum)、remark、sort |
| `CompanyChecklistItem` | company、category、name、description、status（企业自定义补充项） |

**必须做快照**：`QuoteChecklistAnswer` 保存 `itemSnapshot`，因为平台清单会升版本，历史结果不能随清单漂移。

### 1.4 接口（Provider）

| 路由 | 能力 | 说明 |
| --- | --- | --- |
| `platform/checklistTemplate/page\|info\|save\|update` | 平台运营维护清单 | 仅平台运营 |
| `quote/checklist/build` | 按本户匹配清单 + 历史回答 | 业主/设计师 |
| `quote/checklist/save` | 提交勾选结果 | 业主本人 |
| `quote/checklist/info` | 查看已提交结果 | 业主/设计师 |
| `quote/checklistitem/save\|delete\|page` | 企业自定义补充项 | BOSS/店长 |

### 1.5 权限与索引

- 业主 Self；设计师/店长按客户数据范围；平台清单仅平台运营。
- 索引：`(com_id, quote_id)`、`(com_id, customer_id)`、`(com_id, run_id, sort)`。

### 1.6 性能约束

- 匹配清单：**一次**模板匹配查询 + **一次**批量取历史回答；禁止逐项查库。
- 响应体：清单项上限 40 条，超出截断并返回总数。

### 1.7 前端落点

- 报价详情页 + 首页待办 →「开工前先对一下」
- 结果页：逐项勾选 + 未确认项汇总 + 「问设计师」按钮

### 1.8 风险

- 「问设计师」若复用 `CustomerFeedback`，会把咨询与投诉混在一个对象里 → 建议复用 `Requirement`（业主诉求），见 `GAP-028` 口径。

## 2. 现场整洁打卡

### 2.1 业务流程

```text
项目经理/工长每日提交现场日报
-> 必含 1 张全景照 + 整洁度自评
-> 业主端「家的相册」按日期可见（只看照片与日期）
-> 连续未打卡 -> 提示项目经理（企业内部待办）
```

### 2.2 关键裁决

- **日报项，不阻断施工**（未打卡不影响阶段推进）。
- 整洁度评级**不进业主端**（避免制造对抗），仅作企业侧现场管理事实。
- **不得对工人产生公开评分或排行**。

### 2.3 对象设计（扩展，不新增）

在既有 `ProjectReport` 上增加：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `reportType` | Enumerable | Progress / Cleanliness / MaterialArrival / Concealed |
| `cleanliness` | Enumerable | Tidy / Normal / Messy（**仅企业侧可见**） |
| `isPanorama` | Boolean | 是否含全景照 |

**不落库"连续未打卡天数"**，由统计推导（对齐 `rules.md` §13 可完成状态投影：完成只由真实领域对象推导）。

### 2.4 接口

| 路由 | 能力 | 说明 |
| --- | --- | --- |
| `project/report/save\|update\|page\|info` | 既有扩展 | 新增三字段 |
| `project/report/report` | 新增统计 | 打卡率（聚合 SQL） |

> 统计必须走聚合/投影 SQL，带 `LIMIT`，禁止全量实体 + Java 循环（`rules.md` §0.4）。

### 2.5 序列化（关键）

- `@Properties` 必须按角色裁剪：**业主视图不得返回 `cleanliness`**。
- 业主端只返回：日期、阶段、照片、落款人。

### 2.6 索引

- `(com_id, project_id, report_date)`、`(com_id, project_id, report_type)`

### 2.7 迁移注意

- 新增枚举列必须**给定默认值**，避免历史行空值导致枚举反序列化失败（参考 `GAP-054` 的 ENUM 缺值事故）。

## 3. 材料到场记录（**2026-10-14 变更**：告知 + 留痕，非确认门禁）

> 本节原为「材料到场确认卡」（业主确认门禁 + 超时放行），已由 `USER-DECISION-20261014-003` 变更。

### 3.1 业务流程

```text
材料到场
-> 项目经理上传自然光无滤镜照片 + 填入现场品牌型号/批次
-> 系统与选材快照比对（只做"是否一致"的事实呈现）
-> 记录留档，业主端告知性可见
   （无确认动作、无倒计时、不阻断施工）
-> 业主发现不符时可随时反馈（走既有诉求/投诉链路）
```

### 3.2 关键裁决（`USER-DECISION-20261014-003`）

| 项 | 口径 |
| --- | --- |
| 性质 | 装企的**执行记录**；业主**告知性可见** |
| 业主动作 | **无确认动作**（仅保留"发现不符可反馈"） |
| 是否阻断施工 | **不存在阻断** |
| 超时机制 | **不需要**（不设门禁，故无超时与放行） |
| 责任 | 到场核对责任归**装企**（项目经理 + 材料员），**不转嫁给业主** |
| 留档目的 | 留个证据：以后能查**当时到场的是什么** |
| **不解决** | 质量是否合格；**到场记录 ≠ 验收**，不得表述为"验收通过" |

### 3.3 对象设计（新增，但**无状态机**）

`MaterialArrivalNotice`（材料到场记录）

| 字段 | 说明 |
| --- | --- |
| noticeId / company / store / project / materialPlan | 归属链（`Company` 必填） |
| batchNo / arrivedAt / reporter(Employee) | 到场事实 |
| evidenceFileIds | 自然光照片/视频（走既有 OSS） |
| snapshotBrand / snapshotModel / snapshotColor / snapshotSpec | 来自 `MaterialSelection` 的选材快照 |
| actualBrand / actualModel / actualColor / actualSpec | 现场填报 |
| compareResult | Enum：Match / Mismatch / Unknown |

**已删除的字段**：`customerStatus`、`customerConfirmedAt`、`timeoutAt`、`releasedBy`、`openForUse`。

**不改变** `MaterialPlan` 既有状态语义；到场记录是平行新事实。

### 3.4 状态

**无状态机。** 记录一经创建即只读；业主反馈走既有诉求/投诉链路，不在本对象上建模状态。

### 3.5 接口

| 路由 | 能力 | 说明 |
| --- | --- | --- |
| `material/arrival/build\|save\|info\|page` | 项目侧创建与查询 | 项目经理/材料员 |
| 业主只读 | 随 `journey/info` 的 material section 返回 | 复用既有投影，不新开路由 |

> 业主侧**没有** `update` 能力——因为不存在业主确认动作。这是本项与其余五项最大的结构差异。

### 3.6 定时任务

**无。** 不设超时，故不需要扫描与放行任务。

### 3.7 索引

- `(com_id, project_id, arrived_at)`
- `(com_id, material_plan_id)`

### 3.8 风险

- 快照来源 `MaterialSelection` 未确认即到场时，`compareResult = Unknown`，**不得默认判 Match**。
- 比对结果只是事实呈现，**不得**作为对供应商的违约判定依据。

## 4. 我的确认记录

### 4.1 业务流程

业主端新增入口，**按确认时间倒序**回看「我确认过什么」：报价版本、方案、合同、验收、增减项、选材、付款。

### 4.2 关键裁决

> **2026-10-14 补充口径（`USER-DECISION-20261014-004`）**：
> 业主进入系统的前提是「合同生效 → 项目立项 → 员工发邀请 → 业主接受」，
> **合同生效前业主在系统中不存在**。因此报价接受、合同签署等前期环节**只能由员工登记**。
> 本视图必须**区分两类**：
> ① 业主本人确认的（阶段验收、整改复验）——标「我确认」；
> ② 线下签认后由企业登记的（报价、合同、增减项、选材、量房）——标「已签认」并显示**登记人**。
> **禁止**把代登记一概表述为业主自助确认（`DEC-015` 硬规定）。

- **只投影业主本人动作产生的确认**，不展示内部审批链。
- 金额默认展示，**业主可关闭**。
- **不可编辑、不可删除**。
- 必须与 `journey/info` **同源同口径**（`ECD-011`）。

### 4.3 实现路线（推荐方案 A）

**方案 A（推荐）**：在既有 `CustomerJourneyContext` 中新增 `confirmationSection(...)`，与其他 10 个 section 同源。

```text
CustomerJourneyContext
├─ measureSection      ├─ contractSection
├─ designSection       ├─ changeSection
├─ quoteSection        ├─ materialSection
├─ constructionSection ├─ acceptanceSection
├─ paymentSection      ├─ feedbackSection
└─ confirmationSection ← 新增（跨来源聚合确认事实）
```

**不做**新路由 `customer/journey/list`——会被误解为"项目列表"，且违背同源口径。

**体积控制（`DEC-037`：响应体大小是一等公民）**：
- `confirmationSection` **默认不返回**，通过 `sections=confirmation` 按需加载；
- 局部加载失败**不得伪装为空**（对齐 `GAP-010` 教训），必须返回"暂不可确认"状态。

### 4.4 性能约束

- 一条 **UNION ALL 投影 SQL**（quote / design / contract / acceptance / change / selection / payment 的确认事实），
  `ORDER BY confirmed_at DESC LIMIT 50`。
- **禁止**逐来源查库后 Java 合并排序。
- 各来源表评估 `(com_id, customer_id, confirmed_at)` 类索引。

### 4.5 验收

- 同一事件在 `journey/info` 其他 section 与本记录中**必须一致**（跨页口径一致）。

### 4.6 风险

- 若某来源缺少"确认时间"字段，必须**如实不展示**，不得用创建时间替代（会误导业主）。

## 5. 360 全景隐蔽工程图

### 5.1 业务流程

```text
水电工程 / 防水工程 施工完成、封槽之前
-> 项目经理上传等距圆柱全景影像
-> 归档为隐蔽工程档案
-> 作为该阶段验收的必须条件
-> 业主确认阶段验收
-> 档案长期保留，业主可随时查看
```

### 5.2 关键裁决

- **是水电与防水阶段验收的必要条件**（这两道工序完成后即封闭）。
- 权属归**租户企业**；业主享**长期查看权**；保留期**不得低于对应质保期**。
- **不引入 3D 引擎**作为必需依赖。
- 只作"当时现场事实"，**不作质量判定**。

### 5.3 对象设计（新增）

`ConcealedWorkArchive`

| 字段 | 说明 |
| --- | --- |
| archiveId / company / project / stage | 归属链 |
| archiveType | Enum：Electric / Waterproof |
| equirectangularFileId / thumbFileId | 走既有 OSS 能力（`USER-DECISION-20261010-007`） |
| capturedAt / capturedBy(Employee) | 采集事实 |
| rooms | 区域引用（复用既有区域对象） |
| acceptance | 关联验收单（可空） |
| status | 有效 / 已替换 / 已失效 |

**不做独立对象复用相册**：相册是展示语义（`ProjectAlbumEntry`），隐蔽工程档案有**验收门禁语义**，两者不同，混用会让门禁逻辑无处安放。

### 5.4 验收门禁实现

- 位置：阶段验收 `build`/`save` 的 Provider 内校验（或 `@ModelSaveInject` 的加载组装阶段）。
- 规则：阶段属于 水电/防水 → 必须存在 ≥1 条 `ConcealedWorkArchive`。
- **门禁失败必须给可执行提示**（"请先上传水电全景影像"），不得只抛通用错误。

### 5.5 技术形态

| 项 | 方案 |
| --- | --- |
| 影像格式 | 等距圆柱（equirectangular）JPG，2:1 |
| 小程序查看 | `web-view` 嵌轻量 H5 全景查看器（优先）；降级为可手势拖动的大图 |
| 缩略图 | 服务端生成 2:1 缩略图，列表用缩略图 |
| 不引入 | three.js 等 3D 引擎作为必需依赖 |

### 5.6 接口

| 路由 | 能力 | 说明 |
| --- | --- | --- |
| `project/archive/build\|save\|info\|page` | 项目侧 | 项目经理 |
| 业主只读 | 随 `journey/info` 的 acceptance / profile section 返回 | — |

### 5.7 索引

- `(com_id, project_id, archive_type)`、`(com_id, acceptance_id, status)`

### 5.8 风险

- 大文件上传失败重试、断点续传需评估；上传失败不得让验收门禁误判为"已归档"。
- 保留期超出质保期后的处置见 `GAP-056`。

## 6. 一键投诉

### 6.1 业务流程

```text
业主提交投诉
-> 按企业配置时限计时（默认 48h）
-> 业主端可见处理进度与倒计时
-> 超时未处理 -> 自动升级至 BOSS + 通知 + 留痕
-> 处理完成 -> 关闭
```

### 6.2 关键裁决

- 时限由**企业配置**，平台不替装企定时限。
- 一人装企（`BR-028`）BOSS 即全角色，**无越级空间**，文案为"**直接送达负责人**"，不得写"越级投诉"。
- 业主**可见进度与倒计时**；**不可见**内部处理人与内部考核。
- **不得**对业主展示任何人被扣分或处罚。

### 6.3 对象设计（扩展）

`CustomerFeedback` 增加字段：

| 字段 | 说明 |
| --- | --- |
| `priority` | Enum：Normal / High |
| `dueAt` | DateTime，按企业 SLA 计算 |
| `escalated` | Boolean |
| `escalatedAt` | DateTime |
| `escalationHandler` | Employee（BOSS） |
| `closedAt` | DateTime |

> **重要**：升级用**独立字段**而不是新增状态枚举值，避免 `GAP-054`（阶段状态 ENUM 缺值导致合同生效失败）那类事故。

`Company.setting` 增加 `feedbackSlaHours`（默认 48）。

### 6.4 状态机

```text
待受理 -> 处理中 -> 已关闭
              └─ 超时 -> escalated = true（status 仍为处理中，handler 变更 + 通知）
```

### 6.5 接口

| 路由 | 能力 | 说明 |
| --- | --- | --- |
| `customer/feedback/save` | 业主提交（既有扩展） | **业主写操作**（依赖 §0.3 前置） |
| `customer/feedback/update` | 处理/关闭（既有扩展） | 员工 |
| `customer/feedback/page\|info` | 查询（既有扩展） | 业主可见倒计时字段 |

### 6.6 定时任务

- 同 §3.6：RedissonLock + 批量 + 留痕 + 通知。

### 6.7 索引

- `(com_id, status, due_at)` ← 扫描用
- `(com_id, customer_id, create_date_time)`

### 6.8 风险

- 倒计时必须在**投影时按当前时间计算**（对齐订阅剩余天数口径：禁止落库递减值）。
- "升级"若被实现成对员工可见的处罚提示，会破坏 `BR-014` 与内部信任，必须避免。

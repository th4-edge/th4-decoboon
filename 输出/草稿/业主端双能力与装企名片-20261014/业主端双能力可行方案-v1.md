## 0. 一页结论

业主端不是一种能力，是**两种**：

```text
业务能力（管"事"）  我的家 │ 进度 │ 【历程】 │ 我的钱 │ 家档案     浅色 · 事实 · 待办 · 金额
价值能力（管"感"）        ↑ 底部中间凸起进入
                        暗色 · 历程 · 画面 · 记忆 · 感受 · 音乐
```

在这之上，还缺**第三块：对外的门面**——

```text
对外门面（管"传"）  装企名片（公开页）+ 分享落地链路
```

三块的分工：**业务能力留住业主，价值能力打动业主，对外门面把业主的好感变成装企的线索。**

## 1. 两条必须先说清的现实

### 1.1 现实一：装得清在业主端**藏不住**，也不用藏

| 事实 | 证据 |
| --- | --- |
| 微信小程序名称就是「装得清」 | `src/manifest.json` → `name: "装得清"` |
| 小程序 App 已被冻结为装得清主业务端 | `USER-DECISION-20261010-006` |
| 关于页标题就是「关于装得清」 | `src/pages/about/index.vue` |
| 小程序顶部胶囊、分享卡片、客服入口都会带出平台信息 | 微信客户端行为 |

所以「业主第一次登录就不可避免知道装得清」**不是失误，是既定口径**。

**结论：不要再试图隐藏，而要重新定义装得清在这段关系里的角色。**

| 角色 | 判断 |
| --- | --- |
| 服务提供者（抢"谁在给你装修"） | ❌ 装企最恐惧，也违反 `ANS-BIZ-20261010-004` §4 |
| **存证与保管方**（"这段记录是被系统存证的"） | ✅ **推荐**：对业主是安心，对装企是公信力背书，不抢客户关系 |
| 竞争者（在业主端推装得清自己的服务） | ❌ 绝对禁止 |

**可直接对业主说的那句话**：

> 「您家的这些记录，不是装修公司单方面保存的，是有系统存证的。」

这句话对业主是**信任**，对装企是**背书**，对装得清是**存在感**——三方都不难受。这才是"不可避免"的正确用法。

### 1.2 现实二：装企名片**对象层不存在**

| 检查项 | 结果 |
| --- | --- |
| `Company` 实体字段 | `comId / title / name / logo / color(品牌色) / size / addr / setting` |
| 企业对外简介、服务区域、主营、资质、对外联系方式 | **无** |
| `Company.Setting` | 仅 `enableStore`、`gradeConfig` |
| 企业名片 / 案例展示对象 | **无**（`content` 域 9 个对象里也没有） |
| 抖音 L2 已定义的核心功能 | 「**品牌/案例 → 预约量房**」（`ANS-BIZ-20261010-004` §3） |

**结论：装企名片在抖音 L2 已经定义了，微信端完全没有。** 这正好解释了你说的"业主推给好友时装企的名片带不进来"。

已有的两块拼图：
- `Company.logo` + `Company.color`（品牌色）→ **品牌元素可以自动带入，零配置**
- `content` 域的 `LeadTouch`（线索归因触点）→ 转介绍线索的归因钩子已有

## 2. 品牌与署名：正式分层口径

### 2.1 三层拆分（对应 `GAP-055`）

| 层 | 口径 | 依据 |
| --- | --- | --- |
| **数据** | 归租户企业 | `OBJ-001`、`DEC-060` §4 |
| **叙事主体** | 归装企：页面第一眼、讲述口吻、默认册名 | `ANS-BIZ-20261010-004` §4 |
| **容器** | 微信端 = 装得清主体（现状）；抖音 L2 = 装企自有主体 | `USER-DECISION-20261010-006`、`DEC-061` |
| **平台角色** | 存证与保管方（非服务提供者） | 本方案新增，待裁决 |
| **署名** | 默认仅"由 XX装饰 提供"；装得清署名以「记录存证方」形式出现 | `ANS-BIZ-20261010-004` §8 默认不显示 → 建议按 1.1 调整为"存证方" |

### 2.2 落位规范

```text
业主端页面内第一眼   →  装企（企业名 + Logo + 品牌色 + 设计师/项目经理姓名头像）
讲述口吻             →  "我们记录了您家的这 16 天"（第一人称是装企）
默认册名             →  "我家装修记"；企业可改 "XX装饰 · 我家装修记"
场景底部 / 关于页     →  "本页记录由 装得清 系统存证与保管"
分享卡片             →  装企名 + 装企 Logo 为主；装得清标识弱化在角标
```

### 2.3 硬边界

- **允许**：存证说明、技术支持说明、记录保管说明。
- **禁止**：在业主端出现装得清的产品推广入口、销售线索入口、订阅引导；禁止主动触达业主（除业主已授权的服务通知）。
- **研发强制**：品牌位做成配置（`brandPrimary` / `custodianCredit`），不得写死。

## 3. 装企名片：设计

### 3.1 定位

装企名片 = **面向陌生人的公开落地页**，是转介绍链路唯一的承接面。

它要同时回答三个问题：
1. 这是谁家装的？（装企是谁）
2. 这家的活怎么样？（能力与案例）
3. 我也想装，怎么联系？（留资入口）

### 3.2 页面结构（建议）

```text
① 品牌头     Logo + 企业名（品牌色）+ 一句话定位 + 服务区域
② 可信数据   成立年限 / 已完工户数 / 在施工地 / 服务保障 —— 均由企业后台自填并审核发布
③ 能力与资质 主营范围、施工标准、质保承诺（企业审核）
④ 案例展示   仅使用满足 BR-014 六条件的案例（真实 + 交付结果 + 企业审核 + 客户书面授权 + 脱敏 + 渠道期限匹配）
⑤ 与我有关   「您朋友家的装修实录」入口（脱敏、需业主开启）
⑥ 联系与预约 电话/微信/预约量房表单
⑦ 页脚       本页由 装得清 系统提供技术支持
```

### 3.3 强制门禁

| 门禁 | 规则 |
| --- | --- |
| **企业审核门禁** | 名片所有对外内容必须由 BOSS 审核发布（`BR-014`：BOSS 拥有最终审核、发布、撤回和删除权） |
| **案例授权门禁** | 禁止把任何业主项目自动变成案例；必须满足 `BR-014` 六条件，含**客户书面授权** |
| **不自动生成门禁** | ②③ 的数字与承诺**不得由系统自动推导**，必须企业自填自审（对齐 `BR-014`：AI 不能直接发布预算/工期/质量/售后内容） |
| **无跨租户门禁** | 名片只能引用本企业数据，不得出现任何跨企业对比、排行、评价 |
| **无平台推广门禁** | 名片页不得出现装得清的产品推广或销售入口（`ANS-BIZ-20261010-004` §5） |
| **撤回门禁** | 企业撤回或客户撤回授权后，名片对应内容立即失效 |

### 3.4 对象设计建议（待研发评审）

不新建大对象，先**扩展现有实体 + 一个新对象**：

| 载体 | 内容 |
| --- | --- |
| `Company` 扩展字段（或 `Company.setting` 内嵌） | 对外简介、服务区域、对外联系方式、名片是否开启、名片版本号 |
| 新对象 `CompanyCard`（企业名片实例） | cardId、company、title、logo、brandColor、intro、serviceArea、contact、publishStatus、reviewer、publishedAt、version |
| 复用 `ContentAsset` + `ContentAuthorization` | 名片上的图片与案例素材，走既有授权模型 |
| 复用 `LeadTouch` | 转介绍线索的归因触点（来源=业主分享、分享人、装企） |

> 注意：以上仅为**建议方向**，需先过业务裁决与选择器/表单评审门禁（`T15`/`T16`/`T17`），不得直接进入编码。

## 4. 分享与转介绍链路

### 4.1 现状缺陷（必须先修）

| 缺陷 | 证据 | 影响 |
| --- | --- | --- |
| 分享链接落地页强制登录 | `share.ts` 要求 path "对方未登录也能打开"；`journey.vue` `onLoad` 首句 `if (!isLoggedIn()) redirectToLogin()` | 家人/好友点开直接跳登录，**分享功能实际不可用** |
| 分享卡片资产缺失 | `share.ts` 注释：专用 5:4 分享卡片未补齐，当前用 Logo 兜底 | 分享出去不好看 |

### 4.2 目标链路

```text
业主在历程页点「分享」
├─ A. 分享给家人 → 亲友观看链接（脱敏 + 时效令牌）
│     · 默认可见：进度、阶段、照片、整改、未来安排
│     · 默认可关：金额（很多业主不想让父母知道花了多少）
│     · 无需登录，令牌过期即失效
└─ B. 分享给好友/邻居 → 装企名片落地页
      · 先看装企名片（公开）
      · 名片内可进入「朋友家的装修实录」（脱敏，需业主授权开启）
      · 留资 → 线索进【该装企】的租户主链
```

### 4.3 线索归属（关键）

| 项 | 口径 |
| --- | --- |
| 线索归属 | **该装企的租户主链**，不是 `SiteLead`（平台域） |
| 依据 | `ANS-BIZ-20261010-004` §5：禁止把 L2 装企业主线索写入平台域；禁止把 L1 装得清销售线索导入任何租户主链 |
| 来源标记 | 渠道 `Referral`（转介绍，枚举已存在）+ `LeadTouch` 归因（分享人、被分享人、时间） |
| 装得清可见性 | 仅做技术存证与统计口径，**不得读取、不得经营该线索** |
| 承接人 | 由装企指定（对齐 `BR-042` 内容任务的"线索承接人"字段） |

**这条链路是纯租户域的转介绍闭环，两端都不越界**——这是它最大的价值。

| 原诉求 | 改造要求 |

| 隐蔽工程 360 全景 | 可作为水电/防水阶段验收必须项；保留期与权属见 `GAP-056` |

| 一键报修连物业 | 只到装企售后 + 调出当年管线图；**不承诺连通物业** |

### 5.3 不能做（4 条）

| 诉求 | 原因 |
| --- | --- |
| 跨装企匿名避坑榜 | 违反租户隔离（`OBJ-001`）与 `DEC-060` §4；平台例外仅限跨企业只读；有对具体装企的名誉权风险 |

## 6. 业主自有数据域（`GAP-056`）

现状：`OBJ-001` 强制每个业务实体含 `Company company`，**制度上不存在"业主自己的数据"**。

无处安放的内容：自记装修账、入住感受、新家照片、装修日记、选材决策过程。

建议（最小定义，不做完整设计）：

| 项 | 建议 |
| --- | --- |
| 所有权 | 归业主本人 |
| 企业可见性 | 默认不可见；业主授权后可见 |
| 生命周期 | 企业停服 / 项目结项 / 业主换装企后，**数据跟业主走** |

| 对外使用 | 仍依次经过 `BR-042` 三层授权 |
| 明确不可归入 | 企业项目成本、账务、经营指标、跨租户对比 |

## 8. 业务能力侧植入「人」与「企业」（2026-10-14 追加）

### 10.1 原则：业务能力侧植入的是「人」，不是「宣传」

| 维度 | 对外门面（名片页 `p-visit`） | 业务能力侧（4 个 Tab） |
| --- | --- | --- |
| 目的 | **拉新**：让陌生人产生兴趣 | **服务**：让已成交的业主安心 |
| 内容 | 企业能力、案例、预约入口 | **责任人的身份、职责与联系方式** |
| 口吻 | 营销 | 服务 |
| 门禁 | `BR-014` 六条件（案例需授权） | 员工信息授权 + 企业审核 |

**不能混**：把"业绩宣传册"塞进业务能力侧，一是让业主觉得"我在被你推销"，二是**稀释掉"我的工地"这个主体**——
业主打开小程序是为了看自己家，不是为了看企业介绍。

### 10.2 现状缺口（已核代码）

| 检查项 | 结果 |
| --- | --- |
| 业主 journey 里出现的人 | 只有零散姓名：`量房设计师`、`整改责任人`、报告落款人 |
| "我的服务团队"概念 | **不存在** |
| `ProjectMember` 对象 | **存在**（数据基础已有），但**未投影给业主** |
| 业主可见的员工字段 | 仅 `Employee.getName()`——无头像、无岗位、无联系方式 |

**结论：业主在整个装修过程里，看不到"在跟谁打交道"。** 这是个不小的信任缺口——业主最基础的需求是"出事了我找谁"。

### 10.3 落点设计

```text
① 首页「管我这件事的人」   横滑人卡：头像 + 姓名 + 岗位 + 一句话职责 + 联系他
② 责任人详情（遮罩页）     从业年限 / 服务户数 / 擅长 / 服务承诺
                          + 「他为您家做了什么」（按时间倒序，来自既有 journey 事实）
③ 家档案「我的服务团队」   全部服务过的人（含施工班组）+ 谁做了哪一段
④ 家档案「服务方」         企业 Logo/名称/简介/联系方式 + 与本户相关的业绩
```

### 10.4 三条关键纪律

1. **员工信息一律企业自填自审**（姓名、头像、从业年限、服务户数、擅长、服务承诺），平台**不推算、不评分、不背书**。
2. **不做评分、不做排行、不做跨企业对比**——包括本企业内部的"评分榜"也要谨慎，它容易变成对内的施压工具。
3. **业绩只放与本户相关的**：显示「本小区已完工 12 户 / 同户型做过 7 户」，
   **不显示"累计 386 户"这类泛泛宣传**。理由：业主在已成交阶段关心的是"你懂不懂我这个小区、这个户型"，不是"你有多大"。

### 10.5 一个被忽略的真问题：换人不通知

项目经理、设计师中途换人时，业主端**目前没有任何机制**告知。
建议：成员变更必须**主动提示 + 留痕**（"您的项目经理由张伟变更为李强，生效日 X"），并保留历史成员。
这既是服务，也是装企的自我保护。

### 8.6 「服务主体知情权」口径（2026-10-14 用户确认原则）

用户口径原文：

> 「在业务能力侧增加企业信息，不是为了宣传——业主总要知道哪家企业在给他装修吧。」

**原则**：业主知道「**哪家企业 + 哪些人**」在为这一户服务，**不是宣传，是知情权**，是合同履行的基本事实。
企业信息与人员信息的露出动机是**知情**，不是**获客**；两者的门禁、口吻与落位因此不同。

按这个原则，人员信息分两层：

| 信息 | 是否露出 | 理由 |
| --- | --- | --- |
| 企业名称 / Logo / 品牌色 | **必须** | 合同相对方，业主有权知道 |
| 企业统一客服与售后电话 | **必须** | 业主的正式救济通道 |
| 员工姓名 | **必须** | 业主需要知道在跟谁打交道 |
| 员工岗位与职责 | **必须** | 业主需要知道该找谁 |
| 员工头像 | **建议**（员工可拒绝） | 提升识别度；属个人信息，需员工同意 |
| 从业年限 / 服务户数 / 擅长 / 服务承诺 | **企业自填自审，可选** | 企业提供的信息，非系统推算 |
| **员工个人手机号** | **默认不露出** | 见下 |

**关于个人手机号——给通道，不给号码：**

| 通道 | 落点 | 好处 |
| --- | --- | --- |
| 「在微信里找他」 | 企业微信群 / 企业微信客服 | 员工离职不影响；号码不外泄；合规 |
| 「打电话」 | **企业统一服务热线**（转接或留工单） | 业主随时能联系上人；装企不依赖个人号 |
| 员工个人号 | 仅在**员工本人选择公开**时露出 | 把选择权还给员工 |

理由：直露个人号会同时伤害三方——员工被私人时间打扰、装企被离职换号拖累（业主反而更找不到人）、
号码被转发后属员工个人信息外泄（关联 `BR-007` 工人档案敏感字段规则）。

**这条原则的另一面是变更告知**：既然业主有权知道是谁在服务，就同样有权知道它变了。
因此原第 15 条与原第 16 条应合并为**同一条口径的两面**：

```text
服务主体知情权
├─ 初始露出：服务开始时，企业与人员信息必须可见
└─ 变更告知：人员或企业主体变更时，必须主动提示并留痕
```

## 10. 不允许的理解

1. 不得把装企客户数据视为平台资产；`DEC-060` §4 不变。
2. 不得在业主端出现装得清的产品推广或销售入口。
3. 不得把业主项目自动变成装企名片上的案例；必须满足 `BR-014` 六条件。
4. 不得把转介绍线索写入平台域 `SiteLead`；必须进对应租户主链。
5. 不得由系统自动生成装企名片的对外承诺、数字与资质。
6. 不得对外宣称平台掌握装企客户数据，或"装企业主端是装得清的产品"。
7. 不得以"业主需求"为名新建跨租户数据通道。
